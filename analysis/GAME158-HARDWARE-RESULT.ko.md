# NES158 실기 — 새 주소 예측은 도달했지만 읽기 기회를 놓침

**SMB3 스테이지 진입은 여전히 실패했다. 새 CHR주소를 미리 예측하는158 수정은 실기 이력에 나타났지만, 해당 주소를 제때 읽는 데에는 실패했다.** 자동 메뉴 복귀와 두 TXT 회수는 통과했다. 같은158 재시험이나 추가 영상은 필요하지 않다.

## 실기에서 확인한 것

- 67/E1 식별, ROM393216바이트 적재·비교, verified1/오류0, 진행104개512바이트 기록의 순번과 시각 단조성 PASS.
- 최초 오류는 PPU 데이터 기한 오류2. line193/dot8, 물리주소 `217A18`, 상태 `60820800:28606060`으로 이전 실패와 같은 배경 상위 비트면이다. 문맥 `e200c2f4:30217a18`은 CPU유효0/요청age1로,157의 CPU유효1/age0과는 다르다.
- STOP 후 카운터20738302 유지, stop_error0, 기본FPGA·최종TXT·메뉴 준비 통과. 사용자의 실제 메뉴 복귀 보고와 영상도 일치한다. 게임 플레이는 실패이며 이동·점프는 확인되지 않았다.
- 패드5건은 `NONE → START → NONE → START → NONE`. 두 Start 수신·해제 구간을 확인했다. 물리 클릭 시각이나 모든 버튼 정상 판정으로 확대하지 않는다.
- 첨부14.83초 영상에서 로딩 표시, 커튼 애니메이션, 플레이어 선택 화면, 메뉴 복귀를 확인했다. 전체1fps 및 마지막 전환 구간8fps 표본을 확인했으며, 그 표본에서는 실제 스테이지 플레이 화면이 보이지 않았다. 정확한 버튼 클릭 시각·모든 영상 프레임·음성 내용은 분석하지 않았다.

## 실패 직전16클록

상대0은 최초 오류 클록이다. 주소는 CPU 명령 주소가 아닌 서비스의 물리 메모리 주소다. 요청·응답이 같은 행에 있으면 전송주소는 새 요청을 나타낸다.

| 상대클록 | 관측 | 의미 |
|---|---|---|
| -15~-13 | 현재 PPU `205A10`, 유효한 미래주소 `217A18`, 이전 PPU 읽기 진행 중, CPU필요1 | 새 주소가 실제 주소 변경 전에 서비스까지 도달했다. 최초 예측 발생은 기록 창보다 앞일 수 있다 |
| -12 | 이전 `205A10` 응답과 새 CPU `03C001` 요청이 동시에 발생 | 미래주소가 있어도 CPU 요청이 선택됐다 |
| -11~-8 | `217A18` 선행 조회 선택 조건1, reader ready0 | CPU 읽기가 진행 중이라 실제 선행 요청을 발행하지 못했다. -8의 낮은 비트면 샘플은 정상 |
| -7 | CPU 응답, dot7에서 hint_valid0, 실제 PPU는 아직 `205A18`; 이 옛 주소로 새 요청 | 읽기 경로가 비었을 때 미래주소 유효 구간이 끝나 실제 옛 주소가 선택됐다 |
| -5 | 실제 PPU `217A18`로 변경, 진행 중 요청은 `205A18` | 필요한 주소가 바뀌어도 이미 발행한 읽기는 계속 처리된다 |
| -2 | 옛 주소 응답 후 새 `217A18` 요청 | 새 주소 읽기를 시작했지만 샘플까지 두 클록만 남음 |
| 0 | dot8 샘플, 응답0/유효0 | 오류2로 보호 종료 |

157에서는 옛 상위 비트면 선행 읽기를 완료한 뒤 샘플 한 클록 전에 새 주소가 나타났다.158에서는 **새 주소 예측이 적어도15클록 전부터 보인다**. 따라서 증상이 같다고 내부 처리도 그대로였다고 판단하면 안 된다. 이번의 직접적인 관측은 예측 생성 이후, CPU 읽기·유효 구간 종료·옛 주소 요청이 이어지는 발행 순서다.

`nes_rom_service.sv`의 선행 조회는 `!ppu_need && !cpu_need && prefetch_need`일 때만 선택하며, reader가 받을 수 없으면 유효 구간을 넘겨 보관하지 않는다. 이 계약이 위 이력과 일치한다. 다만 현재 이력에는 raw CPU R/W, cart_pre, 매퍼 쓰기 값, CPU PC가 없어 `03C001` 요청의 명령 수준 원인까지 확정할 수 없다.

## 먼저 확인할 작은 수정 후보

실제158 소스에서 조기 CPU 읽기 자격은 `rom_cpu_address_valid=prg_addr[15] && prg_allow`다. 반면 `prg_write=mw_int && cart_pre`, MMC3의 ROM `prg_allow`는 `!prg_write`에 의존한다. 따라서 높은 주소에 **raw 쓰기 mw_int=1이지만 cart_pre=0인 선행 구간**에는 prg_write0/allow1이 되어 읽기 자격이 켜질 수 있다. 이 MMC3 어댑터의 `prg_conflict`는0이므로 버스 충돌 처리를 위한 ROM 읽기도 요구하지 않는다.

이는 소스에서 확인한 조건이며, 이번 실기의 `03C001` 요청이 반드시 이 조건에서 생겼다는 확정은 아니다. 그러나 중재 전체를 바꾸기 전에 확인할 구체적인 후보다. 다음 시험은 CPU 요청을 외부에서 강제로 넣는 대신 실제 `mw_int/mr_int → cart_pre/prg_allow → rom_cpu_address_valid` 연결을 살려 이 쓰기 구간의 불필요한 읽기 여부를 확인한다. 정상 CPU·DMA 읽기와 실제 샘플 기한을 보존해야 한다. 다른 매퍼의 버스 충돌 계약까지 같은 것으로 일반화하지 않는다.

158의 기존 합성 시험은 CPU 읽기와 샘플을 직접 강제했고 CPU 샘플을0으로 뒀다. 특정 쓰기 선행 관계와 앞선 읽기12종은 통과했지만, 이번 실기의 **낮은 비트면 응답 → CPU 점유 → hint 유효 종료 → 옛 뱅크 읽기** 순서를 다루지 못했다. 이 한계를 기록하고 동일 시험 통과만으로 다시 배포하지 않는다.

## 다음 작업

1. 실제 CPU 읽기 자격 연결과 위 순서를 짧게 재현한다. 매퍼 쓰기 구간의 불필요한 ROM 읽기가 확인되면 그 조건부터 최소 수정한다. 정상 읽기·DMA·PPU 낮은/높은 비트면 기한은 그대로 확인한다.
2. 정당한 CPU 읽기와도 같은 문제가 남으면, 유효 구간이 지난 선행 요청의 보관과 샘플 기한에 맞춘 발행을 검토한다. 단순히 PPU를 항상 우선하거나 오래된 뱅크 데이터를 반환하지 않는다. 원본의 메모리 시간 계약과 비교한다.
3. 변경 경계만 검증한 뒤 같은 SMB3 스테이지 진입·이동·점프 실기로 돌아간다. 새 매퍼 구현, 큰 캐시, 새 관측 틀, 무변경 전체 부팅 시험부터 시작하지 않는다. 현재 M9K56/56의 임시 이력은 원인 확인 뒤 축소한다.

펌웨어 시각 DISPLAY232920→240160ms는7.240초, 메뉴 준비243410ms는 종료 후3.250초다. 영상은 촬영 시작점이 다르고 화면 전송·메뉴 재적재가 있으므로 펌웨어 RUN 구간과 영상 시간을 동일시하지 않는다. screen_frames13/trusted0도 FPS 측정값이 아니다. 음원 채널 쓰기 차단은 유지됐으며 정상 오디오는 아직 미완료다.

이번에는 PR100에 결과와 다음 계획만 추가한다. 펌웨어·FPGA·패키지·frozen158 및 기존 공개 소스 핀은 변경하지 않는다.044/GBC 복원이나 같은158 재시험은 요구하지 않는다.
