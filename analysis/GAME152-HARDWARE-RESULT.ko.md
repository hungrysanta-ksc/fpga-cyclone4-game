# NES152 실기 — 월드맵 전환 후 정지, 오류 문맥 수신 결함 확인

**제목 뒤 WORLD 1 시작 안내가 겹친 월드맵까지 표시됐으나 이후 화면이 정지했다.60초 이상 기다려도 메뉴 복귀가 없고 최종 TXT도 만들어지지 않았다.152 재시험은 불필요하다.** 실제 배포 C 코드에서 새 PPU 주소 표식과 기존 수신 검사의 불일치를 확인하고 재현했다. 이 결함은152 제작 시 연동 검사를 빠뜨린 개발 측 누락이다.

## 영상·사용자 관찰

영상 길이는94.13초,720×1280,평균 약29.96fps다.2Hz로 프레임을 추출하고 초반0~21초1초 간격 및20~90초5초 간격 표본,15/16초 원해상도 장면을 확인했다. 약9~10초부터 화면 전환,11~13초 커튼·바닥,14~15초 제목/플레이어 선택,15~16초부터 WORLD 1/MARIO×4 안내가 겹친 월드맵이다. 이후90초대까지 같은 구도를 유지하며 실제 스테이지 플레이는 확인되지 않는다. CRT 촬영 띠는 동작 변화로 보지 않는다.

사용자는14초경Start를 한 번 눌렀고 이후 추가 버튼에도 오브젝트가 움직이지 않았다고 보고했다. 버튼 음성의 별도 자동 전사는 하지 않았으며 입력 시각·횟수는 사용자 설명을 근거로 구분한다. 제목→월드맵 전환은 입력 반응과 부합하나, 실제 패드 상태·누름/뗌 시퀀스가 없어 **중복 입력을 확정하지 않는다.** 현재는 한 프레임을30vblank 유지하므로 중간 화면이 건너뛰어 보일 수 있고, 한 번 길게 유지된 상태가 여러 화면 단계에서 소비됐을 가능성도 남는다.1회 누름=2회 독립 입력으로 바로 등치하지 않는다. 멈춘 뒤의 무반응으로 나머지 버튼 전체를 고장 판정하지 않는다.

사용자 추가 확인: 프리즈 뒤60초 이상 기다렸지만 자동 복귀하지 않았다. 본체 리셋으로도 메뉴가 안 나왔고 전원 온·오프 후 메뉴가 나왔다. 영상에서도 실행 시작 후 약80초 이상 동일 장면이 보인다. 촬영 초반9~10초를 전체 ROM 적재 시간으로 해석하지 않는다.

## 진행 로그

83기록(seq0~82)이 연속으로 남았다.393216바이트 LOAD 마지막95130ms, CHECK 마지막232730ms를 지나 최종 기록은 `DISPLAY_NEXT elapsed_ms=232740`이다. 코드상 전량 검증을 마치고 RUN 명령을 보내기 직전에 기록하는 지점이다. 영상은 이후 실제 화면 실행을 뒷받침한다.

`DISPLAY_STOPPED`,STOP,BASE,메뉴 준비 기록이 없고 `nes-game-last-152.txt`도 미생성이다. 이 설계는 RUN 중 SD를 쓰지 않고 종료 후 기록하므로 **DISPLAY_NEXT가 마지막이라고 그 지점에서 실행이 멈췄다는 뜻은 아니다.** 실제 RUN 오류 코드·카운터·새 PPU 요구 주소는 확보하지 못했다.151의오류2/주소0x217A18을152에도 그대로 적용하지 않는다.

## 확정된 펌웨어 결함

152 FPGA 서비스는 PPU 샘플 실패 때 fault_context bit63=1을 기록하도록 바뀌었다. SPI71의hi[3] bit7이 이 비트다. 그러나 같은 패키지 MCU의 `context146()`에는 이전 형식의 `(hi[3]&0x80u)` 거부 조건이 남아 있었다. 엄격한62/DC 식별은 바꿨지만 문맥의 의미 변경을 수신 검증에 반영하지 않았다.

PPU 오류→observe→context146 거부→nes_cf86_fail094 경로가 가능하다. fail094는SNES RESET을 잡고 세션/복귀 오류 상태를 설정한다. 이후cleanup은STOP/base 재적재를 건너뛰며, 최종 보고도BLOCKED_RESET_HELD/persist=false 경로여서SD TXT를 저장하지 않는다. 따라서 멈춘 그림·최종TXT없음·RESET버튼으로도복귀안됨이라는 관찰과 부합한다. **이번 실제 실기에서 이 분기를 탔다는 오류 원문은 없으므로 현상 원인으로는 강한 후보, 코드 결함 자체는 확정**으로 구분한다.

실제 배포 `nes_run136.inc`의run136/context146 전체를 가져와 전송·guard·대기·STOP만stub으로 바꾼 호스트 재현을 실행했다. 합성한 유효 tagged PPU 오류 응답을 넣은 결과:

| 대상 | fail | display leave | STOP | DISPLAY_STOPPED | 문맥 저장 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 배포152 그대로 | 1 | 0 | 0 | 0 | 0 |
| bit63 거부 한 조건만 제거한 대조 | 0 | 1 | 1 | 1 | 1 |

태그0 기존 형식과 잘못된ID·valid·오류번호3개 거부도 확인했다. 대조는 비공개 호스트 실행용이며 새 펌웨어를 배포한 것이 아니다. 실제 게임 PPU 원인 재현·실기 복귀 검증도 아니다. 첫sandbox host GCC 실행은DLL 매핑 오류로 시작하지 못했고, 허용된 호스트 실행에서 통과했다. 라이선스 문제가 아니다.

## 다음 작업·검증 누락 방지

1. 다음 후보에서 새 주소 형식을 MCU 수신에 반영한다. 기존152 동결 소스와 ZIP은 수정하지 않는다. 같은FPGA·배치·게임표시를 재사용할 수 있으므로 이 수신 수정만을 이유로 FIT/전체부팅을 반복하지 않는다.
2. 실제MCU 함수에 **tagged PPU 오류→문맥수신→정상 오류STOP→최종보고 저장·메뉴 복귀 경로**를 연결한 시험을 추가한다. FPGA가 새 필드를 쓰는 단위 시험과 ARM 링크만 각각 통과한 것을 연동 검증으로 취급하지 않는다. 잘못된ID·응답·guard 거부는 유지한다.
3. 같은SMB3 한 번의 실기에서 실제오류주소를 확보한다. 그 결과로 PPU 요청/주소변경/응답기한과 Start 누름·뗌을 분리해 진단한다. 게임을 처음 멈춘 오류 자체와 그 뒤의 복구 실패는 별도 문제다. 같은152/044/A-B 재시험은 요구하지 않는다.
