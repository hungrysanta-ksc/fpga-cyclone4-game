# NES150 첫 실제 게임 실기 결과

**384KiB 적재·전량 대조, 유한 RUN·STOP, 로그와 실제 메뉴 복귀는 통과했다. SMB3 게임 화면 표시는 실패했으며 입력은 미확인이다.** `run_passed=1`은 관측한 실행 활동과 오류 조건의 통과이지 게임 내용의 정확성 판정이 아니다. 이번 기록은 기존150 시험 결과만 추가하며 펌웨어·RTL·패키지는 변경하지 않는다.

## 관측한 결과

사용자는 실행 약5~6분 뒤 점멸이 시작되어 약1분 지속됐으며 메뉴로 정상 복귀했다고 보고했다. 제공 영상은9.67초이고 종료 구간을 담았다. 10Hz로97개 프레임을 추출하고, 0.3초 간격33개와 대표 확대 화면을 검토했다. 초반에는 밝고 거의 균일한 화면으로 게임 그림을 식별할 수 없고, 약3.5초부터 어두운 화면, 약7초부터 정상 메뉴가 보인다. 촬영 주기·노출과 CRT 주사 때문에 이 샘플에서 실제 점멸 주파수나 표시 FPS는 산출하지 않는다. 대각선 띠는 기존 사용자 설명대로 촬영 간섭으로 제외한다. 약1분 전체 점멸은 사용자 관찰이며 영상 전체 길이와 혼동하지 않는다.

두 TXT는60/DA 식별, loaded/compared=393216, verified/end_accepted=1, run_passed=1, run_error/rom_error/first_error/stop_error=0, stop_ok/base_restored=1이다. RUN 관측 카운터는148922→174088630→174089528로 증가했다. 이는 정지 상태만은 아니라는 근거지만 CPU 명령의 정답·PPU의 게임 내용·60초 전체 게임 로직을 검증하지 않는다. ROM 응답 기한 오류가 없다는 사실도 모든 전기적 여유나 모든 RUN 데이터의 정확성을 보장하지 않는다.

`screen_stage=112`, `screen_frames=47`, `screen_phase_mask=8`, **`screen_telemetry_trusted=0`**를 원본 그대로 보존한다. 새 SNES 클라이언트가 쓰는 단계1/2/3/5/6과112가 맞지 않으며, 이 표식으로 DMA 완료·화면 정상·47FPS를 주장하지 않는다. 로그의 마지막 `MENU_PREPARED_RESET_HELD` 이후 실제 복귀는 사용자와 영상으로 확인했다.

## 소요 시간

진행104개 기록(seq0~103)의 firmware `elapsed_ms` 기준이다. 파일 선택부터 측정했는지와 실시간 보정이 확인된 외부 초시계 측정은 아니므로 사용자 체감5~6분을 잘못된 관찰로 바꾸지 않는다.

| 구간 | 로그 시각(ms) | 소요 |
| --- | --- | --- |
| LOAD 0→393216 | 2890→95120 | 92.230초 |
| CHECK 0→393216 | 95140→232730 | 137.590초 |
| ENTRY→DISPLAY_NEXT | 0→232740 | 232.740초(3분52.740초) |
| DISPLAY_NEXT→DISPLAY_STOPPED | 232740→293390 | 60.650초 |
| ENTRY→MENU_PREPARED | 0→296550 | 296.550초(4분56.550초) |

적재+대조 합계229.820초가 대기의 대부분이다.149 하드웨어 SPI가 적용돼 기존146의80KiB/518.990초보다384KiB를 더 짧게 처리했지만, 바이트별 명령·전량 대조 비용은 여전히 크다. 게임 자체가 원래 수분을 필요로 한다는 뜻은 아니다. 검증을 근거 없이 생략하지 않으며 전송 개선은 화면의 첫 차단 문제와 구분한다.

## 원인 판단과 다음 작업

확정된 구조상 비용은 SNES가 매번57344바이트를 forced blank 중 DMA하고 다음 vblank에 표시한다는 점이다. 따라서 점멸·낮은 표시 갱신률에 기여할 수 있다. 그러나 **밝은 화면에 게임 그림이 보이지 않는 현상까지 정상으로 취급할 근거는 없다.** 단순 FPS 조정만으로 해결된다고 보지 않는다.

남은 후보는 실제 PPU 출력 자체의 문제, 프레임 캡처·공개/반환 문제, 물리 SNES 읽기/DMA·VRAM·팔레트 전달 문제다. 현재 증거로 어느 하나를 확정하지 않는다. 기존 client03은 모델이 공급한 바이트를 실제 SNES CPU/DMA/PPU로 표시했고, video02는 저장된30번 프레임을 FPGA RTL로 재생했다. 두 통과를 보드에서 동시에 동작한 게임 경로의 통과로 합치지 않는다. 기존30번 프레임은 붉은 커튼과 하단 무늬가 있는 초기 장면이며 현재 밝은 영상과 다르지만, 촬영 시각이 다르므로 동일 프레임 비교나 독립 게임 정답은 아니다.

다음 작업은 같은 SMB3의 실제 픽셀·프레임 전달 경계를 우선 확인한다. 최소한의 PPU 원본/고정 버퍼 요약과 SNES 수신 결과를 대조해 최초로 달라지는 위치를 찾고, 필요하면 실제 게임 한 프레임을 잠시 유지해 점멸에 가려지는지 확인한다. 관련 버스 시험은 기존270ns 샘플 가정과 실제 DMA 읽기 구간을 대조한다. 이 가정 자체를 실측 성공으로 간주하지 않는다. RUN 중 SD 쓰기를 추가하지 않고 필요한 요약은 안전한 STOP 후 저장한다. 전체 진단 체계·A/B 패턴·동일30프레임·044복원 반복을 새 선행 조건으로 만들지 않는다. 게임 화면이 식별된 뒤 Start·이동·점프와 연속 갱신을 확인한다.

원본 TXT·영상은 비공개로 보존하고 [검증 메타데이터](game150-hardware-verification.json)에 파일명·크기·SHA256·원시 로그 필드·진행 기록과 판정을 남긴다. 기존150 frozen4235파일 및 패키지 해시, GBC/NES 원본과 이전 public pin은 유지한다. [150 구현 결과](GAME150-RESULT.ko.md) · [현재 인계](../cores/nes/HANDOFF.ko.md).
