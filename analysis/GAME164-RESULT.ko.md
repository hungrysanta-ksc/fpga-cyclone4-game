# NES164 — 반복 화면 소거 제거용 실기판

PR105 머지 `6f0457d167a15ee7e3d0aecfa68e745fd426eb1f`를 확인했다.163의 사운드·플레이 성공을 유지하고, 첫 게임 화면 이후 반복되는 전체 화면 소거를 제거했다. **구현과 모델 검증·실기판 준비는 완료했다. 실기 점멸 제거는 미확인이고, 부드러운 연속 화면 목표 전체는 아직 미완료다.**

## 화면 전송 변경

163은 매번 강제 블랭크 상태에서57344바이트를 전송하고 화면을 켠 뒤6번의 수직 공백을 기다렸다. 이 구조에서는 프레임을 더 자주 보내려고 hold만 줄이면 화면 소거도 더 자주 보인다.

164는 첫 프레임만 기존 전체 전송으로 초기화한다. 이후에는 화면을 켜 둔 채 **5632바이트×10회+1024바이트×1회**를 각각 별도의 수직 공백에서 전송한다. 마지막 바이트 전송 뒤에만 FPGA의 동결된 프레임을 해제한다. DMA 소스는 기존처럼40뱅크 안에서 주소가 순환하고 VRAM 목적지는 자동 증가한다. 매번 소스·VRAM 시작 주소를 초기화한다. 새 프레임 대기 중과 매 전송 뒤에도 패드를 읽으며, auto-joy 대기는 큰 DMA 뒤에 둬 수직 공백 시작 시간을 확보했다.

전체 그림은11번에 걸쳐 교체되어 위아래에 이전·새 장면이 섞일 수 있다. 전체 프레임 갱신이163보다 빨라졌다는 뜻도 아니다. 이 단계의 목표는 검정 점멸을 없애는 것이며, 아직60fps·전체 화면 동시 교체·입력 유지 문제 해결을 주장하지 않는다. 초기 준비 중 검정 구간은 남는다.

SNES VRAM64KiB에서 현재8bpp 그림 하나가57344바이트를 쓰므로 동일 크기2면을 단순 추가하는 방식은 맞지 않는다. FPGA도 LAB3/M9K0 여유로 대용량 버퍼를 더 넣기 어렵다. 따라서 이번에는 기존 픽셀·색상·해상도를 유지하며 화면 소거부터 제거했다. 이후 전체 갱신 속도를 높이려면 실제 게임의 변경 영역·타일 재사용 등 전송량을 줄이는 접근이 필요하다. 그 별도 설계를 이번 실기 전에 확대하지 않는다.

## 최소 검증과 재사용

- 실제 SNES CPU/SPC를 실행하는 NTSC Mesen에서 새 프레임 준비를3·17프레임 지연시킨2조건을 확인했다. 각 조건에서2개 RGB 화면이 기존 기준과 바이트 단위로 같다. Mesen 캔버스는256×239로 총244736픽셀, 활성256×224 그림은 총229376픽셀이다.
- 화면을 켠 이후 모든 VRAM 쓰기와 소스 읽기가 수직 공백 안에 있었고, 가장 큰 DMA의 마지막 읽기는259번 줄이었다. 이후 입력 읽기도 같은259번 줄이다. 이는 모델 관측이며 실제 보드 여유의 독립 측정이 아니다.
- 프레임을 끝까지 읽은 뒤 해제했으며 주소 순환·전송량을 확인했다. 첫 표시 이후 모든 프레임에 패드 폴링이 있고 입력은 각각17·31회였다. 주입한 DOWN 유지값·변화값은 그대로 전달됐다. 실제 컨트롤러부터 NES 소비까지 입력 유지가 해결된 증거는 아니다.
- 기존163 클라이언트를 같은 검사에 넣으면 첫 표시 이후 다시 화면을 끄는 동작이 거부된다. 본체 사운드 초기화는 두 정상 조건 모두A9다. SPC 생성기는163과 정확히 같고 기존 실패 주입 근거를 재사용했다.
- MCU는163→164 파일명·식별 문자열/함수명만 바꿨다.1393개 준비 입력의 동일성 또는 정확한 이름 치환을 확인해163의 상태 RTL54사례·host 회수13사례·입력 포맷256마스크 검증을 재사용했다. 같은 시뮬레이션·전체 적재를 반복하지 않았다.
- 새 ARM은188828바이트이며 강한NMI·15stores/0calls·기존 안전 회수 연결을 다시 검사했다. FPGA는 generated MIF를 검증 교체하고 update_mif→ASM/CPF만 수행했다.47개 로직·설정·배치/타이밍 보고서가163과 같다. 새 MAP/FIT/STA는 없다.

자원14711LE/5572regs/960·963LAB/56·56M9K/122핀/1PLL과 setup+0.121ns/hold+0.177ns는162의 동일 배치 재사용 값이다. 전체IO·MTBF·PCB2ns·reset recovery 한계도 유지한다.6B/E5 식별과A9 상태는164 고유 식별이 아니므로 실기 적용 시 펌웨어·FPGA를 함께 복사해야 한다.

초기 검사에서 Mesen 캔버스 높이를224로 오인한 실패, 게임 코드와 무관한 기존판 대조군의 검사 종료 처리 오류, ARM objdump의 샌드박스 DLL623 오류를 보존했다. 최종 client05는 수정된 검사기를 고정해 두 정상 조건과 기존판 거부를 통과했다. 앞선 client04 도중 검사기 실패 처리 줄이 변경돼 최종 근거는05로 통일했다. 실제 펌웨어 소스 수정 실패나 라이선스 오류로 기록하지 않는다.

## 실기와 다음 단계

`NES GAME 164.nh1`로 실제 SMB3 첫 레벨을 실행해 반복되는 전체 검정 구간이 없어졌는지, 소리 유지·이동/점프·메뉴 복귀를 확인한다. 새 패키지는 아직 실기 미확인이다. 부분 갱신·전체 프레임 지연은 남을 수 있으므로 짧은 영상과 두164 TXT로 분리 판단한다. 적재 절차·60초 예산은 그대로다.
