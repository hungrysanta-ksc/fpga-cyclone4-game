# NES144 결과 — 읽을 수 있는 NES 그림으로 실기 전진

## 목표와 완료 범위

143의 A/B/C/D 화면 비교와 자동 메뉴 복귀를 사용자가 확인했다. [실기 기록](SCREEN143-HARDWARE-RESULT.ko.md)을 반영하고, 무작위 무늬를 고장으로 취급하던 조사 대신 읽을 수 있는 NES 그림으로 진행했다.

144는 `NES 144` 글자·테두리·색 막대와 A/B 표시를 기존 NES→NCR1→SNES 전송 경로에 넣는 시험판이다. 제작과 로컬 검증은 완료했고 실기 결과는 대기 중이다. 게임·입력·오디오 완료를 의미하지 않는다.

## 구현

- NES PRG 64KiB와 iNES 헤더는 143과 동일하다. SHA 기반 무작위 CHR 16KiB만 직접 작성한 글자·테두리로 교체했다. 기존 NES 프로그램이 순차 타일을 쓰고 MMC3 CHR 뱅크0/8을 전환하므로, 위아래로 반복되는 `NES 144 A/B` 그림이 나온다. fine-X 1픽셀도 유지한다.
- SNES 프로그램은 이미 통과한 단색·직접 타일·ROM 비교 구간을 생략하고 새 atlas를 적재한 뒤 기존 NES 패킷을 표시한다. SNES가 별도로 완성 그림을 그려 놓는 대체 경로를 추가하지 않았다.
- MCU는 144 파일명·버전·새 진단 ROM CRC를 엄격히 확인한다. 기존 600×50ms 관측, RUN/STOP·오류 처리·SD 기록·메뉴 복귀를 유지한다. 기존 FPGA RTL·배치·프로토콜 ID 5E/D9는 동일하며 새 ROM/MIF와 ASM만 갱신했다.
- 143의 단계 기록 불일치 때문에 `screen_telemetry_trusted=0`을 명시한다. 원시 stage/mask/frames는 보존하되 그림의 성공 조건으로 사용하지 않는다. 이는 관측기 자체를 고쳤다는 뜻이 아니다.

## 검증과 의미

현재 선택된 CPU/PPU·ROM service/cache·reader RTL로 변경된 CHR를 한 위상에서 실행했다. NES 4프레임 245,760픽셀, fetch 65,552개, 실제 전송 8,032바이트가 통과했다. 패킷 복원과 NES 출력이 같으며, 독립 공간 기준으로 글자 위치·색·fine-X를 대조했다. 선택된 CHR 뱅크는 A/B/A/B였다. 테스트벤치는 124의 기존 수송·70ns RAM 모형을 재사용하며 실제 보드 전체를 동시에 시뮬레이션한 것은 아니다.

이 실제 RTL 패킷 3개를 SNES 에뮬레이터의 65816/PPU/DMA 프로그램에 공급해 183,552픽셀을 정확히 대조했다. 길이·헤더 오류도 각각 검출했다. 기준 PNG는 이 실제 에뮬레이터 출력에서 만들었다. 원래 MCU 소스의 호스트 21사례, ARM NMI와 소스 일치, 새 ROM 65,536주소 버스 검사, ROM/MIF 24,576바이트 대조, 압축 FPGA 역변환, ZIP 13개 항목 해시도 통과했다.

같은 FPGA 회로의 배치·같은 클록 setup +0.185ns/hold +0.150ns와 기존 조건부 외부 IO 근거를 재사용한다. 변경 없는 MAP/FIT/STA·전체 적재 검증·여러 위상 전체 코어 검사는 반복하지 않았다. 전체 외부 IO·MTBF나 보드 실측 승인으로 확대하지 않는다.

## 단계 표식 문제를 다룬 범위

143 실기에는 stage112(0x70), mask8이 남았지만 A/B/C가 사진으로 확인됐다. 기존 관측기는 쓰기 구간에서 처음 안정된 데이터 쌍을 잡은 뒤 그 쓰기 동안 다시 잡지 않는다. 테스트에서 WR 이후 데이터가 80ns 늦게 도착하도록 주면 목표0x63 또는0x31 대신 이전 값0x70을 잡는 현상을 재현했다. 지연 없는 대조는 정확한0x63을 기록했다.

이는 실기 관측값과 맞는 가설을 지지하지만 실제 보드 입력 지연을 측정한 것은 아니다. 정확한 실기 원인과 해결은 미완료다. 디버그 관측만을 위해 검증된 표시 회로를 다시 배치하지 않았고, 이번 통과 여부는 실제 그림·실행 오류·자동 메뉴 복귀로 판정한다.

## 시행착오 보존

첫 CHR 작성본은 뱅크 선택 묶음을 잘못 나눠 A/B를 구별하지 못할 구성이었다. bank//2로 고친 fixture02/client02를 선택했으며 초기본은 보존했다. RTL 실행은 첫 회에 통과했으나 후처리가 그림을 픽셀마다 다시 만드는 비효율이 있었다. 해당 작업의 Python 프로세스만 중단하고 저장된 결과를 수정한 검사기로 확인했다. 그로 인한 wrapper 종료1은 RTL·라이선스 실패가 아니다. 시뮬레이션을 다시 실행하지 않았다.

초기 샌드박스 호스트 ID 조회 실패는 같은 승인된 FLOAT 래퍼를 실제 호스트에서 실행해 해결했다. 새로운 라이선스나 라이선스 내용 수정은 없었다. 과거 동결 자료는 변경하지 않았다.

공개 소스 해시 검사에서 CRLF와 Git LF 변환 차이가 검출돼 다섯 텍스트 파일의 개행만 통일했다. 최초 동결본과 패키지는 보존하고 최종 `evidence-final`/`release02`를 만들었다. 코드 의미·ROM·펌웨어·FPGA 바이트는 같고 안내 문서 개행만 패키지에서 바뀌었다.

## 다음 작업

[144 안내](../docs/nes-screen144-instructions.ko.md)에 따라 한 번 실행한다. 두 TXT, 글자를 읽을 수 있는지와 A/B 관찰, 자동 메뉴 복귀를 받는다. 기존 약9분 적재 뒤 약30초 표시이며 전체 관찰 기준은 최대10분이다. 이미 통과한143/044/GBC를 반복하지 않는다.

읽을 수 있는 NES 영상이 확인되면 패드 반응 연결로 진행하고, 첫 게임 SMB3(J)의 mapper4·384KiB 이미지 지원과 플레이·오디오 범위를 순서대로 확장한다. 제한된 진단 fixture를 상용 게임 호환 완료로 간주하지 않는다. 141 ACK16ns 실패, E1/E2·8µs·양 클록 정지 CE9µs·source-lock4·124 격리는 유지한다.
