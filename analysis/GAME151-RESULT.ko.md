# NES151 쓰기 종료 수신과 실제 게임 화면 유지

## 작업 목표

PR92는74f94640f7ee0e24cb971db565fd485a1562688f로 머지됐다.150 실기에서 적재·RUN 활동·메뉴 복귀는 성공했으나 게임 그림 없이 점멸했다. 다음 시험은 동일 SMB3로 진행하며, 화면 갱신을 막을 수 있는 쓰기 수신 문제를 최소 경계 검사로 고친다. 사용자가150의 체감5~6분을 철회했으므로 그 차이를 원인이나 성능 근거로 사용하지 않는다. 다음 실측은 실행→첫 화면→메뉴 복귀로 나눈다.

## 작업 내용

150 소비자는 /WR이 내려간 초기의 데이터를 한 번 잡았다. 상태 관측도 같은 초기 구간에서 stable한 값을 잡았다. 데이터가 나중에 바뀌면 안정됐다는 이유만으로 초기 버스값을 잘못 채택할 수 있다. 프레임 반환 주소00:6000에서 A5를 놓치면 ready가 계속 켜진 첫 프레임을 재전송하고 NES 코어 자체는 계속 돈다.150의 stage112(0x70)도 상태 주소00:7000의 초기값을 넣은 모델과 일치한다. **초기값이 실제 보드에서 어디서 왔는지, 이것이 실기 원인인지까지 확정한 것은 아니다.**

151은 동기화된 /WR 종료를 검출하고, 직전의 주소·데이터·읽기 상태 튜플을 사용한다. 이 튜플은 raw /WR이 낮았던 마지막 호스트 샘플이다. 수신 트랜시버가 raw /WR 종료와 함께 꺼져도 뒤의 무효 데이터를 명령으로 쓰지 않는다. 프레임 반환·패드·단계 표식에 적용하며 reset은 진행 중 쓰기를 취소한다. 읽기 경로와 프레임 메모리, CPU/PPU/MMC3/PSRAM reader·loader는 변경하지 않는다.

SNES 클라이언트는 실제 게임 화면을30 vblank 유지한 뒤 반환한다. 이후 현재 게임의 다음 완성 프레임을 받으며 게임 CPU/PPU는 멈추지 않는다. 약0.5초 유지로 첫 게임 그림 확인을 쉽게 하며, 전체57344바이트 DMA의 짧은 검정 구간은 남는다. 이는 의도적인 낮은 표시 갱신률이고60fps 구현이 아니다. 입력도 화면마다 갱신하므로 시험 중 버튼을 약1초 유지하도록 안내한다.

새 식별은61/DB다. MCU는150 대비 후보명·식별만 바꾸며 기존393216바이트 적재·전량 대조·60초 RUN·STOP/base/menu·강한NMI 경로를 그대로 사용한다. SPI 명령60과 크기0x60000은 바꾸지 않는다. 화면 표식의 자동 신뢰 불가 판정도 유지하며 물리 확인 전 성공/FPS로 승격하지 않는다.

첫 FLOAT 실행은 샌드박스의 호스트 식별 조회 제한으로 wrapper 선검사에서 중단됐고 기존 승인 FLOAT를 호스트 권한으로 실행해 실제 시험을 통과했다. 새 라이선스 문제로 해석하지 않는다. 첫 ARM 검사도 샌드박스의 objdump DLL 로딩 실패로 중단되어 읽기 전용 검사를 호스트 권한으로 통과했다. 로그 취합 도구의 UTF16 로그를 기본 인코딩으로 읽은 실패는 보존하고 같은 실행 원문을 올바르게 읽었다. 기능 시험 실패를 숨기거나 다시 돌려서 덮은 것이 아니다.

수정·시험판 준비 목표를 달성했고 실기 해결 여부는 미확인이다. 기존150의 적재·복귀 성공은 보존하지만 새151의 게임·입력·복귀는 사용자 시험으로 확인한다. 전체 게임 정답, 지속 저장, 오디오, 색 강조, 정상 속도 화면, 기존IO/MTBF/양클록 정지 제한은 미완료다.

## 작업 의미

실제 게임 화면 갱신을 위한 제어 배선 수정이다. 진단 체계를 확대하기보다 관찰된 정지 화면과 맞는 기존 수신 결함을 재현해 바로 고쳤다. 다음 목표는151에서 마리오 그림·Start/이동/점프·메뉴 복귀를 확인하는 것이다. 해결되지 않으면 같은 게임의 PPU 원본/고정 버퍼와 물리 SNES 수신 결과를 최소한으로 비교한다. A/B 패턴,변경 없는30프레임·전체적재·044복원을 반복하지 않는다.
