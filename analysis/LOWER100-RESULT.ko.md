# NES100: 실제 SRAM·SPI 연결과 오류 후 칩 선택 차단

기존 SPI 오류 뒤에도 FPGA 칩 선택을 다시 내릴 수 있던 매크로를 수정했다. SRAM 접근과 FPGA 명령을 실제 STM32 SPI 함수까지 연결해 단위13·main 통합21경우, 보호 제거 대조5개를 검증했다. 같은 수정의 ARM 링크도 확인했다. 이번 소프트웨어 하위 SPI 연결 범위는 완료했으며 물리적 전송 종료와 나머지 주변장치 검증은 남아 있다.

PR49는 `2026-10-08T13:08:01Z`에 병합됐으며 master `13118bdb15df113fe8e68df00f99344840fccbbd`가 기존 head를 포함함을 확인했다.

## 발견과 수정

원본 `FPGA_SELECT()`는 `spi_tx_sync()`가 진단 오류로 반환해도 CS를 LOW로 만들었다. `FPGA_SELECT_ASYNC()`도 공유 오류를 확인하지 않았다. 원본099를 사용한 대조에서 기존 SD CRC 오류 뒤 SRAM 호출이 새 칩 선택을 만드는 것을 검출했다. 이 결과는 소프트웨어 경로의 결함이며 과거 사용자 실기 장애의 원인으로 단정하지 않는다.

진단 중 두 매크로는 공유 오류가 있으면 CS를 내리지 않도록 변경했다. 동기 select는 SPI 동기화가 새 오류를 만든 경우도 확인한다. deselect의 CS HIGH는 진행 중이던 선택을 종료하는 정리 동작으로 유지했다.

SPI BSY/TXE/RXNE 대기와 FPGA READY 대기는 매 반복에서 기존 공유 예산과 최초 오류를 확인한다. RX FIFO를 비우는 루프도 공유 보호를 검사한 후 DR을 읽는다. 개별25tick/1,000,000poll과 메뉴·보고서 공유 예산 중 먼저 끝나는 조건을 사용한다. 이전 오류를 덮거나 예산을 다시 시작하지 않는다.

생산 변경은 `stm32f4xx/spi.c`, `fpga_spi.h`, VERSION 세 파일이다.099 RTC,098 메뉴 주소 수정, main, memory, fpga_spi 명령 함수, native SD, CF86 전송 코드는 그대로다. 진단 비활성 분기의 원래 SPI 동작은 유지했다. 일반 경로의 명령별 CPU 사이클이나 이번 보드 GBC 플레이를 새로 측정한 것은 아니다.

## 실제 실행 범위

기존099 호스트의 SRAM 즉시 응답과 FPGA 설정 함수 모델을 제거하고 다음 본문을 연결했다.

- 실제 main의 기존 두 복귀 구간과 전체 load_rom, cfg/status/fileops,099 RTC, FatFS/native SD.
- memory의 byte/long/block read/write와 memset 7개 본문, fpga_spi 설정 함수16개 본문, STM32 SPI 함수9개 본문을 원문 그대로 추출·컴파일했다. 진단 및 단위 시험이 호출하는 분기를 실행했으며 모든 레거시 분기를 실행한 것은 아니다.
- FPGA 매크로와 CMSIS SPI 비트 정의를 사용했다. 상태/DR/CS와 메모리 응답은 모델이다. DR 접근을 바이트 모델로 치환하고, 미실행 DMA 레지스터도 컴파일용으로 연결했다. 비트 단위 SPI/RTL 재생이나 DMA 시험은 아니다.

## 한계와 인계

이번 결과는 추가 소프트웨어 접근 차단의 근거다. 이미 시작된 SPI 비트가 언제 끝나는지, BSY 고장 시 CS 해제와 SCK/SPE/GPIO 상태가 물리적으로 어떻게 되는지는 증명하지 않았다. 레지스터·바이트 응답·시간·SD 카드/핀/CRC primitive는 모델이며 실제 UART/printf·CIC·RESET GPIO·GBC disarm도 아직 모델이다. 전체 main 부팅/메뉴 루프는 제외다. 외부IO와 두 클록 동시 정지+locked HIGH의 CE9us 반례도 남아 있다.

호스트가 CRLF를 LF로 바꾼 `fpga_spi.c`와 `spi.h` 두 파일은 줄끝 정규화 후 원문 일치를 검증했고 두 해시를 따로 기록했다. 수정된 SPI/header 및 다른 입력도 내용 일치를 확인했다. 초기 함수 생성 줄바꿈 누락과 매크로/미실행 DMA 컴파일 오류, checker의 줄끝 비교 실패, Make 의존성 재시도는 보존했다. arm01은 줄바꿈 수정 전 준비본이며 최종 빌드는 arm02다.

다음은 실제 UART/printf·타이머·CIC·RESET 호출을 연결하고, 이미 시작된 SPI 전송의 취소/핀 상태까지 확인하는 단계다. 그 뒤 최종 ARM/097 FPGA/정확한044 복원본과 관측 가능한 제한 실기 절차를 확정한다. 새 RTL/fit/STA/ASM/Questa/실기 패키지는 만들지 않았다.084·092 실기 성공은 그대로 보존하며 반복 시험을 요청하지 않는다.
