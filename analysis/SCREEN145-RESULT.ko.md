# NES145 결과 — 검정·고정 그림으로 부분 갱신을 구분하는 시험판

## 목표와 완료 범위

144의 문자 출력·메뉴 복귀는 실기 통과했지만 육안 부분 갱신이 남았다. 받은 그림을 장시간 고정해 전환 중 변화와 고정된 혼합 그림을 구분하는145 시험판을 완성했다. 실제 원인·수정 성공·게임 정상화는 아직 확인하지 않았다.

## 구현

- NES ROM80KiB·CHR·PRG·CRC는144와 바이트 단위 동일하다. 화면의 `NES 144` 글자는 의도적으로 유지한다. 실행 파일·FPGA 파일명·MCU·두 TXT는145로 구분한다.
- SNES는 기존처럼2008바이트 전체 패킷을 받아 검사·COMMIT한다. 수직 귀선 후 forceblank 상태로90프레임 기다리고 VRAM·팔레트·스크롤을 갱신한다. 표시를 켠 뒤180프레임은 새 패킷 요청·DMA·PPU 쓰기 없이 그림을 유지한다. NTSC 약1.5초 검정/3초 그림, PAL 약1.8초/3.6초다. 전환은 받은 패킷 순서이며 A/B 교대를 강제로 만들거나 혼합 패킷을 정정하지 않는다.
- MCU 표시 대기만600→1200회×50ms(명목60초)로 확대했다. START 전 전량 대조, 각 비트의 소유권/RDY/DONE 검사, NMI, RUN 중 SD쓰기 금지, RESET 유지 후STOP·base/menu 복구를 보존했다.
- 기존142/144 회로·배치·ID5E/D9·조건부 IO 근거를 재사용했다. 프로그램 HEX와 생성 MIF24576바이트를 대조하고 ASM만 실행했다. MAP/FIT/STA나 변경 없는 NES 전체 프레임을 반복하지 않았다.
- 9분 적재를 줄이는 변경은 이번에 포함하지 않았다. 화면 원인 판별과 전송 경로 변경을 동시에 섞지 않기 위해 기존 적재를 유지했다. 하드웨어SPI·묶음 전송·FPGA측 검증 검토를 후속 공정에 남겼고, 검증 생략이나 달성하지 않은 로딩 시간을 약속하지 않는다.

## 검증

- 실제 SNES65816/PPU/DMA 에뮬레이터에서3개 패킷 각각 검정90프레임·고정180프레임을 확인했다. 검정3장과 그림 초반/중간/후반9장의 RGB를 독립 디코더와 대조했다. 고정 구간 PPU/DMA/MMIO 쓰기0을 확인했다.
- 의도적으로 위·아래 A/B 타일맵을 섞은 유효 패킷도 같은 위치에 정확히 고정됐다. 이 대조는 섞인 데이터가 들어오면 시험판이 숨기거나 정상화하지 않음을 확인한다. 실제 보드 원인이 혼합 패킷이라는 증명은 아니다.
- 길이·헤더 오류2사례는 기존 오류 처리로 거부했다. 정상·혼합 합계 고정 RGB18장/검정6장이다. MMIO는 Lua 모형이며 전체 FPGA/MCU/SNES 동시 시뮬레이션은 아니다.144 실제 NES RTL4프레임 근거는 ROM·코어 무변경 범위에서 재사용했다.
- 실제 MCU 호스트21사례, 명목60초/1200관측, 오류 조기종료·STOP·메뉴 예산, ARM186792바이트의 강한NMI15store/0call/3DSB/2ISB와 호스트 소스 일치가 통과했다.
- Questa에서 전체64KiB ROM 주소 대응을 확인했다. 기존 FLOAT1seat를 사용했고 새 라이선스·회로 배치는 없다. 패키지13항목·모든 해시·FPGA 압축 역변환·044복원본 일치를 확인했다.
- 초기 도구 실행은 샌드박스 DLL/설정 접근과 잘못 선택한 비포터블 Mesen 경로로 실패했고, 기존144와 같은 포터블 Mesen 해시로 실행했다. 복사한 ARM 검사기의 숫자2621440 오타와 Lua 모형의 이전 단계 잔류값 조기종료를 고쳤다. 실제145 ARM/SNES 프로그램은 이 검사 수정 중 변경하지 않았고 초기 자료를 보존했다.

## 재현과 다음 작업

`nes_screen145.py --baseline <private-probes> --kind arm|host --out <fresh>`로145 MCU 소스를 만든다. 기존 ARM 도구로 `build_nes_screen145_arm.ps1`, `test_nes_screen145.py`, `check_nes_screen145_arm.py`를 실행한다. `build_nes_screen145.py`는 동결144 CHR를 입력받는다. 실제144 패킷을 이용해 `test_nes_screen145_client.py --mode normal|mixed|bad_length|bad_header`를 각각 새 폴더에서 실행한다. `update_nes_screen145_rom.py`→`assemble_nes_screen145.py`, 승인된 FLOAT 래퍼의 `test_nes_screen145_bus.py`, 기준 그림 생성과 `release_nes_screen145.py` 순서다. `verify_nes_screen145.py --baseline <private-probes>`는 동결 근거·공개 소스·ZIP을 읽기 전용 확인한다. 공개 clone만으로 private 보관 근거를 재현할 수 있다는 뜻은 아니다.

[실행 안내](../docs/nes-screen145-instructions.ko.md)에 따라 한 번 촬영하고 두 TXT·메뉴 복귀 여부를 받는다. 고정 중 변화가 계속되면 소비·표시를, 혼합이 고정되면 생산/패킷 내용과 표시 상태를 우선 점검하되 영상만으로 원인을 확정하지 않는다. 이후 실제 입력과 SMB3(J) mapper4·384KiB·오디오로 진행한다. 로딩 단축도 별도 미완료 항목이다.

이는 실기 표시 문제를 구분할 수 있는 시험판의 완성이다. 게임 기능이나 원인 수정 완료는 아니다. 전체IO/MTBF, ACK16ns 실패, E1/E2·8µs·양 클록 정지CE9µs·source-lock4·124격리 사항은 유지한다.
