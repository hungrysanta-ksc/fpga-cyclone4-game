# NES153 — PPU 오류 문맥 수신과 로그·메뉴 복귀 수정

PR94 머지 `b01e7cf5926b9e637987c49cb4e135ae65416970`에서 진행했다. [152 실기 결과](GAME152-HARDWARE-RESULT.ko.md)의 무복귀 결함을 수정하고 [153 실기 패키지](../docs/nes-game153-instructions.ko.md)를 준비했다. **PPU 읽기 오류 자체의 수정이나 실기 정상 구동 완료는 아니다.**

## 변경과 의미

152 FPGA는 오류 문맥 bit63을 PPU 실제 요구 주소 표식으로 사용했지만, MCU의 `context146()`은 이 비트를 여전히 금지했다. 이 불일치로 정상 형식의 PPU 오류를 받아도 보호 실패 경로로 들어가 STOP·기본 FPGA 복원·최종 TXT·메뉴 복귀를 건너뛸 수 있었다.

153은 이 금지 조건만 제거하고 양쪽 응답의 DC 식별·유효 플래그·오류 코드 일치/비영·형식 버전1 검사를 유지한다. 식별62/DC도 그대로다. 비트63은 주소 종류이며 오류 원인 코드가 아니다. 따라서 다른 오류가 우선 보고되어도 PPU 주소 표식을 수신할 수 있다. 나머지 변경은153 표식·ROM/FPGA 경로·로그·버전 이름이다. 실제 MCU 소스는4파일만 변경했다.

FPGA 압축 이미지, 배치·타이밍, 게임·입력·영상 처리는152를 그대로 재사용했다. `fpga_n153.bi3`는 이름만 바뀌었으며 SHA-256은 `3fa965058abd3af8e103f1911aa28a496d16d1bf0b0fcc6c2975534b76aa8b9e`다. 새 Quartus·Questa·게임30프레임·A/B 시험을 반복하지 않았다.

이번 작업은 **실제 게임 오류를 숨기지 않고 회수하여 원인 수정으로 이어가기 위한 복귀 경로 수정**이다. 화면 배선이나 새로운 게임 기능을 추가한 작업은 아니다.

호스트 시험은 실제 `nes_run136.inc`, `nes_h1_stm32.c`, 메뉴·진행 로그·FatFS 코드를 사용한다. SD/GPIO/FPGA 응답/시간은 모델이고, SPI 하드웨어 엔진 대신 이전 비트뱅 전송 어댑터를 사용한다. 변경하지 않은 SPI149 엔진의 기존 검증을 재사용한다. **ARM 실행·전기 특성·실제152 정지 원인을 재현했다고 주장하지 않는다.** 384KiB 실행은 변경된 오류 복귀와 실제 파일 저장을 연결하기 위한 비교2건이며, 새 PSRAM 전량 실기 쓰기 검증이 아니다.

저장된 모델 로그는 `run_passed=0`, `run_rom_error=2`, `run_stop_error=0`, `fault_context_valid=1`, `fault_context_hi=e200c2f4`, `fault_context_lo=30217a19`, `base_restored=1`이었다. 오류를 성공으로 바꾸지 않았다. 최종 TXT의 `PREPARED_RESET_HELD`는 저장 시점의 상태다. 그 뒤 실제 메뉴 경로의 RESET 해제는 호스트 assertion으로 별도 확인했다.

초기 준비 실패도 보존했다. arm01은 버전 문자열 개수6→7 교정, host01/02는 Unicode 소스 위치, host03은 헤더 구성 오류였다. 선택 결과는 arm02·armcheck01·host04·context01·release01이다. 제품 실행 실패나 라이선스 오류가 아니다.

## 남은 목표와 다음 한 번의 시험

같은 SMB3(J)를153으로 실행하여 두 TXT와 영상을 받는다. 게임이 일찍 멈추더라도 오류 문맥을 보존하고 메뉴로 복귀하면 이번 수정의 실기 목표에 부합한다. 이전152 재시험과 변하지 않은044/GBC 보고는 요구하지 않는다.

실제152의 오류 코드·주소는 여전히 미확인이다. 새 로그의 PPU 실제 요구 주소와 처리 중 주소를 비교해 요청/선행읽기/캐시/응답 기한을 좁힌다. 주소가 같거나 다르다는 사실만으로 PSRAM 또는 특정 원인을 확정하지 않는다. Start 한 번의 중복 소비 여부도 미확정이며, 입력 DMA/대기 공백·약0.5초 표시·소리·저장·기존 IO/MTBF 제한은 남아 있다.
