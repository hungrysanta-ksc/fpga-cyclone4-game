#048 OAM 자원 최적화 결과

**스프라이트 기능과 메모리 용량을 유지하면서 통합 회로870 LE를 줄였다. LAB 여유는10개에서37개로 늘었다.** 채택 후보는 `tools/nes_oam_compact.py`이며 실기 기준044는 변경하지 않았다.

|---|---:|---:|---:|---:|---:|
|047 기준 |14,153|953|10|26|4,797|
|048 첫 시도: 묶음 분리만 — 미채택 |14,161|961|2|26|4,797|
|048 최종: 정상 쓰기 경로 공유 |13,283|926|37|26|4,797|

256바이트 primary OAM을8개의32바이트 묶음으로 표현하고, 동시에 발생할 수 없는 행 복사와 CPU 쓰기의 주소 선택 회로를 공유했다. 상태 저장 쓰기와 같은 주소에 겹칠 때의 우선순위, 읽기 시점, 속성 비트 마스킹, 행 손상 복사, 보조 OAM, 스프라이트 평가와 오버플로 동작은 유지했다. 첫 구조 분리만으로는 합성이 개선되지 않아 채택하지 않았으며 해당 회귀/fit 결과도 보존했다. 최종 OAM 계층의 logic-cell 수는7909→7000이다. 계층 logic-cell 합과 배치 후 LE/LAB는 서로 다른 집계이므로 단순 합산하지 않는다.

## 동작 검증

- 원본과 최종 후보를216,362클록 동안 매 클록 비교했다. 출력·평가 상태·primary256바이트·secondary64바이트 모두 일치했다.
- 행 복사2,426회, CPU 쓰기3,111회, 상태 저장 쓰기10,473회, 같은 클록의 쓰기 중첩2,012회를 포함했다. 별도로256개 주소의 CPU/상태 저장 충돌과8개 목적지 묶음의 행 복사/상태 저장 충돌을 직접 검사했다.
- 동일한 초기화와 입력으로 NTSC/PAL 전체 스캔라인 범위, 렌더링 전환, 네 평가 상태와 결정적 난수 입력을 검사했다. 합성 전 RTL 비교이며 형식 검증으로 모든 경우를 증명한 것은 아니다.
- 수정 코어에서 `banks32`/`fine_x` ROM을 새로 실행했다.8프레임·16,064바이트·491,520픽셀과 전체 fetch/프레임/전송 기록이047과 바이트 단위로 같았다. NES 실행 정지나 프레임 누락을 추가하지 않았다.

원본의 `eval_count`는 명시적인 초기화/RESET 설정이 없다. 비교 테스트는 먼저 원본 X 상태를 보존한 후 두 모델에 같은0..3 값을 주어 실제 평가 전이를 검사했다. 이 테스트 초기값 주입은 제품 수정이나 실기 초기화 보장이 아니다. BG-only 전체 코어 회귀만으로 스프라이트 게임 정확도가 완료됐다고 판단하지 않는다. 향후 스프라이트/RESET 검증 항목으로 기록했다.

## 실기 통합 자원 예산

현재 fit에는 CPU/APU/PPU/MMC3,047 PPU 포트 연결,046 인코더,045 생산기,044 전송부와018 자원 측정용12KiB RAM이 포함된다. ROM 크기는047과 같은64KiB PRG·16/32KiB CHR 진단 범위다.237가상 핀/5위치 미지정 핀, PLL0이며 전체 STA는 실행하지 않았다. 메모리 비트182,922와 M9K26은 변하지 않았다.

별도044 실기 진단의 경계 회로 자체는402 logic cells, 프로그램 ROM은18 logic cells/24 M9K, PLL은1개였다. 이 값은 기존 측정의 참고치다. 향후 NCR1 런타임 크기나 공동 LAB 비용으로 그대로 더해 완성 보드가 들어간다고 판단하지 않는다.

아직 실제 ROM/PSRAM/SRAM 서비스와 중재, SNES NCR1 런타임/CHR 접근, 보드 클록·RESET/epoch 전달·SPI 수명주기, 입력·오디오·저장·물리 핀 타이밍을 함께 연결해야 한다. **37 LAB 확보는 통합을 진행할 여지를 늘렸지만 완성 보드 적합성 확인은 아니다.**

다음은 실제 메모리/클록/소비자 인터페이스를 연결한 공동 배치와 수신·PPU 갱신 마감 검증이다. 지원 모드를 넓히기 전에 OAM 초기화/RESET 범위도 명확히 한다. 완성 후보의 보드 검증과 복구 경로가 준비되면 새 실기 패키지를 제공한다.044 SD와 GBC 보호152개 파일은 유지했다.
