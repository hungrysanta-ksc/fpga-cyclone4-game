# NES138 실기 결과 — CPU ROM 응답 마감 실패

사용자는 적재 뒤 글리치처럼 보이는 화면이 잠시 표시되고 메뉴로 복귀했으며, 두 TXT 작성과 정상 펌웨어 복원이 성공했다고 보고했다. **화면 시험은 실패다.** 이번 실행의 GBC 플레이 여부는 별도로 보고되지 않았다. 기존136 CPU 활동 시험의 성공과 구분한다.

## 확인된 결과

| 구간 | 결과 |
| --- | --- |
| 후보 식별 | FPGA5A / 관측D5 일치 |
| 적재·읽기 대조 | 81920바이트 모두 완료, `verified=1`, 오류0 |
| NES 실행 | `run_passed=0`, 최초 ROM 오류1 |
| CPU의 유효 ROM 샘플 수 | 처음·마지막·STOP 후 모두123028, 관측 중 증가 없음 |
| 종료 | `stop_ok=1`, 기본FPGA 복원·메뉴 준비 성공 |
| 사용자 확인 | 메뉴 복귀·정상 펌웨어 복원 성공, 정상 패턴 표시 실패 |

진행 파일47개512바이트 기록의 순서와 경과시간이 일치한다. `DISPLAY_NEXT`는522580ms(약8분43초), `DISPLAY_STOPPED`는532920ms, `MENU_PREPARED`는536040ms(약8분56초)다. 약10분 뒤 화면을 봤다는 사용자 관찰과 모순되지 않는다. 이 시간은 펌웨어 기준이며 독립적인 벽시계 측정값은 아니다. 화면이 즉시 나오지 않은 이유는 앞에 전체 적재와 읽기 대조가 있기 때문이다.

## 오류 해석

실제138의 `nes_rom_early`에서 오류1은 `cpu_sample && cpu_rom && !cpu_valid`다. CPU가 ROM 바이트를 소비해야 하는 시점에 현재 주소와 일치하는 캐시 또는 완료 응답이 없었다. 단순히 SD 쓰기 실패나 표시 시간 부족으로 볼 수 없다.

다만 이 오류 하나로 PSRAM의 전기적 실패, 특정 주소, 요청 충돌, 클록 위상 중 원인을 확정할 수는 없다. 글리치 화면의 직접 원인도 이 로그에 기록되지 않는다. 메모리 대조 성공은 정적 적재/읽기의 성공이며, 실행 중 CPU/PPU 공유 읽기의 응답 마감 통과를 뜻하지 않는다.

`run_flags=3`은 **마지막 STOP 이후** 관측이다. bit0은 STOP 후 코어 reset 유지, bit1은 sticky ROM 오류다. 이 값으로 RUN 도중 reset이 걸렸다고 해석하지 않는다. `run_error=3`도 MCU가 마지막 STOP 관측 검사에서 앞선 오류를 덮어쓴 값이다. STOP 명령 자체의 실패와 구분하며 최초 ROM 오류1을 원인 분류에 사용한다.

## 다음 작업

추가로 동일138 기능 RTL·fixture를 사용해 SNES 반주기23.280ns, 시작 위상3.5ns, 이상적인84/168MHz PLL,70ns PSRAM 모델에서 RUN 후100ms를 확인했다. 이전090의 COUNT1342354/DIVISOR16/WINDOW8000000은 CLKIN8MHz 가정에서 약21.477664MHz이며, 이번 모델은 그 비율에 가깝다. **이 한 조건에서는 ROM deadline 오류가 재현되지 않았다.** 총102.161ms 시뮬레이션/184344검사가 통과했으며, 기존 모델의75개 연결/초기값 경고는 원문 로그에 보존했다.

이는 실제 보드 지연·PLL·모든 위상·실제65816 소비자 동시 실행을 재현한 시험이 아니다. 샘플 픽셀의 정의 여부를 검사했지만 이번에는 패킷/영상의 완전 일치 검증을 다시 수행하지 않았다. 클록 비율만 바꾸면 해결된다는 근거가 없으므로 임의의 읽기 시간 축소나 오류 검사 제거는 하지 않는다. 다음 후보는 아래2번의 최소 최초 실패 관측을 우선한다.

1. 동일138 RTL·진단 ROM의 CPU/PPU 공유 읽기 경계만 조사한다. 기존090 실기 클록 비율에 가까운 조건과 현재 모델을 대조하고, 최초 deadline의 주소·미완료 요청·나이를 확인한다. 변경 없는 저장·부품·전체 적재·배치를 반복하지 않는다.
2. 모델에서 재현되면 원인에 맞춰 요청 중재/응답 경계를 수정한다. 재현되지 않으면 최초 실패 시점의 CPU 주소·pending 주소/소유자·age를 보존하는 최소 관측을 다음 실기 후보에 넣는다. 일반 trace 체계를 선행하지 않는다.
3. 다음 MCU는 최초 RUN 오류를 STOP 결과와 별도로 보존하고, 알려진 ROM 실행 실패 뒤 불필요한 표시 대기를 줄인다. RUN 중 SD 쓰기 금지와 RESET 재유지→STOP→메뉴→044 복원 계약은 유지한다.
4. 수정 후보의 관련 경계만 확인한 뒤 새 패키지로 화면 실기를 다시 한다. 정상 화면 전에는 입력·SMB3 구현을 완료로 승격하지 않는다. **동일138 재시험이나 추가 영상은 현재 실패 확인에 필요하지 않다.**

원본 두 TXT는 기존138 동결 증거 밖의 새 관측 폴더에 그대로 보존했다. 공개 요약과 원본 해시는 [관측 메타](screen138-hardware-observation.json)에 기록한다. 기존 [138 제작 결과](DISPLAY138-RESULT.ko.md)는 제작 당시 결과로 유지한다.
