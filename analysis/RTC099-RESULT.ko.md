# NES099: RTC 대기 종료와 메뉴·저장 오류 전달

RTC 준비 신호가 오지 않으면 내부 루프에서 멈추던 진단 경로를 수정했다. 실제 RTC 함수와 공유 런타임의 18경우, 실제 main·적재·FatFS·native SD를 연결한 12경우, 보호 제거 대조 4개가 통과했다. 같은 소스의 ARM 링크도 확인했다. 이번 RTC 범위는 완료했으며 전체 하위 IO와 실기 준비는 남아 있다.

PR48 병합 `4ea53133ff225c332d10cb2739b115c39892b214`를 기준으로 작업했다. 이전098의 메뉴 주소 수정과097의 FPGA·base·메뉴 이미지를 재사용했다.

## 수정

- 진단 활성 상태에서 `read_rtc`의 RSF와 `set_rtc`의 INITF 대기에 로컬 100tick·100,000회 한도를 적용했다. 매 반복에서 기존 메뉴/보고서 공유 예산과 최초 오류도 확인한다. 정상 tick의 명목 1초이며 실제 MCU 실행 시간이나 WCET 측정값은 아니다. tick이 멈춰도 반복 횟수로 종료한다.
- 로컬 한도는 새 오류 `NES_DIAG_RTC=17`을 설정한다. 기존 오류 번호는 그대로다. 공유 예산이 먼저 끝나면 기존 오류16을 유지한다. 예산·오류를 지우거나 재시도하지 않는다.
- 읽기 실패 시 출력 구조를 0으로 초기화하고 BCD/FAT 시간 반환값도0으로 만든다. 호출자는 공유 오류로 실패를 판별한다. 설정 대기 실패 시 INIT 요청 해제와 쓰기 보호 복원만 수행하며 TR/DR/세기/유효 표식은 갱신하지 않는다. 후속 RTC 호출도 중단한다.
- 진단 비활성 상태의 기존 GBC/일반 RTC 대기·날짜 변환은 보존했다. 일반 경로의 모든 무한 대기를 해결했다는 뜻은 아니다.

수정 파일은 파생 펌웨어의 `stm32f4xx/rtc.c`, 오류 enum을 추가한 `nes_diag_runtime.h`, VERSION뿐이다. main·전체 load_rom·native SD·CF86 세션 C는 변경하지 않았다. 공개 adapter는 고정098 입력으로 이 세 변경을 재현한다.

## 검증과 한계

| 검증 | 결과 |
| --- | --- |
| 실제 RTC/공유 런타임 18경우 | 읽기·쓰기·BCD/FAT 변환, 지연, RSF/INITF 무응답, 진행/정지/wrap tick, 최초 오류·후속 차단, 무효 RTC, 기존 비활성 경로 통과 |
| 실제 main/FatFS 12경우 | FAT16/SDHC 80KiB와 FAT32/SDSC 96KiB. 정상·무효 RTC·지연·중간 공유 오류·무응답·정지 tick·TXT 저장 중 시간 읽기 실패 확인 |
| 대조 4개 | 로컬 poll/time 한도, 설정 실패 정리, 오류 전달을 각각 제거하면 검증 실패 |
| 원본 반례 | 원본098 RTC의 무응답 읽기는 호스트 외부 감시 200,002회까지 반환하지 않음. 실제 보드 정지의 원인 재현으로 확대하지 않음 |
| ARM01 | 181,200바이트, SHA256 `a37e782bc168e36a9147881e828452ac2d1fa81b3a0a027df68391cdfd23c67a`. RTC와 오류 헤더가 호스트 입력과 일치. main→RTC, FatFS f_open/f_sync→get_fattime, 한도·오류17·INIT/WPR 정리 분기를 ELF에서 확인 |

정상 SD명령은80KiB 1534회,96KiB/autoboot 있음1637회이며 보고 쓰기5회는 RESET 해제 전이다. RTC 무응답은 오류17·해제0회로 종료한다. TXT 저장의 RTC 무응답은 더 짧은 기존 보고서 공유 예산이 먼저 소진되어 오류16·저장0바이트·해제0회가 된다. 이때 SD명령은80KiB1525회/96KiB1627회에서 멈춘다. 최초 공유 오류 이후 추가 SD명령·에지·CF86프레임·구성 바이트가 없음을 검사했다. 실패 후 TXT가 항상 남는다고 약속하지 않는다.

RTC 함수 전체와 실제 STM32F401 CMSIS 비트 정의를 사용하되 레지스터·BITBAND·시간은 호스트 모델이다. FatFS의 고정 시간 stub을 실제 RTC 호출로 교체했다. Windows DWORD/uint32_t 명칭 차이를 위한 호스트 wrapper가 있다. SRAM/SPI, UART/printf, CIC, RESET, 시간 경과와 SD 카드·핀·CRC primitive는 여전히 모델이다. 실제 ARM 실행, 물리 MMIO 정지, 전체 main 부팅/메뉴 루프, 전기적 타이밍의 증거가 아니다.

ST의 [공식 STM32F4 RTC 드라이버](https://github.com/STMicroelectronics/stm32f4xx-hal-driver/blob/master/Src/stm32f4xx_hal_rtc.c)는 RSF 동기화와 INITF 준비 확인을 별도 단계로 다룬다. 이번 변경은 기존 프로젝트 API를 유지하며 진단의 종료 한도를 추가한다. 제조사 드라이버를 이식하거나 물리 클록을 측정한 것은 아니다.

## 보존한 실패와 다음 단계

초기 호스트 COFF 미사용 함수 링크 실패, 날짜 기대값/RSF 클리어 접근 수/공유 시계 질의 수의 모델 오류, Win64 FAT 시간 ABI 충돌, 중간 오류 주입 시작 위치 오류를 원시 로그와 생성 소스에 보존했다. 이 실패들은 테스트 연결을 수정한 것이며 펌웨어 변경은 최초 ARM01 소스 그대로다. 초기 실패 실행 일부는 driver 자체 snapshot이 없으므로 생성 소스·로그 범위의 증거다. 최종 main04 이후 driver snapshot은 보존했다. ARM checker의 CRLF 정규식 실패는 같은 ELF의 줄끝 정규화로 수정했다. 기존 Make 첫 의존성 실패 후 재시도 로그도 보존했다.

다음 작업은 실제 SRAM 함수→fpga_spi→STM32 SPI 및 UART/printf/타이머/CIC/RESET을 현재 main/load_rom과 연결해, 공유 오류 이후의 후속 호출이 하위에서도 차단되는지 확인하는 것이다. 그 뒤 같은 최종 ARM/097 FPGA/정확한044 복원본, 외부IO·두 클록 공통고장 정책, 관측 가능한 제한 실기 절차를 확정한다. 새 RTL/fit/STA/ASM/Questa/실기 패키지는 만들지 않았다.

084 저장·화면·044복원·메뉴/GBC와092 클록 활동·TXT·복원 실기 결과는 보존한다. 준비도4완료/7부분/1미완료, 설치false. 첫 게임 SMB3(J)의 mapper4·384KiB 목표도 유지한다.
