# NES160 실기 — 첫 레벨 진입 오류와 화면 갱신 지연

**첫 레벨 플레이는 실패했다. 종료 원인은60초 제한이나 마지막 A입력 누락이 아니라 PPU 읽기 오류2다.** 겉으로는 이전과 같은 메뉴 복귀지만 실패 위치는159의 line193/dot336/217000에서160의 line193/dot6/205FF0으로 달라졌다. 이 차이만으로159의 원인이 완전히 해결됐다고 선언하지 않는다. 이번은 PR102에 실기 결과를 추가하는 작업이며 기존160 패키지는 변경하지 않는다.

## 로그 확인

- 69/E3 식별,393216바이트 적재·전량 대조,verified=1,104개512바이트 진행기록 정상.
- DISPLAY_NEXT232870→DISPLAY_STOPPED249310: 펌웨어 시각 기준16.440초. 이후3.240초 뒤 MENU_PREPARED252550. 실시간 외부 초시계·FPS와 구분한다.
- run_rom_error=2,run_first_error=1,STOP 성공·base 복원·메뉴 준비 완료. 사용자는 첫 레벨 진입 시 튕겼다고 보고했다. 정상044 복원은 재요청하지 않는다.
- 입력 변화16건이 모두 보존됐고 마지막은 A. START/해제·A/해제·RIGHT/UP도 기록됐지만 물리 버튼 클릭 시각이나 모든 입력의 정확한 지연을 측정한 것은 아니다.
- screen_frames=29와screen_telemetry_trusted=0은 원본 보존.29FPS나 실제 표시 횟수로 사용하지 않는다.

## 이전과 다른 데이터 교체 경계

오류 문맥 `e200c2ff:f0205ff0`: 실제 요구205FF0,처리 중217FF8,age1,PPU sample=1/valid=0. 마지막16 NES클록은 다음을 보여 준다.

| 오류 기준 클록 | 관측 |
| --- | --- |
| -15~-8 | 현재주소3A07F0,힌트205FF0은 캐시에 존재. CPU03F886 응답 후 reader가 빈 상태 |
| -7 | 실제주소205FF0으로 전환,데이터 valid=1. 다음힌트217FF8 선행 요청 |
| -6~-3 | 실제205FF0은 계속 valid=1,217FF8 읽기 진행 |
| -2 | 217FF8 응답과 같은 주소의 중복 요청이 동시에 발생. 현재205FF0 valid=1 |
| -1 | 실제주소205FF0은 그대로지만 valid=0으로 떨어짐. 힌트217FF8은 캐시 hit=1 |
| 0 | 실제205FF0 샘플에서 오류2 발생 |

실제 service는 PPU응답마다 기존 첫 번째 캐시를 두 번째로 옮기고 새 응답을 첫 번째에 넣는다. **현재 사용 중인205FF0이 두 번째 슬롯에 있었다면,미래주소217FF8 응답이 이를 밀어내는 경계**와 로그가 부합한다. 내부 캐시 태그는 기록되지 않아 물리 원인 확정 대신 우선 재현할 구체적 후보로 둔다. 응답과 같은 클록의 중복 선행 읽기도 관측됐지만 최초 유효 데이터 상실과 별도로 검토한다. 대기시간 증가·샘플 검사 해제·전역 우선순위 변경은 근거가 없다.

## 화면이 끊기는 이유와 이번 결정

선택160 FPGA의 실제game-program.hex를152 생성 코드로 만든 바이트와 전량 비교해 같음을 확인했다.151 소스만 보고 판단하지 않는다.

현재 SNES 표시기는 한 장면을 캡처하고57344바이트를 화면 강제 소거 중 전송한 뒤30 vblank 동안 표시한다. NES 게임 로직은 그동안 계속 실행한다.60Hz 기준 약0.5초마다 화면이 멈춰 보이는 구조이며 정상 연속 표시가 아니다.30프레임 대기는 메모리 오류 검출에 필수인 조건이 아니라 **전체화면 전송의 점멸을 줄이기 위한 임시 표시 방식**이다.

버튼은152에서 이미 표시 유지 중 매 vblank마다 자동 수집 완료를 기다려 전달하도록 수정했다. 이번A도 기록됐다. 다만 화면 반응이 늦게 보여 입력 판단이 어렵다는 사용자 관찰은 타당하고,DMA·다음 프레임 대기 중 수집 공백도 남아 있다. 기존152의 패드 갱신 개선을 다시 구현하지 않는다.

**이번에는30 대기를 단순 삭제하지 않는다.** 현재57344바이트 전체 전송은 vblank를 넘으므로 강제 소거를 제거할 수 없고,대기만 없애면 새 화면을 더 자주 보이는 대신150에서 문제가 됐던 점멸이 다시 두드러질 수 있다.30→0이60fps 전환이라는 설명도 잘못이다. 이전150은 쓰기 캡처 수정도 함께 필요했으므로 점멸 전체 원인이 대기 하나였다고 단정하지 않는다.

후속 구현에서는 첫 레벨 데이터 교체 오류와 함께 표시 지연을 개선 대상으로 둔다. 최소한 현재 입력 수집을 유지하면서 표시 보유 시간·전송/캡처 대기를 분리하고,강제 소거 점유를 줄이는 전송 방식을 확인해야 한다. 플레이 판단에 필요한 연속 화면이 목표이며 새 A/B 진단 반복을 선행 조건으로 추가하지 않는다. 이번에 프레임 제한을 해제했다거나 입력 지연을 해결했다고 표시하지 않는다.

## 다음 작업

현재 요구205FF0이 두 번째 캐시에 있는 상황에서217FF8 응답이 들어오는 짧은 실제service 경계를 재현한다. 사용 중인 바이트 보존과 처리 중 힌트의 중복 요청 방지를 검토하고,정상 CPU/DMA/PPU기한을 유지한 최소 수정 후 같은 SMB3 첫 레벨로 돌아간다. 표시 개선은 버튼 처리의 기존성과를 보존하며 추진한다. 동일160 재시험·044/GBC·전체 부팅 재검증은 반복하지 않는다.

첫 레벨 플레이·연속 화면·오디오·속도·저장 미완료.160 제작 당시 검증은 [제작 결과](GAME160-RESULT.ko.md),이번 실기는 [원본 해시와 해석](game160-hardware-verification.json)이 기준이다. frozen160·ZIP·공개 소스 핀은 그대로 보존했다.
