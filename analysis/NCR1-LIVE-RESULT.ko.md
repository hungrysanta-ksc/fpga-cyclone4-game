#047 실제 NES 코어 → 화면 패킷 통합 결과

**직접 작성한 ROM을 새로 실행하여 PPU→047 감시부→046 인코더→045 생산기→044 전송 경로를 검증했다. 실기 기준은044로 유지한다.**

- `banks32`와 `fine_x` 진단을 각각 연속4프레임 실행했다. 총131,104개 BG fetch,16,064바이트 전송,491,520픽셀 복원이 실제 PPU 출력과 일치했다. 저장된 fetch 재생이나 완성 패킷 주입을 사용하지 않았다.
- 실제 MMC3 변환 후 CHR 주소와 PPU 데이터가 일치했고, 속성값0~3이 관측됐다. 네 팔레트 그룹이 모두 같은 지정4색인 경우만 속성을 그룹0으로 정규화한다. 일반 다중 팔레트 지원을 뜻하지 않는다.
- 입력 감시20항목 통과: BG/스프라이트/VBlank 분류, PPU CE, 프레임 경계, 실제 속성 정규화, 모드·팔레트·스크롤·CHR 변경과 잘못된 물리 주소 거부, RESET 복구 등을 확인했다.
- 코어를 멈추거나 프레임을 버리지 않고 네 연속 프레임을 전송했다. 단, 테스트벤치 소비자는 실제 SNES 런타임이 아니며, 수신 완료가 다음 프레임 시작을 지난 경우도 있다. SNES VBlank DMA 마감 검증으로 해석하지 않는다.

실제 PPU 포트 연결과047/046/045/044를 같은 top에 배치했다.012/014 CPU 수정이 적용된 코어와018의 CPU2KiB·CIRAM2KiB·PRG RAM8KiB 자원 래퍼를 포함한다. 마지막 래퍼는 초기화 없는 자원 측정용이며, 시뮬레이션의 초기화된 이상적 메모리 서비스와 동일한 구현은 아니다.

## 발견·수정한 통합 문제

자원 측정용018 Mapper4 어댑터는 전체 주소를 보존하며 ROM 크기 마스크를 적용하지 않았다. 이를 이상적64KiB ROM 서비스에 그대로 연결하면 리셋 벡터가 범위를 벗어나며 초기 팔레트가 설정되지 않았다. 입력 마스크 값만 변경해도 어댑터가 무시하므로 개선되지 않았다.047의 별도 로컬 생성본에 실제 PRG/CHR 마스킹을 적용하고 CPU/PRG RAM·CIRAM 주소 구분을 보존하여 두 실행을 통과시켰다.018/044/045/046 원본은 수정하지 않았다.

포트 선언 순서, Questa 작업 라이브러리/INI 경로, 테스트벤치 `$time` 시작 신호 문제도 수정했다. 실패 실행01~06과 ROM 마스크 수정 전 공동 배치 원문을 함께 보존했다. 이들 준비/어댑터 오류를 기존 실기 실패 원인이나 새 라이선스 필요로 분류하지 않는다.
