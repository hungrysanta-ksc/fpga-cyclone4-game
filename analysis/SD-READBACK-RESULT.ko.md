# NES060 — SD 적재·전체 읽기 비교·복구 연결

후보 **NES-SD-READBACK-060**,2026-10-07. 기존056의 SD 승인/적재·GPIO 보호·기본 복구를 보존하면서059의59 프로토콜과 실제 바이트 비교를 새 진입점으로 연결했다. [계약/재현](../docs/nes-sd-readback-contract.md) · [검증 요약](sd-readback-verification.json).

## 새로 확인한 결과

| 검증 | 결과 | 범위 |
| --- | --- | --- |
| 실제 C + 플랫폼 모형 |41실행·복구 경우/18헤더·크기 거부 |80/96KiB 정상 경로,IRQ 초기 on/off,기존 실패와15개 새 오류/복구 경우 |

세 번째 SD 읽기는256바이트 버퍼를 사용한다. 마지막 바이트를 비교기에 넘기기 전에 최종 크기·전체 CRC·파일 닫기를 확인한다. 길이 완료,실제 비교 완료,STOP 확인,기본 복구 성공은 별도 상태다. 검증 성공 뒤 STOP 응답이 불확실해도 기본 재설정 성공 여부로 메뉴 복귀 가능성을 판단한다. 모든 경로에서 START와 SD 쓰기는 없다.

## 재사용한 근거와 한계

SPI/메모리5개 생성 RTL은059 fit와 해시가 같다.059의959/963LAB·26M9K·4LAB 여유와2ROM/8프레임/491520픽셀은 **재사용 근거**이며060에서 새 합성/전체 코어 실행을 하지 않았다. 이번 파형은044 식별자와59 SPI가 같은 디지털 경계에서 공존하는 검사다. 실제 PSRAM 전기 타이밍·물리 보드 fit/STA를 뜻하지 않는다.

전체 길이 C 실행은 FatFS/GPIO/설정 모형이며,실제 STM32/SD 실행은 아니다. GPIO 파형은 적재와비교의256바이트 구간을 따로 재생했다. 두 번째 파형의96KiB는 loader 입력을 통해 핀에 써서 준비했으며 전체 C 적재 파형이라고 부르지 않는다. ARM 새 함수 크기는 하위 helper 전체 비용과 다르다. 아직 메뉴 호출·새 SD 이미지가 없다.

초기 호스트 모형의 sticky-error 명령 처리 오류,task 선언 순서 컴파일 실패,Make dependency 최초 실패와재시도를 보존했다. wave02는 통과했지만 실행 중 편집한 driver의 종료 시점 해시가 저장돼 원본 결과를 유지하고,wave03에서 실행 snapshot을 직접 해시하도록 고쳐 다시 확인했다. 생산 C/RTL은 이 수정에서 바뀌지 않았다.

다음은 CPU/PPU를 실행하지 않는 load/verify/STOP 진단의 실제 보드 핀·클록·타이밍·복구와 메뉴 대기/결과/로그를 묶는 작업이다. 해당 범위의 검증을 마친 새 MCU/FPGA 쌍으로 실기에 진입한다.044 실기와 GBC,이전 원시 근거를 유지한다.
