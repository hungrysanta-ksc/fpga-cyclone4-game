# 122 — 등록형 보호 reader의 정상 속도 코어 연결

## 작업 목표

PR67 병합 `79daf3f539c1f0956d71f2fc50c0984e3293c4ef`을 확인했다.121에서 통과한 실제 CPU·PPU·선행 요청 서비스·CDC 경로에 CF86의 SETUP/ACTIVE/HOLD/RELEASE reader를 연결해, 핀 보호 순서를 유지하면서 코어의 읽기 기한을 만족하는 후보를 찾는다.

## 작업 내용

제품 RTL은 변경하지 않았다. 핀된052 코어 테스트벤치의 reader만 기존 CF86 등록형 소스로 교체하고 CHECK 입력은0으로 묶었다. 먼저 READ8/84MHz·70ns 모델을 검사했다. 이 조합은 reader 단독16위상 시험에서는8,400읽기/208취소를 통과했지만, 실제 코어에서는 첫 fine_x 사례의 tick852209에서 CPU 기한 오류가 났다. 첫 실패 뒤 시험이 종료됐으므로 다른 입력까지 실패했다고 해석하지 않는다.

원시16클록 이력에서 tick852198에 PPU `0x201ff2` 요청이 먼저 들어가고, 다음 클록에 CPU 주소가 `0xe184`로 바뀌었다. PPU 응답은852204에 도착했고 그때 CPU 요청을 수락했다. CPU가852208에 데이터를 소비할 때 응답이 없어 다음 클록에서 오류가 검출됐다. 단독 핀 시험의 성공만으로 공유 서비스의 기한을 보장할 수 없다는 실제 반례다.

선정 후보는 **reader 제어168MHz·READ16**이다. 메모리 샘플까지16×5.952=95.232ns를 확보해 기존 READ8×11.904ns와 같은 접근 시간을 유지하면서, SETUP/HOLD/RELEASE와 요청 동기화의 부가 지연을 줄였다. 실제 NES 클록과 데이터 검사는 그대로다.60ms 캡처 시작·150ms watchdog·프레임 생성/전달 검사를 유지했다.168MHz는 제어 클록 목표이며 PSRAM 버스의168MHz 동기 동작을 주장하는 값이 아니다.

## 작업 의미

**실기 코어의 메모리 배선 구현을 위한 후보 선정·기한 검증**이다. 보호 reader를 연결하면 기존84MHz가 그대로 통과할 것이라는 가정을 실제로 배제했고, 보호 순서와 정상 NES 속도를 유지하는 후보를 확보했다. 게임 기능·SMB3 호환성 완료나168MHz 보드 타이밍 통과는 아니다.

다음 작업은 같은 후보의 PLL/클록·reset·독점 소유권·자원·STA 가능성을 먼저 확인하는 것이다. 기존 로더는8MHz에서 WRITE3클록=375ns다. 이를168MHz에 그대로 연결하면17.856ns로 짧아지므로 금지한다. 읽기 도메인 분리 또는 쓰기 시간 매개변수화 중 실제 구현을 선택하고 검증해야 한다. guard085의8MHz/20–22MHz heartbeat·timeout 가정도 그대로 사용할 수 없다. 비동기 raw fault 취소, 각 도메인 동기 reset 해제, SPI/CHECK/RUN 독점 소유권을 보존한다.

과거059의959/963LAB·가상핀·PLL0은 최종 보드 여유가 아니다. 같은 후보의 물리 fit/STA에서168MHz가 불가능하면 reader/서비스 구조를 다시 선택하며 NES 감속이나 프레임 버림으로 덮지 않는다. 실제 SNES 소비자/DMA/표시 기한과 최소 RUN의 진행 관측·오류 종료·044 복원도 남아 있다. 이 조건을 준비하면 실기에서 새 데이터를 얻고,119에서 통과한 같은 전체80KiB·BASE·ENTRY는 반복하지 않는다.

119 동일116/097 CF86의 전체80KiB·메뉴 복귀·사용자044복원 성공, 그 시험의 GBC 플레이 미보고,113 정지 원인 미확정은 유지한다. 외부 E1/E2·8µs·양 클록 정지 lockedHIGH CE9µs 반례는 해결되지 않았다. 제한 진단6완료/5부분/1미완료는 게임 완성률이 아니다. 첫 게임은 SMB3(J),mapper4,PRG256KiB+CHR128KiB이며 현재80/96KiB 진단의 메모리 크기·불변 CHR·배경 전용 검증과 구분한다.
