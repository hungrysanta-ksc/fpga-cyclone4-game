# NES161 실기 결과 — 첫 레벨 플레이·정상 종료 통과

이번 실기에서 SMB3(J)의 첫 레벨 진입과 이동·점프가 확인되었고, 약60초 실행 구간을 ROM 오류 없이 마친 뒤 메뉴로 복귀했다. 사용자는 대시도 정상이라고 확인했다. **첫 레벨 플레이를 막던 종료 현상은 이번 세션에서 재현되지 않았다.** 다만 아래 방향을 누르고 있어도 마리오가 일어서는 현상이 남아 있어, 지속 입력과 게임 전체 호환성까지 완료된 것은 아니다.

[기존 구현·검증](GAME161-RESULT.ko.md) · [실기 수치·입력 이력](game161-hardware-verification.json) · [현재 인계](../cores/nes/HANDOFF.ko.md)

60.660초는 펌웨어 실행 구간이며 제목·선택·월드맵까지 포함한다. 첫 레벨 안에서만60초 플레이했다거나 외부 시계로 정확한60초를 측정했다는 뜻은 아니다. 최종 메뉴 출력은 로그의 PREPARED 표시뿐 아니라 영상과 사용자 보고로 확인했다.

67.43초 영상 전체를1초 간격으로, 후반을0.5초 간격으로 추가 확인했다. 약18~23초 및29~65초의 레벨 장면과 이동·점프·스크롤, 약66초의 메뉴가 보인다. 물리 컨트롤러는 보이지 않으며 음성·오디오는 분석하지 않았다. 카메라와 CRT의 대각선 띠는 기존 사용자 설명대로 판정에서 제외했다. 표본 영상만으로60fps·속도 정확성·무점멸을 판정하지 않는다. `screen_frames=365`는 `screen_telemetry_trusted=0`이므로 실제 표시 프레임 수나 FPS로 사용하지 않는다. APU 채널 차단은 유지되어 소리 구동 통과도 아니다.

## 남은 문제 — 방향키를 누르는 동안 입력 해제

사용자는 DOWN을 누르고 있는데 마리오가 반복해서 일어났다고 보고했다. 로그는 게임이8비트를 끝까지 읽은 뒤 값이 바뀐 사건250개 중 마지막16개만 보존한다. 앞234개는 덮어써졌으며,250회를 실제 버튼 누름 횟수로 해석하면 안 된다.

마지막 이력 초반은 `NONE → DOWN → NONE → DOWN → NONE → DOWN → NONE`이다. 뒤에는 `A → A|LEFT → A → A|LEFT → LEFT → NONE`, `RIGHT → NONE → RIGHT`도 있다. 사용자의 유지 입력 문제와 부합하는 해제 상태가 **게임 소비 지점**에 기록되었다. 그러나 물리 버튼의 연속 누름 시점과 원본 SNES 패드 스냅샷이 없어, 의도한 해제인지 어느 전송 단계에서 바뀐 것인지는 아직 확정하지 못한다. 의도적 연타 기능이 원인이라고 단정하지 않는다.

소스 대조상152부터 표시 유지 구간의 매VBlank에 패드를 수집하며161도 이 경로를 유지한다. 따라서 이를 새로 구현하는 작업은 중복이다. FPGA `current_buttons`는 새 스냅샷 수신이나 reset 전까지 보존하므로, DMA 중 폴링 공백만으로 자동으로0이 된다고 설명할 수 없다. 기존 클라이언트 시험은 모델 입력 전달을 검증했지만 실물 자동 패드 읽기부터 NES 직렬 소비까지의 지속 누름을 검증한 것은 아니다.

## 다음 작업 — PR103 머지 후

1. 실제 `$4212` 자동 패드 읽기 busy와 `$4218/$4219` 스냅샷 시점, `$6002/$6003` 수집·commit을 대조한다.
2. 요청/응답 CDC와 `current_buttons`, NES strobe/read 직렬 소비를 연결해 지속 DOWN 및 다른 버튼 동시 입력에서 값이 유지되는지 최소 경계 시험으로 확인한다. 원인을 확인하기 전에 임의 debounce·해제 지연·연타 억제를 넣지 않는다.
3. 필요한 변경과 최소 검증 후 같은 SMB3 첫 레벨에서 앉기 유지·이동·점프·대시를 시험한다. 입출력 양쪽 관측이 꼭 필요하면 범위를 제한하며, 일반 디버그 확장으로 실기 시험을 미루지 않는다.

161 캐시 보존,159 실제 CPU/DMA 읽기 조건,160 rendering restart, 유한 실행·STOP/base/menu를 보존한다. 현재 M9K56/56으로 무조건적인 이력 RAM 추가는 피한다. 연속 화면 전송·속도 정확성·APU 복구·저장·다른 매퍼는 후속 과제로 남는다. 전체 IO/MTBF/PCB2ns 가정/reset recovery 제약은 기존 구현 보고서의 미완료 상태를 유지한다. 이번 성공으로 이를 소급 승인하지 않는다.

## 기록 범위와 보존

이번 변경은 제출된 로그·영상 분석과 현재 계획 갱신뿐이다. 새로운 RTL·MCU·ASM·시험판·Questa·Quartus 실행은 없다. 기존 동결161 검증의 `physical_test=false`는 제작 당시 기록으로 그대로 두며 현재 실기 결과는 이 문서가 보완한다. 정상 종료 이력의 `history_flags=1`에는 오류 고정 비트가 없으므로 일반 필드명 `INCLUDING_FAULT`만 보고 PPU 오류로 오인하지 않는다.

원본 TXT·영상은 로컬에 보존하고 Git에는 수치·해시·분석만 기록한다. 동결161의2238파일 manifest `fcd86aa4cf794770c27b1c80f5cbc16a883824a6800b1ce1d8f66789ea72097a`, ZIP `5c075d858ad1f8cacf2d6c81fc9186565d305817c6ca0d65196bc1bfcf91a11a`와 이전 공개 소스 핀은 변경하지 않는다. 같은161/044/GBC/A-B/무변경 전체 부팅을 반복하지 않는다. 사용자 머지 전에는 다음 구현을 시작하지 않는다.
