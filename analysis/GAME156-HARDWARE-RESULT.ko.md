# NES156 실기 — Select 동작 확인, Start 이후 같은 PPU 오류

**Select로 커서를 이동하는 데 성공했고, Start로 진행하면 이전155와 같은 PPU 읽기 기한 오류로 종료됐다.** 사용자가 실제 메뉴 복귀를 확인했다. 입력 관측·오류 회수는 통과했지만 스테이지 플레이는 아직 실패다. 이번 결과를 PR98에 추가하며156 펌웨어·FPGA·ZIP·동결 증거는 변경하지 않는다.

## 로그와 사용자 관찰

- 보드65/관측부DF로156 조합이 확인됐다. ROM393216바이트 적재·전체 비교·검증 통과, 진행104기록(seq0~103, 각512바이트)이 연속이고 시간 역전이 없다.
- `apu_channel_writes_blocked=1`, `pad_trace_valid=1`, total=count=15, flags=1이다. 최근16건 한도 내여서 이력 덮어쓰기와 시각 래핑이 없고, 오류/STOP 후 고정된 기록이다.
- `run_passed=0`, `run_rom_error=2`이며 `run_error=1`은 MCU 오류 분류다. CPU ROM 오류1 또는 전체 실행 성공으로 읽지 않는다.
- `stop_ok=1`, `run_stop_error=0`, `base_restored=1`, `safe_to_reload=1`. 마지막/STOP 카운터35827852가 같고 최종 TXT1598바이트가 저장됐다. `menu_state=PREPARED_RESET_HELD`와 별도로 사용자가 실제 메뉴 복귀를 확인했다.

## 게임이 읽은 버튼

| 1~4 | 121139200 / 121496576 / 121853952 / 123283456 | START → NONE → START → NONE |
| 5~6 | 169383680 / 172601344 | SELECT → NONE |
| 7~8 | 184393216 / 185465088 | SELECT → NONE |

| 11~12 | 208337920 / 212982272 | SELECT → NONE |

Select는 마스크04, Start는08로 서로 구분되어 전달됐다. Select 네 차례의 수신·해제와 사용자 커서 이동 관찰을 함께 확인했다. 이는 “최초 입력 이후 모든 버튼이 실패한다”는 가설과 맞지 않는다. 이동·점프·A/B 버튼 정상 여부는 여전히 미확인이다.

초반 Start는 두 번의 수신 구간으로 기록됐다. 중간 NONE과 다음 START 간격은357376클록이다. **물리적으로 두 번 눌렀다는 뜻이나 중복 입력 결함 확정은 아니다.** 완료된8비트 읽기의 상태 변화만 기록하며, 실제 클릭·SNES 원본 스냅샷·부분 읽기·누락된 짧은 입력은 기록하지 않는다. 같은 버튼을 유지한 중복 읽기는 생략된다. 이번 커서 선택 성공을 막는 증거는 없으므로 PPU 오류 수정에 앞선 새 차단 조건으로 삼지 않는다.

시각은256클록 단위로 내림한 NES 마스터 클록이며 MCU의 진행 밀리초·RUN 관측 카운터와 같은 단위가 아니다. 마지막 Start 해제가 기록됐지만 최초 오류와 동일 단위의 시각이 없어 버튼부터 오류까지의 정확한 지연은 산출하지 않는다.

## 남은 정지 원인

| 항목 | 155 Select 실패 | 156 Select 성공 후 Start 실패 |
|---|---|---|
| ROM 오류 | PPU 기한 오류2 | PPU 기한 오류2 |
| 주소 문맥 | `e200c2f4:30217a18` | 동일 |
| PPU 상태 | `60820800:28606060` | 동일 |
| PPU line / dot | 193 / 8 | 193 / 8 |
| 논리 / 실제·대기 물리 주소 | `0x0A18` / `0x217A18` | 동일 |
| age / 응답 / PPU 유효 데이터 | 1 / 0 / 0 | 동일 |

일반 배경 상위 비트면을 소비할 때 유효한 응답이 없었다. pending과actual 주소는 같지만, 직전 요청이 언제 발행됐고 무엇에 막혔는지는 이 스냅샷으로 알 수 없다. 현재 `$2007` 읽기/쓰기 파이프는0, 렌더링1/스프라이트구간0이다. dot8에서 hint0은 예상되는 상태이므로 선행 읽기 자체가 없었다고 단정하지 않는다. PSRAM 불량이나 반환 바이트 손상으로 확정할 증거도 없다.

음원 채널 쓰기를 차단한 상태에서도 같은 오류가 남았다. 따라서 **내부 음원 채널·DMC 활동만을 유일한 원인으로 삼는 설명은 부족하다.** Select 통과는 진전이지만 차단에 따른 APU 상태·게임 분기 변화, 관측부 추가와 새 배치도 있어 사운드가 Select 실패의 원인이었다고 확정하지 않는다. CPU의 사운드 처리 코드는 계속 실행되고 프레임 카운터도 유지되므로 사운드 관련 코드의 ROM 점유 영향까지 배제하지 않는다. 음원 차단은 진단용이며 정상 오디오 구현이 아니다.

진행 기록의 DISPLAY_NEXT232.920초→DISPLAY_STOPPED245.410초는12.490초, 이후 메뉴 준비248.570초까지3.160초다. 실제 첫 화면·입력·벽시계 시간을 측정한 값은 아니다. `screen_frames=22`, `screen_telemetry_trusted=0`을 FPS나22개의 정상 표시 프레임으로 해석하지 않는다.

## 다음 작업

우선순위는 BG 상위 비트면 dot5~8의 예측주소→MMC3 물리주소→공유 ROM 승인→캐시·응답→샘플 경계다. 기존 소스·증거로 직전 CPU/PPU 점유, 매퍼 변경, 응답 지연 중 첫 실패를 좁힌다. 기존 관측으로 구분할 수 없을 때만 해당 경계의 최소 직전 이력을 추가한다. 음원 전체 재설계·모든 버튼 검증·새 일반 진단 체계를 선행 조건으로 만들지 않는다.

원인에 맞춘 변경의 최소 검증 뒤 같은 SMB3에서 Start→스테이지→이동·점프로 돌아간다. 기한 검사 삭제, 근거 없는 캐시 확대, 같은156/044/GBC/A-B 재시험, 변경 없는 장시간 전체 부팅 반복은 하지 않는다. 이 결과 커밋에서는 새 구현·빌드·실기 패키지를 만들지 않았다.
