# NES159 실기 — 월드맵 진입·이동 통과, 첫 레벨 전환 중 PPU 오류

**월드맵 진입과 방향키 이동에 성공했다. 첫 레벨에서 실제로 달리고 점프하는 단계는 아직 통과하지 못했다. A로 레벨에 진입하는 화면 전환 중 PPU 읽기 기한 오류2로 보호 종료됐으며, 60초 제한에 의한 정상 종료가 아니다.** 기존159 패키지로 재시험하거나 제한 시간만 늘릴 필요는 없다.

## 완료와 미완료

- 사용자 확인: 플레이어 선택에서 Start로 월드맵 진입, 방향키 이동 정상. 첫 레벨로 이동해 A를 누르면 진입 전환 중 메뉴로 돌아왔다.
-31.90초 영상의1fps 표본에서 커튼·타이틀·플레이어 선택·월드맵·화면 축소·메뉴 복귀를 확인했다.23~26초 구간은4fps로 추가 확인했다. 레벨 내부에서 플레이하는 화면은 보이지 않았다. 모든 프레임이나 음성·물리 버튼 클릭 시각을 분석한 것은 아니다.
-68/E2 식별, ROM393216바이트 적재·비교와 verified1/오류0,104개512바이트 진행 기록의 순번·시각 단조성 통과.
- `run_passed=0`, `run_error=1`, `run_first_error=1`, `run_rom_error=2`: 실행 중 관측한 ROM 서비스 오류에 따른 조기 종료. ARM은 오류 관측 시 반복문을 즉시 종료한다. `run_last=run_stopped=75239400`, `run_stop_error=0`, `stop_ok=1`, `base_restored=1`, 메뉴 준비 및 영상의 실제 복귀 통과.
- 펌웨어 `DISPLAY_NEXT=232680ms`, `DISPLAY_STOPPED=258920ms`: 구간26.240초. 메뉴 준비262110ms는 그 뒤3.190초. 전자는 실행·진입/종료 처리를 포함한 구간이며 게임 프레임 시간이나 정확한 오류 순간과 동일하지 않다. 영상과 펌웨어 시간도 별개의 기준이다. 오류 필드 자체가 시간제한 종료와 구분하는 근거다.
- 패드 변화33건 중 마지막16건이 보존됐다. DOWN/LEFT/RIGHT/UP/SELECT/START/A와 해제를 확인하며 마지막2건은 A→NONE. 앞17건은 덮어써져 처음 두 Start를 이 로그만으로 재구성할 수 없다. 버튼 처리 완료 시점의 기록이지 물리 클릭 시각이나 모든 게임 동작 정상의 증거는 아니다.

## 오류 위치가 달라졌다

이전158은 line193/dot8/물리217A18이었다. 이번159는 **line193/dot336/물리217000**이다. 문맥 `e70142e0:00217000`은 PPU 대기 읽기 진행 중, age2, CPU샘플1/유효1, PPU샘플1/유효0, reader응답0이다. CPU 데이터 부족으로 종료한 것이 아니다. 마지막 PPU 상태 `60d40800:01e00000`은 렌더링1/스프라이트0/ALE0/read2007·write2007파이프라인0, 내부vram주소0078/주소하위래치00을 나타낸다.

상대0은 최초 오류 클록이다. 주소는 서비스의 물리 주소이며 CPU PC를 뜻하지 않는다.

| 상대클록 | 관측 | 판단 |
|---|---|---|
| -15~-12 | dot333, PPU217B00, reader ready1/busy0, CPU필요0, 유효힌트0 | 읽을 기회는 있었으나 요청 없음 |
| -11 | dot334, CPU03F86E 요청 | CPU 읽기 한 건 발행 |
| -6 | dot335, CPU 응답, ready1 | CPU 점유 종료 |
| -5~-4 | reader ready1/busy0, CPU필요0, 유효힌트0, 요청0 | 이후에도 빈 구간 있음 |
| -3 | dot336, PPU217000으로 변경, 같은 행에서217000 요청 | 새 주소가 보인 즉시 읽기를 시작 |
| -2~-1 | 새 PPU 읽기 진행, 응답0 | 아직 데이터 없음 |
| 0 | dot336 샘플, CPU유효1/PPU유효0/응답0 | PPU 오류2로 종료 |

158과 달리 이 기록에서는 새217000의 유효한 선행 요청이 없다. CPU가 샘플 직전까지 reader를 붙잡은 것도 아니다. 실제 주소가 바뀐 뒤의 요청은 지연 없이 승인됐지만 샘플까지3클록뿐이었다. 159의 조기 CPU읽기 수정 이후 사용자가 이전에 막혔던 월드맵 진입을 통과한 것은 실기 진전으로 기록하되, 모든 읽기 기한 문제가 해결됐다고 표시하지 않는다.

## 다음 구현에서 확인할 경계

이번 이력의 `hint_valid`는 PPU의 원시 예측 신호가 아니라 서비스에 들어가는 **결합 조건**이다. 실제 연결은 다음과 같다.

```
game147_prefetch_hint &&
    (rom_ppu_valid || (ppumem_addr >= 0x3a0000 && ppumem_addr < 0x3a0800))
```

이력의 현재주소217B00은 해당 로컬 메모리 범위 밖이고 PPU유효0이므로, 원시 예측 신호가 있었더라도 이 결합 조건에서 차단된다. 다만 원시 예측/렌더링/PPUDATA 파이프라인의 **이전 각 클록 값**은 기록되지 않았으므로, 원시 신호가 실제로 켜져 있었다고 단정할 수 없다. 오류 순간의파이프라인0을 앞16클록 전체에 일반화해서도 안 된다.

또한 힌트 주소 비트는217078→217070이지만 유효0이며 필요한217000과도 다르다. 단순히 결합 조건을 제거하면 올바른 주소를 일찍 읽는다는 보장이 없다. PPU의 실제 주소는 `vram_a` 상위와 ALE/외부하위주소래치를 조합한다. 이번0078/래치00 불일치, 레벨 전환 중 렌더링 재개·PPUDATA 접근·ALE 관계를 먼저 대조해야 한다. 어느 한 CPU 레지스터 쓰기나 MMC3 IRQ가 원인이라는 증거는 아직 없다.

다음 작업은 dot333~336의 빈 reader 구간, 무효217078힌트, 마지막217000 요청과3클록 샘플 간격을 실제 PPU/래치/서비스 결선으로 짧게 재현하는 것이다. 최소한의 현재주소 유효 조건과 안전한 조기주소 생성을 확인하고, 정상 CPU/DMA·PPU 샘플과159 읽기 자격을 유지한다. 예측 조건을 무조건 풀거나 샘플 기한을 없애거나 PPU를 항상 우선하는 수정은 하지 않는다. 필요한 관측을 현재 범위에서 얻은 뒤 최소 변경 시험 → 동일 SMB3 첫 레벨 진입 → 이동·점프로 돌아간다.

이번 PR101에는 실기 결과와 다음 계획만 추가한다. 펌웨어·FPGA·ZIP·frozen159·이전 공개 소스는 변경하지 않는다.044/GBC 복원·같은159 재시험·추가 영상은 필요하지 않다. 음원 채널 차단은 유지됐고, 정상 오디오·레벨 플레이·속도·저장은 미완료다. `screen_frames=48`, `screen_telemetry_trusted=0`은 FPS 측정값으로 사용하지 않는다.
