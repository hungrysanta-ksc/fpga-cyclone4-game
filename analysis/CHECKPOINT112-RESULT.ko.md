# NES112 단계 로그 개선판

111 실기에서 최초 메뉴는 정상, 표식 선택 후1분 이상 로딩, 리셋으로 미복귀, 전원 재투입 후 메뉴 정상, 로그 없음이 보고됐다. 600초 관측 전에 종료했으므로 영구 멈춤이나 고장 종료 경로 진입을 확정하지 않는다. 기존 소스는80KiB 통신 대기만 최소113초이며 SD·설정 시간은 별도다. 정상044 복원·GBC 결과는 이번 보고에 없었다. 영상은 필요 없다고 안내했다.

사용자가 개선판 제작을 요청하여, 최종 메뉴 준비 후에만 남던094 보고서 외에 **진행 중 영속 체크포인트**를 추가했다. 기존에 승인한 정상 전원·80KiB 1회 범위와 수동044 복원을 유지한다.

## 구현

- `nes-progress-112.txt`를 진단 시작 때 새로 만들고512바이트 기록을 추가한다. 입력 열기, 검증, 구성 시작/준비, 적재 시작, 적재·비교16KiB 경계, STOP 시작/완료, 기본FPGA 복구 시작/완료, 메뉴 복사·준비를 구분한다. 각 기록에는 순번·단계·처리량·MCU 경과시간이 들어간다.
- 각 기록은 `f_write`→`f_sync`→`f_close` 성공 뒤 진행한다. 추가 작업 직전의 START 기록은 그 작업의 성공이 아니다. 정상80KiB 호스트 경로는33개 기록, 마지막은 `MENU_PREPARED`다. 이 기록도 실제 RESET 해제/메뉴 화면을 증명하지 않는다.
- 기록 전후에 CF86 상태를 확인하고, 동기식 전경 코드에서만 잠시 SD 쓰기를 허용한다. 로그 허용 중에는 FPGA 프레임을 보내지 않는다. observer/ISR/NMI에서 FatFS를 호출하지 않는다.
- 체크포인트의 제한 시간은 별도로 적용하고, 기존 IO 시작시각·남은 폴링 횟수를 그대로 복구한다. 메뉴의60초 예산을 재시작하지 않는다. 오류·불확실한 쓰기 뒤에는 닫기/재시도/복구 IO를 추가하지 않고 공유 고장으로 종료한다. CSS/NMI·공유 고장 이후 새로운 SD 기록은 금지한다.
- 기존 최종 `nes-verify-last-094.txt`,094 표식, CF86 FPGA, 정상044는 유지한다. ARM 버전만 `CF86-LOG112`로 변경했다. 화면 진행 UI는 추가하지 않았다.

## 검증과 한계

109의 실제C/FatFS/native SD/메뉴·하위 IO/CSS 통합을 재사용해24개 정상·고장 사례를 실행했다. 단계 로그의 SD 쓰기 실패5지점, CSS/NMI11지점, 진입 거부3조건, 정상2조건과 하위IO 고장3조건을 포함한다. 기존 고장 이후 명령·SD 에지·FPGA 프레임 금지 확인을 유지했다. 시간예산·중복 로그창 진입 거부는 별도 시험했다.

FAT16 80KiB와 FAT32 96KiB 정상 모델에서 **실제 FatFS로 로그 파일을 다시 열어** 순번과 마지막 기록을 확인했다. 후자는 파일시스템 회귀이며96KiB 실기 승인이 아니다. 제품 SD 명령은 각각1814/1943, 완료 후 시험기 전용 읽기 명령36/39는 별도 집계했다. 모형 SD backing image의 기록과 파일 재열기 결과를 모두 보존한다.

ARM184452바이트 SHA-256 `ac778c02d7561f2813c0930a8fecd3af67b4ca886455a214b068a3fbbb40fb16`, ELF SHA-256 `5862e9a8052ca36c283bd369cd82da1ac0d52574c5b7602dabf7ae7c1e126450`. 실제 벡터 `0x08018f95`→NMI `0x08018f94`, 기존15 store/0 call 종료 코드와 CSS 시작→체크포인트→입력파일 순서를 확인했다. 호스트와 ARM의 변경 C·헤더6개 해시 연결을 확인했다. ARM CPU에서 실행한 시험이나 전기적 시간 증명은 아니다.

실행 ZIP은588448바이트, SHA-256 `91a9c9cb9d1ec084be7725b3d2a7c80176c5eddb1d6f0b947d4375a2072b0889`.12항목이며 펌웨어 외8역할은109 원본과 같다. 새 FPGA/RTL/fit/STA/ASM/Questa 실행은 없다.

초기 준비기 문자열이 역사적 두 함수에 중복되어 arm01 준비가 중단됐다. 적용 범위를 `nes_menu_sd_probe`로 한정하여 arm02에서 성공했다. host01의 WinError623은 제한 환경의 GCC 실행 문제로, 호스트 실행에서 해결했다. ARM 검사기의 잘못된 사전 키를 고쳐 같은 ELF를 다시 검사했다. 초기 실패·중간 시험 및 Make의 첫 의존성 생성 재시도 로그를 보존했다. 자동 승인 검토 거부는 없었다.

## 결과와 다음 작업

**완료:** 단계 로그 구현, 관련 정상/고장·시간예산·파일 재열기·ARM 연결 검사, 개선판과044 복원 패키지. **미완료:** 새112의 실제 로그·메뉴 복귀·복원 관측. SD 전원 차단 원자성, MCU 최악 시간, E1/E2·8µs·전체NES 게임 실행은 보장하지 않는다. 경과시간 모형 값을 실기 예상 시간으로 쓰지 않는다.

사용자는 [안내](../docs/nes-checkpoint112-instructions.ko.md)에 따라80KiB를 한 번 실행하고 최대10분 관측 후 두 TXT 또는 없음/0바이트, 실제 메뉴 복귀·시간,044 복원 후 메뉴·GBC 결과를 제공한다. 다음 작업은 **실제 마지막 단계**로 원인을 좁히는 것이다. 영상·동일 진단의 반복을 먼저 요구하지 않는다.

이 작업은 실기 디버깅의 관측 기반 개선이다. 실기에서 멈춘 위치를 알 수 있도록 만들었으며 코어 배선·게임 호환성은 늘리지 않았다. SMB3(J) mapper4/384KiB 첫 목표,084/092 성공, 전체 준비도4완료/7부분/1미완료는 유지한다.111·이전 동결 증거는 수정하지 않는다.
