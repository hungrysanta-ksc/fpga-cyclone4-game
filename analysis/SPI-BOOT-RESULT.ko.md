# NES 054 SPI ROM 적재 경계 결과

**MCU용 C 전송 코드 → 044와 공유하는 SPI → 053 로더 → PSRAM 핀 쓰기**를 연결했다. 프레임 길이·CRC·완료 바이트 순번을 확인한 뒤 CS 종료 때만 명령을 반영한다. 적재 완료와 실행 시작을 구분한다.

| 검사 | 결과와 범위 |
| --- | --- |
| 전체 직렬 적재 | PRG64KiB+CHR16KiB, 81920바이트를 SPI와 실제 모델 핀 쓰기로만 적재 |
| 읽기·수명주기 | 81921회 읽기, 163894검사, 14오류 시나리오 통과. START/STOP/재시작, 조기 END/START, 부분/초과 프레임, CRC·중복·순번 오류, RUN 중 쓰기 거절 |
| 실제 C 전송 파형 | 139프레임/8896샘플 중 응답7784비트 일치. 64바이트 핀 쓰기, CRC 오류와 sticky fault 확인 |
| 기존 044와 공존 | 같은 SPI 핀의 F0/F1 응답 A5/44, PLL 상실 시 구동 차단·이미지 무효화 확인 |
| MCU 타깃 | Cortex-M4 코드 객체 컴파일 통과. 완성 STM32 펌웨어/메뉴 경로의 실행은 아님 |
| 공동 fit | 13866 LE, 948/963 LAB, 5158레지스터, 26 M9K. 053보다 +254 LE/+19 LAB/+142레지스터, LAB 15개 남음 |

전체 적재 시험은 시간을 줄인 **디지털 SPI 스트레스**이고 전기 타이밍 검증이 아니다. 실제 C 파형 재생은 250kHz 및 상승 후 +2µs 샘플 시점을 사용한다. 모델의 PSRAM 가정은 053과 동일하다. 두 시험과 공동 fit의 회로 소스 해시가 같다.

공동 fit는 053의 실제 코어·영상 생산/전송 회로에 새 SPI 경계를 추가한 자원 측정이다. 핀 22개는 배치되지 않았고 가상 핀 289개, PLL 0이다. H1 진단 프로그램/셸, 실제 SNES 소비자, 보드 클록·외부 IO 제약·STA를 포함한 최종 fit가 아니다. 남은 15 LAB만으로 보드 통합이 가능하다고 판정하지 않는다.

처음 두 파형 준비에서 진단 생성물의 하위 경로와 기존 H1 ROM 지역 신호의 이름 충돌을 수정했다. 실패 산출물은 로컬에 보존했다. 라이선스 오류는 없었고 기존 Starter FLOAT 경로를 사용했다.

## 다음 관문

1. 96KiB 전체 SPI 적재와 실제 NES 코어 실행을 새 경계로 연결하고, 실제 STM32 GPIO 소유권·SD/iNES 로딩 호출을 연결한다. 현재 C는 핀/시간 callback 기반 전송기다.
2. 물리 메모리 무결성 확인, 실제 NES 클록/reset, 소비자·마감·복구를 정한다. CRC8은 전송 검사이며 `loaded`는 PSRAM 무결성 확인이 아니다.
3. 추가 회로를 고려한 공동 자원 예산·필요한 최적화를 먼저 확인한다. 보드 핀/PLL/소비자가 들어간 fit/STA 뒤 복구 가능한 새 실기 쌍을 준비한다.

**044 실기 기준과 GBC는 유지했으며 새 SD 이미지는 없다.** 실제 코어 8프레임 결과는 이전 053의 증거다. 이번에는 새 SPI 경계의 핀 적재/읽기, C 파형 및 공동 자원을 검증했다.
