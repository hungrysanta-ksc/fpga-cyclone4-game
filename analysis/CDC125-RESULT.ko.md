# 125 — 메모리·영상 데이터의 클록 간 전달 시간 검증

## 작업 목표

PR70 병합 `85e98c9243ea917fc7879ef53caab76778556a66` 이후, 같은124 배치에서 reader와 영상 bridge의 데이터가 수신 전에 안정되는지 검증했다. **묶음 데이터 372개 출발점/종착점 쌍의 조건부 지연 제약과 디지털 캡처·유지 검사는 완료했다.** 첫 동기화 단계·reset·외부 IO를 포함한 전체 타이밍과 실기 RUN은 미완료다.

## 작업 내용

동결124 DB를 새 디렉터리에 복사해 세 corner의 교차 클록 setup 경로1,218개를 추출했다. 출발점/종착점은378쌍이며 데이터372쌍과 첫 동기화 단계 제어6쌍으로 분리했다. 합성은 reader의 `address_hold`를 서비스의 `pending_address`와 병합했다. 따라서 소스 이름을 추측하지 않고 실제 `pending_address`에서 chip/lane/PSRAM주소로 가는22쌍을 제약한다. 반환 데이터257쌍에는 서비스뿐 아니라 CPU/PPU/APU/DMA 직접 소비 경로가 포함된다.

요청과 응답은 각각 데이터를 고정하고 토글을 보낸다. 두 단계 동기화의 두 번째 값을 상태 회로가 다음 에지에서 소비하므로, 정상 디지털 클록·공통 reset·단일 보류 요청 조건에서 수신은 출발 뒤 최소 두 수신 주기를 기다린다. reader 반환은 데이터 캡처 뒤 HOLD/RELEASE까지 추가로 기다린다. 데이터를 다음 요청/응답까지 유지하는 조건도 관측했다. 독립 reset, 아날로그 metastability 실패, 임의의 클록 고장은 이 논리 증명의 전제가 아니다.

`get_path_info -data_delay`의 데이터 지연과 `set_max_delay`의 클록 기준 지연을 구분한다. Quartus25.1의 이 명령은 `-datapath_only`를 지원하지 않는다. 데이터 자체는 아래 예산보다 빨라야 하고, 별도 SDC 최대 지연은 수신 한 주기로 정한다. 최소 캡처까지 남은 한 주기는 여유로 남긴다. 정확히 하나로 해석되는 레지스터 쌍372개에만 제약하며, 전체 클록 false-path/clock-group 면제는 없다.

372쌍×3corner=1,116개 제약 결과가 통과했다. 원시 setup 목록1,218개에는 같은 쌍의 복수 경로가 있으므로 행 수가 다르다. 최대 데이터 지연은 원시 목록 전체에서 계산했다. 원시 최소 −8.477ns는 그대로 보존한다. 제어6쌍은 reader request/ack, bridge request/ack 및 두 방향 peer-up이며 이번 데이터 제약에 포함하지 않았다. 비동기 reset→release의 recovery/removal도 별도 미완료다. 이 결과는 전체 setup/hold/CDC 완료 선언이 아니다.

정확한124 reader/bridge/queue RTL을 사용하고 시험 클록을 STA와 같은22/84/168MHz의1ps 양자화 값으로 맞췄다. reader 두 위상에서1,050회 읽기 완료·26회 취소,bridge 세 위상에서 각13항목·6,426응답이 통과했다. 요청과 캡처 사이 실제 최소 관측은 reader 주소11.915ns/반환108.231ns,bridge 요청92.759ns/응답23.809ns였다. 수신 뒤 데이터 덮어쓰기까지 한 수신 주기 이상 유지하는 검사도 통과했다. 이 유한 위상 시험을 모든 위상·아날로그 MTBF 증명으로 확대하지 않는다.

동기화 첫 단계를 바로 소비하도록 바꾼 reader/bridge 부정 대조2개는 각각 주소/요청 도착 시간 검사에서 실패했다. 정상 실행의 회로는 변경하지 않았다. 전체 코어 프레임·합성·배치는 반복하지 않았고124 기준을 재사용했다. 원본 GBC/NES 제품 RTL·MCU·ARM/ASM·SD 패키지에는 변경이 없다.

### 실패와 보정 기록

- 최초 탐색 실행은 작업 디렉터리가 잘못되어 `live` 프로젝트를 찾지 못했다. 도구 실행 위치를 고쳤다.
- `sta02`는 데이터 예산4ns를 클록 기준 SDC에도 그대로 적용해 주소 경로가−0.175ns였다. 최종 `sta03`은 데이터4ns 제한을 유지하고 SDC를 프로토콜에서 독립적으로 유도한 한 주기5.952ns로 구분했다. 해당 상세 경로에는 데이터1.319ns,clock skew−2.797ns,uncertainty0.080ns가 기록된다. 임의로 음수 경로를 면제하지 않았다.
- 초기 동결 전 검사는 TimeQuest가 재생성하는 `db/live.taw.rdb`까지 동일해야 한다고 요구해 실패했다. 변경된 DB는 이 타이밍 분석 파일 하나뿐이며, 실제 routed/incremental DB는 전부124 해시와 같다. 미완료 묶음에 manifest를 쓰기 전에 검증기를 보정했다.
- protocol01은 당시 STA02 모듈에서 ROOT/sha/put만 가져왔다. sha/put의 AST가 최종 모듈과 같음을 검증하며, 실행한 프로토콜 드라이버·정상 RTL·모니터는 모두 공개 소스와 일치한다.

증거910파일,manifest `36a3effc9f2ce72ca3bd660724b9bc9392f0f9d0fe52aa0c95f54e6171c3039c`를 동결했다. [검증 메타](cdc125-verification.json)와 `verify_nes_cdc125.py`가 원시 경로·제약 목록·정상/부정 로그·소스·DB 보존을 재검사한다. 이전 완료 증거는 수정하지 않는다.

## 작업 의미

**실기 코어 배선의 클록 간 데이터 전달을 검증하고 재현 가능한 제약을 마련한 작업**이다. 새로운 게임 기능이나 mapper 구현은 추가하지 않았다. 메모리와 영상 데이터가 언제 안전하게 수신되는지에 대한 미완료 항목을 좁혔다.

다음은 같은124 배치에서 제어6쌍의 첫 단계 fanout·실제 동기화 체인·다음 단계까지의 settling slack 및 reset 해제 종착점을 확인해 남은 CDC 경계를 명시하는 것이다. 필요하면 정확한 회로/배치 속성을 고치되 전체 false-path는 피한다. 이후 로더 WRITE375ns·guard·독점 소유권·전체 자원·실제 SNES 소비자를 통합하고,진행 관측·오류 종료·044복원이 가능한 최소 RUN을 실기로 확인한다. 변경 없는125 데이터 시험을 다시 수행하는 PR은 만들지 않는다.

119의 전체80KiB/메뉴/044복원,122/124 코어 기준,SMB3(J) mapper4/384KiB 첫 게임 목표를 유지한다. E1/E2·8µs·양 클록 정지 lockedHIGH CE9µs 반례,113 정지 원인 미확정,119 GBC 플레이 미보고는 남는다. 제한 진단6완료/5부분/1미완료는 게임 완성률이 아니다. 이번에는 사용자가 설치할 새 패키지나 실기 요청이 없다.
