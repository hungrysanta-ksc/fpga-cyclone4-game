# NES140 실기 결과 — 동일 ROM 마감 실패와 메뉴 복귀 실패

**적재·대조와 TXT 저장은 성공했지만 NES 실행과 메뉴 복귀는 실패했다.** 사용자는 약9분 뒤 검은 화면이 지속되고 본체 리셋으로도 메뉴가 돌아오지 않았으며, 전원을 껐다 켠 뒤 메뉴가 정상 로드됐다고 보고했다. 실행 파일 진입 성공을 코어 실행 성공으로 해석하지 않는다. 동일044 복원 반복 시험은 앞으로 생략한다는 사용자 지시를 아래 시험 정책에 반영했다.

## 로그로 확인한 범위

| 구간 | 결과 |
| --- | --- |
| 후보 | NES-SCREEN-140 / FPGA5C / observerD7 일치 |
| 적재·전체 대조 | 81920바이트, verified=1, verify_error=0 |
| 코어 실행 | run_passed=0, 최초 실행 오류1, ROM 오류1 |
| 최초 실패 상태 | 440181c30800e184 —139와 동일 |
| CPU ROM 유효 샘플 | 최초·마지막·STOP 후 모두123028 —139와 동일 |
| 종료·기본FPGA | stop_ok=1, run_stop_error=0, base_restored=1 |
| 메뉴 준비 | 65536바이트 복사·검증 후 PREPARED_RESET_HELD |
| 사용자 육안 확인 | 검은 화면 지속, 메뉴 복귀 실패, 리셋 복귀 실패, 전원 재인가 메뉴 성공 |
| 독립044 복원·GBC | 이번 시험은 미확인; 전원 재인가 메뉴 성공과 구분 |

최초 오류에서 CPU 매핑 주소와 pending 주소는 모두0xE184, busy=1, pending_ppu=0, age=3이다. CPU 소비 시점에 cpu_valid=0, rom_response=0, rom_ready=0이었다. age는 NES 마스터 클록 수이며 CPU 사이클 수가 아니다. 이 주소를 CPU PC로 단정하지 않는다. 그 순간 요청 소유자는 CPU지만, 앞선 PPU 요청의 경합 영향은 배제할 수 없다. STOP 후 flags3은 reset 유지와 sticky 오류이며 RUN 중 reset을 입증하지 않는다.

진행 TXT는 순서와 시간이 일치하는47개512바이트 기록이다.

| 체크포인트 | 실행 시작 후 경과시간 |
| --- | --- |
| DISPLAY_NEXT | 524870ms =8분44.870초 |
| DISPLAY_STOPPED | 524940ms =8분44.940초 |
| BASE_DONE | 525820ms =8분45.820초 |
| MENU_PREPARED | 528110ms =8분48.110초 |

표시 구간의 기록 간격70ms는 MCU 처리 시간을 포함한다. 실제 화면 표시 시간이나 정확한 오류 시각이 아니다. 약9분은 주로 ROM 적재·전체 대조에 사용됐다. NES가9분간 정상 실행한 뒤 멈췄다는 뜻도, 더 기다리면 진행된다는 뜻도 아니다.

## 메뉴 준비와 실제 복귀를 구분해야 하는 이유

140에 사용한 `nes_menu_diagnostic.c`의 `nes_menu_diagnostic_prepared()`는 reset을 유지한 상태에서 최종 TXT와 MENU_PREPARED를 저장한다. 이후 `main.c`는 reset 해제,100ms 대기, CIC 상태 처리, 메뉴 상태 전송, 복귀 오류·SRAM 검사를 거친다. 검사 실패 시 reset을 다시 유지하고 차단할 수 있다. `nes_menu_diagnostic_released()`의 RETURN_READY_RESET_RELEASED는 `save_report(..., false)`로 UART에만 출력하고 SD에는 저장하지 않는다.

따라서 **MENU_PREPARED가 마지막인 것은 현재 로그 설계상 정상이며, 그 뒤 MCU가 멈췄다거나 reset을 한 번도 해제하지 않았다는 증거가 아니다.** 반대로 이 로그로 메뉴 실행 성공을 주장할 수도 없다. 이번 사용자 관찰로 실제 복귀 실패는 확정됐지만, 해제 전 차단·해제 후 재차단·메뉴 시작/통신 실패 중 어느 경로인지는 아직 구분되지 않는다. 전원 재인가로 메뉴가 로드된 사실은 정상 부팅 경로가 남아 있다는 근거다.

## 140 수정의 판정과 다음 작업

140은 READ16/168MHz와 핀 유지 시간을 보존하며 RUN ACK를 RELEASE에서 HOLD로 한 에지 앞당겼다. 기존 지연 모델에서의 개선과 제한 프레임 통과는 유효한 모델 결과지만, **실기에서는 최초 오류가 그대로여서 해결책으로 검증되지 않았다.** 요청5ns/ACK8ns 모델이 실제 보드를 충분히 설명한다는 가설을 재검토해야 한다. 새 식별자가 확인됐으므로 단순히139를 다시 실행한 것으로 처리하지 않는다.

1. 메뉴 준비부터 실제 메뉴 시작까지의 reset·CIC·SRAM·보호 상태 전환을 먼저 좁혀 확인한다. SD의 마지막 기록만으로 reset 위치를 추정하지 않는다. 필요한 관측은 이 경계에 한정하고, RUN 중 SD 금지와 오류 시 reset 유지 원칙을 지킨다.
2. 동일0xE184/샘플123028 실패를 회귀 기준으로 유지한다. 실제 요청 시작·이전 PPU 경합·응답 동기화·CPU 소비 경계를 비교하고, 모델과 실기의 차이를 설명하는 수정만 채택한다. 근거 없이 읽기 창을 줄이거나 deadline 검사를 끄지 않는다.
3. 관련 경계 확인과 수정 후보를 묶어 다음 실기 패키지를 만든다. 동일140 재시험·추가 영상·무변경 fit·저장/부품 시험은 요청하지 않는다. 화면이 정상화된 뒤 패드, 첫 목표 SMB3(J) mapper4/384KiB, 오디오로 진행한다.

이번 결과 반영에서는 새 펌웨어·FPGA 빌드·패키지를 만들지 않았다. 원본 두 TXT는140 동결 증거 밖에 보존했고 [관측 메타](screen140-hardware-observation.json)에 SHA-256과 해석값을 기록했다. [140 제작 결과](RESPONSE140-RESULT.ko.md), 기존 패키지와 고정 소스는 보존한다.

## 앞으로의 실기 시험 정책

- 사용자 지시에 따라 **동일044 복원본을 매번 설치하고 메뉴·GBC를 다시 확인하는 반복 시험은 생략한다.** 이전 성공 근거와 복원 파일은 유지한다.
- 후보 자체의 STOP→기본FPGA→메뉴 복귀와 전원 재인가 결과는 새 후보의 동작 결과이므로 별도로 기록한다. 이를 독립044 복원 시험과 혼동하지 않는다.
- 복원 파일/설치 경로가 실제 변경되거나 기존 정상 경로의 회귀 근거가 생긴 경우에만 변경점과 재확인 이유를 명시해 필요한 범위를 다시 정한다. 단순 후보 번호 변경은 반복 시험 사유가 아니다.
- 과거 동결 실행 안내의 매회044 시험 문구보다 이 정책과 현재 HANDOFF를 우선한다. 생략한 시험을 새 PASS로 기록하지 않는다.
