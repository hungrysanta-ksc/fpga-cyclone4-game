# 133 실제 상위 회로의 RUN·reset·CHR 시작과 종료 검증

PR78 병합 `4df157e5fbc8ce0d92a93b59eea0e8c1cbe91879`에서 시작했다. **131fit05의 실제 상위 회로에서 RUN 시작과 취소, CHR 용량 변경, CPU의 최초 메모리 읽기를 확인했다.** 새 생산 RTL이나 배치 변경은 없다.

## 작업 목표

132에서 별도 검토 대상으로 남긴 CHR 설정183쌍과 RUN/오류 제어115쌍의 기능 계약을 실제 결선에서 확인한다. 설정이 안정되기 전에 코어가 실행되거나 STOP/오류 이후 reader가 계속 접근하는지 검사한다. 과거 단독 reader 시험을 전체 상위 회로의 동작 증명으로 상속하지 않는다.

## 작업 내용

고정131의 상위 `nes_live_joint`와 실제 CPU/PPU·ROM 서비스·내부 RAM 초기화·SPI 명령 해석기·로더·clock guard·reset·transport를 포함한37개 입력 파일을 사용했다. 시뮬레이터가 거부하는 초기값 없는 선언4개만 앞으로 옮겼으며, 변환 전후 해시와 정확한 이동 내용을 기록했다. 결선·절차·식은 그대로다. 도구가 합성한 기존 배치 원본은 수정하지 않았다.

PLL은 이상적인84/168MHz 클록과 즉시 lock 모델로 대체했다. PSRAM은 기존70ns 핀 모델이다. 이미 검증한80/96KiB 전체 쓰기와 CHECK를 반복하지 않기 위해 합성 시험 이미지·적재 바이트 수·검증 완료 플래그를 초기값으로 넣었다. **이 부분은 실제 MCU/SD/전체 SPI 적재 시험이 아니다.** BEGIN/END/START/STOP 및 잘못된 CRC는 실제8바이트 SPI 프레임을 통해 처리했다. 검증 완료 플래그를 넣지 않은 START는 실제 해석기가 오류8로 거부했다.

CPU 시험 이미지는 reset vector `$8000`, 명령 `JMP $8000`으로 이루어져 있다. 상용 ROM은 사용하지 않는다. 실제 CPU가 요청한 주소와 PSRAM 응답을 바이트 단위로 대조했다. 외부 CHR 입력을 바꿔도 로더가 수락한 용량만 쓰는지, STOP 이후 같은 이미지 재시작과16↔32KiB CHR 재적재 시 소비자가 reset에 잡히는지도 확인했다.

## 작업 결과

최종 **test03**, source clock 위상0/3.5ns 두 경우 모두 통과했다.

| 항목 | 두 위상 합계 또는 관측 |
|---|---|
| RUN 시작·core reset 해제 | 20회 |
| 취소·START 차단 | 22회 |
| 실제 ROM 서비스 요청/응답 | 420회/412바이트. 중간 취소된 요청8개 포함 |
| CPU 실행 | 모든 RUN에서 `$FFFC/$FFFD` 읽기 후 `4C 00 80` 명령·피연산자 반복 확인 |
| 내부 RAM 초기화 | RUN마다 8,192개 scrub clock 후 core reset 해제 |
| STOP·재적재 | 같은 이미지 재시작, STOP 후 CHR16↔32K 변경 |
| 오류 종료 | CRC 오류, 원시 reset, NES clock 정지, memory clock 정지, 미검증 START 거부 |
| 실제 결선 부정 대조 | memory_ready reset 조건 제거, RUN reset 조건 제거 모두 검출 |

각 위상의 취소/차단은 STOP2·CHR 재적재 전 STOP2·SPI CRC2·원시 reset2·source clock 정지1·memory clock 정지1·미검증 START1이다. 한쪽 클록을 다시 켜도 guard fault는 유지되고 RUN이 재개되지 않았다. 응답412바이트는 매번 RAM 모델의 해당 주소와 같았으며, reset vector와 명령 피연산자 순서도 별도 검증기로 확인했다.

START의 RUN 신호에서 core reset 해제까지 최소 **372,513.658ns**, 마지막 CHR 변경에서 해제까지 최소 **388,718.502ns**였다. 이는8,192주소 초기화를 포함한 디지털 모델 관측값이다. 실제 보드 지연·WCET·입출력 승인값이 아니다. CHR 설정은 소비자가 reset에 잡힌 동안 바뀌고 RUN 중 유지됐으며, 첫 요청 전 안정 시간은1 NES clock 이상이었다. 132에서 관측한 CHR 데이터 경로 최대8.759ns와 기능적 안정 구간을 구분해 기록한다. 새 STA 예외를 추가하지 않았다.

현재 reset/요청 결선의 기능 계약은 이 모델과 두 위상에서 통과했다. 그러나 모든 위상·게이트 지연·조합 글리치·비동기 pulse 폭·metastability를 증명한 것은 아니다. clock 정지 뒤 핀 취소는 **10µs 뒤 관측**했으며8µs 보장을 주장하지 않는다. reset assertion 검사의1ps는 시뮬레이터 delta 안정화 대기이고 실제 하드웨어 지연이 아니다. 132의 비동기 reset 체인 입력107음수행을 삭제하거나 기능 통과만으로 물리 승인하지 않는다.

PPU와 encoder/transport reset은 실제 연결돼 있지만 `arm=0`, SNES 버스는 idle이다. 따라서 PPU 렌더링·패킷 소비·실제 SNES 소프트웨어·영상·입력·오디오·게임 호환성은 이번에 검증하지 않았다. 실제 CPU 실행은 확인했으나 전체 NES 동작 완료와 구분한다.

test01은 Quartus가 허용한 forward declaration을 Questa가 거부해 컴파일 실패했다. 초기값 없는 선언4개를 이동한 test02는8RUN/위상의 초기 시험을 통과했다. test03에서 CHR 변경 재시작·모든 응답 바이트 대조·미검증 START 거부를 추가한 뒤 다시 통과했다. 초기 로그와 실행 소스를 모두 보존했다. reset gate 제거 부정 대조는 각각 RAM 초기화 생략, RUN 전 소비자 해제로 실패했다. 첫 elaboration 및 time0 VHDL 초기값 경고는 원문 로그에 남으며, 정상 시험의 Error/Fatal은0이다. 라이선스 오류·승인 검토 거부는 없었다.

동결 **265파일**, manifest `83c2acf15d4730e4c207382ddc6e0b5a78252c1d6c70b14c4c59146251eb24c5`. 공개 검증기는 입력 해시·선언 이동·20회 reset vector/명령 읽기·전체 응답·취소 원인·부정 대조를 다시 확인한다. 새MAP/FIT/STA/ARM/ASM/실기 패키지/실기 시험은 없다. 완료 finalizer와 archive044–133은 수정하지 않는다.

## 작업 의미

**실기 코어 동작을 위한 시작·종료 결선의 통합 검증**이다. reader 단독 수준에서 실제 CPU와 메모리 초기화·SPI 명령·reset을 포함한 상위 회로 수준으로 진전했다. 새 게임/MMC3 기능이나 로그 기능 추가가 아니라, 이미 연결된 코어가 안전한 순서로 시작하고 중지하는지 확인한 작업이다.

다음 목표: 재사용131fit05/133test03의 RUN 기능 계약을 유지하고 실제 외부IO와 SNES 소비자 연결을 확인한다. 가상 포트와 실제 핀을 구분해 PSRAM/SPI/SNES 소유권·입출력 타이밍·소비자 관측 경로를 정리하고, 최소 RUN 상태·오류·044 복원을 확인할 실기 경로를 구현한다. 같은 초기화/전체쓰기/371CDC/배치를 무변경 반복하지 않는다.

131fit05의14,078LE/954LAB/같은 클록memory +0.041ns,132의데이터371쌍/16체인 결과를 유지한다. 물리 CDC·외부IO·MTBF·E1/E2·8µs·양클록정지CE9µs 반례는 미완료다. 119 실기 통과 범위와 SMB3(J)/mapper4/PRG256KiB+CHR128KiB 목표, 제한 진단 준비도6완료/5부분/1미완료를 유지한다.
