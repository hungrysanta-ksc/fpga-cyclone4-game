# NES 다음 작업 인계 — 054 이후

현재 후보는 **NES-R1-SPI-BOOT-054**다. [결과](../../analysis/SPI-BOOT-RESULT.ko.md)와 [프로토콜 계약](../../docs/nes-spi-boot-contract.md)을 먼저 읽는다. 실기 기준은044이며 새 SD 이미지는 없다.

## 완료한 경계

- 고정8바이트 SPI 프레임의 CRC/길이/순번을 확인한 뒤 CS 종료에서 명령을 반영한다. END와 START를 분리한다. 오류는 sticky이며 상태를 계속 읽을 수 있다.
- 기존053 로더/052 읽기 소유권을 그대로 연결했다. 80KiB 전체 직렬 적재와81921읽기/163894검사/14오류 시나리오를 통과했다.
- 새 C 전송 callback 파형을 materialized044+054 같은 SPI 핀에 재생해7784응답 비트를 확인했다. Cortex-M4 객체 컴파일을 통과했다. 아직 STM32 GPIO 소유권/SD 입력/메뉴 호출을 연결한 펌웨어는 아니다.
- 실제 코어 자원 형상에 SPI를 넣은 공동 fit13866LE/948LAB/26M9K 통과. **LAB15개만 남았다.** 보드 PLL/핀·실제 소비자·H1 프로그램 셸은 포함하지 않았다.

## 다음 구현 순서

1. 96KiB 전체 SPI 적재와 실제 NES 코어 실행을 연결한다. 기존053의2종8프레임을 새 SPI 로딩 뒤 재현하고 입력 소스/패킷 tick 위상 차이를 기록한다. 054 단위시험을 실제 코어 실행이라고 부르지 않는다.
2. 044의 실제 STM32 GPIO/SPI 소유권 및 USB IRQ 보호 아래 새 C 전송기를 호출하고, SD/iNES 입력 및 실패/복구 경로를 정의한다. 현재1바이트 명령+상태 조회는80KiB 약45.5초이므로 진단 처리량으로 명시한다. 블록 전송 최적화는 순번/commit 보장을 유지한다.
3. 물리 메모리 무결성 확인·공통 reset과049 scrub·실제 NES 클록을 연결한다. SNES_SYSCLK/PIN_A9는 후보일 뿐 주파수/지역/라우팅 미확인이다. CRC8/loaded를 PSRAM readback 검증으로 취급하지 않는다.
4. 남은15LAB 안에 보드 클록/소비자가 들어갈지 공동 예산부터 확인한다. 필요한 최적화는 동등성 회귀를 동반한다. 실제 SNES 소비자/frame deadline/복구·핀/PLL 공동 fit·외부 IO/CDC/STA가 끝나기 전 새 실기 이미지를 만들지 않는다.

044 화면 순환/RESET 복구·GBC 보고, 기존041 실패와043/044 SDF 실패,050/051 지연 대조 및053 실패 기록을 보존한다. 054 초기 경로 오류·신호 이름 충돌과 최종 통과도 로컬 원본에 남겼다. 원본053 이하 코드를 고치지 않았다.
