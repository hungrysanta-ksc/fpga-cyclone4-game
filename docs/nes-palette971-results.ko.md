# 911 팔레트·테이블 선행 발행 실험

## 목표

970에서 일반 데이터가 준비됐다고 가정한 재생은 911을 한 VBlank에 공개했다. 이번에는 MMC966 ARM이 실제로 생성하는 데이터를 사용해 911 공개와 다음 912 최종 ACK가 함께 앞당겨지는지 확인했다.

## 작업내용

MMC966 원본 바이너리에서 911 BEGIN부터 각 패킷 발행까지 ARM 기본 블록마다 버퍼를 읽었다. 기존 SPI·65816 이벤트, 타일 생산 기록과 실기 형식 BIN이 관측 전후 바이트 단위로 같았다. 아래는 마지막 불일치 직후부터 실제 송신까지 일치한 최초 관측 시각과 970이 요구한 발행 시각의 차이다. OAM은 이때 값이 일치해도 OBJ 슬롯 배정과 검사 완료 전에는 발행할 수 없다.

| 911 데이터 | 위상 1 지연 | 위상 2 지연 |
|---|---:|---:|
| 첫 팔레트 32B | 7.299ms | 7.300ms |
| 첫 OAM 176B | 5.218ms | 5.216ms |
| raw·테이블 앞 201B | 9.979ms | 9.724ms |
| raw·테이블 뒤 240B | 9.258ms | 9.005ms |

기존 ARM으로 같은 ROM 허가 일정을 실행한 대조군, BG 행 확정 뒤 팔레트만 발행하는 후보, 팔레트와 201B·240B 두 패킷까지 발행하는 후보를 비교했다. 두 후보 모두 대상 뱅크 재사용 조건을 통과하고 map 쓰기가 없으며 raw 행이 하나인 경우에만 선행 발행한다. 두 번째 후보는 OBJ 검사 임시 영역을 기존 버퍼 안에서 옮겨 조립 데이터의 수명을 보장한다. OAM은 슬롯 배정과 독립 검사 순서를 따른다. 일반 송신 함수를 그대로 쓴 음성 대조군은 두 위상에서 905–907 공개 후 908의 END 전 진행 검사에서 중단됐다. 완주한 두 후보는 scroll이 쓰는 END 전 송신 경로로 표준 DATA를 보낸다.

## 성과

| 빈 캐시 연속 실행 | 911 BEGIN→첫 팔레트 발행 | BEGIN→E9 발행 | 910→911 공개 간격 | 912 최종 ACK 지연 |
|---|---:|---:|---:|---:|
| MMC966 동일 조건 대조군 | 10.589 / 10.638ms | 9.00 / 9.05ms | 2 / 2 VBlank | 기준 |
| 팔레트 선행 | 6.688 / 6.690ms | 11.24 / 11.24ms | 2 / 2 VBlank | +16.828 / +16.815ms |
| 팔레트·테이블 선행 | 6.790 / 6.792ms | 13.10 / 13.10ms | 2 / 2 VBlank | +16.917 / +16.941ms |

순서는 위상 1 / 2다. 타일 생성에 필요한 E9가 팔레트와 같은 SPI를 쓴다. 두 후보에서 첫 BG 발행은 BEGIN 뒤 약 9.55–9.60ms에서 11.92ms와 13.65ms로 밀렸다. 두 후보 모두 연속 일정에서 처음 한 VBlank를 잃는 화면은 908이다. 911에서 첫 팔레트를 약 4ms 앞당겨도 908의 손실을 만회하지 못했다.

두 후보 모두 두 위상에서 905–912 여덟 RGB 화면이 대조군과 일치했다. 위상 1에서는 911의 SEAL 세대 불일치(0xE0)와 검사 중 STOP(0xE4) 각각에서 여섯 번의 공개 뒤 910 화면을 보존했다. ARM Flash는 대조군 212,460B, 팔레트 212,660B, 결합 후보 212,716B로 모두 212,992B 한도 안이다.

비교는 ARM 최종 링크·65816 실행과 ROM 경합 모델을 사용했다. 기존 MMC966 RTL 응답 시각을 고정한 재생에서는 905–912 공개가 동일 조건 대조군보다 한 VBlank 일찍 시작하므로 두 일정의 절대 ACK를 섞지 않는다. FPGA·65816·메뉴 복귀 구현 변경은 없으며 971 실기 FPS와 메뉴 복귀는 측정하지 않았다.

## 후속작업

이후 [972의 E9 우선 발행 시험](nes-palette972-results.ko.md)에서 ARM 팔레트 쓰기와 실제 링크의 공개·ACK까지 측정했다.

MMC966을 유지한다. 911에서 E9 발행을 BEGIN 뒤 9.00 / 9.05ms 이내에 우선 확보하고, FPGA가 ROM을 읽는 동안 ARM이 준비할 수 있는 첫 팔레트 조각부터 검토한다. 908과 911을 함께 통과하고 912 최종 ACK가 두 위상에서 앞당겨질 때 실기판을 만든다. [두 위상 원시 클록·패킷·오류 시험 결과](../analysis/palette971-results.json)

재현 순서는 다음과 같다.

1. MMC966·965wire5 원본 재생 폴더가 있는 TEMP에서 `check_nes_ready971.py TEMP PHASE TEMP/nes-ready971-pN.json`을 두 위상에서 실행한다.
2. `nes_palette971.py`의 `prepare`, `prepare-direct`, `prepare-pair`에 TEMP를 지정하고 생성된 각 link를 `build_nes_trial577.ps1`로 빌드한다. 새 작업 폴더를 사용한다.
3. 같은 스크립트의 `control`, `early`, `direct`, `pair`에 TEMP와 `--phase 1` 또는 `--phase 2`를 지정한다. early의 런타임 거부는 기대 결과다.
4. `analyze_nes_palette971.py TEMP TEMP/nes-971-VARIANT-FAULT --candidate VARIANT --guard FAULT`로 direct·pair 각각의 bad_seal·stop_decode를 실행한 다음 TEMP와 결과 JSON 경로를 주어 집계한다.
