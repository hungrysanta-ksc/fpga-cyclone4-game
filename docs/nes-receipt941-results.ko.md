# 941 · 906 OBJ 공급과 65816 뱅크 반환

940 ARM과 같은 ROM 허가 일정에서 906의 64B OBJ(token 8)가 늦어진 원인은 직전 576B OBJ(token 6)의 뱅크 반환이었다. 65816의 연속 범위 검사를 묶어 이 지연을 줄였지만, 다른 타일 37건의 공급 마감을 네 조건에서 모두 만족한 후보는 없었다. 적용 기준은 940을 유지한다.

## 906의 첫 검사부터 token 8 준비까지

단위는 21,477,272Hz master clock이다. 같은 위상에서는 기존·빈 캐시가 906에서 같은 시각을 보였다.

| 항목 | 935 위상 1 | 940 위상 1 | 935 위상 2 | 940 위상 2 |
|---|---:|---:|---:|---:|
| 첫 검사 | 11,431,937 | 11,431,852 | 11,811,574 | 11,790,682 |
| 마지막 수요 ROM 응답 | 11,772,713 | 11,772,713 | 12,130,073 | 12,130,073 |
| 두 뱅크가 모두 차서 대기 시작 | 11,774,215 | 11,774,215 | 12,131,575 | 12,131,575 |
| 두 뱅크 대기 → token 6 반환 | 30,281 | 30,559 | 29,899 | 31,441 |
| token 6 반환 → token 8 준비 | 304 | 304 | 304 | 304 |

각 위상에서 마지막 plan의 수요 읽기 7건, 허가 뒤 응답 35클록 합계가 같았다. 940은 첫 검사를 85·20,892클록 앞서 시작해 같은 ROM 허가를 더 오래 기다렸다. 935 대비 실제 공급 지연은 278·1,542클록이다. 이를 token 6 E8 응답 → ARM E1 발행 → 65816 수락 → 반환으로 분해하면 위상 1의 누적 차이는 −778 → −773 → +262 → +278클록, 위상 2는 +2,443 → +2,447 → +1,476 → +1,542클록이다.

## 변경과 대조

`prefix`는 OBJ offset 0부터 독립적으로 확인한 32B 단위 16개를 한 번에 두 바이트의 비트맵에 등록한다. 이미 받은 단위가 하나라도 있으면 해당 명령을 거부한다. 나머지 단위와 짧은 범위는 원래 검사로 처리한다. 576B 읽기 자체와 실제 소비 뒤 뱅크 반환은 그대로 실행한다. ARM 전체 링크는 940과 바이트가 같고 Flash는 212,992B이다. 이 65816 정적 ROM에는 9B가 남았다.

같은 ROM 패킹과 부트로더에서 원래 단위별 검사를 쓰는 대조군(`pairbase`)을 별도로 실행했다. 일반 8·16단위 묶음, OBJ 전용 좌표 계산, 검증된 길이 재사용의 네 조건 결과도 측정 JSON에 수록했다. `objaligned`는 909 두 OBJ를 네 조건 모두 940 안에 공급했지만 기존 캐시 위상 2에서 910 캡처를 놓쳐 14 VBlank를 썼다.

`prefix`에서 token 6 수락 → 반환은 940의 22,916·22,970에서 15,050·15,090클록으로 줄었다. token 8 준비는 **935보다** 8,406·6,114클록 빨랐다. 939에 대한 940의 입력 개선 방향도 유지했다. 단, 940의 정확한 시각과 비교하면 기존 위상 1의 909 첫 D1·planner가 518·517클록, 빈 위상 2의 911 입력 시작 → planner가 46클록 늦었다.

두 빈 캐시 위상에서 지정된 목적지에 SEAL 전 496B와 288B → 32B DMA를 확인했다. 빈 위상 1에서 909 token 19와 20의 FPGA 준비 시각은 세 판 모두 14,631,615·14,632,311이다. token 19의 준비 → 유효 E8은 940의 3,925에서 7,410클록으로 늘었다. token 20 반환은 940보다 5,664클록 늦었고 후속 token 22 준비도 같은 양만큼 밀렸다. 다음 비교에서는 token 19 준비 시점을 걸치는 E8 조회가 무엇을 반환하는지, 그 뒤 공유 SPI에서 어느 거래가 다음 유효 E8을 늦추는지 확인한다.

## 검사 및 재현

세대 905–912를 940 ARM과 후보별 실제 65816 코드로 재생했다. 렌더링·DMA 목적지·최종 ACK를 기존 독립 검사와 맞췄다. `prefix`에서 token 6의 중복 단위 0·15·17은 aperture 첫 읽기 전에 거부됐고, 576번째 바이트에서 STOP을 걸면 token을 반환하지 않았다. 부팅 복원·손상 거부, 잘못된 descriptor·SEAL, 표시 중 STOP, 288B DMA 이후 새 패킷·STOP 우선권도 검사했다. SRAM D0 네 곳과 base·메뉴 복구는 같은 해시의 940 ARM 검증을 사용했다. 수치는 ROM 중재·SPI 모델과 Mesen 버스 이벤트를 연결한 재생 결과다. 실기 FPS 및 새 보드 합성 결과는 이번 측정 범위 밖이다.

`tools/nes_receipt941.py prepare <mode> <temp>`로 ROM을 생성하고, `replay <mode> <temp> <phase> <cache>`로 두 위상과 warm/cold를 실행한다. `tools/check_nes_receipt941.py`의 `faults`, `guards`, `edges`가 오류·복구 경계를 검사한다. `tools/check_nes_longrun694_boot.py`로 부트 복원과 손상 거부를 독립 실행한 다음 `tools/analyze_nes_receipt941.py <temp> <out> <modes...>`로 [측정 JSON](../analysis/receipt941-results.json)을 생성한다.
