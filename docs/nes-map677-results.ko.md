# 677: bulk 완료와 map 구간 공급

**952의 두 위상 3 VBlank와 선행 map DMA는 회복했다. 그러나 위상 1의 마지막 ACK가 MMC666보다 0.484ms 늦어 전체 채택 조건은 실패했다. 실기·제품 기준은 MMC666을 유지한다.**

676의 초기 zero/BG 허가와 큰 마지막 plan 묶음은 그대로 두고 ARM의 map/bulk 중재만 두 방식으로 교체했다. 각 후보를 두 시작 위상에서 53화면씩, 총 212화면 재생했다. FPGA·65816·입력 형식·압축·독립 검증은 변경하지 않았다. [최종 비교](../analysis/map677-verification.json) · [예약 단독 비교](../analysis/map677-reserve-verification.json)

## 구현과 실제 비용

676의 952 후속 map 발행에는 E8 조회→기존 bulk 완료 E0→다음 tile E1→map E1이 반복됐다. map 한 패킷의 함수 실행은 0.75ms에서 1.18–1.75ms로 늘었다. 앞선 map이 수락됐어도 마지막 192B만 DMA에 선택되었고, 이후 새 패킷이 들어오면서 빈 큐 기회가 끝났다.

첫 `reserve` 후보는 bulk 토큰을 유지하면서 큐 한 칸을 예약하고 map 두 개까지 추가 조회 없이 발행했다. 실제로 offset2048/2240은 약 0.75ms로 줄었지만 나머지 구간에서 tile 삽입이 다시 반복됐다. 952 선행 DMA는 두 위상 모두 0B, 표시는 4회였다. 밀집 평균 +3.273/+3.322ms, 마지막 ACK +16.629/+16.916ms여서 기각했다. 전송 조회를 앞에서 줄인 비용이 뒤로 이동한 것이다.

두 번째 `run` 후보는 END가 이미 발행되고 warm 두 뱅크 이력이 유효하며, 마지막 발행 명령이 map인 경우에만 적용한다. 먼저 기존 bulk의 실제 검사된 소비 완료를 확인한 뒤, map 구간 안에서는 다음 생산자 조회·새 bulk 삽입을 미룬다. 기존 4credit 큐가 map을 운반하며 가득 차면 CRC·반환 수·마지막 identity를 확인한다. 일반 명령과 FINAL에서는 원래 생산자 조회와 bulk 처리를 재개한다. 새 상태·타이머·버퍼·고정 지연은 없다. E0 수신 완료를 VRAM DMA 완료나 최종 표시 ACK로 바꾸지 않는다.

map 구간은 주소가 반드시 연속이라는 뜻이 아니라 **연속으로 발행하는 map 명령 구간**이다. 수신 순서·map 범위 검사와 최종 coverage는 그대로다. cold/이력 미확정, 직전 tile, ordinary/FINAL에는 새 우선권을 적용하지 않는다. 모든 53입력에서 676과 plan bank의 count·first·decoded가 일치해 후속 큰 묶음이 분할되지 않았음을 확인했다.

## 같은 작업량·두 시작 위상 결과

| 항목 | MMC666 | 676 결합 | 677 map 구간 우선 |
|---|---:|---:|---:|
| 952 표시 간격 | 3/3 VBlank | 4/4 | **3/3** |
| 밀집951–955 합계 | 15/15 VBlank | 16/16 | **15/15** |
| 밀집 평균 변화 | 기준 | +3.272/+3.282ms | **−0.04455/−0.05386ms** |
| 957 마지막 ACK 변화 | 기준 | +16.948/+16.711ms | **+0.48395/−0.17609ms** |
| 952 선행 map | 1536/1536B | 192/192B | **1536/1152B** |
| 952 마지막 tile ACK, 직전 표시 기준 | 43.313/43.263ms | 32.536/32.594ms | 40.472/40.346ms |
| 952 마지막 map 수락, 같은 기준 | 33.125/33.405ms | 35.986/36.030ms | 33.607/34.067ms |

952의 map 수락은 원본보다 여전히 약 0.48/0.66ms 늦지만, 실제 빈 큐 DMA 선택이 맞아 표시 3회를 회복했다. 위상 1은232선 tile16B,247선 map384B,252선 map1152B를 전송했다. 위상 2는235선에서 map1152B를 전송했다. 실제 수락된 범위 안에서만 전송하는 것을 packet ACK와 CPU `idle524`/`ppu_dma`로 대조했다. 후반 DMA 상한·fresh beam·STOP/새 패킷 우선 코드는 기존665와 같고,252선1152B의 최악 수평 위치 경계 근거는 기존639/672 검증을 유지한다.

**676의 타일 이득을 모두 유지한 것은 아니다.** 952의 tile 완료는 MMC666보다 2.84/2.92ms 빠르지만, 676보다는 7.94/7.75ms 늦다. map 우선권으로 타일 이득 일부를 사용해 선행 DMA를 회복했다. 큰 plan 묶음 유지와 타일 완료 시각 유지는 서로 다른 조건이다.

911은 SEAL 수락186/188선·검사 후 진입212/214선,951은 두 위상239선이다. 957 최종 대기는 두 위상0회이고, 원본보다 VBlank 표시 횟수가 늘어난 입력이나 새 최종 대기는 없다. 모든 map·OBJ 작업량, canonical 출력과 최종 ACK는 독립 비교와 일치했다. 실제 두 bulk 슬롯 상한도 유지했다.

53화면의 SPI 총량은 MMC666 대비1616/1540B 감소했다. 입력 D1/D2와 출력 E1 데이터량은 같고, 조회·반환 거래와 plan 묶음 차이를 포함한 전체 합계다. 밀집 평균의 작은 감소를 실기 FPS 개선으로 환산하지 않는다. 같은 전체 시작 시각에서도 구간 진입 위상이 달라질 수 있으므로 마지막 ACK를 별도 필수 조건으로 유지했다.

map 구간 후보에서는 map 완료 때 OBJ 진행 조건이 달라져676의 map-tail 입력 callback은 실행되지 않았다. 다음 입력은 기존 최종 ACK 대기 경로에서 처리하며 전체 D1/D2 양은 같다. 이번 DMA 회복은 입력 callback의 효과가 아니라 앞선 map/bulk 중재의 변경 효과다.

## 마지막 ACK가 남은 이유

위상 1은955 표시 시각까지 원본과 같지만,956 표시가0.347530ms 늦어져957에 진입한다. 957 자체 표시 간격도0.134561ms 늘고 ACK 공개 차이0.001862ms가 더해져 마지막 ACK가0.483953ms 늦다. 이 차이는 추가 VBlank 한 번이 아니라 같은 VBlank 안의 DMA·설정·공개 지연이다.

956의 선행 map은 원본640/512B에서 두 위상128B로 줄었다. 957 위상 1에서는32.207ms·231선까지 map512B와 tile16B만 전송하고, 이미 수락된 offset2048의1536B map을 남긴 채 후속 tile 패킷을 수락했다. 957의 업로드 DMA 시간은 원본0.3789→0.8212ms로 늘었다. 위상 2는 선행 map1664B를 확보해 마지막 ACK도 빨랐다. **952에서 회복한 기회를956·957에서 다시 잃지 않는 중재가 남았다.**

## 안전 검사·자원·검증 범위

- 예약 후보: 실제 M4의13개 허가 경계,2개 제한 map suffix,3개 지연 완료 오류(CRC/credit/identity)를 검사했다.
- map 구간 후보:7개 map E1과4credit 상한, 기존 bulk 완료, 지연 CRC·STOP, identity·credit·cold·ordinary·FINAL·wrap 등13조건을 검사했다. 최종 표시 ACK는 시험기가 만들어 주지 않았다.
- 각 바이너리에서 초기 grant12조건, 마지막13-record grant7조건, END9조건, 입력/map-tail13조건, routing12조건, 메뉴 준비·해제5조건/marker4조건을 통과했다. 추가 reset 문맥이 없고 기존 STOP/부분 수신 무효화·cold 경로를 유지한다. 새 실기 복구를 시행했다는 뜻은 아니다.
- Flash는 예약212732B/free260B, map 구간212724B/free268B다. 후자는676보다36B,MMC666보다228B 증가했다. data10040/BSS19544B와 `nes_plan200_progress`의함수 stack32B는 동일하다. 전체 호출 stack 상한을 새로 입증한 것은 아니다.
- FPGA·65816 바이트가 같아665의 전체15324LE·962LAB·56M9K 및 setup+0.511/hold+0.149/recovery+1.828/removal+0.393ns를 재사용했다. 새 FIT/STA나 새 회로 절감은 없다. 실제 M4·65816에CPI2·SPI/IRQ 모형·반복 ROM 달력을 적용한 결과이며, 전체 live NES/PSRAM과 물리 FPS 증명은 아니다.

## 재현·다음 순서

`prepare_nes_map677.py <676 joint01> <새 폴더> --mode reserve|run`은676 firmware hash를 확인하고 `nes_plan_service200.c`만 변경한다. `build_nes_trial577.ps1`로 전체 링크한 뒤 `check_nes_map677.py` 또는 `check_nes_map677_run.py`를 실행한다. 전체 재생은 기존 `test_nes_idle676.py`와 동일한 인자를 사용한다. 실제 인자는 private `probes/nes-map677/replay.ps1`·`run-replay.ps1`, 결과는 ASCII Temp `nes-map677-reserve1/2`·`nes-map677-run1/2`다.

시작은7288416/7467100 master clock이며905–957의53화면을 연속 실행한다. `analyze_nes_map677.py --mode reserve|run`이 실제 수락 범위·DMA·표시·ACK와자원을 대조한다. 두 후보의 원시 로그·실행 바이너리·소스·검사는 [private 보관 요약](../analysis/map677-archive.json)에 연결한다. 게임 ROM/save/RESTORE와 기존 설치본은 변경하지 않았다.

다음은 **956에서 넘겨받는0.3475ms와957 자체0.1364ms를 함께 줄이는 경계**다. 952의3회·선행 map과 큰 plan 묶음을 유지하면서, 이미 수락된 map 범위와 후속 tile 패킷의 준비·credit·수락·실제 DMA 선택을 연결한다. 타일을 무조건 미루거나 큐를 계속 채우는 방식 모두 단독 해법으로 채택하지 않는다. 우선권 전환에 실제 DMA 진행 신호가 필요하면 독립 identity·STOP/CDC·Flash/LE 예산부터 확정한다. 고정 대기·위상 상수·같은 예약 수의 반복 탐색은 보류한다. 두 위상의 마지막 ACK까지 통과하기 전에는677을 전달하지 않는다.
