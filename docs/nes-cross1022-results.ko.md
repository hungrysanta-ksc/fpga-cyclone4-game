# 별의 커비 주 측정과 모험도 4 교차 검증

별의 커비 일본판을 주 측정 게임으로, 모험도 4 일본판을 회귀 대조군으로 정했다. 모험도의 실기 기준은 MMC1012다. 두 번의 실기에서 1–30초는 23.55·24.10 FPS, 30–60초는 24.47·24.93 FPS였다. 커비 실기 FPS는 아직 미측정이다. [MMC1012 실기 원자료](../analysis/tail1012-hardware.json)

## 이번 비교

두 ROM을 Mesen에서 각각 독립적으로 두 번 기동했다. 새 세이브 폴더에서 패드 입력 없이 3,600 NES 프레임을 실행했다. 명목 60Hz로 창을 나누고 매초 중간 한 화면에서 원본 CHR 주소·바이트와 해당 줄에 유효한 OBJ의 패턴 읽기를 기록했다. 첫 1초를 제외해 창별 29·30장을 비교했다. 두 기동에서 같은 게임의 읽기 기록과 화면 변화 집계가 바이트 단위로 일치했다. 6프레임마다 표본 픽셀 해시를 대조한 화면 변화 횟수는 커비 194/290·279/300, 모험도 239/290·286/300이었다. 이 수치는 원본 데모의 움직임을 확인하는 지표다.

동일한 순서의 읽기를 128슬롯·16B/슬롯인 OBJ 캡처 뱅크에 재생했다. 화면마다 새 캡처를 열고, 관측한 서로 다른 바이트 주소를 첫 등장 순서로 한 번씩 조회했다. 실제 FSM의 세대·소유권·태그·바이트 유효 비트를 검사했고, 모든 적중 데이터는 원본과 대조했다. 미적중 응답은 고정 지연으로 공급했다. 미러 복사에 필요한 포트는 비어 있다. ARM plan의 선택, 실제 공유 ROM 경합, 화면 공개 일정은 이 비교에 들어 있지 않다. 두 타이틀 합계 120개의 캡처에서 Questa RTL과 독립 모델이 일치했고, STOP 또는 뱅크 반환 뒤 이전 캡처의 조회가 차단됐다. [정량 결과](../analysis/cross1022-results.json) · [RTL 대조](../tests/nes-functional/tb_nes_cross1022.sv)

측정 전에 고정한 두 주소 배치 모두 모험도 후반에서 미적중을 줄였고 커비 후반에서는 늘렸다. 주 슬롯에 XOR을 적용하면 모험도에서도 오프닝이 악화됐다. 그대로 채택하기 어려운 후보들이다. 세 번째 후보는 같은 타일을 다시 조회할 때 직전 바이트가 미러에서 적중했으면 미러를 먼저 조회한다. 두 위치의 태그·유효 비트 검증과 원본 ROM 폴백을 유지했다. 후반 캐시 포트 서비스 클록은 커비 2.78%, 모험도 2.07% 감소했고 미적중 수는 같았다. 절대 이득은 30개 표본을 모두 합쳐 각각 112·156클록이다.

## 실기 기준점 진입

MMC1012 ARM은 커비 헤더 16B를 읽고 중단한다. 커비 전용 후보는 PRG 512KiB·CHR 256KiB, 배터리 플래그와 수평 초기 미러링을 대상으로 한다. 전체 ARM 링크는 212,736/212,992B다. 최종 기계어의 파일 입력 시험에서 786,448B 전체 CRC를 통과해 FPGA 프로그래밍 호출에 도달했고, 모험도 ROM과 마지막 바이트를 바꾼 커비 파일을 각각 거부했다. 진단용 보드 식별자를 분리했다. [ARM 준비·검증](../tools/prepare_nes_kirby1022.py)

기존 13비트 태그에 맞춰 커비 CHR 상위를 접으면 표본 OBJ 읽기만으로도 두 구간에서 7,267·3,374바이트의 값이 달라진다. 14비트 태그를 보존해 비교했다. 로더·CHECK·RUN 주소 변환, MMC3 마스크, 캡처 캐시를 확장했다. 별도 메모리 시험에서는 단축된 쓰기 스트로브와 단일 시험 클록으로 실제 로더 및 물리 reader의 핀을 PSRAM 모델에 연결한다. 원본 786,432바이트 전부의 쓰기 핀 주소·데이터와 CHECK 응답을 대조했다. 1KiB마다 처음과 끝에서 총 1,536개의 RUN 읽기를 대조하고 STOP 뒤 메모리 소유권과 카운터 회수를 확인했다. ARM의 전체 링크 시험과 이 RTL 시험은 독립 실행이다. [보드 변경](../tools/prepare_nes_kirby1022_board.py) · [전체 주소 대조](../tests/nes-functional/tb_nes_kirby1022_load.sv)

남은 경계는 캡처의 BG·OBJ 태그를 압축 입력과 ARM planner를 거쳐 E9 및 타일 ROM 요청까지 보내는 부분이다. MCU와 보드가 같은 세대의 상위 CHR을 끝까지 보존하고 원본 PPU와 표시가 일치하는지 확인한 후 전체 Quartus Lite FIT·STA와 실기 STOP·메뉴 복귀를 확인해야 한다. 이번 포트 실험은 부팅 가능한 설치본과 분리했다.

## 이후 채택 기준

1. 최적화를 끈 커비판에서 오프닝과 데모 전환을 원본과 대조한 후 무입력 실기 60초를 최소 두 번 측정한다. 1–30초는 29초, 30–60초는 30초를 분모로 사용한다.
2. 같은 계측량에서 공개 FPS, 화면별 VBlank 간격 분포, 마지막 ACK와 ROM 대기를 함께 기록한다. 커비에서 실제로 한 VBlank를 놓친 원인부터 다룬다. 이번 조회 순서 후보는 전체 경로에서 이득이 관측될 때만 채택한다.
3. 후보 고정 후 모험도를 같은 조건으로 다시 실행한다. 변경 전후 차이를 **각 게임 안에서** 계산한다. 한 게임만 이득을 얻는 경우 다른 게임의 회귀와 ROM·Flash·회로 비용을 따로 기록한다. 반복 간 차이와 비슷한 이득은 추가 반복으로 확인한다.

이전 23행 실험에서는 SEAL 이후 약 0.36ms를 줄였지만 앞선 패킷의 큐 반환이 늦어져 공개 VBlank가 같았다. 이는 특정 구간의 비용 감소를 화면 성능으로 해석할 수 없는 사례다. 주소 배치 실험은 한 게임 안에서도 장면 선택에 따라 후보의 평가가 달라지는 사례다. 두 문제를 구분해서 추적한다. [23행 공동 실행](nes-accept1021-results.ko.md)


## 재현 경로

두 ROM은 로컬에서 SHA-256으로 식별한다. ROM이나 캡처 원본은 Git에 보관하지 않는다.

1. `tools/cross_nes1022.py capture 게임 ROM폴더 작업폴더 --mesen Mesen.exe`를 kirby와 adventure에 대해 실행한다. 다른 빈 작업폴더에서 반복한다.
2. `tools/prepare_nes_kirby1022.py prepare ROM폴더` 후 `tools/build_nes_trial577.ps1 -SourceRoot ../probes/nes-cross1022/link`로 링크한다.
3. `tools/prepare_nes_kirby1022_board.py MMC1012보드소스 ROM폴더 ../probes/nes-cross1022/load`로 메모리 시험 입력을 만든다.
4. `tools/check_nes_cross1022.py emit 첫작업폴더`로 조회 벡터를 만든다. 기존 Questa FLOAT wrapper에서 `tools/check_nes_cross1022.ps1`과 `tools/check_nes_kirby1022_load.ps1`을 순서대로 실행한다.
5. `tools/check_nes_cross1022.py check 첫작업폴더 --repeat 두번째작업폴더 --rom-dir ROM폴더 --result analysis/cross1022-results.json`으로 두 기동의 기록과 프레임별 회로 결과, 메모리 모델과 ARM 전체 링크를 검사한다.
