# 951에서 변경된 map을 쓰는 비용과 기존 map을 다시 확인하는 비용

**621을 유지한다.** 951에서 4B 그룹 384개 중 바뀐 28개를 WRAM에 쓰는 데 약 0.44ms, 생략한 356개를 읽고 두 검산 값을 갱신하는 데 약 9.57ms가 들었다. 생략 그룹 검사 시간만 전부 제거한다고 가정해도 기존 구현에는 10.31ms가 남는다. 기준 5.58ms에 도달하려면 패킷 해석·범위 확인·행 진행까지 함께 줄여야 한다.

## 보낸 시각과 실제 수락 시각

625의 두 시작 위상에서 905–951까지 모든 패킷의 발행 예정 클록을 고정했다. 951의 오른쪽 map 여덟 패킷에서만 628 ARM이 실제 만든 변경 payload를 대입했다. 나머지 명령·순서·identity는 원본과 같다. 네 칸이 차면 같은 패킷을 보류하고 다음 실제 credit에서 넣었다. 기준 재생의 65816 이벤트는 원래 기록과 모두 일치했다. 각 경우의 47장 RGB와 표시 map을 독립 기준에 대조했다. [기계 판독 결과](../analysis/map629-verification.json)

625 일정에서는 629의 발행 예정과 실제 수신 큐 진입 사이 최대 지연이 10.080 / 9.520ms였다. 그래서 이전 628 ARM 실행에서 수신기가 이미 감당한 PUSH 시각으로도 **완전히 같은 패킷 스트림**을 재생했다. 이 대조에서는 그룹별 처리와 행 단위 처리 모두 두 위상에서 credit 보류가 0회였다. 소비 합은 19.883 / 19.886→19.730 / 19.732ms, 표시는 모두 5 VBlank였다. 실제 951 표시 ACK는 232 / 0 master clocks 빨라졌다. 두 위상 모두 목표의 3 VBlank에 도달하지 못해 957까지의 새 연결 일정과 보드 FIT·실기 시험은 진행하지 않았다.

## 65816 명령 경계에서 확인한 비용

625 일정의 628 수신기에서 변경된 그룹을 쓰는 명령은 0.440 / 0.445ms였다. 같은 그룹의 두 워드 검산에는 0.751 / 0.755ms, 보존한 그룹의 두 워드 검산에는 9.568 / 9.571ms가 들었다. 후자의 수치는 356개 그룹에서 실제 WRAM 읽기부터 두 합 저장·인덱스 갱신까지 잰 시간이다. 마스크 분기·행 제어·일반 map 두 패킷·공통 헤더와 ACK는 소비 합에 별도로 들어 있다.

629는 변경 4B를 먼저 쓰고 같은 64B 행의 32워드를 주소 순으로 읽는다. 네 워드씩 처리하면서 첫 번째 합을 레지스터에 유지한다. 순서가 있는 두 번째 합도 수신한 기대값과 독립 비교한다. 그 행 전체 검산에만 9.164 / 9.164ms가 들었다. 65816 본체는 5,700→5,761B, 추가 scratch는 16비트 행 끝 주소 하나다. 628의 ARM과 패킷은 그대로 사용해 기존 Flash 688B 초과도 남는다.

## 보호 경계와 다음 결정

cold 변경 패킷, 잘못된 이전 serial, 합 손상, 길이 초과·부족, 생략 WRAM 손상 여섯 경우를 거부했다. 두 번째 행에서 STOP을 넣으면 직전 화면을 보존하고 두 뱅크 이력을 지웠다. 중단된 WRAM·VRAM 16KiB를 그대로 둔 뒤 전체 행으로 905·906을 다시 표시하고 최종 ACK를 확인했다. 원래의 64B 서비스 간격과 246번 표시 검사선을 사용한다.

다음에는 4B 마스크 검사 루프 튜닝을 중단한다. 951의 이 여덟 패킷에서 24개 행 모두 앞 34B 뒤에 0이 30B 붙는다. 이전 뱅크를 믿고 생략하는 대신 ARM이 완전한 행을 기술하고 65816이 literal DMA와 고정값 채우기로 전부 쓰는 경우를 예산화한다. 기존 514·515의 이력 검사와 구분하고, 행별 descriptor 2B라면 이 표본의 순절감은 672B(2.625MHz 순수 선로 약 2.05ms)다. 625에서 951 SEAL 단독 마감 초과가 5.861 / 6.625ms였으므로 **이 절감만으로는 부족하다**. 후속 팔레트·OAM 발행과 DMA가 같은 마감 앞으로 올 수 있는지 먼저 확인하고, 가능성이 있을 때만 연결 구현한다. ## 재현

1. 628의 두 위상 `nes-map628-checked-{1,2}`와 625의 `nes-seal625-tables-bg-{1,2}`, 624 및 628 client를 준비한다. `tools/nes_group629.py`로 분리 검사 client를 만든다.
2. `tools/replay_nes_group629.py`의 `--trace`에 625, `--compressed`에 같은 위상의 628을 준다. `--base-client`는 624, `--group-client`는 628이다. `--client`는 base에 624, literal·group에 628, split에 629를 준다. 기본 4모드 결과 폴더는 `nes-map629-{mode}-{phase}a`, group·split의 `--paced` 결과는 `nes-map629-{mode}-{phase}paced`다.
3. `tools/check_nes_group628.py`에 629 client와 628 위상 1 패킷을 주고 `nes-map629-guards`에 저장한다. `tools/analyze_nes_map629.py --root $env:TEMP --out analysis/map629-verification.json`으로 발행·보류·검산 구간·복구 결과를 비교한다.
