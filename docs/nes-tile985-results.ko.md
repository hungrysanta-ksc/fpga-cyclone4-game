# 911의 타일 선행 DMA와 246선 마감

## 목표

978의 65816과 리터럴 전송 형식을 유지한 채, 이미 수락한 911 타일을 직전 VBlank에 보내면 911 표시 간격과 912 최종 ACK가 함께 줄어드는지 검증했다. 기준은 908의 VBlank 38·245선 공개, 909 선행 DMA 624B, 910 캡처 성공이다.

## 작업내용

map 업로드가 없고 raw 패치 한 줄을 보내는 경우에 기존 ARM 큐 반환 확인을 한 번 추가했다. 첫 후보는 201B 반환을 확인한 뒤 240B 리터럴을 발행한다. 두 번째 후보는 240B 반환을 확인한 뒤 SEAL을 발행한다. 타일이 수락되고 큐가 비면 기존 65816이 비활성 VRAM으로 DMA한다. 새 패킷과 STOP의 우선순위, 독립 검사, 최종 ACK 처리는 978의 ROM을 그대로 사용했다.

각 후보의 전체 ARM 링크를 두 시작 위상에서 905–912까지 SPI·ROM 공급 모델 및 Mesen 65816과 연결했다. 별도 대조 실험에서는 978의 부팅과 앞선 패킷 시각을 고정하고 해당 반환을 즉시 안다고 가정했다. 다음 거래의 실제 전송 시간과 공유 SPI 직렬화 비용을 포함했다. 이 고정 재생은 911까지이며 912 결과는 전체 ARM 실행에서 얻었다.

## 성과

두 ARM 후보 모두 911의 BG 16B, OBJ 32B, OBJ 384B를 **VBlank 44에서 SEAL 전에 전부 전송**했다. 원본은 이 432B를 VBlank 45에서 보냈다. DMA 시작과 마지막 바이트를 따로 추적했다. 아래 수치는 위상 1 / 2 순이다.

| 전체 ARM 실행 | 978 | 201B 반환 뒤 240B 발행 | 240B 반환 뒤 SEAL 발행 |
|---|---:|---:|---:|
| VBlank 44에서 타일 432B의 마지막 바이트 | 전송 0B | 241 / 237선 | 244 / 245선 |
| 908 공개 | 38·245선 / 38·245선 | 동일 | 동일 |
| 909 선행 DMA | 624 / 624B | 624 / 624B | 624 / 624B |
| 910 캡처 여유 | 0.216 / 0.196ms | 0.213 / 0.193ms | 0.217 / 0.197ms |
| 911 공개 | 45·244선 / 45·244선 | 45·240선 / 45·240선 | 45·240선 / 45·240선 |
| 911 표시 간격 / 밀집 여섯 간격 | 양쪽 2 / 13 | 양쪽 2 / 13 | 양쪽 2 / 13 |
| 912 최종 ACK 지연 | 기준 | +0.015 / +0.024ms | +0.010 / +0.013ms |

240B 반환을 기다린 후보는 253 / 252선에 SEAL 검사에 진입했다. 팔레트 512B·OAM 544B의 마지막 바이트는 두 위상 모두 VBlank 45의 238선에 기록됐다. 그 결과 같은 VBlank 안에서 911이 네 줄 일찍 공개됐지만 한 주기를 절약하지 못했다. 고정 재생에서도 두 방식 모두 432B를 직전 VBlank에 보냈다. 단, 240B 뒤에 대기를 넣은 고정 재생의 위상 2에서는 384B 전송이 245선에 시작해 247선에 끝났다.

### 어느 시각을 당겨야 하는가

978에서 240B 반환부터 VBlank 44의 246선 끝까지 남은 시간은 **0.759 / 0.513ms**였다. 같은 실행의 SEAL 진입→독립 검사·업로드 준비는 **1.306 / 1.308ms**, 팔레트 DMA 시작→공개는 **0.565 / 0.565ms**였다. 타일 432B를 이미 보냈다고 가정해도 raw 192B에 전송만 최소 0.072ms가 든다.

이 비용을 마감에서 거꾸로 빼면 SEAL은 늦어도 **216선 부근**에 시작해야 한다. 반환 직후 비용 없이 SEAL을 시작한다고 잡아도 현재 240B 반환은 두 위상에서 각각 **1.183 / 1.432ms 늦다**. 이 계산은 raw DMA 설정과 추가 큐 대기를 0으로 둔 낙관적 예산이다. 특히 위상 2에서는 검사를 전부 미리 끝냈다고 가정해도 현재 반환 시각부터 실제 팔레트·OAM 공개 및 최소 raw DMA까지 0.124ms가 모자란다.

### 검증 범위

전체 링크 네 실행에서 978과 동일한 65816 ROM, 여덟 RGB 화면, map 범위·값, plan 레코드, 911까지의 패킷·타일 바이트를 대조했다. 65816 재생기는 선행 DMA 후 실제 VRAM 바이트를 수락한 타일과 대조한다. 각 후보의 두 위상에서 432B 선행 후 STOP과 잘못된 SEAL을 각각 주입했다. 여덟 경우 모두 0xE4 또는 0xE0를 반환하고 910 화면을 보존했다. 두 ARM 링크의 메뉴 복귀 분기도 검증했다. 두 후보의 펌웨어는 각각 213,040B로 한도를 48B 초과했다. 실기 기준 MMC966과 개발 기준 978을 유지한다. ## 후속작업

911 타일의 추가 반환 대기는 종료한다. 다음 검증에서는 240B 리터럴이 확정된 뒤에도 먼저 처리 중인 OAM·테이블 작업을 시간순으로 나눠, 마지막 반환 자체를 앞당기는 경우와 SEAL 검사의 일부를 먼저 실행하는 경우의 합산 여유를 계산한다. 수신 도중 먼저 검사한 범위는 은행·세대와 묶고 후속 쓰기나 STOP에서 무효화해야 한다. 위상 2의 1.432ms와 909의 선행 624B를 함께 만족할 예산이 있는 경로부터 구현한다.

재현은 `nes_tile985.py prepare between|after TEMP`, 생성한 link의 `build_nes_trial577.ps1` 전체 링크, 두 위상의 `run`·`fixed` 순이다. 각 후보와 위상에 `guard --fault stop_decode|bad_seal`을 실행한 뒤 `check_nes_tile985.py TEMP analysis/tile985-results.json`으로 대조한다.
