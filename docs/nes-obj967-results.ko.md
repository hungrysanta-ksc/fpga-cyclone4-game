# MMC966의 56.36초 OBJ 타일 공급

## 목표

55–60초 데모에서 MMC955와 같은 타일 작업량인데 마지막 OBJ 준비가 7.022ms 늦었던 화면을 추적했다. 다음 최적화의 대상은 ROM 허가를 기다린 첫 타일이다. [MMC966 실기 결과](nes-hardware966-results.ko.md)

## 작업내용

두 실기 BIN에서 토큰·뱅크·타일 길이를 검증한 뒤 상세 기록을 비교했다. MMC955 세대 1393과 MMC966 세대 1452는 BG 529, OBJ 14, 변경 map 행 0, 타일 9개, 묶음 4개로 일치한다. 아래 시각의 원점은 각 화면의 첫 E9다. FPGA 시각의 한 칸은 0.390ms다.

| 묶음 | MMC966 토큰 | ROM 허가 횟수 955→966 | 뱅크 반환 시각 955→966 |
|---|---:|---:|---:|
| BG 16B | 3756 | 0→0 | 1.950→1.950ms |
| OBJ 128B | 3757 | 0→8 | 3.511→10.533ms |
| OBJ 64B | 3758 | 0→1 | 4.681→11.703ms |
| OBJ 64B | 3759 | 0→39 | 8.582→12.873ms |

## 성과

128B 묶음의 네 번째 타일에서 공유 ROM 요청이 0.390ms에 기록됐고 첫 허가는 9.752ms였다. 요청→첫 허가 9.362ms가 가장 먼저 관측된 긴 대기다. 마지막 64B 묶음은 같은 뱅크의 직전 반환(10.533ms) 전에 이미 첫 허가(9.752ms)를 받았다. 이 기록기는 현재 타일 읽기와 두 종류의 선행 읽기가 공유하는 포트를 센다. 39회만으로 마지막 타일의 캐시 미스 수나 CHR 주소를 역산할 수 없다.

첫 E9→마지막 타일 준비는 3.511→10.533ms였고 입력 완료→ARM 첫 유효 최종 ACK는 31.567→34.024ms였다. 두 판의 첫 E9→진단 조회는 23.406ms, 조회 비용은 1.152ms로 같았다. 이 화면의 최종 ACK 지연은 2.457ms다. 타일 준비 지연 전체를 표시 지연에 더하면 과대평가한다.

MMC966의 보드 RTL에서 E9 시각과 목표 32B OBJ를 고정하고 7B 페이지 명령을 SPI로 보냈다. 서로 다른 두 ROM 허가 일정에서 E9 이전의 남은 허가 수와 페이지 주소를 바꿨다. 목표 타일의 32B는 독립 기대값과 일치해야 하며, 호스트 기록기의 허가 수도 실제 공유 포트와 대조한다.

| 페이지 명령 조건 | E9 전 허가 | E9 뒤 타일 완료까지 허가 | 대조군보다 앞당긴 완료 시각 (위상 1 / 2) |
|---|---:|---:|---:|
| 명령 없음 | 0 | 8 | 기준 |
| 일찍, 대상 페이지 | 128 | 0 | 9.356 / 9.552ms |
| 마지막 여덟 허가만, 대상 페이지 | 8 | 0 | 9.356 / 9.552ms |
| 늦게, 대상 페이지 | 0 | 8 | 0 / 0ms |
| 일찍, 다른 페이지 | 128 | 8 | 0 / 0ms |

두 위상은 실기 한 칸보다 작은 허가 위상 차이를 둔 합성 일정이다. 목표 타일은 시험 페이지의 첫 타일이다. 실제 세대 1452에서 이 주소가 언제 확정됐는지와 앞선 허가 슬롯이 몇 개였는지는 BIN에 없다. 여기서 측정한 것은 RTL 타일 완료 시각이다. 65816 공개·최종 ACK·FPS는 기존 실기 기록으로만 비교했다. 같은 보드의 페이지 CRC·세대·계획 우선순위·STOP 무효화 시험도 통과했다.

## 후속작업

1. 실제 ARM이 직전 입력에서 처음 알 수 있는 OBJ 태그·행과 페이지 내 위치를 구하고, 현재의 8태그 정렬·전체 마스크·뱅크 이력 조건을 적용한다. 세대 1452 자체를 복원할 자료가 부족하면 그 점을 명시하고 재현 가능한 동일 부하 화면에서 검증한다.
2. 같은 시작 시각에서 ARM의 7B SPI 발행과 기존 ROM 사용자의 허가를 함께 재생한다. 대상 행이 허가 구간 안에 들어가고 다른 타일이 늦어지지 않는 조건만 다음 전체 일정 시험에 올린다.
3. 기존·빈 캐시 두 위상에서 첫 E9→마지막 OBJ와 최종 ACK·표시 간격을 함께 비교한 뒤 실기판을 결정한다. 실제 표시 FPS 기준은 MMC955이며 다음 후보는 MMC966의 30–60초 24.87 FPS와도 비교한다.

### MMC966 ARM에서 페이지 주소를 알게 되는 시각

실기 세대 1452의 BIN은 CHR 주소를 저장하지 않는다. 대신 MMC966의 검증된 빈 캐시 연속 일정에서, ARM이 OBJ 여덟 태그와 행 마스크를 확인한 뒤 `page964`가 페이지 주소를 저장하는 명령을 관측했다. 첫 E9 전에 7B 페이지 명령(EB)을 발행한 두 세대의 결과다. 두 위상 모두 계측 전후 SPI 이벤트·65816 표시 일정·타일 준비·BIN이 바이트 단위로 일치했다.

| 재생 세대 / 첫 태그 | 페이지 확정→EB 발행 (위상 1 / 2) | 확정→EB 완료 사이 ROM 허가 기회 | 그중 이전 세대 EA 완료 이후 | EB가 실제 공급한 행 (재생) |
|---|---:|---:|---:|---:|
| 907 / 3136 | 14.267 / 15.157ms | 298 / 299 | 0 / 0 | 0 / 0 |
| 909 / 3072 | 3.013 / 3.013ms | 0 / 0 | 0 / 0 | 128 / 128 |

907은 **ARM이 주소를 충분히 일찍 확정했다.** 그러나 마지막 허가도 직전 세대 EA 완료보다 각각 3,760·4,792 마스터클록 빨랐다. 기존 endpoint는 이전 계획이 끝나 반환 중일 때 페이지 명령을 수락하지 않으며, 수신 쪽은 캡처 세대도 대조한다. 909는 EB 발행을 3ms 앞당겨도 그 사이 빌려 쓸 ROM 허가가 없었다. 기존 EB로 첫 타일 여덟 행을 모두 받았다.

따라서 이 두 사례에서는 현재 세대 경계를 유지한 채 ARM 발행 순서만 바꿔 추가로 쓸 수 있는 허가가 0회다. 다음 비교 대상은 **직전 세대가 소유한 동안 다음 세대의 페이지를 별도로 예약하는 비용**이다. 진행 중인 타일에 필요한 허가를 빼앗는지, STOP 시 취소가 되는지, 초기 페이지의 태그가 실수요와 일치하는지를 먼저 확인한다. 허가 기회는 기존 ROM 경쟁 캘린더를 재생한 수이며 실기 1452의 점유율은 미확인이다. 모험도 4의 실기 FPS 측정값은 이번 재생으로 바뀌지 않는다. [ARM 확정·SPI·ROM 허가 시각](../analysis/page968-results.json)

`python tools/check_nes_page968.py <기존 재생 TEMP> analysis/page968-results.json`으로 두 위상을 재현한다. 같은 위치에서 재실행할 때는 새 출력 폴더 접미사를 `--tag`로 지정한다.

후속 보드 시험과 일곱 조건의 연속 재생에서 907의 선행 읽기 이득이 SEAL과 화면 공개까지 이어지는지 확인했다. [세대 반환 전 CHR 선행 읽기와 표시 마감](nes-reserve969-results.ko.md)
