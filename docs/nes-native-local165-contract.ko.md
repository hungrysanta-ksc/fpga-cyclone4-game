# NES165 SNES 내부 차분과 동적 DMA

카트리지 SRAM·세이브·자동 저장·복구 영역은 영상 저장소로 사용하지 않는다. 이번 코드는 SNES 본체의 휘발성 WRAM bank7F만 사용한다. 기존164의 사운드·입력·STOP/메뉴 경로와 저장 코드는 변경하지 않았다. 설치 후보는164이며 새165 SD 패키지는 아직 없다.

## 구현과 검증 범위

[65816 생성기](../tools/nes_native_local165.py)는 두 WRAM 후보를 직접 비교하고 최대32개 DMA 명령을 만든다. [실행 시험](../tools/test_nes_native_local165.py)은 기존 두 SMB3 장면을 WRAM에 공급한 뒤 실제 SNES CPU가 만든 명령으로 PPU를 갱신한다. PC가 차분 명령을 미리 만드는 시험이 아니다. 실제 MCU mailbox·물리 ACK·전체 게임 실행은 포함하지 않는다.

선택 local03은 비교938바이트와 업로더288바이트다. 시험 ROM의 코드2,964바이트에는 초기화·fixture 공급·오류 주입도 포함된다. 기존 실기 client의 공간에 들어간다는 근거는 아니며 실제 연결 때 코드·WRAM 배치를 다시 확인한다.

첫 장면5,493논리바이트/6명령, 다음18바이트/2명령으로 기준 C 결과와 일치했다. 첫 HDMA21바이트는 WRAM 직접 참조라 PPU DMA는5,472바이트다. 두 장면의 유효 영역114,688픽셀과 캡처 전체 바이트가 기존 기준에 일치했다. 표시 이후 PPU 데이터 쓰기가 vblank 안에 있는지도 확인했다. 이 두 작은 장면의 성공이 모든 예산·장면의 vblank 수용을 보증하지 않는다.

9개 실행 사례는 두 장면, 후보 방향을 뒤집은 무변경, 잘못된 후보 주소, BG 크기 초과, 64바이트 경계의 변경 병합, 예산 초과, 32명령 초과, 홀수 길이 HDMA 마지막 바이트 변경이다. 거부된 목록을 업로더에 전달해도 READY가 아니면 즉시 반환한다. test-only MVN은 초기화된 WRAM만 읽도록 수정했다. 이전 local01/02와 소스·로그도 보존했다.

## 메모리·호출 계약

진입/반환은 native A16/X16, DBR=DP=0이며 A/X/Y와 DP40–6F를 사용한다. 호출자는 인터럽트와 서비스 루틴이 이 scratch를 훼손하지 않게 해야 한다. 두 후보는 bank7F의0000/8000, 각32KiB다. 표시 중에는 서로 달라야 한다. 아래는 SNES 주소이며 MCU `sram_*` 주소가 아니다.

| 위치 | 의미 |
| --- | --- |
| 1000 / 1010 | 새/이전 후보의 여섯 u16 길이 |
| 1020 / 1022 | 새/이전 후보 시작0000 또는8000 |
| 1024 / 1025 | 기존 표시 여부 / 상태 byte |
| 1026 / 1028 / 102A | 명령 수 / 예산 계산량 / payload u16 |
| 102C / 102E / 1030 | 가로·세로 스크롤 / visible 예산 u16 |
| 1070 | 업로더의 목록 크기 scratch |
| 1100–11FF | 32명령: source16,dest16,size16,kind16 |

시험의1034/1036은 pad polling latch/호출 횟수이며 실제 mailbox ABI가 아니다. 후보 내 BG/OBJ/map/CGRAM/OAM/HDMA 시작은0000/4000/5000/6000/6200/6500이다. 각 최대 크기는16384/4096/4096/512/544/1121바이트다. BG·OBJ 길이 정렬, map/CGRAM/OAM 고정 크기와 HDMA의 비어 있지 않음을 검사한다.

상태1은 비교 중,2는 READY,3은 로컬 DMA 완료, E1/E2/E3은 잘못된 입력/명령 상한/예산 초과다. **3은 물리 ACK가 아니다.** 호출자가 serial·generation·후보 소유권을 유지하고 완료를 게시해야 한다. 비교 중에는 PPU를 쓰지 않는다. READY 목록과 후보는 업로드 완료까지 불변이어야 한다. 외부에서 받은 임의 목록을 검증 없이 업로더에 넣지 않는다.

같은64바이트 블록은 빠르게 건너뛰고 차이가 있는 블록·끝부분·길이 증가는 정확히 비교한다. BG/OBJ/map의 변경 사이 간격32바이트까지 병합한다. CGRAM/OAM/HDMA는 차이가 있으면 해당 표 전체를 갱신한다. 예산은 payload+명령당96이며 실기 시간 보증값은 아니다. 첫 화면은 호출자가 blank를 유지하고, visible 갱신은 새 vblank를 기다린다. HDMA는 데이터가 같아도 항상 새 후보를 참조한다.

선택적 service callback은 비교 진행 중 호출된다. DBR/DP=0과 A/X16, scratch 보존을 지켜야 하며 게임 입력·수신·종료 처리를 연결할 자리다. 시험은 자동 joypad 레지스터를 읽는 짧은 서비스만 사용했다. 실제 조작 유지·오디오 연속성 검증으로 확대 해석하지 않는다.

## 속도와 남은 작업

| 비교 | local01 | local02 | 선택 local03 |
| --- | ---: | ---: | ---: |
| 두 번째 장면 master ticks | 2,595,110 | 693,782 | 638,300 |
| 무변경 master ticks | 2,588,626 | 621,054 | 564,700 |
| 명령 초과 사례 master ticks | 1,195,152 | 1,362,940 | 1,356,928 |

Mesen masterClock, NTSC 명목21.477MHz 환산에서 두 번째 비교 약120.8→29.7ms, 무변경26.3ms다. service 호출과 명령 생성은 포함하지만 실제 전송·표시 대기·MCU 변환 시간은 제외한다. 명령 초과 사례는 약63.2ms로 초기 구현보다 느려졌다. 최악 실행 시간 또는 실기 FPS를 확정한 수치가 아니다.

MCU가 이전·새 표10,986바이트를174회 재독출하는 비교는 이 루틴으로 대체할 수 있다. **아직 MCU 호출부를 교체하지 않았으며, 실제 왕복 감소를 측정한 것은 아니다.** 후보5,493바이트 공급과 기존 SPI 약39.59ms도 남아 있다. 18바이트 갱신을 전체 전송량이나60fps로 표시하지 않는다.

다음은 실제 MCU→SNES WRAM 수신·로컬 비교 호출·완료 ACK를 하나의 소유권 경로로 연결한다. 긴 비교 중에도 입력·STOP·수신 처리가 살아 있도록 스케줄한다. 전체 MCU 링크/stack/heap, 실제 client 공간, 기존38M9K 프레임버퍼 교체와 배치·타이밍의 변경 경계만 검사한 뒤 SMB3 첫 레벨 실기로 간다. 같은 부팅·A/B·044 시험은 반복하지 않는다. 60fps를 위한 추가 변경은 실제 연결의 병목 측정에 따라 결정하고, 일반 진단을 더 늘리지 않는다.
