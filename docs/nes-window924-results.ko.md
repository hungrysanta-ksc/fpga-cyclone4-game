# 924 · 세대 909의 OBJ 선행 DMA와 910 캡처 마감

선택한 ARM 후보는 `objheader`다. 이전 패킷이 OBJ 타일이고 다음 명령이 OAM 채우기일 때만 큐를 비운다. BG 뒤에도 대기하는 `safeheader`보다 Flash를 8B 더 쓰지만, 같은 최종 ACK 시각을 얻으면서 발행 순서를 바꾸는 경우가 적다. 최종 링크는 212,940 / 212,992B로 52B가 남는다.

| 측정 항목 | 기존 캐시 위상 1 | 기존 캐시 위상 2 | 빈 캐시 위상 1 | 빈 캐시 위상 2 |
|---|---:|---:|---:|---:|
| 908 공개 VBlank | 38 | 39 | 39 | 40 |
| 910 마지막 D2의 목표 캡처선 여유 | 5.59µs | 23.23µs | — | — |
| 906→912 여섯 표시 간격 합, MMC915→924 | 14→13 | 14→13 | 16→16 | 16→16 |
| MMC915 대비 912 최종 ACK 단축 | 16.739ms | 16.688ms | 4.94µs | 12.66µs |

기존 캐시에서는 908이 MMC915보다 한 주기 먼저 공개됐고, 910의 D2가 마감을 통과하면서 그다음 캡처도 정확히 357,368클록 앞당겨졌다. 923의 910→911 표시 간격이 3회에서 2회가 되며 여섯 간격은 두 위상 모두 2·2·3·2·2·2였다. 빈 캐시의 912는 두 위상 모두 기존과 동일한 496개 목적지 바이트를 SEAL 전에 DMA했다. 기존 캐시의 912 자체 선행량은 923의 112 / 112B에서 112 / 48B가 됐지만 최종 ACK는 두 위상 모두 빨라졌다.

## 923이 캡처를 놓친 이유

기존 캐시에서 909의 OBJ는 직전 VBlank에 이미 65816이 수락한 상태였다. 923의 65816은 위상 1에서 VBlank 40의 229–246선, 위상 2에서 VBlank 41의 225–242선을 OAM 패킷 수락과 복원에 썼다. 큐가 비었을 때 실행하는 타일 DMA가 이 구간을 쓰지 못했다. 910의 마지막 D2는 같은 시작 시각의 캡처선보다 10,641 / 11,369 마스터클록 늦었다.

ARM에서 타일 패킷 뒤의 OAM 발행을 잠시 보류했다. 기존 E0 확인을 최대 12회 사용하며, VRAM 기록 여부는 65816의 실제 DMA 주소·길이·시각으로 별도 확인했다. 그 결과 909의 비활성 VRAM에 위상 1은 BG 16B와 OBJ 512B, 위상 2는 BG 16B와 OBJ 544B를 미리 썼다. 각 DMA의 첫 바이트 전에 해당 범위를 소유한 마지막 타일 뱅크가 반환됐고, 두 위상 모두 바로 다음 VBlank에 909가 공개됐다.

## 반환 경로에서 줄인 비용

기존의 유효 E0, EA, 다음 세대 D3와 마지막 D2는 모두 확인한다. D3 뒤 이미 입력이 준비됐으면 같은 ARM 단계에서 처리한다. 최종 E0와 EA 사이에 있던 수동 진단 명령 `0x78`의 첫 헤더는 실제 쓰는 16B만 읽고, 상세 페이지 0과 128은 각각 32B로 유지한다. 실제 ARM 호출 길이에 맞춰 SPI 전송 시간과 거래당 준비 시간을 모두 청구했다. 보드 RTL에서도 16B에서 SS를 해제한 뒤 상세 페이지·token·시각을 읽고 STOP을 처리했다.

| 기존 캐시에서 910 마지막 D2 | 위상 1 | 위상 2 |
|---|---:|---:|
| 923 기준, 캡처선 초과 | 10,641클록 | 11,369클록 |
| OAM 앞 최대 4회 확인만 적용, 초과 | 7,039클록 | 6,025클록 |
| 최대 12회 확인 및 반환 처리, 기존 진단 길이 | 923클록 초과 | 46클록 여유 |
| 선택한 최종 링크 | 120클록 여유 | 499클록 여유 |

923의 유효 E0→EA→D3→최종 D2는 위상 1에서 5,920 + 4,502 + 5,958클록, 위상 2에서 5,920 + 4,501 + 5,958클록이었다. 최종 링크에서는 각각 4,862 + 4,501 + 5,893클록과 4,862 + 4,502 + 5,892클록으로 줄었다. 두 개입을 합쳐 같은 캡처선에 대해 D2가 10,761 / 11,868클록 앞당겨졌다. 위상 1의 여유는 5.59µs라 실기판에 새 로그명을 넣고 재링크할 때도 같은 마감 검사가 필요하다.

## 검증 범위와 재현

1. 923 `warm` 전체 링크를 준비한 뒤 `tools/nes_window924.py prepare MODE`와 `tools/build_nes_trial577.ps1 -SourceRoot ../probes/nes-window924/MODE/link`를 실행한다. `control`은 923 바이너리 자체를 사용한다.
2. `tools/nes_window924.py replay MODE TEMP PHASE`를 위상 1과 2에서 실행하고 `--cold`로 빈 캐시를 재생한다. 기존 923 거래별 SPI 보정값을 보관된 `joint.json`에서 읽는다. 대조군은 네 조건 모두 923의 시각과 결과가 일치해야 한다.
3. `guards MODE TEMP`와 `proof MODE TEMP`로 손상 descriptor·중복·불량 SEAL 거부, 복사 및 표시 중 STOP, 909의 32B·352B OBJ 마지막 바이트 STOP, SRAM D0 네 곳, CRC 거부와 base·메뉴 복귀를 확인한다. 보고 코드 통합 전후에는 같은 입력으로 로그 세 파일의 내용과 출력 버퍼 경계 9건을 비교한다.
4. 기존 Questa FLOAT 래퍼로 `tools/check_nes_header924.ps1`을 실행한다. `tools/analyze_nes_window924.py TEMP analysis/window924-results.json --select objheader --recovery checked object safeheader objheader`로 같은 세대의 실제 수락·뱅크 반환·DMA·공개와 최종 ACK를 대조한다.

연속 재생에는 링크된 ARM·65816 명령을 사용했다. SPI·IRQ·ROM 중재는 기존 모델이고, 비교한 여덟 화면의 RGB·map·팔레트·section 5·타일 목적지 바이트를 검사했다. 보드와 65816은 교체하지 않았다. 실기 기준은 MMC915다.
