# NES 653 · map 직접 저장과 CRC16 회로 공유

## 실제 교체 경로

NES exporter는 query 응답의 상위 비트와 lease를 검사한 뒤 15비트 셀·index·generation과 map 마지막 셀 표식을 기존 mailbox로 넘긴다. 호스트는 첫 수락 클록과 이어지는 한 클록에 셀의 하위·상위 바이트를 기존 SPI M9K에 쓴다. 셀 쓰기·압축·SPI 읽기는 각자의 RAM 점유 구간에만 실행된다. NES에서 4셀/반복 record를 만들던 경로와, 호스트가 봉인 뒤 record를 파싱해 셀로 복원하던 경로를 삭제했다.

블록 경계도 바꿨다. 12 B 프레임 헤더와 함께 보내는 첫 블록에는 최대 80셀, 이후에는 최대 84셀을 담고 map 끝에서 봉인한다. 이 크기면 원래 4셀 명령으로 전부 복구해도 블록당 최대 252 B다. 652가 앞 일곱 블록에만 적용했던 블록 내부 1·2·4·33셀 참조를 모든 map 블록에 적용했다. 참조가 없으면 공유 RAM에서 원래 kind-0 명령을 생성한다. non-map은 기존 serializer를 쓴다. ARM의 652 ELF와 65816 ROM을 그대로 사용했다.

CRC16은 ordinary 바이트, 복원한 셀, 최종 wire 바이트의 세 단계가 **하나의 계산 회로**를 번갈아 쓴다. 헤더에 넣을 셀 CRC 상태를 보존하고 wire CRC는 첫 바이트부터 다시 계산한다. 원본 복구·ARM의 독립 CRC·D1 길이 검사·D2 token 반납·표시 최종 ACK는 각각 유지한다.

## 바이트와 RAM 준비 시간

| 지표 | 652 | 653 |
|---|---:|---:|
| 905–957 D1 블록 수 | 802 | 901 |
| 905–957 D1 payload | 100,804 B | 79,392 B |
| 955 한 세대 D1 payload / 블록 수 | 2,139 B / 16 | 1,746 B / 17 |
| 955 첫 7블록 payload | 495 B | 500 B |
| 첫 7블록의 블록별 준비 시간 합 | 371.988 µs | 258.893 µs |
| 그중 봉인 뒤 RAM 처리 | 313.595 µs | 151.083 µs |

첫 7블록 준비는 113.095 µs 짧아졌다. 이 중 ARM이 다른 일을 하는 시간과 겹치는 부분은 표시 시간에서 별도로 빼지 않았다. 고정 셀 단위로 나누면서 53세대에 99개 블록이 늘었으므로 아래 연속 일정에는 실제 D0 조회·D1·D2·반납 확인을 모두 포함했다.

## 두 시작 위상의 연속 일정

아래 표는 위상 1 / 2 순서다. 954 마감 여유는 648과 같은 직전 953 표시 기준이다. 901개 블록 모두 D1 시작이 실제 RAM 준비 시각 이후임을 확인했다. 각 실행에서 53화면의 map WRAM·VRAM과 이미지, 팔레트·OAM·HDMA, 두 staging 슬롯, 앞 화면의 최종 ACK→EA→다음 COMMIT 순서를 대조했다. BG 적중 48회와 OBJ 캡처 1,200회도 확인했다.

| 검증 지표 | MMC643 | 652 보드 소유권 일정 | 653 직접 저장 |
|---|---:|---:|---:|
| 954 SEAL 상대 여유 | — | 122.15 / 11.34 µs | **768.02 / 446.22 µs** |
| 954 표시 (VBlank) | 4 / 4 | 3 / 3 | **3 / 3** |
| 955 표시 (VBlank) | 4 / 4 | 3 / 3 | **4 / 4** |
| 951 공개선 | 246 / 245 | 240 / 239 | 239 / 239 |
| 957 최종 추가 대기 | 0 / 0 | 0 / 0 | 0 / 0 |
| 951–955 표시 간격 평균 | 59.834 / 59.870 ms | 53.280 / 53.283 ms | 56.470 / 56.466 ms |
| 957 ACK 단축 (MMC643 대비) | 기준 | 82.957 / 82.787 ms | 116.616 / 116.437 ms |

D0·D1·D2·D3 전체 거래는 118,306 / 118,322 B에서 98,839 / 98,879 B로 줄었다. 957 ACK 절대 시각은 68,589,578 / 68,946,926 master clock이다. 652보다 33.659 / 33.650 ms 일찍 끝났다. 이 비교에는 직접 저장·CRC 공유와 새 블록 경계 및 전체 map 압축의 효과가 함께 들어 있다.

955의 직전 표시→END 진입은 652의 27.174 / 26.935 ms에서 25.510 / 25.124 ms로 빨라졌다. 반면 END→출력 진입은 약 6.97 / 6.96 ms에서 9.17 / 9.17 ms로 늘었다. 65816의 SEAL 수락은 188 / 189번 선에서 200 / 202번 선으로, 업로드 진입은 214 / 214번 선에서 225 / 227번 선으로 밀렸다. 954 SEAL 여유를 확보하고도 955의 3 VBlank 조건을 놓친 지점이다.

동일 EP4CE15F17C8, 보드 설정·SDC·RAM 이미지로 전체 컴파일을 실행했다.

|---|---:|---:|---:|
| LE | 16,103 | 15,880 | 15,408 |
| 필요한 LAB | 1,016 | 1,004 | 963 |
| 조합 논리 / 전용 레지스터 | 15,186 / 8,807 | 15,039 / 8,688 | — |
| M9K / 논리적 RAM 비트 | 56 / 309,360 | 56 / 309,360 | 56 M9K |

ABORT 수정 전에는 470 LE·43 LAB가 부족했다. 수정 후의 판정은 **472 LE·41 LAB 부족**이다. 셀 직접 저장과 CRC16 공유를 함께 적용해 652보다 223 LE·12 LAB를 회수했다. Fitter가 배치를 완료하지 못해 배치 후 STA·SOF는 생성되지 않았다.

## 검증 범위와 재현

- `prepare_nes_direct653.py <652 보드> <새 보드>`로 실제 export/SPI 인스턴스와 Quartus 프로젝트를 만들고 Lite의 `quartus_sh --flow compile board`를 실행한다. 652 ARM 전체 링크는 212,436 B로 Flash 여유는 556 B다.
- 한 좌석 FLOAT wrapper에서 `check_nes_direct653.py`의 일반 실행 및 `--guards` 실행을 별도 디렉터리에 수행한다. 실제 exporter·양쪽 mailbox·SPI RAM을 거친 D1 payload와 CRC를 독립 packer와 대조한다. 원본 복구에서는 99셀 전부와 마지막 세 셀을 검사한다.
- 첫 번째 구현을 검토하던 중 map 봉인 전에 lease를 잃으면 남아 있는 셀이 E002 ABORT를 가릴 수 있는 경로를 발견했다. 최종 RTL은 ABORT 수락 때 잠정 셀을 버린다. 8셀에서 lease를 취소하고 실제 D1에서 원래 세대의 E002와 CRC를 확인한다. 부분 D1, STOP 후 old POP도 검사한다. 정상 53세대에서 수정 전후의 바이트와 블록별 준비 클록을 대조한다.
- `check_nes_direct653_arm.py`로 같은 ELF에서 원본 명령의 시작·generation·수량·길이·중복 token 오류를 주입하고 cold 재수신 및 16비트 token wrap을 확인한다. 압축 CRC·범위·generation 오류도 별도로 차단한다. 652와 동일한 ELF로 END·SEAL·queue·geometry·메뉴 및 base 복귀의 정상과 네 실패 경로를 다시 실행한다.
- `test_nes_direct653.py --sender653 <RTL 출력>/sender.json --geometry650 --commit-pop-bound --keep-run`에 652의 동일 입력·ROM 달력·IRQ·SPI 드라이버·client01과 시작 클록 7,288,416 / 7,467,100을 준다. 최초 준비는 앞 plan 종료·ROM drain과 다음 캡처 소유권으로, 후속 준비는 D2 반납 또는 마지막 COMMIT의 D3 허가로 제한한다. ARM은 CPI 2로 실행하고 65816은 Mesen에서 실행한다. 이는 보드 배치 후 실기 FPS 측정과 구분한다.
