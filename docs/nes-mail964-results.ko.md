# 964 · CHR 선행 읽기의 보드 타이밍과 ARM Flash

905·906의 첫 E8부터 실제 보드 RTL 응답을 반환했을 때의 결과는 [965 검증 기록](nes-credit965-results.ko.md)에 있다.

## 목표

963에서 빈 캐시의 여섯 표시 간격을 14→13 VBlank로 줄인 OBJ 선행 읽기를 실제 보드 예산 안에 넣고, FPGA의 E8 응답을 ARM에 돌려줬을 때 그 이득이 유지되는지 확인한다. 실기 기준은 MMC955이며 964 측정 구간은 세대 905–912다.

## 작업내용

- host가 확정한 EB의 세대·페이지 26비트를 NES 클록 레지스터에서 받은 뒤 주소 순회를 시작한다. 송신 데이터는 ACK가 돌아올 때까지 유지한다. 배치된 비트별 데이터 경로 26개와 단일 비트 제어 경로 4개를 세 가지 동작 조건에서 각각 확인했다. 비동기 clear 예외는 두 리셋 해제 체인의 네 입력 핀에만 추가했다. 로컬 해제 이후 recovery와 데이터 수신 후의 조합 경로는 STA에 포함했다.
- ARM은 입력 검사에서 만들어 둔 OBJ 비트맵을 사용해 온전한 8태그 묶음이 있을 때만 행 마스크를 확인한다. 페이지 표식은 리셋 때 지우고 이전 뱅크 이력이 준비된 COMMIT 이후에만 EB를 보낸다. 실제 ELF에서 태그 0·최종 태그, 경계에 걸친 묶음, 부분 행, 중복 태그, 빈 입력을 검증했다.
- 공용 FatFS 파일명 대문자 변환표를 구간과 홀짝 간격으로 압축했다. MMC955와 964의 실제 ARM 함수를 16비트 입력 65,536개에 대해 실행해 결과가 모두 같음을 확인했다. 데이터 10,080B와 BSS 20,952B를 유지했다.
- 905–912의 각 세대에서 실제 ARM의 EB를 SPI 핀에 재생하고 이전 세대의 CHR RAM을 다음 세대로 전달했다. plan과 뱅크 반환에는 같은 실행의 바이트·credit·반환 시각을 사용했다. FPGA가 먼저 내준 OBJ 응답을 실제 ARM 명령 경로에 넣어 다음 SPI 거래를 다시 산출한 뒤 이 새 일정으로 RTL을 다시 실행했다.

963의 동일 선행 읽기 재생 대비 빈 캐시 최종 ACK는 각각 392·128클록 늦었다. 표시 시점은 같았다. 독립 비교에서 여덟 화면의 RGB와 VRAM 결과가 일치했다. 잘못된 SEAL과 STOP에서는 907 화면을 유지했다. 연결한 ARM의 SRAM D0 호출 네 곳, 잘못된 블록 CRC 거부, base 복구와 메뉴 해제를 주변장치 모델에서 확인했다.

빈 캐시 두 위상에서 909의 EB는 기준 태그 3072로 수락됐고, 실제 공유 포트가 인접한 16태그의 128개 행 주소를 각각 한 번 읽었다. 위상 2의 910에서는 마스터클록 15,348,988에 모델이 빈 응답을 예상했지만 RTL은 이미 세 번째 OBJ descriptor를 공개했다. ARM이 이 값을 받자 E8 조회 하나를 건너뛰고 다음 E1을 15,357,204→15,354,457에 시작했다. 같은 일정으로 RTL을 다시 재생해 907–912의 E8 속성·수락 수·토큰 차이가 두 위상 모두 0건임을 확인했다. 이 2,747클록은 912 최종 ACK 시각을 바꾸지 않았다.

## 후속작업

처음 남은 차이는 905의 E8이다. 두 위상 각각 7,850,028·8,242,176클록에서 RTL은 다음 plan 수락 가능, 모델은 대기로 응답했다. 토큰과 누적 수락 수는 일치했다. 전체 905·906 응답에서 이와 같은 상태 차이는 위상 1에서 59·14건, 위상 2에서 58·15건이었다. 다음에는 최초 차이부터 ARM에 돌려주고, 변경된 E9의 실제 바이트 수락과 뒤따르는 906 입력 시각을 검증한다. 현재 빈 캐시 13회의 측정은 이 두 시작 세대에 모델의 상태 응답을 사용했다. 실기 FPS와 설치본은 그 검증 후 MMC955와 비교한다. [측정값과 보고서 해시](../analysis/mail964-results.json)

### 재현

1. 963 보드와 MMC955 링크를 준비한 뒤 `nes_arm964.py`로 ARM 소스를 만들고 `build_nes_trial577.ps1 -SourceRoot ../probes/nes-mail964/link`로 링크한다. `nes_mail964.py TEMP --fit`으로 전체 보드를 합성한다. `report_nes_mail964.tcl`을 생성된 보드 디렉터리에 복사한 뒤 그 디렉터리에서 Quartus Lite의 `quartus_sta -t report_nes_mail964.tcl`을 실행한다.
2. 각 위상과 캐시에 `nes_page963.py replay --work ../probes/nes-mail964 --temp TEMP --phase P --cache CACHE --neighbor`를 실행한다. `nes_wire964.py TEMP`로 입력을 만들고 저장소의 Starter FLOAT 래퍼로 `check_nes_mail964.ps1`을 실행한다.
3. 두 위상에 `nes_wire964.py TEMP --feedback P`를 실행한 뒤 `nes_wire964.py TEMP --tag 964feedback`으로 변경된 입력을 만든다. `NES_MAIL964_TAG=964feedback`으로 같은 RTL 시험을 한 번 더 실행한다.
4. 두 위상에 `nes_tail961.guards(TEMP,P,'963bnes-mail964both')`를 적용한다. `check_nes_transfer512_recovery.py --arm ../probes/nes-mail964/link/src --trial 955 --fault none --out ../probes/nes-mail964/proof/base`와 `analyze_nes_mail964.py TEMP --out analysis/mail964-results.json`으로 검증한다.
