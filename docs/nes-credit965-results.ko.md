# 965 · FPGA의 E8 수락 가능 응답과 다음 세대의 입력

## 목표

MMC955를 실기 기준으로 두고 964의 동일 ARM·65816·FPGA에서 세대 905·906의 실제 plan 수신 가능 시각을 ARM에 반영한다. 첫 응답 하나의 효과와 두 세대 전체 응답의 효과를 나눠, 다음 입력과 912 최종 ACK까지 확인한다.

## 작업내용

모험도 4의 같은 입력과 ROM 허가 일정을 두 시작 위상으로 재생했다. 첫 실험은 모델이 대기를 표시한 첫 E8에서 실제 FPGA의 수락 가능 비트만 ARM에 반환했다. 905를 반영해 전체 일정을 다시 실행한 다음, 그 일정에서 관측한 906의 첫 차이를 적용했다. 후속 E9의 명령 표본 및 모든 payload 바이트의 도착 시각에 보드의 쓰기 허가를 확인하고, 마지막에 길이·CRC·pending·누적 수락 수를 검사했다.

전체 응답 실험은 FPGA의 쓰기 허가, 이전 묶음의 메일박스 해제, END를 따로 관측했다. 원래 일정에서 즉시 받은 허가를 앞당긴 패킷에 그대로 적용하면 위상 1의 905 여섯 번째 E9는 거부됐다. 이 경우 FPGA가 실제로 허가할 때까지 추적한 뒤 ARM을 처음부터 다시 실행했다. 최종 일정에서는 세대 시작의 첫 조회와 첫 묶음도 포함했다. 위상 1은 E8 101+174회, 위상 2는 133+175회 모두 상태·수락 수·토큰이 RTL과 일치했고 E9는 각 위상에서 14개씩 수락됐다. 각 응답의 descriptor를 ROM에서 읽은 타일, 세대, 슬롯, ARM 토큰에 대조했다. 이 응답을 표본 시각 그대로 링크된 ARM에 반환해 전체 SPI·65816 소비·화면·ACK 기록을 다시 비교했다.

## 성과

아래 단축 시간은 같은 ROM 위상의 964 재생 대비다. 첫 응답만 바꾼 실험에서 905 위상 1의 4번째와 위상 2의 5번째 E9는 모두 113B였고 각각 0.255ms·14.785ms 먼저 수락됐다. 이 변경만으로는 906 첫 D1이 각각 0·39마스터클록 빨라지는 데 그쳤다. 906의 첫 응답만 추가한 효과는 위상 1의 7번째 E9(83B)에서 15.143ms, 위상 2의 6번째 E9(127B)에서 0.255ms였다.

| 905·906 전체 E8 응답을 반영한 결과 | 위상 1 | 위상 2 |
|---|---:|---:|
| 905 대상 E9 수락 단축 | 0.255ms | 14.785ms |
| 906 대상 E9 수락 단축 (905에서 누적된 이득 포함) | 31.764ms | 16.765ms |
| 906 입력 첫 D1 단축 | 12.958ms | 13.236ms |
| 905 공개 VBlank | 28→27 | 29→28 |
| 906 공개 VBlank | 34→33 | 35→34 |
| 912 최종 ACK 단축, 빈 캐시 | 16.634ms | 16.654ms |
| 912 최종 ACK 단축, 기존 캐시 | 16.644ms | 16.648ms |

빈 캐시 위상 1에서는 910의 E8 한 건에서도 FPGA가 모델보다 먼저 토큰 3을 공개했다. 이 응답까지 ARM에 반영하자 912 최종 ACK가 224클록 더 앞당겨져 964 대비 총 16.644ms 단축됐다. 바뀐 일정으로 910·911·912의 E8을 각각 10·4·9회 다시 조회해 전부 일치하는 것을 확인했다. 위상 2의 빈 캐시는 907–912에서 추가 응답 차이가 없었다.

906의 입력 캡처는 네 경우 모두 8,189,456클록에 준비됐다. ARM이 905의 736B OBJ(token 1)를 전달하는 E1을 마치자 D0 조회와 첫 D1이 이어졌다. 이 E1 종료부터 첫 D1까지의 간격은 전후 모두 약 1,924클록이었다. 906 입력이 빨라진 시간은 이 E1이 앞당겨진 시간과 일치한다.

양 캐시·양 위상에서 여섯 표시 간격 합 13 VBlank, 911 공개 전 입력 17블록, 912 직전 DMA 496B와 목적지 바이트 범위를 확인했다. 905·906에서 한 VBlank 앞당긴 출발이 912까지 유지됐다. 여덟 출력의 RGB, VRAM DMA 총량 22,512B, map·팔레트·section 5·타일 작업량을 대조했다. 908에 잘못된 SEAL 및 STOP을 각각 주입했을 때 마지막 정상 화면 907을 보존했다. 964와 동일한 바이너리로 base 복구와 메뉴 해제를 확인했다. 보드나 펌웨어를 변경하지 않은 시뮬레이션이므로 새 실기 FPS는 측정하지 않았다.

### 재현

964 보드와 ARM 링크, 964의 입력·ROM 허가 fixture를 사용한다. `nes_verified965.py TEMP PHASE CACHE --record analysis/credit965-wire.json`으로 최종 ARM에 보관한 응답을 직접 반환한다. 인수 `PHASE`는 1·2, `CACHE`는 cold·warm이다. 재생 디렉터리 이름은 `965measured`다.

보드에서 같은 기록을 다시 추출하려면 `nes_credit965.py`의 905·906 대조군을 차례로 실행한다. 각 단계는 두 위상 ARM 재생(`--phase P`), fixture 생성(위상 인수 생략), Starter FLOAT 래퍼로 `check_nes_mail964.ps1` 순서다. `NES_MAIL964_TAG`는 각각 `965first`·`965both`다. 이후 `nes_writable965.py TEMP 965both 965wireN --phase P --cache CACHE`로 N=1부터 보드 수락·해제 기록에 맞춰 재생한다. `--fixtures-only --phase P`로 RTL 입력을 만들고 동일 태그·위상으로 보드를 재생한다. 위상 2는 N=3부터, 위상 1은 N=4부터 `--include-initial`을 사용했다. N=5에서 각 세대의 첫 조회부터 마지막까지 대조한다. `nes_tail961.guards(TEMP,P,'965wire5')`로 STOP·SEAL 오류 주입을 재실행할 수 있다.
