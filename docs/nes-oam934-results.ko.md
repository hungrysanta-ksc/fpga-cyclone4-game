# 934 · 288B OBJ 반환 뒤 OAM 발행과 세대 912의 마지막 32B DMA

빈 캐시의 두 시작 위상 모두에서 원래 여섯 목적지 중 **464/496B**를 같은 VBlank에 전송했다. 밀집 여섯 간격 합은 양쪽 모두 15회였다. 남은 32B는 65816 복사와 뱅크 반환을 마쳤지만 선행 DMA 마감을 넘겼다. 기존 캐시 위상 2의 910 캡처도 한 번 늦어져 실기 기준은 MMC925를 유지한다.

## 어느 사건을 늦췄나

933 페이지 대조군에서 첫 OAM은 65816이 288B OBJ를 반환하기 **0.752 / 0.818ms 전**에 이미 ARM의 공유 SPI를 점유했다. 65816이 OAM을 수락한 시각은 OBJ 반환 뒤였다. 세대 912의 E1 패킷과 명령 순번을 대조해 ARM 송신 시작, FPGA 수신 완료, 65816 수락을 분리했다.

| 빈 캐시, 위상 1 / 2 | 288B 반환에서 첫 OAM 송신까지 | 같은 VBlank의 기존 DMA 범위 | 여섯 간격 합 |
|---|---:|---:|---:|
| 933 행 이력 512B 기준 | 반환 전 | 176 / 176B | 15 / 15 |
| 933 행 이력 + 페이지 공급 기준 | −0.752 / −0.818ms | 48 / 48B | 15 / 15 |
| 288B의 정상 큐 반환을 기다린 뒤 OAM 발행 | +0.296 / +0.393ms | 176 / 176B | 15 / 15 |
| 첫 OAM에서 준비된 OBJ를 먼저 소비 | +4.484 / +4.244ms | 176 / 464B | 15 / 15 |
| 후속 32B 반환 직후에도 큐를 비워 둔 후보 | +5.873 / +5.871ms | **464 / 464B** | **15 / 15** |

표의 ARM 변경 세 가지는 같은 933 페이지 공급 대조군에서 실행했다. 마지막 후보는 처음 32B OBJ가 확인됐을 때 팔레트 전송 전에 타일을 처리하고, 큰 OBJ 다음 32B를 소비할 때까지 기존 두 뱅크의 독립적인 큐 반환을 확인한다. 그 직후 12회의 상태 조회 동안 다음 패킷과 OAM의 발행을 보류한다. 이전 타일 DMA가 이미 진행 비트를 세울 수 있어, 그 비트를 마지막 32B의 완료 증거로 사용하지 않는다. 큐가 빈 동안에도 STOP·수신 검사는 계속된다.

## 32B가 남은 위치

위상 1 / 2의 목표는 각각 VBlank 48 / 49였다. 288B OBJ 뒤 32B가 반환된 선은 240 / 239였다. 이후 64B 두 건과 288B가 실제로 VRAM으로 전송됐다. 288B의 마지막 PPU 쓰기는 254 / 253선이었다. 동일 ROM의 명령 실행을 추적하니 두 위상 모두 256선에서 목적지 `0x8440`, 길이 32B인 마지막 descriptor가 주사선 검사에서 보류됐다. 실제 ROM은 252선까지만 이 경로의 검사를 허용한다. 추적 전후 ARM SPI·65816·타일 공급·DMA 기록은 바이트 단위로 일치했다.

다음 비교는 **288B DMA 종료에서 후속 32B의 주사선 검사까지**를 앞당기는 데 둔다. 목표는 마지막 descriptor를 252선 안에 검사하는 것이다. 같은 ARM의 큐 비우기를 페이지 공급 없이 933의 512B 행 이력에만 적용한 경우에는 여전히 176 / 176B였다.

## 유지 조건과 결정

- 마지막 후보의 912 최종 ACK는 MMC925보다 빈 캐시에서 **16.615 / 16.574ms** 빨랐다. 두 위상의 빈 캐시 910 캡처 기회는 유지됐다. 나머지 타일 37묶음 중 11 / 8개의 준비가 933 페이지 기준보다 늦었고 최대 지연은 0.182 / 0.156ms였다.
- 기존 캐시 위상 1은 밀집 13회와 910 캡처를 유지했다. 위상 2는 910의 마지막 D2가 캡처선보다 938클록 늦어 밀집 간격이 13→14회로 늘었다.
- 첫 E9에 확정된 부분 OBJ와 후속 전체 OBJ 두 개를 보고 상태 조회를 일찍 시작한 대조군도 빈 캐시 464 / 464B였다. 기존 캐시에서는 두 위상 모두 910 캡처가 늦어졌다.
- 마지막 ARM 링크는 213,068B로 Flash 한도 212,992B를 76B 넘었다. 두 위상 모두에서 496B·다른 타일 공급·캡처·링크 한도를 함께 충족한 후보는 없었다.
- 실제 링크한 ARM과 고정된 65816 ROM을 재생했다. 화면·map·타일·팔레트·section 5, SRAM D0 네 곳, CRC 오류·잘못된 descriptor·중복·잘못된 SEAL 거부, 복사 중·표시 중·OBJ 마지막 바이트 STOP, 타이머·base·메뉴 복귀를 대조했다. 공유 ROM 허가와 새 행 이력은 933 일정 모델이다. 신규 보드 합성·카트리지 FPS 측정은 수행하지 않았다.

재현은 `tools/nes_oam934.py prepare MODE TEMP`로 생성한 링크를 `tools/build_nes_trial577.ps1`로 빌드한 뒤 `replay MODE TEMP STORAGE PHASE CACHE`로 진행한다. `depth`는 512B 행 이력이고 `fair`는 페이지까지 사용하는 기존 933 대조군이다. `return`은 반환만 대기하고, `stream`은 첫 OAM 앞에서 준비된 타일을 소비하며, `window`는 후속 32B 반환 뒤 큐를 비운다. `proof`와 `guards`는 해당 링크의 복구 시험을 실행한다. 분석기는 세대·token·VRAM 목적지 범위, DMA 첫·마지막 PPU 쓰기, SEAL, 공개 후 ACK를 같은 시작 위상의 원본과 대조한다.

핵심 비교를 재집계하려면 두 위상에서 `beam window TEMP fair PHASE cold`도 실행한 뒤 아래 명령을 사용한다. `TEMP`는 925·933 기준 재생과 934 결과가 있는 경로다.

```text
python tools/analyze_nes_oam934.py TEMP summary.json 933/depth 933/fair return/fair stream/fair window/depth window/fair --warm 933/depth 933/fair stream/fair window/fair --proof stream window
```
