# MMC905 · 55–60초 데모의 OBJ 공급 계측

## 실기에서 한 번 실행하기

1. 전원을 끄고 ZIP 안의 `MMC905-ADVENTURE-60SEC-SD-ROOT` 폴더 내용물을 SD 루트에 복사한다.
2. MMC903에서 사용했던 일본판 모험도 4 ROM을 `sd2snes/nes/mmc905.nes`로 복사한다.
3. 메뉴에서 **NES MMC3 905.nh1**을 선택한다. 시작 후 버튼을 누르지 않고 60초 자동 종료와 메뉴 복귀를 확인한다.
4. 메뉴 복귀 뒤 `sd2snes` 폴더의 **nes-frame-mmc905.bin**, **nes-budget-mmc905.txt**, **nes-progress-mmc905.txt**, **nes-game-last-mmc905.txt**를 보관한다. 같은 판을 재실행하면 네 파일을 덮어쓴다.

## 어느 지연을 구분하는가

MMC903에서 세대 1086은 변경 map 0, BG 528, OBJ 45였고 입력 완료부터 마지막 OBJ 32B가 준비되기까지 약 118ms 걸렸다. 세대 번호는 실행마다 달라질 수 있다. MMC905는 55–60초의 화면마다 세대·작업량·ARM 입력 완료·첫 유효 최종 ACK와 FPGA가 첫 E9 명령 바이트를 받은 시각, 마지막 타일 공개 시각, 타일·token 개수를 기록한다. 제일 오래 걸린 OBJ 화면 하나에 대해서는 모든 token의 상세 내역을 남긴다.

- 선택 기준은 ARM 입력 완료부터 FPGA의 마지막 OBJ 준비까지다. ARM과 FPGA의 시계는 조회 시각으로 맞추고 약 0.39ms 단위로 비교한다. 같은 시간 단위 안의 사건은 선후가 모호할 수 있다.
- 타일마다 캐시를 통과해 실제 하위 ROM 읽기가 필요해진 첫 요청, 첫 허가, 마지막 허가, 총 허가 수를 기록한다. 허가 0인 타일은 하위 ROM을 읽지 않았다. 첫 허가부터 마지막 허가까지에는 계산과 응답 시간도 들어간다.
- 65816이 유효한 consume token을 썼을 때 실제 반환된 뱅크 번호, 길이, BG/OBJ 종류, 시각을 기록한다. 생성 순서의 타일을 소비자가 확인한 길이로 나눈 뒤 실제 token 하위 11비트와 마지막 ARM descriptor의 32비트 token을 대조한다.
- 첫 E9까지 늦으면 ARM 계획·공유 SPI, 요청에서 허가까지 늦으면 ROM 중재가 다음 조사 대상이다. ROM 허가가 끝난 뒤 이전 뱅크 반환까지 길면 소비·뱅크 재사용 일정을 확인한다. 이 기록으로 모든 후속 읽기의 개별 대기나 동시 대기의 단일 원인을 확정할 수는 없다.

일반판은 최대 124장의 요약과 선택된 한 장의 상세 내역을 기존 8KiB 메뉴용 메모리에 저장한다. 프레임당 타일 255개 또는 token 63개에 도달한 화면은 상세 비교에서 제외하며, 창을 넘긴 프레임 수는 헤더에 남긴다. SPI 조회는 해당 화면의 표시·최종 ACK를 마친 뒤에만 수행하고 SD 파일은 메뉴 복귀 과정에서 쓴다. 상세 후보를 교체한 화면에서는 추가 조회가 다음 화면 일정에 영향을 줄 수 있다. 각 행에 전체 조회 비용이 남는다. 독립 CRC·token 검사, SRAM D0 송신, 65816 표시 ROM과 STOP 경로는 MMC903과 동일하다.

기본 시험은 MMC3 한 번이면 된다. 별도 대조가 필요할 때에만 기존 로그를 복사한 뒤 NES-DIAG의 CONTROL로 동일 데모를 재생한다. 분석 명령은 `python tools/read_nes_supply905.py nes-frame-mmc905.bin`이다.

## 전달 전 검증

- 실제 65816 ROM은 MMC903과 바이트가 같다. 최종 ARM 링크는 212,732/212,992B이며 네 D0 경로의 SRAM 송신, 정상·손상 입력 CRC, 60초 타이머, STOP·base·메뉴 복귀를 검사했다.
- Quartus Lite 전체 FIT는 15,297/15,408 LE, 963/963 LAB, 54/56 M9K를 사용했다. STA 최저 여유는 setup +0.281ns, hold +0.140ns다. 기존 외부 I/O 미제약은 남아 있다. 22MHz NES 쪽에서 등록한 세 관측 신호는 84MHz의 첫 동기화 플립플롭까지 11.904ns 배선 예산을 주었고, 그 이후 경로는 일반 타이밍 검사에 포함했다.
- 실제 SPI·ROM arbiter·두 뱅크 RTL 시험에서 캐시 적중, 여러 허가를 기다린 타일, 두 번째 E9, token 자리올림, 잘못된 수령 확인, STOP을 확인했다. SPI로 읽은 두 실제 페이지를 BIN 분석기에 넣고 bank·token·길이를 각각 훼손한 자료가 거부되는 것도 확인했다.
- 최종 ARM·65816의 연속 실행은 이전·후반 표본 각 8장의 RGB가 두 위상 모두 MMC903과 같았다. 여섯 표시 간격 합은 전반 14/14, 후반 13/13 VBlank였다. 후반 마지막 ACK 차이는 위상 1에서 −120클록, 위상 2에서 −2,156클록이었다. 이 재생은 SPI 조회 시간을 부과하며, 읽기 페이지의 ROM 필드는 캐시 적중 모형이다. 실제 ROM 요청·허가는 별도의 RTL 시험에서 검증했다. 실기 FPS와 약 118ms 정체의 원인은 새 로그로 판단한다.

보드 재생성은 `tools/prepare_nes_supply905.py`의 `board`, `fit`, `image` 순이다. ARM은 `prepare_nes_supply905_arm.py`로 903 링크에 적용할 소스를 생성한 뒤 `build_nes_mmc479_arm.ps1`로 링크한다. 최종 검사는 `check_nes_supply905_arm.py`, FLOAT 래퍼를 통한 `check_nes_supply905_wire.ps1`, 두 위상·두 구간의 `replay_nes_supply905.py`, `package_nes_supply905.py` 순이다.
