# NES165 세이브 보호와 WRAM 화면 후보

## 저장 메모리 판단 수정

사용자는 다른 게임의 세이브에 영향이 없어야 한다고 명시했다. 처음 제안한 카트리지 U511 SRAM의 영상 임시 저장 전용은 철회한다. 현재 NES 이미지가 사용하지 않는다는 사실은 다른 코어의 데이터가 없다는 근거가 아니다. **카트리지 SRAM과 기존 세이브·자동 저장·복구 영역은 NES 영상 저장소로 사용하지 않는다.** 백업 후 덮어쓰기를 기본 해법으로 삼지 않는다.

기존 펌웨어의 `SRAM_SAVE_ADDR`는 MCU 주소 `0xE00000`이다. 검토한 로컬 sd2snes SA-1·GSU HDL은 MCU 주소 상위5비트 `11100`(E00000–E7FFFF)을 별도 RAM 버스로 보내며, `RAM_WE`에 SNES의 `IS_SAVERAM` 쓰기도 연결한다. 따라서 별도 SRAM이 게임 RAM/세이브 경로에 사용된다는 우려는 타당하다. 일반 base 코어를 포함해 모든 코어가 똑같이 배치된다는 의미는 아니다. `sram_*` 함수명도 특정 실물 칩 하나를 뜻하지 않는다.

GBC 저장에는 `SRAM_SAVE_ADDR`뿐 아니라 `SNAPSHOT_BASE=0xE20000` 등 복구용 내용도 있다. 어느 게임의 현재 저장 크기만 보고 나머지를 빈 공간으로 간주하지 않는다. SD의 `.srm` 파일과 실행 중 RAM/아직 저장되지 않은 내용은 구분한다. 배터리 전원 배선까지 이번 코드 검토로 확정하지 않는다.

기존164 물리 top은 `RAM_ADDR=0, RAM_OE=1, RAM_WE=1, RAM_DATA=Z`로 별도 SRAM을 비활성화한다. 이번 작업은 그 파일과 기존 저장 코드를 수정하지 않았으며, 실기에 새 쓰기를 실행하지 않았다. [부품 식별](development/FXPAK-HARDWARE-REFERENCE.ko.md)과 세이브 소유권은 별도 확인 항목이다. 이 보호 규칙은 이후 다른 코어에도 적용한다.

## 구현한 범위

[유한 C 변환기](nes-native-video165-contract.ko.md)의 출력에 연결할 `nes_native_stage165`를 추가했다. 저장 주소는 **SNES 본체의 휘발성 WRAM bank7F**다. MCU의 메모리 주소나 카트리지 SRAM/PSRAM 주소가 아니다. SNES CPU가 요청을 받아 WRAM을 읽고 써주는 전송부가 필요하며, 그 실제 전송부는 아직 없다. callback에 기존 MCU `sram_readblock`/`sram_writeblock`을 연결하면 안 된다.

두 후보 슬롯은 `$7F:0000–7FFF`, `$7F:8000–FFFF`다. 각32KiB 안의 상대 배치는 다음과 같다.

| 내용 | 상대 시작 | 최대 크기 |
| --- | --- | --- |
| BG 패턴 | 0000 | 16384바이트 |
| OBJ 패턴 | 4000 | 4096바이트 |
| 타일맵 | 5000 | 4096바이트 |
| CGRAM | 6000 | 512바이트 |
| OAM | 6200 | 544바이트 |
| HDMA 표 | 6500 | 1121바이트 |

기존164의 SNES client `$7E:2000`과 CPU 스택은 별도 bank다. 전체 새 client의 코드·스택·오디오·통신 작업 공간과 함께 최종 배치 확인은 남아 있다. MCU에는 두 화면 복사본을 만들지 않는다. ARM의 관리 구조는460바이트, 코드1290바이트, step 직접 스택168바이트다. 기존 단순 합산60316에460을 더하면60776바이트이고 링커 영역65424와의 차이는4648바이트다. **전체 링크/heap/중첩 callback/인터럽트 스택 안전 승인 수치가 아니다.**

## 순서와 실패 처리

`begin → pattern → seal → step 반복 → READY → arm → SNES 전송 게시 → 표시 ACK` 순이다. 패턴은 BG16/OBJ32바이트, 나머지 표는64바이트 이하로 외부 저장한다. 슬롯은 순서대로 채우며 누락·중복·범위를 거부한다. `seal`은 유한 반복이지만 완전 비동기는 아니므로 각 callback에서 기존 고장/시간 가드를 확인해야 한다.

`step`은 한 번에 최대64바이트, 외부 읽기 최대2회로 나누어 기존 CF86/STOP 검사 사이에 호출할 수 있다. VRAM은2바이트 단위로 비교하고32바이트 이하의 틈을 합친다. 팔레트/OAM/HDMA는 다르면 전체 표를 선택한다. 최대32명령, 이후 화면은 `payload + 명령당96` 정책 예산을 적용한다. 초기 화면만 blank 중 전체 적재를 허용한다. 이 예산은 최악 실기 처리시간 증명이 아니다.

표시 완료는 generation16과 별도 serial32가 모두 일치해야 수락한다. generation 반복도 허용하지만 serial은 재사용하지 않으며 최대값에서 새 후보를 거부한다. READY는 표시 성공이 아니다. 전송을 게시하기 **전에** WAIT로 바꾸고, 결과가 모호한 실패/중단이나 실패 ACK는 FAULT로 유지한다. 이전 표시 기준과 슬롯을 재사용하지 않고 consumer·전송·C를 함께 리셋해야 한다. 단순 재시도나 C만 초기화하는 복구는 금지한다. 게시 전 실패만 임시 후보를 폐기하고 다시 시작할 수 있다. 물리 ACK의 형식·무결성·timeout은 향후 전송부 책임이다.

HDMA는 bank7F의 후보 표를 직접 읽는다. WRAM→WRAM DMA를 사용하지 않는다. 표 바이트가 같아 명령이 없어도 **매 표시 commit마다 새 후보의 HDMA 포인터를 설치**해야 한다. 완료 후 이전 슬롯을 덮어쓸 수 있기 때문이다. 스크롤만 바뀐 경우와0명령 화면도 표시 ACK를 생략하지 않는다.

## 변경 경계 검증

선택stage02는 이전 video03이 이미 변환한 서로 다른 SMB3 frame12/15 자료를 재사용했다. C 변환기·코어 부팅·SPI·Questa 전체 시험은 반복하지 않았다. 이번에 달라진 차분 생성·소유권·SNES WRAM 출력만 확인했다.

- C가 직접 명령을 생성했다. 초기 논리 갱신5493바이트/6명령, 다음18바이트/2명령으로 이전 PC 참조와 같다. 초기 HDMA21바이트는 이미 WRAM에 있어 PPU DMA량은5472바이트이며, 논리 갱신량과 구분한다.
- 실제 SNES CPU/DMA/PPU 모델이 bank7F의 패턴/맵/팔레트/OAM과 직접 HDMA 표를 사용했다.114688픽셀이 기존 원본과 일치했다. 두 번째 표시 완료는vblank226행이다. 첫 구현stage01의 CPU HDMA 복사 성공 자료도 보존하고, 복사가 필요 없는stage02를 선택했다.
- 호스트 WRAM 모델은 모든 접근을 bank7F·64바이트 이하로 검사하고 표시 중인 슬롯 쓰기를 금지했다. 쓰기/읽기 실패, 패턴 순서, 잘못된 seal, 예산/명령 초과, 모호한 게시 중단, 실패 ACK, serial 소진9종을 거부했다. 별도로 오래된/다른 generation ACK, 중복 ACK, ACK 전 새 후보, 무변경 화면,64바이트 경계의 변경 병합, 패턴 축소 후 재확장을 검사했다.
- C의 ACK 입력은 호스트 시험이 주입한다. SNES의 실제 출력 완료 표식과 C가 물리 버스로 왕복한 시험은 아니다. ROM에 넣은 입력으로 WRAM을 채우는 시험용 전달부이며 실제 MCU mailbox가 아니다.

재현: `tools/test_nes_native_stage165.py --video <video03> --out <새 경로> --gcc <host GCC> --arm-bin <ARM bin> --mesen <Mesen>`.

## 성능 한계와 다음 작업

**18바이트는 PPU 갱신량이지 전체 전송량이 아니다.** 두 번째 장면도 새 후보5493바이트를 쓰고 비교용10986바이트를174회 읽는다. 이를 전부 MCU↔SNES 왕복으로 구현하면 작은 PPU 갱신 이득을 잃을 수 있다. 이번 C 구현은 정확한 비교/소유권의 기준이며 아직 제품의 빠른 경로로 승인하지 않았다. 기존 장면 SPI만39.59ms인 병목도 그대로다.

다음은 bank7F 전송·비교·표시 완료를 실제 SNES client와 연결하는 일이다. **비교를 SNES WRAM 내부에서 처리하거나 변경 결과를 묶어 전송해 전체 표를 MCU로 재독출하지 않는 경로**를 우선 검토한다. 새 일반 진단을 늘리지 말고 해당 경계의 실제 호출량/전송량을 측정하여 선택한다. 이후 MCU RUN 스케줄·전체 SRAM 링크·38M9K 프레임버퍼 교체·최소 fit/타이밍 검사와 SMB3 첫 레벨 실기로 간다. 기존 사운드·입력·STOP·메뉴 복귀를 유지한다. 설치 후보는164이고 새165 패키지는 없다.
