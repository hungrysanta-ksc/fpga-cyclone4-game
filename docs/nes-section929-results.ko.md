# MMC929 · section 5 선행 발행과 OBJ 뱅크 반환

실기 성능 기준은 MMC925를 유지한다. 실제 ARM 링크에서 201B 패킷을 마지막 OBJ보다 먼저 보낼 수 있었지만, 기존 캐시에서는 다음 캡처 한 번을 놓쳤고 빈 캐시에서는 원본이 이미 두 패킷을 먼저 보내고 있었다.

## 어떤 credit이 비었는가

MMC925의 55–60초 재생 클립에서 마지막 세대 912의 동일한 441B를 추적했다. ARM이 첫 패킷 발행 함수에 진입할 때 메모리를 읽고, 두 SPI payload를 이어 붙인 해시와 대조했다. 기존 캐시 두 위상 모두 201B·240B가 이미 조립돼 있었다. 그때 마지막으로 확인한 E0의 수신·반환 카운터에 이후의 실제 E1 발행을 더하면 네 칸 중 세 칸이 미반환이었다. 관측을 켠 재생과 끈 재생의 전체 65816 이벤트 시각도 일치했다.

ARM만 바꾼 두 후보 모두 첫 201B에만 우선권을 주었다. 미반환 타일의 식별자가 기존 네 칸의 검사 범위를 벗어나지 않을 때만 기존 DATA 발행 경로를 사용한다. 다음 240B와 SEAL은 원래 타일·반환 검사를 수행한다.

| 912의 기존 캐시, 직전 공개 기준 | 한 칸 예약, 위상 1 / 2 | 마지막 한 칸 사용, 위상 1 / 2 |
|---|---:|---:|
| 201B SPI 시작 변화 | +0.001 / +0.002ms | −1.766 / −1.519ms |
| SEAL 수락 변화 | 0 / 0ms | +0.663 / +0.930ms |
| 실제 수락 순서 | OBJ → 201 → 240 → SEAL | 201 → OBJ → 240 → SEAL |

마지막 칸을 쓰면 910의 마지막 D2가 캡처선을 658 / 263 마스터클록 넘겼다. MMC925에서는 120 / 499클록 여유가 있었다. 이 차이가 나타난 표시 구간은 910→911로, 두 위상 모두 2→3 VBlank가 됐다.

## 여섯 표시 간격과 912 최종 ACK

| 캐시 · 위상 | MMC925 | 한 칸 예약 | 마지막 칸 사용 | 최종 ACK 차이, 예약 / 사용 |
|---|---:|---:|---:|---:|
| 기존 · 1 | 13 | 13 | 14 | 0 / +16.645ms |
| 기존 · 2 | 13 | 13 | 14 | 0 / +16.639ms |
| 빈 캐시 · 1 | 16 | 16 | 16 | −0.019 / −0.019ms |
| 빈 캐시 · 2 | 16 | 16 | 16 | 0 / +0.008ms |

표시 간격 합의 단위는 VBlank이고, ACK 차이에서 양수는 지연이다. 빈 캐시는 원본부터 201 → 240 → 마지막 OBJ → SEAL 순서였다. 두 후보 모두 빈 캐시의 선행 DMA 496B와 목적지 주소를 유지했다.

## 다음에 앞당길 경계

MMC925 기존 캐시에서 마지막 128B OBJ(token 38)는 직전 VBlank의 246선이 끝난 뒤에야 준비됐다. 실제 빔 위치 표본으로 계산한 지연 범위는 위상 1에서 1.074–1.083ms, 위상 2에서 0.959–0.966ms였다. 928에서 SEAL 수락을 인위적으로 201선에서 195선으로 옮겨 얻은 0.383ms 예산은 이 연속 일정에 그대로 적용되지 않는다.

| MMC925, 세대 912 | 위상 1 기존 / 빈 캐시 | 위상 2 기존 / 빈 캐시 |
|---|---:|---:|
| 마지막 128B 준비 → 직전 32B OBJ(token 37) 뱅크 반환 | 3.527 / 0.611ms | 3.551 / 0.657ms |
| 그 반환 → token 38의 첫 유효 E8 | 0.333 / 0.418ms | 0.323 / 0.439ms |

다음 대상은 마지막 두 OBJ의 생산·소비 일정이다. token 37의 ROM 허가·수락·복사·뱅크 반환과 token 38의 첫 ROM 허가를 같은 시계에 맞춰, 32B 반환을 앞당기는 것이 128B 준비와 수락 중 어디까지 전파되는지 검증한다. 판정에는 910 캡처 여유와 912 선행 DMA도 포함한다.

## 검증 범위와 재현

두 ARM 링크 모두 212,992B로 Flash 한도와 같았다(MMC925는 212,940B). 각 링크에서 부팅, SRAM D0 송신 네 곳, CRC 오류 거부, 타이머·STOP·base/메뉴 복귀 경로를 시험했다. 손상·중복 descriptor 및 불량 SEAL은 거부됐고 복사·표시 중 STOP과 32B·352B OBJ 마지막 바이트 STOP을 확인했다. 두 위상·두 캐시에서 타일 내용, map, 팔레트, section 5, 여덟 RGB 화면을 원본과 대조했다. SPI·IRQ·ROM 경쟁에는 기존 공동 실행 모델을 썼다. 실기 FPS와 물리 메뉴 복귀는 이번 후보로 측정하지 않았다.

1. MMC925의 최종 링크와 재생 폴더를 준비한다. 두 후보는 `tools/nes_section929.py prepare` 및 `prepare --last-credit`로 생성하고 `tools/build_nes_trial577.ps1`로 각각 전체 링크한다.
2. 각 후보에서 `replay TEMP PHASE warm|cold`를 실행한다. 마지막 칸 사용 후보에는 `--last-credit`를 붙인다. 두 위상의 기존 캐시에서 `--observe base`와 `--observe prefix`를 각각 실행한다.
3. 각 링크에서 `check_nes_supply905_arm.run(...,925,short_header=True)`, 후보별 태그로 `nes_return920.guards`와 `nes_obj923.obj_stops`를 실행한다. `tools/analyze_nes_section929.py TEMP analysis/section929-results.json`으로 링크·표시 내용과 발행·수락·ACK 시각을 대조한다.
