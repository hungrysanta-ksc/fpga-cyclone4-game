# MMC540 첫 레벨 실기 결과와 다음 집계 기준

2026-11-02 수신. 실행·메뉴 복귀 정상이며 사용자는 비슷한 동선에서 소폭 개선을 느꼈으나 확신하지 못했다고 보고했다. 이후 마지막 5초는 움직임이 거의 없는 레벨 클리어 장면이라고 설명했다. **후반 전체 증가율을 전투·이동 장면의 개선율로 해석하지 않는다.**

| 최종 표시 완료 시각 | MMC533 | MMC540 | 관측 변화 |
|---|---:|---:|---:|
| 1초 이상 40초 미만 | 467회 · 11.97fps | 501회 · 12.85fps | +34회 · +7.28% |
| 40초 이상 60초 미만 | 253회 · 12.65fps | 287회 · 14.35fps | +34회 · +13.44% |
| 전체 관측 | 735회 / 60.07초 · 12.24fps | 803회 / 60.08초 · 13.37fps | +68회 · +9.23% |

위 두 구간은 펌웨어의 `display_1_40_60` 완료 카운터다. 전체 평균 간격은 81.73→74.82ms다. 최초 1초의 표시 수는 모두 15회다. 같은 동선이라는 사용자 관찰은 있지만 입력·적 배치·클리어 시각은 동기화하지 않았다.

## 마지막 5초의 영향

기존 5초 bin은 **작업 시작 시각으로 묶은 완료 작업 수**다. 실제 표시 완료 시각의 구간과 혼용하지 않는다.

| 작업 시작 구간 | MMC533 | MMC540 | 참고 변화 |
|---|---:|---:|---:|
| 5–40초 | 421회 / 35초 · 12.03회/초 | 443회 / 35초 · 12.66회/초 | +22회 · +5.23% |
| 40–55초 | 194회 / 15초 · 12.93회/초 | 199회 / 15초 · 13.27회/초 | +5회 · +2.58% |
| 합계 5–55초 | 615회 / 50초 · 12.30회/초 | 642회 / 50초 · 12.84회/초 | +27회 · +4.39% |
| 55–60초 | 58회 / 5초 · 11.60회/초 | 87회 / 5초 · 17.40회/초 | +29회 · +50.00% |

후반 증가 대부분은 마지막 구간에 집중됐다. 사용자 설명과 일치하며, 움직이는 장면에서 크게 빨라졌다는 근거는 아니다. 전반 완료 카운터의 +7.28%, 후반 클리어 전 작업 시작 bin의 +2.58%가 소폭 개선 체감과 더 잘 맞는다. 정확한 5–55초 완료 FPS는 기존 로그로 복원할 수 없다.

## 처리 비용과 종료

전체 실행 DWT 누적 시간을 완료 표시 수로 나눴다. IRQ·전송·대기를 포함하며 SPI opcode·poll 비용은 여기에 중첩된다.

| 항목 | MMC533 | MMC540 | 변화 |
|---|---:|---:|---:|
| 수신 | 19.95ms | 18.86ms | −1.09ms |
| 계획·공급 | 16.17ms | 14.51ms | −1.67ms |
| 출력·최종 ACK | 44.97ms | 40.84ms | −4.13ms |

출력·최종 ACK가 여전히 가장 크다. 장면 구성이 달라 각 감소분을 코드 변경의 순수 이득으로 확정할 수 없고, 이 로그에서 순수 DMA·마지막 VBlank 대기를 분리할 수 없다. 전체 74.82ms와 60Hz 예산 16.67ms의 차이는 약 58.15ms이며 지속 60fps는 미달이다.

384KiB 적재·readback, START, STOP, base 복구, MENU_PREPARED를 확인했다. 전송 실패·CRC 오류·ROM 오류는 0건이다. input commit 804회 중 표시·EA 완료는 803회이고 마지막 완료는 59.96초다. 마지막 SEAL 요청은 미완료이며 표시 수에 넣지 않았다. `native_result=1`, window error 3, sink error 2는 선택 ARM의 deadline/transfer 경계 종료와 일치한다. 실패한 임의 전송을 정상으로 간주하는 규칙은 아니다. 마지막 큐 sent/retired는 모두 22095다. 보존된 capture 거부·회복 이력 2쌍은 fetch/ROM 오류가 없으나 전체 캡처 무손실을 증명하지 않는다.

## 다음 집계와 작업

사용자 요청에 따라 다음 시험판부터 **0–5초와 55–60초를 제외**한다. 최종 ACK 후 표시 완료 시각 기준 **[5,40), [40,55), 합계 [5,55)**를 사용한다. 60초 실행·STOP·메뉴 복귀는 그대로다. 새 로그 필드는 `display_5_40_55`이며 기존 두 카운터를 재사용한다. 기존 `display_1_40_60` 로그는 원래 정의로 해석하고 새 구간으로 소급 변환하지 않는다.

[생성기](../tools/prepare_nes_windows541.py)는 검증된 MMC540에서 집계 조건과 로그 필드만 변경한다. [경계 검사기](../tools/check_nes_windows518.py)의 `--layout trimmed`로 4.99/5.00초, 39.99/40.00초, 54.99/55.00초 경계·reset·미완료 제외를 확인한다. 다음 전달본은 성능 후보에 이 변경을 함께 넣고 새 파일명을 사용한다. 현재 전달된 MMC540 ZIP은 변경하지 않는다.

새 집계를 적용한 ARM02 전체 빌드와 실제 linked ARM 경계 검사는 통과했다. firmware 212,428B·Flash 여유 564B·BSS 18,592B로 MMC540과 같다. [검사 결과](../analysis/windows541-verification.json) 초기 ARM01은 sandbox의 임시 드라이브 매핑 거부로 빌드 전에 멈췄고 별도 ARM02에서 기존 임시 빌드 절차로 완료했다. 이 빌드는 다음 전달용 집계 변경의 검증이며 새 ZIP을 배포한 것은 아니다.

후속 성능 작업은 MMC540을 기준으로 출력·최종 ACK의 잔여 DMA와 마지막 VBlank를 동일 입력·두 시작 위상에서 분리하고, 첫 BG ROM 구간·STOP·새 패킷 우선·독립 검사·최종 ACK를 유지한다. 실기 비교는 새 5–55초 카운터로 판단한다. 이번에는 FPGA나 소비 ROM을 변경하거나 다시 합성하지 않았다.
