# 911의 마지막 테이블 반환과 팔레트 보존 여부

## 목표

978에서 911의 마지막 240B 반환과 SEAL 독립 검사를 앞당기면 911을 VBlank 44의 246선까지 공개하고 912 최종 ACK도 줄일 수 있는지 확인했다. 908 공개, 909 선행 DMA 624B, 910 캡처, STOP과 마지막 정상 화면 보존을 함께 대조했다.

## 작업내용

전체 ARM 링크 세 개를 각각 두 시작 위상에서 905–912까지 실행했다. high는 OAM 상위 속성 32B만 마지막 테이블 뒤에 발행한다. split은 추가로 OAM 반복 구간을 두 테이블 패킷 사이에 둔다. fifo는 high의 순서를 사용하고 마지막 OAM 32B를 큐에 넣으면 이어서 SEAL을 발행할 수 있게 했다. 중간에 다른 패킷이 들어오면 이 조건을 해제한다. 수신기의 순차 수락·독립 검사와 최종 ACK 확인은 유지한다.

978의 65816 ROM을 Mesen에서 그대로 실행해 세대별 RGB, 실제 WRAM 읽기 주소, 빈 큐 조회, DMA 시작·종료를 추적했다. 240B 반환 뒤 SEAL 시점에 WRAM을 바꾸는 오류도 별도로 주입했다. 시간은 공유 SPI·ROM 모델과 ARM 전체 링크를 연결한 재생 결과다.

## 성과

911은 모든 후보에서 표시까지 2 VBlank가 걸렸다. 밀집 여섯 표시 간격 합도 두 위상 모두 13회였다. 아래 시간은 978 대비 ms이며 각 칸은 위상 1 / 2 순이다. 음수는 기준보다 이른 시각이다.

| 911 발행 순서 | 마지막 240B 반환 | 마지막 일반 패킷 반환 | SEAL 진입 | 912 최종 ACK | 909 선행 DMA | VBlank 44의 911 타일 DMA |
|---|---:|---:|---:|---:|---:|---:|
| high | −0.305 / −0.709 | +0.191 / −0.213 | +1.002 / +0.791 | +0.004 / 0.000 | 624 / 592B | 432 / 432B |
| split | −0.150 / −0.372 | +0.346 / +0.124 | +1.157 / +1.069 | +0.010 / +0.008 | 592 / 592B | 432 / 432B |
| fifo | −0.451 / −0.674 | +0.045 / −0.178 | −0.148 / −0.176 | +0.015 / +0.023 | 624 / 624B | 0 / 0B |

OAM 32B를 뒤로 보내면 테이블이 빨리 반환돼도 SEAL 전에 그 OAM의 큐 반환이 남는다. fifo는 대기를 줄였지만 새 패킷이 먼저 수락되어 타일 DMA를 시작할 빈 큐 구간도 사라졌다. 978에서 240B 원본 확정→ARM 조립 마지막 쓰기는 4.134 / 4.259ms였고 여기에는 앞선 패킷 발행과 조회가 포함된다. 마지막 쓰기→E1 시작은 0.958 / 0.958ms, 전송은 0.839 / 0.839ms, 도착→65816 수락은 0.369 / 0.421ms, 수락→반환은 0.370 / 0.370ms였다.

스크롤 검사는 5개 주소를 읽어 약 0.090ms가 걸렸고, 두 위상 모두 수신 초반에 이 시간을 확보할 수 있었다. 테이블·길이 검사는 69개 주소를 읽어 약 0.545ms가 걸렸고 그중 60개는 마지막 240B에 있었다. 마지막 일반 패킷 반환 즉시 SEAL을 시작하고 두 검사 시간을 모두 숨기며 타일 432B까지 끝냈다고 가정해도, 246선까지 978에서 0.548 / 0.797ms, fifo에서 0.595 / 0.618ms가 부족하다. 이 값은 raw 192B에 바이트 전송 시간만 부과한 낙관적 하한이다.

후보 여섯 실행 모두 908을 VBlank 38의 245선에 공개했고 910 캡처에 성공했다. 여덟 화면 RGB는 기준과 일치했다. 각 후보에서 STOP·잘못된 SEAL을 주입했을 때 910 화면을 보존했고, 스크롤 또는 테이블 WRAM을 반환 후 손상한 두 시험에서도 기존 독립 검사가 0xE0로 거부했다. 세 링크에서 메뉴 복귀 조건을 확인했다. Flash는 high 213,120B, split·fifo 213,152B로 212,992B 한도를 각각 128B·160B 초과했다. 실기 기준 MMC966과 개발 기준 978을 유지한다. [두 위상 클록·오류 주입·메모리 대조 결과](../analysis/tail986-results.json)

## 후속작업

다음 후보는 **OAM이 바뀌어도 같은 팔레트만 독립적으로 재사용하는 경로**다. 두 위상에서 909·910·911의 실제 팔레트 패킷을 복원하니 세대별 512B가 같았다. 909 최종 ACK, 910 최종 ACK, 911 BEGIN, 911 첫 팔레트 수락 직전에 대상 뱅크 WRAM과 표시 중인 CGRAM을 직접 읽었고 각각 불일치 0B였다. OAM 후반 432B는 911과 비교해 909에서 93B, 910에서 57B가 달랐다.

911은 이 팔레트를 4개 패킷, 공유 SPI 344B로 다시 보냈다. SPI 점유는 양쪽 1.248ms, 65816 수락→반환 합은 1.631 / 1.635ms였다. 두 작업은 겹치므로 합을 절감량으로 쓸 수 없다. 다음에는 팔레트 재사용 권한을 대상 뱅크의 최종 ACK에 묶고, 65816의 독립 대조 및 재사용 명령 비용까지 반영한다. CGRAM 재전송 생략은 현재 표시 팔레트의 일치까지 확인할 때만 시험한다. cold·STOP·부분 쓰기에서 전체 복원하고 WRAM 손상을 거부하는 조건으로 909 선행 624B, 911 공개선, 912 최종 ACK를 다시 측정한다.

재현에는 `nes_tail986.py`의 prepare·run·guard, `trace_nes_tail986.py`의 기본 추적·--damage·--palette, `check_nes_tail986.py`를 사용했다.
