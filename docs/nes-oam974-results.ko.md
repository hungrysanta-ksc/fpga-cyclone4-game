# 911 반복 OAM 복원과 화면 공개

## 목표

973의 232B 팔레트 앞 OBJ 서비스와 같은 ARM을 사용했다. 911의 반복 OAM 패킷을 빨리 소비했을 때 908 공개를 유지하면서 910→911 표시 간격과 912 최종 ACK까지 함께 줄어드는지 확인했다.

## 작업내용

빈 캐시 두 시작 위상에서 리셋부터 905–912까지 ARM 바이너리와 65816 프로그램을 실행했다. FPGA 타일 공급과 SPI에는 기존 포트 모델을 사용했다. 원래 프로그램은 세대 911에서 OAM 오프셋 176에 네 바이트 `00 f0 00 00`을 DMA로 읽고, 나머지 332B는 WRAM 안에서 반복 복사한다. 실행 주소별 시각을 같은 패킷의 수락·반환 기록과 연결했다.

8B 후보는 원래 부트로더의 빈 코드 공간을 사용했다. 16B 후보는 원래 4B DMA와 범위 검사를 거친 다음 남은 길이의 앞부분을 MVN으로 복원하고, 16B마다 16비트 쓰기 여덟 번으로 반복한다. 이 후보를 넣기 위해 부팅 시 복원·검증 바이트 루틴을 공유하고 분기 하나를 단축했다. 각 로더로 원래 OAM 본체도 실행해 부팅 시각의 영향을 분리했다. 최종 SEAL 검사는 모든 후보에서 같다.

## 성과

원래의 반복 OAM 수락→반환은 1.1803 / 1.1799ms였다. 그중 MVN이 두 위상 모두 17,784 마스터 클록(0.8280ms)을 썼다. 나머지 약 0.352ms에는 패킷 판독·범위 검사, 최초 4B DMA 설정·실행, 서비스와 ACK가 포함된다. 앞선 스크롤 패딩은 수락부터 반환까지 1.505 / 1.504ms였고, 첫 OBJ가 포트 모델에 공개되기 **1.015 / 1.065ms 전**에 이미 반환됐다.

| 같은 로더 안에서 비교 | 위상 1 | 위상 2 |
|---|---:|---:|
| 8B 후보의 OAM 수락→반환 | 1.1803 → 1.2133ms | 1.1799 → 1.2129ms |
| 16B 후보의 OAM 수락→반환 | 1.1826 → 0.9362ms | 1.1788 → 0.9338ms |
| 16B 후보의 911 SEAL 수락 변화 | 46.84µs 빠름 | 0.28µs 늦음 |
| 16B 후보의 910→911 표시 간격 | 2 → 2 VBlank | 2 → 2 VBlank |
| 16B 후보의 912 최종 ACK 변화 | 10.43µs 늦음 | 2.23µs 빠름 |

16B 복원은 명령 하나에서 약 0.245ms를 회수했다. 같은 로더 대조군과 후보의 911 공개는 모두 244선이었고 905–912의 공개 VBlank도 모두 같았다. 973에서 측정한 직전 VBlank 부족분은 2.386 / 2.297ms였다. 16B 후보를 리셋부터 원래 973과 비교하면 로더 비용까지 반영되어 908·911 모두 위상별로 3 / 1 VBlank 늦었다. ARM Flash는 212,856 / 212,992B, 65816 ROM 여유는 원래 24B, 8B 후보 1B, 16B 후보 0B였다.

모든 실행에서 여덟 RGB 화면이 원본과 일치했다. 두 후보에 서로 다른 네 바이트를 주입한 별도 재생에서 길이 8·12·332·336B의 전체 결과와 양쪽 이웃 바이트를 확인했다. 복원 중 들어온 STOP은 기존 서비스 경계에서 0xE4로 처리됐다. 334B 비정렬과 오프셋 176에서의 340B 범위 초과는 쓰기 전에 0xE0로 거절됐다. 모든 오류 재생에서 910이 마지막 공개 화면이었다. 실기 FPS·메뉴 복귀와 보드 합성은 이번 실험에서 새로 측정하지 않았다. ## 후속작업

MMC966과 기존 65816을 유지한다. 다음 비교는 911의 입력 완료→plan 발행→첫 BG·OBJ 준비부터 시작한다. 패딩이 끝난 뒤에도 타일이 준비되지 않은 구간에서 실제 ROM 허가를 앞당길 수 있는지, 그 시간과 마지막 일반 패킷 발행을 겹쳤을 때 SEAL 수락이 직전 VBlank까지 이동하는지 확인한다. 8B·16B OAM 루프 단독 튜닝은 여기서 종료한다.

재현에는 973의 두 위상 `973before232` 결과와 같은 TEMP를 사용한다. `nes_oam974.py trace TEMP --phase N`은 원래 복원을 계측한다. `build TEMP`와 `run TEMP --phase N`에는 각각 옵션 없음, `--control`, `--inline`, `--wide`, `--wide --control`을 적용한다. `guard_nes_oam974.py TEMP LENGTH`를 여섯 길이에 대해 기본과 `--wide`로 실행한 후 `check_nes_oam974.py TEMP analysis/oam974-results.json`으로 집계한다. 각 재생에는 새 출력 폴더를 사용한다.
