# 커비 첫 입력 블록의 FPGA 준비 시각

MMC1029·1030 실기에서 33.23초의 입력 수신량은 두 판 모두 16블록·1,657B였다. 첫 D1 이후의 수신 소요가 같았는데도 직전 화면 공개를 기준으로 MMC1030의 첫 D1이 10.78–14.04ms 빨랐다. 당시 BIN은 D1 전의 FPGA 상태를 기록하지 않았다. [실기 비교](nes-kirby1029-input.ko.md)

## 두 원인이 같은 로그를 만드는 조건

커비 캡처 1830의 BEGIN과 map 셀 80개를 보드의 압축기와 SPI 송수신기로 재생했다. 아래 두 실험은 같은 120B 블록을 읽고, 기준 기록의 모든 바이트와 CRC를 대조한 뒤 D2와 다음 D0로 token 반환을 확인했다. 공유 SPI 부하는 다른 명령에 할당된 117B 거래 100건으로 고정했다. 이 부하는 실기 33.23초의 거래 내역을 재구성한 값이 아니다.

| 84MHz 호스트 클록 | 생산을 12ms 늦춤 | 데이터가 준비된 채 같은 버스 일정을 기다림 |
|---|---:|---:|
| 첫 블록 읽기 가능 | 1,010,886 | 2,886 |
| 첫 유효 D0 opcode 수신 | 1,028,004 | 1,028,004 |
| D1 opcode 수신 | 1,028,877 | 1,028,877 |
| 읽기 가능 → D1 | 0.214ms | 12.214ms |
| D2로 전달된 대기 구간 | 0–0.390ms | 12.093–12.483ms |

별도 재생에서는 유효 D0 이후 D1만 12ms 늦췄다. FPGA는 첫 조회 후 보존된 블록의 대기도 셌다. 4개 캡처의 첫 블록과 포화값, 대기 중 공통 리셋에 의한 블록·token·시간 폐기를 검사했다. 이 재생은 65816의 화면 픽셀이나 실제 ARM의 SPI 점유율을 측정하지 않는다.

## 실기에서 읽는 방법

FPGA는 헤더를 포함한 첫 블록의 압축·CRC 생산이 끝난 뒤부터 D1 opcode가 들어올 때까지 센다. 32,768클록(약 0.390ms) 단위이며 127은 약 49.54ms 이상이다. 원래 사용하던 D2 응답의 길이 상위 바이트에서 여유 7비트를 사용한다. D0 길이·token·전송 CRC는 원래대로 확인하고, ARM은 D2 응답 CRC와 다음 D0의 token 증가까지 확인한 세대에만 시간을 남긴다. 완성된 입력의 기존 32비트 바이트 합계에 여유 상위 바이트가 있어 BIN 크기와 샘플 수를 유지했다.

MMC1031은 OBJ 선행 읽기, MMC1032는 기본 캐시 대조판이다. 양쪽의 400ms 표본에서 BG·OBJ·map·타일·묶음 수 및 수신 블록·바이트 수를 맞춘다. 준비 후 대기가 줄면 ARM이 준비된 데이터를 읽기까지의 구간에서 얻은 이득이다. 준비 후 대기가 같아도 직전 공개 기준 첫 D1이 앞당겨지면, 해당 화면은 FPGA 준비와 이전 공개의 상대 위상을 살핀다. ARM의 첫 D1 호출과 FPGA의 opcode 수신 사이에는 거래 시작 비용이 있으므로 서로 다른 클록의 절대 타임스탬프를 직접 빼지 않는다.

두 BIN의 순서는 `python tools/compare_nes_kirby1031.py nes-frame-mmc1032.bin nes-frame-mmc1031.bin`이다. 포화 구간의 상한은 미정으로 남긴다. FPS는 실기 budget 로그의 1–30초와 30–60초 표시 수로 비교한다. 화면 깨짐과의 시간 대조에는 발생 시각 또는 영상이 필요하다.

## 재생과 보드 검증

- `tools/prepare_nes_kirby1031.py board --edition N`과 `arm --edition N`이 각 판의 소스를 만든다. 기본 캐시판에서 전용 계수기만 추가한 후보는 964/963 LAB, 기존 시각 신호를 공유한 후보는 965/963 LAB를 요구했다.
- 기본 캐시판의 `bus --edition 1032` 후보는 MMC1027에서 검증한 SNES 주소·데이터 동기화와 SPI73 응답 회로를 재사용한다. 두 판 모두 첫 블록에는 동일한 전용 계수기를 사용한다. 기본 캐시판은 기존 보드와 10,966클록의 ROM·패킷·ACK·STOP 및 리셋, SPI73 응답 346비트를 대조한다.
- Questa FLOAT에서 `check_nes_kirby1031.ps1`과 `check_nes_kirby1032.ps1`을 순차 실행한다. ARM 빌드 뒤 `check_nes_kirby1031.py N`은 실제 링크의 수신기에 지연 31과 포화 127을 전달해 세대 905·906을 검사한다. 정상·첫 D1 CRC 오류·빈 응답 1,247회 조건을 포함한다.
- 각 보드에 `fit_nes_kirby1027.ps1`을 사용한다. `package_nes_kirby1031.py N`은 실기판의 FIT·STA·PSRAM I/O, 최종 링크의 75회 샘플링·STOP·base·메뉴 복귀, 프로그래머와 ZIP 내용을 확인한다.

| 최종 설치본 | ARM Flash | LE | LAB | M9K | 57개 STA 항목 중 최소 여유 |
|---|---:|---:|---:|---:|---:|
| MMC1031 선행 읽기 | 212,676B | 15,348 | 963 | 53 | +0.131ns |
| MMC1032 기본 캐시 | 212,676B | 15,341 | 963 | 53 | +0.125ns |

두 판의 ARM 실행 이미지는 판 번호·파일명을 치환하면 바이트 단위로 일치한다. FPGA 계수기와 D2 응답 코드도 일치한다. [MMC1031 검증 기록](../analysis/trial1031-package.json) · [MMC1032 검증 기록](../analysis/trial1032-package.json)

## 무입력 60초 실기 결과

각 한 차례 실행했다. 두 판 모두 ROM 786,432B 검증, STOP, base 복구 및 메뉴 복귀에 성공했다. 1–30초·30–60초의 공개 수는 MMC1032 기본 캐시 805·852장, MMC1031 선행 읽기 790·858장이다. 기본 캐시 대비 오프닝은 27.76→27.24 FPS, 데모는 28.40→28.60 FPS였다.

각 판의 75개 표본 중 유효한 74개를 비교했다. 50.83–50.84초 한 건씩은 직전 공개와 SEAL 사이에서 16비트 시각이 돌아 헤더가 무효였다. 같은 400ms 구간에서 BG·OBJ·map·출력 타일·묶음·입력 블록·바이트가 전부 일치한 쌍은 0개다. BG를 제외한 36쌍에서는 선행 읽기판의 BG 슬롯 수가 모두 5개 많았고, 공개 간격은 36쌍 모두 같은 VBlank 수였다. 33.23–33.24초의 출력 타일도 10개와 5개여서 앞선 시험의 12ms 차이를 같은 작업량으로 재현했다고 볼 수 없다.

FPGA 준비 후 첫 D1까지 0.390ms 미만인 표본은 기본 캐시 41개, 선행 읽기 42개다. 가장 긴 표본의 상한도 각각 3.901ms·5.852ms다. 3 VBlank가 걸린 화면에서 첫 E9→마지막 타일 준비 중앙값은 기본 캐시 25.55ms(10장), 선행 읽기 23.41ms(6장)였다. 두 판 모두 2 VBlank 화면에서는 0.39ms였다. 화면별 타일 수가 다르므로 판 간 속도 차이의 원인으로 단정할 수 없다. 다음 병목 대조는 긴 공급 구간의 타일 수·묶음·캐시 적중을 맞춰 ROM 허가와 뱅크 반환을 확인한다.

사용자가 보고한 MMC1032의 36–37초·53–54초에는 유효 표본이 3개·2개 있었다. 5개 모두 공개 간격은 약 2 VBlank(32.77–33.55ms)였고 map dirty는 0이었다. 전체 전송 실패·캡처 중단·native video 오류는 0이었다. 종료 요약의 수신 상태 23(D1 전송 또는 CRC 실패)에는 발생 시각이 없다. 400ms 표본에 표시 픽셀이 없어 순간 깨짐을 특정 세대에 연결할 증거는 없다. 재시험과 수정은 보류한다.
