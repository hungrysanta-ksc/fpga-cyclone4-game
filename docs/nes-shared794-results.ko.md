# MMC792 검은 화면과 PR160 eGBC 호환성

전원을 완전히 껐다 켜면 SD 메뉴가 뜬다. 사용자는 MMC792 설치 후 NES와 eGBC를 각각 선택했고 두 경우 모두 검은 화면을 관찰했다. 마지막으로 정상 동작한 eGBC 설치본은 PR160의 `GBC774-RGB555-SD-ROOT.zip`이다. 전원을 끈 뒤 이 ZIP의 `sd2snes` 폴더를 SD 루트의 같은 폴더에 병합 복사하고 기존에 성공했던 eGBC로 확인한다. 이 ZIP에는 공용 ARM·eGBC FPGA·SNES 렌더러 세 파일이 들어 있다.

## eGBC

792·793 빌드가 PR160 이전의 ARM 소스 트리를 계승했다. 설치본은 공용 `firmware.stm`을 덮어썼지만 eGBC FPGA와 렌더러는 제공하지 않았다. `load_rom`의 실제 호출 위치부터 ARM 기계어를 실행하고 FatFS와 SRAM 쓰기·읽기만 모델링했다. GBC774 렌더러 131,072바이트가 원본과 같아도 두 링크는 CRC32 `0af44f8a`를 기대해 거부했다. 이 검사를 통과해야 SNES 리셋을 풀어 eGBC 로딩 화면을 띄운다. 기존 ARM에는 PR160의 MBC5 8MiB 헤더·용량 확인도 빠져 있었다.

794·795 개발 링크에는 PR160의 헤더 처리와 8MiB 로더, FPGA 용량 응답 검사, 렌더러 CRC32 `b6ed88f2`를 반영했다. Flash 공간은 배포 설정에서 비활성인 GBC 상태 텍스트 보고 루틴을 컴파일할 때 제외해 확보했다. 두 링크 모두 원본을 수락하고 SRAM 마지막 바이트를 바꾼 시험에서는 거부했다. 펌웨어 크기는 212,656·212,620B로 212,992B 한도 안이다. 이 결과가 검증하는 범위는 로더의 렌더러 수락 분기까지다. 실제 화면 출력과 8MiB 게임 실행은 이번 링크에서 미확인이다.

## NES

MMC792의 80개 진행 레코드는 seq 0–79까지 이어진다. 마지막 `DISPLAY_NEXT`는 231.830초에 기록됐다. 해당 호출에 도달하려면 393,216바이트 적재, 전체 읽기 비교, FINISH 상태 `0x82` 검사를 통과해야 한다. 성공한 MMC763도 같은 지점까지 233.240초가 걸렸다. 다음 기록인 `DISPLAY_STOPPED`는 리셋 재인가, STOP, 상태 보존 검사를 모두 지난 뒤에 남는다. RUN 중에는 SD에 기록하지 않는다. 따라서 이번 파일만으로 START 응답 `0x86`, E0 준비, 리셋 해제, 65816 준비 상태 3, 첫 화면 또는 종료 처리 중 어느 지점까지 실행됐는지는 판별할 수 없다.

수정 링크의 기존 메뉴 준비 시험과 정상·program·DONE·busy·token의 base 복귀 모형 시험은 양쪽에서 통과했다. NES 실기 기준은 MMC763이다. 다음 재현은 792의 보드·부팅 ROM을 고정하고 START 응답, 리셋 전후 E0, 65816 준비, 첫 프레임 진입을 순서대로 구분한다. RUN 중 SD 쓰기를 추가하지 않고 STOP·독립 검사를 유지한다. 새 실기 설치본은 보류한다.

## 재현

1. `tools/prepare_nes_shared794.py 794 <patch794>`와 `795 <patch795>`로 두 패치를 만든다. `tools/build_nes_mmc479_arm.ps1`에서 각 792·793 전체 빌드를 Base로 지정하고 결과를 `../probes/nes-shared794/link794`와 `link795`에 저장한다.
2. `tools/check_nes_shared794.py`로 GBC774 ZIP의 렌더러를 원본 두 링크와 수정 두 링크에 공급한다. 최종 ELF의 로드 구간을 실제 STM 파일과 대조하며 손상 시험은 수정 링크의 마지막 SRAM 읽기에서 한 비트를 바꾼다.
3. 각 수정 링크에 `tools/check_nes_menu533.py`와 `tools/check_nes_transfer512_recovery.py`의 다섯 fault 조건을 적용한다. 검증 출력은 각 링크의 `menu.json`, `base-*/result.json`에 있다.
