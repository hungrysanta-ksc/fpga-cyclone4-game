# MMC1010 · 마지막 타일 뒤 실제 공개 간격 계측

## 목표

MMC966의 모험도 4 무입력 데모에서 타일 공급이 2ms 이내였는데 ARM의 완료 확인까지 1 VBlank를 넘긴 29장이 있었다. 같은 화면 세대의 이전 공개, SEAL 첫 헤더 읽기, 마지막 PPU DMA 쓰기, 현재 공개, 최종 ACK를 직접 관측해 어느 구간에서 늦었는지 판별한다. 실기 작업량 대조군은 [1009의 네 쌍](nes-demo-loss1009-results.ko.md)을 사용한다.

## 작업내용

- MMC966의 상세 타일·ROM 페이지 기록을 다섯 개의 16비트 시각으로 교체했다. 관찰 시계는 84MHz를 32,768분주해 한 눈금이 0.390095ms다. FPGA는 마지막 E9 공급 세대의 요약, 수락된 마지막 descriptor의 token, 세대와 기록 상태를 기존 SPI 명령 `0x78`에 실어 보낸다. ARM은 SPI 성공·세대·token·완료 플래그·마지막 바이트를 확인한 기록만 사용한다.
- 공개 신호는 SEAL 헤더를 읽은 뒤의 첫 `$2100` 쓰기다. DMA 끝은 WRAM `$7F`에서 PPU `$2118/$2119/$2122/$2104`로 실제 전송한 마지막 바이트다. SEAL의 큐 반환과 ARM의 첫 유효 E0를 별도로 관측한다. ARM–FPGA 시계 간 지연은 조회 시간과 두 시계의 해상도를 포함한 범위로 해석한다.
- 최종 ACK가 빠졌거나, 한 클록에 두 시각이 겹치거나, 16비트 시계가 랩되거나, 조회 도중 소유권이 바뀌거나 STOP이 걸리면 해당 기록을 폐기한다. 새 세션의 첫 공개는 다음 세대의 비교 기준을 만든다.
- 55–60초에는 판독 한 번에 32B를 쓴다. MMC966 일반 헤더보다 16B 많아 2.625MHz에서 순수 전송 시간이 약 48.8µs 늘고, 상세 페이지 조회는 없어진다. 실기 비교에서는 기록된 화면 수, 유실 수, 조건에 맞는 세대 수를 함께 센다.

## 성과

1. Questa에서 실제 sink의 SPI 패킷·CRC·65816 헤더 읽기와 ACK 쓰기·PPU 스트로브를 통해 두 위상 각각 906–912의 다섯 시각을 읽었다. 기록된 978 일정을 주입한 14개 간격에서 원본을 같은 눈금으로 변환한 값과 모두 일치했다. STOP을 SPI 마지막 바이트에 건 경우, 잘못된 ACK, 불완전 세대, 세대 번호 재사용 및 시계 랩도 확인했다.
2. MMC966의 설치 65816 ROM을 Mesen에서 같은 패킷 도착 일정으로 재실행했다. 14개 구간 모두 SEAL과 최종 ACK 사이의 `$2100` 쓰기는 한 번이었고 값은 `$0F`였다. 마지막 PPU DMA의 원본 뱅크와 목적지 포트도 보드 관측 조건에 들어왔다. 이 검증은 해당 ROM과 재생 장면을 대상으로 한다.
3. 최종 ARM 링크는 **212,052B**, Flash 여유는 **940B**다. MMC966보다 408B 줄었다. 메뉴 scratch 사용은 **8,044→7,458B**다. 60초 타이머, SRAM D0, 손상 ROM CRC 거절, 최종 큐 identity, STOP·base·메뉴 복귀 분기, 4개 파일 모드와 버퍼 포화 처리를 링크된 ARM에서 검증했다. 실기 FPS와 실제 화면 품질은 새로 측정하지 않았다.

4. Quartus Lite 전체 FIT에서 15,328/15,408 LE, 963/963 LAB, 55/56 M9K를 사용했다. MMC966보다 12 LE와 1 M9K 줄었다. 전체 STA 최저 여유는 setup +0.449ns, hold +0.176ns, recovery +1.230ns, removal +0.346ns다. B의 초기화→계측 레지스터 경로(−1.459ns)와 C의 초기화→SPI 응답 경로(−1.141ns)를 분리해 추적하고 취소 상태를 호스트에서 등록했다. CPU·PPU의 STOP 실행 경로는 그대로 사용한다.

## 후속작업

모험도 4를 MMC1010에서 한 번 무입력으로 60초 실행한다. [설치와 로그 회수](nes-mmc1010-trial.ko.md). 1–30초와 30–60초 표시 수, 55–60초 세대별 기록의 누락·유효 수를 먼저 확인한다. MMC966과 작업량이 맞는 화면에서 이전 공개→현재 공개를 구하고, 마지막 타일→공개와 공개→ARM E0를 구분한다. 공개가 한 VBlank 밀렸는지 판별할 때에는 연속 공개의 주기와 0.390ms 계측 눈금을 함께 사용한다. E0가 늦은 화면은 다음 입력·공개까지 그 지연이 이어진 경우에 우선한다.

## 재현

1. `tools/prepare_nes_display1010_arm.py`로 검증된 MMC966 링크를 복제하고 `tools/build_nes_trial577.ps1`로 전체 링크한다. `tools/check_nes_display1010_arm.py <모험도4 ROM>`으로 검사한다.
2. `tools/nes_display1010.py <temp> --compile`로 964 설치 보드 프로젝트와 Quartus Lite를 사용한다. `tools/test_nes_display1010_wire.py <probes/nes-display1010/tb_nes_display1010.sv>`로 테스트를 생성하고 기존 FLOAT 래퍼로 `tools/check_nes_display1010_wire.ps1`을 실행한다.
3. `tools/check_nes_display1010_ppu.py <temp> <1 또는 2>`로 두 위상을 대조한다. `tools/analyze_nes_display1010.py <temp>`는 링크·보드 보고서와 관측 결과를 [결과 JSON](../analysis/display1010-results.json)에 기록한다. 계측 BIN 해석기는 `tools/read_nes_display1010.py`다.
4. `tools/package_nes_display1010.py <temp>`는 합성 후 초기화된 5,120B ROM, 펌웨어 CRC, BI3의 복호화·프로그래머 출력, 기준 ZIP 자산의 해시와 최종 압축 파일을 확인한다.
