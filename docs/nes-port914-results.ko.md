# 914I · E9 선행 읽기와 공유 PSRAM 포트

913idle ARM과 912 표시 ROM의 바이트를 고정하고 MMC907 실기판의 FPGA에 선행 읽기를 연결했다. 세대 912의 두 타일 뱅크에서 실제로 head가 보인 시각을 CPU 재생에 적용했다. 네 조건 모두 913의 표시 간격과 최종 ACK 시각이 유지됐다. 실기 비교 기준은 MMC907이다.

| 캐시·시작 위상 | 여섯 표시 간격 합 MMC907 → 914I | 세대 912 SEAL 전 DMA | MMC907 대비 65816 최종 ACK |
|---|---:|---:|---:|
| 기존 1 | 15 → 14 VBlank | 16B | 16.657ms 빠름 |
| 기존 2 | 15 → 14 VBlank | 16B | 16.644ms 빠름 |
| 빈 캐시 1 | 20 → 16 VBlank | 496B | 66.541ms 빠름 |
| 빈 캐시 2 | 20 → 17 VBlank | 496B | 49.936ms 빠름 |

기존 캐시에서 911 COMMIT의 마지막 D2가 다음 캡처선보다 96.474 / 75.708µs 먼저 끝났다. 세대 910·911의 E8 조회 85회와 세대 912의 네 조건 153회에서 RTL의 head token, E9 수락 수, 상태를 ARM이 읽은 시각에 대조했다. 238회 모두 일치했다. 912의 여덟 묶음 656B는 네 조건에서 게임 CHR로 독립 계산한 바이트와 일치했다. 빈 캐시 선행 DMA는 기존 496B와 전송 주소가 모두 일치했다.

## 공유 포트와 STOP

75.708µs는 기존 캐시 위상 2에서 얻은 여유다. 빈 캐시 위상 2의 같은 비교선은 3.911µs 늦었고, 이 조건의 여섯 표시 간격 합은 17회였다.

CRC를 통과한 E9의 기존 payload RAM을 NES 클록에서 읽는다. 정규 decoder가 같은 RAM을 요구하면 정규 읽기가 먼저다. 기존 CHR 캡처가 적중하면 그 값을 쓰고, 실제 OBJ 읽기가 빗나간 뒤부터 남는 PSRAM 허가를 선행 읽기에 사용한다. 한 번의 물리 읽기로 두 bitplane을 가져온다. core 요청과 정규 타일 요청이 우선하며, 실제 출력 범위는 원래 plan과 독립 검사가 결정한다.

빈 캐시의 288B와 뒤이은 32B를 회복하려면 타일 주소와 행 마스크를 함께 봐야 했다. 세대 912는 같은 CHR 태그 0x196F를 처음에는 마스크 0x3F로, 다음에는 0xC0으로 사용했다. 중복 주소 읽기를 없앤 H에서는 464B까지 선행 전송했다. I에서는 검증된 OBJ의 앞 네 행이 모두 필요할 때 같은 불변 타일의 남은 행도 유휴 허가로 채운다. 후속 32B가 두 위상 모두 SEAL 전에 들어왔다.

STOP은 논리적 소유권과 행 유효 상태를 취소한다. 수락된 물리 요청은 응답까지 추적하며 폐기한 응답은 타일이나 ACK로 발행되지 않는다. 같은 generation으로 다시 시작해 CHR 내용을 바꾸는 시험, 잘못된 CRC·generation, core와의 충돌, full 형식의 희소 대체 행 및 backpressure를 시험했다. 65816의 잘못된 SEAL 거부와 업로드 중 STOP은 네 번째 확정 화면을 보존했다. ARM의 D0 SRAM 송신 네 곳, 최초 D1 검사와 D2 반환, 타이머 종료와 base·메뉴 반환을 같은 firmware 해시로 확인했다.

첫 구현 A는 13 LAB 초과였다. SPI 응답의 CRC와 주소 비교를 공용화하고 대체 CHR 태그를 RAM으로 옮겼다. E에서 드러난 host→NES setup −5.218ns는 bank와 길이를 수신 클록에서 받아 사용해 해소했다. I의 전체 hold / recovery / removal / minimum pulse slack은 각각 +0.159 / +1.326 / +0.293 / +2.630ns다. 수신 문맥 11비트의 개별 제약도 모두 통과했다. 전역 보고서의 미제약 입력·출력 수는 MMC907과 같다. ARM Flash 212,872 / 212,992B이며 FPGA RAM 블록은 모두 사용한다.

## 재현 범위

1. 906 보드 작업 디렉터리와 912 소비자 HEX, 913idle 최종 링크를 준비하고 `tools/prepare_nes_port914.py <temp> --revision I --fit`을 실행한다.
2. `tools/fixture_nes_port914.py`로 위상 1·2 각각 기존·빈 캐시 및 기존 캐시 `--lead-in`의 E9 바이트·E8 표본·ROM 허가 일정을 생성한다. 지역 게임 CHR는 지정된 해시를 확인한다.
3. Starter FLOAT 단일 좌석으로 `tools/check_nes_port914.ps1`을 실행한다. `NES_PORT914_VARIANT=I`가 최종 보드이며 `NES_PORT914_LEAD=1`은 910·911의 선행 구간이다. 원래 SPI와 새 SPI를 같은 핀 입력으로 대조하는 시험도 포함한다.
4. `tools/replay_nes_head914.py`의 `--rev I`로 네 CPU 재생을 실행한다. `tools/analyze_nes_port914.py`는 비교 구현들의 결과와 보호 시험을 함께 점검한다. [조건별 수치·해시·배치 결과](../analysis/port914-results.json)

ROM 허가에는 기존 509 경쟁 일정을 썼다. 타일 포트 RTL과 CPU의 연속 실행은 E9 수락·E8 조회·타일 반환 시각을 대조한 별도 재생이다. 실기 60초 FPS와 실제 카트리지의 최소 캡처 여유는 다음 보드 시험에서 확인해야 한다.
