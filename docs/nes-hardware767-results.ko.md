## 천장이 내려오는 방

사용자가 월드 1 레벨 1·2 이후 성의 두 번째 장면에서 같은 기믹이 동작할 때 양쪽이 튕겼다고 확인했다. 764·766의 PPU 스냅샷이 **64비트 전체에서 일치**한다(`51000a00 00220800`). 162선 dot 0, 렌더 중, sprite_fetch 0, PPUDATA 읽기 파이프라인 0x10, 쓰기 0, 주소 래치 0x82, 선행 hint 0이다. 두 판 모두 실제 FPGA가 sticky ROM 오류 2를 기록했다. RTL에서 이 값은 PPU가 ROM 바이트를 샘플링할 때 유효 데이터가 없는 조건이다.

**766**의 동결 문맥 `e201408104204082`에서 수락된 PPU 주소와 필요한 물리 주소는 모두 `0x204082`다. age 2, busy 1, ready/response/ppu_valid 모두 0이다. 이 순간 진행 중인 요청은 올바른 주소였고 마감까지 응답이 오지 않았다. 162선 dot 0에서는 일반 렌더 읽기가 억제되고 실제 읽기는 `read_2007_delayed[4]`로 성립한다. 707D의 readtail 예측은 dot>0·특정 pattern 주기에 한정된다. 705에서 재현한 193선 dot 230·주소 0x21E161과는 다른 경계다. 앞선 주소 결정·PSRAM 점유·허가·응답을 기록한 파형이 없으므로 어느 요청이 몇 클록을 지연했는지 또는 어느 클록에서 선행 발행이 안전했는지는 미확정이다.

**764**는 이전 65816 출력 상태를 ARM이 거부한 경로에서 먼저 빠졌다. window error 4는 상태 헤더·CRC 또는 오류 비트 검사에서 쓰인다. 남은 flags 0x83에 fault 비트가 있다. STOP 명령은 수락됐으나 observer 보존 대조는 error 3이었다. STOP 후 읽은 PPU 위치와 ROM 오류가 766과 일치해 같은 종류의 마감 실패라는 근거가 강하다. 764는 fault_context_valid=0이므로 정확한 물리 주소·reader age나 오류 순서까지 같았다고 판정하지 않는다. 두 실행 모두 failed_transfers 0, cost_crc_errors 0, plan_error 0이다. 순환 집계의 마지막 사용 bin에서 가장 긴 표시 간격은 300/290ms였고 이 간격에 특정 게임 이벤트를 대응시킬 타임스탬프는 없다.

A 60초판은 이전 MMC704 2회(18.69/19.87fps)보다 5–55초 전체 19.04→20.64fps였다. 5–40초 화면당 mapdirty는 10.90→9.67, OBJ는 31.53→75.44다. 40–55초는 mapdirty 9.18→10.53, OBJ 31.29→94.65다. 출력·최종 ACK 구간 평균은 32.26→26.53ms, 30.67→24.63ms였다. 각 실행의 작업량이 달라 707D만의 속도 개선으로 환산하지 않는다. 장시간 B는 A보다 첫 구간 111장을 더 표시했고 다음 구간은 1장 더 표시했다. 764·766은 작업량 bin이 420.13초/300.12초부터의 값으로 순환해 초반 작업량 대조가 불가능하다. 목표였던 같은 동선의 60초 A/B는 MMC767 대기다.

## MMC765의 부팅과 다음 시험

직전 765 설치본은 60초 타이머를 부팅과 플레이가 공유하는 `native_service165`에 넣었다. `native_boot172`가 이를 먼저 호출한 뒤 `native_frames222 → nes_runtime165_begin`에서 시작 tick을 초기화한다. 초기 BSS에서 started=0이면 MCU 가동 시간이 6,000 tick 이상인 첫 부팅 poll에서 타이머가 만료된다. 직전 검증은 RUN 진입 뒤와 정상 값을 주입한 메뉴 경로를 검사해 이 조합을 놓쳤다.

배포한 765 ELF로 부팅 함수와 서비스·오류 분류를 실행했다. 정상 GPIO·준비 응답을 제공해도 5,999 tick에는 통과하고 6,000·25,000·0xFFFFFFF0에서 첫 서비스가 거부된다. 세 실패 로그와 같은 poll 1/ticks 0/first=last=0이 나왔다. 실기 세 번 모두 로더 진입부터 DISPLAY_NEXT까지 이미 231.78–233.79초가 지나 60초를 넘었다. 현물의 절대 tick은 로그에 없다. 767은 기존 RUN receiver 소유권이 생겼을 때만 타이머를 적용한다. 초기 부팅, 시작 시각 wrap, 60초 deadline과 실제 하드웨어 고장 우선권, 종료 시 포인터 해제·최종 ACK·메뉴/base 복구를 연결 바이너리로 검사했다. 765의 실기 실패 원인을 가리는 재시도나 타임아웃 연장은 추가하지 않았다.

다음 실기에서는 767만 기존 763 2회차와 같은 동선으로 비교한다. 766 장시간판은 그대로 제공한다. 중간 성은 162선 dot 0의 PPUDATA 읽기와 직전 주사선 말의 실제 주소·CHR bank, 첫 요청 수락·PSRAM 응답을 재현하는 별도 과제로 둔다. 화면 속도 판단과 마감 오류 재현을 독립적으로 진행한다. [설치 안내](nes-mmc767-trial.ko.md)

MMC767 전체 링크는 Flash 212,972/212,992B다. 두 시작 위상에서 각각 905–957의 53개 RGB·map·기대 바이트가 기준과 일치했다. 952–957은 모두 3 VBlank, 951 공개는 236선, 952·957의 1,536B map 단일 DMA와 957 최종 대기 0회를 확인했다. 밀집 표시 간격은 49.916/49.912ms다. 이 수치는 고정 캡처의 연결 시뮬레이션 결과이며 MMC767 실기 FPS는 다음 시험에서 확인한다.
