# MMC516의 section 5 소비와 최종 VBlank 재사용

MMC509에서 오래 걸리는 HDMA·raw 데이터 소비와, SEAL 검사가 끝난 뒤 새 VBlank를 기다리는 시간을 분리했다. 65816 변경 두 가지를 함께 적용하자 SMB3 905~916의 **첫 두 화면 이후 평균 표시 간격이 두 시작 위상에서 각각 93.110→83.262ms, 93.109→83.261ms**로 줄었다. MMC516은 실기 비교용으로 전달한다. 확인한 실기 기준은 MMC509의 12.82fps다. [측정 JSON](../analysis/window516-verification.json) · [실기 시험 방법](nes-mmc516-trial.ko.md)

## 어디에서 시간이 소요됐나

동일한 linked MMC509 ARM과 실제 65816을 실행해 패킷 수신, ACK, SEAL 검사, 첫 PPU DMA, 최종 표시 시각을 한 master clock 기준으로 기록했다. 기본 위상에서 마지막 section 5 ACK→SEAL 패킷 읽기까지 1.105~1.293ms, SEAL 패킷 읽기→검증이 끝난 업로더 입구까지 2.318~2.403ms였다. 둘을 합한 후반 평균은 3.586ms다. section 5 자체의 패킷 읽기→소비 ACK는 평균 11.324ms였고 그중 긴 반복 패킷(op5)이 6.697ms였다. 두 측정 구간은 인접하지만 시작점과 완료 조건이 다르다.

검증된 업로드 목록의 첫 VRAM DMA는 후반에 225~226행에서 시작했다. 팔레트·OAM·표시를 위해 추가로 새 VBlank를 기다린 화면은 기본 위상에서 909·910·912·913·914·915·916이었다. 각각 252·249·250·248·254·256·246행에 대기를 호출했다. 새 VBlank에서 복귀한 뒤 최종 ACK까지 15,900~16,050클록이 걸렸다. 현재 VBlank 안에 있더라도 늦은 행에서는 그만큼의 시간이 남지 않는다. [측정기](../tools/test_nes_window516.py)

## 두 변경

- **section 5의 긴 0 채우기**. op5의 길이·섹션·범위 검사를 통과하고 실제 인코딩 워드의 두 바이트가 모두 0일 때만, 검사된 WRAM 주소로 고정 소스 DMA를 실행한다. 한 번에 최대 64B이며 각 전송 전과 마지막 ACK 전에 STOP과 입력을 확인한다. 0이 아닌 워드는 기존 복원기로 처리한다. 과거 491의 범용 반복 워드·MVN 경로와 구분해 이 한 경우의 비용을 MMC509에서 직접 비교했다.
- **최종 표시 대기**. 기존 예산으로 같은 VBlank에 표시할 수 있는 경로는 그대로 둔다. 예산이 부족한 경우에만 실제 VBlank 상태, 새 H/V latch의 유효성과 9비트 수직 카운터를 확인한다. 화면이 이미 표시 중이고 225~246행을 읽었을 때만 팔레트 512B, OAM 544B, 표시 레지스터 변경과 최종 ACK를 이어서 실행한다. STOP을 다시 확인하고 늦거나 불확실한 표본은 기존의 serviced wait로 보낸다. 새 예산을 앞선 tile·map·raw DMA에 부여하지 않는다. [구현](../tools/nes_window516.py) · [Nintendo SNES Development Manual](https://floating.muncher.se/bot/manual/book1_text.pdf)

## 같은 일정에서 비교

ARM CPI 2, 동일 SPI 드라이버·IRQ 비용, ROM 허용 캘린더(stride 48, phase 0), 일반 큐 4개·bulk 슬롯 2개를 사용했다. 평균은 906의 최종 ACK부터 916까지 열 구간이다. 기본 시각은 3,000,000 master clocks, 두 번째 시각은 178,684클록(약 8.32ms) 늦췄다. 원본 두 실행은 저장된 모든 최종 ACK 시각과 SPI 전송량을 재현했다.

| 후반 지표 | MMC509 | 최종 대기만 | 0 채우기만 | 결합 MMC516 |
|---|---:|---:|---:|---:|
| 기본 시각의 평균 간격 (ms) | 93.110 | 91.581 | 84.790 | **83.262** |
| 두 번째 시각의 평균 간격 (ms) | 93.109 | 91.582 | 84.787 | **83.261** |
| 기본 시각의 section 5 소비 평균 (ms) | 11.324 | 11.324 | 6.176 | 6.178 |
| 기본 시각의 마지막 section 5 ACK→검증 완료 평균 (ms) | 3.586 | 3.576 | 3.604 | 3.604 |
| 기본 시각의 12화면 전체 SPI (B) | 141,259 | 140,143 | 135,327 | 134,227 |
| SysTick / ROM 읽기 배정 | 140 / 3,280 | 138 / 3,280 | 131 / 3,280 | 130 / 3,280 |
| 65816 본체 (B, 4,960B 가용) | 4,311 | 4,387 | 4,414 | 4,490 |

후반 op5 패킷 10개에서 11,000B를 WRAM에 채웠다. 결합의 op5 소비는 평균 1.522ms였다. 최종 VBlank 재사용은 각 위상에서 916번 한 번으로, 10개 간격 전체에서 약 15.3ms를 절감했다. 0 채우기의 이득은 907·908·910·913·916에 걸쳐 나타났다. 결합의 기본 위상 후반 범위는 66.535~99.841ms다. 전송 내용과 출력은 같고, 빨라진 소비에 따라 상태 조회와 IRQ 횟수가 달라졌다. 60fps 목표인 16.67ms까지는 기본 위상 평균으로 약 66.6ms가 더 필요하다.

## 경계와 비용

- 시작 위상 2개 × 구성 4개 모두 12개 VBlank 최종 ACK·EA, RGB, 각 대상 WRAM·VRAM map 4,096B가 일치했다. 독립 검사와 기존 패킷 순서·내용, VRAM DMA 36,144B를 확인했다. SPI·IRQ·ROM 중재는 모델이며 이 결과가 실기의 FPS 측정값은 아니다.
- 진입 시각만 조정하는 진단 ROM에서 실제 PPU의 224·225·246·247·256행, 유효하지 않은 latch, 검사 중 STOP, 잘못된 SEAL을 시험했다. 두 뱅크 모두 246행 후반에 진입시킨 경우 247행에서 재사용을 결정해 259행에 최종 ACK를 썼다. 247행과 256행의 표본은 새 VBlank로 넘어갔다. 새 표시 전 취소와 잘못된 SEAL은 이전 표시 serial·RGB를 보존했다. 이는 시험한 NTSC 경로의 경계 측정이다. [경계 시험](../tools/test_nes_window516_edges.py)
- 실제 결합 ROM에서 64B 직후 STOP, 마지막 꼬리 직후 STOP, 242B·258B 길이, 반복 워드의 첫째·둘째 바이트만 0이 아닌 경우, 홀수·범위 초과 길이를 검사했다. 중단된 패킷은 완료 ACK를 공개하지 않았고, 완료 전 쓰기 범위와 이전 표시가 일치했다. 두 정상 꼬리 길이의 시험은 검사한 패킷의 ACK 뒤 의도적으로 다음 순서를 틀리게 해 종료했다. [채우기 시험](../tools/test_nes_window516_fill.py)
- 세 변경 ROM을 각각 Quartus Lite 25.1 EP4CE15F17C8 전체 보드에서 배치했다. 세 경우 모두 원본과 같은 15,164 LE, 14,172 조합 함수, 8,394 FF, 264,816 RAM bits, 51 M9K였다. 기존 SDC의 관련 setup +0.078ns, hold +0.139ns다. 새 WRAM 할당은 없고 결합은 기존 임시 변수 두 워드를 재사용한다. ARM Flash 사용은 212,956B, 잔여 36B다.

## 실기 인계

두 위상에서 후반 총 시간이 줄고 경계·복구·전체 보드 검사를 통과한 결합안을 선택했다. 전달용 ARM은 기존 ARM의 784개 함수 주소·크기·명령이 같고 메뉴·ROM·FPGA·로그 이름만 바뀌었다. 입력 이미지 헤더 CRC, 40개 진행 응답 비교, base 복구와 네 오류의 안전 반환 차단을 확인했다. 선택한 보드 SOF를 RBF·BI3로 변환해 역변환 일치와 ZIP 재개봉을 검사했다. MMC516의 실제 부팅, 화면·입력·메뉴 복귀와 성능은 사용자가 보드에서 확인할 항목이다. [전달본 명세](../analysis/window516-package.json)

재현에는 [기존 빌드 입력](../cores/nes/REPRODUCING.ko.md)과 MMC509 ARM03·489 client03, 513 capture04를 사용한다. `nes_window516.py --mode gate|fill|both`로 client를 생성한다. `test_nes_window516.py`를 두 시작 시각에서 실행하고, 전체 보드에는 507 입력 중 sink-program.hex만 바꿔 compile·timing506.tcl을 실행한다. [분석기](../tools/analyze_nes_window516.py)에서 비교하며 [전달 도구](../tools/package_nes_window516.py)로 제한 시험본을 만든다.

로컬 전달본은 `probes/nes-window516/trial02/MMC516-TRIAL.zip`이다. 원본 실행 기록·CLK trace·전체 배치 보고서·경계 및 복구 시험에서 선택한 63개 자료는 `probes/nes-window516/selected-evidence.zip`에 보관했다. 보관본 SHA-256은 `acf642f9212d0fec2e42477c86481325d9bb9699af7c4e3c10565a7ed8ab9edc`이다.
