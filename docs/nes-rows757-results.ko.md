# 757 · 957의 마지막 페이지를 언제 발행할 수 있는가

## 목표

753의 957에서 오른쪽 페이지 여덟 범위가 각각 완성되는 시점에 발행해 첫 VBlank 248선 안에 마지막 map을 반환할 수 있는지 검사했다. 표시 2 VBlank, 952·957의 SEAL 전 1,536B 단일 DMA, 같은 blank의 BG→map→OBJ 순서, 749 E8·OBJ 마감, 밀집 표시 간격과 957 최종 ACK를 함께 판정했다.

## 작업내용

- 원본 ARM과 751 sharedfast 정적 65816 ROM을 리셋부터 다시 실행했다. 957에서 ARM의 map 실제 쓰기 주소·쓰기 전후 값, resident의 BG slot 사용 비트가 처음 설정되는 시각을 기록했다. 최종 map에 기록된 각 가시 셀이 해당 세대에 확보한 slot을 참조하는지 확인했다. 192B마다 가시 셀 57개를 쓰고 나머지 39개 셀은 이전 값을 유지했다. slot 확정은 ARM 할당기의 소유권 취득이며, 해당 CHR의 ROM 읽기나 VRAM DMA 완료는 이후 별도 이벤트다.
- 3행·6행·24행 단위로 ARM 발행 기회를 추가했다. 한 compact group은 왼쪽의 한 행과 오른쪽의 한 행만 수정한다. 따라서 group의 마지막 store와 행 완료 콜백이 끝나면 이전 세 행의 192B는 고정된다. warm 이력·tile 계획이 있는 경우에만 대상 뱅크의 stale 및 현재 dirty 마스크를 확인하고 세 행 모두 필요할 때 기존 패킷 형식으로 보낸다. 4슬롯 큐의 실제 credit을 확인한 뒤 기존 tile 우선권 확인을 통과해야 한다. 24행 후보도 여덟 패킷을 하나의 거래로 예약하지 않는다. 호출 시 이미 확정된 범위들을 순서대로 시도하고 새 head·tile 우선권 또는 credit에서 멈춘다. 성공적으로 enqueue한 범위만 8비트 마스크에 기록하고, 공통 map 커서가 나중에 같은 범위를 중복 전송하지 않도록 했다.
- 905–957의 map·RGB 53장씩, 독립 재구성한 map 커버리지와 나머지 packet·tile 작업량을 같은 위상의 753과 대조했다. ARM은 전체 링크 명령 실행(CPI 2), MCU 드라이버는 실측 보정, ROM은 고정 경쟁 달력, 65816은 Mesen의 CPU·PPU·DMA 시각을 사용했다. 시작 클록은 7,288,416과 7,467,100이다. FPGA와 65816 바이너리는 기존 것을 사용했다.

위 표는 **753 원본**의 ms이며 각 셀은 위상 1 / 2다. 0은 956 공개 다음 첫 VBlank에서 248선이 끝나는 시각(경계 오차 최대 4 master clock)이다. 마지막 쓰기와 마지막 값 변경은 이 여덟 구간에서 일치했다. credit 열은 원래 FIFO 순서를 기준으로 해당 E1에 슬롯이 생겼음을 ARM이 처음 관측한 시각이다. 반환 열은 65816이 해당 패킷을 실제로 소비하고 ACK한 시각이다. 이 두 시각과 해당 ACK를 ARM이 나중에 E0로 관측한 시각은 원시 결과에 분리했다.

가장 빡빡한 구간은 **offset 3,200에서 시작하는 마지막 두 패킷**이었다. 실제 값 변경이 끝나자마자 보낸다고 놓고 credit·CPU·다른 SPI·드라이버 비용을 전부 0으로 잡아도, 211B 두 번을 2.625MHz로 보내는 데 1.286ms가 필요하다. 두 위상에서 마지막 E1 바이트만으로도 248선을 0.059 / 0.327ms 넘는다. 753에서 측정한 E1별 드라이버 시간까지 넣으면 +0.159 / +0.427ms, 관측한 65816 서비스 시간을 겹쳐 재생하면 마지막 반환은 +0.740 / +1.008ms다. 이 계산은 753의 범위별 생산 시각·211B 패킷 형식·순서를 고정했다. offset 3,200의 첫 쓰기부터 마지막 쓰기까지는 0.920ms이며 그 안에 tile E8 20B와 E9 22B가 각각 한 번 있었다. 그 비용은 두 범위의 전송 예산과 따로 기록했다.

### 안전과 비용

실제 링크의 ARM에서 STOP·CRC·오류 credit·잘못된 최종 ACK와 메뉴 복귀 함수 경로를 시험했다. 새 helper는 tile 우선권, 부족한 credit, enqueue 실패 시 미발행 상태, 불완전 3행, 중복 금지를 별도로 검증했다. 3행 후보의 두 위상에서 957의 576B 실제 DMA 직전 STOP과 수행 중 STOP, 새 head 우선, 오래된 표시 identity를 재생했다. 중단·손상 시 52개 커밋과 956 화면을 보존했고, 새 head 주입은 DMA보다 head를 먼저 처리해 53개 커밋과 최종 ACK로 끝났다. Flash 상한은 212,992B다. 실기 구동과 새로운 Quartus FIT는 이번 측정에 포함하지 않았다.

## 후속작업

753을 유지한다. 다음 비교 대상은 3,200·3,392 두 범위의 **생산 마감과 소비 검사 비용**이다. 3,200 범위 안의 tile E8·E9 마감과 BANK 소유권을 고정하고 map의 slot 탐색·행 쓰기 중 얼마를 앞당길 수 있는지 확인한다. 0.059 / 0.327ms는 순수 wire만 남긴 부족분이므로 실제 후보는 credit, 65816 검사와 반환도 포함해 첫 248선을 통과해야 한다. 수락된 앞부분을 65816이 먼저 DMA해 1,536B가 나뉘는 비용도 함께 검증한다.

## 재현

1. `tools/prepare_nes_rows757.py <753 prefix의 src> <새 overlay> row|pair|page` 후 `tools/build_nes_mmc479_arm.ps1`로 전체 ARM을 링크한다. 이전 stage의 경로는 [756 검증](nes-window756-results.ko.md)에 있다.
2. `tools/run_nes_rows757.ps1 -Variant control|row|pair|page -Phase 1|2 -Game <ROM>`을 각각 실행한다. 모든 출력을 같은 trace root에 둔다.
3. `tools/check_nes_rows757.py <ARM src> <mode> <probe>/guards-<mode>.json`을 실행한다. 두 row trace에 `tools/check_nes_static751.py --source 22528 --size 576`의 before·during·head·stale를 각각 적용하고 결과 폴더를 `nes-rows757-row<위상>-<fault>`로 둔다.
4. `tools/analyze_nes_rows757.py --temp <trace-root> --probe ../probes/nes-rows757 --out analysis/rows757-verification.json`으로 원시 이벤트·해시와 표 수치를 재검산한다.
