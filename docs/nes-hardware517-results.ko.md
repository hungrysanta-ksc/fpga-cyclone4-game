# MMC516 실기 결과와 복잡한 화면의 지연

사용자는 실행과 메뉴 복귀가 정상이었고, 이전보다 부드럽게 느껴져 더 진행할 수 있었다고 보고했다. 적이 많이 움직이는 장면에서는 느려짐을 느꼈다. 이번 SMB3 실기 로그는 **60.07초에 최종 표시 660회, 평균 10.99fps**다. MMC509는 60.08초에 770회, 12.82fps였다. 같은 동선의 쌍대 시험이 아니므로 관측 평균의 −14.27%를 변경 자체의 성능 회귀율로 해석할 수 없다. 516 모델의 약 93.11→83.26ms는 동일 입력에서의 비교이고, 실기 로그의 평균은 서로 다른 플레이를 포함한다. ## 45~50초의 변화

ARM 동작 시작 기준 5초 구간 중 가장 적게 표시한 구간은 45~50초다. 카운터는 프레임 작업을 시작한 구간에 귀속되므로 표시율은 구간 근사치다. 전체 평균의 단계 시간은 84MHz DWT로, 구간 평균은 10ms tick 누적값을 해당 구간의 표시 수로 나눠 계산했다.

| MMC516 실기 | 5~10초 | 45~50초 | 50~55초 |
|---|---:|---:|---:|
| 표시 수 / 근사 표시율 | 81 / 16.2fps | **30 / 6.0fps** | 56 / 11.2fps |
| 수신 (ms/표시) | 19.75 | 21.67 | 19.46 |
| 계획·공급 (ms/표시) | 12.84 | **45.00** | 14.46 |
| 그중 END 추가·flush (ms/표시) | 0.62 | **25.00** | 1.61 |
| 출력·최종 ACK (ms/표시) | 29.51 | **100.33** | 53.75 |

45~50초에는 계획 932건·29,344B가 수락됐다. ARM은 성공한 tile-plan 공급마다 OBJ용 kind 1에 32B, 나머지에 16B를 기록한다. 따라서 OBJ 계획은 `(29,344 − 16×932)/16 = 902`건으로 **표시당 30.07건**이다. 5~10초에는 표시당 1.31건이었다. E8 상태 조회도 표시당 22.0회에서 249.8회로 늘었다. 45~50초에 관측한 최대 표시 간격은 330ms였고, 실행 전체에서 가장 큰 380ms는 첫 구간에 있었다. OBJ 계획 수는 적 개수나 모든 OAM 엔트리 수가 아니다. END 시간은 계획·공급에 포함되며 E8은 여러 진행 상태를 조회하므로 독립적인 ROM 대기 시간으로 더하지 않는다.

새 타일 공급이 많은 구간에서 계획 완료와 출력 경로가 함께 늦어진 것은 확인된다. 현재 로그에는 프레임별 적 수·게임 상태, 표시 시각과 연결된 영상, NES 논리 업데이트 횟수, ROM 대기·DMA·VBlank의 개별 시간이 없다. 따라서 이 구간을 사용자가 본 특정 적 장면으로 단정하거나 원작의 게임 로직 지연과 포트의 표시 지연 비율을 분리할 수 없다.

## 실행 종료와 복구

384KiB 적재·readback 검증, START·STOP, base 복원·메뉴 준비가 기록됐고, 사용자가 메뉴를 확인했다. CRC·전송 실패·receiver/video/ROM 오류는 0이다. 마지막 표시가 59.98초에 확정된 뒤 입력 commit 하나가 더 있었으나 661번째 요청은 다음 화면의 BEGIN으로 완료 ACK가 없었다. 소프트웨어 sent와 retired는 모두 18,404였다. 전달 ARM ELF에 이전 표시를 유지하고 deadline을 주입한 BEGIN 시험에서 새 E1 없이 runtime/window/sink 1/2/2가 재현됐다. 정상 대조군은 BEGIN을 수락했다. 종료 직전 상태를 대상으로 한 주입 시험이며, 45~50초의 저하를 이 마지막 오류로 설명하지 않는다. 보존된 capture 이력은 거부 2·회복 2이고 해당 fetch 오류는 0이다. 이는 전체 실행의 캡처 누락률을 제공하지 않는다. ## 다음 비교

MMC516은 실기 실행과 복귀가 확인된 버전으로 기록하고 MMC509를 비교 기준으로 보존한다. 우선 동일한 첫 레벨 구간·비슷한 입력에서 OBJ 작업이 몰리는 프레임을 식별한다. 같은 입력의 NES 참조 실행에서 게임 상태가 실제로 진행한 시점과, 포트에서의 프레임별 OBJ 계획 수·END 대기·마지막 tile 공급·SEAL 준비·표시 ACK를 비교한다. 이를 통해 게임 로직 자체의 지연, tile 공급 병목, VBlank를 놓친 표시를 구분한다. ROM이나 일반 map 전송을 다시 바꾸기 전에 이 경계부터 검증한다.
