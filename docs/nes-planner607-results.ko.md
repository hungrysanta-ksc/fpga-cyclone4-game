# 607 · 첫 BG 발행 전에 반복하던 슬롯 조회

954에서 604 ARM의 마지막 D0 응답을 받은 뒤 파서가 성공을 반환하는 명령부터 첫 E9 완료까지 추적했다. 606과 같은 바이너리·SPI 거래·시각을 재현했다. 전송 밖에서 321,122개 명령을 실행했고, 84 MHz·CPI 2 모델에서 7.646 ms다. SPI와 드라이버는 별도로 0.509 ms다. 이 수치는 보드의 사이클 카운터 측정값과 구분한다.

## 어느 작업을 먼저 할 수 있었나

- map 수신 중 확정되는 것은 물리 tag의 동일성이다. 954의 여섯 번째 POP까지 받은 594칸 중 452칸이 두 칸 앞과 같은 tag였다. 그 시점에 행·raster·예외 목록은 아직 완성되지 않았다.
- 목적지 슬롯과 팔레트는 확정된 행 그룹과 표시 뱅크 이력에 의존한다. 앞의 ACK 전에는 대상 뱅크에 쓰지 않는다. COMMIT 뒤 같은 그룹에서 두 칸 앞의 tag가 같고 그룹에 예외가 없으면, 앞의 검사를 통과한 슬롯을 재사용할 수 있다. 이 슬롯은 해당 계획이 끝날 때까지 퇴거할 수 없다. 팔레트 비트는 현재 셀에서 읽고, 쓰기와 dirty 처리는 원래 경로를 거친다.
- 그룹 경계에서 슬롯 이력을 버리고 처음 두 칸·서로 다른 tag·예외 그룹은 전체 검사를 거친다. 선행 발행 시점, 최종 표시 ACK에 의한 이력 발행, STOP 때의 이력 소유권은 기존 규칙을 따른다.

단위는 ms다. 952의 55개, 954의 58개 E1·E9·EA 전체 거래와 순서, 최종 video 구조체와 수신 geometry·raw가 모두 일치했다. 거래 총량도 각각 8,115 B와 8,349 B로 같았다. 132 B 반복 표를 추가하면 구조체 정렬을 포함해 receiver가 9,880→10,016 B로 커졌다. 604 계열에서 전체 Flash는 대조군이 112 B, 직접 재사용이 224 B, 반복 표가 284 B 초과했다.

606의 954 여섯 블록 선행 수신 가정에 직접 재사용을 대입하면 이전 EA 뒤 첫 E9가 16.852→13.212 ms다. 이후 현재 필수 출력 wire만 더해도 SEAL까지 **25.808 ms**가 걸려 두 위상의 표시 기한 15.910 / 15.941 ms를 넘는다. 입력 전부를 숨기고 bulk 묶음과 별도 8 B map 형식까지 합친 12.522 ms는 실제 채택 일정에 포함하지 않는다.

## MMC577에 옮긴 비용과 검사

대조용 ARM558에 같은 map 재읽기 코드를 붙인 전체 이미지는 213,020 B다. MMC577에서 최근 슬롯 두 개를 배열에 둔 형태는 213,000 B, 두 스칼라를 순서대로 넘기는 형태는 **212,976 B**였다. 마지막 형태는 원본보다 68 B 크고 Flash 16 B가 남는다. 정적 BSS 18,592 B와 data 10,040 B는 같다. FPGA와 65816 바이너리는 원본을 사용한다. 기존 Quartus Lite 전체 비용은 15,260 LE·51 M9K다. 이번 ARM 변경에 해당하는 새 합성 결과는 없다.

MMC577 원본과 두 스칼라 후보에 동일한 실제 수신 패킷을 제공했다. page 경계 31/63, 현재 셀별 다른 팔레트, 일반 열과 열 0의 예외를 넣은 네 경우에 출력 plan과 receiver·video·resident 전체 상태가 일치했다. 별도로 잘못된 CRC의 POP 차단, 6 POP 뒤 ABORT·늦은 COMMIT 거부·cold 재수신, 잘못된 표시 ACK의 EA 차단, EA 시점 STOP을 확인했다. 메뉴·base 복구는 실제 ARM 함수와 모델 IO로 정상 및 실패 분기를 검사했다.

## 두 시작 위상의 실제 ARM·65816 연속 실행

같은 53개 입력·시작 클록·driver 평균·SysTick·두 bulk 뱅크·주기 ROM 허가표에서, 561의 기준 실행과 MMC577의 두 스칼라 후보를 비교했다. 580 manifest가 고정한 561 기준은 MMC577의 동등 경로다. 각 위상에서 WRAM/VRAM map, 최종 표시 RGB 53개, 소비된 tile, DMA 114,352 B 및 ROM 읽기 5,616회가 일치했다. 실기 메뉴 복귀는 MMC577에서 확인된 상태이며 이 후보의 종단 시각은 시뮬레이션 결과다.

|---|---:|---:|
| 951–955 평균 표시 간격 | 83.157 → 79.775 ms | 83.121 → 79.780 ms |

시간의 양수는 단축, 바이트의 양수는 증가다. E1·E9 payload 형식과 독립 검사는 그대로다. 952·954에서 요구한 47 / 120 B 추가 절감과 표시 전 버스 완료 약 10 ms 단축은 달성하지 못했다. 952·954 최종 대기 0회와 VBlank 중 공개는 유지했다. 957에서 더 이른 SEAL이 어느 DMA를 선행 경로에서 최종 경로로 옮겼는지는 이 결과만으로 단정하지 않는다.

**다음 판정**은 두 스칼라 후보를 대조군으로 삼아 952·954에서 늘어난 E8의 응답별 상태 변화와 첫 유효 ROM 허가를 한 타임라인에 놓는 것이다. 준비·credit·STOP이 처음 바뀌는 응답을 지키며 중복 조회를 없애 실제 거래량과 마지막 payload 시각을 함께 줄일 수 있는지 확인한다. 957의 마지막 선행 DMA·SEAL·검사선·표시를 같은 실행에서 대조해 최종 대기 0회를 복구해야 한다. MMC577을 실기 기준으로 유지한다.

## 재현

1. 580 manifest의 ARM558·MMC577 프로젝트, 604에서 고정한 ARM·warm 이력·입력 보드·delta231/test07을 사용한다. 각 생성기의 첫 동작이 원본 firmware 해시 대조다. `prepare_nes_planner607.py BASE OUT direct|prefix`로 604 두 후보를 만들고 각각 `build_nes_trial577.ps1`로 링크한다. 같은 FLOAT 래퍼에서 `trace_nes_planner607.py`, 이어서 `check_nes_planner607.py`를 실행한다.
2. `--baseline 558`과 `direct`로 연속 일정용 직접 재사용 대조 후보를 만든다. `--baseline 577`에는 각각 `slots`, `recent`를 지정한다. 두 경우 모두 같은 전체 링크를 사용한다. `recent`의 원본은 실기에 전달한 MMC577이다. `guard_nes_planner607.py`로 경계·ACK·취소를 확인한다. `--corpus`는 905–975의 원본 geometry·raw를 MMC577 형식으로 패킷화한다. 예전 478 생성기는 BEGIN 버전 0x2232이며 MMC577은 0x2233을 요구한다.
3. 561 연속 실행 방법에 따라 `test_nes_close561.py --keep-run`을 각 바이너리에 대해 시작 클록 3000000과 3178684로 실행한다. fixture는 grant555, plans와 capture는 output489/audit01, client는 admit556/client01, ROM은 service509/rom03, 드라이버는 hardware503-mmc502이다. `budget_nes_planner607.py`가 원본 561 파일 해시와 53회의 표시·DMA·RGB 및 마지막 ACK를 대조한다. 여기서 원본 입력 ABI를 사용하므로 604의 압축 이득과 합산하지 않는다.
