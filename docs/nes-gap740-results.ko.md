# 740 · 마지막 map 반환 전 OBJ 조회와 빈 큐 DMA

**727을 유지한다.** 957의 마지막 map을 전송한 뒤 소비 ACK를 기다리는 동안 OBJ descriptor를 조회하면, 두 위상 모두 246선 안에 OBJ·OAM 처리를 마치고 952·957의 1,536B map을 SEAL 전에 DMA할 수 있었다. 다만 727이 같은 VBlank에 처리했던 BG 48B가 최종 업로드로 넘어갔다. 가장 일찍 후속 패킷을 재개한 경우에도 957 마지막 ACK는 0.050 / 0.064ms 늦었다. [시각·DMA 주소·검사 기록](../analysis/gap740-verification.json)

## 먼저 조회하고 실제 반환을 확인한 비용

두 위상에서 727의 연속 map 8개를 원래 master clock에 고정했다. 956 공개부터 센 시각을 아래에 표시했다. 조회만 먼저 시작하고, 실제 E0에서 마지막 map의 sequence·표시 identity·CRC·빈 큐를 확인한 다음 기존 D0 입력 서비스 한 번과 OBJ 발행 비용을 포함했다. OBJ 데이터와 OAM 재사용 명령은 727과 같은 바이트다.

| 957 사건 | 위상 1 | 위상 2 |
| --- | ---: | ---: |
| OBJ 조회 시작 | 31.181ms | 31.246ms |
| 직전 map의 실제 소비 ACK | 31.531ms | 31.631ms |
| OBJ 명령을 65816이 수락 | 32.050ms | 32.149ms |
| OAM 독립 검사 통과 | 33.108ms | 33.205ms |
| OAM ACK 후 246선 끝까지 남은 시간 | 0.414ms | 0.324ms |
| 빈 큐에서 1,536B DMA 시작 → 마지막 PPU 쓰기 | 33.892 → 34.482ms | 33.986 → 34.576ms |

같은 조건에서 **조회를 map ACK 뒤까지 미룬 뒤 OBJ와 OAM을 연속 발행**하면 두 위상 모두 OAM ACK는 246선을 지켰지만 957의 1,536B 선행 DMA를 잃었다. OBJ만 옮기고 OAM 발행 시각을 그대로 둔 대조군은 두 위상 모두 OAM 검사 마감을 넘겼다. 조회를 앞당기는 구간과 실제 수락을 허용하는 구간을 분리해야 했다.

## 후속 전송과 마지막 ACK

아래 두 값은 위상 1 / 위상 2 순서다. 밀집 표시 간격은 951 공개부터 957 공개까지 여섯 간격의 평균이다. 양의 ACK 차이는 727보다 늦은 결과다.

| 시험 | 952·957 선행 DMA | 밀집 표시 간격 | 957 마지막 ACK 차이 |
| --- | --- | ---: | ---: |
| 727 | 둘 다 유지 | 49.932 / 49.932ms | 기준 |
| map ACK 후 OBJ·OAM | 952만 유지 | 49.972 / 50.055ms | +0.239 / +0.734ms |
| 조회 선행·실제 map 반환 확인, 후속 시각 고정 | 둘 다 유지 | 49.943 / 49.943ms | +0.066 / +0.064ms |
| 위 조건에 첫 map DMA 완료 직후 후속 전송 재개 | 둘 다 유지 | 49.941 / 49.943ms | +0.050 / +0.064ms |
| 두 번째 map DMA 완료 뒤 재개 | 둘 다 유지 | 49.942 / 49.943ms | +0.060 / +0.064ms |

첫 완료는 384B, 두 번째 완료는 1,536B의 실제 65816 `$601D` 쓰기다. 각 쓰기 뒤 E0 조회·ARM 처리·E8 및 첫 scroll E1 비용을 부과하고, 이후 section 5 패킷과 SEAL 사이 간격을 727에서 가져왔다. 첫 완료를 사용하면 후속 패킷은 1.107 / 0.829ms, SEAL 수락은 0.968 / 0.633ms 앞당겨졌다. 그래도 SEAL 수락 시각은 직전 246선 끝보다 5.352 / 5.446ms 늦어 957 표시는 그대로 3 VBlank였다. 두 번째 완료만 고르는 실험은 비교용이다. 기존 E0의 진행 비트는 연속된 두 쓰기의 횟수를 구분하지 못한다.

727은 384B map, **BG 48B**, 1,536B map 순서로 선행 DMA했다. 첫 완료로 후속 전송을 재개한 후보에서는 위상별로 243 / 244선에 384B map, 249 / 251선에 1,536B map DMA가 시작됐다. BG의 WRAM source `$0840` 48B는 다음 VBlank에서 OBJ 288B보다 먼저 실행됐다. 실제 최종 업로드는 5건에서 6건으로 늘었다. 최종 표시 직전 별도 VBlank 대기는 두 위상 모두 0회였다.

## 검사와 범위

- 원래 727의 ARM·SPI 기록으로 producer 일정을 구성하고 실제 694 65816을 Mesen에서 실행했다. 6가지 일정 각각 두 위상에서 전체 53개 커밋·RGB, 956까지의 CPU 이벤트와 시각, 957의 패킷 순서·토큰·payload·독립 검사를 대조했다. 957에서만 선택한 발행 시각을 바꿨다. 새 ARM 바이너리나 실제 보드의 처리 시간으로 해석하지 않는다.
- 선행 조회 및 첫 완료 재개 일정에서 유지형 STOP과 오래된 OAM 표시 이력을 각각 주입했다. STOP에서는 두 뱅크 이력을 무효화했고, 오래된 이력은 0xE0으로 거부했다. 네 경우 모두 956 픽셀과 52개 커밋을 유지하고 957 최종 ACK를 막았다. 727 정상·장시간 ARM에서 메뉴/base 복귀 5경로와 파일명 4조건도 각각 다시 실행했다.
- CPU·SPI·FPGA의 실행 파일은 바꾸지 않았다. 707D의 FIT·STA와 727 Flash/RAM 근거를 승계한다. 이번 검증은 실기 FPS와 별개다.

## 다음 작업과 재현

다음에는 384B map DMA가 끝난 뒤 65816이 이미 수락한 BG 48B를 고를 수 있는 빔 시각과, 그 뒤 1,536B 전체가 VBlank 안에 끝나는 가장 늦은 시작 시각을 맞춘다. BG 48B를 회복하면 727과 최종 전송량이 같아진다. 727보다 앞서려면 최종 OBJ 288B 또는 그 일부까지 선행시킬 수 있는지도 따로 확인해야 한다. 목표는 두 위상의 실제 화면 간격과 마지막 ACK가 모두 줄어드는 것이다.

1. [739의 고정 727 입력과 Mesen·694 client](nes-owner739-results.ko.md)를 준비한다. Lua 출력 경로에는 ASCII 임시 경로를 사용한다.
2. `tools/replay_nes_gap740.py --phase N --policy P --trace <temp>/nes-pair727-aN --out <temp>/nes-gap740-PN-trace --mesen <Mesen.exe> --client <694 client>`를 실행한다. `obj`는 OBJ 단독, `pair`는 반환 뒤 OBJ·OAM, `issued`는 선행 조회 예산, `checked`는 실제 반환·입력 서비스까지 포함한다. `checked`를 `nes-gap740-checkedN-pulses`에도 실행해 실제 진행 쓰기가 CPU 일정에 영향을 주지 않았는지 비교한다. 이후 `first`, `both`를 실행한다.
3. 위상 1의 `issued`, `first`를 `--mode stop`, `--mode stale`로 재생한다. 폴더 이름 끝의 `trace`를 모드 이름으로 바꾼다. 기존 `check_nes_menu533.py`를 장시간판 숫자 690, 정상판 704로 실행해 `menu-690.json`, `menu-704.json`을 보관한다.
4. `tools/analyze_nes_gap740.py --temp <temp> --probe <메뉴 검사 폴더> --out <결과 JSON>`이 원본 SHA-256, 실제 E0 반환, 모든 입력·픽셀·마감 및 오류 주입 결과를 대조한다.
