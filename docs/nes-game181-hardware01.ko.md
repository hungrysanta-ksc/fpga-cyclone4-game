# NES181 실기 — 첫 레벨 표시 복구, 표시 처리량은 미달

사용자는 첫 레벨 진입 후 화면 정지가 사라졌고 사운드와 약60초 후 메뉴 복귀도 정상이라고 확인했다. 영상 표본에서도 첫 레벨 진입·캐릭터 위치 변화·월드맵 복귀·마지막 파일 메뉴를 확인했다. **이번 SMB3 시험의 지속적인 화면 정지는 해결됐지만, 심한 끊김과60fps 미달은 남았다.** 모든 장면·게임·매퍼의 영상 정확성 통과로 확대하지 않는다.

## 로그로 확인한 결과

- ROM393,216B 적재·비교 완료, verify/RUN/ROM/최초/STOP 오류0.
- BEGIN/END/COMMIT 각각137, ABORT0. 최종 표시ACK까지 완료된 화면136개, 마지막 완료세대206, 마지막 완료시각59.71초.
- DISPLAY 구간232,450→292,510ms, 총60,060ms. STOP·기본FPGA 복원·메뉴 준비295,760ms 완료. 영상65초 표본에도 파일 메뉴가 보인다.
- 사운드는 사용자 청취로 정상. 로그SPC A9/유효1/unmute1도 일치한다. `screen_error=169`는 사운드 초기화A9이며 영상 오류가 아니다. 음성 스트림 청취·음질 정량 검사는 수행하지 않았다.
- `native_result=1`은 정상적인 시험기한 종료다. 마지막세대208의DATA/section2/offset764/240B 요청은 최종ACK까지 끝나지 않았다. `sink_io170=09`,polls3은POLL_TRANSFER 단계 실패이며, runtime guard가 기한에 도달하면 발생할 수 있다. ACK유효0·전부0인placeholder는잘못된CRC/손상ACK의증거가 아니다. 원인1이먼저보존된구현과60.06초를고려하면sink_error2는종료중부차결과로판단한다.

## 처리량과 병목

|누적 구간|시간|포함하는 작업|
|---|---:|---|
|receive|28.38초|후보 수집/전송 대기, 상태polling, FPGA→MCU 수신·확정|
|build/stage|7.74초|MCU 변환, BEGIN, CHR callback의SNES 전송·ACK|
|seal/ACK|23.71초|나머지section 전송, SNES 복사·공개·최종ACK|
|합계|59.83초|10ms단위 누적값; 세부CPU/순수SPI/PPU시간으로 분리된 계측은 아님|

136/60.06 = **초당2.264회 표시 완료**, 전체구간 환산 약441.6ms/완료다. 이는 카메라가 측정한FPS나NES CPU/PPU 실행속도가 아니라, 전체시험의완료ACK평균이다. 장면별지연·p50/p95·중복화면여부는기록되지않았다.60Hz TV의주사율과도구분한다. 사용자체감의끊김을뒷받침하지만정확한실시간FPS로표현하지않는다.

기록된native전송은137,469transaction/4,811,300clocked bytes다.2.625MHz에서이바이트의순수전송하한만약14.66초다. 이수치에는양쪽경로·status/ACK/polling이섞이고서비스observer의직접SPI는포함하지않는다. TX+RX를두배로세지않는다. 현재교통량을완료136개로나누면약35.4KB/완료지만, 이것을필수화면payload로간주해서는안된다. polling/요청/유효데이터별카운터가없으므로유효바이트절감량이나CPU병목을단정할수없다.

한단계만없애도60fps가된다는근거는없다. 기존22.154ms는합성raw7장면의SNES전송하한일뿐이며, 이번전체실기약442ms/완료와충돌하지않는다. 이번자료로생산경로의지연이훨씬크다는점을확인했다.

## 남은 후보 거부

최근16사건은8회거부/8회회복이다. 모두224행이며기존180에서관찰한raster08/compact82는이16건에없다. fetch01 거부6건,fetch04 거부1건,보고오류0·mask00거부1건이다. 나머지회복은오류0이며generation은256순환한다.

배포소스상fetch01은이전low의high짝이완료되기전에새low가온경우,04는high의주소/논리주소/설명/tag짝검사가실패한경우다. 합법적렌더링중단이나fetch정렬을포함해원인은더좁혀야하며ROM응답오류로단정하지않는다. errors0거부도가능하다:geometry_valid에는patch_valid와추가완결성조건이들어가지만25비트history에는patch_errors가없다. 따라서오류0이라고거부가오류없이발생했다거나빈화면만이원인이라고단정하지않는다.

이기록은전체프레임별통계가아니며시각도없다. 거부가어느버튼·장면인지,얼마나오래표시를늦췄는지는알수없다. 전송ABORT0도BEGIN전후보거부가없다는뜻이아니다. 패드237변화/최근16기록은실제클릭수또는입력유지품질의증명이아니다.

## 다음 작업

1. 이번181을첫레벨표시복구기준으로보존한다. 같은181·180·044재시험,무변경FIT·장시간부팅모델·새범용진단은하지않는다.
2. 실제전송호출에서유효payload/status/poll/ACK와CHR소규모callback의비용을분리하고,작은패킷집계·변경section만전송하는방식을우선검토한다. 이미구현한raw차등갱신·1813/1815압축을없는것처럼재구현하지않는다.
3. capture lease와MCU workspace·SNES표시bank는서로다른소유권이다. exporter COMMIT시FPGA가release하며, MCU는최종displayACK까지다음수신을진행하지않는다. 다음수집과전송/표시를겹치는구조를같은16.7ms서비스예산·기준세대검사·RAM/IRQ여유로평가한다. 세이브SRAM은사용하지않는다.
4. fetch01/04거부·재동기화는처리량개선과함께확인하되보호조건을삭제하지않는다. 정확한표시가유지되는작은구현검사후실제SMB3로검증한다. 최종지속60fps·음성→장기플레이/오류·리셋로그→입력유지순서유지.

이번에는실기결과만기록했다. 새RTL/펌웨어/FIT/ZIP은없고기존181·180/GBC164/세이브SRAM/완료archive는유지한다. 영상은65.90초/촬영약29.95fps이며2fps표본과4초간격overview로장면을확인했다. 이샘플링으로정확한표시FPS를측정하지않았다. CRT띠·촬영색변화는오류로분류하지않는다.
