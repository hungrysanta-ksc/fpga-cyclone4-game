# 공개 저장소 관리 규칙

## 목적과 경계

이 저장소는 FXPAK Pro GBC 이식의 재현 가능한 진행 기록·지원 자료와, 차기 Cyclone IV 게임기 코어 이식의 참고 절차를 함께 보관한다. 공개 `repository/` clone만 GitHub에 올린다. 로컬 전체 snapshot, 상용 게임 자산, 사용자의 SD 카드·세이브·덤프는 private이다.

## 등록 판정

| 자료 | 공개 조건 |
| --- | --- |
| 자체 작성 계획·감사·표·작은 fixture·스크립트 | 사적 절대 경로, ROM 바이트, 개인정보/계정, 라이선스 키·토큰, 외부 도구 번들을 제거하고 결과의 검증 범위를 명시한다. |
| RTL/MCU/renderer 소스 | upstream URL·고정 commit·원래 저작권/라이선스·수정 범위·필수 의존성 및 빌드 가능 범위를 등록한 뒤 **선택 파일만** 추가한다. 미확인 코드를 공개하지 않는다. |
| 시험 결과 | 후보 ID, 소스·제약 해시, 도구/seed, 입력의 공개 가능성, model scope, pass/fail, 미결 사항을 갖춘 요약만. 원본 ROM/SAV/SRM, 메모리/영상 dump, 개인 경로가 든 raw log는 제외한다. |
| bitstream·펌웨어·설치 ZIP | 소스/라이선스/재현 빌드와 같은 후보의 기능·자원·타이밍·CDC·보드·실기 gate가 끝난 후 별도로 결정한다. 현재는 등록하지 않는다. |
| 상용 ROM·boot ROM·사용자 save·라이선스/키/토큰·도구 설치본·캐시 | **등록 금지**. 해시와 공개 가능한 시험 조건만 문서화한다. |

`.gitignore`는 허용 목록이다. `git add .`, `git add -f`, 전체 snapshot 복사·업로드를 사용하지 않는다. 허용 목록 변경과 실제 stage된 파일을 각각 검토한다. 비밀이 한 번 commit에 들어갔다면 단순 삭제 commit만으로 해결됐다고 보지 않고 유출 대응·이력 정리를 별도 판단한다.

## 브랜치와 변경 기록

- 보존할 baseline과 실험을 구분한다. 작업 브랜치는 `codex/` 접두사를 사용한다. 기본 브랜치에는 검토된 문서/도구/승인된 구현만 올리고 force-push하지 않는다. 원래 SDC와 실패 결과를 유지하며 새 제약은 별도 버전으로 근거·diff·영향 경로를 기록한다.
- PR은 한 가설 또는 한 관리 목적에 맞춘다. 후보 ID, 변경 파일과 출처, 불변 조건, 동일 후보 검증 결과, 실패/unknown, 물리 자원 비용, 다음 gate를 적는다. issue/PR 양식을 사용하되 작은 문서 수정에도 불필요한 장기 빌드를 요구하지 않는다.
- 상태 표기는 `계획`, `모델`, `RTL`, `fit`, `constraint coverage`, `board`, `실기`, `제품`을 분리한다. `timing_pass`, 양수 constrained slack 또는 제한된 RGB exact 하나로 board/제품 완료를 표시하지 않는다. 이전 G12S2 save 성공을 새 G13 전체 검증으로 이전하지 않는다.
- 하드웨어 실기 패키지 전에는 대상·복사 파일·세이브 백업·rollback·관측·중단 조건을 명시한다. 파일 배포와 실기 실행은 별도 승인 gate이다.

## 외부 기여·차기 코어 이식

차기 코어는 `PORTING-PLAYBOOK.ko.md`로 요구와 보드 계약을 처음부터 대조한다. GBC의 33.56/84MHz, 270ns slot, 색·오디오·메모리 배치를 새 코어의 사실로 복사하지 않는다. upstream 코드·라이선스의 병합 가능성과 보드 핀/전압/클록·메모리 예산을 먼저 기록한다.

이 저장소 전체에 대한 재사용 라이선스는 현재 미정이다. 기존 upstream 표시를 지우거나 새 라이선스로 덮지 않는다. 공개 자료의 재사용 조건이 필요하면 소유자가 명시적으로 결정하고 `DEPENDENCY-REGISTER.ko.md`의 검토를 마친 뒤 파일별/전체 범위를 문서화한다.
