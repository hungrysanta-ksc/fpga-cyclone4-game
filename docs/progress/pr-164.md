## 목표

PR163 병합 커밋 `e5952ca`와 실기 MMC813을 기준으로 첫 레벨 5–40초의 출력·최종 ACK 증가를 조사한다. 같은 입력과 부팅 위상에서 951→970의 표시 간격 합과 970 최종 ACK를 모두 앞당기는 후보를 찾는다.

## 작업내용

- MMC807·813 실기 로그의 5–40초를 각각 일곱 구간으로 나눴다. 시각을 바꾼 49쌍에도 화면당 변경 map·OBJ·BG가 모두 MMC807 대비 ±20% 안에 드는 쌍은 없었다. 각 판의 원래 화면 수 비중에서 가장 적게 벗어나도록 5초 구간에 음이 아닌 가중치를 주고, 두 판의 세 평균 작업량을 정확히 맞췄다. 가중치 선택에는 출력 시간이나 FPS를 쓰지 않았다. 각 판 한 번의 수동 플레이에서 얻은 추정값이다. 구간 안의 개별 화면이나 VBlank 시각은 실기 로그에서 복원할 수 없다.
- 815 ARM 대조군은 긴 map이 수락되고 OBJ가 적을 때, 검증한 DMA 진행 조회 상한만 24→32회로 늘렸다. 815R은 MMC813 ARM 바이트를 유지하고 65816의 raw 타일 DMA 경로만 바꿨다. 대상 뱅크에서 독립 비교한 6행 중 마스크가 `0x1d`이면 1·5번 행 64B씩 직접 전송한다(0번부터 센다). 기존 `0x15`는 1·3·5번 행을 전송한다. 나머지 마스크는 기존 일반 경로를 사용한다. 건너뛰는 중간 행에서도 STOP을 확인한다.
- 같은 SMB3(J) 입력 905–970, SPI 드라이버, IRQ와 ROM 허가 일정, 두 시작 클록(7,288,416·7,467,100)에서 실제 링크된 ARM·65816을 재생했다. 각 위상의 66화면에서 기대 map·WRAM/VRAM map·표시 RGB·section 5를 대조했다. raw 영역 DMA 179건은 세대·뱅크·출발지·도착지·길이·순서까지 같았다.

## 성과

**실기.** 전체 평균 증가 1.69ms 중 작업량을 맞춘 비교에서 남은 차이는 0.74ms다. 화면당 변경 map 11.53그룹·OBJ 39.47개·BG 517.14개로 맞추면 MMC807은 29.21ms, MMC813은 29.94ms다. E0는 51.08→58.72회, E8은 39.01→34.50회였다. 구간별 조회 횟수에 각 판 전체 실행의 평균 거래 시간을 곱하면 두 조회의 합은 9.90→10.30ms다. 조회는 다른 단계에도 걸치므로 이 0.40ms를 출력 구간의 직접 지연으로 합산할 수 없다.

**동일 입력 재생.** MMC807에서 952–970의 SEAL 이후 마지막 VBlank 대기는 평균 0ms였다. MMC813은 위상 1에서 958·960·962, 위상 2에서 960·962가 한 번 더 기다려 평균 2.41·1.60ms가 됐다. 이 장면들은 독립 비교에서 같은 raw 행을 재사용해도 기존 65816이 생략 행의 주소와 진행 상태를 순회한다. 위상 1의 960에서 두 소비자는 업로드 VBlank 재개 뒤 모두 2,224B를 DMA했다. 재개부터 최종 검사 진입까지는 MMC813의 1.349ms에서 815R의 1.164ms로 줄었다. 최종 검사선은 246→243선, 추가 대기는 1→0회였다. 이 재생은 실기 5초 구간과 일대일로 대응하지 않는다.

| MMC813 대비 | 위상 1 | 위상 2 |
|---|---:|---:|
| 815 ARM 대조군 · 밀집 표시 간격 변화 | −33.284ms | −0.014ms |
| 815 ARM 대조군 · 970 ACK 변화 | −33.266ms | +0.010ms |
| **815R · 밀집 표시 간격** | **981.742→931.835ms (59→56 VBlank)** | **965.109→931.812ms (58→56 VBlank)** |
| **815R · 970 ACK 변화** | **−49.910ms** | **−33.277ms** |

815R의 960·962는 두 위상 모두 4→3 VBlank다. 951의 BG 16B·map 1,536B 선행 DMA, 236선 공개, 959 표시 2회를 유지했다. 246선 검사 기준과 표시 뒤 ACK 코드는 그대로다. 실제 CPU에 STOP을 주입한 11건은 이후 DMA·새 화면 ACK를 차단하고 직전 화면을 보존했다. 두 뱅크에서 늦은 STOP 이후 cold 재시작과 손상 manifest 거부를 검사했다. MMC813 ARM의 종료·base·메뉴 경로는 기존 실기에서 확인했다.

815R의 ARM은 212,988B(Flash 여유 4B), 65816 프로그램은 기존 5,120B(여유 24B)이고 WRAM 추가는 없다. 압축 ROM의 비압축 앞부분이 512→128B가 되어 독립 부팅 시험에서 복원이 18.712ms 더 걸렸다. 손상 바이트 주입은 두 ROM 모두 거부했다. 위 표의 마지막 ACK는 같은 시작 클록에서 계산했고, 밀집 간격은 951 표시 시각을 빼서 비교했다. [실기 로그 해시·구간 가중치·두 위상 재생·부팅과 STOP 결과](../../analysis/output815-results.json)

**실기 전달 준비.** MMC816은 815R의 60초 ROM을 그대로 사용했다. MMC817은 MMC814의 직접 종료 처리를 보존하고 같은 raw 행 처리 구간을 적용했다. 5,120B ROM 여유는 각각 24B·4B, 최종 ARM Flash 여유는 4B·44B다. 두 판 모두 MIF의 5,120바이트를 CPU 시험에 쓴 ROM과 대조한 뒤, 새로 배치한 SOF에서 만든 BI3를 프로그래머 전송 시험으로 확인했다.

Quartus Lite 25.1에서 두 판을 각각 처음부터 MAP·FIT·ASM·STA 했다. 각각 15,333/15,408 LE, 963/963 LAB, 56/56 M9K를 썼다. 세 코너에서 보고한 57개 타이밍 항목의 TNS는 모두 0이었다. 최저 setup/hold/recovery/removal 여유는 0.419/0.147/1.372/0.490ns다. 기준 보드와 미제약 I/O 수가 같다. 두 ROM은 각각 부팅 복원·손상 거부, 행 경계 STOP 11건과 두 뱅크의 cold·손상 manifest 검사를 통과했다. 장시간판은 패킷 및 DMA 중 직접 종료 후 1,000회 대기 루프에서 추가 ACK·DMA가 없었다. 두 ARM에서 STOP 뒤 base 복원 성공 시 메뉴를 해제하고, 주입한 복원 실패 네 종류는 안전하게 차단했다.

| 최종 링크 · MMC813 대비 | 밀집 간격 단축 (위상 1 / 2) | 970 ACK 단축 (위상 1 / 2) |
|---|---:|---:|
| MMC816 · 60초 | 49.907 / 33.297ms | 49.910 / 33.277ms |
| MMC817 · 장시간 | 49.922 / 33.279ms | 49.914 / 16.638ms |

네 재생에서 951→970은 모두 56 VBlank였다. 각 재생의 66개 화면·map·section 5와 raw DMA 179건이 MMC813과 일치했다. 951은 236선에 공개했고, 959는 2회, 960·962는 각각 3회에 표시했다. 장시간판 위상 2의 951은 MMC813보다 한 VBlank 뒤에 표시돼 밀집 간격 단축 전부가 절대 ACK 시각에 반영되지는 않았다. 같은 장시간판끼리 비교하면 MMC814 대비 970 ACK는 위상 1에서 16.625ms 빨랐고 위상 2에서 28클록(1.30µs) 늦었다. [최종 보드·ARM·ROM·재생·ZIP 검증값](../../analysis/trial816-package.json)

### 무입력 60초 기준 변경

타카하시 명인의 모험도 4(MMC819)를 기본 속도 시험으로, 캡틴 츠바사 II(MMC818)를 큰 스프라이트가 많은 보조 시험으로 선택했다. 두 첨부본 모두 iNES mapper 4, PRG 256KiB·CHR 128KiB, 헤더 미러링은 수직이다. MMC816의 실제 링크는 두 파일을 16B 헤더에서 거부했다. 새 링크는 각 판의 원본 전체 CRC를 검사하고 교차 ROM 및 마지막 바이트 손상을 거부한다. 보드는 MMC3의 초기 수직 미러링을 설정한다. 캡틴 츠바사는 첫 미러링 명령 전에 PPUDATA를 4,096회 썼다.

Mesen에서 각 ROM을 리셋부터 무입력으로 3,600프레임씩 두 번 실행했다. 실행별 화면 표본과 프레임별 OAM 기록은 반복 간 바이트 단위로 일치했다. 아래 초는 60프레임을 1초로 환산한 기준이다. 화면 변화는 6프레임마다 같은 위치에서 채취한 픽셀 표본의 해시가 직전 표본과 달라진 횟수다.

| 게임 · 구간 | 화면 변화 | OAM 슬롯이 바뀐 프레임 | 화면 높이 안의 OAM 슬롯 평균 |
|---|---:|---:|---:|
| 타카하시 · 5–40초 | 307/350 | 1,707/2,100 | 9.8 |
| 타카하시 · 40–55초 | 142/150 | 746/900 | 9.7 |
| 캡틴 츠바사 · 5–40초 | 194/350 | 852/2,100 | 56.4 |
| 캡틴 츠바사 · 40–55초 | 84/150 | 83/900 | 57.8 |

OAM은 스프라이트가 프레임 중 켜진 경우 화면 높이 안에 있는 슬롯을 센다. 슬롯 수에는 투명 타일이나 겹친 스프라이트도 들어간다. 실제 화면 기여를 별도 대조한 결과, 스프라이트 표시만 끄면 타카하시의 전·후반 표본 333/350·146/150과 캡틴 츠바사의 310/350·141/150에서 화면이 달라졌다. 같은 대조에서 게임의 OAM·마스크·미러링 기록은 같았다.

두 ARM의 Flash 여유는 각각 4B다. MMC816과 최종 ELF의 이름 있는 함수 794개를 비교했고 기계어가 달라진 함수는 ROM을 검사하는 `nes_menu_sd_probe` 하나다. 공통 수직 미러링 보드는 Quartus Lite 전체 FIT·STA를 통과했다(15,325 LE·963 LAB·56 M9K, 최저 setup 0.588ns·hold 0.147ns). Mesen의 60초 재생, 실제 보드 소스의 CPU·PPU에서 외부 ROM을 지연 없이 공급하는 부팅 시험, 두 ARM의 헤더·CRC·자동 종료·메뉴 복구 시험은 각각 별도로 실행했다. 보드 RTL에서 캡틴 츠바사는 13번째 프레임에 4색, 타카하시는 25번째 프레임에 7색을 관측했다. 타카하시의 최초 600초 벽시계 제한 후 같은 판정 조건으로 재실행했다. 다음 실기에서 실제 PSRAM 경쟁과 SNES 표시를 포함한 60초 완주를 확인한다. [검증값과 설치 파일 해시](../../analysis/opening818-results.json)

## 후속작업

MMC819를 선택한 뒤 무입력 상태로 자동 메뉴 복귀까지 60초를 측정한다. 첫 정상 로그로 타카하시 자체의 5–40초·40–55초 기준을 만들고 이후 같은 ROM과 구간으로 비교한다. MMC818은 별도 스프라이트 부하 기준으로 기록한다. 장시간 SMB3 시험은 MMC817을 유지한다. [새 설치·로그 안내](../nes-mmc818-819-trial.ko.md)

무입력 시험은 `probe_nes_opening818.py <ROM> <Mesen.exe> <새 폴더>`로 두 번 재생하고 `--hide-sprites`로 배경 단독 대조를 만든다. `prepare_nes_opening818.py arm --edition 818|819`는 MMC816 ARM용 패치를, `board --temp <추적 루트>`는 수직 미러링 보드 소스를 만든다. `check_nes_opening818.py`는 원본 ROM·교차 ROM·손상 ROM에 대해 링크된 ARM의 파일 수락 여부를 확인한다. `core_nes_opening818.py <보드 폴더> <새 폴더> <캡틴 ROM> <타카하시 ROM>`은 기존 FLOAT 래퍼 안에서 두 게임을 순서대로 부팅한다. 설치 ZIP과 증거는 `package_nes_opening818.py <추적 루트>`로 묶는다.

전달본은 `prepare_nes_trial816.py clients`에서 만든 패치를 각각 MMC813·814 ARM에 전체 링크한다. 같은 스크립트의 `board`, `fit`에 각 판 번호와 804 원본이 있는 임시 루트를 지정하고 `package_nes_trial704.py image`로 BI3를 생성한다. `run_nes_output809.ps1 -Variant 816|817 -Phase 1|2`를 각 최종 링크에 실행한다. 행 STOP, 부팅·직접 종료, ARM의 모드·메뉴·복원 검사 산출물을 준비한 뒤 `package_nes_trial816.py <추적 루트>`로 검증된 파일을 묶는다.

재현 시 `tools/prepare_nes_output815.py arm|client <새 폴더>`를 사용한다. ARM 대조군은 MMC813 링크에 패치를 적용해 기존 `build_nes_mmc479_arm.ps1`로 링크한다. `run_nes_output809.ps1 -Variant 815|815R -Phase 1|2`에 기존 ROM과 추적 루트를 지정한다. `check_nes_raw815.py`는 MMC813 위상 1의 패킷열, 815R client와 Mesen을 사용한다. `check_nes_longrun694_boot.py`로 기준·후보 ROM의 복원과 손상 거부를 실행한다. `analyze_nes_output815.py --downloads <실기 로그 폴더> --traces <추적 루트> --output <결과 JSON>`으로 대조한다.
