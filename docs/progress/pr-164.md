## 목표

PR163 병합 커밋 `e5952ca`와 실기 MMC813을 기준으로 첫 레벨 5–40초의 출력·최종 ACK 증가를 조사한다. 같은 입력과 부팅 위상에서 951→970의 표시 간격 합과 970 최종 ACK를 모두 앞당기는 후보를 찾는다.

## 작업내용

- MMC807·813 실기 로그의 5–40초를 각각 일곱 구간으로 나눴다. 시각을 바꾼 49쌍에도 화면당 변경 map·OBJ·BG가 모두 MMC807 대비 ±20% 안에 드는 쌍은 없었다. 각 판의 원래 화면 수 비중에서 가장 적게 벗어나도록 5초 구간에 음이 아닌 가중치를 주고, 두 판의 세 평균 작업량을 정확히 맞췄다. 가중치 선택에는 출력 시간이나 FPS를 쓰지 않았다. 각 판 한 번의 수동 플레이에서 얻은 추정값이다. 구간 안의 개별 화면이나 VBlank 시각은 실기 로그에서 복원할 수 없다.
- 815 ARM 대조군은 긴 map이 수락되고 OBJ가 적을 때, 검증한 DMA 진행 조회 상한만 24→32회로 늘렸다. 815R은 MMC813 ARM 바이트를 유지하고 65816의 raw 타일 DMA 경로만 바꿨다. 대상 뱅크에서 독립 비교한 6행 중 마스크가 `0x1d`이면 1·5번 행 64B씩 직접 전송한다(0번부터 센다). 기존 `0x15`는 1·3·5번 행을 전송한다. 나머지 마스크는 기존 일반 경로를 사용한다. 건너뛰는 중간 행에서도 STOP을 확인한다.
- 같은 SMB3(J) 입력 905–970, SPI 드라이버, IRQ와 ROM 허가 일정, 두 시작 클록(7,288,416·7,467,100)에서 실제 링크된 ARM·65816을 재생했다. 각 위상의 66화면에서 기대 map·WRAM/VRAM map·표시 RGB·section 5를 대조했다. raw 영역 DMA 179건은 세대·뱅크·출발지·도착지·길이·순서까지 같았다.

## 성과

**실기.** 전체 평균 증가 1.69ms 중 작업량을 맞춘 비교에서 남은 차이는 0.74ms다. 화면당 변경 map 11.53그룹·OBJ 39.47개·BG 517.14개로 맞추면 MMC807은 29.21ms, MMC813은 29.94ms다. E0는 51.08→58.72회, E8은 39.01→34.50회였다. 구간별 조회 횟수에 각 판 전체 실행의 평균 거래 시간을 곱하면 두 조회의 합은 9.90→10.30ms다. 조회는 다른 단계에도 걸치므로 이 0.40ms를 출력 구간의 직접 지연으로 합산할 수 없다.

**동일 입력 재생.** MMC807에서 952–970의 SEAL 이후 마지막 VBlank 대기는 평균 0ms였다. MMC813은 위상 1에서 958·960·962, 위상 2에서 960·962가 한 번 더 기다려 평균 2.41·1.60ms가 됐다. 이 장면들은 독립 비교에서 같은 raw 행을 재사용해도 기존 65816이 생략 행의 주소와 진행 상태를 순회한다. 위상 1의 960에서 두 소비자는 업로드 VBlank 재개 뒤 모두 2,224B를 DMA했다. 재개부터 최종 검사 진입까지는 MMC813의 1.349ms에서 815R의 1.164ms로 줄었다. 최종 검사선은 246→243선, 추가 대기는 1→0회였다. 이 재생은 실기 5초 구간과 일대일로 대응하지 않는다.

|---|---:|---:|
| 815 ARM 대조군 · 밀집 표시 간격 변화 | −33.284ms | −0.014ms |
| 815 ARM 대조군 · 970 ACK 변화 | −33.266ms | +0.010ms |

815R의 960·962는 두 위상 모두 4→3 VBlank다. 951의 BG 16B·map 1,536B 선행 DMA, 236선 공개, 959 표시 2회를 유지했다. 246선 검사 기준과 표시 뒤 ACK 코드는 그대로다. 실제 CPU에 STOP을 주입한 11건은 이후 DMA·새 화면 ACK를 차단하고 직전 화면을 보존했다. 두 뱅크에서 늦은 STOP 이후 cold 재시작과 손상 manifest 거부를 검사했다. MMC813 ARM의 종료·base·메뉴 경로는 기존 실기에서 확인했다.

815R의 ARM은 212,988B(Flash 여유 4B), 65816 프로그램은 기존 5,120B(여유 24B)이고 WRAM 추가는 없다. 압축 ROM의 비압축 앞부분이 512→128B가 되어 독립 부팅 시험에서 복원이 18.712ms 더 걸렸다. 손상 바이트 주입은 두 ROM 모두 거부했다. 위 표의 마지막 ACK는 같은 시작 클록에서 계산했고, 밀집 간격은 951 표시 시각을 빼서 비교했다. **실기 전달 준비.** MMC816은 815R의 60초 ROM을 그대로 사용했다. MMC817은 MMC814의 직접 종료 처리를 보존하고 같은 raw 행 처리 구간을 적용했다. 5,120B ROM 여유는 각각 24B·4B, 최종 ARM Flash 여유는 4B·44B다. 두 판 모두 MIF의 5,120바이트를 CPU 시험에 쓴 ROM과 대조한 뒤, 새로 배치한 SOF에서 만든 BI3를 프로그래머 전송 시험으로 확인했다.

Quartus Lite 25.1에서 두 판을 각각 처음부터 MAP·FIT·ASM·STA 했다. 각각 15,333/15,408 LE, 963/963 LAB, 56/56 M9K를 썼다. 세 코너에서 보고한 57개 타이밍 항목의 TNS는 모두 0이었다. 최저 setup/hold/recovery/removal 여유는 0.419/0.147/1.372/0.490ns다. 기준 보드와 미제약 I/O 수가 같다. 두 ROM은 각각 부팅 복원·손상 거부, 행 경계 STOP 11건과 두 뱅크의 cold·손상 manifest 검사를 통과했다. 장시간판은 패킷 및 DMA 중 직접 종료 후 1,000회 대기 루프에서 추가 ACK·DMA가 없었다. 두 ARM에서 STOP 뒤 base 복원 성공 시 메뉴를 해제하고, 주입한 복원 실패 네 종류는 안전하게 차단했다.

| MMC816 · 60초 | 49.907 / 33.297ms | 49.910 / 33.277ms |

네 재생에서 951→970은 모두 56 VBlank였다. 각 재생의 66개 화면·map·section 5와 raw DMA 179건이 MMC813과 일치했다. 951은 236선에 공개했고, 959는 2회, 960·962는 각각 3회에 표시했다. 장시간판 위상 2의 951은 MMC813보다 한 VBlank 뒤에 표시돼 밀집 간격 단축 전부가 절대 ACK 시각에 반영되지는 않았다. 같은 장시간판끼리 비교하면 MMC814 대비 970 ACK는 위상 1에서 16.625ms 빨랐고 위상 2에서 28클록(1.30µs) 늦었다. ### 무입력 60초 기준 변경

타카하시 명인의 모험도 4(MMC819)를 기본 속도 시험으로, 캡틴 츠바사 II(MMC818)를 큰 스프라이트가 많은 보조 시험으로 선택했다. 두 첨부본 모두 iNES mapper 4, PRG 256KiB·CHR 128KiB, 헤더 미러링은 수직이다. MMC816의 실제 링크는 두 파일을 16B 헤더에서 거부했다. 새 링크는 각 판의 원본 전체 CRC를 검사하고 교차 ROM 및 마지막 바이트 손상을 거부한다. 보드는 MMC3의 초기 수직 미러링을 설정한다. 캡틴 츠바사는 첫 미러링 명령 전에 PPUDATA를 4,096회 썼다.

Mesen에서 각 ROM을 리셋부터 무입력으로 3,600프레임씩 두 번 실행했다. 실행별 화면 표본과 프레임별 OAM 기록은 반복 간 바이트 단위로 일치했다. 아래 초는 60프레임을 1초로 환산한 기준이다. 화면 변화는 6프레임마다 같은 위치에서 채취한 픽셀 표본의 해시가 직전 표본과 달라진 횟수다.

| 게임 · 구간 | 화면 변화 | OAM 슬롯이 바뀐 프레임 | 화면 높이 안의 OAM 슬롯 평균 |
|---|---:|---:|---:|
| 타카하시 · 5–40초 | 307/350 | 1,707/2,100 | 9.8 |
| 타카하시 · 40–55초 | 142/150 | 746/900 | 9.7 |
| 캡틴 츠바사 · 5–40초 | 194/350 | 852/2,100 | 56.4 |
| 캡틴 츠바사 · 40–55초 | 84/150 | 83/900 | 57.8 |

OAM은 스프라이트가 프레임 중 켜진 경우 화면 높이 안에 있는 슬롯을 센다. 슬롯 수에는 투명 타일이나 겹친 스프라이트도 들어간다. 실제 화면 기여를 별도 대조한 결과, 스프라이트 표시만 끄면 타카하시의 전·후반 표본 333/350·146/150과 캡틴 츠바사의 310/350·141/150에서 화면이 달라졌다. 같은 대조에서 게임의 OAM·마스크·미러링 기록은 같았다.

두 ARM의 Flash 여유는 각각 4B다. MMC816과 최종 ELF의 이름 있는 함수 794개를 비교했고 기계어가 달라진 함수는 ROM을 검사하는 `nes_menu_sd_probe` 하나다. 공통 수직 미러링 보드는 Quartus Lite 전체 FIT·STA를 통과했다(15,325 LE·963 LAB·56 M9K, 최저 setup 0.588ns·hold 0.147ns). Mesen의 60초 재생, 실제 보드 소스의 CPU·PPU에서 외부 ROM을 지연 없이 공급하는 부팅 시험, 두 ARM의 헤더·CRC·자동 종료·메뉴 복구 시험은 각각 별도로 실행했다. 보드 RTL에서 캡틴 츠바사는 13번째 프레임에 4색, 타카하시는 25번째 프레임에 7색을 관측했다. 타카하시의 최초 600초 벽시계 제한 후 같은 판정 조건으로 재실행했다. 다음 실기에서 실제 PSRAM 경쟁과 SNES 표시를 포함한 60초 완주를 확인한다. ### MMC819 데모 전환

실기에서 ROM 393,216B 대조와 START에 성공했다. 무입력으로 470화면을 표시한 뒤 25.38초에 세대 503에서 마지막 표시를 마쳤다. 5–40초 표시 수는 383, 40–55초는 0이다. 출력 큐의 4,276건이 전부 반환됐고 ROM 오류·SPI 전송 실패는 0이다. ARM은 입력 대기 중 60초 제한으로 종료했고 STOP·base 복구·메뉴 준비에 성공했다. 수신 코드 21은 D0 거래 또는 상태 검사 공통 종료값으로, 타이머가 거래를 중단시켜도 기록된다. 이것만으로 SPI 고장을 판정할 수 없다.

거부·회복 기록의 마지막 항목은 세대 하위 바이트 248, PPUMASK 0, 일반 BG 그룹 0, 팔레트 0인 거부다. 직전 표시 세대의 하위 바이트는 247이다. 관측기는 연속 거부 중 첫 건만 남기고 raw 행 오류를 별도 기록하지 않는다. 따라서 마지막 로그 항목을 데모 한가운데의 마스크 값으로 해석할 수 없다.

같은 ROM을 Mesen에서 3,600프레임 무입력 재생했다. 1,557번째 프레임의 192선 dot 96에서 게임이 PPUMASK를 0x1E에서 0x0E로 바꾼다. BG는 유지하고 OBJ는 끈다. 192선의 같은 전환이 2,016프레임에서 발생했다(dot 91–108). MMC819에 합성한 raster와 raw 행 저장 RTL에 마스크만 재생하면 192–231선에서 40개 raw 행을 요청한다. 199선에서 8번째 행이 7행 한도를 넘겨 오류 0x08로 프레임을 거부한다. dot 96·91에서 같은 결과이며, 0x1E 대조군은 전후 모두 224행을 수락한다. 이는 게임의 마스크 전환만으로 거부가 발생함을 확인한 시험이다. 실기의 이후 각 거부 사유 전체나 실제 픽셀을 재생한 시험은 아니다. 캡틴 츠바사의 별도 3,600프레임에서는 0x0E 전환이 없었다. [마스크 수집기](../../tools/trace_nes_opening819.lua) · [보드 RTL 재현 시험](../../tools/opening819_mask_tb.sv)

## MMC820 모험도 4 경계 복구

MMC819에서 25.38초 뒤 표시가 멈춘 무입력 데모를 대상으로 수정했다. FPGA는 줄 안에서 PPUMASK가 바뀌면 원래 합성색 256픽셀을 raw로 보존한다. 0x0E가 줄 전체에서 유지되면 BG의 색·스크롤·왼쪽 마스크를 일반 행으로 보낸다. ARM은 스프라이트 원본 행과 수직 반전을 고려해 해당 행의 OBJ 비트플레인만 비운다. 다른 위치의 raw 전환은 그대로 판정한다. 65816의 표시 코드와 패킷 형식은 MMC819와 같다.

- 같은 무입력 ROM의 3,600프레임을 원본·스프라이트 숨김 설정으로 각각 재생했다. 192선 전환 2,016프레임에서 193–231선의 픽셀 차이는 0이었다. 합성 보드에 쓰인 raster와 raw 저장기를 dot 91–108 전체에서 재생해 각 조건당 경계 한 줄만 raw로 확정했다.
- 원본 PPU 버스와 합성색을 FPGA 캡처·export RTL에 재생하고 최종 링크 ARM을 실행했다. 타이틀 1,500, 전환 1,557, 경계 근처 2,095–2,098·2,130, 데모 2,100·3,000·3,600의 10개 화면을 대조했다. 재생한 데모 프레임의 raw 행은 가시 좌표 0·184였다. 184가 NES 192선이고, 0은 타이틀 대조군에도 있던 첫 행이다.
- ARM의 map·OAM·palette·tile·HDMA를 별도 65816 DMA 드라이버로 SNES PPU에 표시했다. 10 × 256 × 224 = 573,440픽셀에서 원본을 RGB555로 변환한 결과와 차이가 없었다. 2,095–2,098에서는 실제 경계 행에서 OBJ가 색을 바꿨다. raw 행의 입력색은 원본 합성색이며, 게임 CPU·PPU를 FPGA와 65816에 60초간 연속 결합한 시험은 수행하지 않았다.
- 설치본의 65816 독립 검사에서 11개 STOP 경계와 cold·late STOP·손상 manifest 6건을 재생했다. 최종 ARM은 ACK 152비트 각각의 손상, ROM 파일 CRC, 60초 종료, 메뉴 해제와 base 복구 경로를 확인했다. 하드웨어 인터페이스 응답을 제공한 실행이므로 메뉴 복귀의 실기 확인은 다음 시험에 포함한다.
- Quartus Lite 전체 FIT는 15,335/15,408 LE, 962 LAB, 56/56 M9K였다. 최악 setup +0.553 ns, hold +0.143 ns이며 기존 미제약 I/O 집계는 MMC819와 같았다. ARM Flash는 212,968/212,992B다. [검증 결과와 해시](../../analysis/mask820-results.json) · [MMC820 설치 및 시험](../nes-mmc820-trial.ko.md)

## MMC820 실기 기준

모험도 4 일본판, ROM CRC32 `a58fe808`, 무입력 60초판의 첫 완주 기록이다. 사용자는 모든 장면의 표시와 메뉴 복귀를 확인했다. ROM 393,216B 대조 성공, 패드 변화 기록은 NONE 한 건, 표시 931회, 마지막 표시는 59.95초였다. 수신 COMMIT 932회·ABORT 0회, ROM·영상·전송 CRC 오류 0, STOP·base 복구·메뉴 준비가 확인됐다. 종료 시 열린 한 건은 표시 수에서 제외했다. MMC819의 25.38초 이후 화면 정지가 이번 실행에서 재현되지 않았다.

| 구간 | 완료 표시 | 표시 FPS | 수신 ms | 계획·staging ms | 출력·최종 ACK ms |
|---|---:|---:|---:|---:|---:|
| 5–40초 | 543 | 15.51 | 7.59 | 11.14 | 45.31 |
| 40–55초 | 243 | 16.20 | 7.33 | 9.26 | 44.44 |
| 5–55초 | 786 | 15.72 | 7.51 | 10.56 | 45.04 |

FPS는 `display_5_40_55`의 **표시 완료 시각**으로 계산한다. 단계 비용은 10ms tick 합계를 **프레임 시작 시각** 기준 구간의 완료 수 544·243으로 나눈 값이다. 5–55초에서 표시 간격 평균은 63.61ms다. 후속 판도 동일 ROM과 무입력으로 실행하고 두 구간을 각각 비교한다.

첫 분석 대상은 10–15초와 20–25초다. 시작 기준으로 두 구간 모두 BG 411개/화면, 변경 map 행 0, OBJ는 31.91·28.57개/화면이다. 출력·최종 ACK는 87.02·18.37ms, 20B E8 조회는 251.45·11.79회/화면이다. 발행한 타일 계획도 19.19·1.48개/화면으로 다르다. 이 작업량 차이와 캐시 적중을 맞춘 뒤 실제 tile 준비→첫 유효 E8→65816 수락→DMA→표시 ACK를 대조한다. 현재 로그에는 각 조회의 대기 사유와 화면별 VBlank가 없어 원인별 비용은 미확정이다.

### MMC821 무입력 데모의 타일 공급과 E8 조회

MMC820 실기에서 10–15초의 새 타일은 화면당 598.13B, 20–25초는 31.43B였다. 실기 로그에는 개별 descriptor 시각이 없어 같은 ROM의 무입력 장면을 따로 채집했다. 각 여섯 화면의 처음 둘로 양쪽 표시 뱅크를 채운 뒤 뒤의 넷을 비교했다. 원본 NES 네 프레임 간격 표본이므로 실기에서 실제 선택한 세대·시작 위상과는 차이가 있을 수 있다.

최종 타일 묶음의 token을 기준으로 FPGA 준비, 첫 유효 E8 반환, ARM E1 발행, 65816 수락·검사 완료, VRAM DMA 시작, 표시 ACK를 이었다. 원본 PPU fetch와 보드 collector RTL에서 입력과 캐시 내용을 구했고, MMC820 전체 ARM 링크 및 815R 65816 ROM을 재생했다. SPI 거래별 평균은 실기 84MHz 카운터로 보정했다. Cortex-M4 CPI 2, 타일 생산·CDC 시간, 기존 여덟 NES 프레임의 ROM 허가표는 모델이다. 보드의 bulk206 RTL 단독 시험에서 다음 OBJ 계획이 직전 16B BG를 공개하는 데 0.596µs, OBJ END에서 두 번째 뱅크 봉인까지 0.145µs가 걸렸다. 이전 token을 소비한 뒤에만 다음 descriptor가 head에 보였고 STOP으로 소유권이 사라졌다.

| 비교한 작업량 | FPGA 준비 → 첫 유효 E8 | E8 → 65816 패킷 읽기 시작 | 읽기 → 수락·검사 완료 | 수락 → VRAM DMA 시작 | DMA 시작 → 최종 ACK |
|---|---:|---:|---:|---:|---:|
| 10–15초, 원본 668·676을 1대5 가중 | 0.48ms | 0.16–0.17ms | 0.60ms | 20.56–20.70ms | 0.83ms |
| 20–25초, 원본 1328 | 1.37ms | 0.19ms | 0.62–0.63ms | 10.39–10.46ms | 0.77ms |

두 행 모두 신규 BG 0, OBJ 2, ARM resident 적중 258, 변경 map 0, FPGA OBJ 바이트 적중 32·미스 0, 고정 BG 16B 포함 80B다. 가중치는 작업량 비교에만 썼다. 실제 한 화면씩 직접 맞는 676·1332도 신규 OBJ 0·resident 적중 260·고정 BG 16B였다. 마지막 묶음의 DMA 시작부터 ACK에는 나머지 출력 처리도 들어간다.

원본 712의 새 OBJ는 36개다. ROM으로 떨어진 184바이트 중 160개는 다른 CHR 태그가 같은 위치에 있었고 24개는 해당 바이트의 유효 비트가 꺼져 있었다. 첫 계획 발행부터 마지막 묶음 준비까지 82.52–82.78ms, 이후 첫 유효 E8까지 0.21ms였다. ROM 응답 지연은 유지하고 허가 대기만 제거하면 네 화면 표시 합이 양 위상 모두 20→15 VBlank, 마지막 ACK가 82.93–82.95ms 앞당겨졌다. 빈 E8만 2B 상당으로 단축하면 20→20이고 712의 조회는 266–268→426–428회로 늘었다.

후반 42.7초 부근 네 화면에서도 같은 실험을 했다. 2568–2580 중 세 화면에 총 166바이트 미스가 있었지만, 허가 대기 제거와 빈 E8 단축 모두 표시 합은 17→17 VBlank였다. 원본 2572의 마지막 타일 수락→SEAL 읽기는 9.79–9.95ms, SEAL→타일 DMA 시작은 18.04–18.50ms였다. 45초 부근의 네 화면은 애초에 모두 캐시 적중이며 세 조건 모두 14 VBlank였다. 후반 구간은 확정 패킷 발행·수락과 직전 VBlank의 DMA 기회를 같이 봐야 한다. 두 실기 집계창의 FPS는 후속 보드에서 다시 측정한다.

712에서 첫 E9 이후 마지막 descriptor 공개 전 빈 E8은 두 위상 모두 238회·26.15ms였다. 동일한 빈 응답만 2B 상당으로 단축하면 이 거래 시간이 3.14–3.15ms가 되어도 화면은 8 VBlank였다. 이 비용 상당 부분은 공급 대기와 겹친다. `supply`는 ROM 허가 대기 제거의 상한 시험이고, `poll`은 유효 응답·변경 상태에 원래 응답과 검사를 그대로 제공하는 시간 대조군이다.

같은 128개 위치에 상·하위 CHR 태그를 XOR해 배치한 캐시 모델도 비교했다. 두 초기 화면의 캐시는 기준과 같게 만들고 이후 채집·조회에 같은 함수를 썼다. 모든 적중 바이트를 원본 ROM과 대조했다. 11.8초 네 화면의 미스 496개와 42.7초의 166개가 모두 사라졌다. 전자는 두 위상 모두 20→15 VBlank, 후자는 17→17이었다. 반면 11.1초·51.9초 표본에 각각 새 미스 100개·32개가 생겼다. 단일 XOR 배치를 보드에 채택하지 않았다. 기존 capture 적중을 보존하는 방식이 비교 대상이다.

재현은 `capture_nes_mask820.py --frames`로 각 시작점(660·700·1320·1440·2440·2560·2700·2860·3110)에서 4프레임 간격 여섯 장면을 수집하고, FLOAT 래퍼의 `replay_nes_mask820.py`로 geometry를 만든다. `prepare_nes_tile821.py <RTL 출력> <캡처> <ROM> <link820b/src> <새 폴더>`로 작업량을 만든다. `replay_nes_tile821.py <자료 루트> <구간 이름> <base|poll|supply|fold> <1|2> <추적 루트> <실행 이름> <MMC820 budget 로그>`는 816 위상 1의 서비스 Lua와 service509 ROM 허가표를 사용한다. 재생별 최종 token의 절대 시각, 위상별 조건 비교와 실기 로그 해시를 보존했다. ### MMC822 충돌 OBJ 공급과 일반 출력 선행 발행

일차 캐시의 저장 위치와 조회 순서를 유지하고, 사용하지 않는 RAM 포트 시간에 OBJ 바이트를 같은 뱅크의 빈 위치 또는 보조 사본 위치에 한 번 더 저장했다. 충돌하면 원래 캡처·조회를 먼저 처리한다. 이전 적중이 사라지면 실패하도록 설정한 Questa 재생에서 9개 구간 54개 원본 화면의 OBJ 응답을 ROM 바이트·주소·세대와 대조했다. 슬롯 반환 및 STOP 뒤에는 옛 세대의 적중이 차단됐다. 712에서 기존 200B 적중과 추가 184B 적중으로 요청 384B를 공급했다. PSRAM 허가 한 번에 두 바이트를 받은 대조군에서는 712의 8 VBlank가 그대로였다.

일반 출력은 BG 계획에서 확정된 스크롤과 영 패딩을 먼저 발행했다. 짝수 길이 테이블은 종단 뒤 첫 패딩 1B를 같은 패킷에 넣고, 나머지를 기존 고정값 채우기로 보낸다. B는 선행 발행이 끝나면 마지막 긴 map 반환을 동기적으로 기다리는 조건을 해제한다. 실제 ARM 전체 링크는 212,968/212,992B다. 두 시작 위상에서 같은 65816의 PPU DMA와 표시 ACK를 기록했다. 아래 간격은 네 화면의 VBlank 합이며 ACK 차이는 MMC820 대비 ms다. 음수는 앞당겨진 시각이다.

|---|---:|---:|---:|---:|
| MMC820 | 20 | 기준 | 17 | 기준 |
| OBJ 공급 | 15 | −82.948 / −82.931 | 17 | 0.000 / −0.046 |
| 일반 출력 B | 20 | +0.227 / +0.229 | 18 | +15.779 / +15.766 |
| 결합 B | 15 | −82.987 / −82.980 | 18 | +15.779 / +15.750 |

결합 B에서 2572의 SEAL 수락은 같은 프레임의 207/200선에서 152/150선으로 이동했다. 두 위상 모두 마지막 OBJ DMA가 VBlank 45의 229선에서 VBlank 44의 226선으로 앞당겨졌다. 2572는 4→3회였지만 2576·2580에서 각각 1,280B map이 SEAL 뒤까지 남아 두 화면이 5→6회·4→5회가 됐다. 상속 map 조건을 둔 C는 2576을 5회로, 분할 OBJ에선 기존 map 대기를 유지하는 E는 2580을 4회로 각각 회복했다. C와 E 모두 후반 합은 17회이며 ARM Flash 한도를 4B·200B 초과했다.

Quartus Lite 전체 보드에서 사본 조회용 주소와 세대 레지스터까지 따로 둔 첫 회로는 970/963 LAB였다. 최종 회로는 외부 plan이 바이트 응답까지 보유하는 주소·세대를 사용했다. MMC820→후보의 LE는 15,335→15,278, LAB는 962/963, M9K는 56/56이다. 최소 setup은 +0.553→+0.497ns, hold는 +0.143→+0.152ns이며 recovery·removal·pulse width도 양수다.

재현에는 `prepare_nes_mirror822.py <추적 루트> --held`와 FLOAT 래퍼 안의 `test_nes_mirror822.py <추적 루트> <nes-output822> <nes-tile821> <모험도4 ROM> --held`를 사용한다. 기본 레지스터 모드를 먼저 실행해 두 결과를 대조한다. 저장된 적중 목록을 `replay_nes_output822.py`의 `mirror`·`jointmirror`에, 기본 캐시를 `ordinary`에 적용한다. `prepare_nes_output822.py`로 만든 후보별 패치를 MMC820 ARM에 전체 링크한다. 재생은 MMC820 실기 SPI 비용, CPI 2, 기존 ROM 허가 일정을 사용한다. 각 재생 여섯 화면의 RGB·map·기대 데이터·색 데이터를 MMC820과 바이트 단위로 대조한다. 캐시 RTL과 ARM·65816 일정은 별도로 재생했다. 상속된 오른쪽 map과 마지막 OBJ descriptor의 유효성·길이를 함께 확인한 결합 F에서도 후반은 양 위상 모두 4·3·5·5 VBlank였다. 2580 ACK는 0.845/0.884ms 빨라졌으나 표시 합은 17회, 링크는 213,012B로 한도보다 20B 컸다.

### MMC823에서 2576·2580의 map DMA와 일반 출력 순서

오른쪽 map은 2,048에서 시작하는 1,472B이고, MMC822B에서 SEAL 뒤까지 남은 부분은 2,240–3,519의 1,280B다. 각 전송에서 큐의 패킷 번호, ARM의 E1 시작, 65816 수락·반환, 유휴 DMA의 첫 주소와 마지막 바이트를 연결했다. 일반 출력 전 완료 바이트 수는 첫 팔레트·OAM·section 5 패킷의 SPI 시작 전에 실제 DMA가 끝난 주소들의 합이다. E0의 빈 큐 또는 진행 비트만으로 DMA 완료를 판정하면 같은 구간에서 다른 결과가 나온다.

일반 출력에 credit을 양보시키는 대조군에서는 2572가 3회였고 두 후속 화면의 map이 팔레트·OAM보다 먼저 전송됐지만, 앞서 발행된 스크롤·패딩까지 포함하면 후반 합은 17회였다. 두 위상에서 긴 map을 BG 확정 직후 먼저 발행하면 후반 합이 16회였지만 2580의 대상 1,280B 중 576B만 일반 출력 전에 끝났고 ARM 링크가 44B 초과했다. 별도 이력을 저장해 오른쪽 행을 먼저 발행한 판도 한도를 넘었다.

입력 OBJ 조각이 28개(112B) 이하인 화면에는 기존 스크롤·패딩 발행을 허용했다. 이 수는 발행 순서에 사용하며 OAM 재사용은 기존 뱅크 이력 검사로 결정한다. 긴 map과 큰 OAM이 함께 있으면 BG가 확정된 뒤 map을 묶어 발행하고 첫 일반 패킷을 미룬다. 대상 뱅크에 상속된 map과 일반 팔레트·OAM이 함께 필요한 경우 OBJ 생산·수락·반환을 진행한 뒤 E0에서 최신 반환 identity와 credit을 확인한다. 진행 비트는 제한된 대기를 끝낼 수 있으며, 표시에는 기존 독립 검사와 최종 ACK가 필요하다.

최종 후보 `wire`는 매 패킷마다 256B 버퍼 전체를 지우던 비용도 줄였다. 16B 헤더는 모든 필드를 기록하고, 본문은 전송 길이만큼 복사하거나 0으로 채운다. 이 변경 전 `flush`에서는 위상 2의 2572가 247선 수평 클록 46에 표시를 검사해 한 VBlank 늦었다. 최종 링크의 후반 결과는 다음과 같다.

|---|---:|---:|---:|---:|---:|---:|
| MMC820 양 위상 | 4 | 4 | 5 | 4 | 17 VBlank | 기준 |
| 823 wire 위상 1 | 4 | 3 | 5 | 4 | 16 VBlank | 16.718ms 단축 |
| 823 wire 위상 2 | 4 | 3 | 5 | 4 | 16 VBlank | 16.724ms 단축 |

두 위상 모두 2576에서는 오프셋 2,048에서 1,472B 한 번, 2580에서는 2,048에서 768B와 2,816에서 704B로 나누어 DMA했다. 두 경우 모두 첫 일반 E1의 SPI 시작 전에 오프셋 2,240–3,519 전체를 전송했다. 같은 작업량에서 2576·2580의 표시 간격은 MMC820과 같고 2572에서 한 VBlank를 줄였다.

두 구간은 MMC820과 동일한 700·2560번 원본 화면에서 부팅 일정을 재생한 뒤 708–720·2568–2580번 네 화면씩을 집계한다. 각 링크의 RGB·색·map 결과를 6화면 모두 기준과 대조했다. 65816과 FPGA 이미지는 MMC822 검증 때와 같다. 패드 로그 포맷을 같은 문자열로 조립해 Flash를 확보했고, 256개 입력 마스크와 1–1,024B 버퍼에서 이전 포맷과 출력 바이트·반환값이 일치했다.

양 위상 모두 초반 네 간격은 MMC820의 4·8·4·4에서 4·4·3·4로 줄었다. 712의 OBJ 공급 개선을 유지했고 720의 마지막 ACK는 82.963/82.968ms 앞당겨졌다. ARM 전체 링크는 212,940/212,992B다. 재현은 `prepare_nes_output823.py wire`로 만든 패치를 MMC820에 전체 링크하고 `run_nes_output823.py wire <추적 루트> <MMC820 실기 budget 로그>`를 실행한다. `check_nes_output823.py`의 `--generation 910`은 OBJ 반환 후 첫 일반 패킷 직전 STOP·E0 CRC 오류·올바른 CRC를 가진 잘못된 반환 번호를 각각 주입한다. [두 위상 DMA·ACK와 오류 주입 결과](../../analysis/output823-results.json)

### MMC824 모험도 4 무입력 60초 실기 전달본

MMC823 `wire` ARM에서 설치·ROM·로그 이름을 824로 바꿔 다시 링크했다. 최종 이미지는 212,940B로 Flash 여유가 52B다. 검증한 822held 보드의 기존 Quartus Lite FIT 데이터에서 SOF를 만들고, 내장 815R 프로그램, BI3 복원 바이트와 프로그래머 전송을 확인했다. 재생한 두 위상 모두 712·2572는 각각 4·3 VBlank였다. 후반 네 간격은 4·3·5·4로 합계 16회였고, 2580 최종 ACK는 MMC820보다 16.718/16.724ms 빨랐다.

최종 ARM에서 원본 ROM 수락·손상 ROM 거절, 60초 종료 경계, STOP·CRC·반환 identity 오류 차단, base 복구와 메뉴 해제를 검증했다. 65816의 정상 부팅·손상 거절과 행 단위 STOP도 통과했다. ZIP은 MMC820의 base·메뉴·eGBC 파일을 유지하며 실기 ROM은 사용자가 같은 원본을 복사한다. [설치와 로그 수거](../nes-mmc824-trial.ko.md) · [최종 링크별 재생·보드·설치본 해시](../../analysis/trial824-package.json)

### MMC824 실기 중단과 MMC825 수정

MMC824는 ROM 393,216B를 적재·대조하고 화면 472개를 표시했다. 마지막 표시는 25.38초, 표시 시작부터 STOP까지는 26.01초였으며 3.34초 후 메뉴 준비를 완료했다. 수신·영상·ROM 오류는 0이고 출력 큐와 plan 오류는 각각 5였다. MMC819에서는 같은 시각에 수신 오류 21이 기록됐다. MMC824의 5–40초 표시 카운터 381은 중간까지의 집계이며 40–55초에는 진입하지 못했다.

실제 모험도 4 ROM에서 타이틀 1500·1504와 스테이지 데모의 1557·1561·1565·1569번 화면을 캡처했다. 822held 수집·캐시 RTL의 결과를 연결한 MMC824 ARM·815R 65816 재생은 두 시작 위상 모두 첫 전환 화면 1557에서 중단됐다. ARM이 완료를 확인할 BG 타일 번호는 86이었는데, 192B map 세 개 뒤에 스크롤과 패딩을 발행해 발행 번호가 91이 됐다. 그 시점에는 90까지 이미 반환됐지만 타일 번호는 완료를 조회할 수 있는 네 패킷 범위 밖이었다. 재생에서 큐 오류 5, 계획 오류 5, 계획 발행 6, 미반환 1이 실기와 일치했다. 별도 카운터 재생에서는 실기의 절대 발행·반환 번호 4,344·4,343도 일치했다.

MMC822의 발행 순서 변경에서 MMC813의 미확인 타일 보호 조건이 빠졌다. MMC825는 ARM의 BG 완료 콜백에 이 조건을 복원해 타일 확인이 남으면 스크롤과 패딩을 기존 일반 출력 경로로 넘긴다. 잘못된 반환 번호는 계속 거절한다. 824의 기존 두 위상 성능 시험은 타이틀과 데모를 각각 이미 진행 중인 상태로 재생했기에 이 전환을 누락했다. 전달본 검증에 여섯 화면을 이어서 재생하는 시험과 네 패킷 경계 시험을 추가했다. [MMC825 설치 안내](../nes-mmc825-trial.ko.md) · [실기 로그 해시와 원인·수정 대조](../../analysis/trial825-package.json)

MMC825는 두 위상 모두 전환 재생의 여섯 화면을 끝까지 표시했고 RGB·map·색·표시 기대 데이터가 MMC820과 일치했다. 여섯 번째 전환 화면의 최종 ACK는 MMC820보다 위상 1에서 0.004ms, 위상 2에서 16.652ms 늦었다. 기존 성능 구간의 712·2572는 4·3 VBlank, 후반 합은 16 VBlank, 마지막 ACK 단축은 16.718/16.724ms였다. 최종 ARM은 212,944B로 48B 여유가 있고 보드와 65816 이미지는 MMC824와 동일하다.

### MMC825 실기 결과

MMC820과 같은 일본판 모험도 4 무입력 데모를 실행했다. MMC825는 1,034화면을 표시했고 마지막 표시는 59.95초였다. 표시 시작 60.37초 후 STOP, 그 뒤 3.25초에 메뉴 준비를 마쳤으며 사용자가 메뉴 복귀를 확인했다. 수신 ABORT·출력 큐 오류·ROM 오류·전송 CRC 오류는 모두 0이었다. 종료 시 수신 COMMIT 1,035건 중 표시가 끝난 1,034건을 집계했다.

| 표시 완료 구간 | MMC820 화면 수 / FPS | MMC825 화면 수 / FPS | 화면당 출력·최종 ACK, MMC820 → MMC825 |
|---|---:|---:|---:|
| 5–40초 | 543 / 15.51 | 597 / 17.06 | 45.31 → 39.60ms |
| 40–55초 | 243 / 16.20 | 270 / 18.00 | 44.44 → 38.19ms |
| 5–55초 합계 | 786 / 15.72 | 867 / 17.34 | 45.04 → 39.16ms |

표시 FPS는 완료 시각 기준이다. 단계 시간은 프레임 시작 시각으로 분류한 구간의 완료 수로 나눈 평균이다. 같은 50초에 81화면(+10.3%)을 더 표시했다. 두 판 각 한 번의 실기 비교이며, 개별 DMA나 VBlank의 기여도는 해당 로그에서 분리할 수 없다. [구간별 집계와 원본 로그 해시](../../analysis/hardware825-vs820.json)

## 후속작업

다음 성능 비교의 실기 기준은 MMC825다. 같은 무입력 동선과 표시 완료 구간을 사용하고, 남은 출력·최종 ACK 39.16ms를 추적할 때 데모 전환과 미확인 타일 보호 검사를 유지한다. 장시간 SMB3는 MMC817을 유지한다.

무입력 시험은 `probe_nes_opening818.py <ROM> <Mesen.exe> <새 폴더>`로 두 번 재생하고 `--hide-sprites`로 배경 단독 대조를 만든다. `prepare_nes_opening818.py arm --edition 818|819`는 MMC816 ARM용 패치를, `board --temp <추적 루트>`는 수직 미러링 보드 소스를 만든다. `check_nes_opening818.py`는 원본 ROM·교차 ROM·손상 ROM에 대해 링크된 ARM의 파일 수락 여부를 확인한다. `core_nes_opening818.py <보드 폴더> <새 폴더> <캡틴 ROM> <타카하시 ROM>`은 기존 FLOAT 래퍼 안에서 두 게임을 순서대로 부팅한다. 설치 ZIP과 증거는 `package_nes_opening818.py <추적 루트>`로 묶는다.

전달본은 `prepare_nes_trial816.py clients`에서 만든 패치를 각각 MMC813·814 ARM에 전체 링크한다. 같은 스크립트의 `board`, `fit`에 각 판 번호와 804 원본이 있는 임시 루트를 지정하고 `package_nes_trial704.py image`로 BI3를 생성한다. `run_nes_output809.ps1 -Variant 816|817 -Phase 1|2`를 각 최종 링크에 실행한다. 행 STOP, 부팅·직접 종료, ARM의 모드·메뉴·복원 검사 산출물을 준비한 뒤 `package_nes_trial816.py <추적 루트>`로 검증된 파일을 묶는다.

재현 시 `tools/prepare_nes_output815.py arm|client <새 폴더>`를 사용한다. ARM 대조군은 MMC813 링크에 패치를 적용해 기존 `build_nes_mmc479_arm.ps1`로 링크한다. `run_nes_output809.ps1 -Variant 815|815R -Phase 1|2`에 기존 ROM과 추적 루트를 지정한다. `check_nes_raw815.py`는 MMC813 위상 1의 패킷열, 815R client와 Mesen을 사용한다. `check_nes_longrun694_boot.py`로 기준·후보 ROM의 복원과 손상 거부를 실행한다. `analyze_nes_output815.py --downloads <실기 로그 폴더> --traces <추적 루트> --output <결과 JSON>`으로 대조한다.
