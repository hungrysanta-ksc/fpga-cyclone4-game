## 목표

PR162가 master `71f50d1`에 병합된 시점의 MMC807·808을 실기 기준으로 삼는다. 첫 레벨에서 작업량이 가까운 구간을 찾고, ARM의 SPI 응답 검사 비용을 줄였을 때 연속 표시 간격과 마지막 ACK가 함께 앞당겨지는지 확인한다.

## 작업내용

- 실기 MMC805·807의 5–55초를 5초씩 나눴다. 같은 시간대에서 화면당 변경 map·OBJ·BG가 각각 MMC805 대비 20% 이내인 구간을 골랐다. 20–25초의 평균 출력·최종 ACK는 30.71→30.00ms, 25–30초는 33.23→26.38ms였다. 각 판의 플레이 횟수는 한 번이고 실기 로그의 시간 단위는 10ms다.
- ARM 후보 809는 입력·plan·큐 상태의 CRC-8을 같은 다항식으로 한 바이트씩 계산한다. 매 응답의 전체 검사 범위와 세대·토큰·실제 소비 검사를 유지한다. 60초판과 장시간판을 각각 전체 링크하고, CRC 바이트 전이 256종과 길이 0–246B의 9개 벡터를 두 최종 ARM에서 실행했다.
- 일정 비교에는 60초판을 사용했다. 같은 ROM·입력 905–970·65816·SPI 드라이버 비용·IRQ·ROM 허가 구간을 두고 시작 위상을 바꿔 대조군과 후보를 각각 재생했다. ARM·65816은 링크된 코드를 실행한다. ARM은 CPI 2, ROM 경쟁은 기록한 허가 일정의 반복으로 모델링한다. 실기와 map·OBJ가 비슷한 캡처는 949와 950이다. BG까지 같은 실기 화면은 특정할 수 없다.
- 810에서는 BG 행이 모두 확정된 뒤 scroll과 0 패딩을 보내고, 긴 map을 수락한 경우 기존 E0 응답의 DMA 진행 비트를 확인한 뒤 OAM을 발행했다. FPGA의 진행 비트는 발행 순서에만 사용한다. 65816의 독립 검사와 표시 이후 최종 ACK는 기존 코드에서 실행한다.
- 959는 마지막 OBJ 슬롯이 확정되고 남은 계획과 END가 E9 한 패킷에 들어갈 때 먼저 FPGA로 보냈다. ARM은 ROM 공급과 동시에 raw 타일을 변환한다. 원본을 쓰는 동안 다음 입력이 덮어쓸 수 없도록 소유권을 검사했다. 958의 SEAL 뒤에는 다음 입력의 CRC·token을 확인하고 D2를 반환한다. 후속 COMMIT에는 직전 표시의 최종 ACK와 retire가 필요하다.

### MMC811·812 최종 링크와 복구 시험

MMC811은 810I의 설치 경로와 로그 이름을 바꾼 최종 링크다. MMC812는 장시간판의 직접 종료 입력과 시간 제한 처리까지 포함해, 각 판에 실제 내장되는 65816 이미지로 905–970을 다시 재생했다. 기준은 같은 시작 시각·ROM 허가 일정의 MMC807이다.

단순히 이름만 바꾼 장시간판은 위상 1에서 951의 긴 map 수락 후 E0 응답을 25회(최초 확인 포함) 받았다. 마지막 응답까지 DMA 진행 비트가 서지 않았고 다음 OAM을 수락한 시점은 235선이었다. 앞선 VBlank에서 BG 16B와 map 192B만 전송했고 나머지 map 1,344B는 SEAL 뒤로 밀렸다. 위상 2에서는 960의 DMA 검사에서 중단됐다. 패킷 시각을 고정한 별도 65816 재생에서 직전 55개 표시 시각이 일치했고, 192B map 명령에서 CPU가 읽은 선은 252, 관측기가 기록한 선은 253이었다. 기존 252선 검사를 유지하고 이 링크를 제외했다.

장시간판은 긴 map을 수락한 뒤 유효한 E0 진행 응답을 기다리는 상한만 24회에서 32회로 늘렸다. 56회 후보도 951·959·970 마감을 지켰지만 960의 위상 2 표시 간격이 5 VBlank였다. 선택한 32회 후보는 두 위상에서 4회였고 951→970 경과 시간이 모두 짧아졌다. 56회 후보는 위상 1의 970 ACK가 선택판보다 약 50ms 빨랐다.

### MMC811·812 실기에서 확인된 1-1 진입 종료

기존 ARM에서 타일 완료를 추적하는 동안 map 패킷 세 개를 보낸 다음, 810의 스크롤·패딩 두 패킷을 먼저 보내는 순서를 실행했다. FPGA가 타일과 앞쪽 map을 소비해 큐 자리는 비어도 ARM이 보관한 타일 번호는 최신 송신보다 다섯 패킷 뒤로 밀린다. 마지막 OBJ와 END를 발행할 때 `nes_window184_through`의 유효 거리 4 검사가 E0 재조회 전에 중단했고, 두 실기 로그의 송신·반환·오류 값이 그대로 나왔다. 실기 로그에는 당시 타일 번호와 마지막 E0 원문이 없어, 같은 오류 번호를 쓰는 E0 카운터 불일치까지 배제할 수는 없다.

MMC813·814는 확인할 타일 완료가 남아 있을 때 스크롤·패딩을 기존 일반 발행 순서로 보낸다. 타일 완료 확인, 표시 뒤 최종 ACK와 STOP 검사는 유지한다. 수정한 두 ARM 모두 같은 입력에서 기존 타일 완료를 확인하고 다음 타일과 OBJ·END 계획을 발행했다. 16비트 카운터 순환도 통과했고 손상된 E0 카운터는 계속 거부했다. ARM은 각각 212,988·212,948B로 Flash 여유가 4·44B다.

두 최종 링크와 각 판의 65816을 두 위상에서 재생했다. 네 조합 모두 66화면의 RGB·map·section 5 및 최종 ACK 검사를 통과했다. 951은 BG 16B·map 1,536B 선행 DMA 후 236선에 공개됐고 959는 2 VBlank였다. 970 최종 ACK는 MMC807 대비 MMC813에서 50.633·83.207ms, MMC814에서 83.922·99.846ms 빨랐다. 951→970 표시 간격 합은 MMC807의 57·58회에 비해 MMC813이 59·58회, MMC814가 57·57회였다. 60초판 위상 1의 밀집 구간은 32.558ms 늘었다. 이번 전달본의 우선 판정은 실기 1-1 진입과 복구다.

재현은 `prepare_nes_prefix813.py`로 MMC811·812 최종 소스에 적용할 패치를 만들고 기존 전체 링커로 `nes-prefix813/link813`, `link814`를 빌드한다. `check_nes_prefix813.py <src> <결과 JSON>`을 기존 링크에, 같은 명령에 `--fixed`를 붙여 수정 링크에 실행한다. 네 조합의 `run_nes_output809.ps1 -Variant 813|814 -Phase 1|2`와 이전 절의 모드별 STOP·복구 검사를 마친 뒤 `package_nes_prefix813.py <재생 폴더의 상위 경로>`로 ZIP의 두 펌웨어와 기준 보드 파일을 대조한다.
