## 목표

MMC763을 실기 기준으로 유지한다. 25–30초에 MMC767의 화면당 출력·최종 ACK가 약 8.14ms 늘어난 이유를 찾고, 다음 변경이 실제 표시 시각을 앞당길 조건을 정한다.

## 작업내용

- PR158 병합 `fb7f104`에서 두 성공 회차의 25–30초 bin을 화면 시작 수로 정규화했다. 10ms tick 합으로 구한 구간 평균과 84MHz DWT의 전체 실행 합계를 구분했다.
- 905–957의 기존 캡처는 OBJ 슬롯 범위가 최대 94다. 같은 첫 레벨 캡처를 970까지 연장하고, map 64B 그룹 8개·OBJ 범위 126인 969를 비교 화면으로 골랐다. 969와 보조 표본 961·967에서는 원본 ARM planner의 map_dirty 비트 수를 직전 화면 대비 최종 map 차이와 대조했다. 969의 BG 범위는 147이고 실제 OBJ tile plan은 4개다. 실기 구간의 BG 약 556·OBJ tile plan 평균 7.37/8.41개와 차이가 있어 실제 특정 화면을 식별할 수는 없다.
- 두 배포판의 링크된 ARM과 정적 65816을 리셋부터 같은 입력·시작 위상·SPI 비용·ROM 허가 일정으로 실행했다. 957–970의 압축 입력은 보드 RTL로 생성했다. 957에서 기존 전송 바이트와 일치하는지 검사하고, 새 캡처의 OBJ 캐시는 기록한 PPU fetch로 구성했다. 65816의 수락·DMA·최종 ACK를 직접 기록했다. ARM CPI·IRQ 경계·SPI 드라이버와 ROM 허가 일정은 재생 모델이다.
- MMC767에만 있는 map DMA 대기를 969 한 화면에서만 건너뛰는 대조를 추가했다. 두 실행 모두 직전 968 최종 ACK까지 원본과 일치해야 한다. 65816의 map·타일·CGRAM·OAM·receipt 검사와 VBlank 공개 조건은 그대로 실행한다.

## 후속작업

1. MMC763을 성능 기준으로 유지한다. 다음 25–30초 실기 계측에서 **출력 안의 E0/E8 조회를 진행 유무·사유별로** 세고, SEAL 발행·65816 수락·업로드 시작·최종 ACK의 시각 또는 VBlank 번호를 같은 화면에 묶는다. 실기에서 추가 조회가 어느 DMA나 표시 마감을 실제로 넘기는지 판별한다.
2. 먼저 496B 선행 DMA 기회를 유지한 채 같은 상태를 다시 읽는 E0 조회를 줄이는 후보를 시험한다. E8은 descriptor가 실제로 준비된 시각과 비교한다. 슬롯 반환·DMA 진행·최종 ACK는 각각 기존 독립 검사를 통과해야 한다. STOP과 새 패킷 우선·메뉴 복귀도 유지한다.
3. 후보는 두 시작 위상의 **표시 간격과 최종 ACK**를 함께 비교하고 실기는 기존 5–40초·40–55초 동선으로 판정한다. 중간 성의 PPU 162선 dot 0 읽기 마감은 별도 안정성 항목으로 보존한다.

## 769 조회 간격 시험과 실기 계측

실기 기준은 MMC763이다. MMC767에서 496B를 선행 전송한 969번 화면(map 8그룹, OBJ 범위 126, BG 147)을 같은 ARM·SPI·IRQ·ROM 달력에 재생했다. 769는 큐 반환을 검사하고 map 진행이 없을 때 기존 입력·STOP 서비스 콜백 한 번을 추가한 뒤 E0를 다시 읽는다. 아래 E0는 출력 함수 진입부터 SEAL SPI 발행 전까지이며, quiet는 직전 E0 이후 retired와 map 진행 비트가 모두 같은 횟수다.

## MMC770–772 실기 회수

770·771 모두 384 KiB 적재·readback, 60초 실행, STOP·base 복구·메뉴 준비를 통과했고 사용자가 메뉴 표시를 확인했다. 첫 레벨의 5–40초 완료 화면은 652→672장(18.63→19.20fps), 40–55초는 283→264장(18.87→17.60fps)이다. 5–55초 합계는 935→936장(18.70→18.72fps)이다. 772 장시간판의 첫 두 구간은 659·314장이고 첫 50초 합계는 19.46fps다. 772의 budget 작업량 bin은 60초 단위로 순환하므로 초기 25–30초 BIN을 마지막 epoch의 b05와 결합하지 않는다.

25–30초에 시작한 화면은 770/771 각각 88/84장이고, 모두 세대와 VBlank 표식이 유효했다. 누락은 0, 조회 카운터 포화는 2/1장으로 횟수 평균에서 제외했다. 같은 b05의 화면 수·map·OBJ·BG 합은 두 판 모두 BIN과 정확히 일치했다. 출력·최종 ACK의 10ms tick 평균은 36.25→36.67ms(+0.42ms)다. 지난 763→767의 +8.14ms와 비교할 때 이번 OBJ 범위 평균은 20.17→74.70으로 다르고, 두 판에 NMI·SPI 계측 비용도 포함된다.

771 세대 601은 map 31그룹·OBJ 범위 64이며 유일하게 SEAL 뒤 첫 DMA까지 2 VBlank였다. 화면 전체 ACK 간격은 6 VBlank, 출력 중 quiet E0 87회다. 개별 조회 시각·ROM 허가·SEAL의 주사선은 수집되지 않아 어느 조회가 마감을 넘겼는지는 확정할 수 없다. 770과 771에 map·OBJ·BG가 모두 일치하는 표본은 없다. 첫 행 및 포화 행을 제외하고 map/OBJ/BG 차이 1/4/8 이내에서 작업량 차이 순으로 중복 없이 맞춘 5쌍은 모두 첫 DMA까지 1 VBlank였다. 평균 ACK 간격은 3.4→3.8 VBlank, 출력 quiet E0는 54.2→55.0회, E8은 36.0→48.4회였다. 더 엄격한 0/2/8 이내의 2쌍에서는 ACK 간격이 3.5→3.5다. 조회 빈도를 일괄 조정하기보다 작업량을 고정한 재생에서 직전 ACK→현재 SEAL의 마지막 descriptor 준비·E8 FINISH·수락 시각을 먼저 대조한다.

772는 DISPLAY_NEXT→DISPLAY_STOPPED 815.660초, 마지막 표시 815.27초·세대 16557, 15,863장 표시, 입력 COMMIT 15,864회·abort 0회였다. 사용자가 같은 중간 성의 장면을 여러 번 진행한 뒤 종료를 관찰했다. ROM 오류 2와 동결 PPU 64비트 `51000a0000220800`가 764·766과 정확히 같다(162선 dot 0, 렌더링 중 PPUDATA 지연 읽기, sprite_fetch 0). 상세 물리 주소 문맥은 772에 없다. 766에서만 실제 요청/필요 주소 0x204082 일치, busy=1, response=0이 기록됐다. 772에서 같은 주소·중재 순서라고 단정할 수 없다. STOP·base 복구·메뉴 준비는 성공했다. 772의 25–30초 BIN은 정상 표식 97장이고 프리즈 직전은 수집 범위 밖이다. 다음 안정성 시험은 직전 주사선 끝부터 주소·CHR bank 확정, PPU 요청 수락과 PSRAM 응답을 같은 파형에 놓고 162:0 샘플을 재현한다.
