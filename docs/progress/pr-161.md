## 목표

MMC763을 실기 기준으로 유지하고, 동일한 작업량에서 직전 표시 ACK부터 SEAL 수락까지 지연이 어디서 생기는지 찾는다.

## 작업내용

PR159의 969 재생을 두 시작 위상에서 다시 분석했다. 마지막 32 B OBJ의 세대·token·목적지·길이를 E8 응답과 E1 패킷에서 맞추고 65816의 수락, SEAL 발행·수락·최종 ACK를 연결했다. 두 판의 map 및 최종 RGB 해시가 같다. 시간은 연속 ARM·65816 재생 모델의 ms다.

| 구간 | 위상 1 MMC763 / 767 | 위상 2 MMC763 / 767 |
|---|---:|---:|
| 968 최종 ACK → 마지막 OBJ를 처음 관측한 E8 응답 완료 | 30.867 / 34.689 | 31.389 / 34.803 |
| 해당 E8 응답 → OBJ 발행 | 0.051 / 0.049 | 0.049 / 0.049 |
| OBJ 수락 → SEAL 발행 | 4.787 / 4.789 | 5.587 / 4.749 |
| SEAL 수락 → 최종 ACK | 13.825 / 9.569 | 12.332 / 9.513 |

## 성과

두 위상 모두 MMC767에서 마지막 OBJ가 ARM에 보이는 시점까지의 경과 시간이 3.822 / 3.413 ms 길었다. E8에서 descriptor를 받은 뒤 발행하는 데 걸린 시간은 두 판 모두 약 0.05 ms였다. 첫 성공 조회는 생산 시각의 상한이다. 이 자료만으로 FPGA의 생산 지연과 ARM 조회 지연을 구분할 수 없다. SEAL 뒤에는 MMC767이 각각 4.255 / 2.819 ms를 회복한다. 969는 실기 25–30초와 작업량이 가까운 재생 표본이며 실기 특정 프레임과의 일대일 대응은 미확인이다.

## 후속작업

마지막 OBJ가 있는 뱅크의 생산 완료·해제와 그 전후 E8 조회 시작을 같은 타임라인에서 대조한다. 496 B 선행 DMA, STOP, 독립 검사와 최종 ACK를 유지하고 실제 밀집 구간의 표시 간격으로 후보를 판정한다. 중간 성의 162선 dot 0 프리즈는 별도 재현 대상으로 남는다.

[측정 결과](../../analysis/preseal775.json). PR159에서 생성한 `nes-cost768-{763,767}-p{1,2}-ext` 폴더를 사용해 `python tools/analyze_nes_preseal775.py <재생 상위 경로> analysis/preseal775.json`으로 재현한다.
