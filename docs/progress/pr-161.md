## 목표

MMC763을 실기 기준으로 유지하고, 동일한 작업량에서 직전 표시 ACK부터 SEAL 수락까지 지연이 어디서 생기는지 찾는다.

### 776의 뱅크 준비와 E8 조회

첫 레벨 재생 969는 map 변경 8그룹, OBJ 범위 126, BG 범위 147이었다. 마지막 네 건은 BG 16B(token 158), OBJ 32B(159), OBJ 64B(160), OBJ 32B(161)였다. 수락된 패킷을 원래 시각에 다시 넣어 두 판·두 위상에서 65816의 토큰 쓰기와 0x6050 소비 명령을 기록했다. 각 66화면의 전체 소비 이벤트와 RGB를 원본과 대조했다. 마지막 OBJ의 네 CHR 읽기는 모두 OBJ 캐시에 적중했다.

707D 보드 소스의 staging·토큰 소비·E8 회로 6개 파일을 핀으로 고정했다. 969의 실제 payload와 65816 소비 시각, ARM의 E8 조회 시작을 넣어 슬롯 8의 쓰기 완료, 최종 descriptor가 reader에 보이는 시각, SPI 응답의 CRC·세대·token·주소·길이를 확인했다. 회로 시험 입력은 완성 타일 인터페이스에서 시작한다. ROM·캐시 공급 시각과 SPI 발행은 기존 연속 재생 모델이고, 이 수치는 실기 프로브 측정값이 아니다.

### 776 발행 후보

- 776A는 map 뒤에 대기 플래그를 세우고 확정 ordinary 준비와 기존 E8 조회를 먼저 수행한다. 처음 본 descriptor는 독립 검사 후 스택에 보유하며, 기존 map 진행 대기를 거친 뒤 E1을 보낸다.
- 776B는 기존 map 대기와 발행 순서를 유지한다. OAM 뒤에 앞선 OBJ receipt를 확인한 경우, 같은 횟수 한도에서 다음 STOP 검사와 E8 조회로 직행한다. 잘못된 CRC·같은 token에 다른 내용·STOP·반복 token 횟수 소진에서 새 E1 발행은 0건이었다.
- 별도로 MMC767의 원래 ELF에서 969의 해당 반환 직후 한 번만 같은 분기를 실행해, 부팅부터 쌓인 위상 변화를 분리한다. 이 분리 시험의 시간은 실제 링크 후보의 시간과 구분한다.

### 777의 969 전송 순서 시험

목표 시각은 968 공개 뒤 두 번째 VBlank의 227선 수평 클록 0으로 고정했다. 기준 MMC767과 두 후보의 링크된 ARM에서 OAM 앞 112B·스크롤·240B 테이블의 마지막 쓰기와 planner 종료 후 값을 기록했다. 일반 발행 시각은 E1 거래, 65816 수락과 반환은 해당 sequence의 head load와 ACK로 측정했다. 프로브를 붙인 기준 재생이 원본과 같은지 66화면 전체의 패킷·소비 이벤트·완료 시각을 대조한다.

- 777A는 기존 map 대기가 실제로 걸리는 warm 화면에서 두 대상 뱅크의 ACK 이력을 검사하고, OAM·스크롤·패딩을 먼저 발행한다. 969에서 각 E1은 135·40·21B로 합계 196B다. 1,100B 패딩은 21B로 전송돼도 65816에서 전체 범위를 채운다. 원래 map 대기 마감과 각 E1의 tile·credit·STOP 중재를 사용한다.
- 777B는 같은 뱅크 이력과 확정된 patch가 있는 warm 화면에서 section 5 전체를 후반 map보다 먼저 보낸다. 스크롤·패딩·raw·테이블 순서와 수신 검사를 유지한다.
- 240B 테이블만 발행하는 대조에서는 원래 ARM이 만든 table 바이트와 세대·뱅크를 사용하고 sequence를 다음 순번으로 맞췄다. 65816은 section 5의 첫 오프셋으로 1,505를 받자 0xE0로 거부했다. 968 화면의 RGB와 마지막 표시 이력은 유지됐다. 현재 ABI에서 독립 검사를 유지하려면 앞 범위를 먼저 수락해야 한다.

### 777 고정 도착 대조

MMC767의 968 최종 ACK까지 모든 65816 소비 이벤트를 고정했다. 마지막 map 반환이 E0에 보인 뒤 OAM·스크롤·패딩 196B만 먼저 넣고 나머지 거래 도착 시각은 보존했다. 각 선행 패킷에 기존 E8·E0·E1 시간을 배정하고, 그 구간의 원래 E0/D0 조회는 대체했다. ARM 소프트웨어의 추가 비용과 IRQ 효과는 별도 전체 링크에서 계산한다. 두 위상 모두 패딩까지 227선 전에 소비했고 같은 496B가 226–239선에 전송됐다. 969 표시는 그대로 3 VBlank였고 최종 ACK는 12 / 120 masterclock 늦었다. 970 최종 ACK 차이는 0 / +12,088클록이다.

기준의 496B 마지막 PPU 쓰기 뒤 246선 끝까지는 0.396 / 0.362ms였다. 같은 969 수신기의 SEAL 수락→검사 완료·업로드 진입은 1.631 / 1.633ms다. 이 DMA를 원래 시각까지 실행한 뒤에 검사를 시작하는 순서라면, 나머지 전송과 표시 비용을 0으로 놓아도 약 1.24 / 1.27ms가 모자란다. 기존 191B는 SPI만의 필요조건이었다.

### 777 전체 링크와 두 시작 위상

### 780의 첫 VBlank와 마지막 OBJ 반환

MMC763의 같은 66화면·65816에서 969만 바꾼 소비 대조를 실행했다. 첫 VBlank에 발행을 허용할 map 세 범위와 tile 두 범위의 순서 보존 조합 12개를 두 위상에서 재생했다. 실제 E1 점유 시간·네 큐 credit·직전 bulk 반환을 적용하고, SEAL 발행 전에 원래 496B 전체가 VRAM 기대값과 일치하는지 확인했다. 첫 VBlank의 DMA는 실제 목적지와 마지막 VRAM 쓰기로 셌다. 이 대조의 이른 공급 시각에는 ARM 생산과 다른 SPI 거래의 비용이 빠져 있다.

* map 오프셋 1,216(192B)·2,304(192B)·2,496(64B)를 먼저 묶어 공급하면 BG 16B까지 총 464B가 두 위상에서 첫 VBlank에 들어갔다. VRAM 16,448의 OBJ 32B가 두 번째로 넘어가 검사 종료는 246선보다 1.036 / 0.994ms 늦었다.
* 같은 map 우선 순서에서 BEGIN을 16선(1.016ms) 더 앞당기자 첫 OBJ 32B도 첫 VBlank의 252 / 251선에 DMA를 시작했다. 이때 마지막 두 OBJ까지 일찍 공급한 대조에서는 496B 모두 보존하고 969를 두 번째 VBlank의 237 / 238선에 표시했다. 970 공급 시각을 고정한 대조이므로 970 ACK 개선 근거로 쓸 수 없다.
* 첫 VBlank에서 위의 496B를 모두 보낸 뒤에도 마지막 두 OBJ의 원래 ARM 발행 가능 시각을 적용하면 SEAL 검사 종료가 5.566 / 6.153ms 늦었다. 두 OBJ 발행을 128선(8.129ms) 당기면 검사는 246선 전에 끝나지만 업로드 뒤 `wait169`에 238 / 244선에 진입해 표시가 다시 한 VBlank 밀렸다. 마지막 검사 이후 DMA와 VBlank 대기도 시간 예산에 들어간다. 160선(10.161ms) 선행은 위상 1만 2회를 달성했다. 176선(11.178ms) 선행에서는 마지막 OBJ가 246선보다 13.212 / 12.735ms 먼저 반환됐고, 검사 종료 여유 2.469 / 2.073ms로 두 위상 모두 237 / 238선에 표시했다. 176선은 시험한 충분조건이며 최소값은 확정하지 않았다.

실제 MMC763 ARM에서는 warm 뱅크의 연속 compact OBJ 슬롯이 끊길 때 정상 E9 경로로 확정 묶음을 즉시 발행했다. 원래 65816과 부팅부터 970까지 같은 입력으로 실행했다. 909·960은 두 위상 모두 3회, 969도 3회였다. 밀집 구간(951 표시부터 957 표시까지 여섯 간격)의 평균은 49.943696 → 49.840067ms / 49.942175 → 49.941538ms였다. 970 최종 ACK는 위상 1에서 16.111ms 빨라지고 위상 2에서 33.284ms 늦어졌다. 마지막 OBJ 수락·반환은 두 번째 246선 기준으로 −2.629·−2.058ms / −2.322·−1.750ms였다. ### 781의 입력 선행과 첫 BG·OBJ 공급

실기판 MMC763의 ARM을 세 가지로 전체 링크하고 같은 65816·SPI·IRQ·ROM 일정으로 부팅부터 905–970을 재생했다. A는 현재 화면에서 정상 배정한 BG 슬롯을 HDMA 조립 전의 임시 공간 128B에 색인한다. 재사용할 때 같은 슬롯의 전체 키를 비교하고 HDMA 생성 전에 색인을 지운다. B는 warm 뱅크에서 슬롯 0과 OBJ를 BG 행보다 먼저 계산하고 E9로 발행한다. OAM 순위 계산은 팔레트 생성 전의 CGRAM 임시 공간을 쓴다. C는 B에 더해 이전 SEAL의 반환이 확인되지 않은 동안 기존 7블록 뒤에도 진행 없는 E0 한 번에 다음 입력 한 블록을 받는다. 기존 POP·CRC·token 검사와 이전 표시의 최종 ACK·EA 뒤 COMMIT을 유지한다.

첫 B·C에서는 tile END 대기 중 입력을 해제해 946의 남은 raw 행 변환이 잘못된 주소를 읽었다. 두 위상에서 재현하고, 현재 planner가 입력을 모두 읽고 resident 준비를 완료할 때까지 입력 소유권을 유지하도록 고쳤다. 이 대기에서도 STOP을 확인한다. 954·955의 팔레트·OAM·raw 쓰기 계측은 변경된 tile END와 분리해 기존 필드 전체와 valid를 resident 준비 진입에서 검사한다.

C의 map 1,216 쓰기 완료부터 해당 패킷 함수 진입까지는 두 위상 모두 6.02ms가 남았다. 위상 1은 1,216을 231선에 수락하고 241선에 반환했다. 244–246선에 1,024부터 384B를 DMA해 목표 중 192B가 들어갔다. 다음 2,304 범위 수락은 248선이었다. 위상 2는 2,304·2,496을 이미 226·234선에 반환했지만 3,072 패킷 수락·반환이 235–243선을 썼다. 큐가 빈 246선에 선택한 192B도 3,072 범위였다. 빠른 타일·map 수락만으로 큐가 빌 때의 DMA 선택 순서를 보장할 수 없다.

세 후보 각각 두 위상에서 66화면의 map·VRAM·RGB와 section 5, 969의 일반 패킷·목적지별 타일 바이트를 MMC763과 대조했다. 링크별 최종 ACK 152비트 변조·입력 CRC·STOP·메뉴 복구 검사를 통과했다. A와 C의 969 테이블에 STOP을 넣은 시험은 세 VBlank 동안 추가 DMA·표시·최종 ACK 없이 968 RGB를 보존했다. A/B/C 모두 212,992B Flash 한도를 넘었다. 이번 실행은 실제 펌웨어 명령과 기존 65816을 사용한 공동 시뮬레이션이며 실기 배포 기준은 MMC763이다.

## 후속작업

C의 선행 수신이 효과를 낸 968→969와 C에서 추가 대기가 생긴 959→960을 같은 기준으로 대조한다. 각 E0에서 다음 입력 한 블록을 받는 비용과 이전 화면의 최종 ACK까지 남은 시간을 재서 적용 조건을 좁힌다. 969에서는 2,496 반환 뒤 후속 3,072 발행을 허용하는 시점과 첫 BG·OBJ의 실제 DMA 순서를 따로 시험한다. 909·960, 첫 VBlank의 다섯 목적지, 두 위상 밀집 간격과 970 ACK, Flash 전체 링크를 함께 통과해야 실기판으로 채택한다. 중간 성 162선 dot 0 프리즈는 별도 과제로 남는다.
