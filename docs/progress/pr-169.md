# MMC855·MMC860의 모험도 4 데모 35–40초

## 목표

머지된 PR168(`0186fb7`)의 실기 기준 MMC855로 돌아가 MMC860에서 늘어난 출력·최종 ACK 시간을 조사한다. 같은 입력을 보내고 SEAL 수락, DMA, 화면 공개, 독립 ACK, ARM의 첫 유효 응답까지 구분한다.

## 작업내용

- 같은 ROM의 35–40초에 해당하는 원본 2120–2364를 4장 간격으로 새로 캡처했다. 처음 두 장은 뱅크 준비에 쓴다. 원본 RGB와 PPU 버스를 dot 0부터 수집기에 재생하고 보드 CHR 캐시·D1 송신기와 독립 ARM 복원으로 확인한다. 실제 실기에서 선택된 원본 ID는 로그에 없다.
- 동일한 60장에 MMC855·MMC860의 최종 ARM/65816을 적용하고 MMC855 실측 SPI 보정과 동일한 ROM 허가 일정으로 두 시작 위상을 비교한다. 화면별 map 범위·BG/OBJ tile의 목적지와 크기 및 실기 카운터와 같은 mapdirty·BG·OBJ 수를 대조한다.
- 대조군은 MMC860의 FINAL_ACK 무진행 간격만 128→256µs로 바꾼다. 실제 ARM의 타이머 비교 뒤 분기만 재생에서 조절하며 STOP 검사, 공유 SPI, IRQ, CRC·세대·반환 identity 검사는 실행한다. 원본 2128에서만 간격을 바꾸는 시험도 두 위상에서 수행해 이전 화면으로부터 누적된 위상 차이를 배제한다.

## 성과

| 실기 35–40초, 시작 시각 기준 | MMC855 | MMC860 |
|---|---:|---:|
| 표본 수 | 70 | 64 |
| 화면당 BG / OBJ / 변경 map 행 | 512.86 / 29.83 / 4.90 | 513.08 / 23.73 / 4.77 |
| 계획한 타일 출력, 전체 / 화면당 | 29,792B / 425.6B | 29,760B / 465.0B |
| E0 전체 조회 / 화면 | 28.33회 | 46.75회 |
| E1 전송 / 화면 | 1,444.06B | 1,607.91B |
| 출력·최종 ACK 합 / 화면 | 4,270ms / 61.00ms | 4,360ms / 68.13ms |

실기에서 같은 5초 동안 계획한 타일 출력은 32B 차이지만 MMC860 표본은 6장 적다. 두 판의 전체 실행에서 잰 거래당 E0 비용(109.08/109.24µs)을 이 구간에 적용하면 E0의 화면당 SPI 비용은 약 3.09→5.11ms다. 이 추정치는 credit·drain 조회를 포함하며 DMA·VBlank 대기와 겹칠 수 있다. FINAL_ACK 사유의 무진행 횟수 7,450→22,751는 60초 전체의 `nes_cost474_pause` 카운터다. 실기 로그에는 해당 5초의 FINAL_ACK 사유별 횟수나 화면별 네 시각이 없다.

### 슬롯 이력과 SEAL 길이

`bg_count`는 해당 화면이 사용한 최고 BG 슬롯 번호에 1을 더한 값이다. MMC860은 256–1023번 슬롯을 하나라도 쓰면 SEAL payload가 72B에서 168B가 된다. MMC860 실기 64장의 BG 합은 32,837이다. 낮은 슬롯만 쓰면 한 장당 최대 256, 높은 슬롯을 써도 최대 1,024이므로 **적어도 22장은 전체 SEAL 경로를 실행했다**. 정확한 건수는 이 로그에서 복원할 수 없다.

같은 시점의 원본을 빈 슬롯 이력으로 시작하면 측정 60장의 BG 범위는 73–87이다. 두 위상 모두 60장 전부 짧은 SEAL이었다. 이 조건에서 MMC855→MMC860의 표시 간격 합은 147→142 / 148→140 VBlank였다. MMC860의 조회 간격을 256µs로 늘리면 무진행 pause는 1,101→771 / 1,005→816회로 줄었지만 표시 간격 합은 142→142 / 140→143이었다.

한 화면(원본 2128)에서만 조회 주기를 두 배로 바꿨다. 양 위상 모두 SEAL 송신부터 수락, 첫 DMA와 마지막 바이트, 공개, 65816 ACK까지 모든 관측 클록이 같았다. 유효 응답 전 E0가 8→6회로 줄었고 ARM이 유효 응답을 받은 시각만 각각 0.131·0.132ms 늦었다.

실기와 같은 전체 SEAL을 비교하기 위해 별도 대조군에서 양쪽 ARM에 439개의 슬롯 키를 먼저 배정했다. 원본 구간과 겹치지 않는 실제 CHR 주소를 사용했고 두 VRAM 뱅크의 유효 비트는 모두 0에서 시작했다. 원본은 같은 CRC 검사를 거치며 실제 사용되는 타일은 전부 정상 경로로 처음 공급한다. 이는 실기 이전 35초의 슬롯 내용에 대한 가정이다. 무입력 원본, 변경 map 범위, 타일 종류·크기·CHR 태그·픽셀을 대조하고 같은 슬롯 조건의 두 판끼리 비교한다.

### 같은 작업량에서의 시간 분해

높은 슬롯 조건의 60장에서는 두 판 모두 SEAL 168B를 보냈다. 각 화면의 map 범위와 타일 작업은 판끼리 같고, 실기 두 판의 중간 작업량(BG 512.97, OBJ 26.78, 변경 map 행 4.83)에 맞추기 위해 시간 관측값을 사용하지 않고 같은 가중치를 양쪽에 적용했다. 유효 표본 크기는 8.74장이다. 아래는 화면당 ms이고, 첫 DMA는 **SEAL 수락 후** 첫 전송이다.

| 구간 | 위상 1 MMC855 → MMC860 | 위상 2 MMC855 → MMC860 |
|---|---:|---:|
| ARM 출력 시작 → 65816 SEAL 수락 | 8.55 → 7.67 | 8.51 → 7.69 |
| SEAL 수락 → 첫 DMA | 12.06 → 10.56 | 10.93 → 10.54 |
| 첫 DMA → 화면 공개 | 2.61 → 4.04 | 1.02 → 4.09 |
| 공개 → 65816 최종 ACK | 0.135 → 0.135 | 0.135 → 0.135 |
| 65816 최종 ACK → ARM 첫 유효 E0 수신 완료 | 2.21 → 1.16 | 2.91 → 1.08 |
| ARM 첫 유효 응답 → 출력 계측 종료 | 0.04 → 0.04 | 2.96 → 0.08 |
| 전체 | 25.61 → 23.61 | 26.47 → 23.62 |

첫 DMA부터 공개까지는 두 위상에서 늘었지만 이 구간의 실제 DMA 전송 시간은 0.414→0.369 / 0.415→0.374ms로 줄었다. SEAL 뒤 첫 DMA와 마지막 DMA가 서로 다른 VBlank에 걸친 화면은 가중 전 8→11 / 5→11장이고 가중 후 비율은 11.0→20.4% / 0.4→20.7%다. 원본 2152에서 MMC860은 위상 1의 247선, 위상 2의 245선에 첫 DMA를 시작하고 각각 16B와 256B를 보낸 뒤 나머지를 다음 VBlank에 보냈다. MMC855는 두 위상 모두 225선부터 같은 VBlank 안에 남은 전송과 공개를 끝냈다. 이는 상대 구간 길이의 차이이며, MMC860은 이 화면에 절대 시각으로는 더 일찍 도착했다.

60장에 같은 비중을 주면 MMC855→MMC860의 표시 간격 합은 147→144 / 149→145 VBlank, 마지막 65816 ACK는 49.92 / 66.53ms 앞당겨졌다. 실기의 +7.125ms는 어느 위상의 전체 평균에서도 재현되지 않았다.

### 반복 조회의 원인과 결과

MMC860의 전체 SEAL 60장에서 유효 응답 전 E0 중 위상 1은 1,165회 중 1,142회, 위상 2는 1,223회 중 1,207회가 **화면 공개 전** 시작됐다. 나머지도 전부 65816이 ACK를 내기 전에 시작했다. 원본 2144만 조회 간격을 128→256µs로 바꾸면 대기 E0는 29→20 / 29→19회가 됐다. SEAL 수락·첫 DMA·마지막 DMA·화면 공개·65816 ACK는 두 위상 모두 같은 클록이었다. ARM의 첫 유효 응답만 위상 1에서 0.060ms 늦고 위상 2에서 0.235ms 빨랐다. 전체 60장에 적용하면 MMC860의 144/145 VBlank가 143/146이 됐다. 조회 비용은 실제로 발생하나 양쪽 위상에서 함께 개선되는 효과는 없었다.

## 후속작업

MMC855를 실기 기준으로 유지한다. 먼저 실기 35–40초에 generation, 대상 뱅크, SEAL 길이, SEAL 수락·첫/마지막 DMA·공개·65816 ACK의 VBlank/선을 기록하고 ARM의 첫 유효 E0 및 다음 입력의 SPI 점유와 같은 generation으로 연결한다. 전송이 다음 VBlank로 넘어간 화면과 같은 작업량으로 한 번에 끝난 화면을 비교한다. 실기에서 이 경계가 확인되면 해당 DMA 묶음의 수락·시작 시각을 앞당긴다. [화면별 원시 클록과 비교 결과](../../analysis/ack861-results.json)

### 재현

1. `tools/prepare_nes_ack861.py capture <temp> <ROM>`, 이어서 같은 인자의 `prepare`를 실행한다. `board` 단계는 기존 단일 좌석 FLOAT 래퍼에서 실행한다.
2. `tools/replay_nes_ack861.py <temp> <855|860> <1|2> 128`로 최종 링크를 비교한다. MMC860에서 `256`과 `256 --only-generation 907`을 각각 실행한다. 입력 준비 도구의 `high` 단계 실행 후 두 판의 128 및 MMC860의 256을 `--high`로 반복하고, `256 --high --only-generation 911`로 한 화면만 변경한다. 원본 입력·원본 RGB와 관측 파일은 로컬에 둔다.
3. `tools/analyze_nes_ack861.py <temp> <두 실기 로그의 폴더> analysis/ack861-results.json`으로 원본·작업량·identity를 검산하고 각 단계의 절대 클록 및 화면당 비용을 계산한다.

## MMC862·863 실기 계측

MMC862에는 MMC855의 65816 이미지, MMC863에는 MMC860의 이미지를 탑재했다. Quartus가 배치한 5,120바이트 전체를 각각 원본과 대조했다. FPGA가 SEAL 헤더 첫 읽기, WRAM에서 PPU로 전송한 데이터의 첫·마지막 바이트, 화면 공개, 65816의 최종 ACK를 수동 관측한다. ARM은 동일 세대의 유효 E0를 받은 시각을 남긴다. 35–40초에 시작한 화면만 저장하고 SD 쓰기는 안전한 메뉴 복귀 단계에서 수행한다. 진단판에서 이전 PPU·패드 이력용 회로를 계측에 사용했고, 첫 오류와 STOP 처리는 보존했다.

| 데모 9개 표시 간격 합 (VBlank) | 원본 | 조회 켬 | 같은 설치본 조회 끔 |
|---|---:|---:|---:|
| MMC862 위상 1 | 20 | 20 | 19 |
| MMC862 위상 2 | 20 | 20 | 20 |
| MMC863 위상 1 | 19 | 19 | 19 |
| MMC863 위상 2 | 19 | 20 | 19 |

두 최종 ARM 링크에서 판별한 E0 오류 거부, 60초 종료·STOP, base 복구와 메뉴 release를 확인했다. Questa에서 실제 버스 신호로 6개 종류와 세대 일치, STOP, VBlank 경계를 시험했다. 별도 ARM·65816 재생에서는 판·위상·조회 유무 8조건에서 각각 11장의 RGB가 원본과 일치했다. 조회 응답은 PPU 이벤트로 구성한 재생 모델이다. 44B 조회 비용은 약 0.183ms이며 직전 화면 계측 종료 뒤에 발생한다. 뒤따르는 화면의 VBlank 위상은 바뀔 수 있으므로 실기에서는 동일 링크의 조회 끔 실행도 비교한다.

Quartus Lite 전체 FIT에서 두 판 모두 15,269/15,408 LE, 963/963 LAB, 53/56 M9K를 사용했다. 전체 STA 최저 setup +0.476ns, hold +0.160ns. 제약되지 않은 입력은 원본 54개에서 63개로 늘었으며 추가 9개는 관측용 PA와 /PAWR이다. 실기 로그의 유효 기록 수·세대·DMA 순서·공개 경계로 실제 보드에서의 관측을 확인해야 한다. ARM Flash는 212,992B 한도에서 740B·736B 남았다.

반환 로그에서는 세대와 대상 뱅크, BG·OBJ·map 개수를 모두 맞춘 뒤 관측된 DMA 종류 사이의 VBlank 대기, 공개→최종 ACK, ACK→ARM 첫 유효 E0의 차이를 구한다. 다중 경계·잘린 기록의 제외 수 및 작업량 일치 표본 수를 함께 읽는다. 원본 실기에서 관측한 +7.125ms 가운데 각 단계가 얼마를 차지하는지는 두 실기판의 파일을 받아 판정한다. [설치와 대조 실행](../nes-mmc862-863-trial.ko.md) · [최종 링크와 합성·재생 근거](../../analysis/frame862-package.json)

재현에는 861의 `high` 캡처와 기존 855·860 빌드가 필요하다. `tools/prepare_nes_frame862.py`로 두 보드를 생성·FIT하고 `package_nes_trial704.py image`로 SOF를 변환해 `<temp>/nes-frame862-final862`와 `final863`(동일 접두사)에 보관한다. 단일 좌석 래퍼에서 `check_nes_frame862_wire.ps1`을 실행한다. ARM은 `prepare_nes_frame862.py arm <판> <temp> --work ../probes/nes-frame862/delivery`로 생성한 패치를 `build_nes_mmc479_arm.ps1`로 같은 폴더의 `build<판>`에 링크한다. `check_nes_frame862_arm.py <temp> <판> <ROM>`, `check_nes_frame862_replay.py <temp> <판> <위상>`(기본값과 `--control`), `package_nes_frame862.py <temp>` 순서로 시험하고 SD 루트 두 개를 묶는다.

## MMC862·863 실기 결과

모험도 4 무입력 60초 시험을 판마다 한 번씩 계측 켬·끔으로 실행했다. 파일명에 (1)이 붙은 텍스트 로그는 CONTROL이다. 네 실행 모두 ROM 393,216B 검증, 실행, STOP, base 복구, 메뉴 준비에 성공했고 사용자가 메뉴 복귀를 확인했다. 전송 실패와 화면 처리 중단은 모두 0회였다.

| 실기 | 1–30초 표시 FPS | 30–60초 표시 FPS | 35–40초 시작 화면 | 출력·최종 ACK 평균 (10ms tick 예산 로그) |
|---|---:|---:|---:|---:|
| MMC855 | 17.93 | 16.80 | 70 | 61.00ms |
| MMC860 | 17.55 | 16.23 | 64 | 68.13ms |
| MMC862 계측 | 18.17 | 16.80 | 70 | 60.00ms |
| MMC862 CONTROL | 17.59 | 16.33 | 64 | 67.66ms |
| MMC863 계측 | 17.90 | 16.80 | 70 | 60.71ms |
| MMC863 CONTROL | 18.14 | 17.27 | 72 | 59.03ms |

바이너리 70·64·70·72개 기록 모두 유효하고 누락은 0이다. 계측 켬의 140장은 모두 168B SEAL이다. ARM 사이클 카운터로 본 전체 70장의 평균 출력 시간은 60.896→60.934ms다. 같은 구간이라도 10ms 단위의 기존 예산 로그와 정밀도가 다르다. 계측 조회는 직전 출력 시간 측정 종료 뒤 평균 0.1845ms였다. CONTROL에서 데모 FPS가 두 판 사이에 서로 반대 방향으로 움직였고 각 조건은 1회다. 기존 7.125ms 증가의 원인을 단일 조회 또는 DMA에 귀속할 수 없다.

계측 켬에서 뱅크·map 변경 수·OBJ·BG 수를 정확히 맞춘 41개 조합에 양쪽 공통 가중치를 주면 판당 67장이다. 862→863에서 출력 시작→SEAL 수락 −0.786ms, SEAL→첫 DMA −1.150ms, VBlank 사이 DMA 대기 +0.225ms, 나머지 DMA 구간 +0.011ms, 65816 ACK→ARM 첫 유효 E0 +1.169ms, 전체 −0.531ms였다. DMA 종료→공개 및 공개→ACK 차이는 각각 0.001ms 이내였다. 862는 BG→raw 4장, 863은 BG→raw 4장과 OBJ→raw 1장이 VBlank를 넘었다. 출력 시작부터 SEAL 수락까지가 전체 70장에서 49.65·49.43ms로 가장 길다.

37.62초에 시작한 화면은 두 실행 모두 bank 0, map 변경 18, OBJ 44, BG 516이다. 862의 로컬 세대는 717, 863은 709다. 862는 OBJ·raw·팔레트·OAM이 한 VBlank에 끝났다. 863은 OBJ 뒤 16.18ms를 기다려 raw·팔레트·OAM을 다음 VBlank에 전송했다. 출력 시작 기준 공개는 50.677→65.556ms, 첫 유효 E0는 56.300→65.885ms였다. 70장 평균에서 이 한 건이 차지하는 대기는 약 0.23ms다. 네 로그의 로컬 세대·뱅크·작업량이 모두 일치하는 사례는 0이다. 계측 켬끼리 로컬 세대까지 일치한 11쌍은 전부 map 변경 0, OBJ 28, BG 508에 몰려 있어 데모 전체의 대표 표본으로 쓰기 어렵다.

다음 비교는 MMC855를 기준으로 37.62초의 작업량을 재생하고, SEAL 수락 전 마지막 패킷과 수락 후 OBJ→raw 시작 허가를 추적한다. 계측기를 다시 비교할 때는 로컬 세대와 함께 원본 캡처 ID나 화면 내용 서명을 남겨 부팅 간 장면을 식별한다. 원본 파일 SHA256과 실행별 수치는 `python tools/analyze_nes_frame863_hardware.py <로그 폴더> <결과.json>`으로 검산할 수 있다. ## 864에서 OBJ 다음 raw가 한 VBlank를 넘긴 조건

실기 37.62초 화면에서 862·863의 출력 시작→SEAL 수락은 46.142·46.125ms였다. 863이 SEAL을 먼저 수락했어도 OBJ 마지막 바이트부터 raw 첫 바이트까지 16.177ms가 걸렸다. 실기 로그에는 원본 캡처 ID가 없다. 같은 ROM의 35–40초 재생 60장에는 실기의 BG 516·OBJ 44·map 변경 18 조합이 없었다. 아래는 양 위상에서 같은 OBJ→raw 경계를 보인 원본 2268(재생 세대 942, BG 521·OBJ 113·map 변경 0)의 기전과 후보 검증이다.

MMC855의 65816은 160B OBJ 뒤 첫 raw 명령의 크기 검사(비용 384, 상한 384)를 통과했다. 이어서 목적지 `$9000`을 확인해 새 VBlank 대기로 분기했다. 이미 251·250선이었고 다음 raw 첫 바이트까지 15.082·15.134ms가 걸렸다. 246선 공개 마감 뒤의 DMA 허용 범위를 넓혀도 그 VBlank에 공개할 수 없다.

기록된 SPI 거래 길이와 네 슬롯의 실제 반환 시각을 유지해 마지막 SEAL만 0.051ms 먼저 도착시켰다. raw부터 SEAL까지 여섯 패킷을 가능한 일찍 보내면 0.430·0.456ms 먼저 도착했다. 두 실험 모두 65816의 SEAL 수락·공개·최종 ACK 클록은 MMC855와 같았다. 앞선 OAM 반복 명령(4B→408B)의 수락→반환만 약 1.40ms였고 이후 raw와 테이블 명령이 같은 큐에서 처리됐다.

864는 MMC855 65816과 168B SEAL을 유지하고 ARM에서 section 5의 마지막 raw 192B와 테이블 249B를 201B·240B 두 패킷으로 묶었다. 원본 2268에서 이 부분은 5→2거래, E1 전송량은 350→479B다. 전송량이 늘어도 수신 측 반복 복원과 패킷 반환이 줄어 마지막 OBJ 반환→SEAL 수락이 7.304→5.734ms, 7.378→5.810ms가 됐다. SEAL 수락선은 219→191선과 218→193선으로 앞당겨졌고, 두 위상 모두 OBJ·raw·팔레트·OAM을 같은 VBlank에 보내 242선에 공개했다. 이 화면에서 ARM이 최종 ACK를 처음 확인한 때는 65816 ACK 뒤 10.42·10.46ms였다. 65816의 공개와 ARM의 응답 시각은 각각 비교한다.

중간 링크는 213,008B로 16B 초과했다. 같은 little-endian 값을 복사하는 두 루프를 줄인 최종 링크는 212,964B로 28B 남았고, 같은 복사 변경만 적용한 대조군도 별도로 링크했다. 기준과 후보 모두 BSS 20,932B, SEAL 함수의 정적 stack 사용량 264B다. raw 크기 192·384·2,048B와 각 송신 단계 거부, 수신 측 coverage·테이블·폭 손상 거부를 검사했다. 전체 SEAL 검사 중 STOP에서는 이전 화면 한 장을 유지하고 취소했고, cold 재시작에서 두 장을 공개했다. 60초 종료·base 복구·메뉴 release는 최종 ARM 링크의 함수 시험을 통과했다.

교차 시험에서 MMC860 ARM과 MMC855 65816은 이 168B SEAL 재생을 통과했다. 반대 조합의 위상 1에서는 세대 963의 704B map에서 252선 보호 검사가 실패했다. 소프트웨어가 읽은 값은 252, 모니터가 래치한 값은 253, 실제 DMA 시작은 254선이었다. 위상 2는 통과했다. 기존 검사선을 유지하고 실패한 조합은 후보에서 제외했다.

|---|---:|---:|
| MMC855 | 147 / 149 | 기준 |
| 복사 루프만 변경 | 149 / 147 | +33.259 / −33.314ms |

두 패킷 후보의 전체 60장 평균 출력 시작→SEAL 수락은 11.470→10.536ms, 11.498→10.523ms였다. 실기에서 관측한 약 49.5ms와는 입력 이력과 원본 화면이 다르다. 세대 942에서는 VBlank 경계를 없앴지만, 60장 중 SEAL 뒤 DMA가 여러 VBlank에 걸친 화면은 8→8장, 5→7장이었다. 표시 간격 합과 마지막 ACK는 같은 시작 시각에서 전체 일정을 실행한 결과다.

오프닝은 MMC855의 실측 SPI 비용으로 재생한 857ref 대조군과 비교했다. 위상 1은 합 126→128 VBlank였고 원본 703이 59→60, 원본 759가 178→180으로 늦었다. 위상 2는 합 128→126이었다. 두 위상 모두 703까지 E1 101개의 바이트가 기준과 같고 묶을 raw가 없었다. 전환 50장은 두 위상에서 모두 원본 RGB와 일치했고, 표시 간격 합 120 VBlank와 빈 구간에서 이전 화면을 유지한 16 VBlank도 같았다. 다음은 703까지의 공통 ARM 경로에서 첫 SPI 발행·credit 반환 차이가 생기는 위치를 복사 변경만 한 대조군과 비교하고 759까지 재생하는 것이다. 실기 기준은 MMC855로 유지한다.

## 865에서 확인한 오프닝 703의 첫 발행·반환 차이

MMC855, 공통 복사만 바꾼 864 대조군, 두 패킷을 실제 발행하는 864의 ARM 최종 링크를 같은 65816·MMC855 실측 SPI 비용으로 처음부터 재생했다. 703까지 E1 101개의 내용과 순서가 같았다. 표의 번호는 부팅 뒤 누적 E1 순번이다. 소비 완료는 65816 ACK, ARM에서 본 credit 반환은 해당 순번이 처음 포함된 CRC 정상 E0 응답의 끝에서 측정했다.

| MMC855에 비해 처음 달라진 시각 | 위상 1 | 위상 2 |
|---|---:|---:|
| ARM의 E1 발행 | 22번 OBJ, 3.068 master clock 빠름 | 21번 OBJ, 3.068 clock 빠름 |
| 65816의 패킷 수락 | 99번 OBJ, 3,268 clock 늦음 | 89번 SEAL, 1,312 clock 빠름 |
| 65816 소비 완료 | 99번 OBJ, 3,268 clock 늦음 | 89번 SEAL, 50 clock 빠름 |
| ARM에서 처음 본 반환 시각 차이 | 18번 map, 3.068 clock 빠름 | 18번 map, 3.068 clock 빠름 |

두 비교군 모두 표의 첫 차이가 같다. 위상 1의 703에서 MMC855는 98번 팔레트·OAM 재사용 패킷 직후 E8에서 새 OBJ token 20을 봤다. 864는 약 4.31µs 먼저 조회해 이전 token 19를 보고 E8을 한 번 더 보냈다. 사이에 받은 E0는 두 판 모두 수락 98·반환 97이었다. 99번 OBJ의 ARM 발행이 0.253ms, 65816 수락과 반환이 0.152ms씩 늦어져 703 공개가 VBlank 59에서 60으로 넘어갔다. 첫 3.068클록 차이와 마감을 바꾼 추가 SPI 거래는 별개로 집계했다.

패킷 헤더의 serial 복사만 원래 루프로 돌린 링크는 파일 앞 8B 이후가 864와 바이트까지 같았다. SEAL의 여섯 길이 필드도 원래 방식으로 쓰고 raw CHR 두 바이트를 함께 복사한 `pairs`는 703을 회복했다. 이 링크의 밀집 합은 143/144 VBlank였지만 오프닝 위상 1의 759는 여전히 180이었다. 144B used 비트와 해당 뱅크의 resident·dirty 비트를 네 바이트씩 비교한 `coverage`는 759를 179까지 당겼다. 유효 여부를 결정하는 비트식과 65816의 독립 검사는 유지했다.

복사 대조군과 864를 직접 대조하면 최초 발행 차이는 두 위상 모두 31번 OAM, 최초 E0 반환 차이는 28번 팔레트였다. 두 차이 모두 864가 1.023 master clock 빨랐고 703까지 65816 수락·반환 시각은 두 링크가 같았다. 703의 첫 추가 조회가 설명하는 범위와 759까지 누적되는 차이도 구분했다. 위상 1에서 864의 공개 지연은 706에서 사라졌다가 724부터 다시 생겼다.

오프닝 62장 중 60장에는 map 패킷이 없었다. `offer`는 비활성 뱅크의 미반영 행과 이번 변경 행이 모두 비어 있고 미반환 bulk가 없을 때 조기 map 발행을 마친다. 이 경로에서도 기존 plan 상태·generation·STOP 검사를 실행한다. 보낼 행이나 미반환 bulk가 있으면 기존 credit 조회와 tile 우선 처리를 거친다. 65816 코드와 FPGA는 MMC855 그대로다.

| 최종 링크 | 703 공개 (위상 1 / 2, VBlank·선) | 759 공개 (위상 1 / 2) | 오프닝 60간격 | 밀집 60간격 | 밀집 마지막 65816 ACK 차이, MMC855 대비 |
|---|---|---|---:|---:|---:|
| MMC855 | 59·248 / 60·228 | 178·232 / 180·238 | 126 / 128 | 147 / 149 | 기준 |
| 공통 복사만 변경 | 60·228 / 60·228 | 180·229 / 179·229 | 128 / 127 | 149 / 147 | +33.259 / −33.314ms |
| 864 두 패킷 | 60·228 / 60·228 | 180·239 / 178·236 | 128 / 126 | 144 / 145 | −49.954 / −66.577ms |
| 865 offer | 59·231 / 59·231 | 178·229 / 178·234 | 126 / 126 | 145 / 144 | −33.314 / −83.226ms |

두 패킷의 순서와 내용은 밀집 데모 전체에서 864와 같았다. MMC855와는 세대별 map·tile 작업량, 복원된 section 5와 공개 RGB를 대조했다. 865 offer의 마지막 65816 ACK는 두 위상 모두 66,446,426 master clock에서 기록됐다. ARM의 첫 유효 E0도 MMC855보다 33.255 / 83.127ms 빨랐다. 864와 직접 비교한 밀집 합은 위상 1에서 한 VBlank 늘고 위상 2에서 한 VBlank 줄었다. 오프닝 E1은 모두 597회였고 E8은 864의 1,704 / 1,672회에서 1,634 / 1,608회로 줄었다. 실제 ARM 최종 링크는 212,988 / 212,992B이고 BSS는 20,932B다.

빈 map 경로에 STOP을 주면 ARM이 plan 오류 2와 송신 오류 5를 기록했다. 보낼 행 또는 미반환 bulk를 주면 기존 credit 함수에 진입했다. 65816은 coverage·테이블·폭 손상 각각에 0xE0을 반환했다. SEAL 검사 도중 STOP에서는 0xE4와 이전 화면 한 장을 유지했고, cold 재시작에서는 두 장을 정상 공개했다. 동일 ARM 링크의 60초 타이머, base 복구, 메뉴 release도 실행했다. ROM 허가·SPI 및 보드 외부 신호에는 재생 모델을 사용했다. 이 수치는 실기 FPS로 환산하지 않는다.

오프닝에서 데모로 넘어가는 별도 50장도 두 위상 모두 원본 RGB와 일치했다. 빈 구간은 이전 화면을 16 VBlank 유지했고 표시 간격 합은 120→119였다. 실기 전달 전에는 새 설치·로그 파일명으로 링크하고 4B의 Flash 여유와 같은 마감을 다시 검사한다.
