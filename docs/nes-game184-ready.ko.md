# NES184 연속 전송 큐 실기 시험

이번 시험은 화면 데이터를 최대 4개 패킷까지 연속 전송하는 방식이다. 화면 완성 확인과 오류 검사는 유지한다. 실기에서 얼마나 빨라지는지는 아직 측정하지 않았으며 60fps 완성판은 아니다.

## 설치와 실행

1. SD의 현재 시험 파일을 백업한다. ZIP의 `01-GAME184-SD-ROOT` **안의 내용**을 SD 최상위에 복사한다. `firmware.stm`과 `fpga_n184.bi3`는 이번 짝으로 함께 사용한다.
2. 정상 메뉴에서 `NES GAME 184.nh1`을 실행한다. 준비 중 ROM 쓰기는 기존 방식이므로 화면이 뜨기까지의 시간과 실제 게임 화면 이후의 시간을 구분한다.
3. 스타트로 플레이어 선택·월드맵에 들어간 뒤 숫자 **1** 타일로 이동하고 **A**로 첫 레벨에 들어간다. 이동·점프·대시와 사운드를 확인한다.
4. 가능하면 첫 레벨에서 20~30초 영상을 촬영한다. 이번에는 화면 끊김의 변화, 화면만 멈추는지, 사운드·입력이 계속되는지가 핵심이다.
5. 게임 실행 구간은 약60초 제한이며 종료하면 메뉴로 돌아온다. 정상 복귀하면 아래 두 로그를 전달한다.

- `sd2snes/nes-progress-184.txt`
- `sd2snes/nes-game-last-184.txt`

전원 종료 전에 자동 메뉴 복귀 여부를 확인한다. 첫 게임 화면 이후 90초가 지나도 복귀하지 않으면 더 오래 기다릴 필요 없이 증상과 남은 로그를 알려준다. 화면·음악·입력·복귀 여부를 함께 기록하면 된다. 같은044 복원 시험을 반복할 필요는 없다. `02-RESTORE164-SD-ROOT`는 기존 정상 조합으로 되돌릴 필요가 있을 때만 사용한다.

## 로그와 제한

`sink_window_*`는 새 큐 진단이다. sent/retired는 MCU가 전송·관측한 16비트 순환 수이며 프레임 수가 아니다. flags/ack는 마지막 CRC·F7 identity 검증을 통과한 상태이고 실시간 값이나 항상 첫 오류의 ACK라는 뜻은 아니다. 기존 `sink_io170` 출력은 제거했다. 오류로 중단되어도 로그 저장은 기존 STOP·기본 코어 복원 이후에만 수행한다.

다음 ACK를 일부 쓰는 동안 ACK-valid가 내려갈 수 있지만 소비된 패킷 수는 유지된다. 큐가 완전히 비었을 때에는 최종 ACK가 반드시 유효해야 한다. 중간 데이터를 잃은 채 표시하거나 ACK를 가짜로 만드는 방식이 아니다.

이번 구현은 같은 FPGA 메모리 블록 안의 여유를 사용한다. 다른 카트리지 게임의 세이브 SRAM은 작업 공간으로 사용하지 않는다. 대용량 화면은 순수 전송 예산도 추가 개선이 필요하므로 이번 결과로 바로60fps를 예상하지 않는다.
