# NES 545 · 짧은 동일 바이트 반복의 65816 복원

MMC540에서 951의 194B와 957의 66B는 section 5의 짧은 반복 명령인 op4로 전달된다. 두 값이 같은 2바이트를 CPU가 반복해서 쓰던 경로에 기존 고정 source DMA를 연결했다. 동일한 ARM 펌웨어에서 65816 프로그램만 바꿔 비교했다. [544의 원인 추적](nes-front544-results.ko.md) · [545 생성기](../tools/nes_repeat545.py)

## 구현과 예산

65816이 패킷 길이·세대·범위·중복 검사를 수행한 뒤, 원본 두 바이트가 같고 확장 길이가 64B 이상인 section 5 op4에 고정 source DMA를 사용한다. 원본은 수락 ACK까지 고정된 패킷의 `$40:0010`이고 목적지는 현재 패킷에 할당된 WRAM이다. 다른 두 바이트를 담은 반복은 기존 word 복원을 사용한다. 긴 op5는 기존 0 채우기 조건을 따른다.

194B는 64+64+64+2B, 66B는 64+2B로 전송했다. 각 DMA 시작 전과 마지막 조각 뒤의 수락 전에 같은 STOP 서비스를 거친다. 활성 패킷은 복원이 끝날 때까지 head를 소유한다. 선행 VRAM DMA의 새 head 우선순위와 246행의 최종 표시 판정은 기존 경로를 사용한다.

본문은 **4,949 → 4,957B (+8B)**, 매핑은 5,120B다. 형식상 남은 3B 중 오프셋 `0x13BE`는 기존 raw 표시 DMA가 읽는 `0xFF` 상수다. 앞의 두 빌드는 4,960B 형식 한도에 들어가도 이 상수를 덮는 검사에서 걸렸다. 최종 빌드는 남은 길이를 직접 페이지에 기록하고, 다음 DMA 길이 쓰기가 덮어쓸 인접 바이트를 이용해 source bank 설정 명령을 줄였다. 추가 WRAM은 0B다. ARM은 같은 5–55초 집계 펌웨어 212,428B, Flash 여유 564B, BSS 18,592B다.

## 안전 동작과 고정 도착 시각 대조

두 뱅크에서 194B의 누적 0·64·128·192·194B, 66B의 누적 0·64·66B에 STOP을 주입했다. 8건 모두 해당 경계까지 쓴 바이트와 아직 쓰지 않은 바이트를 확인했다. 오류 ACK `0xE4` 뒤 추가 DMA와 새 표시 identity 공개가 차단됐으며 이전 화면의 RGB가 유지됐다. 새 head·STOP 우선·누락/중복 검사 22건, SEAL·raw 전송 중 STOP 7건, 같은 ARM의 메뉴 복구 5조건·marker 4조건을 확인했다. 메뉴 I/O는 모델이다. [STOP 주입 시험](../tools/test_nes_repeat545_stop.py)

초기 공동 실행은 시험기가 고정 source의 소유자를 op5로만 인정해 중지됐다. 관측기에 op4의 두 원본 바이트·패킷 길이·주소·64B 서비스·수락 전 WRAM 검사를 추가했다. [소유권과 바이트 검사](../tools/observe_nes_repeat545.py)

대조군의 패킷 도착 시각을 고정한 별도 재생에서는 각 위상 53화면에서 op4 126개를 318회 DMA로 복원했다. 총 13,756B다. 아래 시간은 해당 패킷을 읽기 시작해 **패킷 수락 ACK**를 보내기까지다.

## ARM 발행까지 연결한 연속 일정

비교 기준은 동일한 완료 시각 집계 [5,40)·[40,55)의 ARM이다. 905–957의 같은 53개 캡처, 8프레임 부트 ROM 허용 일정, 시작 3,000,000/3,178,684 master clocks를 사용한다. ARM·공유 SPI·SysTick·두 bulk 슬롯·65816 소비·표시 ACK를 함께 실행한다. 각 위상에서 따로 재생한 65816의 이벤트와 RGB도 비교한다. 이 시험의 밀집 표시 간격은 951–955 다섯 간격의 평균이다. [분석기](../tools/analyze_nes_repeat545.py)


재현할 때는 538 생성기에 `--early-final --inline-raw-service`를 주어 기준 65816을 빌드하고 MMC540 SHA256과 대조한다. 545 생성기로 후보를 빌드한 뒤 두 위상에서 `test_nes_tile532.py --trace-credit --trace-rom`을 실행한다. 입력은 544와 같은 dense519/fixture01·order520/oracle-compact01·service509-rom03이고 ARM은 hardware541/ARM02다. 독립 재생은 `replay_nes_front544.py --decode`, 고정 도착 대조는 `test_nes_dma542_fixed.py`를 사용한다.

패킷 수락까지는 951이 1.431/1.426 → 0.571/0.570ms, 957이 0.675/0.675 → 0.424/0.422ms였다. 951의 마지막 SEAL 전 VBlank에 큐 head가 차지한 시간은 1.748/1.750 → 0.893/0.926ms로 줄었다. 957은 패킷 처리에 여전히 1.811/1.811ms를 썼다. 957의 final212 진입은 247/248행이고 두 위상 모두 최종 대기 1회다. 952·954는 최종 대기 0회, 첫 BG 상대 ROM 구간도 보존했다.

ARM 출력 데이터 E1 전송량은 같았다. 위상별 전체 SPI는 5,816/5,696B 줄고, E0 상태 조회가 5,440/5,780B 줄었다. ARM 명령은 1,454,920/1,487,053개, SysTick은 6/7회 줄었다. 각 위상에서 5,616회 ROM 읽기, 125,488B VRAM DMA, 두 bulk 슬롯, 53장 RGB와 실제 map/tile 소비를 확인했다. 별도 65816 재생에서도 표시와 최종 ACK 이벤트가 일치했다. [검증 수치](../analysis/repeat545-verification.json)

**판정.** 원본 MMC540보다 53번째 최종 ACK가 양쪽 모두 약 49.92ms 빨랐다. 반면 밀집 구간은 원본과 같은 30/30 VBlank이며 평균 변화는 +0.003669/−0.001769ms다. 전체 일정 개선분을 후속 조합용으로 보존하고 실기 전달 기준은 MMC540으로 둔다. 다음 비교는 545를 별도 대조군으로 두고 957의 마지막 SEAL 전 head와 SEAL 이후 DMA의 일정을 연결해 246행까지 부족한 1–2행을 줄이는지 확인한다. 이번 결과의 범위는 연속 시뮬레이션과 복구 경로 시험까지다. 후보 ROM을 넣은 새 보드 FIT/STA 및 실기 FPS는 미측정이다.

원시 시험과 바이너리, 중단된 초기 실행, 독립 재생, 재현 소스는 로컬 `probes/nes-repeat545/archive01/evidence.zip`에 보존했다. 2,643개 항목을 재해시한 ZIP SHA256은 `6a871ca9de10752a56f7f1b0fe3603e69409e3d28fdadc5c79b7ef3fdfa4ef7a`이다.
