# 165 CIRAM·OAM 수집과 공통 소유권

기존 CHR 캐시와 행별 상태에 실제 타일맵·스프라이트 메모리를 연결하고, 한 화면의 수집 종료·조회·해제를 한 곳에서 관리한다. [검증 결과](../analysis/native-scene165-verification.json) · [이전 행 상태 계약](nes-native-raster165-contract.ko.md). 전체 픽셀 복사를 대체하기 위한 데이터 경로 구현이며 새 실기 패키지는 아니다.

## 실제 메모리 연결

- **CIRAM**: 기존2KB RAM의 게임용 쓰기/동기 read-old-data 동작을 유지하고, 독립된 읽기 전용 동기 포트를 추가했다. `nes_local_memory`의 기존 주소 선택·초기 소거·CPU/PRG RAM 경로는 유지한다. 관측 주소는 게임 주소를 빼앗거나 쓰지 않는다.
- **OAM**: 실제 `OAMEval`의8개 바이트 뱅크를 기존 `oam_read` 함수로 조회한다. CPU 쓰기를 별도 배열로 복제하지 않는다. 따라서 속성 비트 마스크, 렌더링 시작의8바이트 행 복사, savestate 쓰기 우선순위를 그대로 읽는다. 원본 OAM 쓰기 로직은 변경하지 않았다.
- CIRAM의 실제 쓰기 조건과 OAM의 실제 배열 변경 조건을 관측한다. 렌더링 중 무시되는 CPU `$2004` 쓰기를 메모리 변경으로 오인하지 않는다. OAM 원본에 없는 전원 초기값을 새로 가정하지 않는다.

새 생성기는 앞선 캐시·행 상태 생성기를 재사용한다. 동결164의 관측 추가 부분을 역변환하고 CIRAM 구현 교체를 되돌리면 기존 파일 바이트가 복원되는지 확인한다. CIRAM 동작 보존은 이 문구만으로 주장하지 않고 원본 메모리 구현을 함께 실행해 비교했다. 실제 NES/probe/local-memory/scene 부모 배선은 생성·컴파일했고 **전체 부모 보드 인스턴스 실행은 하지 않았다.**

## 프레임 수집·조회 계약

`nes_native_scene165`가 변경하지 않은 CHR 캐시와 행 상태 수집기를 포함한다. 초기 CHR 메타데이터 소거가 끝난 뒤 NES8행 dot1에서 수집을 시작한다. CIRAM2048바이트와 OAM256바이트를 별도2304바이트 버퍼에 복사하며, 동기 CIRAM 응답과 조합 OAM 읽기를 한 단계 정렬한다. 시작 이후2305 NES클록에 마지막 바이트 저장이 끝나고 완료 상태를 올린다. PPU/CPU를 정지시키거나 새 PSRAM 읽기를 요청하지 않는다.

수집 시작부터232행 dot1까지 CIRAM/OAM이 바뀌면 해당 묶음을 거부한다. 복사를 마친 뒤 원본이 바뀌어도 거부한다. 현재는 화면 중간 메모리 변경을 여러 버전으로 보관하지 않는다. 종료 시 복사가 미완료이면 거부한다. 메모리 오류 비트0=CIRAM변경,1=OAM변경,2=복사미완료다.

종료/ROM 오류 시 CHR 캐시를 동결하고 메타데이터 쓰기 마무리와 행 상태 봉인을 기다린 뒤 공통 `owned`를 올린다. `release_scene`과 reset은 세 경로의 소유권과 진행 중 복사·조회 응답을 함께 취소한다. 소유 중 다음 프레임과 원본 쓰기는 고정 버퍼를 덮어쓰지 않는다. 오류 묶음의 메모리·CHR·상태 조회는 성공 데이터로 반환하지 않는다. ROM 오류는 PPU CE가 멈춰도 NES클록만 동작하면 공통 종료로 진행한다.

메모리 조회 주소0~2047은 **물리 CIRAM**,2048~2303은 원본 OAM 순서다. 범위 밖 주소는 miss/0을 반환한다. 주소0~4095의 NES 논리 네임테이블이나 완성된 SNES 타일맵을 의미하지 않는다. mapper 미러링, 프리페치 위치, 실제 sprite 평가/우선순위와의 연결은 다음 단계다. 세대 번호는 기존 행 수집기의16비트 순환값이다.

**`snapshot_valid`는 완성된 화면의 ready가 아니다.** 메모리/행 상태가 이 제한된 형식에서 일관되고 CHR 조회 소유권까지 확보했다는 뜻이다. 캐시는 이전 프레임의 동일한 CHR-ROM 바이트를 재사용하며, 일부만 받은 타일은 여전히 miss다. 시험에서도 valid인 묶음에 부분 CHR가 존재하는 경우를 명시적으로 확인했다. 사용 타일별 물리 태그·바이트 완성 검사, 필요한 바이트 보충, 한 논리 슬롯의 여러 뱅크 버전 처리가 남았다.

## 검증한 범위

선택 test02: **6991검사, 게임 메모리 포트53634클록 대조, 합성7프레임, 거부5시나리오 PASS**.

- 실제 local-memory 초기화와2048바이트 쓰기, 실제 OAM256바이트 쓰기, CPU 속성 마스크와 시드한 렌더링 시작 행 복사를 실행했다. 원본 메모리와 OAM 구현을 모듈 이름만 바꿔 대조군으로 함께 실행했다.
- 원본/새 local-memory의 CPU·PPU 데이터와 init_done을 매 클록 비교했고, 초기 OAM 적재 뒤에는 같은 조회 주소의 원본 OAM 바이트도 비교했다. 전체 코어 동등성/게이트 동등성 증명이 아니다.
- 두 세대2304바이트 전수 조회, 소유 후 원본 변경/다음 화면 차단, CIRAM 복사 중 쓰기, OAM 복사 후 쓰기, 마지막 경계 쓰기, 복사 미완료, PPU CE 정지 중 ROM 오류, 진행 중 해제·리셋, 범위 밖 조회, 부분 CHR miss와 실패 후 최신 바이트 재수집을 검사했다.
- 컴파일 오류/경고0, 시뮬레이션 오류0/경고18. 경고는 시험의 실제/대조 OAM 인스턴스에서 사용하지 않는 출력 포트에 대한 것이다.

초기 test01도6983검사/53617포트대조로 통과했다. test02는 렌더링 중 무시되는 OAM CPU 쓰기·비CIRAM활동·부분 CHR·실패 이후 최신 바이트 확인을 추가했다. 기존 CHR/행 상태 RTL 및 실제 SMB3 부팅20프레임 결과는 그대로 재사용했고, 무변경 전체 부팅을 다시 돌리지 않았다. 이번 프레임 일정은 합성이며 SMB3 실행·버튼·실기 영상 검증은 아니다.

## 남은 표시 연결

1. 물리 CIRAM/OAM과 실제 BG/OBJ fetch를 연결해 필요 타일·mapper 미러링·슬롯별 물리 버전을 정한다. 원시 Loopy 값과 주 OAM 스냅샷을 최종 픽셀 좌표/그 행에서 선택된 sprite로 오인하지 않는다. 행7의 프리페치가 행8에 쓰이는 경계도 확인한다.
2. 필요한 부분 CHR를 제한된 방법으로 보충하고, 전체 게시 조건에 사용 타일의 완성을 추가한다. 이후 host CDC와 SNES 맵·OAM·팔레트·CHR 소비를 연결한다. 현재 모든 입력/조회는 NES클록 영역이다.
3. 기존38M9K 픽셀 버퍼를 대체한 전체 설계에서 실제 합성 자원·타이밍을 확인하고 최소 경계 검사 후 SMB3로 이동·점프·스크롤을 평가한다. 현재56/56M9K 설계에 덧붙이는 빌드는 금지한다.

추가 스냅샷은 논리2304바이트이며 실제 M9K 배치, OAM 추가 읽기 논리량, SNES 전송 예산은 아직 확인하지 않았다. 행/팔레트 포함 원시 상태량3904~4896바이트를 매 프레임 그대로 전송한다는 설계도 아니다. 필요 영역·변경분과 SNES 갱신 명령으로 바꾸는 단계에서 전송량을 정해야 한다. FPS 개선은 아직 주장할 수 없다.

설치 후보164·사운드·STOP·메뉴 복귀 유지. PR107을 열어둔 채 결과를 추가한다. 실기 영상 개선 다음60초 제한 해제/오류·본체리셋 안전로그, 장시간 입력 유지 순서는 유지한다.
