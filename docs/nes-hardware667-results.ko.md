# MMC666 실기 피드백: MMC662 비교

실행·메뉴 복귀는 성공했다. 사용자는 같은 첫 레벨 동선에서 개선을 느꼈지만, 완료 표시 집계는 초반 소폭 상승·후반 하락이다. 이번 플레이의 map·OBJ 작업량이 크게 달라 구현의 성능 개선 또는 회귀를 단독 확정할 수 없다. MMC662 비교 기준과 MMC666 산출물을 함께 보존한다.

## 완료 표시와 비용

첫·마지막 5초를 제외하며 최종 완료 카운터로 계산한다.

| 구간 | MMC662 | MMC666 | 변화 |
|---|---:|---:|---:|
| 5–40초 | 682회 / 19.49fps | 687회 / 19.63fps | +0.73% |
| 40–55초 | 316회 / 21.07fps | 290회 / 19.33fps | −8.23% |
| 5–55초 | 998회 / 19.96fps | 977회 / 19.54fps | −2.10% |

전체 60.32초는 1,224→1,221회, 20.29→20.24fps로 거의 같다. 전체 평균 간격은 49.28→49.40ms다. 개별 표시 간격 분포나 p95는 이 로그로 확인할 수 없으므로 체감 부드러움을 평균 FPS만으로 판정하지 않는다.

| 전체 DWT 비용 / 완료 표시 | MMC662 | MMC666 | 차이 |
|---|---:|---:|---:|
| 수신 | 10.662ms | 10.436ms | −0.226ms |
| 계획·공급 | 11.321ms | 11.344ms | +0.023ms |
| 출력·최종 ACK | 26.510ms | 26.841ms | +0.331ms |

DWT에는 IRQ·대기가 포함된다. 중첩된 SPI/poll 비용을 다시 더하지 않는다. 출력 비용을 DMA·VBlank로 임의 분배하지 않는다.

## 작업량 차이

아래는 프레임 시작 구간의 표시당 평균이다. 위 완료 시각 구간과 집계 기준이 다르며, 같은 동선은 동일 장면·입력 재생을 뜻하지 않는다. OBJ는 로그의 처리 계수이며 화면의 적 수나 신규 DMA 타일 수와 동일시하지 않는다.

| 항목 | 5–40초 MMC662→666 | 40–55초 MMC662→666 |
|---|---:|---:|
| BG 계수 | 513.04→526.82 (+2.7%) | 588.34→616.26 (+4.7%) |
| OBJ 계수 | 29.47→59.05 (+100.4%) | 18.77→34.85 (+85.7%) |
| 변경 map 행 | 10.06→13.96 (+38.7%) | 7.31→16.93 (+131.6%) |
| E1 출력 바이트 | 1,996.06→2,371.30 (+18.8%) | 1,856.72→2,718.91 (+46.4%) |
| D1 payload 바이트 | 1,543.07→1,498.55 (−2.9%) | 1,460.37→1,579.11 (+8.1%) |

초반은 더 많은 출력 작업에도 표시 수가 소폭 늘었다. 후반은 출력 작업 증가와 표시 수 감소가 함께 관측됐다. 각 계수를 선형 시간 비용으로 환산하거나 나눠서 구현만의 개선율을 만들지 않는다. 고정 재생에서 입증한 665의 VBlank 이득과 이번 실기 평균을 구분한다.

## 종료·복구 판정

- 393,216B 적재·readback, START, STOP, base 복구·안전 재적재 모두 성공. 마지막 단계는 `MENU_PREPARED`, 상태는 `PREPARED_RESET_HELD`다.
- run/ROM/first/STOP/receiver/plan 오류와 전송 실패·CRC 오류·trace abort는 0이다. `native_result=1`은 정상 60초 DEADLINE이다.
- 입력 COMMIT/BEGIN/END는 1,222회, 표시·EA는 1,221회다. 마지막 표시는 59.97초이며 다음 화면의 map 패킷 하나(serial 1222, generation 1270, offset 448, length 192)가 ACK 없이 남았다. 표시 수에 더하지 않는다.
- 종료 스냅샷의 sink/window/video 오류는 2/3/7이다. 최초 runtime 결과는 DEADLINE으로 유지된다. 실제 코드에서 video 7은 map offer 실패를 포함한 여러 분기에 쓰이므로 마지막 map 발행의 종료 전파와 일치하지만 정확한 실패 PC는 입증하지 못했다. 중간 타일 용량 초과로 단정하지 않는다. STOP→메뉴 준비는 3.29초다.
- 캡처 이력은 오류 0인 REJECT→RECOVERY 네 쌍이다. 빈 캡처 회복은 확인되지만, 이 이력에는 벽시계 정렬이 없어 전체 누락 수나 FPS 손실을 역산할 수 없다.

## 다음 판정과 재현

MMC666은 실기 실행·복귀 성공으로 기록하고 전체 속도 개선 승인은 보류한다. 다음 개선은 출력이 많은 map·OBJ 조건을 맞춰 ARM 발행·65816 수락·DMA·VBlank를 대조한다. 기존 두 시작 위상의 고정 재생에서 확인한 952 3 VBlank·957 최종 대기 0회·STOP·독립 검사·최종 ACK를 유지해야 한다. 이번 분석에서는 펌웨어·RTL·합성 산출물을 변경하거나 빌드를 반복하지 않았다.

[분석 JSON](../analysis/hardware667-mmc666.json)에는 원본 3개 SHA256, MMC662 근거 및 MMC666 패키지 hash, 모든 구간·비용·종료 필드가 있다. [분석기](../tools/analyze_nes_hardware667.py)는 원본을 검증한 뒤 계산한다. 원본은 비공개 작업 경로 `../probes/nes-hardware667/run01`, 비교 원본은 `../probes/nes-hardware663/run01`에 보존했다. 다른 PC에서는 동일 hash의 사용자 로그 3개씩이 필요하며 저장소만으로 원본 플레이를 재생할 수 없다.

```text
python tools/analyze_nes_hardware667.py --raw ../probes/nes-hardware667/run01 --baseline ../probes/nes-hardware663/run01 --out analysis/hardware667-mmc666.json
python tools/check_repository_docs.py
```
