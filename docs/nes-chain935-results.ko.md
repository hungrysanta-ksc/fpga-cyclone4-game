# 935 · 마지막 OBJ 32B의 252선 선택

세대 912의 빈 캐시 두 시작 위상에서 288B 뒤의 32B를 252선에 선택했다. 여섯 DMA의 실제 VRAM 쓰기 496B가 모두 SEAL 전에 같은 VBlank에서 끝났다. 밀집 여섯 표시 간격은 두 위상 모두 15회였다. 기존 캐시의 910 캡처와 다른 타일 공급에는 회귀가 있어 실기 기준은 MMC925를 유지한다.

## 934에서 시간을 되찾은 경로

934의 후속 OBJ는 이미 240 / 239선에 반환됐지만, 그 앞의 288B 마지막 쓰기가 254 / 253선까지 걸렸다. 반환 직후의 폴링만 줄인 대조군에서도 마지막 32B는 남았다. 따라서 288B 이전의 64B 두 건부터 같이 측정했다.

새 65816 경로는 이전 VRAM DMA가 설정한 채널 모드·소스 뱅크·VMAIN을 재사용한다. 최종 후보 `bounded`는 이미 수락된 OBJ descriptor를 최대 네 개까지 검사한다. 다음 head의 실제 길이와 주소로 채널을 설정하고, 매 전송 전에 주사선을 새로 래치하고 STOP·새 패킷을 확인한다. 실제 마지막 쓰기가 끝난 뒤에만 head를 전진시킨다. 새 패킷이나 다른 종류의 범위가 끼면 일반 중재로 돌아간다. map 진행 통지와 SEAL·최종 ACK는 기존 경로를 사용한다. 기존 idle 이력 검사의 16B 비교는 같은 여덟 단어를 순회하도록 줄여 정적 ROM에 넣었다.

| 빈 캐시의 912 | 934 위상 1 / 2 | 935 bounded 위상 1 / 2 |
|---|---:|---:|
| 목표 VBlank | 48 / 49 | 48 / 49 |
| 288B 마지막 VRAM 쓰기 선 | 254 / 253 | 251 / 252 |
| 32B 주사선 검사 | 256 / 256에서 보류 | 252 / 252에서 통과 |
| 32B 실제 전송 시작 → 마지막 쓰기 선 | — | 252→253 / 253→253 |
| 같은 VBlank의 SEAL 전 DMA | 464 / 464B | 496 / 496B |
| 밀집 여섯 표시 간격 합 | 15 / 15 | 15 / 15 |
| MMC925 대비 최종 ACK 단축 | 16.615 / 16.574ms | 16.641 / 16.620ms |

비교한 여섯 목적지는 `C000:16`, `8320:32`, `8720:64`, `87C0:64`, `8CA0:288`, `8440:32`이다. 주소는 VRAM 바이트 주소다. 양쪽 모두 각 범위의 수락, 첫 쓰기와 마지막 쓰기, VRAM 내용, 이후 SEAL과 최종 ACK를 같은 실행에서 대조했다. 934 대비 이번 최종 ACK의 추가 단축은 약 0.026 / 0.046ms다.

## 보존 조건과 후속 작업

- 빈 캐시의 910 캡처 기회는 두 위상 모두 유지됐다. 나머지 타일 37묶음은 933 페이지 공급 기준보다 10 / 11묶음이 늦었고 최대 차이는 0.069 / 0.184ms였다. 934 일정과 직접 비교해도 각 위상에서 11묶음이 늦었다.
- 기존 캐시에서는 910의 마지막 D2가 기준 캡처선보다 7,694 / 1,241 masterclock(0.358 / 0.058ms) 늦었다. 밀집 간격은 MMC925의 13회에서 14회가 됐고, 912 최종 ACK는 16.465 / 16.346ms 늦어졌다. 같은 65816에 MMC925 ARM을 연결한 대조군에서는 기존 캐시 위상 1만 13회로 돌아왔고, 빈 캐시의 선행 전송은 양쪽 모두 176B로 줄었다. 다음 작업은 496B DMA가 끝나는 경로를 보존하고, 909 표시와 910 입력의 마지막 D2를 기준으로 OAM 앞에서 쓰는 ARM 대기가 어느 타일 공급까지 필요한지 좁히는 것이다.
- 934의 ARM에서 메뉴 파일명의 중복과 후처리 보고서의 중복 분기를 줄였다. 최종 링크는 212,992B로 Flash 한도에 정확히 들어간다. 65816의 5,120B 프로그램 저장 공간에는 2B가 남는다. 실제 ARM의 SRAM D0 송신, 첫 블록 CRC 거부, 타이머, base 복구와 메뉴 해제를 확인했다.
- 두 위상에서 각각 마지막 32B 선택 직후에 STOP과 새 패킷을 주입했다. 정상 재생의 선택 시각과 같은 클록에 도달했고, 네 경우 모두 DMA를 시작하기 전에 같은 head에서 중단했다. STOP은 취소 상태를 세웠고 새 패킷은 취소 상태를 세우지 않았다. 별도 시험에서 잘못된 descriptor·중복·SEAL이 거부됐고, 복사 중·표시 중·OBJ 마지막 바이트 STOP도 통과했다.
- 재생은 실제 링크한 ARM과 정적 65816 ROM을 사용한다. ROM 경쟁과 행·페이지 캐시는 933의 공유 포트 일정 모델이다. 이번 결과에서 실기 FPS를 추정하지 않는다.

## 재현

1. `tools/nes_chain935.py arm TEMP`로 934 window에서 ARM 소스를 준비하고 `tools/build_nes_trial577.ps1 ../probes/nes-chain935/arm-final/link`로 전체 링크를 만든다.
2. `tools/nes_chain935.py prepare TEMP --variant bounded`로 정적 ROM을 준비한다. `replay TEMP final PHASE CACHE --variant bounded`를 위상 1·2와 cold·warm 각각에 실행한다. ARM만 MMC925로 돌리는 대조군은 `final`을 `base`로 바꾼다.
3. `proof TEMP`와 `guards TEMP --variant bounded`로 ARM 복구와 65816 오류 주입을 검사한다. `tools/check_nes_chain935.py TEMP bounded PHASE stop`과 `head`는 마지막 32B의 주사선 검사에서 STOP·새 패킷을 주입한다. 기록한 PUSH 시각을 재생해 원래 실행과 같은 클록에 도달했을 때에만 통과시킨다.
4. `tools/analyze_nes_chain935.py TEMP analysis/chain935-results.json direct burst fused gated bounded`가 공개·ACK와 실제 VRAM 쓰기를 집계한다. 각 비교 ROM은 같은 이름으로 준비하고 재생한다.
