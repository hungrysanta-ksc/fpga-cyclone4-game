# 755 · 956 표시 대기 중의 957 수신과 첫 VBlank 마감

**753을 유지한다.** 956 최종 ACK 전에 확인한 957 입력은 두 위상 모두 17블록 중 8개에서 16개로 늘었다. 마지막 한 블록은 이전 표시를 확인하고 EA를 완료한 뒤 D3로 요청하는 COMMIT이다. 앞당긴 입력으로 957 표시를 한 번 줄인 경우는 있었지만, 952·957의 긴 map DMA와 같은 VBlank의 OBJ 마감을 함께 지킨 후보는 없었다. [검증값과 추적 파일 해시](../analysis/front755-verification.json)

## 두 위상의 전체 링크 결과

고정 707D 보드 응답과 751 정적 ROM을 사용해 각 ARM 전체 링크를 리셋부터 905–957까지 실행했다. ARM 명령·65816 명령과 DMA를 실행하고 SPI 서비스·IRQ·ROM 경쟁은 기존 일정으로 모델링했다. 성공적으로 끝난 각 실행의 53개 RGB 화면과 패킷 내용·개수, WRAM→VRAM 검사를 대조했다. 첫 VBlank는 **956이 실제 공개된 바로 다음 VBlank**로 고정했다. 248선 종료 경계에는 beam counter의 4클록 단축 가능성을 반영했다. 표에서 슬래시는 시작 위상 1 / 2이고, 마지막 ACK 차이는 같은 부팅 시각부터 누적한 값이다.

## 어느 비용이 이동했는가

입력 선행 후보는 일반 warm의 SEAL 대기에서 최대 24블록까지 빌리고 COMPLETE에서 멈춘다. cold의 첫 묶음은 7개다. 956 ACK를 0으로 놓으면 957 입력 시작은 −6.970 / −6.912ms에서 −17.007 / −17.036ms, 첫 BG E9 시작은 +14.241 / +14.514ms에서 +6.578 / +6.787ms가 됐다. ACK부터 마지막 map 소비 반환까지 실제 완료한 SPI 거래가 79 / 79건에서 51 / 52건, 4,363 / 4,363B에서 3,047 / 3,067B로 감소했다. 이 구간의 SPI 점유는 17.179 / 17.179ms에서 11.782 / 11.827ms로 줄었다. 부팅부터 53화면 전체 SPI도 345,067 / 346,827B에서 325,191 / 326,991B로 줄었다. E1 패킷 자체의 내용은 같다.

입력 선행 후보는 위상 1에서 957을 두 번째 VBlank에 표시했지만, SEAL 전 대상 map DMA는 위상 1에서 0B, 위상 2에서 192B였다. OBJ는 236 / 232선에 시작했다. 같은 blank에서 완료된 1,536B map 직후의 시작이라는 조건은 어느 쪽도 충족하지 않았다. 직전 956의 공개선과 957 공개선이 달라 정수 표시 간격만으로 map 선행 여부를 알 수 없다.

별도 geometry 후보는 META_END에서 검증된 입력으로 column 0의 224개 fine Y를 계산해 최대 7개 raw 행 뒤의 비어 있는 scratch에 저장했다. 기존 행별 예외·경계 검사와 최종 ACK는 유지했다. 957 첫 BG 발행은 ACK 뒤 6.603 / 6.652ms였다. BG map 확정은 11.368 / 11.419ms였지만, 마지막 1,536B 범위의 첫 map 제출 함수에 진입한 시각은 14.940 / 14.989ms였다. 마지막 map 반환은 23.293 / 23.312ms였다. credit으로 map 쌍을 추가 제공한 후보도 표의 248선 마감을 넘었다. 범위를 한꺼번에 비운 대조군은 양쪽 모두 907에서 ARM 표시 오류로 중단됐고, 큐가 비었는지 확인하지 않은 선행 수신은 양쪽 모두 빈 큐 검사에서 중단됐다.

## 보호 조건과 다음 예산

수신 후보와 geometry의 전체 링크에서 cold 7블록, 정상 warm 16블록, 후반 STOP·CRC·retire·I/O 오류에 대한 중단, 이전 표시 확인 전 COMMIT 차단, 최종 ACK·메뉴 복귀 함수 경로를 시험했다. 같은 정적 65816 ROM은 credit 재사용 후보의 양쪽 기록으로 DMA 전후 STOP, 새 head 우선, stale identity 거부를 재생했다. 실기 설치본이나 새 Quartus 빌드는 만들지 않았다.

먼저 957에서 BG map 확정 후 마지막 페이지 발행까지 약 3.57ms를 OBJ 계산·준비와 겹칠 수 있는지 검사한다. 대상 뱅크의 직전 공개인 955와 대조하면 957의 1,536B 중 변경은 64B, 4B 그룹은 34개다. 기존 여덟 head를 유지하고 head마다 6B 마스크를 보낼 때 계산상 payload는 184B이고, 2.625MHz에서 순수 wire 절감 상한은 4.120ms다. 두 절감을 더한 값은 달성한 시간이 아니다. 628의 65816 생략 바이트 재검사는 같은 종류의 wire 이득을 소비 지연으로 되돌렸다. 우선 955 최종 ACK에 묶인 이력을 독립적으로 확인하고 957의 WRAM 연속 범위를 복원하는 시간을 기존 소비기와 대조한다. 전체 행 복구·STOP 비용을 포함해 첫 248선과 map 뒤 OBJ를 함께 통과한 경우에만 두 번째 VBlank 표시를 채택한다. ## 재현

1. 753 prefix 전체 링크를 base로 두고 `tools/prepare_nes_front755.py --base ../probes/nes-credit753/arm-prefix --policy K --out ../probes/nes-front755/patch-K`를 실행한다. 해당 overlay를 `build_nes_mmc479_arm.ps1`로 `../probes/nes-front755/arm-K`에 링크한다.
2. `tools/run_nes_front755.ps1 -Variant K -Phase N -Game <ROM> -TraceRoot <temp>`로 시작 위상 1과 2를 각각 실행한다. 각 변형과 중단 대조군의 이름은 검증 JSON의 candidates와 rejected에 있다.
3. receive·geometry는 `check_nes_front755.py --arm ../probes/nes-front755/arm-K/src --out ../probes/nes-front755/late-K.json`으로 검증한다. wire의 각 위상에서 기존 `check_nes_static751.py`를 공유 ROM·해당 trace에 적용하고 before/during/head/stale 각각의 출력을 `<temp>/nes-front755-wireguard-N-FAULT`에 둔다.
4. `tools/analyze_nes_front755.py --temp <temp> --probe ../probes/nes-front755 --out analysis/front755-verification.json`으로 표시·거래·DMA·보호 조건을 같은 증거에서 다시 계산한다.
