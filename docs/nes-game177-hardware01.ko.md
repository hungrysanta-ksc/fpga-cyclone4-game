# NES177 실기 — START 화면 전환과 영상 정지의 연관

사용자는 이번에 **START로 화면을 전환할 때 영상이 멈추며, 그 전에는 끊기더라도 계속 움직인다**고 관찰했다. 소리는 계속 나고 첫 레벨에도 진입하는 것 같다고 보고했다. 이는 단순 실행 시간보다 게임 장면·입력을 포함해 재현해야 한다는 근거다. 버튼 시점과 정지 시점의 정확한 시간 대응은 이번 로그로 확인할 수 없다.

## 로그에서 확인한 사실

| 항목 | 결과 |
| --- | --- |
| BEGIN / END / COMMIT / 표시 완료 ACK | 각각 27회 |
| 마지막 표시 generation | 38 |
| 마지막 표시 완료 | RUN 기준 12.48초 |
| 진행 로그 DISPLAY 구간 | 60.05초 |
| ABORT / ROM / sink / video 오류 | 모두 0 |
| 종료 | DEADLINE 1, STOP·기본 FPGA 복구·메뉴 준비 통과 |
| 입력 | 변화 441회, 최근 16개에 A/B/RIGHT/해제 기록 |

60초 한도까지 약 47.52초 동안 추가 표시 완료가 없었다. 174의 마지막 표시 3.81초와 다르므로 ‘항상 같은 실행 시간에 멈춘다’는 가정을 유지하지 않는다. 27회가 실제 TV 프레임률을 뜻하거나, 174의 12회보다 성능이 개선됐다는 뜻은 아니다.

실행 절차는 정상 종료됐으며 `MENU_PREPARED`는 실행 295.71초에 기록됐다. 실제 메뉴가 보였는지는 이번 메시지에서 별도로 명시되지 않았다. `screen_frames=0`은 신뢰하지 않는 구형 계측값이다. `screen_error=169`는 SPC 초기화 A9이며 영상 오류가 아니다. `native_receiver_error=21`은 deadline guard가 전송을 거부하면서 남을 수 있는 후속 값으로, 단독 SPI 손상 근거가 아니다.

## 새 관측이 좁힌 범위

종료 직전 16클록 표본 모두 다음 상태다.

- exporter `IDLE`, frame_owned=0, raw geometry_valid=0.
- 수집기 initialized=1, active=1. 주사선40에서 dot107→111과 ROM/PPU 관련 주소가 진행한다.
- fill_busy=0, fill_abort=0, arbiter_fault=0.
- tx_valid=0 / tx_ready=1, host_valid=0 / host_ready=1.
- fill_idle은 0/1로 변한다. 이는 공유 리더의 코어 트래픽·ready 조건도 포함하므로 fill 교착의 증거가 아니다.

따라서 **이 표본 시점에는 완성 프레임이나 전송 데이터를 붙잡고 기다리는 상태가 아니다.** DRAIN, WAIT_ACK, fill busy에 갇힌 상태도 관측되지 않았다. 현재 후보 수집/허용 조건과 화면 전환의 연관을 먼저 조사한다.

단, active=1·owned=0·geometry_valid=0은 정상 수집 중간에도 나오는 상태다. 마지막 16클록만으로 프레임이 반복 거부되는지, 특정 종료/결합 조건을 놓친 것인지 확정할 수 없다. 실제 수집 generation과 거부 이유는 이 표본에 없다. 중재기 fault는 sticky이므로 현재 0은 해당 reset 구간의 중재기 fault 가설에 반대되는 근거지만, 모든 메모리·타이밍 문제를 배제하지 않는다.

## 사용자의 처리량 가설과 현재 구현

화면 전환이 원인이라는 관찰은 우선 반영한다. 다만 ‘SNES에 너무 많은 데이터를 보내다가 멈췄다’는 해석을 바로 확정하지 않는다. 27번째 전송은 표시 ACK까지 끝났고 이후 새 BEGIN이 없으며, 마지막 표본에서도 전송기가 비어 있다.

현재 FPGA 영상 수집기는 모든 NES 장면을 일반적으로 표현하지 못한다. 배포 소스에는 다음 거부 조건이 있다.

- compact 행 묶음 최대32, sprite fragment 최대128, plane 예외 최대128.
- 프레임당 팔레트 상태 최대2, 특정 표시 mask `0x1e` 요구.
- 한 주사선 도중 팔레트·fine-X·pattern mode·mask 변경 거부, 불완전 행·plane pair 거부.

화면 전환으로 변경량이 커져 이 **표현 용량**을 넘거나, 표시 제어·팔레트·스크롤 변화가 현재 제한과 맞지 않을 가능성이 있다. exporter는 BEGIN 전 부적합 후보를 release/DRAIN으로 보내며 이 경우 ABORT 패킷을 만들지 않으므로 ABORT0과도 양립한다. 위 조건 중 무엇이 실제로 걸렸는지는 아직 미확인이다. 일시적인 전환 프레임 한 장의 거부만으로 이후 수십 초 정지를 설명할 수 없으므로 **전환 후에도 계속 거부되는지/재수집이 회복하는지**까지 확인해야 한다.

처리 속도 부족은 별도로 남는다. build+pattern stage 1,790ms와 seal+ACK 4,180ms를 27회로 나누면 평균 221.1ms다. 이는 직렬 단계 비용이며 TV FPS가 아니다. 수신 51,700ms에는 화면 정지 뒤 폴링이 포함된다. 서로 다른 장면·입력이므로 174의 평균 167.5ms와 단순 성능 비교하지 않는다.

## 다음 작업

1. 기존 실제 CPU/PPU/MMC3 모델에 정상 컨트롤러 직렬 입력으로 START 누름·해제를 넣고 플레이어 선택과 다음 화면 전환을 재현한다. 이전 176의 무입력 도입부 360프레임 통과는 이 장면을 검증하지 않았다.
2. 장면 전환 전후 수집 generation·fetch/compact/raster 오류·행/묶음/객체/예외/팔레트 개수·표시 mask를 모델에서 비교한다. 즉시 소비와 느린 소비를 구분하고, 과거 초기 화면만 반복하는 시험은 생략한다.
3. 실제 거부 이유 또는 수집 결합 실패를 재현하면 해당 표현/복구 경계만 수정해 최소 회귀 뒤 SMB3 실기로 간다. 제한값을 무작정 늘리거나 검사·watchdog를 끄지 않는다. 재현되지 않으면 그때 부족한 경계만 추가 관측한다.
4. 동시에 177 계약에 남긴 앞단 테이블 변경분 전송과 기준세대/ACK 계약으로 초기 끊김을 줄인다. 정지 해소만으로 60fps 목표를 완료 처리하지 않는다.

이번에는 같은 177 재시험·영상·044 복원 검증을 요청하지 않으며 새 펌웨어/FPGA/ZIP을 만들지 않았다. 177 원본 패키지·검증 기록은 보존하고 이 실기 결과를 PR111에 별도 추가한다.
