# NES183 실기 — 표시 완료 171→173회, 큰 차이 없음

사용자는 “미세하게 개선된 것 같지만 큰 차이는 없다”고 보고했다. 로그에서도 약60초 동안 표시 완료가171회에서173회로 늘어난 정도다. **약1.19%의 작은 차이이며, 다른 장면·입력으로 진행한 단회 시험이라 중복 조회 절감의 확실한 성능 효과로 단정하지 않는다. 60fps 목표는 미달이다.** 이번에는 TXT 두 개만 받았으며 영상·음질·육안 메뉴 복귀를 별도로 확인하지 않았다.

## 182와 비교

|항목|182|183|
|---|---:|---:|
|실행 구간|60.07초|60.06초|
|최종 표시 완료 ACK|171회|173회|
|전체 평균 완료율|2.847회/초|2.880회/초|
|전체 시간/완료 수|351.3ms|347.2ms|
|수신·후보 대기 누적|28.52초|25.66초|
|변환·CHR 전송 누적|9.25초|8.10초|
|나머지 전송·표시 확인 누적|21.81초|25.76초|
|SPI transaction|280,177회|284,849회|
|clocked bytes|7,351,325B|7,466,878B|

완료율은 전체 시험의 표시 ACK 평균이다. NES 코어 실행FPS, CRT 주사율, 순간 화면 갱신율과 구별한다. 현재 코드를 특정 저속FPS로 제한한 결과가 아니다.

수신 누적은 줄고 나머지 전송·표시 확인은 늘었다. 각 구간에 대기·SPI·SNES 처리가 함께 들어가며 장면별 데이터량도 다르다. 10ms 단위 누적이고, 실패로 반환한 마지막 구간은 누적되지 않을 수 있다. 따라서 수신 감소를 전부183 캐시 효과로, 표시 구간 증가를 새 회귀로 해석할 수 없다.

전체 clocked bytes는 유효 화면 payload만 세는 값이 아니다. 상태 조회와 ACK polling이 포함되고 service observer의 직접SPI는 별도다. 이번 순수 wire시간 하한은2.625MHz 기준 약22.756초이며, 한 화면당 평균 약43.2KB도 필수 전송량을 뜻하지 않는다. 중복 D0 재사용 횟수나 종류별 전송량 카운터가 없어서 실기에서 정확히 몇 건을 절감했는지는 계산할 수 없다.

## 종료 기록

- ROM393,216B 적재·비교 성공. verify/RUN/ROM/최초/STOP/receiver/video 오류0. BEGIN·END·COMMIT174,ABORT0,최종 표시 완료173회.
- 마지막 표시265세대/59.73초. 다음266세대는 생산자COMMIT까지 완료했지만 최종 표시 확인 전 기한에 도달했다.
- `native_result=1`은60초 기한 종료다. 실제 runtime은 최초 원인을 보존한다. 이번 `native_sink_error=2`, `sink_io170=02/00000000/...`는 **PRE_GUARD**, 즉 다음E0 상태 조회를 보내기도 전에 guard가 종료시킨 경우다. SNES CRC오류·ACK불일치·poll한도 초과가 아니다.
- 남은 요청은 REPEAT op4/section3/sequence33/serial174/generation266/offset32/전송2B·확장226B다. 이 요청은 전송 시작 전 차단됐고,0으로 채워진 ACK는 받은 응답이 아니다.
- STOP·기본FPGA 복원·메뉴준비295920ms 완료. 이는 로그상 복귀 준비이며 이번 사용자 육안 확인을 대신하지 않는다.
- SPC A9·유효1·unmute1은 기록됐다. `screen_error=169`는 SPC초기화 결과이며 영상 오류를 뜻하지 않는다. 음질 판정은 하지 않는다.

최근16episode는8거부/8회복,모두224행/raster·compact 오류0이다. 거부는fetch01×7과오류0·candidate mask00×1이다. 01은새low fetch 앞에 기존pair가 남은 조건이며, 마지막 회복에는objects66·exception1이 기록됐다. 시각·위치·전체빈도·거부 중간 변화가 없으므로 특정 버튼이나 장면의 원인으로 단정하지 않는다. 25bit observer는 모든patch 오류를 포함하지 않는다. 입력 변경 로그도 연속 입력 유지 품질의 합격 근거로 사용하지 않는다.

## 작업 의미와 다음 순서

183은 실기 실행을 마쳤지만 눈에 띄는 처리량 향상은 입증하지 못했다. **상태 조회를 조금 더 줄이는 수정만 반복하지 않고, 합의한 연속 전송 구조와 전송량 축소로 넘어간다.**

1. 실제 FPGA→MCU 및 MCU→SNES 경로의 빈 버퍼·수명·소비 범위를 정의한다. 제한된FIFO/credit로 여러 조각을 연속 전송하고 소비 확인을 묶는다.
2. 최종 표시 완료와 버퍼 재사용의 소유권은 유지한다. CRC·순번·세대·STOP/reset·버퍼 가득참을 처리하고 완성된 후보만 화면에 공개한다.
3. 목적bank의 기준세대가 확인되는 차등 갱신과 유효payload 절감을 함께 적용한다. 중간 프레임을 버렸다면 누적 변경 또는 전체 재구축이 필요하다. ACK만 없애도 해결된다고 가정하지 않는다.
4. 수집·전송·표시의 중첩과 공유SPI16.7ms 예산을 함께 검토한 뒤, 필요한 최소 통합 검사와 실제SMB3 시험으로 검증한다. 기존 타일 묶음·1813/1815 압축을 중복 구현하지 않는다.

이번에는 결과만 기록하며 새FW/FIT/ZIP과 동일183·044 재시험은 없다. GBC164·기존 세이브·완료자료 보존. AV60fps→장기플레이/오류·실기리셋로그→입력유지 순서를 유지한다.
