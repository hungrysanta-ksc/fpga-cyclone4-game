# MMC551 실기 두 실행

성공 실행은 기존과 비슷한 첫 레벨 동선이었고 사용자 확인으로 두 실행 모두 메뉴에 복귀했다. 실행 실패 로그는 부팅 경계의 표본으로 따로 보존하고 FPS 집계에는 성공 실행만 포함했다.

## 실제 표시 성능

| 구간 | MMC551 표시 완료 | MMC551 FPS | 같은 작업 시작 bin의 MMC540 → MMC551 |
|---|---:|---:|---:|
| 5–40초 | 458회 | 13.09 | 443 → 458 (+3.39%) |
| 40–55초 | 214회 | 14.27 | 199 → 214 (+7.54%) |
| 합계 5–55초 | 672회 | 13.44 | 642 → 672 (+4.67%) |
| 전체 60.08초 | 822회 | 13.68 | 전체 완료 803 → 822 (+2.37%) |

MMC551은 새 완료 카운터로 두 구간을 직접 측정했다. MMC540의 완료 카운터는 1–40초·40–60초였으므로 오른쪽 열에서는 양쪽 모두 작업 시작 시각 기준 5초 bin을 합산했다. 이번 MMC551에서 두 방식의 구간 합계가 일치했다. 45–50초는 두 실행 모두 69회였고 50–55초는 61→75회였다. 동선은 비슷하지만 입력과 적 배치는 동기화하지 않았다.

표시당 DWT 평균은 수신 18.86→19.95ms, 계획·공급 14.51→14.53ms, 출력·최종 ACK 40.84→37.98ms였다. 전체 평균 표시 간격은 74.82→73.09ms다. DWT 위상에는 IRQ와 대기가 포함된다. 마지막 구간에서 세대 시작 823회 중 822회가 완료됐고, 큐 전송·반환은 모두 21,316회였다. 마지막 표시 시각은 59.99초였다. 종료 상태는 60초 제한 도달이며 D2 수신 오류 24가 함께 기록됐다. 전송 중단·CRC 오류·ROM 오류는 0회였다.

## 실행 실패와 기록 수정

| 경계 | 성공 | 실패 |
|---|---|---|
| ROM 적재·전체 비교·START | 393,216B 검증, START | 동일 |
| reset 해제 뒤 큐 응답 | 빈 F7 정상 | 동일 |
| SNES 준비 대기 | 566회 조회, 70ms에 stage 3 | 44,425회 조회, 5,000ms 후 TIMEOUT |
| 첫 상태 → 마지막 상태 | 01480000 → 01fca903 | 01480000 → 01580000 |
| native 전송·표시 | 822회 표시 | native 전송 0, BEGIN 0, 표시 0 |
| STOP·base·메뉴 | 정상 | 정상 |

실패 때 SNES 화면 프로그램의 준비 단계 3이 관측되지 않았다. 마지막 stage는 0이고, RESET 비활성·FPGA DONE·MCU_RDY는 두 조회 경계에서 같았다. 이 관찰로는 SNES CPU가 어떤 명령을 실행했는지, reset 해제·첫 fetch·상태 쓰기 중 어디에서 진행이 끊겼는지 구분할 수 없다. MMC480과 MMC492에도 같은 준비 대기에서 끝난 사례가 있다. 버전별 회로·소비 ROM이 다르고 총 시도 횟수를 몰라 같은 원인이나 발생률로 묶지 않는다. 다음에 자연히 발생하면 세 로그와 화면·메뉴 복귀 여부를 같은 실행으로 보존한다. [MMC480 기록](nes-mmc481-startup.ko.md) · [MMC492 기록](nes-boot493-contract.ko.md)

실패 예산 로그에서는 12개 bin이 전부 0인데 `cost_phase_02`가 869회를 보고했다. MMC551은 메뉴 진입에서 bin을 초기화하지만 DWT 통계는 SNES 준비가 성공해야 초기화한다. 그러므로 이번 실패의 처리 비용으로 쓸 수 없다. 다음 빌드용 수정에서는 로더에 들어가기 전에 이전 DWT 보고서를 무효화하고, 측정 전에 종료되면 `cost_sampled=0`만 출력한다. 준비 대기·타임아웃·재시도 동작은 유지했다.

같은 ARM 메모리에서 성공→프레임 전 실패→성공 순서를 재현했다. 원본은 실패 보고에 이전 호출 3회를 남겼고 수정본은 미측정을 표시했으며 다음 성공은 1회부터 다시 집계됐다. 링크된 메뉴 코드에서도 무효화 호출이 SD 로더보다 먼저 실행됨을 확인했다. 수정 ARM은 212,800B(기존보다 80B 증가), Flash 여유 192B, BSS 18,592B다. 이 수정은 이미 배포한 MMC551에는 들어 있지 않다. [실기 로그 해시·구간 집계·보고 검사](../analysis/hardware552-mmc551.json)

## 출력 병목 후속 시험

실기 DWT로는 최종 DMA와 VBlank 대기 시간을 분리할 수 없어, 같은 MMC551 소비 ROM·ARM 실행 코드의 고정 입력 53개 연속 일정에서 마지막 tile ACK와 SEAL 수락 사이를 다시 측정했다. 951에는 일반 출력과 SEAL을 합쳐 E1 18개·1,292B, 957에는 21개·1,917B가 남았다. 두 위상에서 각각 12.77 / 12.97ms와 16.46 / 16.54ms였다. 반면 953은 SEAL 1개·187B, 약 1.76ms만 남아 출력 단계 안에서도 공급 순서가 다르다. 이 프레임 번호는 실기 로그의 초 단위 장면에 대응하지 않는다.

성능 후보는 보고서 수정과 별도 ARM에 링크했다. section 5의 연속 mode 배열 두 개를 81B씩 두 번 넘기던 것을 기존 비용 선택기에 162B로 한 번 넘겼다. 단일 패킷 길이 제한, RLE 판정, 독립적인 65816 복원·검사와 최종 ACK 경로를 유지했다. 53화면에서 E1 패킷 53개·1,007B가 줄었고 957의 마지막 tile ACK 후 발행은 21→20개였다. 하지만 이 구간은 여전히 약 16.55ms였고, 밀집 표시 간격의 합계도 두 시작 위상 모두 28 VBlank였다. 마지막 ACK 차이는 −49.91 / +16.59ms로 방향이 갈렸다. 952의 SEAL 전 5 VBlank 및 957 최종 대기 0회는 유지했다. 성능 후보는 채택하지 않는다. [두 위상 비교·독립 재생](../analysis/modes552-verification.json)

다음은 MMC551을 대조군으로 957에서 마지막 tile ACK 뒤 남는 map 패킷 세 개(각 192B)의 준비 완료·실제 발행·수락 시점을 대조한다. 큐가 빈 시간(기준 4.12 / 4.20ms) 중 데이터가 확정된 때만 앞당길 수 있는지 검증한다. 953은 같은 지연이 없으므로 회귀 대조로 유지한다. 새 실기 전달 기준은 두 위상의 밀집 VBlank 수와 마지막 ACK 동시 단축, 952·957 및 STOP·메뉴 복귀 보존이다.
