# 911의 마지막 입력 반환부터 첫 BG·OBJ 공급까지

## 목표

973의 232B 팔레트 앞 OBJ 서비스와 기존 65816을 대조군으로 삼았다. 세대 911의 첫 타일이 input·plan·ROM 중 어디에서 기다리는지 확인하고, 908 공개·911 공개 간격·912 최종 ACK가 함께 개선되는지를 채택 기준으로 두었다.

## 작업내용

두 시작 위상에서 빈 캐시로 부팅해 905–912를 연속 실행했다. ARM과 65816은 링크한 프로그램을 실행하고 FPGA 공급은 기존 포트 모델을 사용했다. 입력 세대 911의 마지막 D2, planner 진입, 첫 E9 송신·수락, 타일 뱅크의 생산·공개·반환, SEAL 수락을 같은 타임라인에 맞췄다. 65816 수락과 FPGA 생산 완료는 각각 기록했다.

ARM 두 후보는 별도로 전체 링크했다. 첫 후보는 보낼 map이 없고 zero BG만 plan에 쌓인 단일 raw 행에서, OBJ 계획을 완성한 다음 기존 스크롤 두 패킷을 발행하도록 했다. 타일 뱅크가 사용 중이면 기존 검사에 따라 일반 출력 경로가 스크롤을 담당한다. 둘째 후보는 755에서 시험한 8,704B BG·OBJ 키 배열의 일괄 초기화 제거만 적용했다. 매 프레임 resident의 사용 비트는 초기화하고, 사용 중인 슬롯의 키만 읽으며 새 슬롯의 키는 삽입 때 기록한다. raw·OBJ 검사 scratch의 초기화와 대상 map 이력은 기존 동작을 따른다.

## 성과

대조군의 마지막 D2→planner는 1.412 / 1.412ms, planner→E9 송신 시작은 7.754 / 7.803ms였다. 후자에서 SPI 점유는 양쪽 모두 0.395ms였다. E9 자체는 118B, 0.409ms였다. zero BG, OBJ 13개, END의 총 15개 레코드를 같은 순서로 수락했다. 이후 16B BG 준비는 약 5µs, 32B OBJ 준비는 약 15µs였고 **911에 귀속되는 수요 ROM 허가는 두 위상 모두 0회**였다. 앞 세대에서 쌓인 캐시를 포함한 결과다.

ARM 함수 진입점을 계측해 보니 planner 진입 후 zero BG 등록은 0.828 / 0.828ms, BG 행 계산 뒤 map 발행 함수 진입은 5.219 / 5.217ms였다. 두 지점 사이의 **4.391 / 4.389ms** 동안 이번 화면의 map 패킷은 하나도 발행되지 않았다. 이 구간에는 BG 슬롯 탐색, 행 쓰기·비교, 스크롤 테이블 생성이 들어 있다. 첫 OBJ 등록은 5.664 / 5.662ms, 마지막 OBJ 등록은 7.540 / 7.589ms였다. 함수 계측 전후 SPI 이벤트·65816 이벤트·타일 기록·프레임 진단 BIN은 바이트 단위로 일치했다.

스크롤 연기 후보에서 911의 1,100B 패딩 복원이 마지막 OBJ 뒤로 밀렸다. 첫 E9는 planner 진입 기준 0.317 / 0.369ms 앞당겼지만 planner→SEAL은 1.343 / 1.424ms 길어졌다. 두 위상 모두 첫 표시 회귀는 908에서 발생했다. 키 배열 후보는 E9 발행 전 65.6µs를 줄였지만 911의 공개 VBlank는 같았다.

두 후보의 905–912 RGB 여덟 장이 각각 대조군과 일치했다. 세대 911에 STOP과 잘못된 SEAL 세대를 주입한 별도 재생은 910 공개 후 각각 0xE4와 0xE0에서 끝났다. ARM·포트 모델·65816의 시스템 재생 결과이며, 이번 단계에서 새 실기 FPS와 메뉴 복귀를 측정하지 않았다. [세대별 클록·레코드·오류 재생 결과](../analysis/plan975-results.json)

## 후속작업

다음 대상은 전송할 map 행이 없었던 세대 911의 BG 처리 4.39ms다. BG 슬롯 조회, 33개 셀의 행 비교·쓰기, 스크롤 테이블 생성을 각각 계측한다. 이전 입력과 행이 같아도 대상 뱅크의 슬롯·표시 이력이 달라질 수 있으므로 이력이 일치하는 행만 재사용할 수 있는지 검증한다. MMC966 실기 기준과 스크롤 선행 발행을 유지하고 908 공개·911 공개·912 최종 ACK까지 함께 개선되는 후보만 다음 실기판으로 넘긴다.

재현에는 973과 같은 TEMP와 973 before232 링크를 사용한다. `nes_plan975.py prepare TEMP`와 `--keys`로 두 후보 소스를 각각 생성하고 `build_nes_trial577.ps1`로 전체 링크한다. `run TEMP --phase N`을 각 후보·위상에서 실행하고 `profile TEMP --phase N`으로 원래 ARM을 계측한다. `check_nes_plan975.py TEMP TEMP/nes-MODE-FAULT --mode MODE --guard FAULT`로 두 후보의 stop_decode와 bad_seal을 재생한 뒤 같은 스크립트에 TEMP와 결과 JSON 경로를 주어 집계한다.
