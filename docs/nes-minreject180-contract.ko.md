# NES180 — 첫 거부·회복 최소 기록 실기 시험판

관측 상태를3비트로 줄인 후보가 기능·배치·실제 클록 타이밍·조건부 외부 경로·펌웨어 링크 검증을 통과했다. `NES180-SMB3-EPISODE.zip`을 실기 시험용으로 채택한다. **화면 정지 해결과 약60fps는 아직 확인되지 않았으며 이 변경 자체는 화면 구현을 수정하지 않는다.**

## 축소한 동작 계약

기존180 후보의 직전 오류25비트 비교와 최초 위치26비트 저장을 없앴다. 남은 상태는 `armed`, `owned_seen`, `previous_bad`다. 기존16×96비트 RAM에 현재 후보의 오류·수집 개수를 직접 기록한다. 추가 프레임버퍼·세이브 SRAM을 사용하지 않는다.

- 최초 유효 geometry가 소유권을 얻으면 관측을 시작한다. 실제 화면 표시 ACK를 기다리는 규칙은 아니다.
- 이후 첫 비유효 geometry에서 거부 사건1개를 기록한다. 거부가 계속되는 동안에는 오류 값이나 위치가 달라져도 추가 기록하지 않는다.
- 다음 유효 geometry에서 정상 회복 사건1개를 기록한다. 이후 새 거부/회복 구간에도 같은 규칙을 적용한다.
- 같은 후보를 오래 보유해도 한 번만 기록한다. release·reset은 기존 소유권 규칙을 따르고, STOP/fault 뒤 history 동결은 유지한다.
- 첫 거부 이전의 일시적인 시작 오류는 남기지 않는다. 초기부터 유효 후보가 한 번도 없으면 기록이 없을 수 있다.

따라서 최초 오류의 line/dot/PPUMASK, 연속 거부 중 원인 변경, 모든 프레임의 실패 목록은 얻지 못한다. 오류/개수는 소유권 확정 때 값이며 조기 실패로 후보가 닫히면 나중에 발생할 다른 오류까지 포함하지 않는다. 첫 레벨의 실제 거부 주체를 좁히기 위한 최소 범위이며 FPS 계측이 아니다.

## 기록 규격3

명령77의 마지막 바이트는3, 로그 표기는 `LAST16_EPISODE180_V3`다. MCU는 규격1·2를 거부하고 규격3만 읽는다. 기존64비트 ROM 오류 문맥과 입력 기록은 변경하지 않는다. 유효하지 않은 ROM 문맥 공간도 재사용하지 않는다.

96비트 사건의 MSB 순서는 다음과 같다.

| 항목 | 비트 | 의미 |
| --- | --- | --- |
| kind / generation | 2 / 8 | 1=거부,2=회복 / generation modulo256 |
| errors | 25 | ROM1 + raster8 + compact8 + fetch8 |
| reserved line / dot | 9 / 9 | 항상511; 측정 위치가 아님 |
| candidate display mask | 8 | 후보의 `native_display_mask`; 첫 오류 시점의 PPUMASK가 아님 |
| rows / groups / objects / exceptions / palettes | 8 / 6 / 8 / 8 / 5 | 소유권 확정 때 개수; 팔레트31에서 포화 |

`tools/decode_nes_minreject180.py`로 TXT를 읽는다. 위치가511이 아니거나 규격 표기가 다르면 거부한다. 오류25비트 전체는 유지하므로 실제 fetch/compact/raster 원인을 구분할 수 있다. row193의 렌더링 중단 시점은179 기준 실행 자료로 참고하되 실기 위치로 주장하지 않는다.

## 실행한 검증

- 전체 SV 컴파일 및 실제 SPI 읽기: 시작 오류 생략, 첫 거부, 오류가 바뀌어도 연속 거부 생략, 정상 회복, 반복 정상 생략, 취소, 순환16개, STOP/fault/reset 통과. 연속 보유9클록 동안 중복 기록도 검사했다.
- 실제 C 판독16경우: 규격1·2 거부, 잘못된 descriptor/태그/길이, 순환 순서·부분/빈 기록·전송 실패 처리 통과. 독립 디코더5벡터로 전체 필드와 위치 미측정 규칙을 확인했다.
- 전체 ARM 링크:198,012바이트, static RAM26,564바이트, RUN37,312바이트·IRQ508바이트를 반영한 여유1,040바이트. 기존 플랫폼/라이브러리 명령 보존과 최대TXT3,921/4,096바이트 통과.
- 단일 FIT:15,061 LE / 962 LAB / 36 M9K. 실제4클록·3코너 최저 setup +0.096ns / hold +0.155ns, NES 클록 setup +7.762ns. 변경 없는 더 엄격한 내부 구현 예산에서는 −0.306ns가 남으며 이를 실제 클록 통과와 구분한다. 타이밍 제약이나 seed는 변경하지 않았다.
- 배치 DB 복사본에서 조건부 IO 확인: PSRAM70ns 가정 여유+2.132ns, SNES 읽기77.858ns<270ns, SPI 응답166.488ns<190.476ns. 영상 payload 음수 reset 경로0. 전기 특성·전체CDC/MTBF·실기 타이밍을 전부 보증한 것은 아니다.
- 실제 채택 입력 재생성, 게임 제어 경로 보존,4096바이트 SNES MIF 동일성을 확인했다. 기존178 SNES/전송 경계 시험은 동일 구현 근거로 재사용하며 새 실행으로 계산하지 않는다. 새 FPGA 압축은 복호화해서 RBF 원본과 바이트 단위로 대조했다.

첫 checker와 최종 checker 사이의 변경은 설명 주석 정정이며 배치·시험 입력은 동일하다. 최종 결과는 `verification02.json`을 사용한다. 기존 RAM/문맥 공유 실패 후보와 해당 완료 기록은 변경하지 않았다.

## 다음 실기와 이후 작업

[설치·시험 안내](nes-game180-ready.ko.md)에 따라 숫자1 타일→A로 첫 레벨에 들어간다. 새 TXT2개와 메뉴 복귀 여부를 확인한다. 같은 화면 정지라면 영상이나044 복원 재시험은 필요 없다. 이 조합이 준비된 뒤에는 같은 FIT·장시간 무입력 부팅 모델을 반복하지 않는다.

실기 오류 벡터에 맞춰 공통 렌더링 중단·재개 및 누락 fetch 표현을 구현한다. 허용 조건을 무조건 제거하거나 ROM 이름·고정 주사선으로 예외 처리하지 않는다. 영상 정지 해소와 함께 앞단 차분/base-generation/최종ACK를 통한 약60fps 목표를 유지한다. 그다음 장시간 플레이·오류/리셋 종료 로그, 마지막으로 입력 유지 품질을 검증한다.

근거: `analysis/minreject180-verification.json`, `probes/nes-minreject180/progress.json`. 배포178·164 복구·GBC·세이브 SRAM은 보존한다.
