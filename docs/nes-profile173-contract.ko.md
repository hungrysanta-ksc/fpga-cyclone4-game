# NES173 — 약60fps 연속 화면을 위한 실기 비용 측정

## 목표와 범위

172는 초기14회 표시부터 끊겼고 이후 화면이 정지했다. 새 후보의 전송 전 탈락 가능성과 화면 갱신 비용을 분리한다. 173 배포 변경은 MCU 측정뿐이며 **172 FPGA 전체 바이트와 SNES ROM을 그대로 사용**한다. 속도 향상·정지 해결·60fps 달성은 아직 아니다. 목표 간격 약16.7ms와 실제 측정치를 혼동하지 않는다.

## 종료 로그

`trace_schema=173`이다. BEGIN/END/ABORT/COMMIT 횟수·최근 수신 generation·최초/마지막 ABORT 사유를 유지하고, 이전 상세 레코드 위치·첫 중단 크기·시각을 아래 값으로 교체했다. 기존 PPU history157, 입력 기록, sink ACK/통신 실패 로그는 그대로다. 구형 trace166 포맷으로 새 로그를 해석하지 않는다.

| 필드 | 단위와 포함 범위 |
| --- | --- |
| `profile_tick_ms` | 10ms/tick, 기존 MCU 시계 |
| `profile_receive_ticks` | 성공적으로 반환한 수신 단계 누적. 상태 폴링·새 후보 대기·FPGA 생산 대기를 함께 포함 |
| `profile_build_stage_ticks` | 성공한 guard·sink BEGIN·C 화면 변환·패턴 staging 전송 누적 |
| `profile_seal_ack_ticks` | 성공한 SEAL 전송·SNES 처리/표시 ACK 대기·guard 누적 |
| `profile_last_display_tick` | RUN 시작부터 마지막 일치하는 표시 ACK 완료까지 경과 tick |

중간 실패한 단계의 미완료 시간은 해당 누적값에 포함되지 않는다. 32비트 tick wrap을 뺄셈으로 처리하며 RUN 시작·종료 한도는 바꾸지 않았다. 수신 누적값은 정지 후 남은 대기시간 때문에 커질 수 있으므로 마지막 표시 시각과 나머지 단계 비용을 함께 읽는다. 10ms 분해능과 단계 경계 반올림 때문에 각 합은 벽시계와 정확히 같을 필요가 없다. 개별 프레임의 최소/최대 간격, 순수 SPI 처리량, TV의 실제 FPS를 측정한 값은 아니다. 표시 ACK 수에는 같은 그림의 재표시도 포함될 수 있다.

## 검증과 선택

- 실제 C runtime/receiver/converter에 기존 캡처191개 전송을 재생하고 synthetic sink ACK45개로 검증했다. 정상·tick wrap·deadline·잘못된 ACK·IO/service/CRC 실패·poll 한도·잘못된 한도 및 정지된 시계 경로10경우를 통과했다. 실기 속도 증명은 아니다.
- ARM static26564바이트, RUN foreground37328바이트, IRQ508바이트, 잔여 여유1024바이트다. 계측 구조체를48→40바이트로 줄여 timer callback 호출로 늘어난8바이트 스택을 상쇄했다. 실제 high-water 측정은 아니다.
- 실제 종료 formatter의 최대 필드 폭·입력16개·history16개에서3934/4096바이트로 통과했다.
- 부팅 gate·플랫폼 안전 코드·6000tick 제한·ROM 적재·사운드·입력·STOP/메뉴 복귀 경로는 기존172 검증을 재사용한다. 재배치/FIT와 동일한 부팅/A-B/044 시험을 반복하지 않는다.

기존96비트 history RAM을 전송 전 허용 상태로 바꾸는 FPGA 실험도 수행했으나, 배치 후 memory setup -0.077ns로 타이밍 기준을 통과하지 못했다. 이 후보는 **미채택·미배포**이며173에는 포함하지 않는다. 이 실패를 회피하려고 clock/false-path/대기 한도를 바꾸지 않았다. FPGA 관측 후보를 기능 검증 완료나 실기 사용 가능으로 취급하지 않는다.

## 다음 판단

확장 재현24번째 프레임의 line193/dot232에서 `low_phys=21e150`, `high_phys=21e1ff`, `low_log=0150`, `high_log=01ff`를 관측했다. pair_pending=1/address_ok=1/BG이며 같은 타일의 예상 high 주소21e158과 다르다. physical tile은1e15→1e1f, fineY는0→7로 바뀌었다. 기존 예외는 **동일 타일의 fineY 차이만** 표현하므로 ordinary/split 판정이 모두0이 되어 fetch error2·compact error1이 발생했다. 프레임12~23은 유효했으며24는185행에서 불완전했다. CPU/PPU ROM 바이트 비교 오류는 없었다.

이는 모델에서 다른 타일에 걸친 비트평면 읽기를 현재 영상 표현으로 담지 못한다는 근거다. `$2006` 등의 정확한 변경 트리거와 실기 정지 원인은 아직 확정하지 않는다. 다음 구현은 양쪽 원본 타일/행을 보존해 필요한 합성 패턴으로 전달하거나 동등한 표현을 마련하고, 두 소스의 수집·수명·팔레트·행 위치를 검증해야 한다. high 주소만 채택하거나 pair 조건만 완화하면 픽셀이 잘못되므로 금지한다. 전체 장면을 대상으로 무제한 예외 저장소를 늘리는 것도 피한다. [주소·소스 해시와 검증 근거](../analysis/profile173-verification.json).

1. 173 로그로 build/staging·seal/ACK의 누적 비용과 마지막 표시 시각을 확인한다. 초기 구간부터 처리량이 부족한지 평가하며 정지 이후 대기시간을 전체 FPS로 환산하지 않는다.
2. 실제 ROM의 확장 시뮬레이션에서 재현한 전송 전 거부 원인을 확인한다. 모델은 CPU/PPU/MMC3·70ns ROM 응답·배포 collector를 포함하지만 매 프레임 즉시 release하며 실제 MCU/fill/SNES 소비 속도를 포함하지 않는다. 모델 프레임 번호와172의 generation27은 동일 시점의 증거가 아니다.
3. 확인한 그래픽 표현 제한 또는 진행 경계를 최소 수정하고 실제 SMB3로 검증한다. 임의로 잘못된 후보를 허용하거나 같은 관측판·타이밍 미달 후보의 무변경 FIT를 반복하지 않는다.
4. 약60fps 연속 AV 이후 장기 플레이·오류/본체 리셋 로그, 그다음 입력 유지 품질 순서를 지킨다. 세이브 SRAM을 영상 임시 공간으로 사용하지 않는다.
