# 여러 코어를 위한 개발 구조

## 실행 구조

각 코어는 별도 FPGA 이미지로 만들고, 선택한 게임에 맞는 이미지를 로드하는 방향을 기본으로 합니다. GBC·NES·PCE 로직을 한 FPGA 이미지에 모두 넣는 방식으로 계획하지 않습니다. 여러 코어 파일은 SD에 공존하되 실제 메모리·버스·상태는 전환 때 명확히 초기화해야 합니다.

MCU와 SNES 출력 코드는 재사용 가능한 부분과 코어 특유의 요구를 나눕니다. GBC에서 통과한 수치나 구현을 새 코어의 정답으로 가정하지 않습니다.

| 경계 | 공통화 후보 | 코어별 확인 |
| --- | --- | --- |
| 게임 선택·코어 설정 | 파일 선택, 보드 지원 확인, FPGA 설정 실패 처리 | 확장자/헤더 판별, 매퍼, 특수 장치 |
| 로딩·메모리 | 블록 전송·검증·타임아웃·소유권 처리 | ROM/RAM 크기·뱅킹·주소 배치 |
| 영상 | SNES 전송·프레임 소유권 프로토콜 | 해상도·색·갱신·대역폭·변환 허용 범위 |
| 소리·입력 | 입력 전달, 출력 장치 연결 | APU·샘플링·버튼 배치·추가 컨트롤러 |
| 저장·RTC | 파일 원자성·검증·복구, SD 오류 처리 | 배터리 형식·RTC·상태 스키마 |
| 메뉴 | 공통 조작·표시·설정 저장 | 코어별 사용 가능한 기능 |
| 진단 | 로그 정책·후보 ID·증거 형식 | 관측 레지스터·덤프 범위·타이밍 영향 |

## 지금 유지하는 실제 경로

GBC 구현은 `src/fpga`, `src/firmware-overlay`, `src/renderer`에 있습니다. `cores/gbc/README.md`와 `cores/registry.json`이 실제 경로를 안내합니다. 검증된 QSF/SDC·생성기·source-manifest 해시를 보존하기 위해 이번 문서 정리에서는 이동하지 않습니다.

NES/PCE는 `cores/nes`, `cores/pce`의 조사 문서만 존재합니다. 구현이 시작되면 전용 소스 경로와 빌드 항목을 추가합니다. 공통 소스 분리는 새 경로로 빌드·기능이 동일함을 증명하는 별도 변경으로 수행합니다.

## 새 코어의 최소 계약

제안서에는 대상 보드, upstream URL/commit/고지, 입력 형식, 자원·클록·RAM 예산, 프레임·오디오 처리량, 리셋·SD 오류 복구, 지원 저장 형식을 기록합니다. 미측정 항목은 미측정으로 둡니다.

코어별 상태는 **조사 → 독립 합성 → MCU/출력 통합 → 실기 후보 → 제품 편입** 순서로 관리합니다. 보드 timing·CDC 검증 한계를 별도로 기록하며, 최종 적합성 판정을 실기 표본 하나로 대체하지 않습니다.

## 회귀 원칙

- 코어 전용 변경: 해당 코어의 영향 범위 검사.
- 공통 로더/SPI/메모리/메뉴/저장 변경: 기존 제품 코어의 시작·복귀·저장·리셋 회귀.
- 코어 전환: A → 메뉴 → B → 메뉴 → A에서 잘못된 SRAM·오디오·화면·상태 잔류가 없는지 확인.
- 파일 경로와 상태 파일은 core ID/ROM identity로 구분하고, 새로운 코어가 기존 저장을 잘못 읽지 않도록 한다.
- 진단은 기능 플래그와 파일 기록 정책을 분리한다. 로그를 끄면서 필수 통신·동기화 코드를 제거하지 않는다.

실험 결과를 제품에 편입할 때 새 코어 코드뿐 아니라 공통 MCU·출력 경로에 미친 영향도 함께 검토합니다.
