# 951의 HDMA 선행 발행과 표시 마감

## 판정

621을 유지한다. 625 tables-bg와 같은 951을 실행해 raw·HDMA 일곱 패킷이 늦는 원인을 분리했다. ARM이 확정한 데이터를 map 앞으로 옮기면 65816이 일곱 개 모두 직전 VBlank 마감 **6ms 이상 전**에 받는다. 대신 팔레트 네 패킷과 OAM 세 패킷(합계 519B)이 마감 뒤로 밀린다. 951 표시는 양쪽 위상에서 4 VBlank였다.

| ARM 후보 | 951 SEAL 발행의 마감 초과 (ms) | 밀집 5화면 합계 (VBlank) | 밀집 5화면 실제 표시 간격 합계 (ms) | 957 마지막 ACK 차이 (ms) |
|---|---:|---:|---:|---:|
| 625 기준 | 5.861 / 6.625 | 20 / 20 | 332.602 / 332.557 | 기준 |
| map 순회만 변경 | 6.518 / 6.716 | 20 / 20 | 332.543 / 332.590 | −0.180 / +0.163 |
| 섹션 5를 map 앞에 발행 | 7.239 / 7.093 | 20 / 20 | 332.548 / 332.547 | −0.184 / +0.156 |
| 섹션 5를 map 뒤에 발행 | 6.404 / 6.396 | 20 / 20 | 332.538 / 332.538 | +16.634 / +16.812 |

각 칸은 시작 위상 1 / 2다. map 앞 후보는 순회만 바꾼 대조군보다 마지막 ACK가 0.004 / 0.007ms 빨랐지만 표시 횟수는 같았다. map 뒤 후보는 양쪽 모두 938에서 이미 VBlank 한 번을 놓쳐 957까지 회복하지 못했다. 922 표시(92번째 VBlank), 923 첫 ROM 응답, 954의 첫 허용 구간 BG 96회, 952·954·955 각각 표시 간격 4회와 957 최종 대기 0회를 확인했다.

## 일곱 패킷의 경로

시간 원점은 951을 한 VBlank 일찍 표시할 때 사용해야 할 246번 선의 끝이다. 음수는 마감 전, 양수는 마감 후다. 이 원점 이후의 SEAL 발행 지연은 회복해야 할 시간의 하한이다. 수신·검사·잔여 DMA에도 시간이 든다.

* 625에서 두 행의 raw 원본, mode·enable 표와 길이 6B 전체가 독립 캡처와 일치한 시각은 −15.738 / −15.531ms였다. 384B 전송 순서로 재배열한 scratch의 마지막 쓰기는 −5.564 / −5.015ms였다. 첫 raw 패킷의 ARM serializer 진입은 −0.695 / +0.068ms, SPI 발행은 +0.041 / +0.804ms, 65816 head 수락은 +2.151 / +2.934ms였다.
* 준비 시작 훅을 추가해 같은 53화면을 다시 실행했다. raw 패킹의 첫 쓰기부터 마지막 쓰기까지는 0.038ms였다. 같은 raw에 대한 패킷 범위 계산은 −1.150 / −0.387ms에야 시작했고, 첫 serializer 진입까지 0.455ms가 걸렸다. 표의 범위 계산은 마감 뒤 +2.633 / +3.396ms에 시작해 첫 serializer 진입까지 0.694ms가 걸렸다. 전체 일정·패킷과 기존 관측 이벤트가 추가 훅 실행과 일치했다.
* 일곱 패킷의 오프셋은 1121·1187·1249·1443(raw), 1505·1745(표), 1748(길이)이다. 원본 바이트의 마지막 쓰기, 전체 문맥 확정, raw 패킹 완료, serializer 진입, header 완성, E1 시작·PUSH, 65816 head와 ACK를 패킷별로 대조했다. header와 실제 전송 바이트의 SHA-256, 압축 해제한 payload와 원본도 일치했다. 전체 문맥 확정 전 개별 쓰기 시각은 발행 허가로 사용하지 않았다. [패킷별 측정](../analysis/tail627-verification.json)
* 전체 문맥 확정에서 마감까지 공유 SPI는 10.564 / 10.455ms 사용됐다. 양쪽 위상 모두 마지막 tile 소비는 마감 전에 끝났다. 506B 선행 발행을 시작하면 같은 SPI와 queue credit을 써야 하는 다른 섹션이 순서를 기다린다.

## 후보와 보호 조건

625 원본, 3행 map 마스크 순회만 줄인 대조군, 섹션 5를 남은 map 앞에 놓은 후보, map 뒤·팔레트 앞에 놓은 후보를 비교했다. 선행 후보는 raw 두 행이 준비되고 END 처리 뒤 plan 한 묶음이 제출됐으며 남은 제출 항목이 0개인 경우에만 쓰였다. 각 E1은 원래 bulk·credit 처리를 거친다. map 앞 후보는 조건에 들지 않는 화면에서도 raw 패킹 자체를 map 앞으로 이동하므로 전체 연속 일정을 비교했다.

ARM Flash 한도는 212,992B다. 625는 212,976B, 순회 대조군은 212,920B, map 앞 후보는 212,988B다. map 뒤 후보는 213,004B로 12B 초과해 진단 실행으로만 비교했다. 비용 계산을 공유한 두 전체 링크는 각각 212,996B, 정렬된 6B 길이를 직접 직렬화한 전체 링크는 213,000B였다. 두 발행 후보의 .data는 10,040B, .bss는 18,592B다.

두 발행 후보는 각 위상에서 951을 포함한 23화면에 선행 조건이 적용됐다. 후보와 기준의 53장 RGB와 map, 소비 tile·ordinary·raw, VRAM DMA 총량 114,352B와 ROM 읽기 횟수가 일치했다. 실제 링크의 ARM 세 개에 각 579개 map 마스크와 enqueue 실패 후 커서, E0 CRC·카운터·identity 오류와 STOP을 주입했다. 65816은 새 head·STOP 우선 및 두 뱅크의 누락·중복 검사 9건을 통과했다.

951에서 위치를 달리해 STOP을 네 번씩 주입했다. 1187과 1505에서는 해당 패킷이 정상 은퇴한 뒤 STOP을 읽어 quiet에 진입했다. 1748과 최종 표시 직전에는 소유 중인 패킷의 취소 ACK가 0xE4였다. 양쪽 모두 이전 46개 표시만 확정했고 950 화면을 그대로 보존했다. 최초 시험의 watchdog은 유휴 상태에서도 0xE4를 기다려 발생했다. 수정한 하네스는 실제 quiet 진입, STOP 래치, 마지막으로 은퇴한 head의 identity를 확인한다.

## 다음 측정 순서

1. 951에서 남은 map 8개는 192B씩 1,536B, E1 전체로 1,688B다. 첫 SPI 발행부터 마지막 PUSH까지 6.527 / 7.086ms였다. 동일 대상 뱅크의 직전 최종 표시(949)와 바이트별로 대조하면 실제로 달라진 것은 56B다. 4B 묶음 단위로는 변경 그룹 112B와 마스크 48B로 표현할 수 있다. 기존 헤더를 유지한다고 가정한 **1,376B·4.19ms**의 순수 전송 절감 상한이다. 새 이력 식별, ARM 생성, 독립 복원·검사, credit·DMA 비용을 차감해야 한다.
2. BG map 확정에서 최종 planner 준비 진입까지 두 위상 모두 2.871ms 동안 SPI가 비었다. 이 구간의 ARM은 planner를 실행한다. 먼저 행별 확정·대상 뱅크 일치·credit 시각을 추적해 실제로 겹칠 수 있는 범위를 구한다. 위 4.19ms와 자동으로 합산하지 않는다.
3. 두 항목을 독립 대조한 뒤 같은 실제 65816에서 결합한다. 512의 열별 압축은 수신 복원 비용으로 후반 표시가 느려졌고 515의 대상 뱅크 이력은 검증된 0 끝부분에 한정됐다. 내부 비영(非零) 그룹을 재사용하려면 독립 손상 검출, 주소·coverage 검사, cold·STOP 뒤 전체 행 복구가 필요하다. 두 위상 모두 951과 밀집 표시 간격, 957 마지막 ACK가 줄고 기존 922·923·952·954·955·957 조건을 지킬 때만 보드 후보로 올린다. [512 실행](nes-transfer512-results.ko.md) · [515 이력](nes-history515-results.ko.md)

같은 4B 그룹 방식을 이미 먼저 보내는 map까지 포함해 계산하면 951–955의 잠재 절감은 각각 1,608 / 1,740 / 754 / 1,644 / 1,586B다. 두 cold 화면은 전체 전송, 기존 반복 패킷과 더 길어지는 후보는 원래 전송을 유지하는 조건이다. 이는 다음 시험의 바이트 예산이며 실측 시간은 위 표의 네 경우에 한한다.

## 재현

625 tables-bg에서 `tools/prepare_nes_tail627.py`로 각 정책을 만들고 `tools/build_nes_trial577.ps1`로 전체 링크한다. [624와 같은 입력](nes-raw624-results.ko.md)과 client에 `tools/test_nes_tail627.py`를 사용한다. 시작 클록은 3,000,000 / 3,178,684, 세대는 905–957이다. `tools/check_nes_tail627_arm.py`, `tools/test_nes_map616_edges.py`, `tools/check_nes_tail627_stop.py`로 보호 경계를 검사하고 `tools/analyze_nes_tail627.py`로 결합한다. 기준 ARM을 다시 실행해 53장의 모든 ACK 클록, 패킷과 65816 이벤트까지 기존 기록과 대조했다.

빌드 입력은 [625 재현 절차](nes-seal625-results.ko.md)를 따른다. `../probes/nes-tail627` 아래 정책 이름은 `control`, `before`, `after`, `after-small`, `after-fit`, `after-native`다. 마지막 세 개는 Flash만 비교한다. 공동 실행 폴더는 원자료 루트의 `nes-tail627-{base,control,before,after}-{1,2}`다. ARM 보호 시험은 해당 빌드의 `guards.json`, 수신기 시험은 원자료 루트의 `nes-tail627-edges`, `nes-tail627-stop02-before`, `nes-tail627-stop-after`에 둔다. 재현한 기준 실행에 준비 시작 훅이 포함되면 별도 `prep` 실행 없이 같은 파일로 검사할 수 있다.

```powershell
python tools/analyze_nes_tail627.py --traces $env:TEMP --plans ../probes/nes-seal538/plans01 --build ../probes/nes-tail627 --out analysis/tail627-verification.json
```

실제 링크한 ARM·65816 코드가 SPI·SysTick·두 슬롯·8프레임 반복 ROM 허가 일정과 함께 실행된 결과다. 실기 기준은 MMC613, 보드 준비 기준은 616B다. 이번에 FPGA와 메뉴 코드는 수정하지 않았고 Quartus와 실기 메뉴 복귀 시험은 추가로 실행하지 않았다.
