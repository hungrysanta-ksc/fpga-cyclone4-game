# MMC509의 8B map 변경 마스크와 부분 DMA

MMC509를 실기 기준으로 유지한다. SMB3 캡처 905~916에서 514는 원본보다 E1 전송과 VRAM DMA를 각각 4,800B 줄였다. 하지만 첫 두 화면 이후 최종 표시 간격이 평균 **93.110 → 104.826ms**로 늘었다. 514는 실기 배포 대상에서 제외했다. 최근 실기에서 확인한 수치는 MMC509의 12.82fps다. [실기 기록](nes-hardware510-results.ko.md) · [측정 JSON](../analysis/trim514-verification.json)

## 구현

- ARM은 기존 map 워드 비교에서 64B 행마다 8B 그룹 여덟 개의 변경 비트를 기록한다. 마지막 표시 이후의 변경을 두 대상 뱅크에 누적하고 해당 뱅크의 정확한 serial·generation·표시 ACK에서만 소거한다. 기존의 최대 세 행 묶음과 전체 반복 워드 전송을 보존한다. 부분 literal은 연속 범위의 앞뒤만 자른다. op10의 기존 16B 헤더에는 실제 offset·length와 생략한 앞뒤를 순서대로 이어 계산한 CRC16을 싣는다.
- 65816은 기존 BEGIN의 epoch·serial·대상 뱅크·표시 이력을 확인한다. op10은 이전 최종 ACK를 공개한 뱅크에만 허용한다. 현재 패킷의 행 범위, 중복 수신, 정렬, 크기, 대상 WRAM의 생략 바이트 CRC를 확인한 뒤 실제 길이만 staging한다. 행 전체의 논리적 수신 범위와 VRAM DMA의 실제 바이트 범위를 별도로 기록한다. cold는 현재 수신한 64행 모두를 요구한다. STOP과 오류는 두 뱅크의 공개 이력을 무효화한다. CRC16은 충돌 가능성이 있는 전송 검사다. 비교 시험에서는 생략 바이트까지 독립적으로 직접 대조했다. [생성기](../tools/nes_trim514.py)
- 공통 CRC와 종료 로그 포맷 공유의 영향을 분리하기 위해 같은 변경만 적용하고 원본 map ARM·65816을 쓰는 대조군도 실행했다. 입력 SPI 형식, START·STOP 및 base 복구 경로는 MMC509와 같다.

## 같은 일정에서의 비용

동일한 SMB3 12개 입력, 시작 3,000,000 master clocks, ROM stride 48·phase 0, ARM CPI 2, 같은 IRQ·SPI 드라이버 비용과 두 bulk 슬롯을 사용했다. 후반 값은 906의 최종 ACK부터 916의 최종 ACK까지 열 구간이다. 실제 링크한 ARM과 65816 코드를 실행했다. SPI·IRQ 도착과 ROM 허용 구간을 모델링한 결과이며 이번 후보의 실기 FPS는 측정하지 않았다. [공동 일정](../tools/test_nes_trim514_schedule.py)

514의 ARM 작업공간 끝은 168B 증가했고 관측 스택 여유는 160B 줄었다. 65816은 공개 이력과 검사 임시에 WRAM 8B를 추가했다. 세 경우 모두 관측한 65816 스택 사용은 11B다. 스택 수치는 이 입력에서 관측한 값이다.

별도 65816 계측에서 같은 88개 map 패킷의 수신 가능 시점부터 ACK까지 합계가 전체 literal **62.222ms → 부분 literal 210.717ms**였다. 같은 구간에서 4,800B를 생략해 아낄 수 있는 SPI 선로 시간은 2.625Mbps 기준 14.629ms다. 공동 일정에서는 E0 조회가 638회 증가해 이것만으로 12,760B가 추가되었다. 소비 시간·선로 시간을 합산해 전체 지연으로 간주할 수는 없다. 실제 최종 ACK에서 후반 합계는 원본보다 117.156ms 늘었다. 첫 표시의 개선은 원본 map을 쓰는 대조군에서도 나타났다. [패킷별 소비 계측](../tools/measure_nes_trim514_consume.py)

Quartus Lite 25.1의 EP4CE15F17C8 전체 배치 결과는 원본과 514 모두 **15,164/15,408 LE, 조합 함수 14,172, FF 8,394, RAM 264,816bit, M9K 51개**다. nominal·implementation의 관련 setup은 +0.078ns, hold는 +0.139ns였다. 보드 입력 중 65816 프로그램 초기화 내용만 교체했다. 기존 SDC 예외도 그대로 적용했다.

## 정확성 및 복구

- 12개 최종 ACK 및 EA, VBlank 표시, 396개 논리 패킷의 내용·순서, RGB 12장이 원본과 일치했다. 각 표시 시 대상 WRAM과 VRAM의 map 4,096B를 독립 planner 이미지와 비교했다. 실제 보드 E1 RTL을 별도로 실행해 ARM 일반 패킷 364개를 read·ACK까지 대조했다. 이 중 부분 map은 88개다. CRC 오류와 공통 reset 뒤 queue clear도 통과했다. [E1 RTL 시험](../tools/test_nes_trim514_queue.py)
- 실제 65816은 CRC가 맞는 cold 부분 행, 과거 coverage를 채워 둔 cold 행 누락, 잘못된 witness·대상 WRAM·섹션·정렬·범위를 거절했다. 검사 중 및 최종 표시 전 STOP에서는 이전 표시 serial과 RGB를 유지하고 늦은 최종 ACK를 공개하지 않았다. STOP 직후 양쪽 map WRAM·VRAM 덤프를 새 실행에 넣고 두 cold 화면을 다시 받아 각각 64행이 복구되는지 확인했다. 이 복구는 에뮬레이터 재시작으로 수행했다. [65816 시험](../tools/test_nes_trim514_guards.py)
- 실제 ARM은 표시되지 않은 ACK, 잘못된 serial·generation·bank와 STOP 뒤 늦은 ACK에서 양쪽 마스크를 무효화했다. 새 epoch에서 양쪽 모두 전체 행으로 시작했다. 동일 ELF의 base-only 복구 시험에서 정상 경로는 base 복원 뒤 메뉴 반환을 허용했고 program·DONE·busy·token 오류에서는 안전 반환을 차단했다. 실제 메뉴 복귀 확인은 기존 MMC509 실기 결과에 속한다. [ARM 이력 시험](../tools/check_nes_trim514_history.py) · [base 복구 시험](../tools/check_nes_transfer512_recovery.py)

## 다음 판단과 재현

생략한 바이트를 패킷마다 65816에서 다시 순회하는 514는 종료한다. 다음 비교에서는 이전 최종 ACK에서 확정된 대상 뱅크·행 이력을 소비자가 보관해 다음 부분 전송을 검증하는 방식을 검토한다. 이력 생성·저장, 잘못된 범위 및 손상 검출, STOP 무효화까지 포함하고 MMC509와 공통 코드 대조군 모두보다 후반 최종 ACK 간격이 줄어야 실기 후보로 삼는다.

[재빌드 입력](../cores/nes/REPRODUCING.ko.md)에 따라 MMC509 ARM03과 513의 capture04를 준비한다. `nes_trim514.py`로 patch와 client를 만들고 공통 코드 대조군은 `--control`로 생성한다. 두 ARM 패치를 기존 `build_nes_mmc479_arm.ps1`로 링크한다. 507 보드 입력에 `prepare_nes_transfer512_board.py --variant map`으로 새 client를 넣고 Quartus Lite 전체 compile과 기존 timing506.tcl을 실행한다. 512 원본 일정과 514의 대조군·부분 DMA 일정, guard·E1·소비 시험 결과를 [분석기](../tools/analyze_nes_trim514.py)로 대조한다. 원본 ROM과 SD 전달본은 이 실험의 Git 산출물에 포함하지 않는다.

로컬 선택 자료는 `probes/nes-trim514/selected-evidence02.zip`에 34개 파일로 보관했다. SHA-256은 `6b138db785f3b709e78854d07cf9deb25aa0a342fe43de95e95e4e50ee607c4f`이다.
