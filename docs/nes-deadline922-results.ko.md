# 922 · 908 공개 뒤 다음 캡처와 912 최종 ACK

MMC915 실기판을 대조군으로, 921 compact와 같은 920 65816·914I 보드 경로에서 ARM만 바꿨다. 동일 입력 905–912를 기존·빈 캐시 각각 두 시작 위상에서 연속 재생했다. 아래 클록은 21,477,272Hz 기준이다. 표시 간격 합은 906 공개부터 912 공개까지 여섯 간격이며, 마지막 ACK는 65816이 실제로 쓴 시각이다. 실제 ARM 링크와 65816 명령을 실행했고 공유 SPI·ROM 허가·IRQ는 기존 재생 모델을 사용했다.

## 기존 캐시에서 908의 이득이 사라지는 경계

921에서 908 공개는 39→38 / 40→39로 앞당겨졌다. 이후 909와 911은 입력과 SEAL이 모두 MMC915보다 빨라졌지만 공개 VBlank는 같았다. 아래의 각 쌍은 위상 1 / 2 순서다.

| 세대 | 마지막 COMMIT D2가 앞당겨진 시간 | SEAL 수락이 앞당겨진 시간 | 921 SEAL 수락선 | SEAL 뒤 DMA | DMA 종료선 | 공개선 |
|---|---:|---:|---:|---:|---:|---:|
| 909 | 6.174 / 6.032ms | 7.218 / 7.068ms | 76 / 77 | 17건 2,320B | 251 / 251 | 253 / 253 |
| 911 | 5.898 / 5.801ms | 1.658 / 1.496ms | 48 / 49 | 7건 1,664B | 242 / 242 | 243 / 244 |

두 세대 모두 직전 VBlank가 끝난 뒤 SEAL을 받았다. 909의 마지막 352B OBJ가 준비되고 물리 뱅크가 반환될 때까지 약 2.61ms, 반환부터 SEAL까지 약 1.39ms가 더 걸렸다. 910의 캡처는 이 타일 처리와 겹친다. 캡처 데이터가 준비돼도 이전 타일 reader와 뱅크가 해제돼야 새 입력을 제공할 수 있다.

OAM 중간에 큐를 비운 후보(idle)는 909의 16+32+32+384B를 선행 DMA했다. 909 ACK는 7,188 / 7,234클록 앞당겨졌다. 반면 910 입력 제공은 30,017 / 30,063클록 늦어지고 마지막 COMMIT D2도 15,748 / 15,839클록 늦어졌다. 921에서 이미 다음 캡처선을 11,314 / 12,688클록 넘긴 경계다. 909의 잔여 DMA만 줄여도 911의 입력은 앞당겨지지 않았다.

## 빈 캐시에서 처음 놓친 마감

911의 데이터 END와 최종 COMMIT의 D2를 구분했다. 다음 캡처 시작을 결정하는 것은 마지막 COMMIT D2다. 921에서는 16,082,128 / 16,439,765클록으로 각각 시작선을 568 / 837클록 넘겼다. 이 때문에 912 캡처와 표시가 한 주기씩 밀렸다. 원래의 496B 선행 DMA는 두 위상에서 같은 목적지로 실행됐다.

묶인 행·팔레트의 순서와 범위를 한 번 구하고 각 값의 상한을 검사하는 rows는 911 D2가 캡처선보다 1,611 / 424클록 빨랐다. 빈 캐시 여섯 간격이 17 / 17에서 16 / 16으로 회복됐고 기존 캐시 908 공개도 유지됐다. 이 구현의 전체 링크는 213,000B로 한도를 8B 넘겼다.

## 한도 안에서 회복한 결과

첫 값을 기존 단일 레코드 검증기로 처리하고 나머지 값의 상한을 검사한 firstrow는 212,988B로 한도보다 4B 작았다. 빈 캐시 911 D2가 캡처선보다 970 / 710클록(45.2 / 33.1µs) 빨랐다. 912는 VBlank 50 / 51의 240선에 마지막 DMA를 끝내고 242선에 공개했다. raw 픽셀을 낮은 비트부터 역순으로 풀어 코드 크기를 줄인 suffix도 212,980B에서 16 / 16회와 기존 캐시의 908 공개 이득을 유지했다.

총 13개 ARM 후보 중 네 조건에서 간격 합과 최종 ACK를 모두 개선한 후보는 없었다. 실기 기준은 MMC915를 유지한다. 후속 비교에는 빈 캐시 회귀를 해결한 firstrow를 사용할 수 있다. 다음에는 909의 연속된 32B OBJ 뱅크 반환과 마지막 352B 공급을 한 시간축에서 다룬다. 마지막 352B 반환을 앞당기면 910의 입력을 일찍 열 수 있는지 확인한다. 911은 위상 1에서 E9 발행 뒤 첫 32B OBJ 준비까지 11.77ms가 걸렸으므로 ROM 허가와 두 뱅크 점유를 따로 측정한다.

## 재현과 판정

각 후보는 같은 921 링크의 복사본에서 생성한다. 입력 복원, SEAL 대기 중 조회 주기, OAM 발행 중 큐 drain, 마지막 타일 우선 완료를 분리했다. 전체 링크 빌드 후 기존·빈 캐시 각각 위상 1·2를 실행한다. 분석기는 8장 RGB·map·팔레트, section 5 내용과 coverage, 타일 데이터와 E9 묶음 크기를 대조하고 마지막 D2와 SEAL·DMA·공개·ACK를 같은 세대로 묶는다. 압축 입력의 손상 사례는 실제 ARM 진입점에서, 잘못된 descriptor·중복·손상 SEAL·복사 중 STOP은 실제 65816에서 주입한다.

firstrow의 입력 검사는 대조군과 같은 42건을 통과했다. 길이 1·7·8의 행과 팔레트에 대해 정상 값, 마지막 바이트 범위 오류, 다른 세대, 순서·개수 오류, 잘못된 토큰, 잘린 입력을 검사했다. 실패 후 다음 패킷도 거부하고 token을 소비하지 않는지 확인했다. SRAM D0 네 곳, 불량 CRC 거부, STOP과 base·메뉴 복구는 최종 링크 시험으로 확인했다. FPGA·65816 변경이나 신규 실기 측정은 없다.
