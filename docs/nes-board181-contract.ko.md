# NES181 실제 보드·전체 ARM 통합과 FPGA 자원 검사

PPU 색상·강조색→부분 행 수집기→전송기와 paired MCU/SNES를 격리 빌드에 연결했다. 전체 ARM 링크와 RUN/IRQ 스택 검사를 통과했다. FPGA는 합성을 통과했으나 배치에 **965 LAB / 기기 한도963 LAB**가 필요해 아직 설치 가능한 시험판이 아니다.

## 이번 연결

- `tools/nes_board181.py`는 승인된180의62 FPGA 입력과1,413 MCU 소스 해시를 확인하고 새 디렉터리로 복사한다. 기존180을 수정하지 않는다.
- `nes_live_joint.sv`의 실제 `color/emphasis`를 frame181에, `patch_count`를 export181에 연결한다. query 종류7이 기존 fill 우선 조회 중재를 거쳐 픽셀 RAM에 도달한다.
- ROM 서비스·PSRAM 중재·fill·SPI·mailbox·리셋·클록·한도는 그대로다. QSF에서 frame/export를 바꾸고181 모듈을 추가했다. 4KB `sink-program.hex`는 이미 검증한 client181 본문과 동일하다.
- MCU는 receiver181/video181/sink181을 기존165 이름/API로 함께 배치했다. version1811은 FPGA→MCU, version1812/SEAL24는 MCU→SNES 규격이다.181 진입 이름·파일 경로를 함께 갱신했다.
- 세이브 SRAM은 사용하지 않는다. 장기 플레이·입력 유지 검사는 아직 진행하지 않는다.

## FPGA 자원 개선

첫 통합 `map01`은 합성 성공 후 **971 LAB**가 필요해 배치 준비에서 실패했다. 따라서 그 결과로 타이밍을 승인하지 않았다.

compact의 이전 행33개×15비트는 타일 비교와 map 복사에서 서로 다른 주소로 읽었다. 복사 중 BG 이벤트는 기존 검사에서 거부되므로 두 읽기 용도는 동시에 필요하지 않다. `tools/nes_board181_area.py`는 `copy_busy`에 따라 단일 주소와 읽은 값을 공유한다. 입력/출력 클록 수, 행당33셀, group32·부분 행7개·오류 검사와 버퍼 수명은 바꾸지 않는다. 기존 공개 수집기 파일도 덮어쓰지 않는다.

최종 `map03`과 원본181 compact를 같은 입력으로 **3,287,929클록** 비교했다. 관측한 모든 출력이 같았으며,14경우·3,328 raw 픽셀·정상180 대비9,624단어·복구된43,923셀 검사가 통과했다. 이는 해당 시뮬레이션의 동등성 근거이며 형식 검증이나 모든 입력 조합 증명은 아니다.

| 전체 보드 결과 | 최초 map01 | 공유 읽기 map03 |
| --- | ---: | ---: |
| 합성 추정 LE | 19,692 | 19,649 |
| 배치 준비 단계 LE | 15,120 | 14,972 |
| 필요한 LAB | 971 | 965 |
| M9K | 39 | 38 |
| FIT | 실패 | 실패 |

LE148개·LAB6개·M9K1개를 줄였으나 LAB가2개 부족하다. **14,972 LE가 전체 LE 한도에 들어간다는 이유로 배치 성공이라고 해석하지 않는다.** 배치/배선 완료 자원 수치도 아니다. 시드·클록·제약을 바꾼 반복 FIT는 하지 않았다. map02는 같은 아이디어의 선언 순서가 Questa에 맞지 않았던 중간 소스이며 채택하지 않는다. 수정 후 map03/test02를 사용한다.

## 실제 배선 결합 검사

`join01`은 준비된 실제 `nes_live_joint.sv`의 frame·fill·export 인스턴스와 조회 중재 코드를 그대로 추출한다. 합성 PPU 인터페이스로185/186행을 대체하고 최종512픽셀·960 CHR바이트·8,192 fill 조회·5,753클록 전송 대기·1 COMMIT와 공유 해제를 확인했다. 대기 중 레코드 고정, fill 응답의 exporter 누출 방지, raw 슬롯·색·순서를 검사한다.

PPU 인터페이스, 메모리 응답, 호스트 대기/ACK는 모델이다. 실제 PPU/mapper 게임 실행·PSRAM 핀·물리 SPI·SNES 동시 실행 시험은 아니다. 이전 실제 PPU 정렬·SPI→C·C→65816 시험은 소스 동일성을 확인해 재사용하며, 각각의 범위를 합쳐 실기 통과라고 하지 않는다.

## 전체 ARM 결과

선택 `arm02/armcheck01`의 FW는199,604바이트다. static RAM26,564 / RUN 밖 free38,860 / foreground bound37,320 / IRQ reserve508 / **남는 여유1,032바이트**로 기존 최소1,024바이트 기준을 통과했다. 기존180의1,040바이트를 재사용한 결과가 아니다.

실제 ELF·93개 도달 함수·컴파일러 stack usage와 callback 경로를 다시 계산했다. SysTick/TIM2/NMI와 각각의 확장 예외 프레임을 포함한다. 정상 플랫폼/라이브러리 본문은 재배치 주소를 정규화해 기존 검토본과 비교했다. 런타임 고수위 실측이나 모든 메뉴/GBC 호출 그래프의 새 증명은 아니다. compiler/version/호출 경로가 바뀌면 다시 확인해야 한다.

receiver18,064/video15,888바이트와 RUN 전용 수명은 유지한다. binary hash는 [검증 데이터](../analysis/board181-verification.json)에 기록한다. **compile-only FW이며 SD 설치 대상으로 제공하지 않는다.**

## 다음 작업과 인계

1. `map03`을 자원 개선 기준으로 삼되 채택된 실기 FPGA로 취급하지 않는다. 남은2 LAB를 해결할 구조를 자원 보고서에서 선택한다. raster의 팔레트 보관/조회·compact rank 데이터처럼 폭넓은 선택 회로의 공유 가능성을 먼저 검토한다. 파이프라인이나 RAM 변환이 필요하면 데이터 수명·연속 이벤트·동일 주소 충돌·행 종료 지연 계약부터 명시한다. 작은 비트 수정과 시드 FIT 반복으로 돌아가지 않는다.
2. 바뀐 경계만 기능 검사한 뒤 전체 배치·실제 클록 타이밍·조건부 IO/리셋 확인을 한다. 현재 두 FIT는 모두 실패했으므로 STA/ASM/RBF/ZIP 승인 근거가 없다.
3. 통과하면 현재 paired ARM과 client181을 재사용해 최소 SMB3 실기를 준비한다. 월드맵의 숫자1 타일로 이동한 뒤 A로 첫 레벨에 들어가 지속 영상·메뉴 복귀·완료 간격을 확인한다. 같은180/044나 완료된 독립 검사를 반복하지 않는다.
4. 정지 해소와60fps는 별도다. raw 경로 최대7fresh-vblank+final·모델 wire53ms·반복 table 비용이 남는다. 생산/전송/표시완료 간격, raw packing, 뱅크별 기준 세대 차분을 개선한 뒤 장기 플레이/리셋 로그, 마지막으로 입력 유지 품질을 검증한다.

`patch_errors`는 frame의 유효성 판정에 포함되지만 기존25비트 observer에 별도로 기록되지는 않는다. 실패 원인을 조사할 때 기존 오류0을 부분 행 성공으로 오인하지 않는다. 추가 진단은 실제 필요가 생긴 경계에만 제한한다.

이전180 배포 ZIP·GBC·164 복구판과 모든 완료 archive/record/audit는 보존한다. 이번 원시 근거는 `probes/nes-board181`이며 완료 후 수정하지 않는다. 초기 ARM 준비의 이름 위치 오류는 `arm01`, 선언 순서 오류는 `map02/test01`로 보존했다.
