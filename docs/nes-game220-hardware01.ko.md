# NES220 실기: 60초 동작 회복, 스크롤 성능은 미달

사용자는60초 플레이·메뉴 복귀·소리·조작 정상, 오프닝은 눈에 띄게 개선됐지만 첫 레벨은 여전히 끊긴다고 보고했다. **이번 실행에서는215의 조기 종료가 재현되지 않았다.60fps 달성은 아니다.** 세 TXT와62.03초 MOV 원본은 `probes/nes-game220-hardware01/raw`에 SHA256과 함께 보존했다. [재현 분석기](../tools/analyze_nes_game220.py), [분석 결과](../analysis/game220-hardware01-verification.json).

## 실행·종료 판정

- ROM 적재와 대조393,216B, 검증·RUN·STOP·base 복원 정상. 실제 메뉴 복귀는 사용자와 영상에서 확인했다.
- DISPLAY_NEXT231,680ms → DISPLAY_STOPPED291,760ms: **60.08초**. 메뉴 준비294,990ms. 최초 로딩 약3분51.68초는 별도이며 로딩 속도를 고친 시험이 아니다.
- 표시 완료265회, 마지막 표시59.81초/gen382. 전체 평균 완료율 **4.41회/초**, 평균 간격226.72ms, 최대 기록 간격440ms. 이는 CRT 주사율이나 특정 스크롤 장면의 정확한 FPS가 아니다.
- 최초 종료 `native_result=1`은 시간 제한. ROM/receiver/sink/video/window/STOP 오류0, 하위 transfer 실패0,215 상태 오류 표본 `plan_valid=0`.
- `plan_error=2`는 선택 소스에서 guard 실패다. 먼저60초 deadline을 보존한 뒤 다음 작업을 취소한 결과와 부합한다. 이전215의 `plan_error=4`, CRC-valid FPGA fault와 다르다.
- BEGIN/END/COMMIT266, 실제 표시265, ABORT0. 다음 gen383이 처리 중인 상태에서 종료했다. window6,797 sent=retired. 마지막 ACK0은 미완료 작업의 표본이며 이전 표시 성공을 무효로 만들지 않는다.
- `screen_frames=0`은 untrusted 구필드이고 `screen_error=169`는 A9 SPC 초기화 결과다. 화면 실패 코드로 해석하지 않는다. SPC unmute 확인과 사용자 보고상 오디오 정상. 마지막 입력 기록에도 RIGHT+B 유지 중 A 추가/해제가 남았다. 입력 품질 전체를 이16개 표본으로 증명하지 않는다.

216의 정상 승인/출력 대기를 watchdog 실행 시간에서 제외한 수정과 이번 결과는 일치한다. 다만220에는217~220 배선 정리도 들어 있으므로 한 번의 실기로 모든 과거 오류의 유일 원인이나 장기 안정성을 입증하지 않는다. 동일220 또는044 재시험은 지금 필요하지 않다.

## 영상 관찰

FFmpeg 초당2장124장을 추출하고, 그중 초당1장62장을 두 contact sheet로 확인했다. 다음은 **영상 자체의 대략적 시각**이다. 샘플 사이의 정확한 프레임 변화나60Hz를 측정한 것은 아니다.

| 영상 시각 | 장면 |
|---|---|
| 0–1초 | 이미 게임이 출력된 오프닝 |
| 2–4초 | 플레이어 선택 |
| 5–11초 | 월드맵 |
| 12–13초 | 첫 레벨 전환 |
| 14–19초 | 첫 레벨 이동·사망 |
| 20–23초 /24–25초 | 월드맵 /재진입 전환 |
| 26–34초 | 첫 레벨,28–30초에 배경의 수평 스크롤 확인 |
| 35–39초 | 월드맵·재진입 |
| 40–46초 | 첫 레벨,42–43초에 스크롤 확인 |
| 47–51초 | 월드맵·재진입 |
| 52–60초 | 첫 레벨,54–55초에 스크롤 확인·마지막 화면 유지 포함 |
| 61초 | 카트리지 메뉴 |

따라서 실제 첫 레벨과 스크롤 근거가 있다. 오프닝/정지 화면만 본 결과가 아니다. 촬영 시작은 게임 시작 뒤이고, 종료·복원 중에도 마지막 게임 화면이 유지된다. 메뉴가 보인 시각과 로그의 MENU_PREPARED도 같은 에지가 아니다. **5초 bin에 영상 시각을 그대로 붙이거나 마지막 화면 유지 시간을 게임 실행 시간으로 더하지 않는다.** 정확한 MCU/영상 offset을 확보하지 않았으므로 개별 bin을 순수 스크롤 FPS로 확정하지 않았다. CRT 색·대각선 촬영 간섭은 결함으로 판정하지 않았다. 오디오는 사용자 확인이며 별도 청음·파형 검증은 하지 않았다.

## 성능: 재사용은 동작하지만 매번 하는 작업이 남음

| 전체 실행 집계 | 210 | 220 |
|---|---:|---:|
| 실행 시간 | 60.06초 | 60.08초 |
| 표시 완료 | 196회 | 265회 |
| 수신 단계 | 11.20초 | 14.46초 |
| 계획 생성·소스/전송 대기 단계 | 22.10초 | 34.68초 |
| SEAL·소비·표시 대기 단계 | 26.42초 | 10.43초 |
| 계측 SPI clock 바이트 | 7,543,494 | 4,563,094 |

서로 다른 입력·장면이므로 이를 통제된 성능 향상률로 사용하지 않는다. 이번 실행에서 **표시 대기보다 계획 처리 단계가 가장 크다.** 이 단계에는 ARM 계산, slot 검색, 계획 배치, 소스/chunk 대기 및 오디오·입력 service가 함께 들어간다.34.68초를 CPU 계산만의 시간이라고 부를 수 없다.

| 220 명령 분류 | clock 바이트 | 집계 비중 |
|---|---:|---:|
| D0–D3 화면 정보 수신·제어·조회 | 2,264,051 | 49.62% |
| E8 계획/소스 상태 | 415,760 | 9.11% |
| E9 새 타일 계획 | 17,781 | 0.39% |
| E0 출력 상태 | 906,260 | 19.86% |
| E1 출력 명령 혼합 | 957,387 | 20.98% |
| 기타 | 1,855 | 0.04% |

12개 bin의 완료 수·바이트·세 단계 시간이 game 로그와 정확히 일치했다. 실제 목적 bank에 남은 타일 재사용 `slot_hits=22,984`, 내보낸 계획1,938개/생성 출력38,320B다. 이는210의 수동 관찰 모델과 달리 **실제로 계획을 생략하는211 슬롯 재사용**이다. hit는 동일 프레임 내부 중복 제거를 모두 세는 값이 아니므로 `hits/(hits+plans)`를 보편적 캐시 적중률로 쓰지 않는다. 계획에는 zero anchor와 마지막 미완료 작업이 포함된다.

현재2.625MHz에서 전체 계측 wire의 순수 clock 시간은13.91초다. E8/E0만 가상으로 없애도 평균 **37.27ms/완료**, D0–D3만으로도 평균 **26.04ms/완료**다. 이는 현재 프로토콜의 상각 비용이며 조회/헤더·마지막 미완료 작업을 포함한다. 유효 payload의 불변 하한이나 최적화 불가능성 증명이 아니다. 그래도 **ACK 조회만 줄이거나 새 타일 캐시만 늘려16.67ms를 달성할 수 있다는 근거는 없다.** 별도 service/audio SPI와 SNES 병렬 aperture DMA는 이 바이트 집계 밖이다.

첫 bin은40회, 나머지는15–25회 완료했다. 첫 bin의 계획 단계는 완료당67.25ms, 이후123.6–175.3ms였다. 첫 bin은 오프닝/선택이 섞일 수 있으며 단독 오프닝 FPS로 표현하지 않는다. `bg`는 변경 타일 수가 아니라 사용 슬롯의 상한 범위다. 평균28.3에서 이후326.7–504.1로 커졌다. 선택 소스를 보면 모든 geometry cell을 다시 계획하고, 같은 프레임 exact key 및 영속 slot을 선형 검색한다. **캐시가 통신은 줄여도 검색·화면 재구성 비용은 남는 구조**다. 확대된 검색 범위는 유력한 최적화 후보이며 실제 CPU 세부 계측으로 확정해야 한다.

`mapdirty`는64B 단위의 직전 표시 화면 대비 변경 수이며, 실제 inactive-bank 누적 union 업로드 수가 아니다. E1도 map만이 아니다. 스크롤 맵 비용은 중요 후보지만 이 로그만으로 전부 map 전송 때문이라고 단정하지 않는다.

## 다음 작업과 작업 의미

이번 작업으로 **실제 게임으로 성능을 평가할 수 있는60초 동작 기준을 회복**했다. 소리·입력·메뉴 복귀를 유지하면서 오프닝과 스크롤의 격차를 확인했다. 제품 소스/FIT/펌웨어/ZIP을 새로 만들지 않고 PR120에 결과와 다음 우선순위를 기록한다.

1. **수신량·계획 CPU·스크롤 맵을 하나의16.67ms 예산으로 다룬다.** 새 타일 계획은 이미 매우 작으므로 추가 캐시/로더/FIT 미세 수정이 다음 목표가 아니다. 동일한 전체 화면 정보를 매번 재수신하고 재구성하는 비용을 줄여야 한다.
2. 다음 성능 변경에서만 필요한 최소 계측을 함께 넣는다. D0–D3 유효 내용과 조회/헤더, ARM 순수 계획·검색과 callback/drain 대기를 분리한다. 별도 진단판만 반복하지 않는다. 현재 aggregate 로그로 실제 cell/key 순서를 복원할 수 있다고 가정하지 않는다.
3. 정확키 인덱싱·변경 부분 계획과 원본 좌표 기반 scroll-map을 검토한다. hash 충돌 시 전체키 비교, row/alt/mask, CHR 내용 epoch, 활성 bank 보호, 마지막 표시 ACK 후 commit을 유지한다. 단순 MMC3 화면 특례나 오래된 내용 재사용으로 속도를 만들지 않는다. ingress 감소와 함께 예산을 잡으며 검색 개선만으로60fps라고 약속하지 않는다.
4. ARM 여유4,952B, FPGA252LE/6LAB/9M9K를 각각 지킨다. 추가 배열은 기존 scratch 수명/IRQ 여유와 함께 계산한다. 저장SRAM/GBC164/봉인220 및 이전 증거는 보존한다. 최소 의미 검증 후 개선판을 같은 SMB3 첫 레벨의 오른쪽+B/A 반복 스크롤로 평가한다. 사운드·조작·메뉴 복귀를 회귀 조건으로 둔다.

장기 플레이/리셋 로그/추가 mapper 기능보다 현재는 부드러운 화면을 우선한다. 이번 자료는 충분하므로 수정 전 동일 플레이를 다시 요구하지 않는다.
