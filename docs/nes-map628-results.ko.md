# 951의 대상 뱅크 map 재사용과 BG 확정 행 선행 전송

## 비교 조건

시간 기준은 625 tables-bg ARM과 624 client다. 627의 map 순회만 바꾼 ARM을 공통 대조군으로 추가했다. 변경 그룹 후보는 이 대조군의 발행 순서를 따르고, 선행 발행 후보는 원래 map 형식과 65816을 쓴다. 시작 클록 3,000,000과 3,178,684에서 각각 905–957의 53화면을 연결 실행했다. ARM CPI 2, SPI 2.625MHz, SysTick, bulk 두 슬롯, 8프레임 반복 ROM 허가 달력, 실제 65816 명령·DMA·PPU를 포함한다. 모든 경우 표시된 RGB·map 53장, 명령의 논리 작업량, 114,352B의 VRAM DMA와 ROM 읽기 할당량이 일치했다. ## 대상 뱅크가 최종 ACK한 4B 그룹

951에서 192B 패킷 여덟 개의 1,536B 중 28개 그룹(112B)만 전송했다. 같은 세대의 map 전체 E1은 1,982→670B, 해당 SPI 거래 시간 합은 6.538→2.540ms였다. 반면 65816이 map head를 받은 뒤 소비 ACK를 쓰기까지의 합은 5.589 / 5.579→19.883 / 19.886ms가 됐다. E0 진행 조회도 74 / 72→143 / 143회가 되어, **모든 SPI 거래를 합친 바이트는 8,835 / 8,815→8,923 / 8,923B**였다. 겹쳐 실행되는 비용이므로 두 시간의 차를 더해 프레임 시간으로 환산하지 않았다. ARM Flash는 213,680B로 한도보다 688B 컸고, BSS는 1,772B 늘었다. 65816 프로그램 본체는 5,323→5,700B다.

ARM은 오른쪽 map 페이지를 뱅크별 880B의 가변 길이 이력에 보관한다. 이전 표시의 최종 ACK와 resident commit 뒤에 해당 뱅크의 32비트 serial을 공개한다. 대상 이력이 유효하고 4B 마스크·체크 값·변경 그룹의 합이 원래 패킷보다 작을 때만 사용한다. 한 페이지의 이력이 저장 공간을 넘으면 그 뱅크는 일반 행으로 복구한다. 기존 반복 패킷은 우선한다.

65816은 대상 뱅크에서 자신이 최종 표시 ACK 뒤에 공개한 serial과 수신한 base를 대조한다. 실제 비활성 WRAM에 변경 4B를 쓰고 생략한 데이터까지 포함해 16비트 워드 합과 누적합을 독립적으로 계산한다. 길이·경계·coverage 검사를 통과한 행만 수락한다. 두 합은 유한 길이 오류 검출 값이므로 충돌 가능성이 있다. STOP은 64B 행마다 확인하며 cold·오류·STOP은 두 이력을 모두 무효화한다.

## BG 확정 직후 선행 발행

ARM planner가 BG map을 확정하면 기존 credit 검사와 E8 응답을 거쳐 E1을 발행한다. 한 패킷 정책과 최대 세 패킷 정책을 따로 실행했다. 후자는 한 번 성공한 뒤에도 매번 같은 우선순위를 다시 검사한다. 951에서 실제 발행한 것은 양쪽 위상 모두 오프셋 2,048의 192B 한 패킷이었다. 20B E8와 211B E1이 먼저 나갔고 outstanding은 2에서 3이 됐다. 최대 세 패킷 정책은 두 번째 시도에서 새 head·bulk용 여유를 남기는 기존 제한에 도달했다. BG 확정부터 다음 준비 함수까지 2.871ms였던 구간은 각각 3.773ms, 3.775ms가 됐다. ARM이 전송 함수를 수행하는 동안 planner도 그만큼 기다렸다.

## 표시 마감과 다음 시험

- 세 번째 VBlank의 246번 검사선을 포함하는 마지막 허용 클록을 기준으로, 625의 SEAL 발행은 이미 5.861 / 6.625ms 늦었다. 한 패킷 선행 뒤에도 6.002 / 6.612ms, 세 패킷 허용 시 6.265 / 7.247ms 늦었다. 전체 링크 Flash는 각각 212,920B와 212,992B였다. 후속 실험은 625의 패킷 도착을 고정한 채 **비활성 뱅크 행에 대해 이미 끝난 검사와 새 데이터 검사를 분리**하고, 수신→소비 ACK의 실측 상한부터 잡는다. 독립 손상 검출·STOP·cold 복구가 동일하고 두 위상 모두에서 충분한 수신 여유가 입증될 때만 ARM 전송 정책과 결합한다.
## 안전성과 재현

- 실제 ARM 인코더 60개 벡터에서 변경 전송 48건·일반 행 12건을 확인했다. 추가로 손상된 run 경계, 오래된 serial, 발행 중 실패와 reset을 검사했다.
- 65816에 cold에서의 변경 전송, 잘못된 뱅크 이력, 체크 값 손상, 길이 초과·부족, 생략한 WRAM 데이터 손상을 주입했다. 여섯 경우 모두 거부했고, 부분 복원 도중 STOP도 이전 표시를 보존했다. 중단 당시 두 뱅크의 WRAM·VRAM 16KiB를 보존해 재시작하고 905·906을 전체 행으로 다시 받아 두 화면과 최종 ACK를 대조했다. 기존 수신 경로는 STOP·새 head 경합, 누락·중복, 마지막 표시 직전 STOP도 검사했다.
- [625](nes-seal625-results.ko.md)와 [627](nes-tail627-results.ko.md)의 빌드·데이터를 사용한다. 두 준비 스크립트의 base에는 625 tables-bg를 준다. 선행 ARM은 `tools/prepare_nes_front628.py`의 기본 / `--burst`, 변경 그룹 ARM은 `tools/prepare_nes_group628.py`로 생성한다. 각각 `tools/build_nes_trial577.ps1`로 링크한다. 변경 그룹 65816은 `tools/nes_group628.py`로 생성한다.
- 동일 일정에서 기존 624 수신기를 쓰는 선행 후보는 `tools/test_nes_board611.py`, 변경 그룹과 재실행한 공통 대조군은 `tools/test_nes_group628.py`를 사용한다. 확장한 runtime을 시뮬레이터가 이중 할당한 최초 실행은 제외했다. 실제 ELF의 정적 runtime을 사용하는 방식으로 공통 대조군의 두 위상 전체 패킷·65816 타임라인이 기존 627과 바이트 단위로 일치하는지 확인했다.
- `tools/check_nes_group628_arm.py`, `tools/check_nes_group628.py`, `tools/test_nes_map616_edges.py`, `tools/check_nes_tail627_stop.py`가 고장 주입과 재시작을 검사한다. 결과는 `tools/analyze_nes_map628.py --traces $env:TEMP --build ../probes/nes-map628 --out analysis/map628-verification.json`으로 모은다. 보드 준비 기준은 616B, 실기 기준은 MMC613이다. 이번 단계의 범위는 연결 시뮬레이션이다.
- 재시작 도구 최초 실행에서 임시 Mesen의 네이티브 DLL이 0B가 되어 로딩에 실패했다. 정상 코어를 복구하고 재시작도 본 시험과 같은 `--enableStdout` 기동 옵션으로 실행했다. 최종 `nes-map628-guards04`는 일곱 고장 주입과 중단 상태에서의 두 cold 표시까지 한 번에 통과했다.
