# MMC866의 map 행 확정과 23행 전송

## 어느 시점에 전송할 수 있는가

MMC866 ARM 바이너리에서 map 쓰기, BG 슬롯 사용 비트, 행 처리 종료와 BG 완료를 계측했다. 두 시작 위상 모두 계측 전후의 SPI 패킷·65816 이벤트·최종 ACK 기록이 바이트 단위로 같았다. 두 뱅크를 채운 뒤의 무입력 밀집 데모 60장에 **42개 세대, 43개 페이지 묶음**이 있었다. 세대 950은 좌우 페이지가 함께 바뀐다. 직전 보고의 43은 묶음 수다. [원시 시각과 두 위상 비교](../analysis/frontier869.json)

| 실제 MMC866 일정에 대입한 조건 | 위상 1 | 위상 2 |
|---|---:|---:|
| 후보 23행 종료·관련 BG 슬롯 확정 뒤, 다른 장치 대기 제외 | 43 | 43 |
| 다른 SPI 거래·65816 점유·2슬롯 반환 순서까지 고정 | 22 | 24 |
| BG 전체 완료를 기다리고, 이 페이지 하나만 전송하는 조건까지 적용 | 16 | 18 |

행 종료 시점에 참조하는 BG 슬롯은 43개 묶음 모두 확정돼 있었다. 경합을 제외한 최소 여유는 0.361 / 0.437ms였다. 반면 세대 950의 왼쪽 페이지는 BG 전체 완료를 기다리면 원래의 마지막 map 반환보다 1.221 / 1.145ms 늦었다. 표는 **각 페이지를 한 번씩 따로 교체한 계산**이다. 마지막 행 조건을 두 위상에서 함께 만족하는 16개가 모두 오른쪽 페이지여서 이를 실제 실행 대상으로 선택했다.

## 어떤 이력을 넣었는가

두 뱅크 양쪽 페이지를 함께 추적하는 ARM 후보는 세대 950에서 일반 map 패킷으로 보낸 반대 페이지의 행까지 최종 ACK 때 반영해야 했다. 수정 후 62장 전체에서 복원한 두 뱅크가 기준 map과 일치했다. 초기 전체 링크는 214,120B로 Flash 한도를 1,128B 초과했다. [두 뱅크 검사](../analysis/history869.json)

오른쪽 페이지 후보는 가장 최근에 표시한 23행과 두 표시 뱅크 간에 차이가 있는 열을 나타내는 32비트를 저장한다. 이전 뱅크와 달랐거나 이번에 바뀐 열의 합집합이 인접한 1–2열일 때만 54/100B 명령을 발행한다. 확정한 열은 23행 전체를 전송한다. 같은 행이 셋 연속인 곳에서 두 행을 생략해 이력 전체를 1,352B에 넣었다. 용량 초과나 이력 무효화 후에는 일반 map 전송으로 복원한다. [ARM의 직접 실행과 전 단어 대조](../analysis/right869.json)

65816은 세대와 뱅크 이력, 범위와 중복을 확인한다. 변경 단어는 쓴 직후 다시 읽고, 생략 단어는 두 WRAM 뱅크에서 각각 읽어 비교한다. 두 뱅크의 같은 위치에서 같은 값으로 일어난 동시 손상은 이 비교의 검출 범위 밖이다. STOP은 열마다 확인한다. 일반 OAM 재사용은 기존 op9·section4, 새 map은 op10·section2를 쓴다. 최초 통합에서 누락된 기존 OAM 허용과 65816의 확장 명령 진입 분기를 각각 복구했다. 다음 재생에서는 923·924가 실제 묶음을 수락한 뒤 925에서 ARM이 발행을 중단했다. BG 완료 호출은 큐 허가를 얻는 경로가 아니며 그 시점에는 END도 발행되지 않았다. 최종 후보는 그 호출에서 발행을 보류하고 기존 허가가 있는 호출 또는 정상 출력 단계에서만 발행한다.

## 수신 오류·STOP·복구

최종 소비기 ROM은 cold 이력, 잘못된 세대·길이·열·범위, 겹치는 행, 생략 단어의 WRAM 손상, 방금 쓴 단어의 손상을 거절했다. 세대 924에서 두 열 중 한 열의 23단어를 쓴 뒤 STOP을 주면 직전 화면은 보존되고 두 뱅크의 이력은 무효화됐다. 이때 남은 WRAM을 그대로 넣고 다시 부팅해 초기 두 장을 일반 map으로 복구했다. 12개 경우 모두 기대 상태와 일치했다. 최종 ARM 링크의 메뉴 복귀 함수에서도 정상 공개·기반 복구 실패·메뉴 실패·오류 유지·체크포인트 실패를 구분했다. [실제 65816 취소 및 재시작 결과](../analysis/strip869-guards.json)

## 종단 비교와 다음 작업

오른쪽 map 묶음 19개가 두 위상 모두 실제 발행됐다. 밀집 데모 60장에서 map 전송은 351→218거래, 69,213→40,158B였다. SPI에서 약 95.17ms를 절약했지만 19개 묶음의 65816 수신·검사 누계는 기존 여덟 패킷씩의 수신 시간 합보다 43.06 / 43.48ms 늘었다. 이 두 항목은 일부 겹친다. 같은 시작 시각에서 실제 마지막 map ACK가 앞당겨진 묶음은 각 위상에서 6개였다.

| 재생 구간 | 위상 1, MMC866 → 후보 | 위상 2, MMC866 → 후보 | 마지막 ACK 차이, 위상 1 / 2 |
|---|---:|---:|---:|
| 밀집 데모 60개 표시 간격 | 145 → 144 VBlank | 144 → 146 VBlank | −16.64 / +33.29ms |
| 오프닝 60개 표시 간격 | 126 → 126 | 126 → 126 | +0.41 / −0.26ms |
| 전환 48개 표시 간격 | 119 → 120 | 119 → 119 | +16.64 / −0.02ms |

두 위상 모두 오프닝 62장·전환 50장·밀집 62장의 활성 영상이 같은 세대의 MMC866과 일치했다. 전환의 빈 입력 동안 직전 화면을 유지한 16 VBlank도 같았다. 오프닝 위상 1은 원본 703의 공개가 VBlank 59→60으로 늦었다. ARM 최종 링크는 212,968B로 Flash 24B 여유이며, 65816의 5,120B 프로그램 ROM은 17B 여유다. ARM은 보정된 SPI 비용과 CPI 2로 실행했다. 새 FPGA 전체 FIT·STA와 실기 FPS는 이번 측정에 포함되지 않는다. [전체 링크와 두 위상 결과](../analysis/strip869-joint.json)

**실기 기준은 MMC866을 유지한다.** 세대 935가 두 위상 모두 3→2 VBlank로 당겨진 뒤 936은 3→5로 밀렸다. 936의 절대 캡처 준비 시각은 동일하고 ARM planner는 약 7ms 일찍 진입했다. 그럼에도 마지막 map ACK→SEAL 수락은 21.48→36.93ms / 21.43→36.86ms로 늘었다. 이 중 마지막 OBJ 반환→첫 팔레트 반환은 9.38→16.76ms / 9.06→16.77ms였다. 그중 팔레트 SPI 발행 전 대기는 8.73→16.22ms / 8.51→16.23ms였고 거래 자체는 0.205ms로 같았다. 마지막 OBJ 반환 뒤 첫 팔레트 발행 전 E0 조회는 62/60회에서 양쪽 모두 121회로 늘었다. 기준에서는 마지막 응답에 DMA 진행 비트가 섰고 후보에서는 한 번도 서지 않았다. 기존 ARM은 이 조건에서 진행 비트를 기다리며 최대 120회 반복한다. 관측된 것은 진행 응답이 없었다는 점이며, 더 일찍 DMA를 시작할 수 있었는지는 별도 대조가 필요하다. 다음 실험은 실제 선행 DMA를 할 수 있는 시점에만 이 대기를 허용해, 팔레트를 앞당겨도 다음 DMA와 독립 검사가 유지되는지 확인한다. 936의 이전 VBlank를 회복한 뒤 오프닝 703과 두 위상 모두의 전체 표시 간격·마지막 ACK로 다시 판정한다.

## 재현

MMC866 링크 소스에 `prepare_nes_frontier869.py --right`로 패치를 생성하고 `build_nes_mmc479_arm.ps1`로 전체 링크한다. `prepare_nes_strip_client869.py`는 column854/client-e에서 정적 소비기 ROM을 조립한다. `replay_nes_strip869.py`로 두 위상의 dense·opening·transition을 재생하며, `check_nes_strip869.py`로 같은 세대의 공개 화면과 최종 ACK, STOP 뒤 cold 복원을 대조한다. 기준 입력과 MMC866 링크는 [866 패키지 기록](../analysis/trial866-package.json)에 고정했다.
