# NES 1054r2 배포판

전원을 끄고 `NES-1054r2-RELEASE-SD-ROOT.zip`을 SD 루트에 풀어 일곱 파일을 함께 덮어쓴다. 게임과 개인 세이브 파일은 설치본에 포함하지 않는다. 디버그판은 기존 `NES-1054-DEBUG-SD-ROOT.zip`으로, 실기 계측 형식과 타이밍을 그대로 비교할 수 있다.

## FF3 확인 순서

1. SD 메뉴에서 이전에 사용한 FF3 한글판 .nes를 선택한다. 메뉴가 사라진 뒤 로딩 글자가 나올 때까지 화면이 깨지는지 확인한다.
2. 로딩 끝에 `100%`와 `Starting NES`가 표시되고 FF3 오프닝이 나오는지 확인한다. 두 문구는 잠깐만 보일 수 있다.
3. 게임이 시작되면 L+R+START에서 EXIT TO MENU로 돌아온다. 실패하면 마지막으로 보인 문구와 자동 메뉴 복귀 여부가 다음 진단의 기준이다.

## 수정과 검증 범위

1054는 기존 파일 메뉴의 화면 정리 응답을 기다리지 않고 RESET을 걸었다. 100% 문자열도 화면 메모리에 쓴 직후 RESET을 걸어서 65816이 마지막 수치를 표시할 시간이 보장되지 않았다. 따라서 95%가 마지막으로 보였다는 관찰만으로 파일의 마지막 5%를 읽다가 멈췄다고 판정할 수 없다.

r2는 GBC에서 쓰는 두 단계 메뉴 인계(0x55 → FPGA_RECONF, 0x77 → RESET)를 완료한다. 복사 시에는 SPI 수신 완료를 본 후 FPGA의 PSRAM 준비 신호를 확인하고 다음 바이트를 보낸다. SD 파일을 닫은 뒤 최종 문구에 100ms를 주고 RESET을 5ms 이상 유지한다. 새 보드의 첫 상태·ID 조회가 늦으면 읽기만 제한적으로 다시 수행한다. BEGIN·END·START의 수락이 불확실할 때 재발행하지 않는다.

최종 ARM 바이너리를 실행해 FF3 512 KiB 및 커비 768 KiB 전체의 데이터·주소, 파일 종료, START·STOP·base 복귀를 검사했다. 보드 응답이 늦거나 계속 없을 때, 파일 메뉴가 응답하지 않을 때, 페이지 중간에 준비 신호를 받지 못할 때도 별도로 시험했다. 같은 FF3에서 첫 보드 식별 응답 하나를 늦춘 대조 시험에서 원본 1054는 한 번 조회하고 START 전 멈췄고 r2는 다음 응답에서 진행했다. 이 조건이 실기에서 발생했는지는 배포판에 로그가 없어 확정할 수 없다. 주변장치 응답과 플레이는 모형이며 설치본으로 FF3의 첫 화면이 뜨는지는 실기 확인 대상이다. 두 NES 보드와 나머지 호환 파일 네 개의 해시가 기존 배포판과 일치한다. FF3 배터리 세이브와 네 개 상태 슬롯의 복원도 최종 펌웨어로 실행했다.

## 커비 디버그판 실기 기록

한글판 CRC32 4169de6b, 일본판 비교 기준 248c7140. 한글판 두 실행의 표시 FPS는 각각 27.83 / 28.90 및 27.38 / 29.00이었다. 앞 구간은 [1,30)초, 뒤 구간은 [30,60)초다. 두 번 모두 STOP과 base 복귀가 기록됐다. 두 실행 모두 화면 관측값 se=a9도 남아 있다. 55–60초에 뱅크 반환까지 해석되는 표본은 각 63개이며 직전 공개→최종 ACK 중앙값은 양쪽 모두 33.55ms였다. 다른 ROM의 FPS는 참고값으로만 사용한다.
