# NES221: 슬롯 검색 개선 실기 시험

220에서60초 동작과 소리·입력·메뉴 복귀를 확인했다.221은 **타일을 재사용할 때도 수백 슬롯을 순서대로 검사하던 ARM 검색**을 인덱스로 바꾼다. 동일 슬롯·동일 전송 결과를 유지하며 새 FPGA 설계는 없다. 이번에60fps를 달성했다고 주장하지 않는다. 화면 정보 수신·스크롤 맵은 여전히 후속 개선 대상이다.

## 설치와 실행

1. 전원을 끄고 ZIP의 `01-GAME221-SD-ROOT` 안 내용을 SD 루트에 덮어쓴다. 이번의 `firmware.stm`을 사용한다. `fpga_n221.bi3`는 검증된220 FPGA의 바이트 동일 별칭이다.
2. 메뉴에서 `NES GAME 221.nh1`을 실행한다.0바이트 launcher가 정상이다. 게임 실행까지의 기존 로딩·검증 과정은 유지된다.
3. 플레이어 선택→월드맵 숫자1 타일에서A→첫 레벨. 오른쪽+B 유지, 필요한 때A를 눌러 달리고 점프한다. 죽으면 다시 들어가도 된다. 이번에도 게임 실행 약60초 후 메뉴로 돌아온다.
4. `nes-progress-221.txt`, `nes-game-last-221.txt`, `nes-budget-221.txt`를 보낸다. 스크롤 체감, 소리·조작·메뉴 복귀도 함께 확인한다. 가능하면 게임 화면부터 영상으로 기록하되 끊김 때문에 일정 주행을 억지로 유지할 필요는 없다.

동일220/044 반복 복원 시험은 필요 없다. 이상이 생겼을 때만 전원을 끄고 포함된 `02-RESTORE164-SD-ROOT`를 사용한다. 저장SRAM/GBC164/사용자 ROM은 변경하지 않았다. 무제한 플레이·실기 리셋 시 로그 저장 기능은 이번 변경에 포함되지 않는다.

## 이번 결과에서 확인할 것

- 오프닝뿐 아니라 첫 레벨 스크롤이220보다 나아졌는가.
- 검색 개선 후 순수 계획 작업과 전송 대기 중 무엇이 남는가.
- 화면 정보 수신에서 D1 인코딩 데이터와 D0 상태 조회가 차지하는 양은 각각 얼마인가.

새 계측은 기존5초 bin/10ms clock을 사용하고 게임 중 추가 파일 쓰기나 새 SPI 조회를 하지 않는다. `planner_ticks`는 계획 함수 전체, `callback_ticks`는 그 안의 동기 전송 callback 부분이다. 전체프레임 종료 시 계획−callback이 계산 부분의 근사다.10ms 양자화와 마지막 미완료 프레임 때문에 정밀 CPU/FPS 측정으로 쓰지 않는다. `d1_payload`는 시도된 인코딩 레코드 bytes로 내부 레코드 헤더를 포함하며, 유효 화면 정보만의 크기는 아니다. `d0_clock`은 D0 전체 clock bytes다. 별도 오디오/service SPI는 기존처럼 집계 밖이다.
