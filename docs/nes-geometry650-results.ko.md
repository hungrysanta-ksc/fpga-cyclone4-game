# 650 · 954 SEAL 마감과 955 geometry 일곱 블록

**648 수신 일정을 유지한 packed가 가장 가까웠다.** 954는 두 위상 모두 3 VBlank, 955는 3 / 4 VBlank였다. 951 공개선과 957 최종 추가 대기 조건을 지키면서 밀집 평균과 마지막 ACK가 양쪽에서 개선됐다. 954 최종 ACK 전 일곱 블록 반환과 955의 양 위상 3 VBlank는 함께 달성하지 못했다. 실기 기준은 MMC643이다.

## 648의 마감에서 역산한 비용

954의 SEAL **SPI 시작**을 마감으로 삼았다. 953 표시를 원점으로 위상 1은 45.320 ms, 위상 2는 44.970 ms다. 두 값과 별도로 부팅 후 절대 시각도 대조했다. 7블록의 완료 기한은 종전대로 954 최종 ACK다. 따라서 일곱 개를 전부 SEAL 전에 끝낼 필요는 없지만, SEAL 거래에 앞서 시작한 블록 때문에 그 거래가 밀려서는 안 된다.

955 캡처 준비와 954의 양성 END 관측이 모두 끝난 시점부터 마감까지는 8.685 / 8.683 ms다. 기존의 다른 SPI 거래를 그대로 놓으면 SEAL 전 빈 시간은 **2.773 / 2.771 ms**, SEAL 전송 종료부터 954 ACK까지는 **4.009 / 4.235 ms**였다. 모두 합쳐도 **6.782 / 7.006 ms**다. 빈 구간에는 출력 준비 등 원래 ARM 작업도 있을 수 있어, 전부 입력에 쓸 수 있다고 둔 낙관적 예산이다.

### 첫 7블록의 비용

단위는 ms, 각 값은 위상 1 / 2다. packed는 기존 648 수신 위치에서 압축 형식만 적용했다. D1·D2·D0에는 실기 기반 드라이버 할당이 포함된다. wire CRC와 복원은 실제 ARM 함수 진입·복귀로 잰 별도 구간이다. 복원에는 새 형식의 복원 CRC도 포함한다. poll 양 끝은 같은 ELF·블록·token을 따로 실행해 센 명령을 CPI 2로 환산했다. 합계는 다른 SPI 거래 사이에 입력 호출을 기다린 시간을 제외한 값이다.

|---|---:|---:|
| D1 전송과 드라이버 | 5.767 / 5.767 | 1.917 / 1.917 |
| D2 반환 거래 | 0.520 / 0.520 | 0.520 / 0.520 |
| 반환 확인 D0 거래 | 0.520 / 0.520 | 0.520 / 0.520 |
| 첫 블록 상태 D0 거래 | 0.074 / 0.074 | 0.074 / 0.074 |
| ARM wire CRC | 0.293 / 0.293 | 0.083 / 0.083 |
| ARM 복원·독립 검사 | 1.176 / 1.176 | 0.533 / 0.533 |
| 거래 사이의 나머지 ARM·서비스 | 0.507 / 0.293 | 0.289 / 0.289 |
| 첫 거래 전 poll 코드 | 0.181 / 0.181 | 0.173 / 0.173 |

| **합계** | 9.116 / 8.902 | 4.187 / 4.187 |

648은 일곱 블록에 **9.116 / 8.902 ms**를 썼다. 흩어진 빈 시간을 모두 합쳐 쓸 수 있어도 최소 **2.334 / 1.896 ms**를 줄여야 한다. 나머지 비용을 고정하고 payload만 줄일 때의 시간 등가는 **766 / 623 B**다. 954의 다른 SPI 거래 시작까지 전부 고정하면, SEAL 전 가장 긴 빈 구간이 양쪽 모두 0.486 ms여서 원래 블록은 하나도 들어가지 않는다. 전체 구간에 원래 블록을 순서대로 넣으면 두 개씩만 끝난다. 각 블록 시간을 같은 비율로 줄이는 감도 계산에서는 **61.9% / 59.4%**를 줄여야 일곱 개가 들어갔다. CPU 복원과 반환 거래를 그대로 두고 D1 payload 시간만 0으로 낮춰도 다섯 개 / 여섯 개다. 이 수치는 고정된 거래 위치에 대한 계산으로, 실제 스케줄 변경의 한계와 구분한다.

### 연속 일정 판정

마감 차이의 원점은 각 실행의 953 표시다. 음수면 648보다 954 SEAL 발행이 빠르다. 957 ACK 차이는 같은 시작 시각의 MMC643 대비 누적값이다.

| 구성 | 954 SEAL 마감 차이(ms) | 954 간격(VB) | 955 간격(VB) | 951 공개선 | 957 추가 대기 | 951–955 평균(ms) | 957 ACK 차이(ms) |
|---|---:|---:|---:|---:|---:|---:|---:|
| MMC643 | 기준 | 4 / 4 | 4 / 4 | 246 / 245 | 0 / 0 | 59.834 / 59.870 | 기준 |
| 648 | +0.000 / +0.000 | 3 / 3 | 4 / 4 | 247 / 248 | 0 / 0 | 59.890 / 56.623 | -16.252 / -32.729 |
| packed | -0.104 / -0.292 | 3 / 3 | 3 / 4 | 239 / 240 | 0 / 0 | 53.279 / 56.457 | -83.024 / -83.152 |
| sealed | +2.494 / +2.808 | 4 / 4 | 4 / 4 | 240 / 240 | 0 / 0 | 59.842 / 59.840 | -33.201 / -66.293 |
| once | +0.512 / +0.646 | 3 / 3 | 4 / 4 | 236 / 239 | 0 / 0 | 56.465 / 56.423 | -83.112 / -83.141 |

**비용 절감과 표시 결과.** 955의 첫 7개 D1 payload는 1,758→495 B(−1,263 B, −71.8%)였다. 블록별로는 40·85·70·56·28·105·111 B였다. D2와 확인 D0는 각각 7번으로 같다. packed의 합계는 두 위상 모두 4.187 ms로, 648의 9.116 / 8.902 ms보다 4.930 / 4.716 ms 짧다. 합산한 시간 여유는 2.596 / 2.819 ms지만 원래 거래를 고정하면 한 번의 입력 poll 도중 출력을 끼워 넣을 수 없다. 첫 블록이 약 0.615 ms를 차지해 SEAL 전 가장 긴 틈보다 약 0.129 ms 길다. 실제 packed 일정에서는 SEAL 전에 0 / 0개, 954 ACK 전에는 5 / 5개를 반환 확인했다. 일곱 번째 D0 완료는 ACK 뒤 2.102 / 1.627 ms였다.

sealed는 7 / 7개를 모두 SEAL 전에 확인했지만 마감이 2.494 / 2.808 ms 늦었고 954는 4회였다. once는 SEAL 전에 1개씩, ACK 전에 6개씩 확인했고 954는 3회를 유지했지만 상대 마감이 0.512 / 0.646 ms 늦었다. packed만 상대 마감과 절대 마감을 양쪽 모두 지켰다. 953 표시에 맞춘 상대 SEAL 시각이 기준보다 0.104 / 0.292 ms, 부팅 후 절대 시각은 누적으로 49.799 / 50.233 ms 빨랐다.

**955 위상 2의 남은 차이.** packed 위상 2의 planner 진입은 위상 1보다 0.475 ms 빨랐다. 그런데 END 함수 진입→출력 함수 진입은 10.718→12.024 ms였다. 결과적으로 SEAL 수락이 직전 표시 뒤 46.076→47.035 ms로 늦어졌다. 65816 업로드 진입은 211번 선과 229번 선, 첫 업로드 VBlank 대기 진입은 219번 선과 256번 선이었다. 위상 2에서는 다음 225번 선까지 기다렸다. 최종 표시의 별도 추가 대기는 955·957 모두 0회였다. 다음 대조는 packed를 유지하고 이 END→출력 1.306 ms 차이를 마지막 tile·ROM·큐 반환으로 나눠야 한다. 남은 입력 두 블록을 SEAL 앞에 일괄 배치하는 방식은 이미 상대 마감 회귀를 보였다.

**대조군과 실기 판정.** 첫 공동 실행에서 기존 일정 설정이 송신 함수를 덮어써 새 바이너리가 원래 D1을 받은 것을 계측에서 발견했다. 이 여섯 실행은 동일 바이너리의 원래 형식 대조군으로 보존했다. 실제 블록 생산 지점에서 함수를 선택하도록 고친 뒤 여섯 후보 일정을 다시 실행했고, 블록마다 실제 D1 거래 크기와 ARM CRC·복원 호출을 검증했다. 예를 들어 같은 packed ELF에서 기존 형식의 955는 5 / 5 VBlank, 압축 형식에서는 3 / 4회였다. Flash는 packed 213,272 B, once 213,344 B, sealed 213,400 B로 한도를 각각 280 / 352 / 408 B 초과한다. FPGA 송신기 비용과 보드 FIT를 포함한 실기 전달 단계는 보류한다.

## 무엇을 바꾸고 어떻게 검사했나

앞 7개의 기존 D1 블록 경계와 token 수는 유지한다. 같은 블록 안의 map 셀이 1·2·4·33칸 앞의 셀과 일치하면 최대 32셀을 복사 명령 하나로 표현하고, 나머지는 16비트 literal로 보낸다. 원래보다 작을 때만 해당 블록을 교체한다. 세대·시작 셀·셀 수·복원 CRC를 보낸다. ARM은 D1 wire CRC에 이어 순차 위치, 15비트 셀 범위, 블록 밖 참조 금지, 전체 복원 CRC를 확인한다. 타일 요구 목록은 이전에 검증한 셀에서 복사한 경우에만 그 요구 내역을 재사용한다. 블록 오류는 현재 입력 전체를 무효화한다.

| 구성 | 입력 수신 일정 |
|---|---|
| 648 기준 | 기존 648 실제 ELF·원래 블록. 계측 전후 957 최종 ACK가 같은지 대조 |
| packed | 648 수신 기회를 그대로 쓰고 블록 형식과 ARM 복원만 교체 |
| sealed | 649에서 확인한 END·미소비 타일 공존 구간과 section 5 발행 사이에도 수신 |
| once | END 경로에서는 이전 수신기가 COMMITTED인 동안 한 번만 선행 수신. 유효 token이 실제로 증가하면 기존 128µs 재대기 생략. 기존 map 경로와 SEAL 후의 총 7회 한도는 공유 |

각 실행은 905–957의 실제 ARM 전체 링크·SysTick, 공유 SPI·ROM 경쟁 모델, 두 타일 슬롯과 Mesen의 65816을 사용했다. map·OBJ 작업, 복원된 section 5, RGB·map·팔레트·OAM·HDMA와 53개 최종 ACK를 비교했다. 65816·표시 독립 검사와 잘못된 ACK 차단은 기존 경로를 거친다. ARM 시험에서는 token 래핑을 걸고 일곱 블록 각각의 **전체 수신 상태**가 원래 형식과 같은지 바이트 단위로 확인했다. 세대·범위·CRC·불법 참조·truncation 등 10개 오류와 실패 후 재시도, D2 직후 STOP·기한 경과, 메뉴·base 정상 복귀와 네 실패 차단도 확인했다.

송신측은 같은 원본 캡처를 읽는 참조 인코더다. 새 FPGA 인코더의 생성 지연과 FIT·STA는 이번 일정에 포함하지 않았다. 새 실기 FPS 측정은 없다. 복원된 바이트의 CRC까지 확인하는 ARM 비용은 실제 후보 ELF에 포함했다.

## 재현

1. `nes_geometry650.py`로 648 packed를 입력으로 packed·once를 만들고 649 sealed를 입력으로 sealed를 만든다. `build_nes_trial577.ps1`로 각각 전체 링크한다.
2. [648 재현 조건](nes-tail648-results.ko.md)에서 `test_nes_geometry650.py --commit-pop-bound`로 계측한다. 기준은 기존 648 ELF, 후보는 `--geometry650`을 추가하고 sealed·once는 `--held649`도 사용한다. 시작 시각은 각각 7,288,416·7,467,100 master clocks다. 네 구성의 두 위상 기준 trace 이름은 `nes-geometry650-base{1,2}`다. 후보는 같은 ELF로 기존 형식을 대조한 `nes-geometry650-{packed,sealed,once}{1,2}`와, 실제 압축 형식을 사용한 같은 이름의 `wire` 접미사 실행을 모두 둔다. 대조군은 `--geometry650`만 뺀다.
3. `count_nes_geometry650.py`로 네 ELF에서 poll의 첫 SPI 전과 최종 D0 응답 후를 따로 계측한다. 648 trace로 token seed를 고정하고 후보는 `--compact`를 쓴다. 모델의 CPI 2와 ARM 84 MHz로 환산한다. 후보마다 `check_nes_geometry650.py`, `check_nes_tail648_arm.py`, `check_nes_menu533.py --trial 643`, `check_nes_dma637.py --late-receive --late-blocks 2`, `check_nes_transfer512_recovery.py --trial 643`의 다섯 복구 케이스를 실행한다.
4. `analyze_nes_geometry650.py --traces … --build … --data … --out …`로 원본 대비 복원, 실제 마감, 블록별 비용 및 고정 시간표의 남는 구간을 검증한다. [수치·검증 해시](../analysis/geometry650-verification.json)
