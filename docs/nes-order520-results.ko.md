# MMC516 E9 패킷 안의 OBJ 순서 변경

## 변경 범위

ARM은 518의 표시 구간 카운터를 포함한 MMC516 빌드에서 출발한다. 계획 버퍼는 240B이고 한 E9에는 최대 15개 레코드를 넣는다. 520은 이미 준비된 8바이트 OBJ 레코드를 목적지 슬롯 순서로 삽입한다. 같은 목적지에 대한 갱신 순서를 유지하고, BG·zero·END·긴 형식의 OBJ에서 정렬 구간을 끝낸다. 새 E9가 수락되면 이전 구간의 시작 위치를 초기화한다. OAM의 게임 내 순서, 타일 배치, 뱅크, 토큰, CRC, credit, VBlank 표시 승인은 기존 경로를 사용한다. 65816 코드와 FPGA 이미지는 MMC516 것을 사용한다.

| ARM 비교 | 펌웨어 크기 | Flash 여유 | BSS |
|---|---:|---:|---:|
| MMC516 계측 기준 | 212,924B | 68B | 18,584B |
| 일반·짧은 OBJ 모두 정렬 | 213,016B | −24B | 18,588B |
| 짧은 OBJ만 정렬 | 212,992B | 0B | 18,588B |

일반형도 기능 검사를 통과했지만 Flash 한도를 초과했다. 연속 일정에는 짧은 OBJ 후보를 사용한다. 두 후보 모두 data는 10,040B다. MCU Flash는 512B 헤더를 포함한다. FPGA는 같은 Quartus Lite 산출물을 사용하므로 기존 전체 보드 비용인 15,164 LE·조합 논리 14,172개·M9K 51개다. 이번 ARM 변경으로 새 합성을 실행하지 않았다.

## 검증 방법

- 실제 ARM에 짧은 형식과 긴 형식, 동일 슬롯·다른 태그, BG·zero 및 15개·240B 경계가 섞인 55개 레코드를 입력했다. E9의 레코드 수와 길이가 기준과 같고, 유효하지 않은 슬롯·태그를 거부해도 기존 버퍼 내용이 유지되는지 검사했다. E9 직후와 bulk 이후 STOP, 잘못된 CRC·세대·수락 수·ACK, 최종 표시 이전 EA 차단을 확인했다.
- 519의 905–957 캡처에서 기존 E9별 길이와 원래 계획으로 전송 순서를 독립적으로 계산했다. ARM이 실제 내보낸 레코드를 해당 순서와 바이트 단위로 대조한다. 손대지 않은 65816이 소비한 타일 444개, VRAM·WRAM map, HDMA, RGB, VBlank·최종 ACK를 두 빌드 사이에서 확인한다.
- 같은 ROM 슬롯 캘린더에서 시작 클록 3,000,000과 3,178,684를 각각 비교한다. 한 실행 안에서는 53세대의 이력, 두 bank와 ARM IRQ가 끊기지 않는다. NES의 해당 장면을 실시간으로 실행한 ROM 중재나 실기 FPS 측정은 아니다.

## 결과와 실기 전달 결정

**MMC520을 제한 실기 시험 대상으로 선택했다.** 두 시작 시각에서 53개 화면의 RGB·최종 ACK, 444개 타일의 내용, VRAM DMA 125,488B를 대조했다. E9 98건의 프레임과 개별 길이는 그대로였다. 7개 세대에서 OBJ 순서가 바뀌었다. 실기 기준은 메뉴 복귀까지 확인한 MMC516이다.

| 시작 클록 | 첫 두 화면 뒤 51개 평균, 기준 → 520 | 밀집 951–955 평균, 기준 → 520 | 957 최종 표시 도착 |
|---|---:|---:|---:|
| 3,000,000 | 93.949 → 92.644ms | 133.229 → 126.578ms | 66.557ms 앞당김 |
| 3,178,684 | 93.948 → 92.970ms | 136.558 → 126.572ms | 49.919ms 앞당김 |

밀집 구간의 OBJ bulk는 양쪽 시작 시각 모두 **19건에서 13건**으로 줄었다. 가장 느렸던 952에서는 16개 OBJ 타일의 전송이 **9건에서 5건**으로 줄고, 첫 OBJ ROM 요청부터 마지막 응답까지의 시간이 83.065→49.787ms로 줄었다. 두 시작 시각에서 이 화면의 표시 간격은 각각 183.612→150.356ms, 183.647→150.346ms였다. 954는 OBJ bulk 1건 그대로였고 첫 시작에서 117.074→133.685ms로 늦어졌다. 두 번째 시작에서는 133.705→133.711ms였다. 개별 프레임에서는 앞선 프레임이 바꾼 ROM·VBlank 위상이 영향을 준다.

| 53세대 비용 | 첫 시작 기준 → 520 | 두 번째 시작 기준 → 520 |
|---|---:|---:|
| 전체 모델 전송량 | 548,583 → 543,778B | 549,323 → 545,594B |
| ARM 명령 수 | 121,598,186 → 119,909,246 | 121,780,726 → 120,538,172 |
| 실행된 SysTick 횟수 | 526 → 519 | 526 → 521 |
| ROM 읽기 / 최대 staging bank / ARM 관측 스택 | 5,616 / 2 / 1,672B 양쪽 동일 | 5,616 / 2 / 1,672B 양쪽 동일 |

정렬 자체의 명령도 포함한 전체 비용이다. 60fps 목표인 표시당 16.67ms까지는 차이가 크다. [측정 기록](../analysis/order520-verification.json)

## 실기 전달본

[설치·플레이 절차](nes-mmc520-trial.ko.md)와 [전달본 명세](../analysis/order520-package.json)를 사용한다. 전달용 ARM은 측정 빌드와 785개 함수의 주소·크기·기계어가 일치하고, 메뉴·ROM·FPGA·로그 식별자만 MMC520으로 바뀌었다. STM3 헤더·CRC, 40개 응답 검사, STOP 후 base 복구와 program·done·busy·token 오류의 안전 반환 차단을 확인했다. 1·40·60초 경계에서 표시 카운터도 검증했다. 동일한 원본으로 포장한 두 ZIP의 SHA-256이 일치했다. 실제 SMB3 플레이와 메뉴 복귀는 보드에서 확인할 단계다.

## 재현

1. [ARM 준비기](../tools/prepare_nes_order520.py)에 518 ARM01/src와 `--compact`를 전달하고 [ARM 빌더](../tools/build_nes_mmc479_arm.ps1)로 링크한다. `--compact`를 생략하면 Flash를 초과한 일반형을 재현한다. [ARM 검사](../tools/check_nes_order520.py)에는 기준과 해당 후보의 src를 전달한다.
2. [순서 검증기 입력 생성](../tools/prepare_nes_order520_oracle.py)에 519 joint01, output489/audit01, `--compact`를 전달한다. [53세대 실행기](../tools/trace_nes_obj518.py)는 519와 같은 fixture01, 516 client 및 캘린더를 사용한다. 기준에는 원래 plans를, 후보에는 검증기용 plans를 준다.
3. [대조기](../tools/analyze_nes_order520.py)에 각 시작 시각의 기준·후보 실행 결과, ARM 검사, 519 fixture와 ROM 캘린더를 전달한다. 게임 ROM·타일 원본은 로컬에 둔다.
4. 두 시작 시각이 모두 채택 기준을 만족하면 [포장 도구](../tools/package_nes_order520.py)의 labels로 시험판 이름을 적용해 빌드한다. label-guards01·windows-label01·recovery 5건을 준비한 뒤 package에 원래 MMC516 ZIP을 전달한다. ROM과 RESTORE는 포함하지 않는다.
