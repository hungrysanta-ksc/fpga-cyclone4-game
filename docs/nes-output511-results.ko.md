# MMC509 출력 일정과 전송 예산 (511)

실기에서 동작한 MMC509를 기준으로 65816의 출력 비용을 분리했다. 다음 구현 후보는 **입력 패킷마다 generation을 한 번만 보내고, 출력 map 행은 두 바이트 열로 압축해 일반 소비기가 직접 복원하는 방식**이다. 후반 10개 화면에 대해 전송량을 줄일 여지는 확인됐다. 다음 단계의 판정값은 같은 입력에서의 최종 표시 시각이다. [측정 JSON](../analysis/output511-verification.json) · [실기 기록](nes-hardware510-results.ko.md)

## 무엇을 측정했나

MMC509 실기에서 ARM이 출력 함수에 들어가서 반환할 때까지 걸린 시간은 평균 **43.17ms**다. 그중 최종 ACK를 기다리며 진행이 없었던 시간은 **8.17ms**로 이 구간에 포함된다. 실기 로그에는 개별 65816 명령의 시각이 없다.

그래서 509의 기존 공동 실행에서 저장한 ARM 명령과 전송 시각을 같은 65816 프로그램에 다시 공급했다. 원래 일정에는 SysTick 140회, ROM 읽기 배정 3,280회, 일반 큐 4개와 bulk 뱅크 2개가 포함돼 있다. ROM 허용 시각은 부팅 때 기록한 8개 창을 반복한 것이다. 실기 SMB3와 재생의 장면은 다르다.

아래는 **마지막 plan END를 실은 E9 전송 완료부터 화면의 최종 ACK 쓰기까지**의 재생 시간이다. 실기의 출력 함수와는 시작과 끝이 조금 다르다. 각 행은 겹치지 않으며 반올림 전에는 합계와 일치한다.

| 화면당 평균 | 초기 2개 | 후반 10개 |
|---|---:|---:|
| 일반 패킷을 처음 읽고 ACK할 때까지 | 32.26ms | 22.66ms |
| bulk 패킷 소비 | 4.62ms | 0.86ms |
| VBlank 대기 함수 (STOP 확인 포함) | 37.10ms | 20.00ms |
| PPU DMA 시작 레지스터 쓰기부터 마지막 데이터 쓰기까지 | 2.79ms | 1.18ms |
| compact 문맥·의미·범위 검사 | 2.07ms | 2.08ms |
| SEAL 안의 나머지 준비와 표시 제어 | 1.80ms | 1.49ms |
| 패킷 도착 전·패킷 사이 | 15.31ms | 7.55ms |
| **합계** | **95.95ms** | **55.82ms** |

후반에 VBlank 대기를 17번 호출했고, 그중 8번은 이미 VBlank에 진입한 뒤였다. 이 함수는 새 VBlank를 기다린다. 남은 VBlank에 그 작업이 실제로 들어갈지는 별도의 조건이다. 이전 505에서 고립된 선행 DMA는 연속 표시 시간을 줄이지 못했다.

후반 **전체** 패킷 수명에서 일반 소비는 평균 23.34ms였다. 이 중 section 5의 HDMA·raw 데이터는 11.32ms, section 2의 map은 6.21ms였다. 위 표는 END 뒤만 집계했으므로 시작점이 다르다. map에서 바이트를 줄여도 65816의 복원 비용이 늘거나 같은 VBlank를 계속 기다린다면 표시 이득은 작을 수 있다.

## 입력과 출력의 바이트 예산

| 후보 | 검증 범위 | 후반 10개 평균 절감 |
|---|---|---:|
| 입력 generation 공유 | 기존 압축 record의 순서와 값을 그대로 복원. 12개 generation에서 D1 크기를 원본 일정과 대조하고 마지막 COMMIT은 별도 패킷으로 보냄 | 519.2B |
| 출력 map 압축 | 16바이트 헤더를 유지하고 원래 범위 길이 2바이트를 부담. 워드의 하위·상위 열을 각각 단순 literal/repeat로 저장 | 1,046.8B |
| **같은 재생 입력의 합계** | D0/E0/E8 조회 절감 제외. 2.625MHz wire 환산 | **1,566.0B / 4.77ms** |

입력은 매 화면 14패킷에서 12패킷으로 줄었다. map은 130개 원본 패킷의 23,360바이트를 모두 복원해 비교했다. 선형 인코더는 전체에서 15,800B를 절감했다. 같은 형식에서 가능한 최소 길이를 계산하면 15,922B로 차이는 122B다. 잘린 본문, 범위를 초과하는 길이, 남는 데이터는 검사에서 거부했다.

실기의 조회 제외 wire는 16.25ms이고 잠정 12ms 예산까지 필요한 감소량은 표시당 **1,395B**다. 실기에서 E1 헤더·명령·CRC 전체가 차지한 양은 465.85B/표시다. 실기의 mapdirty 카운터는 직전 **표시**와 비교한 행을 센다. 실제 전송은 대상 뱅크가 마지막으로 표시된 후 변경된 행을 모으므로 이 카운터만으로 실기의 압축률을 계산할 수 없다. 재생의 4.77ms는 전송선 위 시간이며 실제 60fps 여부는 여전히 최종 ACK 간격으로 판정한다.

## 일치 검증과 동기화 수정

PR140 병합 커밋 `ab55afeefd629bbcc37cbcc57c4d35f1a0172f7e`의 두 번째 부모와 병합 결과의 트리가 일치했다. 이 기준에서 프로그램과 ROM 배정을 고정하고, 65816 함수 입구·호출자 복귀 및 실제 PPU 쓰기만 관측했다.

- 보관본의 명령과 응답 8,013쌍을 SHA-256으로 확인했다. 8,011개 응답은 원본과 일치했다. 나머지 두 SYNC는 원본 응답 시각이 요청보다 각각 289,889클록과 304,430클록 빨랐다. 재생 응답은 각 요청의 21클록과 28클록 뒤였다. 두 건 모두 큐 상태와 ACK identity가 같았고 새 소비·retire 이벤트는 없었다. 과거 기록의 시각이 달랐던 원인은 미확정이다.
- 이후 공동 실행기는 요청보다 빠른 응답을 즉시 오류로 처리한다. 보존된 두 조기 응답이 실패하고 요청과 같은 시각 및 늦은 응답이 통과하는 것을 확인했다.
- 재생 결과는 **12개 RGB 화면, 모든 최종 ACK masterclock, VRAM DMA 36,144B**가 원본과 같다. 실기 STOP·메뉴 복귀 근거는 MMC509 수신 기록을 따른다. 이번 단계의 실행물은 기존 ARM/FPGA/65816이며 기능 변경이나 새 설치본은 없다.
- 재현 자료는 작업공간의 `probes/nes-output511/replay05`에 있다. `measure_nes_output511.py`에는 원본 509 calendar02, 489 client04, Mesen과 빈 출력 경로를 전달한다. `analyze_nes_output511.py`에는 같은 fixture, 재생 폴더, 905–916 geometry/raw 데이터와 새 JSON 경로를 전달한다. 재생 01·02의 실패 및 03에서 찾은 시각 불일치, 04의 Lua 문자열 오류를 선택 결과와 분리했다. ## 다음 구현 순서

1. 일반 map 소비에서 압축 본문을 목표 WRAM에 한 번 복원한다. 원래 길이·주소·identity를 확인하고 기존 CRC·coverage와 dirty 목록이 확인한 범위만 DMA에 넘긴다. STOP 중간 취소 뒤 뱅크 재사용, 최종 ACK 전 공개 차단을 먼저 시험한다.
2. 같은 전송에서 공통 generation 입력을 별도로 연결한다. ARM·FPGA의 중복 처리를 실제로 대체하고 COMMIT·SPI CRC·입력 credit 검사를 유지한다. 실기의 Flash 잔여 36B, FPGA 잔여 244LE·5M9K, 65816 프로그램 본문 여유 649B를 각각 확인한다.
3. 기존 509, map만, 입력만, 둘 다 적용한 네 경우를 같은 입력·시작 시각·ROM 허용 구간에서 비교한다. 실제 ARM·SPI·IRQ와 65816 복원 비용, 초기 두 화면 이후의 최종 표시 간격까지 줄어든 후보만 합성·실기로 넘긴다.
