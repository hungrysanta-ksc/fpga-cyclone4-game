# PR157 회고와 다음 작업 순서

**결정은 707D의 배경 CHR 수정과 753의 기능 검증을 보존하고, 60fps 연구의 우선순위를 공유 SPI의 전송량·거래 수와 입력/출력 데이터 경로로 옮기는 것이다.** 905–957 전체에서는 같은 화면을 더 일찍 표시했다. 그러나 적과 map 작업이 몰리는 952–957에서는 여섯 화면 모두 여전히 세 번의 VBlank가 필요했다. 소폭의 발행 순서 변경만으로 후속 작업을 이어갈 근거는 약하다.

## 707D에서 753까지 실제로 줄어든 시간

같은 시작 클록(7,288,416 / 7,467,100), 같은 ROM 공급 달력에서 905–957의 원시 기록을 다시 집계했다. 두 위상 각각 53장의 RGB, map, 기대 데이터 파일이 전부 바이트 단위로 일치했다. 표의 밀집 간격은 951 공개부터 957 공개까지 여섯 간격의 평균이다. 마지막 ACK는 957에서 65816이 실제로 쓴 시각이다. 실행한 ARM·65816 코드에 SPI·IRQ·ROM 경합 모델을 연결한 재생이며, 하드웨어 FPS 실측은 아래에 따로 기록했다. [재집계 결과](../analysis/pr157-retrospective.json) · [재현 도구](../tools/review_nes_pr157.py)

[753 후보 비교](nes-credit753-results.ko.md)

PR 진입 전 실기 MMC704 성공 실행은 5–40초 **18.69fps**, 40–55초 **19.87fps**, 5–55초 **19.04fps**였다. 장시간 MMC705의 해당 구간은 각각 19.29 / 23.53 / 20.56fps였고 플레이 작업량은 달랐다. 스페이드 보너스 통과와 메뉴 복귀는 이때 이미 확인했다. PR157에서 707D 또는 753 조합을 설치해 같은 동선으로 잰 기록은 없다. 배경 CHR 수정의 실기 재발 여부와 플레이 FPS 증감은 다음 전달에서 확인한다. 반복 타일 깨짐과 별도 5초 부팅 타임아웃은 기존 관찰 항목으로 둔다. [실기 원본 분석](nes-hardware706-results.ko.md)

## 60fps를 가르는 공유 SPI 예산

연속 여섯 화면을 60fps로 내보낼 시간은 **100ms**다. 2.625MHz SPI가 쉬지 않고 보낼 수 있는 양은 그동안 **32,812.5B**다. 753의 같은 여섯 표시 간격 안에서 시작하고 끝난 SPI 거래만 합쳐도 위상별 **39,048 / 39,040B**였다. 순수 직렬 시간은 119.003 / 118.979ms, 재생에서 거래 시작부터 종료까지 점유한 시간의 합은 **168.617 / 168.542ms**였다. 707D의 같은 구간은 38,016 / 38,064B였다. 순서 최적화 후에도 이 구간의 총 거래량은 늘었다. 이 집계는 공개 시각으로 자른 창이라 인접 세대의 선행 거래가 섞일 수 있고, 경계를 걸친 거래와 별도 observer 이벤트를 제외한다. 다른 구조에 그대로 적용할 고정 하한은 아니다. [거래별 바이트 및 집계 방식](../analysis/pr157-retrospective.json)

753에서 D1 입력과 E1 출력만으로 두 위상 모두 **251거래·27,094B**였다. 이 두 명령의 거래 점유만 95.018ms여서 100ms 중 다른 명령에 남는 시간은 4.982ms다. 지금의 전체 거래를 그대로 둔 채 ARM 계산과 겹쳐도 이 직렬 비용은 남는다. 같은 일을 여섯 화면마다 계속 처리한다면 현 기록 대비 위상별 최소 **6,236 / 6,228B**의 선로 바이트와, 고정비까지 포함한 **약 68.6ms**의 점유를 줄여야 한다. 두 수치는 같은 비용을 다른 방식으로 본 것이므로 서로 더하지 않는다.

957 한 화면의 입력 시작→planner는 17.424 / 17.422ms였다. D1 거래 6.238ms, D1 종료→D2 준비에 복원·IRQ 등을 포함해 3.133 / 3.129ms가 걸렸다. 직전 ROM 허가 구간에 BG 24회 읽기를 넣으려면 실제 요청보다 13.342 / 13.610ms 빨라야 한다. 입력 복원과 다음 수신을 겹치는 실험은 이 차이를 얼마나 메우는지 검증하는 데만 쓴다. 현재 구간 안에서 첫 ROM 허가를 기다린 2.574 / 2.306ms와 직전 구간을 잡는 데 필요한 선행 시간은 구분한다. [762 입력·ROM 내역](nes-watch762-results.ko.md)

## 다음 작업 순서와 중단 기준

1. **실기 기준을 닫는다.** 707D에 기존 실기 ARM·65816을 묶은 대조군과 같은 보드의 753 ARM·751 정적 ROM 후보를 구분해 검증한다. 전달 전에 전체 링크, 설치 이미지가 사용하는 보드와 ROM, STOP·빈 캡처 회복·메뉴/base 복귀를 확인한다. 시험판은 고유 이름의 60초판·장시간판으로 만들고 RESTORE는 제외한다. 첫 레벨 같은 동선에서 5–40초·40–55초 최종 표시 수와 map/OBJ 작업량을 각각 기록한다. 장시간판은 스페이드·종료 사유와 BG CHR 마감 재발을 확인한다. 753을 실기 성능 기준으로 승격할지는 이 결과로 결정한다.
2. **프로토콜의 거래·바이트 예산을 먼저 결정한다.** 첫 후보는 D1 수신과 복원의 겹침, D2/D0 반환 묶음이다. 두 번째 후보는 FPGA가 이미 가진 map/tile에서 SNES가 필요한 데이터를 직접 읽고 ARM은 배치·slot·DMA 명령을 발행해, 같은 데이터가 ARM을 거쳐 SPI로 되돌아오는 구간을 없애는 방식이다. 기존 압축, 2슬롯, 실제 source 보유 수명과 재사용 시점, RAM 포트·ROM 경쟁, 독립 비교용 기대값의 출처, partial/STOP 후 cold 복구와 최종 ACK 소유자를 명시한다. 기존 RAM·제어를 무엇으로 교체하는지와 D1/E1 각각 실제로 없어지는 바이트·거래를 계산한다. 사용 중인 56개 M9K를 전부 비용에 포함한다.
3. **가망 있는 한 경로만 끝까지 연결한다.** 연속 작업량당 wire 5,468.75B/화면 이내는 필요조건이다. 실제 거래 고정비를 더한 예산도 따로 본다. 두 위상 952–957과 더 긴 연속 구간에서 시작·끝의 미처리 입력/출력량을 맞춰, 단순히 창 밖으로 밀린 거래를 절감으로 세지 않는다. 753과 같은 RGB·map·독립 검사, 911·951·952·957 마감, STOP/최종 ACK를 지키며 먼저 밀집 표시 간격에서 한 VBlank를 양쪽 모두 줄여야 한다. 보드 변경은 Quartus Lite 전체 FIT·STA까지 확인한다.
4. **60fps의 합격 기준은 연속 입력을 따라가는 속도다.** 밀집 구간의 3→2 VBlank는 중간 성과다. 최종 목표는 밀집·스크롤·장면 전환을 포함해 캡처를 놓치지 않고 매 VBlank에 완성 화면을 하나씩 표시하는 것이다. 관측 가능한 표시 간격의 분포와 최장 정지를 평균·최종 ACK와 함께 확인한다. 위 예산을 만족할 교체안이 없다면 기존 보드의 검증된 플레이 가능 성능을 남기고 구조·하드웨어 제약을 다시 논의한다.

새 작업량 근거 또는 바뀐 하드웨어 경계가 생기기 전에는 개별 E0 조회, 동일 map 쌍 순서·scanline 미세 조정, 65816에서의 동일 행 재검사, 별도 M9K를 쓰는 DMA 감시기를 반복하지 않는다. 이 회고는 보관된 결과를 재집계한 것으로, 새 합성·실기 시험 또는 설치본 전달은 포함하지 않는다.
