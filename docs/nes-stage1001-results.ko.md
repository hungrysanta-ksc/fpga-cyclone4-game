# 1001 · 912 패킷 수락 검사와 최종 DMA 준비

## 목표

978의 두 시작 위상에서 세대 912를 VBlank 46의 246선 종료 전에 공개하고 최종 ACK를 앞당길 수 있는지 확인한다. 908 공개, 909 선행 DMA 624B, 910 캡처, STOP과 독립 검사를 보호한다.

## 작업내용

| 시점 | 65816에서 수행한 일 |
|---|---|
| BEGIN 수락 | 대상 WRAM 뱅크가 결정되면 팔레트·OAM용 채널 4·5에 포트·원본 주소·기본 길이를 기록한다. 전송 시작은 기존 최종 게이트에서만 허용한다. 기존 HDMA 활성값 0x0E·0x02는 채널 1–3을 사용한다. |
| section 5 수락 | 별도 후보에서 offset 1,322의 240B 패킷을 WRAM에 쓴 뒤, 대상 형식의 HDMA 테이블을 기존 검사기로 검사한다. 검사한 세 테이블의 22B씩과 길이 6B를 저장한다. 임시 상태는 유효 표시를 포함해 74B다. |
| SEAL 수락 | 원래의 세대·토큰·뱅크·형식 검사와 coverage를 유지한다. 테이블 후보는 실제 raw 개수·마스크·테이블 위치와 WRAM의 72B를 다시 대조하고 불일치하면 원래 의미 검사를 실행한다. BEGIN과 무효화 경로는 이전 검사 상태를 지운다. |
| DMA·공개 | 첫 일반 VRAM descriptor의 원본·목적지·길이를 그룹 대기 전에 설정한다. raw 전용 전송, STOP 서비스, 최종 빔 위치 검사, 화면 공개와 그 뒤의 최종 ACK를 유지한다. 짧은 팔레트·OAM 형식은 실제 전송 직전에 길이를 조정한다. |

978의 ARM·SPI 기록을 고정하고 905부터 부팅한 Mesen 65816 재생이다. 코드는 912 BEGIN에서만 WRAM에 설치했다. 추가로 일반 패킷을 앞세운 999 일정, 마지막 D2 직후 BEGIN을 낼 수 있는 경우, 검사 완료 뒤 다음 새 VBlank의 전 시간을 주는 대조군을 각각 재생했다. 시간은 SNES 마스터 클록(21.477272MHz)이다.

## 성과

**새 VBlank의 실행 예산은 충족했고 978의 VBlank 46 공개는 두 위상 모두 실패했다.** 온전한 VBlank를 주고 DMA 준비만 바꾸면 두 위상의 공개가 16,777,610에서 16,775,660클록으로 1,950클록 당겨졌다. 246선 종료까지 84클록(3.91µs)이 남았다. 이 실험에서 실제 전송은 타일 656B·raw 192B·팔레트 512B·OAM 544B였다.

| 978 발행 시각 고정 | 위상 1 공개 / 최종 ACK 클록 | 위상 2 공개 / 최종 ACK 클록 |
|---|---:|---:|
| 978 | VB47 242선 / 16,772,306 | VB47 242선 / 16,772,126 |
| DMA 준비만 이동 | VB47 240선 / 16,770,184 | VB47 241선 / 16,770,640 |
| DMA 준비와 테이블 검사 이동 | VB47 241선 / 16,770,536 | VB47 241선 / 16,770,536 |

978의 VBlank 46 마감은 16,418,380클록이다. 마지막 section 5 반환은 이미 마감보다 6.322 / 6.321ms 늦었고 SEAL 처리 진입은 6.483 / 6.481ms 늦었다. 마감 뒤에는 두 OBJ 반환과 팔레트·OAM 패킷 반환도 포함됐다. DMA 준비만 옮긴 후보의 ACK 이득은 2,122 / 1,486클록(98.8 / 69.2µs)이다.

**마지막 패킷에 검사를 옮기면 큐 반환이 늦어진다.** 테이블 수락 처리(load→ACK)는 8,194→26,768 / 8,190→26,760클록이었다. SEAL 진입→업로드 진입은 29,206→23,304 / 29,182→23,262클록으로 줄었다. 두 위상에서 실제 검사 결과를 재사용했다. SEAL 안에서 compact 형식 해석 진입까지 2,596 / 2,596클록, 그 후 테이블 원본 대조 진입까지 4,128 / 4,134클록, 대조 진입부터 성공 분기까지 5,752 / 5,742클록, coverage 진입부터 업로드 진입까지 10,704 / 10,666클록이었다. 이 수치에는 각 경계 사이의 이동·준비도 들어간다.

일반 패킷을 앞세운 일정에서 DMA 준비만 바꾸면 업로드 진입은 두 위상 모두 237선이었다. 마지막 D2 직후 BEGIN까지 앞당기면 231선이지만 공개는 여전히 VB47이다. 같은 두 일정에서 수락 검사를 추가하면 각각 247선·242선에 업로드에 진입했다. 마지막 패킷의 반환 대기와 전체 실행 시간을 함께 고려해 978을 유지한다.

정상 16개 재생에서 911까지 65816 이벤트가 같았고 905–912 RGB가 978과 일치했다. 최종 두 DMA의 WRAM 뱅크·주소·포트·길이와 소비 바이트를 검사했다. 두 위상에서 잘못된 SEAL identity, coverage 손상, 수락 검사 후 WRAM 손상은 0xE0, raw 전송 중 STOP은 0xE4로 끝나 911 화면을 보존했다. 현재 배치로 압축하면 DMA만 바꾼 후보는 물리 ROM 한도를 91B, 검사까지 옮긴 후보는 351B 초과한다. 측정은 에뮬레이터 결과이며 새 실기판을 만들지 않았다. ## 후속작업

978의 912 마지막 뱅크 반환과 일반 패킷의 실제 준비·SPI 시각을 역산한다. 이미 확정된 팔레트·OAM·section 5가 마지막 OBJ와 겹칠 수 있는 구간을 찾고, **독립 검사와 그룹 준비까지 VB46 시작 전에 끝낼 수 있는지** 먼저 판단한다. 999의 낙관적인 발행 순서에서도 업로드 진입은 231선이었으므로, 같은 패킷의 순서 변경만 반복하기 전에 필요한 추가 시간과 획득 가능한 시간을 대조한다. 84클록의 실행 여유는 이번 두 위상의 측정치다.

재현은 `tools/nes_stage1001.py TEMP PHASE MODE`로 한다. PHASE는 1·2, 정상 MODE는 recorded·paid·begin·fresh·tablerecorded·table·tablebegin·tablefresh다. paid·table에는 `--fault bad_seal`과 `--fault stop_raw`를 적용하고, tablecorrupt·tablecoverage에는 `--fault bad_seal`을 적용한다. 978·999·1000의 원자료와 같은 TEMP에서 `tools/check_nes_stage1001.py TEMP analysis/stage1001-results.json`으로 결과를 대조한다.
