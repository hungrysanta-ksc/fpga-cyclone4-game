# NES171 실기 — 첫 표시 요청의 응답 대기 한도 초과

NES171 실기에서 첫 화면 표시 전에 종료됐다. ROM393216바이트 적재·비교와 첫 영상 후보 COMMIT1은 성공했지만, 첫 BEGIN 요청이 FPGA에 보관된 채 SNES 완료 ACK 없이65536회 대기 한도에 도달했다. 표시 구간13410ms, 표시 완료0회, ROM 오류0이며 STOP·기본 FPGA·메뉴 준비는 정상이다.170의0x34 수집 시간 초과와 다르고169의 초기 응답 실패와 같은 경계다. FIFO의 연속 화면 개선 효과는 아직 실기에서 확인하지 못했다.

사용자는 게임 화면 없이 바로 메뉴로 돌아온 것 같다고 보고했다. 아래 시간은 펌웨어 기록이며 독립적인 실측 시간이 아니다.

| 항목 | 결과 |

| ROM | 393216바이트 적재·비교 일치, 오류0 |
| 영상 후보 | BEGIN1 / END1 / COMMIT1 / ABORT0 |
| 표시 요청 | BEGIN, sequence0 / serial1 / generation12 |
| 전송 상태 | F6 / flags01 / ACK 12바이트0 / CRC7C 일치 |

## 어디까지 확인됐나

배포한 C 전송 코드는 매 상태 응답의 ID·flags·CRC를 검사하고 ACK가 있으면 즉시 성공한다. 이번 실패 코드는 상태 손상이나 guard 실패가 아닌 반복 한도 소진이다. 마지막 상태도 직접 CRC를 계산해7C 일치를 확인했다. FPGA flags01은 sealed1·ACK_valid0·fault0이며, sealed는 E1 패킷 길이와 CRC 검증을 통과한 요청이 보관되면 설정된다. 따라서 MCU→FPGA 요청 수락과 상태 응답 경로는 진행됐고, SNES가 처리한 완료 ACK의 게시가 관찰되지 않았다. ACK의0바이트는 성공/오류 응답이 아니라 아직 없는 값이다.

SNES가 아예 시작하지 않았는지, WRAM 프로그램으로 넘어가다 멈췄는지, 패킷을 읽었지만 ACK를 완료하지 못했는지는 현재 기록으로 구분할 수 없다. screen_stage0·SPC 초기화 결과 없음은 보조 근거이며 구형 screen_telemetry_trusted0 값을 CPU 정지의 단독 증거로 사용하지 않는다. ROM 오류나60초 정상 종료가 아니며, SNES가 E2/E3를 반환한 경우도 아니다.

첫 영상 후보 COMMIT은 통과했으므로 이번 실패를170의 CHR 수집 전체 시간 초과로 분류하지 않는다. 그러나 첫 후보 하나만으로 FIFO의 연속 전송 개선을 실기 통과 처리하지도 않는다.169에서 발생하고170에서는 나타나지 않았던 첫 BEGIN 실패와 같은 경계가 다시 관찰됐다. 같은 근본 원인인지, FPGA 변경에 따른 발생 조건 차이가 있는지는 미확정이다.

## 다음 작업

다음은 SNES 표시 프로그램의 실제 reset 해제→ROM 부팅→WRAM 복사→첫 패킷 읽기→ACK 게시 경계를 좁혀 수정한다. sealed1/ACK0만으로 부팅 실패나 FIFO 회귀를 확정하지 않는다. 기존 프로그램 바이트 일치·모델 부팅·무변경 FIT를 반복하거나 대기 한도만 늘리지 않는다. 변경 경계의 최소 검증 후 실제 SMB3로 돌아간다. 같은171·044 재시험이나 추가 영상은 필요하지 않다. 연속 AV→장기 실행/오류·본체 리셋 로그→입력 유지 순서와 세이브 SRAM/GBC/164 보호를 유지한다.
