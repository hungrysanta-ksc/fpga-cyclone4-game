# NES174 실기 — 영상 정지 지속, 전송 비용 일부 감소 관측

사용자는173과 마찬가지로 초반 몇 화면 뒤 영상만 멈추고 게임·사운드·조작은 계속되는 것으로 보고했다. 로그도 **12회 표시 완료 뒤 추가 BEGIN 수신이 없고 약60초 한도로 종료**한 결과다.174의 타일 간 비트평면 수정·묶음 전송으로 연속 화면 문제가 해결되지는 않았다. 같은174 재시험이나 추가 영상은 이 결과를 판단하는 데 필요하지 않다.

## 완료 지점과 시간

| 항목 | 173 | 174 |
| --- | --- | --- |
| BEGIN / END / COMMIT / 표시 완료 | 각각16 | 각각12 |
| 마지막 generation | 30 | 23 |
| 마지막 표시 완료 시각, RUN 시작 기준 | 5.79초 | 3.81초 |
| ABORT | 0 | 0 |
| ROM / sink / video 오류 | 모두0 | 모두0 |
| 종료 사유 | DEADLINE 1 | DEADLINE 1 |
| 진행 로그의 DISPLAY 구간 | 60,060ms | 60,050ms |

`native_frames`는 matching SEAL/display ACK 후 증가하는 카운터다.174는12회까지 완료했고 마지막 완료부터60초 한도까지 약56.19초 동안 추가 완료가 없다. 이 시간이 TV 화면을 직접 측정한 값은 아니다. 완료 횟수가16에서12로 줄었다고 처리량이 나빠졌다고 단정할 수도 없다. 서로 다른 세대·그림·입력과 후보 선택 시점이 섞여 있다.

ROM393216바이트 적재·비교, RUN, STOP, 기본 FPGA 복구가 통과했다. MENU_PREPARED는 실행295490ms에 기록됐고 종료 로그는 PREPARED_RESET_HELD다. **로그상 메뉴 복귀 준비는 정상이며, 실제 메뉴가 보였다는 사용자 확인은 이번 메시지에 없다.** `run_passed=1`은 이 실행/종료 절차 통과이며 연속 영상이나 정상 플레이 합격이 아니다.

SPC 초기화A9·unmute1이며 사용자는 소리가 정상으로 보인다고 했다. 입력 변화152회, 최근16개에는B·LEFT·해제 등이 기록됐다. 따라서 입력 경로가 살아 있다는 보고와 부합하지만 입력 유지·모든 버튼·프레임 품질까지 검증한 것은 아니다. 새 영상은 첨부되지 않았다.

## 처리 비용 비교

| 단계 | 173 누적 / 완료1회 평균 | 174 누적 / 완료1회 평균 |
| --- | --- | --- |
| 변환·패턴 전송·BEGIN/guard | 910ms / 56.9ms | 460ms / 38.3ms |
| 테이블·SEAL·SNES 처리·ACK/guard | 2340ms / 146.3ms | 1550ms / 129.2ms |
| 위 두 단계 합 | 3250ms / 203.1ms | 2010ms / 167.5ms |

174에서 평균 비용이 작게 관측됐다. 묶음 전송의 의도와 부합하지만 동일 장면을 고정한 비교가 아니므로 차이 전체를 최적화 효과로 귀속하거나 정확한 개선율로 선언하지 않는다. 수신·생산 대기를 제외한 두 직렬 단계만 평균167.5ms여서60fps의 약16.7ms와 여전히 큰 차이가 있다. 영상 정지와 초기 끊김은 각각 해결해야 한다.

수신 단계55.24초는 전체 실행 누적이며 정지 뒤 상태 조회·후보 대기를 포함한다.12장의 전송에55초가 걸렸다는 뜻이 아니다. 단계 합57.25초와60초의 차이2.75초를 특정 장치·단계에 임의 배정하지 않는다. 전체60초에 완료 횟수를 나누거나 첫 완료 이전 대기를 포함한 ACK 빈도를 실제 TV FPS라고 부르지 않는다.

## 원인 범위와 다음 판단

- 12개의 BEGIN/END/COMMIT과 표시 완료가 모두 대응하며 수신된 ABORT가 없다. 현재 로그는 마지막 그림을 SNES에 보내다가 오류로 멈춘 증거를 보여주지 않는다. 이후 새 후보가 MCU에 도착하지 않는 쪽이 우선 조사 지점이다.
- `native_result=1`이 최초 deadline 종료다. guard가 전송을 거부한 뒤 수신 함수가21을 남길 수 있으므로 `native_receiver_error=21`만으로 SPI 손상을 단정하지 않는다. sink/video 오류와 전송 실패 snapshot은 없다.
- 실제 exporter는 IDLE에서 geometry/count 허용 조건에 실패하면 BEGIN/ABORT를 보내지 않고 release/DRAIN으로 간다. 따라서 ABORT0만으로 FPGA에 거부가 없었다고 해석할 수 없다. frame 수집·허용 조건, release/DRAIN, fill_busy, host 전달 상태는 이번 로그에서 분리되지 않는다.
- 모델 frame24와 실기 generation23/24를 같은 사건으로 취급하지 않는다. 이전 모델12~26 통과도 실기의 약4초 이후 handoff·입력·가변 backpressure를 그대로 검증한 것이 아니다. 타일 간 plane 구현은 특정 표현 문제를 고쳤지만 이번 실기 정지의 충분한 해결책이 아니었다.

다음 구현은 **연속 COMMIT 이후 다음 후보를 생산·해제·전달하는 실제 연결 경계**를 우선한다. 기존 SPI/host 시험이 이 경로와 실기처럼 느린 소비 조건을 얼마나 다뤘는지 먼저 확인하고, 확인되지 않은 경계만 재현한다. 실기에서만 구분이 필요하면 다음 시험의 종료 시점에 이 경계의 상태·거부 원인만 최소한으로 읽는다. 같은174 재실행·범용 디버그 확장·무변경 FIT·044 반복은 하지 않는다.

처리량은 전체 map/CGRAM/OAM/HDMA 반복 전송과 패킷별 ACK 비용이 계속 남는다. 기존 SNES 변경분 DMA는 재구현하지 않는다. 다음 후보의 실제 경계 수정과 함께 안전한 전송 왕복 감소를 검토하되, 교대 WRAM의 기준 세대 보장 없이 테이블을 생략하거나 세이브 SRAM·두 번째 MCU 전체 프레임을 사용하지 않는다. 연속 AV → 장기 플레이/오류·리셋 로그 → 입력 유지 우선순위는 유지한다.
