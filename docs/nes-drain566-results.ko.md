# 566 · STOP 전후 타일 소비 ACK의 소유권

MMC558의 ARM과 65816 바이너리, 후보 565의 타일 생산기·뱅크·소비 제어 RTL을 사용했다. 565에서 같은 토큰 1이 두 세션에 발행될 때 이전 ACK로 새 뱅크를 반환할 수 있었다. 이번에는 CPU가 실제로 발생시킨 쓰기 다섯 개를 두 시작 위상에서 추적했다. **시험한 ARM STOP·재시작 경로 8건에서 이전 ACK가 새 뱅크를 반환한 횟수는 0회**였다. 따라서 이 경로에 세션 토큰을 추가할 근거는 얻지 못했다. [측정값과 입력 해시](../analysis/drain566-verification.json)

## STOP을 허용하는 조건

링크된 ARM의 `nes_menu_sd_probe` 내부 START·STOP 분기를 실행했다. START는 상태 `82`와 393,216B를 확인하고 `63`을 전송한 뒤 상태 `86`을 요구했다. 표시 진입·이탈에는 실제 `nes_display_enter146`·`nes_display_leave146`를 사용했다. 이탈 시 GPIOA 모드 쓰기로 SNES RESET을 건 뒤 별도 GPIO 입력으로 핀을 읽었다. 핀 모델이 계속 해제 상태를 반환하도록 바꾸자 실패를 래치했고 STOP 프레임은 0개였다. 정상 피드백에서만 STOP과 그 응답 검사까지 진행했다.

STOP부터 다음 START까지 실제 ARM이 생성한 명령은 `64, 65, 65, 63`이었다. 각 8B를 2.625MHz로 연속 전송하면 STOP까지 최소 24.38µs, 다음 START까지 최소 97.52µs다. 이 비교에서는 메뉴 실행, 다음 이미지 재적재·검증, 소프트웨어와 전송 간격, NES RAM 초기화 시간을 모두 0으로 두어 새 뱅크가 가장 일찍 노출될 수 있게 했다. SPI 응답과 GPIO 입력은 모델이다. ARM의 실제 프레임 루프는 표시 이탈 지점으로 축약했다.

## 마지막 읽기와 두 토큰 쓰기 사이의 취소

MMC558 소비 ROM에 기존 두 도착 기록을 공급했다. 첫 cold 화면의 34번째 패킷은 토큰 1을 사용하는 320B OBJ다. 취소 뒤에도 이전 헤더의 토큰 바이트를 읽게 해, ACK가 도중에 다른 값으로 바뀌어서 시험이 우연히 통과하는 경우를 막았다. Mesen의 reset 요청 뒤 CPU가 실제로 쓴 값은 `01 00 00 00 A5`였다. 두 위상의 쓰기 주소·값·간격을 그대로 사용해 565 RTL을 한 좌석에서 순차 실행했다.

| 취소 지점 | 취소부터 이전 A5까지, 위상 1 / 2 (SNES master clocks) | 두 위상의 RTL 결과 |
|---|---:|---|
| 마지막 1B가 남았을 때 | 926 / 920 | STOP 중 쓰기. 새 뱅크는 새 CPU의 ACK로만 반환 |
| 마지막 1B를 읽었을 때 | 918 / 912 | STOP 중 쓰기. 새 뱅크는 새 CPU의 ACK로만 반환 |
| 첫 토큰 STA 명령 실행 직전 | 198 / 198 | 이전 뱅크를 STOP 전에 정상 반환. 새 뱅크도 한 번 반환 |
| 토큰 하위 2B를 쓴 직후 | 158 / 158 | 이전 뱅크를 STOP 전에 정상 반환. 새 뱅크도 한 번 반환 |
| RESET 없이 이전 CPU를 재개하는 대조군 | 918 / 912 | 새 뱅크를 읽기 전에 반환하는 현상 재현 |

정상 8건 모두 Mesen에서 reset 적용 이벤트와 reset 벡터의 첫 명령 실행을 확인했다. 재부팅 후 BEGIN부터 다시 수신해 320B 전체를 읽고 타일 ACK와 해당 패킷의 일반 ACK를 완료했다. Mesen은 리셋 시 master clock을 다시 시작하므로 이전 시각과 새 시각을 빼서 전체 재시작 시간으로 사용하지 않았다. RTL은 CPU가 사용한 토큰 1과 길이를 맞추고, 표적 패킷 이전의 입력 큐를 생략했다. 서로 다른 패턴의 320B 뱅크를 생성해 주소마다 읽은 뒤 새 ACK를 재생했다. CPU 재생과 RTL은 관측 기록으로 연결했으며, 이 시험의 ACK는 타일 소비 ACK다. 최종 표시 ACK와 53화면 일정의 근거는 [565 재생](nes-reuse565-results.ko.md)에 있다.

대조군은 CPU 실행을 중단한 사이 FPGA만 재시작해 같은 토큰을 다시 공개한 경우다. 두 위상 모두 이전 CPU의 실제 쓰기가 읽지 않은 뱅크를 반환했다. **FPGA 단독 재시작을 허용하는 새 경로를 도입할 때는 이 시험을 다시 열어야 한다.** 핀의 전기적 동작, 전원 장애, 실기의 드문 실행 실패 원인은 이번 시험 범위 밖이다.

## 다음 보드 작업

565의 기존 Quartus Lite timing netlist와 MMC558의 같은 코너를 대조했다. 남은 회귀 5개는 세 경로로 좁혀진다. [코너별 원본 끝점](../analysis/drain566-verification.json)

| 우선순위 | 시작 → 끝 | MMC558 → 565 slack (ns) |
|---|---|---|
| 1 | NES core reset 해제 → 84MHz native records mailbox valid | 85°C −7.081 → −7.286, 0°C −6.504 → −6.727 |
| 2 | 84MHz plan rearm held → NES received | 85°C −4.603 → −4.620, 0°C −4.586 → −4.614 |
| 3 | 기준 클록 고장 → 168MHz memory release 첫 단 | fast 0°C −2.653 → −2.669 |

첫 경로부터 reset의 즉시 차단과 목적 클록의 해제 순서를 검증한다. 두 번째는 송신 데이터 유지와 수신 capture 에지를, 세 번째는 클록이 멈춘 상태에서도 메모리를 차단하는지를 확인한다. 후보를 바꾸면 같은 소스의 전체 FIT·STA와 두 위상의 952·957 표시 간격 및 마지막 ACK를 다시 측정한다. 이번 단계는 시험과 분석만 바꿨으므로 FPGA·ARM 자원과 실기 FPS의 새 측정값은 없다. 실기 기준은 MMC558이다.

## 재현 순서

1. `tools/check_nes_drain566_arm.py`에 materialize한 ARM558의 `src`와 출력 JSON을 전달한다.
2. `tools/test_nes_drain566.py`에 565의 각 위상 재생 폴더(`client.sfc`, `arrivals.tsv`), ARM JSON과 Mesen을 전달한다. 출력은 위상마다 새 폴더를 사용한다.
3. 기존 Starter FLOAT wrapper로 `tools/check_nes_drain566_rtl.py`를 한 번 실행한다. 565 보드 폴더와 두 CPU 결과를 넘긴다.
4. `tools/analyze_nes_drain566.py`로 두 CPU 결과, RTL 결과, 565의 `arg564-paths.tsv`를 대조한다. 각 시험 명령의 인자는 `--help`에 있다.
