# MMC643 후반 OAM·HDMA 확정 시각과 두 후보

**955의 OAM을 먼저 수락시키는 데 성공했지만 955는 두 위상 모두 4 VBlank였다.** 후반 전송량을 별도로 줄인 후보도 같은 결과였다. MMC643을 유지한다.

## 측정 조건

부팅 완료 후 ARM 시작 7,288,416 / 7,467,100 master clocks에서 각각 MMC643 원본, 연속 발행 후보 A, 전송량 후보 B를 새로 실행했다. 각 실행은 905–957의 연속 53화면이다. 링크한 Cortex-M4 명령, SysTick, 공유 SPI 실기 기반 서비스 비용, 두 bulk 슬롯·ROM 허용 일정과 Mesen의 실제 65816 실행을 연결했다. 기준 두 실행의 밀집 VBlank 열과 957 최종 ACK는 645 기준과 정확히 일치했다. 모든 실행에서 map·OBJ 작업과 확장된 section 5의 주소·바이트, map·화면 RGB, 실제 표시 ACK의 CGRAM 512 B와 OAM 544 B를 대조했다. 아래 시간은 MCU CPI 2를 사용한 연결 일정 값이다. [원시 추적 해시·시각·판정](../analysis/tail646-verification.json)

## 언제 발행할 수 있었나

planner 호출부터 END 함수 진입까지 실제 ELF의 video 구조체에 대한 메모리 쓰기를 관측했다. 값이 우연히 앞서 최종값과 같았던 시점 대신 마지막 저장 명령을 사용했다. 단위는 planner 진입 후 ms이며 각 쌍은 위상 1 / 2다.

955 END 진입은 12.642 ms다. OAM은 약 1.785 ms 먼저 끝나지만 op9는 OAM 앞 112 B와 대상 뱅크 serial을 보내고 팔레트·OAM 후반 이력까지 확인한다. CGRAM과 계획 확정 이전에 op9 전체가 준비됐다고 계산할 수 없다.

## 분리 실험 결과

| 구성 | 954 간격 | 955 간격 | 955 절대 표시 프레임 | 밀집 951–955 평균 간격(ms) | 957 최종 ACK 차이(ms) |
|---|---:|---:|---:|---:|---:|
| MMC643 | 4 / 4 | 4 / 4 | 192 / 193 | 59.834 / 59.870 | 기준 |
| A · 연속 발행 | 4 / 4 | 4 / 4 | 193 / 190 | 59.909 / 59.833 | +16.973 / −49.787 |
| B · 전송량 감소 | 4 / 4 | 4 / 4 | 191 / 193 | 59.887 / 59.884 | −16.676 / +0.337 |

모두 밀집 간격이 3·4·3·4·4, 합계 18 VBlank였다. 누계 마지막 ACK의 음수는 앞선 세대부터 누적된 이득을 포함한다. 954→955 자체를 한 번 줄였는지는 상대 간격으로 판정했다. 951 공개선은 246 이내, 952는 4 VBlank, 957 최종 추가 대기는 0회였다.

**A. END 대기에서 op9 한 거래를 통째로 배정했다.** E9가 가능하면 먼저 발행한다. 이미 확인한 여유 credit, bulk 소비 대기 없음, 일치하는 두 뱅크 이력·현재 세대·valid 계획에서만 기존 quiet-map 기회 하나를 op9에 준다. 원래 wire opcode와 STOP 검사, sequence 및 최종 ACK는 유지한다. 실제 955에서는 op9가 18번째에서 8번째 패킷이 됐다. 직전 표시 기준 65816 OAM 수락은 **41.288 / 41.499 → 29.758 / 29.668 ms**였다. 그런데 마지막 map/tile 발행은 39.166 / 39.435 → 40.033 / 39.695 ms였고, 첫 section 5 거래 시작은 41.241 / 41.511 → 41.604 / 41.266 ms였다. SEAL 수락은 48.067 / 48.279 → 48.185 / 47.735 ms로 한쪽만 빨라졌다. 954에서는 op9가 마지막 map/tile 뒤에 남았다.

**B. 마지막 HDMA enable 테이블의 패딩을 기존 동일 단어 명령으로 보냈다.** 실제 길이까지 먼저 보내고 남은 바이트가 같을 때만 기존 65816 op4로 복원한다. 955의 section 5는 9거래 그대로 **567→509 B**, E1 서비스 합은 **2.176→1.999 ms**였다. 끝에서 두 번째 거래는 기존 3 B literal에서 60 B 복원 명령으로 바뀌어 65816 수락→개별 ACK가 0.280–0.281 → 0.635 ms로 늘었다. 이 서비스는 송신과 겹친다. SEAL 수락은 48.364 / 48.358 ms였다. 954도 58 B가 줄었고 표시 간격은 유지됐다. 전체 53화면 E1은 154,250→151,176 B였다.

## 안전 경계와 후속 작업

두 후보의 전체 링크 바이너리를 각각 실행하고 메뉴 marker·복구 진입 및 base 정상 복귀·네 실패 차단, 수신 취소·STOP·CRC·기한 및 잘못된 최종 ACK를 검사했다. A의 단독 ARM 시험은 중복 발행·bulk 대기·cold 이력·세대 차이·팔레트 차이·STOP을 구분했고 op9 수락만으로 EA를 허가하지 않았다. 별도 Questa 시험에서는 실제 MMC643 보드 RTL에서 32→33, 97→98 거부 입력의 폐기, 앞 화면 반환, 다음 유효 입력 재개와 STOP을 확인했다. 53화면 연속 일정은 유효 캡처를 사용했다.

Flash는 기준 212,932 B, A 213,116 B, B 213,008 B다. A와 B는 보드 한도 212,992 B를 각각 124 B와 16 B 초과했다. 두 시간 기준도 미달이므로 크기만 줄여 설치본을 만들지 않는다. 보드와 65816은 기존 MMC643과 동일하며 새 실기 성능 측정은 없다.

다음에는 955의 section 5를 **발행과 소비 양쪽**에서 줄일 수 있는지 먼저 본다. 예를 들어 21 B 스크롤 뒤의 빈 1,100 B는 이미 payload 2 B로 보내지만, 기준 두 위상에서 65816 수락→개별 ACK는 약 1.50 ms였다. 이 구간과 인접한 raw 복원에 대해 생략 가능 범위·독립 coverage·STOP 후 전체 복구 비용을 함께 대조하고, SEAL 수락이 실제 앞당겨질 때만 전체 일정을 다시 평가한다.

재현은 `prepare_nes_tail646.py`의 grant/short를 MMC643 arm01에 각각 적용하고 `build_nes_trial577.ps1`로 링크한다. 645와 같은 자료·65816·시작 시각에서 `test_nes_export636.py` 대신 `test_nes_tail646.py --commit-pop-bound`를 사용한다. `check_nes_tail646_guards.py`, `guard_nes_offer610.py --obj-only`, `check_nes_overlap634_arm.py --in-place --before-seal`, `check_nes_dma637.py --late-receive --late-blocks 2`, 기존 643 메뉴·base 검사와 `check_nes_tail646_recovery.py`를 실행한다. 마지막으로 `analyze_nes_tail646.py`에 여섯 추적 상위 폴더, build/기준 ELF 폴더, 643 보드·recovery 결과를 전달한다.
