# NES 652 · 실제 geometry 송신 준비와 보드 배치

## ARM Flash와 검사

651 grant의 213,316 B를 기준으로 652 전체 링크는 212,436 B다. CRC32의 바이트 인덱스 표 1,024 B를 상위·하위 4비트 표 두 개(128 B)로 바꿨다. 테이블 896 B 절감에서 코드·정렬 증가분을 뺀 순절감은 880 B이며 212,992 B 한도에 556 B가 남는다. 원래 표의 256개 항목을 전수 대조했다. 두 ELF에서 임의의 이전 상태를 포함한 768개 입력을 다항식 기준과 비교했다. CRC32 갱신은 바이트당 ARM 명령 6→10개다. 이 비용은 같은 함수를 쓰는 GBC 저장·덤프에도 적용된다. NES 블록의 독립 CRC16과 부트로더 이미지에는 이 교체를 적용하지 않았다.

## FPGA에서 측정한 송신 비용

MMC643의 NES exporter가 96비트 mailbox로 보낸 record를 84 MHz 호스트 SPI 수신기의 새 압축기에 연결했다. 준비 승인은 기존 17비트 ACK mailbox를 거친다. 수신 RAM 하나에서 원본(0–255), 압축 결과(256–511), 128셀 해석 공간(512–767)을 나눈다. 원본을 닫은 뒤 압축기가 RAM 포트를 소유하고, 완료된 payload와 CRC를 D0에 공개한 뒤 D1·D2로 소유권을 넘긴다. 앞 7개 블록만 시도하며 비-map, 공간 초과, 원본보다 짧아지지 않는 경우에는 보존한 원본을 보낸다. token은 실제 D1 길이·D2 소비 검사 뒤에 증가한다.

905–957의 원본 query 값을 한 NES 클록 응답으로 재생했다. 실제 exporter·mailbox·SPI RTL이 보낸 **802개 D1 payload와 wire CRC**를 비교했다. 부분 D1·잘못된 POP·압축 중 STOP·128셀 초과 원본 복귀·준비 중 D0도 별도로 시험했다. 첫 RTL 시도에서 연속 셀을 풀 때 다음 하위 바이트 쓰기를 건너뛰어 미정 바이트가 검출됐다. 쓰기 순서를 수정하고 53세대 전체 및 독립 오류 검사를 다시 실행했다.

495 B 준비 시간 합은 **371.988 µs**, 그중 같은 RAM을 점유해 압축·CRC를 처리한 시간은 **313.595 µs**다. 이 시간은 ARM·SPI가 다른 일을 하는 동안에도 흐른다. 표시 시간에는 각 D0의 실제 조회 시각과 겹치지 못한 지연만 반영했다.

## 두 시작 위상의 연속 표시

각 칸은 위상 1 / 2다. 세 경우에 같은 652 ELF·65816 ROM·작업량을 사용했다. 648의 954 SEAL 마감은 직전 953 표시로부터의 경과 시간을 기준으로 한다. 밀집 평균은 951–955의 다섯 표시 간격이다.

보드의 시작 허가를 적용했을 때 955 첫 블록은 ARM의 첫 D0 샘플보다 9.656 / 9.654 ms 일찍 준비됐다. 첫 일곱 블록 중 5 / 5개는 954 최종 ACK 전에 반환까지 확인했다. 준비가 늦어 한 번 더 조회한 경우는 위상 1의 세대 935였다. 954 SEAL의 공통 시작 기준 여유도 49.809 / 33.313 ms였다.

MMC643의 밀집 평균은 59.834 / 59.870 ms였다. 652 보드 소유권 일정의 957 최종 ACK는 master clock 69,312,476 / 69,669,640이었다. 651 grant와 비교하면 위상 1은 4.19 µs 늦었고 위상 2는 같은 클록이다. 세 경우 모두 53번의 화면·map 및 65816 최종 ACK를 대조했고, 앞 화면 ACK→EA→새 COMMIT 순서, 두 staging 슬롯, BG 적중 48회·OBJ 캡처 1,200회를 확인했다. 같은 ARM에서 독립 검사·STOP·메뉴 복귀와 base 정상 복구·네 실패 차단도 통과했다.

## 다음 구현의 삭제 예산

MMC643 대비 보드 전체 증가는 749 LE다. 압축기를 추가하기 전 여유는 54 LE였으므로 다음 후보는 이번 구현에서 **최소 695 LE, 53 LAB**를 줄여야 한다. 현재는 exporter가 map을 기존 record로 구성하고, 호스트가 그 record를 RAM에서 다시 읽어 15비트 셀로 푼 뒤 압축한다. 다음 비교 대상은 셀을 받는 시점에 같은 RAM에 저장해 이 중복 변환을 제거하고, 원본·복원값·압축 wire CRC를 계산하는 상호 배타적 단계에서 계산 회로를 공유하는 구조다. 원본 fallback의 CRC 상태와 ARM 독립 검사는 보존한다.

## 재현 조건

- ARM은 `prepare_nes_sender652.py <651 grant> <새 ARM 디렉터리>`로 준비하고 `build_nes_trial577.ps1`로 전체 링크한다. 651과 같은 geometry·END·queue·SEAL·menu 검사와 base 정상 복귀·네 실패 차단을 이 ELF로 실행한다.
- 보드는 같은 스크립트에 `--board <MMC643 보드 디렉터리> <새 보드 디렉터리>`를 주고 Quartus Lite에서 `quartus_sh --flow compile board`를 실행한다. 한 좌석 FLOAT에서 `check_nes_sender652.py`의 일반 실행과 `--guards` 실행을 각각 새 출력 경로로 수행한다.
- 651의 CPI 2·공유 SPI 드라이버·IRQ·ROM 달력, 637 client01, 시작 클록 7,288,416 / 7,467,100, 905–957 및 `--geometry650 --commit-pop-bound --keep-run`을 사용한다. `test_nes_sender652.py`의 대조군은 같은 652 ELF를 사용한다. ARM 첫 조회를 시작점으로 한 대조군에는 `--sender652 <RTL 출력>/sender.json`을 추가한다. 보드 소유권 일정에는 `--board-owner`도 지정한다. 이때 첫 블록 준비는 캡처 완료, 이전 plan의 닫힘을 확인한 실제 E8, 이전 세대 마지막 ROM·cache 응답 후 네 master 클록 중 가장 늦은 시각에 시작한다. 이전 staging 타일은 자기 token으로 계속 소비한다. [닫힌 plan과 타일 소비의 보드 RTL 시험](nes-receive649-results.ko.md) D2 반납(마지막 COMMIT은 D3 승인)과 첫 입력 공급을 기준으로 실제 송신 바이트가 준비될 때까지 D0의 ready를 보류한다. 연속 일정은 측정한 RTL 준비 클록과 모델의 SPI·IRQ·ROM 이벤트를 결합한 재생이다. 보드 배치 후 시간이나 실기 FPS를 측정한 결과는 아니다.
