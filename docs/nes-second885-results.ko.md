# 885 · 962 테이블 발행 전 963 두 번째 블록 수신

실기 기준은 MMC872, 구현 대조군은 883 공유 링크다. 884에서 첫 입력 블록은 일찍 받았으나 963 표시는 두 위상 모두 3 VBlank에 머물렀다. 이번에는 같은 884 ARM·65816 바이너리에서 962의 마지막 OBJ 반환 뒤 일반 출력의 큐 credit을 한 번 빌려 두 번째 입력 블록도 처리했다. 실험 A는 팔레트 후반의 첫 credit을, B는 section 5의 201B 패킷을 보낸 뒤 240B 테이블 직전 credit을 사용했다.

## 962와 963의 일정

| 같은 884 링크, 위상 1 / 2 | 두 번째 D2 후속 확인이 빨라진 시간 | 962 테이블·SEAL 발행 지연 | 963 표시 간격 | 밀집 60간격 합 | 밀집 마지막 65816 ACK 차이 |
|---|---:|---:|---:|---:|---:|
| A · 팔레트 반환 때 수신 | 3.443 / 3.441ms | +7,934 / +7,934클록 | 3 / 3 | 139 / 139 | +104 / +350클록 |
| B · 테이블 직전 수신 | 1.687 / 1.687ms | +7,934 / +7,934클록 | 3 / 3 | 139 / 139 | −392 / +240클록 |

차이는 모두 같은 위상의 884 원본 대비이며 ACK의 양수는 지연이다. 분기 직전까지 A는 8,963 / 8,997건, B는 8,969 / 9,003건의 SPI 거래가 원본과 일치했다. A는 두 번째 블록의 토큰 확인까지 **원래 테이블 발행 전**에 끝냈다. B는 실제 테이블 직전에 끝냈으나 원래 테이블 발행보다 6,730 / 6,729클록 늦었다.

공유 SPI에서 31B D1, 8B D2, 8B D0 확인을 먼저 수행한 만큼 테이블과 SEAL이 모두 0.369ms 밀렸다. SEAL 뒤에는 같은 블록을 다시 받을 필요가 없어 963의 입력 END 확인 시각은 원본보다 15 / 16클록 늦은 시각으로 수렴했다. 두 후보 모두 962 최종 ACK 전 **D2 후속 확인까지 마친 블록은 12개**로 같다. ARM이 마지막 유효 E0를 확인한 시각도 A는 657 / 4,858클록, B는 564 / 339클록 늦어졌다.

950의 1,472+64B 선행 DMA와 3 VBlank 표시, 952의 2 VBlank 표시를 유지했다. 같은 화면·작업량·최종 ACK 순서와 오류 주입 시험은 통과했다. 두 번째 블록 재배치는 단독 후보로 종료하고, 구현 대조군은 883, 실기 기준은 MMC872를 유지한다.

## 앞선 화면에서 회수할 수 있는 시간

883에서는 961 캡처를 한 번 앞당기려면 960의 COMMIT 패킷 D2를 58,250,984 / 58,608,352클록보다 먼저 끝내야 했다. 실제 완료는 5,058 / 4,583클록 늦었다. 959 최종 ACK 뒤에 온전한 E0 거래(2,343클록)를 즉시 시작한다고 가정해도, 유효 E0부터 마지막 D2까지 실측한 13,113클록을 그대로 쓰면 2,080 / 1,936클록이 부족하다. 이 계산은 ACK·EA·재무장·COMMIT 순서를 유지한다. 하한 계산에 사용한 실측 시각은 [원시 결과](../analysis/second885-results.json)의 `upstream_capture961`에 있다.

959에서 883의 65816은 위상 1에서 226선, 위상 2에서 225선에 `wait169`에 진입해 다음 VBlank 225선에 돌아왔다. 대기는 각각 356,236 / 356,778클록이었다. 882 위상 1은 같은 화면에서 223선에 진입하고 2,660클록 만에 돌아왔다. 두 링크는 앞선 입력 위상이 다르다. 다음 시험은 883에서 959의 SEAL 수락부터 업로드·대기 함수 진입까지를 대조해 두 위상 모두 225선 전에 대기를 시작할 수 있는지 확인한다. 768B 선행 DMA와 16B 타일 처리, 246선 검사, STOP을 보존하고 961 캡처 및 밀집 마지막 ACK까지 재생해야 한다.

## 검증 범위와 재현

- `replay_nes_second885.py TEMP PHASE WORK palette|table`을 위상 1과 2에서 실행한다. WORK는 884 링크다. 재생 도구가 962의 지정된 credit 콜백에서만 기존 ARM 한 블록 수신 경로를 선택한다. FINISH·준비 완료·수신 중·잔여 예산 6을 검사하고, 실제 D1·CRC·D2·D0 확인과 STOP 검사를 실행한다. 추가 제품 분기 비용은 이 대조에 포함되지 않는다.
- `guard_nes_second885.py WORK/link-credit/src TEMP/nes-ack861/sender-demo/sender.json OUT`은 실제 963 첫 두 블록으로 정상 수신, 읽기 전 STOP, D1 뒤 STOP, D2 뒤 STOP, 데이터 CRC 오류, 정상 CRC를 가진 이전 토큰 응답을 검사한다. 실패마다 예산이 유지되고 전체 초기화 후 두 블록의 수신 상태가 정상 대조와 일치해야 한다.
- `check_nes_second885.py TEMP OUT analysis/second885-results.json`은 변경 전 SPI 거래, 962 E1 패킷의 바이트와 순서, 세대별 활성 RGB·map·최종 ACK 순서, 950의 기존 DMA 일정과 두 위상의 최종 공개를 대조한다. 이전 최종 ACK 전에 수신한 블록은 D1 데이터 전송 완료와 D2 뒤 토큰 확인 완료를 구분해 센다.
- 보드·메뉴·실기 설치본은 기존 MMC872를 사용한다. 이번 결과는 지정된 ROM 허가표와 공유 SPI 비용을 포함한 두 CPU의 결합 재생이다.
