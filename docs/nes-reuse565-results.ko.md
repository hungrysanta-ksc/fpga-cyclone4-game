# 565 · PSRAM 읽기 여유와 취소된 타일 뱅크 재사용

실기 기준은 MMC558이고 비교 대상은 564다. 565에서는 loader의 OE가 항상 비활성이고 소유자가 없으면 physical reader가 비동기 reset을 받는다는 조건을 이용해 boot의 중복 OE 선택을 제거했다. host 타일 취소 체인은 공통 reset을 이미 host 클록에서 해제한 신호로부터 해제한다. 양쪽 도메인의 고장 신호에 의한 비동기 차단은 유지했다. 564 보드와 입력 파일을 대조하면 변경은 `nes_rom_boot.sv`와 `nes_tile_bulk206.sv` 두 개다.

## ROM_OE부터 데이터 샘플까지

Quartus Lite에서 같은 기기·seed·제약으로 FIT했다. 기존 12ns 핀 제약은 원래 보드 STA에서 판정했다. 별도 timing netlist에서는 패키지 핀을 기준으로 지연 0의 가상 IO 클록을 사용해 읽기 출력과 입력의 두 구간을 각각 조회했다. 각 경로에서 `latch − launch − setup_slack`을 사용해 클록 삽입 지연과 캡처 setup을 포함했다. 출력은 주소 20핀과 1CE·2CE·OE, 입력은 ROM_DATA 16핀 모두에서 해당 reader 캡처 레지스터까지의 최악 경로를 검사했다.

주소·chip은 샘플 17 메모리 클록 전, 읽기 CE·OE는 16클록 전에 발행한다. 기존 예산과 같은 메모리 주기 5.952ns, PSRAM 접근 70ns, PCB 편도 2ns를 사용했다. 조건부 여유는 각 구간에서 `클록 수 × 5.952 − FPGA 출력 구간 − 2 − 70 − 2 − FPGA 입력 구간`이다. [기존 예산의 조건](../analysis/GAME160-RESULT.ko.md)

| Slow 85°C | MMC558 | 564 | 565 |
|---|---:|---:|---:|
| ROM_OE 출력 구간 | 12.302ns | 12.696ns | 11.160ns |
| 데이터 입력 최악 구간 | 6.024ns | 6.912ns | 6.152ns |
| 16클록 내 CE·OE 조건부 여유 | +2.906ns | +1.624ns | **+3.920ns** |
| 17클록 내 주소 등 조건부 여유 | +7.457ns | +4.640ns | +8.849ns |

565의 CE·OE 여유는 Slow 0°C에서 +5.980ns, Fast 0°C에서 +11.569ns였다. 원래 보드 STA의 12ns ROM_OE 제약도 세 코너 모두 통과했다. 85°C slack은 −0.606→+0.930ns다. 가상 IO 계산과 원래 핀 제약은 쓰는 클록 기준이 다르다. 이 여유는 보드에 장착된 칩과 배선 지연을 직접 측정한 값이 아니다.

실제 loader·reader RTL을 70ns 핀 RAM 모델에 연결했다. 두 위상의 952·954 주소 자극을 합쳐 각 설계에서 974개 캡처가 모두 OE 하강 16클록 뒤에 일어났고, 기준과 후보의 수락·반환 이벤트 1,930개가 일치했다. 두 클록을 모두 멈춘 활성 CHECK 읽기에서 소유권만 해제해도 CE·OE는 비활성이 됐다. 이 시험은 합성 패턴의 첫·끝 바이트를 핀으로 쓰고 중간은 초기화한 경계 시험이다. 384KiB 전체 적재 기록은 [562](nes-owner562-results.ko.md)에 있다.

## reset 해제와 토큰

실제 타일 생산기·mailbox·두 aperture 뱅크·버스 소비 제어에 보드 direct path의 양방향 sticky-fault 동기화와 reset 배선을 연결했다. 세대 952의 48B BG 일부를 읽고 32비트 소비 토큰의 하위 두 바이트를 쓴 뒤 공통 core reset을 인가했다. 이전 데이터는 즉시 버스에서 사라졌다. 새 세대 953에서 같은 뱅크에 다른 16B를 썼고 각 바이트와 이전 tail의 비노출을 확인했다.

| reset 해제 뒤 관측한 host 에지 | 564 | 565 |
|---|---:|---:|
| aperture가 새 쓰기를 받을 수 있음 | 5 | 7 |
| 첫 16B 작업에 실제 OPEN 수락 | 204 | 204 |
| 새 세대의 첫 chunk 공개 | 255 | 255 |

두 시작 위상에서 동일했다. 물리 뱅크의 준비는 host 2클록 늦어졌지만 이 자극에서는 새 타일 공급이 더 늦어 실제 공개 시각은 같았다. core reset을 직접 입력한 시험이며, loader 재시작·RAM scrub·ARM 재발행 시간을 포함한 실기 재입장 시간이 아니다. 이전의 직접 `core_release → bulk.hcancel` recovery 경로는 세 코너에서 사라졌다. 565의 해당 체인에는 source_failed에서 시작하는 비동기 recovery가 남는다(85°C −6.190ns).

**ACK 재사용의 조건도 재현했다.** reset 전의 두 바이트에 이어 새 세대에서 나머지 두 바이트와 commit을 쓰면 mask 검사가 이를 거부해 host fault가 래치됐고 소비 펄스는 0회였다. 반면 코어 reset 뒤 첫 토큰은 다시 1이다. 새 chunk를 한 바이트도 읽기 전에 이전 토큰 네 바이트와 commit을 모두 재전송하면 두 설계 모두 새 뱅크에 소비 펄스 1회를 냈다. 이 명령은 타일 운송의 소비 ACK다. 최종 표시 ACK와는 별개다. 이 벡터는 이전 버스 쓰기가 재개되는 경우를 주입한 것으로 실기에서 재현된 실패는 아니다. [reset을 넘는 버스 정지 조건](nes-mux258-contract.ko.md)

두 위상에서 실제 65816 소비를 다시 실행하고 각 121개 chunk의 descriptor 읽기, 마지막 데이터 읽기, 토큰 네 바이트 쓰기와 commit을 기록했다. 진행 중인 정상 실행에서 마지막 데이터 읽기→commit의 최댓값은 69.469 / 69.283µs, descriptor→commit은 양쪽 모두 2.565ms였다. 정상 시간 분포만으로 reset 동안 CPU가 멈췄다 재개하는 경우까지 배제할 수 없다.

## 보드와 결정

| 지표 | MMC558 | 564 | 565 |
|---|---:|---:|---:|
| LE / 15,408 | 15,164 | 15,223 | 15,182 |
| 조합 논리 / FF | 14,172 / 8,394 | 14,197 / 8,399 | 14,187 / 8,401 |
| M9K | 51 | 51 | 51 |
| 대상 setup / hold | +0.078 / +0.139ns | +0.415 / +0.162ns | +0.042 / +0.156ns |
| 전체 최악 setup / recovery | −7.081 / −8.480ns | −6.724 / −8.877ns | −7.286 / −7.937ns |
| MMC558 대비 악화된 기존 음수 STA 항목 | 기준 | 10 | 5 |

남은 항목은 84MHz setup 2개, NES setup 2개, 168MHz fast recovery 1개다. MMC558 대비 가장 큰 차이는 84MHz slow 0°C setup의 0.223ns다. 미제약 출력 포트 경로 수는 7개 줄었고 다른 미제약 집계는 늘지 않았다. 기존 ARM·SPI·IRQ·ROM 도착 기록의 65816 재생은 두 위상 모두 53개 RGB·ACK 추적이 일치했다. 952는 5 VBlank, 밀집 5화면 합계는 25 VBlank이고 957 최종 검사 뒤 추가 대기는 0회다. 565로 실기 FPS를 측정하지 않았다.

**MMC558을 실기 기준으로 유지한다.** 다음은 이전 마지막 데이터 읽기 전후와 첫 토큰 쓰기 직전에 취소를 주입해 실제 65816과 ARM STOP→재시작 경로에서 쓰기가 어디까지 진행되는지 확인하는 것이다. 새 토큰을 공개하기 전에 이전 소비자의 버스 쓰기가 종료된다는 보장이 없으면 재시작 승인 절차와 세션을 구별하는 토큰을 비교한다. 565의 OE 여유를 유지하면서 남은 setup·recovery도 같은 보드에서 다시 평가한다. [측정값·해시·전체 판정](../analysis/reuse565-verification.json)

## 재현

1. `prepare_nes_reuse565.py`로 MMC558 보드에서 후보를 생성하고 Quartus Lite 전체 compile과 기존 `timing506.tcl`, `report_nes_owner562.tcl`, `report_nes_arg564.tcl`을 실행한다.
2. MMC558·564·565 배치에서 `report_nes_pins565.tcl`을 실행한다. IO 구간을 조회한 뒤 원래 SDC를 새로 읽어 취소 recovery를 별도 보고한다. 원래 제약 파일은 변경하지 않는다.
3. FLOAT wrapper에서 `check_nes_reuse565.py`를 실행한다. 선택 보드는 board01, RTL은 rtl04다. 예비 시험에서 벤치 생성 위치와 의도된 sticky-fault 판정을 보정하고, 최종 시험에 클록 정지 중 CHECK 해제를 추가했다. `replay_nes_close561.py --all-banks`로 두 위상을 재생한 뒤 `analyze_nes_reuse565.py`에서 세 보드의 예산과 토큰·53화면 기록을 합친다.
