# NES174 — 타일 묶음 전송, 실기 배포는 보류

174 후보의 배경·스프라이트 패턴 전송을 묶었다. SMB3 모델 frame24·25에서는 패턴 요청이 화면당18회에서3회, BEGIN·테이블·SEAL을 포함한 전체 요청은45회에서30회로 줄었다. 최종 후보 데이터와 SNES 표시 픽셀은 기준과 일치한다. 실기 시간·FPS 개선은 아직 측정하지 않았다.

**화면 끊김 개선을 위한 구현이며 목표 전체는 미달성이다.** FPGA는 이전174의 memory setup -0.807ns 실패 결과를 그대로 유지한다. 이번에는 FPGA 소스·클록·제약을 바꾸거나 무변경 FIT를 반복하지 않았다. 새 설치 ZIP은 없으며 단독174 firmware.stm을 기존173 FPGA와 섞어 사용하면 안 된다.

## 구현과 버퍼 수명

| 구간 | 임시 저장 | 묶음 크기 | 다음 용도로 넘기는 조건 |
| --- | --- | --- | --- |
| BG 변환 | 후보 OAM의 앞240바이트 | 연속15타일, 최대240바이트 | 마지막 부분 묶음 ACK 후 OAM 전체544바이트를 지우고 OBJ 작성 |
| OBJ 변환 | 후보 CGRAM의 앞224바이트 | 연속7타일, 최대224바이트 | 마지막 부분 묶음 ACK 후 CGRAM 전체512바이트를 지우고 팔레트 작성 |

0번 빈 BG 타일도 첫 묶음에 포함한다. 중복 타일은 기존 슬롯을 재사용하고 새 슬롯만 순서대로 누적한다. 콜백은 반환 전 데이터를 소비하며 포인터를 보관하지 않는다. 오류 시 후보 valid는 false로 남고 SEAL·재시도 없이 기존 종료 경로로 간다. ACK가 확인된 묶음의 타일 수만 진행시킨다.

패킷의 기존 DATA 명령·섹션·바이트 오프셋·최대240바이트는 유지한다. 오프셋은 `첫 슬롯 × 타일 크기`이며 묶음 길이를 곱하지 않는다. 0길이, 타일 크기 배수가 아닌 길이, 초과 길이, 잘못된 종류·순서·끝 슬롯을 거부한다. 실제 전송 패턴 바이트는 줄이지 않으며, 이 두 모델 장면에서는 헤더·ACK 합계420바이트/화면을 절약한다. 전체 요청 약33% 감소를 화면 속도33% 향상으로 환산하지 않는다.

MCU 수신 문맥18,064바이트와 후보15,888바이트는 그대로다. 두 번째 프레임 버퍼·카트리지 세이브 SRAM·RUN 중 SD 쓰기를 추가하지 않는다. 174의 cross-tile ABI1741·4바이트 예외와 172의 SNES 코드, 사운드·입력·STOP 처리는 유지한다.

한 패킷의 최대 길이는 기존 테이블 전송과 같은240바이트지만, 변환 도중 콜백을 부르는 간격은 달라진다. 실기에서 사운드·입력·STOP 응답 간격도 함께 확인해야 하며, 소스 유지나 패킷 수 감소만으로 최악 응답 시간을 보장하지 않는다.

## 검증과 한계

- 실제 구·신 C 변환 결과: 합성7경우와 SMB3 모델 frame24·25, 총9경우의 전체 후보·패턴 바이트 일치. 요청342회→45회는 이 테스트 집합의 합계다.
- 각 묶음의 전송 실패, stale ACK, 길이·순서·경계 오류62경우에서 중단 확인. BG1024슬롯·OBJ128슬롯 끝까지 패킷 오프셋·개수 확인.
- 실제 C 패킷 송신기와 기존172의 실제65816 수신기를 파일 mailbox로 연결: 정상3회 표시·92ACK, STOP1회 표시·60ACK, 총229,376픽셀 일치. 240/16/64바이트 패턴 패킷, invalid section, stale token, STOP 거부 경로 포함.
- C 바이트 비교는 모델 ACK를 사용한다. 별도 실제SNES 시험은 그와 동일한 미리 계산된 패턴 바이트를 묶어 전송한다. 물리 SPI·실기 프레임 속도 증명은 아니다.
- ARM 전체 링크: 정적RAM26,564 / foreground37,312 / IRQ508 / 여유1,040바이트. 기존174의 여유1,024보다16바이트 늘었다. 실행 중 측정한 최고 스택 사용량은 아니다.
- firmware SHA256: `89c98add72ed3a6d983f9961c96b7ac2d7da6a889ba0fc5d5595da25dacfaa87`. 검증 후보이며 설치 허가가 아니다.

초기 C 실행은 sandbox DLL 재배치 오류(c01), 이어 테스트 복사 목록에 진단 헤더가 빠진 오류(c02)로 실패했다. 헤더·구현을 포함한 c03이 통과했으며 기능 후보는 바뀌지 않았다. 두 실패도 원본 그대로 보존한다. 새 Questa/FLOAT 실행은 없었다.

## 타이밍 검토와 다음 작업

174의 `control.load_valid → loader.fault`는4논리 단계이며 데이터 배선5.372ns, 셀1.052ns다. 실제 경로가 X19의 fault 논리에서 X29의 error_code 공유 논리를 거쳐 다시 X19로 돌아간다. `check_failed → fault/loaded_bytes`도 미달이다. 원인을 신규 수집기 자체로 단정하지 않는다.

과거165의 평탄화된 fault·error 단일 owner·counter/command 변경 실패를 대조했다. 같은 수식을 다시 FIT하거나 seed·클록·false path로 우회하지 않았다. 다음에는 현재167의 C0raw/C1causes/C2decode/C3accept/C4counter 구조를 기준으로 **공유 오류 판정과 장거리 배선을 실제로 줄이는 변경**을 먼저 설계한다. 명령 수락 에지·오류 우선순위·진행 중 WRITE/HOLD drain을 바꾸려면 계약을 명시하고 MCU 간격까지 확인한다. 변경 경계 검증과 전체 타이밍 통과 후 필요한 IO/ARM 확인만 거쳐 최소 SMB3 실기로 돌아간다.

전송에서는 아직 map4096+CGRAM512+OAM544 및 HDMA 전체와 패킷별 ACK가 남아 있다. SNES 쪽 변경분 비교·DMA는 이미 구현돼 있으므로 재구현하지 않는다. 테이블 생략을 도입하려면 교대 WRAM 후보 뱅크의 기준 세대가 같음을 먼저 보장해야 한다. 단순히 동일 바이트를 보내지 않으면 두 세대 전의 데이터가 남을 수 있다.

실기 우선순위는 연속 영상·사운드 → 장기 플레이와 오류/본체 리셋 시 로그 → 입력 유지 품질이다. 동일173·044·부팅/A-B·통과한174 픽셀/SPI 시험은 관련 입력이 바뀌지 않으면 반복하지 않는다.
