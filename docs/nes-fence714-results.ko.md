# 714 BG 묶음 ROM 마감과 map 연속 DMA의 공동 발행 검증

## 목표

707D·기존694/704 ARM·기존694 65816을 기준으로, 필요한 BG 묶음의 ROM 공급과 map 연속 DMA를 함께 보존하는 구조를 검증한다. 같은 작업량·두 시작 시각에서 STOP·독립 검사·최종 ACK·메뉴와 911/951/952/957 보호 조건을 유지하며, **952–957 합계18 VBlank와 밀집 평균·957 마지막 ACK가 모두 감소해야 채택**한다. [검증 JSON](../analysis/fence714-verification.json) · [원시 근거 보관](../analysis/fence714-archive.json)

## 작업내용

713의 행 완료 즉시 전송은 BG 생산을 막았고, 첫 BG 한 개만 기다리는 수정도 실패했다. 이번에는 **BG 전체 계산 → 남은 BG plan의 실제 E8/E9 발행 → OBJ 계산 중 실제 생산기 대기에서 확정 map 공급**이라는 한 후보를 구현했다. 행별 조기 SPI와 `nes_sink527_early`를 제거하고 기존 오름차순 `map527`·cursor·quiet callback을 재사용한다. 두 페이지 모두 확정된 뒤에만 callback을 열고, E9·준비된 tile·실제 bulk receipt·queue credit 우선권은 기존 `drive554`와 `poll`에 둔다. 새 시간 상수·세대/위상별 분기·ROM 선반영·credit 가정·ABI는 없다.

quiet callback은 map의 dirty/stale 합집합을 사용한다. OBJ 계산 전에는 최종 `map_upload`가 아직 확정되지 않기 때문이다. 실제 ARM hook에서 모든 map 패킷이 BG 완료 이후의 동일 바이트인지, 이후 쓰기가 바꾸지 않는지, 중복 발행이 없는지 검사했다. 정상60초·장시간판을 각 원본에서 전체 링크했고, 실제 M4/65816 53화면씩 두 위상을 끝까지 실행했다. 시작7288416/7467100, 공유SPI·driver·IRQ·2bulk·credit·반복 ROM 달력은 대조군과 같다.

이 결과는 실제 링크 코드의 모델 일정이다. 실물 FPS, 실제 게임 NES/PSRAM 전체 RTL의 공동 실행, 물리 메뉴 복귀를 새로 증명한 것은 아니다.

911의 수락≤189선·upload≤214선 조건이 두 위상에서 깨졌다. 951 공개≤246선,952 표시3회,957 최종대기0회,7블록 선행 수신은 유지했다. 전체 일정에서 위상1은911·941이 각각 한 VBlank 늘고, 위상2는 cold905가 한 VBlank 앞당겨지고907은3→2회·941은3→4회다. 따라서 위상2의 마지막 ACK 단축을 지속 FPS 개선으로 계산하지 않는다.

954의 BG 발행은 약1.14–1.16ms 빨라졌지만 **이전 BG ROM 허용 구간의 끝에는 여전히2.211/2.140ms 늦는다.** 마지막 BG 생산 호출 자체도 그 구간보다0.739/0.668ms 늦다. E9/검사/ROM 읽기 비용을 0으로 두어도 단순 발행 순서만으로 해결되지 않는 생산 부족이다. 이 값은 필요한 선행량의 하한이며, 해당 구간 끝까지 읽기 전체를 완료할 수 있다는 충분조건이 아니다.

955는 마지막 BG 생산 호출이 이전 구간 끝보다0.535/0.605ms 먼저다. 그러나 **남은 BG 행 계산에2.385ms**, 마지막 묶음 발행에 약0.489ms가 더 들어 E9가2.348/2.277ms 늦는다. 954의 생산 지연과955의 이미 생산된 plan 보류를 같은 원인으로 취급하지 않는다.

현재 callback으로는 이 사이에 map을 공짜로 전송할 수 없다. **951–957의 quiet callback 실행은 모두0회**였다. 실제 E9가 허가되면 즉시 반환하고, 이어지는 행/OBJ 계산에는 생산기 대기 callback이 없다. SPI 버스가 비어 보이는 시간에도 ARM은 계산 중이며, 새 발행을 삽입하면 계산을 다시 늦춘다. 동기식 전체 BG 완료 조건은 기존 조기 map을 없앴지만 그 시간을 대체할 실행 지점을 만들지 못했다.

map 패킷의 주소별 연속 묶음과 전송 바이트는 원본과 같았다. 특히 오른쪽1536B의 연속 발행도 유지됐다. 그래도 실제 수락이 VBlank에 늦으면 선행 DMA는 줄어든다. **주소 연속성·행 확정·queue 저장 credit은 DMA 실행 시각을 보장하지 않는다.**

### 안전 검증과 실패 보존

- 실제 링크 M4의7개 fence/실제 대기/전체4096B cold 복구/STOP/E8 CRC/credit CRC/모호한 E1 조건을 통과했다. 단위 endpoint의 시간·입력 대기는 모델이며, 실제 ARM/IRQ/input 경로는 두 위상 통합 재생에서 실행했다.
- 장시간/clock/status/credit wrap/STOP/최종 ACK 분리16조건, 메뉴 준비·해제5조건과marker4조건을 확인했다. 메뉴·로그·IRQ I/O는 모델이다.
- 새 패킷 순서를 기존65816에 넣어 STOP4조건과 사용자 종료2조건을 실행했다. 이전 표시 보존, 최종 ACK 취소, 종료 후 DMA/ACK 중단을 확인했다.
- 처음 guard fixture는 reason4 입력 대기를 오래된 단순 pause 함수에 전달해 실패했다. 모델 대기를 바로잡았고 타깃 코드는 바꾸지 않았다. 이후 빈 flush helper의 반복 호출 대신 fault 이후 실제 plan 발행 차단을 검사했다. 잘못된 메뉴 marker696은 원본690으로 바로잡았다. 분석기의 BG 없는951 처리를 추가했다. 모든 실패 로그를 남겼다.

## 후속작업

이번 후보는 저장·비교 근거로만 보존한다. 전체 BG 완료를 기다리는 정책, 행 수·고정 시간·위상별 상수의 변형, quiet callback만 추가하는 반복은 보류한다. 새 설치본은 없다.

다음 구조는 **필요한 BG의 탐색·slot 확정/plan 발행과 나머지 map 행 쓰기를 분리**하는 경계다. 954는 최소0.739/0.668ms의 생산 선행에 E9·실제 읽기 비용을 더 지급해야 하고,955는 마지막 BG 뒤2.385ms의 행 작업보다 먼저 해당 묶음을 발행할 수 있어야 한다. 동시에 기존 map 수락 마감과 VBlank DMA 기회를 잃지 않아야 한다. 확정되지 않은 slot·행을 전송하거나 추가 탐색/CRC/복사를 비용0으로 두지 않는다.

기존1,116B 교체 상한 대비714 경계에는154B, 정상 전체Flash에는244B가 남지만 **714는 미채택이므로 제품의 확보 공간이 아니다.** 새 후보는 기존 코드를 실제 삭제하면서 같은 바이너리에서 이 예산을 입증해야 한다. 새 packet buffer·추가 RAM·중단/재개 문맥은 소유권과 stack 비용을 먼저 산정한다. FPGA·65816 변경은 현재0 예산을 유지한다.
