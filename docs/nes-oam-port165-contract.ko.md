# NES165 OAM 주소 범위 명시와 실제 배치 결과

PR108의 [면적 합성](nes-oam-select165-contract.ko.md)을 이어서 진행했다. **실행 시점을 바꾸지 않고 조합 논리 1,719개를 추가로 줄였다.** 전체 조합 논리는 칩 한도 안으로 들어왔지만 실제 배치는 LAB 1개 초과로 아직 실패한다. [검증 기록](../analysis/oam-port165-verification.json). 설치 후보164와 세이브 영역은 그대로이며 새 SD 패키지는 없다.

## 조사에서 구현으로 연결한 판단

- FPGA 내부 블록 RAM은 동기 읽기를 요구한다. 현재 OAM의 비동기 읽기·동시 접근을 그대로 RAM으로 선언하는 것만으로는 해결되지 않는다. 지연을 추가한다면 CPU/PPU 소비 시점, 행 복사, 같은 주소 읽기·쓰기 계약을 함께 바꿔 검증해야 한다. [Intel Standard 설계 권고](https://www.intel.com/programmable/technical-pdfs/683323.pdf).
- 다른 FPGA NES 구현도 OAM 접근과 스프라이트 평가를 별도 제어한다. 다만 조사한 FPGANES는 mapper와 APU를 구현하지 않은 교육용 사례이므로 현재 SMB3/MMC3·사운드 경로의 대체 구현으로 채택하지 않았다. 구조 참고에 한정한다. [FPGANES 개발 보고서](https://github.com/jtgebert/fpganes_release).
- 제조사 면적 최적화 문서에는 배치 단계의 조합 논리 최적화와 레지스터 결합 설정이 있다. 실제 적용값과 결과를 확인했으며, 이 후보에서는 LAB 초과를 해결하지 못해 기본값으로 돌아왔다. [Intel Standard 면적 최적화](https://www.intel.com/programmable/technical-pdfs/683230.pdf).

조사 후 실제 합성 보고서를 읽어 더 작은 수정 지점을 찾았다. 일반적으로 좋은 방식이라는 이유로 전체 메모리를 먼저 재설계하지 않았다. **관측된 큰 읽기 선택 회로가 왜 살아 있는지, 주소 범위를 합성기가 알고 있는지부터 확인**하는 것을 다른 코어에도 적용한다.

## 채택: 추가 스프라이트 쓰기 주소의 상위 비트 명시

원래 추가 스프라이트 쓰기는 `oam_secondary_row_ex < 8` 안에서만 실행된다. 이때 4바이트 각각의 주소는 다음 두 표현이 동일하다.

```verilog
// 기존: row는 4비트, 주소는 6비트
{oam_secondary_row_ex, 2'b00} + 6'd32
// 변경: 기존 row < 8 조건 그대로 유지
{1'b1, oam_secondary_row_ex[2:0], 2'b00}
```

Y/tile/attribute/X 네 주소만 바꿨다. 원래 주소도 조건 아래에서 32~63이므로 동작을 고치는 변경이 아니다. 상위 비트를 명시하자 합성기가 상위 secondary OAM 쓰기를 하위 32바이트와 분리하고, 현재 보드에서 사용하지 않는 추가 스프라이트의 하류 회로를 더 제거했다. `extra_sprites` 설정이나 기능을 삭제한 것은 아니다. 추가 스프라이트 평가가 실제로 쓰는 64바이트 전체를 비교했다.

레지스터·클록·CE·데이터 소비 시점·CPU/상태 저장 쓰기 우선순위는 변경하지 않았다. 내부 RAM 사전 읽기는 이번 채택안에 추가하지 않았다. 기존 구현의 타이밍을 유지하는 주소 표현 변경만으로 먼저 큰 절감이 나왔기 때문이다.

| 항목 | 이전 AREA | 채택 map02 |
| --- | ---: | ---: |
| 합성 추정 LE | 21,070 | 19,351 |
| 전체 조합 논리 | 15,647 | 13,928 |
| OAMEval 조합 논리 | 5,663 | 3,939 |
| 레지스터 | 8,294 | 8,284 |
| 메모리 비트 | 197,104 | 197,104 |

전체 조합 논리는 이전 AREA보다 약11.0%, 최초 board03의16,441개보다2,513개(약15.3%) 감소했다. 물리 Fitter는 **14,983 LE, 35/56 M9K, 964/963 LAB**를 보고하고170012/171000으로 실패했다. 실패한 배치의 중간 자원 수이며 완성된 배치·배선 결과가 아니다. LE 한도15,408 이내라는 이유로 설치 가능하다고 판단하지 않는다. STA/새IO 승인도 없다.

## 검증과 재사용 범위

- 기존 banked OAM과 매 클록 출력·관측 포트·primary256바이트·secondary64바이트·평가 상태를 비교: **216,362클록, 행 복사2,426회, CPU 쓰기3,111회, 상태 저장 쓰기10,473회, 충돌2,012회 일치**. 초기 미정 상태, 난수 입력, NTSC/PAL 주사 순서 포함.
- 별도 지시 시험에서 추가 행 값0~15 전부 확인: 허용8행·거부8행, 총1,024바이트 비교. 허용된 경우 상위4바이트만 바뀌고 나머지는 그대로인지 검사했다. 상위 비트를0으로 잘못 바꾼 대조군은 첫 행의 하위 주소0에서 검출했다.
- 기존 조건 아래32가지 행·바이트 조합의 주소 계산도 전수 대조했다. 전체 OAM 상태 공간에 대한 형식적 등가 증명을 주장하지 않는다.
- 최종 공개 생성기로 입력을 다시 만들고 실제 map02와 모든 입력 바이트가 같은지 확인했다. board03 대비 QSF와 `rtl/ppu.sv`만 다르고 다른59파일은 그대로다. 생성기의 후속 선택지 추가는 실행된 모듈 본문과 별도로 대조했다.
- 소비 시점을 바꾸지 않아 동일 SMB3 부팅·SPI/SNES·044 시험은 반복하지 않았다. 이전 실제 보드 연결 시험과 게임 자료의 적용 범위는 유지하되, 새 배치의 타이밍은 재승인해야 한다.

## 제외한 시도와 반복 금지

| 시도 | 결과 | 판단 |
| --- | --- | --- |
| map01 main/repeat 읽기 공유 | 조합15,665, 기능 비교 통과 | 일부 소비자는 이미 제거되어 효과 없음 |
| fit03 배치 조합 논리 면적 최적화 | 설정On 확인, 여전히964LAB | 같은 MAP DB 재사용; 채택 안 함 |
| fit04 Minimize Area 레지스터 결합 | 적용 확인, 여전히964LAB | 같은 MAP DB 재사용; 채택 안 함 |
| map05 primary OAM bank enable 인식OFF | 조합15,761,170011실패 | LUT 비용 증가; 채택 안 함 |

선택은 **기본 AREA + 주소 네 곳 수정(map02)**이다. 잘못된 대조군의 예상 실패와 처음 검증기가 기존 Balanced 보고서까지 Area로 요구한 검사 오류도 별도로 보존했다. 과거 공개 파일·핀·완료 archive/record/audit를 수정하지 않는다.

## 다음 작업

1. map02를 기준으로 남은 OAM 행 복사·primary 저장 회로와 실제 LAB 제어 묶음을 축소한다. 같은 네 제외안을 반복하지 않는다. 비동기 메모리의 M9K 전환이 필요하면 PPU CE 사이 사전 읽기, CPU 즉시 주소 지정, 행 복사, 상태 저장 동시 쓰기의 소비 시점을 먼저 정의한다. 기능을 제거하거나 CPU/PPU를 느리게 하지 않는다.
2. 전체 배치가 성공하면 해당 배치의 setup/hold, PSRAM CE/OE/데이터, 새 SPI/SNES 경로의 최소 타이밍을 확인한다. 기존 SDC를 완화해 통과시키지 않는다.
3. MCU RUN 수신→변환→ACK와 실제 경과시간·오디오·입력·STOP 서비스, 전체 링크·중첩 스택을 연결해 SMB3 첫 레벨 실기로 간다. 일반 진단을 추가하거나 변경 없는 부팅·044 복원을 반복하지 않는다.

카트리지 SRAM·세이브·자동 저장·복구 영역은 영상 임시 저장소로 쓰지 않는다. 사운드·입력을 빼서 자원 수를 맞추지 않는다. 실제 FPGA 배치와 MCU 연결이 미완료이므로 정상 플레이·60fps·실기 시험 준비 완료로 표시하지 않는다.
