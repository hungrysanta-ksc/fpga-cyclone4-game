# NES179 — 첫 레벨의 화면 중간 렌더링 중단·재개

178 실기의 **월드맵에서는 갱신되고 첫 레벨에서는 멈췄다가 월드맵에서 회복되는 현상**에 맞는 출력 제약을 재현했다. 목표 ROM을 기준 에뮬레이터에서 실행하면 첫 레벨의 상태창 경계에서 매 프레임 렌더링을 잠깐 끈다. 그 설정 변경을 배포178의 실제 raster 수집기에 넣으면 거부되고, 월드맵 설정으로 되돌리면 다시 유효해진다.

이는 기준 ROM 동작과 수집기 제약의 확인이다. **실기에서 발생한 모든 오류·유일한 원인 또는 수정 완료를 입증한 것은 아니다.** 배포178과 기존 패키지는 유지했고 새 펌웨어·FPGA·ZIP은 만들지 않았다.

## 재현한 장면

사용자 지정 첫 레벨 진입은 **월드맵의 숫자1 타일로 이동 → A**다. START 두 번만으로 첫 레벨에 들어갔다고 판단하지 않는다.

- ROM은 기존 SMB3 일본판 SHA-256 `dbb1cb5e18b091ca9101b1c2f5a5d6bdbeaa4a30ae1a504251310f6765cabb49`와 일치한다. ROM·게임 RAM은 수정하지 않았다.
- Mesen의 실제 게임 실행에서 START30..33/90..95, RIGHT400..419, UP450..469, A500..505를 입력했다. 각 구간 사이에 버튼을 놓았다. 이 숫자는 모델의 프레임 번호이며 실기의 대기 시간 안내가 아니다.
- 이미지480에서 마리오가 숫자1 위치에 도달했고,650/700에서 실제 첫 레벨과 움직이는 오브젝트·진행하는 타이머를 확인했다. 초기 시도01..03의 입력은 월드맵 진입 안내 중 무시되거나 목적 타일까지 도달하지 못했다. 최종 기준은reference05다.
- 기준 에뮬레이터는 자체 NES 데이터베이스의 MMC3A 설정을 사용했다. 이식된 FPGA 코어와 같은 구현·같은 세부 타이밍이라고 주장하지 않는다. 영상과 원본 레지스터 기록은 비공개 증거 폴더에 보존했다.

## 발견한 반복 패턴과 시험 범위

첫 레벨의 기준 프레임600..699 전체100개에서 `$2001`이 주사선193 도중 `18 → 00`으로 바뀌고, 뒤에 `18`로 복구된다. 재개는94개에서 같은 주사선,6개에서 다음 주사선194의 dot1이다. 일부 시점에는 `$2006`도 바뀐다. 특정 줄 번호를 구현의 예외 조건으로 사용해서는 안 된다.

이것은 화면을 몇 분 동안 전송하느라 바쁜 현상과 다르다. 정상 게임이 화면을 그리는 도중 상태를 바꾸는 동작이며 현재 출력 표현의 지원 범위와 대조해야 한다. 렌더링이 꺼지면 배경·객체 fetch와 출력 상태도 달라진다. 비활성 구간의 색은 항상 검정이 아니므로 임의의 검정 타일로 대체하면 안 된다. [NES PPU 레지스터](https://www.nesdev.org/wiki/PPU_programmer_reference), [PPU 렌더링](https://www.nesdev.org/wiki/PPU_rendering)

| 시험 | 결과 | 판단 가능한 범위 |
| --- | --- | --- |
| 실제 ROM의 월드맵/숫자1/레벨 PPUMASK 기록을 배포178 raster에 재생 | 16경우 통과: 월드맵 수용, 레벨 `08` 또는`48` 거부, 깨끗한18로 복귀 시 수용 | mask 변화만으로 거부하기에 충분함. 다른 raster 입력은 고정했으므로 실제 전체 오류 묶음은 아님 |
| 기록된 시점에0/1/3 dot 지연을 적용 | 다음 행 시작을 넘는 경우에도 거부 확인 | 기준 에뮬레이터의 쓰기 콜백과 FPGA의 유효 시점이 같다는 가정에 의존하지 않음. 모든 지연의 증명은 아님 |
| 실제 compact에 정상224행·타일1개 누락·행1개 누락·회복 입력 | 5경우 통과: 누락은`82`, 정상/회복은0 | 별도 합성 입력. 실제 첫 레벨에서 compact82가 발생했다고 단정할 수 없음 |

`08`은 행 도중 mask 등의 상태 변경, `48`은 여기에 행 시작의 미지원/불일치 mask가 함께 걸린 경우다. `82`는 compact의 순서/위치 불일치와 불완전 행 종료다. 출력 전 단계의 거부라면 전송 BEGIN/ABORT가 추가되지 않을 수 있어 실기의 ABORT0과 모순되지 않는다.

## 수행하지 못한 검증과 중단한 작업

전체 CPU/PPU/MMC3·직렬 패드·178 수집기를 묶은 `probe_nes_level179.py`도 준비했다. 첫 시도는 테스트벤치 선언 순서 오류로 컴파일 실패했고, 수정한 두 번째 시도는 컴파일됐으나 시작6개 프레임까지만 진행한 뒤 중단했다. 예상 전체 재현 비용에 비해 실제 레벨 경계에 필요한 정보를 빨리 얻지 못했다. `result.json`이 없으며 **전체 코어 레벨 재현·기존26상태/24·25픽셀 비교 통과로 계산하지 않는다.**

기준 에뮬레이터 실행과 분리된 수집기 재생을 대신 완료했다. 최초6프레임의 중단 자료는 실패/중단 증거로 보존한다. 다음 작업에서 같은 긴 부팅 모델을 무조건 반복하지 않는다. 현재 증거로 판별할 수 없는 실제 fetch/compact 오류는 작은 실기 관측으로 보완하는 편이 적절하다.

## 다음 구현의 범위

1. **화면 중간 렌더링 중단·재개를 우선한다.** 이전 계획의 독립 왼쪽 클리핑1a/1c 확대보다 첫 레벨의 실제 요구가 먼저다. 게임명·매퍼4·고정193행으로 허용하는 예외는 만들지 않는다.
2. raster의 오류 비트만 끄지 않는다. 표시 가능한 구간과 비활성 구간, 누락된 fetch와 다음 행의 재시작, 스크롤·팔레트 상태를 함께 표현해야 한다. 비활성 구간 전체에 숨겨진 타일만 명시적 placeholder로 다룰 수 있으며 보이는 부분에 오래된 타일을 채우면 안 된다.
3. 구현 전에 실제 보드에서 아직 모르는 항목만 확인한다. 유효한 프레임 이후 처음 거부된 세대의 fetch/compact/raster 이유·mask·행/dot·개수를 잡고, 이유 변경과 회복을 구분한다. 정상적인 화면 전환 blank가 첫 표본을 독점하지 않도록 한다. 기존 종료 로그와 관측 공간을 우선 재사용하며 RUN 중 SD 기록이나 전체 프레임 버퍼를 추가하지 않는다.
4. 출력은 기존 SNES 행별 상태/윈도우가 표현할 수 있는지 먼저 검토한다. 행 도중 색·상태를 정확히 재현할 수 없는 경우에만 제한된 예외 구간의 실제 픽셀을 보존하는 대안을 비교한다. 타일·스프라이트 우선순위·backdrop·재시작이 맞는지 확인하기 전 패키지에 넣지 않는다. 이 문서에서 어느 대안도 구현/적합성 확인 완료로 기록하지 않는다.
5. 작은 경계 시험 뒤 바로 같은 SMB3의 숫자1→A→실제 레벨로 간다. 필요 이상의 일반 진단을 늘리거나 같은178/044 시험을 요청하지 않는다. 표시 정지 해소와 약60fps는 별도 합격 조건이다. 앞단 차분/base-generation/최종ACK 기반 전송 개선도 유지한다.

이는 실기 코어 실행 성공을 지속 영상으로 연결하기 위한 출력 구현 준비다. 화면이 멈춰도 게임·음악·입력이 계속될 때는 이 수집 거부 경계를 우선 확인하되, 모든 게임의 같은 증상을 같은 원인으로 분류하지 않는다. 매퍼 IRQ·PPU 자체 오류·표현 용량 초과·전송 지연은 각각의 증거로 구분한다.
