# NES227 실기: 구동 정상, 전송 소폭 개선·스크롤 목표 미달

사용자는 실행·소리·메뉴 복귀가 정상이고 전체 프레임은 늘어난 듯하지만 스크롤 개선은 크지 않다고 보고했다. 로그와 영상은 이 평가에 부합한다. **227의 정확성은 실기에서도 유지됐지만 스크롤60fps는 달성하지 못했다.** 이번에는 결과만 PR125에 기록하며 새 펌웨어를 만들지 않는다.

완료 횟수는2.88% 늘었지만 장면·조작이 다른 두 실행이므로 통제된 FPS 개선율은 아니다. NES 내부 동작FPS나 CRT 주사율과도 다르다. 이번 영상은15~54초에 첫 레벨이 이어지고,18~22초·25~33초·43~52초에 배경 이동이 보인다. 55초 전환 뒤56~62초는 월드맵,63초부터 카트리지 메뉴다. 65.33초 영상에서131개 반초 샘플을 추출하고66개 초 단위 샘플을 육안 확인했다. 샘플은 장면 구분용이며 고유 프레임 수나 오디오를 측정하지 않았다. 소리 정상은 사용자 관찰을 근거로 한다.

호스트20~50초의5초 묶음은 각각29·30·29·33·34·33회 완료했다. 영상상 첫 레벨에 해당할 가능성이 높으나 호스트와 촬영 시작이 정확히 동기화된 것은 아니다. 이를 엄밀한 스크롤FPS로 표시하지 않는다.

## 개선이 작았던 이유

- E1 바이트/완료는15.13%, SEAL 시간/완료는5.28% 감소했다. 반복 전송 절감과 양립하는 결과다. 다만 표시된 객체 수/완료도46.63% 감소했고 실기 op8 사용량·OAM별 바이트를 따로 기록하지 않으므로 감소 전체를227의 효과로 단정할 수 없다.
- 타일 출력/완료는22.08%, 계획 수는17.50% 늘었고 finish 시간/완료는9.68% 늘었다. 장면에 따라 새로 필요한 타일·전송·대기가 달라 절감 일부가 상쇄된다. 이를227 자체의 타일 회귀로 해석하지 않는다. 실제 planner/runtime/receiver는226과 바이트가 같다.
- BEGIN0.93초 + planner7.36초 + finish8.97초 = build17.26초이며12개 묶음 각각도 일치한다. finish는 END·source 완료·bulk 처리·drain을 포함하므로 순수 FPGA 계산시간이 아니다.
- 현재2.625MHz SPI에서 **D1으로 수신한 인코딩 데이터만 평균17.88ms/완료**, 계측된 전체 SPI는51.69ms/완료다. 60fps의 전체16.67ms 예산을 수신 데이터만으로 초과한다. 별도 오디오/service와 병렬 aperture DMA는 이 바이트 계산에 들어 있지 않다.
- 중간20~50초 묶음은 D1만19.3~19.8ms/완료, E0/E1도31.7~35.8ms/완료다. 작은 OAM 표현 변경만으로는 스크롤60fps를 해결할 수 없다. 이 수치는 현재 전송 경로의 비용이며 하드웨어에서 NES60fps가 원천적으로 불가능하다는 증명은 아니다.

## 종료 코드와 안정성

ROM393216바이트 로드·비교·검증, RUN·STOP·기본코어 복원·메뉴 준비가 통과했다. 실제 메뉴도 사용자와 영상에서 확인했다. 화면 오류처럼 보이는169는 SPC 초기화 성공값A9이며 screen_telemetry_trusted=0이므로 screen_frames=0을 표시 실패로 해석하지 않는다.

`native_result=1`은 최초60초 deadline이다. `native_receiver_error=24`는 다음 geometry658의 D2에서 transfer callback 실패 또는 status 검사 실패를 합친 코드다. 코드상 deadline은 먼저 보존되며 이후 callback 실패가 receiver24로 남을 수 있다. 마지막 표시657은59.99초에 완료됐고 BEGIN466/COMMIT465/display465, window sent=retired=13158, sink/window/video/plan 오류0, 실제 SPI 실패0이다. 따라서 **기존 표시 패킷 미처리나 별도CRC 손상이 입증된 상황은 아니다.** D2 원시 응답은 없어서 전송 전 거절과 전송 후 deadline 중 어디였는지는 구분할 수 없다. 이 종료 흔적을 중간 게임 실패로 집계하지 않는다.

## 작업 의미와 다음 우선순위

227은 디버그 기반 추가가 아니라 실제 표시 전송량을 줄인 변경이며, 이번 실기로 정상 구동과 제한적인 효과를 확인했다. 다음에는 OAM 압축 변형을 더 늘리지 않는다. 남은 큰 비용인 **기하 데이터 수신과 맵·메타데이터 출력의 반복 전송, finish/drain**을 함께 줄이는 방향을 우선한다.

현재 스크롤 자료로 전체16.67ms 예산을 먼저 세우고, 내용 불변성이 보장된 데이터 재사용·차분 전달 또는 기존 병렬 aperture 재사용을 비교한다. 같은 SPI 왕복을 다른 위치로 옮기는 것만으로 해결했다고 하지 않는다. CPU 계산·전송·표시 완료를 포함한 순효과가 있는 경로를 고른 뒤 최소 경계 검증과 첫 레벨 실기로 간다. 클럭 인상·확인응답 제거·프레임 생략을 암묵적인 해결책으로 사용하지 않는다.

CHR epoch, row/alt/mask, inactive bank의 누적 변경 범위, 실제 최종 ACK와 공통 STOP을 유지한다. MMC4/MMC5의 fetch 시점·가변메모리 의미를 깨는 SMB3 전용 추정을 피한다. ARM 여유1800바이트·저장SRAM·GBC164·봉인된 기존 증거를 보존한다. 같은227/044 재시험은 필요하지 않다.
