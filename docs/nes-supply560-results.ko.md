# 560 · MMC558의 952 OBJ 공급 순서

PR148 병합 커밋 `c12cd861d926524e74c121b0fe03c3e5e5a5a527`을 포함하는 master에서 분기했다. 비교 기준은 실기 MMC558과 같은 표시 경로를 실행한 557의 두 뱅크 연속 일정이다. 실기에서는 5–55초에 13.72fps를 기록했다. 아래 952는 고정 입력을 재생하는 검증용 세대 번호다. [실기 측정](nes-hardware559-results.ko.md) · [일정의 검증 범위](nes-end557-results.ko.md)

## 952에서 시간이 쓰이는 곳

각 시각은 951의 실제 65816 표시 레지스터 변경부터 경과한 ms다. 기준은 905에서 시작해 957까지 중단 없이 진행한 두 일정이다.

| 사건 | 위상 1 | 위상 2 |
|---|---:|---:|
| 다음 입력 시작 | 0.636 | 0.700 |
| ARM planner 진입 | 23.910 | 23.759 |
| 첫 BG ROM 응답 완료 | 33.276 | 33.260 |
| 마지막 OBJ 계획과 END 수락 | 42.432 | 42.498 |
| 슬롯 39의 첫 ROM 허가 | 82.985 | 82.968 |
| 마지막 OBJ ROM 응답 | 83.408 | 83.392 |
| 마지막 OBJ 소비 ACK | 86.034 | 86.006 |
| SEAL을 65816이 읽음 | 87.464 | 87.368 |
| 화면 표시 | 99.761 | 99.727 |
| 최종 ACK | 99.896 | 99.863 |

OBJ 27·29·31·34가 각각 떨어진 목적지를 쓴 뒤 39–50이 이어진다. 슬롯 39가 들어 있는 E9는 42.5ms 이전에 수락됐다. 그런데 위상 1에서 슬롯 31의 첫 ROM 요청은 51.325ms, 허가는 66.345ms였다. 슬롯 39의 요청도 67.351ms로 밀려 다음 허가 구간인 82.985ms까지 기다렸다. 두 staging 뱅크의 이전 chunk가 소비되고 다음 슬롯으로 넘어가는 순서가 ROM 허가 구간과 맞물린다.

두 위상 모두 SEAL 수락 **전** 5 VBlank, 수락부터 실제 표시까지 1 VBlank였다. 그 안에 남은 DMA가 있으며, final212 검사 이후 추가 VBlank 대기는 0회였다.

다음 ROM 구간으로 넘어가는 기준도 역산했다. 슬롯 39–50의 112회 읽기에 관측한 요청 간격을 그대로 적용하면, 한 구간 앞에서 모두 끝내기 위한 최초 요청 마감은 66.756 / 66.740ms다. ARM의 계획 수락은 이미 마감을 지켰다. 실제 ROM 요청을 **0.595 / 0.454ms** 앞당겨야 한다. 이는 해당 ROM 읽기의 마감이며 전체 표시 단축 여부는 별도로 측정해야 한다.

## 후보와 검증 방법

ARM에서 정렬된 compact OBJ 15개의 끝에 붙은 연속 구간을 확인한 뒤 한 레코드만 더 본다. 다음 슬롯까지 이어지면 긴 구간을 먼저 보내고 분리된 앞쪽 슬롯을 후속 E9로 보낸다. 두 구간에 같은 슬롯이 있으면 원래의 안정 정렬을 지킨다. 추가 레코드와 SPI 응답을 보관하는 곳은 기존 248B 버퍼다.

검증은 실제로 링크된 Cortex-M4 명령, 공유 SPI 비용, IRQ, 측정한 부팅 ROM 허가 달력, 두 plan 뱅크와 Mesen 65816을 사용한다. Cortex-M4는 CPI 2 가정이고 타일 생산에는 모델 비용이 들어간다. 같은 시작 시각의 53화면, 타일·map 바이트, DMA·ROM 읽기량, 표시 시각과 최종 ACK를 각각 대조한다. 957의 선행 map과 952·954·957의 최종 대기도 별도로 확인한다.

## 전체 결과와 결정

| 지표 | 위상 1 기준 → 후보 | 위상 2 기준 → 후보 |
|---|---:|---:|
| 슬롯 39 첫 허가 (ms) | 82.985 → 49.706 | 82.968 → 49.690 |
| 952 SEAL 수락 (ms) | 87.464 → 87.129 | 87.368 → 87.104 |
| 952 표시 간격 (ms) | 99.761 → 99.750 | 99.727 → 99.750 |
| 951–955 표시 합계 (VBlank) | 26 → 26 | 26 → 26 |
| 951–955 평균 표시 간격 (ms) | 86.5553 → 86.5586 | 86.5847 → 86.5847 |
| 957 마지막 ACK의 절대 시각 변화 | 0.0112ms 늦음 | 0.0179ms 빠름 |

OBJ의 세 ROM 허가 구간에 각각 30·18·112회였던 읽기가 126·18·16회로 바뀌었다. 마지막 개별 슬롯 34가 마지막 구간을 차지하면서 SEAL 앞에서 기다리는 VBlank 수는 두 위상 모두 5회 그대로였다. 953·954는 각각 5 VBlank를 유지했다. 957의 map 세 건 모두 마지막 tile ACK 전에 발행됐고 952·954·957에서 최종 검사 후 VBlank 대기는 0회였다.

각 일정에서 53개의 RGB와 타일·map 내용이 기준과 일치했다. ROM 읽기 5,616회, VRAM DMA 114,352B도 동일했다. 독립 65816 재생에서 각각 9,481·9,476개 이벤트가 일치했다. 두 위상의 전체 SPI 변화는 −20 / 0B, ARM 명령 수 변화는 −3,553 / −19이며 IRQ 횟수는 같았다. Flash는 212,908→213,012B로 증가해 탑재 한도 212,992B를 20B 초과했다. ELF의 data 10,040B와 BSS 18,592B는 동일했다. ARM의 전송 전후 STOP, 같은 슬롯 순서, 메뉴 복구 분기는 모델에서 확인했다.

FPGA와 65816은 MMC558 산출물을 그대로 사용했다. 기존 Quartus Lite FIT는 15,164 LE, 조합 14,172개, FF 8,394개, M9K 51개다. 기존 STA에서 대상 경로 setup/hold는 +0.078/+0.139ns, 전체 최악 setup/recovery는 −7.081/−8.480ns다. 이번 ARM 실험으로 새 합성을 실행할 변경은 없다. [전체 수치와 해시](../analysis/supply560-verification.json)

**MMC558을 유지한다.** 다음 검증은 희소 OBJ 앞에서 이미 완성된 chunk를 언제 공개할 수 있는지에 집중한다. 기준에서 마지막 48B BG의 ROM 읽기는 33.276 / 33.260ms에 끝났지만 65816용 패킷 발행은 50.360 / 50.426ms, 패킷 ACK는 51.369 / 51.437ms였다. 먼저 실제 RTL에서 다음 descriptor의 목적지 불연속 확정, 기존 chunk 공개, 최종 바이트 read와 bank 반환을 같은 trace에 놓는다. 다음 타일의 전체 payload 도착 전 기존 chunk를 공개하는 경우에도 받은 토큰의 실제 소비와 STOP 취소를 확인해야 한다. 이후 두 시작 위상에서 112회 ROM 읽기의 마감, 952의 5 VBlank 표시, 밀집 합계와 957 ACK 동시 단축을 다시 판정한다. 순서 변경 후보의 Flash 축소나 실기 전달은 진행하지 않는다.

## 재현 순서

1. `prepare_nes_supply560.py`에 ARM558의 `src`를 지정하고 출력한 한 파일을 `build_nes_mmc479_arm.ps1`의 patch 입력으로 빌드한다. 기준 펌웨어 SHA-256은 준비 단계에서 검사한다.
2. 빌드한 ARM으로 `check_nes_supply560.py`를 실행한다. 이어서 `check_nes_menu533.py --trial 558`로 메뉴 진입·복구 분기를 검사한다. 실험 펌웨어는 MMC558 라벨을 사용한다.
3. 557의 두 뱅크 기준 추적 `nes-end557-banks-base1 / base2`에 사용한 동일 캡처·달력·client를 사용한다. `test_nes_banks557.py --long-run-first`로 시작 clock 3000000·3178684를 각각 재생한다. 캡처는 output489/audit01, fixture는 grant555/fixture, 65816은 admit556/client01, SPI 비용은 hardware503-mmc502, 달력은 service509-rom03이다.
4. 각 추적에 `replay_nes_admit556.py`를 실행한 뒤 `analyze_nes_supply560.py`로 두 위상을 대조한다. 분석기는 각 슬롯의 ROM 요청·허가, 대상 뱅크의 타일 바이트, 53개의 RGB와 표시 ACK를 검사한다.
