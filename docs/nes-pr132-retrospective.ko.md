# PR132 회고: 실기 진입과 60프레임을 위한 방향 전환

검토일: 2026-10-28. 구현 기준 `68a37b2fe0385ac1ceffd5910e0d6248e1dc6602`, PR132. 이 회고는 구현을 제품으로 승격하지 않는다. 병합 이후의 실행 계획은 [nes-pr132-next-plan.json](nes-pr132-next-plan.json)이며 과거 403의 즉시 구현 NEXT보다 우선한다.

## 판단

ARM 화면 계획, FPGA 압축 처리·독립 소비 검사, SNES DMA·표시의 역할 분담은 유효한 연구 후보이나 기존 보드의 지속 60프레임 달성은 입증되지 않았다. 하나의 동일한 구현에서 기한과 보드 자원을 함께 만족한 적도 없다. 기능이 완료되기 전 구조 예산과 단독 국소 실험을 되풀이하는 방식은 실기 진입의 불확실성을 충분히 줄이지 못했다. 404에서 요청된 공동 실행기·raster·lease 본체는 실제 구현하지 못했다. 단독 staging 실험을 해당 목표 달성으로 보지 않는다.

PR132는 60fps 완성이나 실기 준비 승인이 아니라 연구·통합 증거와 실패를 보존하는 체크포인트로 정리한다. 사용자 병합을 기다린 뒤 origin/master의 병합 반영을 확인하고 새 `codex/` 브랜치와 새 PR에서 계획을 수행한다. 이 회고에서 새 RTL이나 비트스트림을 배포하지 않는다.

## 증거와 현재 거리

* 실제 M4 실행, 공유 SPI·IRQ, 입력 중 ROM 경쟁 및 실제 65816 header DMA와 view/HDMA 관측 서비스 envelope를 같은 일정에 연결했다. 402는 12회 표시와 정확한 ACK, 908..917의 캡처 시작 수락 10/10을 확인했다. 917 표시 완료, 연속 71프레임, 완전한 resident 65816 실행이나 전체 위상의 WCET는 아니다.
* 402 funded_RAM은 400/401의 같은 전체 Lite MAP 대비 **−1,915 LE/−868 조합 논리/−986 FF/−34,313 RAM bits**다. 일부 RAM 절감은 미사용 program padding 삭제이며 범용 실행기 삭제가 아니다. 현재 **20,199 LE/16,508 comb/7,917 FF/347,991 bits**는 장치 15,408 LE보다 4,791 LE, reserve 포함 15,253 comb 목표보다 1,255 comb 초과다. LE와 comb 초과를 서로 더하지 않는다. MAP은 FIT·STA가 아니다.
* 402의 914·915 실제 표시 gate는 398.778896ms/431.116201ms, 각각 이전 실제 표시에 이은 목표에 1.401853ms/0.460335ms 늦다. 914를 회복하면 915의 목표도 VB25에서 VB24로 이동한다. 915의 현재 gate와 VB24의 17.099747ms 차이에는 앞선 누락으로 생긴 VBlank 대기가 포함되며 새 CPU 작업의 크기가 아니다. 관측 최대 warm 표시 간격은 34.048237ms다.
* 고정된 기존 생산 일정에서 마지막 E1 완료만으로도 914/915의 당시 다음 gate에 1.128634ms/0.231550ms 늦다. 최종 검사만 빨리 해서는 부족하다. 실제 저장 credit·IRQ·ARM 발행 및 ROM 경쟁을 함께 바꿔야 한다. 일정 변경 시 이 하한을 그대로 새 구조의 불가능성으로 해석하지 않는다.
* 404는 402 staging의 복사·bind stamp scratch만 공유했다. 단위 테스트는 ring/ordinary/동시 commit·consume/STOP 및 metadata pause를 통과했다. 기존 402와 같은 ARM 및 시작 위상의 12-frame 전체 이벤트와 ARM 결과는 정확히 같았다. 전체 Lite MAP은 **20,221 LE/16,580 comb/7,898 FF/347,991 bits**, 402 대비 **+22 LE/+72 comb/−19 FF/0 RAM**이다. 시간 이득은 0이며 단독 후보를 기각한다. 이 후보는 기존 VM·IO·raster·lease를 유지하며 새 공동 실행기·포트 경쟁·독립 검사에 대한 추가 검증을 입증하지 않는다. 보존된 로컬 원본은 `probes/nes-stage404/test04`, `build01`, `map02`, `live01`, `comparison404.json`이다. 원본은 workspace 상위에 있으며 Git에 포함되지 않는다.
* 402의 fixed_host는 실제 header 조기 공개 오류와 control 비용 증가가 관측되어 기각됐다. 안전한 ACK·STOP·독립 expected/actual read CRC·coverage는 삭제하거나 새 결과를 기존 테스트로 대체하지 않는다.

근거는 [402 계약](nes-joint402-contract.ko.md), [403 계약](nes-scope403-contract.ko.md), [402 검증](../analysis/joint402-verification.json), [404 재현 도구](../tools/probe_nes_stage404.py), [404 비교 도구](../tools/verify_nes_stage404.py)다. 404의 전체 실험은 이 PR에서 추가된 기능이 아니다.

## 무엇을 바꿀 것인가

1. **제한된 실기 진입과 지속 60fps를 별도 관문으로 운영한다.** 먼저 실기 최소 NROM 장면·보드·FPGA/ARM/65816 산출물·입력/오디오/STOP·복구 경로·계측 방법을 확인한다. 기존 production227은 보존하고, 실제 보드 적합성과 산출물·검증 이력을 조사한 뒤에만 출발점으로 선택한다. FIT/STA·CDC/IO와 안전한 패키지 이전에 보드 구동을 가정하지 않는다. 첫 제한 실기는 완전한 MMC4/5나 모든 71프레임·60fps 성공을 기다릴 필요는 없지만, 그 결과를 그 목표의 성공으로 부르지 않는다.
2. **역할 배치 후보를 같은 경계에서 판정한다.** 402 구조의 실질적인 공동 교체와 ARM/SNES 쪽으로 처리를 옮긴 더 단순한 대안을 비교한다. 삭제할 기존 본체, 유지할 검사, 포트·CDC·RAM·program, 추가 wire bytes, 실제 ARM/SNES 비용을 명시한다. 구조적 교체를 실제 구현하기 전에 목표 숫자를 성과로 쓰지 않는다. 양 후보에 대해 공정한 기준·범위·측정 계획과 차선책을 먼저 확정하고, 가장 불확실성이 큰 가정을 최소한의 연결 실험으로 검증한다.
3. **중단 기준을 앞당긴다.** 국소 실험은 실제 본체 삭제나 중요한 소유권·시간 불확실성을 해소할 때만 수행한다. 타당성 후보는 독립 검사·STOP·최종 ACK·VBlank와 캡처 보존을 먼저 확인한 후 동일 소스의 전체 Lite MAP 및 같은 ROM 위상 일정으로 비교한다. 면적만 좋거나 일정만 좋은 후보는 기록하고 실기 후보로 승격하지 않는다. 구조 후보들이 모두 목표를 크게 놓치면 ABI/역할·기능 범위·기존 보드 용량을 재검토하고 같은 구조의 소규모 FSM/opcode/seed/FIT 조정을 반복하지 않는다. 성능/회로는 사용자에게 실제 수치와 함께 보고한다.
4. **MMC4/5 위험을 일찍 표본화한다.** 실제 mapper 구현 상태와 대표 ROM 요청·화면 변화를 조사하고 입력·출력 경쟁, hint/IRQ·FIFO 요구를 계측한다. 예제 몇 개는 범용 mapper 호환이나 60fps의 증명이 아니다. NROM 결과를 MMC4/5에 자동으로 일반화하지 않는다.

최종 60fps는 지역별 실제 표시 주기에서 프레임 ID·capture 누락·반복·최악 지연을 실기에서 확인해야 한다. 시작 cold/STOP 복귀는 gameplay warm과 분리해 보고, 실측 전 실기 날짜나 물리 60fps를 약속하지 않는다. Quartus Lite를 기본으로 사용하며 Standard 구매와 머지는 자동으로 진행하지 않는다.
