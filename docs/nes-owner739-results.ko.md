# 739 · 957의 마지막 OBJ와 map DMA 경합

727을 유지한다. 두 위상에서 마지막 OBJ 288B는 1,536B map DMA보다 9.234 / 9.108ms 먼저 준비됐다. 앞선 BG가 staging 선두를 점유한 시간은 1.263 / 1.217ms였다. 선두가 열린 뒤 ARM이 다음 OBJ를 조회하기까지 7.996 / 7.789ms가 더 걸렸다. 두 ARM 후보 모두 OBJ 수락·OAM 검사를 246선 안으로 옮겼지만 957의 1,536B map DMA가 SEAL 뒤로 밀렸다. [측정값과 검증 식별자](../analysis/owner739-verification.json)

## 727에서 어디서 기다렸나

아래 시각은 각 위상에서 956 화면이 공개된 순간부터의 ms다. 65816의 OBJ 수락은 큐 선두를 읽은 때, OAM 검사 완료는 두 뱅크의 독립 비교를 통과한 `proven635` 실행 시점으로 구분했다. 마감은 956 표시 후 두 번째 VBlank의 246선 끝이다. 다음 프레임 초반의 작은 주사선 번호를 마감 전으로 세지 않았다.

| 957 사건 | 위상 1 | 위상 2 |
| --- | ---: | ---: |
| 마지막 OBJ 288B staging 준비 | 23.875 | 23.942 |
| 65816이 앞선 BG의 staging 사용권 반환 | 25.138 | 25.159 |
| ARM이 다음 OBJ descriptor 조회 시작 | 33.135 | 32.948 |
| 1,536B map DMA 시작 → 마지막 PPU 쓰기 | 33.109 → 33.701 | 33.050 → 33.642 |
| OBJ 큐 진입 → 65816 수락 | 33.561 → 33.796 | 33.377 → 33.737 |
| OBJ 소비 ACK → OAM 독립 검사 통과 | 34.606 → 34.823 | 34.546 → 34.761 |
| OAM 검사가 246선을 넘긴 시간 | 1.096 | 1.029 |

957의 마지막 9개 OBJ는 캡처 캐시에서 공급됐다. 생산 모델의 마지막 plan bank 처리 후 END에서 열린 288B 묶음이 확정된다. 그 뒤 앞선 BG의 실제 토큰 119가 반환돼야 OBJ 토큰 120을 선두에서 조회할 수 있다. 이 반환 이후 첫 E8 조회까지 ARM은 map E1 8개를 실었다. 위상별로 E1에 4.952 / 4.998ms, E0 상태 조회에 1.309 / 1.200ms, D0에 0.371 / 0.297ms, SPI 거래 밖에 1.364 / 1.294ms를 썼다. 이 사이 map 진행 함수가 일곱 번 반환됐다.

BG 반환부터 OBJ 조회 응답까지 실제 큐에는 최대 한 패킷이 있었다. OBJ E1 발행 때 물리 큐와 ARM 발행 카운터 모두 미반환 0개였다. 큐 슬롯을 늘려도 이 시점의 지연을 설명할 수 없다. ARM이 연속 map 발행에 SPI를 사용하고 producer 조회를 미룬 순서가 가장 큰 대기였다. 조회가 끝난 뒤 OBJ가 큐에 들어갔을 때는 이미 65816이 map DMA 중이었다.

## 순서를 바꾼 실제 ARM 비교

A는 한 페이지에서 연속 24개 이상의 map 행과 양쪽 뱅크의 재사용 이력이 확인되면, 기존 producer 완료와 OAM 검사를 먼저 진행했다. B는 더 좁게 연속 OBJ 한 묶음에서만 OAM을 먼저 발행하고, 기존 staging 사용권이 반환된 뒤 producer를 한 번 조회했다. 두 후보 모두 map 패킷 형식, 65816, 707D 보드와 독립 검사 코드는 동일하다.

표의 두 값은 위상 1 / 위상 2 순서다. 앞당겨진 마감 여유는 양수, 마지막 ACK가 늦어진 시간은 +로 표시했다. 밀집 간격은 951 공개부터 957 공개까지의 여섯 간격 평균이다.

| 결과 | 727 | A | B |
| --- | ---: | ---: | ---: |
| 246선까지 OBJ 수락 여유, ms | −0.070 / −0.006 | 7.962 / 7.975 | 7.816 / 7.678 |
| 246선까지 OAM 검사 여유, ms | −1.096 / −1.029 | 5.758 / 5.769 | 8.368 / 8.227 |
| 246선까지 마지막 map ACK 여유, ms | 2.195 / 2.100 | −0.884 / −0.873 | −0.485 / −0.775 |
| SEAL 전 1,536B DMA 완료 세대 | 952·957 모두 | 없음 | 952만 |
| 952–957 밀집 간격, ms | 49.932 / 49.932 | 52.831 / 50.052 | 50.056 / 50.055 |
| 957 마지막 ACK 차이, ms | 기준 | +34.007 / +17.362 | +0.738 / +0.737 |

B에서 957의 마지막 map ACK는 956 공개 후 34.212 / 34.501ms였다. 이때 일반 패킷의 선행 DMA에는 1,536B보다 앞에 있는 384B만 들어갔고, 1,536B는 최종 업로드에서 처리했다. 위상별 마지막 SEAL 수락은 727보다 0.489 / 0.576ms 빨랐지만 SEAL부터 최종 ACK까지는 1.228 / 1.309ms 늘었다. 957의 최종 대기 횟수는 세 방식 모두 0이었다. 최종 대기 횟수와 마지막 ACK 시각을 따로 봐야 하는 경우다.

## 안전성과 적용 범위

- 각 후보·위상에서 905–957 전체 53개 plan·map·tile·section 5와 53장의 RGB를 대조했다. 동일하게 기록한 큐 유입 시각으로 실제 65816을 별도 재생해 원래 CPU 이벤트와 시각까지 일치함을 확인했다.
- 957 OAM 패킷의 직전 표시 serial을 손상시키면 727·A·B 모두 독립 검사에서 0xE0으로 거부했다. OAM 수락 때부터 STOP을 유지하면 다음 서비스에서 두 뱅크의 이력을 비우고 정지했다. 세 경우 모두 STOP과 손상 주입 각각에서 956 화면, 커밋 52개가 유지됐고 957 최종 ACK가 없었다. OAM 구간에만 건 짧은 펄스는 이미 비교가 끝난 경로에서 샘플되지 않아 실제 STOP 검사에는 유지형 신호를 사용했다.
- 정상판·장시간판 전체 링크 4개에서 발행·오류 주입 50건, 링크별 기존 admission 35조건·마감 17조건과 메뉴·base 복귀 분기를 검사했다. Flash는 정상판/장시간판 기준 A 212,932 / 212,888B, B 213,040 / 212,996B였다. B는 한도 212,992B를 48 / 4B 초과한다. 정적 RAM 섹션은 네 빌드에서 같았다.
- 시간은 링크한 ARM·65816을 실행하고 SPI·credit·ROM 일정을 결합한 재생값이다. staging의 생산 시각은 기존 보드 모델에서 구하고 반환과 수락은 실제 65816 명령에서 관측했다. 새 FPGA 합성이나 실기 FPS 측정은 이번 비교에 포함하지 않았다.

## 다음 작업

727의 마지막 map ACK와 DMA 시작 사이에는 1.578 / 1.419ms가 있다. map 8패킷의 발행 시각을 고정하고, 그 구간에 OBJ descriptor 조회와 큐 수락을 넣었을 때 65816이 빈 큐에서 1,536B DMA를 시작할 수 있는지 먼저 재생한다. 이 구간에서 두 작업이 양립하는지, 앞선 BG 반환 이후 상태 조회나 OAM 검사 중 일부를 더 일찍 끝내야 하는지 구분한다. 두 위상 모두 952·957 선행 DMA, 246선 마감, 밀집 간격·최종 ACK가 함께 개선되는 경우에만 ARM 변경을 채택한다.

## 재현

1. 727 정상판과 장시간판에 각각 `tools/prepare_nes_owner739.py <727 빌드> <패치 디렉터리>`를 적용한다. B에는 `--single`을 붙인다. 727과 같은 479 전체 빌드 절차로 링크한다.
2. [727 재현 절차](nes-pair727-results.ko.md)의 동일 707D·694 client·ROM 허가 일정과 905–957 입력에 `tools/test_nes_observer717.py`를 사용한다. 시작 master clock은 7,288,416과 7,467,100이다. 기준 기록은 `nes-pair727-a1/a2`, 후보 기록은 `nes-owner739-{a,b}{1,2}`에 둔다.
3. `tools/trace_nes_owner739.py --trace <각 기록> --out <출력> --mesen <Mesen 실행 파일> --client <694 client>`로 CPU·beam·사용권을 재생한다. 출력 폴더는 `nes-owner739-{ref,a,b}{1,2}-trace`다. 위상 1에서 `--mode stale`, `--mode stop`도 각각 실행한다. 기준 유지형 STOP 결과 이름은 `nes-owner739-ref1-stop-held`다.
4. 네 링크에 `tools/check_nes_owner739.py <ARM src> <issue 결과 JSON>`과 기존 admission·deadline·menu 검사를 실행한다. B의 발행 검사에 `--single`을 붙인다. `tools/analyze_nes_owner739.py --temp <재생 기록 상위 폴더> --probe <빌드·검사 폴더> --out <결과 JSON>`에서 토큰, 실제 큐 점유, beam 마감, 전체 픽셀·표시·ACK를 함께 대조한다.
