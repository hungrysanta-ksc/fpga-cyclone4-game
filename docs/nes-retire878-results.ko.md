# 950 공개 뒤 EA 재무장과 951 COMMIT 반환

실기 기준은 MMC872다. 직전 시험에서 950의 1,088B 선행 DMA와 3회 표시를 양쪽에서 지킨 877 테이블 우선 링크와, 같은 공통 명령 생성기를 사용한 기존 발행 순서 대조군을 출발점으로 삼았다.

## 무엇을 줄였나

950의 유효 E0는 65816이 SEAL을 소비하고 화면을 공개한 뒤 ARM이 전체 CRC·큐 반환 수·SEAL identity·완료 상태를 검사한 응답이다. 기존 순서는 E0 → E8(계획 종료 재확인) → EA(해제) → E8(재무장 확인) → D3(다음 세대 승인) → D0(준비 확인) → D1(COMMIT 읽기) → D2(반환)다. 마지막 D2 뒤의 D0로 토큰 반환도 확인한다.

- **FINISH 재사용**은 마지막 타일 receipt까지 끝난 FINISH의 E8에서 정확한 종료 상태, 빈 descriptor, 받은 plan 수, 상태 CRC를 확인한다. ARM이 이전 화면의 유효 E0까지 확인하면 EA를 발행한다. MMC872 FPGA는 EA 수락 시 현재 세대와 plan 수, producer idle, chunk 유무, STOP·fault, 명령 CRC를 다시 검사한다. EA 뒤에는 E8에서 재무장 상태·빈 descriptor·카운터 0을 확인해야 D3로 넘어간다.
- **END 뒤 즉시 조회**는 같은 코드에 한 가지 조건을 더했다. SEAL 대기 중 다음 입력의 END 검증과 D2 반환이 끝났으면 기존 128µs 조용한 대기 없이 E0를 다시 조회한다. 조회마다 STOP 검사는 실행한다.
- **END 완료 때만 재사용**은 877 대조군의 테이블 순서를 유지한다. 유효 E0가 반환된 시점에 다음 입력이 이미 COMPLETE면 FINISH의 확인 결과를 재사용하고, 입력이 남았으면 기존 사전 E8을 실행한다.

후보 모두 FPGA와 65816은 MMC872와 동일하다. D3 직후 준비를 확인하는 D0도 유지했다. MMC872의 입력 SPI는 준비되지 않은 D1이나 길이가 다른 D1에서 fault를 기록하기 때문이다.

## 유효 E0를 같은 시각에 두면 얼마나 남는가

950의 공개·선행 DMA가 회복된 참조 실행에서 유효 E0 시각을 고정했다. 중복 E8과 ARM 명령 사이의 모든 공백을 없앤다고 가정하고, 필수 EA·E8·D3·D0·D1·D2 여섯 거래의 측정 구간만 더했다. 이 구간에는 실기 계측으로 보정한 SPI 드라이버 비용이 들어간다. 두 위상 모두 여섯 거래는 합계 66B다.

|---|---:|---:|---:|---:|
| 874 | 1 | 10,309 | 10,710 | −401 |
| 874 | 2 | 8,714 | 10,712 | −1,998 |
| 877 테이블 우선 | 1 | 9,336 | 10,710 | −1,374 |

877 테이블 우선의 위상 1은 유효 E0 수신 자체를 **최소 64µs** 앞당기거나 여섯 거래의 실제 비용을 그만큼 줄여야 한다. 이 수치는 후속 ARM 코드 비용을 0으로 둔 하한이다. 위상 2에서는 나머지 코드에 128µs가 주어진다. 순수 전선 속도나 물리 보드에서 잰 신규 FPS로 해석할 수 있는 수치는 아니다.

## 950 공개 시각을 고정한 결과

877 테이블 우선 ARM을 그대로 부팅했다. 950 유효 E0까지 모든 SPI 거래의 시작·종료·응답이 참조와 일치했고, 공개 클록과 1,088B DMA 클록도 일치했다. 이 한 화면에서만 EA 직전 조회에 이미 확인한 FINISH 응답을 돌려주었다. 950은 두 위상 모두 3 VBlank에 표시됐다.

| 항목 | 위상 1 | 위상 2 |
|---|---:|---:|
| 950 공개 클록 | 51,081,914 | 51,439,778 |
| 유효 E0 → 마지막 D2 · 기존 → 재사용 (클록) | 15,780 → 13,211 | 15,781 → 13,212 |
| 마지막 D2와 직전 캡처선의 차이 | 3,875클록 늦음 | 256클록 빠름 |

한 번의 E8 절감은 두 위상에서 똑같이 2,569클록이었다. 위상 2에서는 952 캡처 준비 시각이 357,368클록 앞당겨졌고 실제 공개도 149→148로 이동했다. 위상 1에서는 캡처 준비가 같은 시각이었다. 위상 1의 후속 비용 13,211클록을 유지한다면 캡처선 51,103,624에 맞는 유효 E0의 최종 시각은 51,090,413클록이다. 관측값은 51,094,288이다. 같은 거래 비용으로는 3,875클록(0.180ms)을 더 앞당겨야 하며, 캡처선보다 엄밀히 먼저 끝내려면 3,876클록이 필요하다.

## 전체 ARM 링크에서의 효과

두 숫자는 위상 1 / 2 순이다. 오프닝 759 마감은 176 / 176, 전환 기준은 119 / 119 VBlank다. 마지막 ACK는 MMC872의 마지막 65816 ACK에 대한 차이다.

| 후보 | Flash B | 950 표시 | 952 공개 | 759 공개 | 전환 48간격 | 밀집 60간격 | 마지막 ACK 차이 (클록) |
|---|---:|---|---|---|---|---|---|
| FINISH 재사용 | 212,892 | 4 / 4 | 148 / 149 | 172 / 174 | 120 / 120 | 140 / 141 | −357,712 / +104 |
| END 뒤 즉시 조회 | 212,912 | 4 / 4 | 148 / 149 | 173 / 176 | 120 / 120 | 140 / 140 | −357,346 / −362,366 |
| END 완료 때만 재사용 | 212,940 | 4 / 4 | 148 / 149 | 175 / 177 | 119 / 119 | 141 / 140 | −224 / −363,248 |

세 정적 후보 모두 950의 1,088B 단일 선행 DMA를 잃었다. FINISH 재사용 링크에서는 950의 마지막 map이 참조의 247 / 246선보다 약 9.6ms 일찍, 화면 표시 중인 96 / 96선에 반환됐다. 후속 scroll은 반환 후 3,883 / 6,642클록 만에 발행됐다. 비활성 뱅크의 map을 선행 DMA하던 빈 큐 구간이 사라졌다. 위상 1에서 업로드 첫 VBlank에 1,472B map DMA 두 건과 후속 tile을 실행한 뒤 2B·112B가 다음 VBlank로 넘어갔다.

END 뒤 즉시 조회는 두 위상의 밀집 합과 마지막 ACK를 함께 줄였지만, 950은 한 VBlank 늦어졌고 전환도 한 번 늘었다. MMC872 대비 앞선 화면들의 간격 변화가 서로 상쇄된 뒤 마지막까지 남은 한 번의 개선은 위상 1의 963, 위상 2의 966에서 확인된다. 952 공개 시각은 변하지 않았다.

모두 ARM Flash 212,992B 한도 안이다. 각 정적 링크의 348개 세대(오프닝 62·전환 50·밀집 62, 두 위상)에서 실제 SEAL ACK 내용·큐 카운터·CRC → EA → 유효 재무장 E8을 대조했고 다음 입력이 있는 경우 D3가 그 뒤에 시작함을 확인했다. 보드 RTL 9조건, 링크별 ARM 경계 19 / 19 / 21조건, 65816의 cold·손상·부분 쓰기·STOP·재시작 12조건과 ARM 메뉴 복귀 검사를 통과했다. 이는 결합 재생 및 지향 시험 결과다.

**실기 기준은 MMC872를 유지한다.** 다음 실험은 950의 1,088B DMA와 정상 공개를 두 위상에서 고정한 채, 위상 1의 END 직전 120B 입력 처리와 첫 유효 E0가 겹치는 지점을 좁힌다. 위상 2에는 256클록만 남으므로 두 위상의 절대 캡처·공개 시각을 함께 판정한다.

## 검증과 재현

1. `prepare_nes_retire878.py BASE/src WORK/patch MODE`와 `build_nes_mmc479_arm.ps1`로 최종 ARM을 링크한다. 모드는 `finish`, `ready`, `overlap`이다. 앞 두 모드는 877 테이블 우선 링크, 세 번째는 877 공통 명령 대조군을 사용한다. 각 후보의 `client02`에 원래의 65816을 사용한다.
2. `replay_nes_table877.py TEMP PHASE WORK 878-MODE CLIP`으로 dot 0 보정 입력에서 `opening`, `transition`, `dense`를 두 위상으로 재생한다. ARM·공유 SPI·타일 ROM·65816의 동일 시계를 사용한다. 공개와 65816 ACK, ARM 유효 E0를 각각 기록한다.
3. MMC872 보드 소스로 `run_nes_retire878.ps1`을 기존 Questa FLOAT 래퍼에서 실행한다. 유효 FINISH 뒤 발생한 source fault, busy, 새 chunk, 잘못된 세대·개수·CRC, STOP, 중복 EA 및 정상 재무장을 시험한다. `check_nes_retire878.py guard WORK WORK/retire-guards.json`에서 링크된 ARM의 E0·EA·재무장 오류를 따로 주입한다.
4. 기존 `guard_nes_capture871`, `guard_nes_scroll874`, `guard_nes_progress870`, `check_nes_menu533 --trial 872`와 각 후보의 실제 패킷을 사용한 `check_nes_strip869 guards`로 STOP·cold 재시작·메뉴 복구를 확인한다. `check_nes_retire878.py report TEMP analysis/retire878-results.json`이 MMC872와 화면별 유효 픽셀·map·작업량 및 이전 EA와 새 COMMIT 순서를 대조한다. [클록별 측정과 합격 조건](../analysis/retire878-results.json)
5. 전체 집계 전에 `replay_nes_retire878_once.py TEMP PHASE ../probes/nes-table877-stable`를 두 위상에서 실행한다. 이 대조 시험은 기존 ARM을 부팅해 세대 950의 EA 직전 E8 한 건에 한해 같은 세대 FINISH에서 검증했던 응답을 재사용한다. 기존 소프트웨어의 세대·개수 판정과 실제 EA·재무장·D3·D2 경로가 그대로 실행된다. 정적 후보의 성능에는 이 진단용 시각을 합산하지 않는다.
