# 531. MMC529에서 출력 함수와 마지막 VBlank 대기 분리

## 실기와 계측 범위

PR144 병합 `bbacb9fa4ddc43cf1ecb97609c49afdcb96f3b55`를 원격 master에서 확인했다. 실기에서 성공한 MMC529의 ARM·FPGA·65816을 기준으로 삼았다. 실기 708회 표시의 84MHz DWT 출력 누적값은 2,860,328,261클록으로 평균 **48.0954ms**다. 이 측정은 ARM의 `nes_sink212_seal` 호출 전후에 있다. 남은 map과 일반 패킷을 만들고 보내는 시간, bulk 서비스·큐 소진, 65816의 독립 검사·DMA·표시, ARM이 최종 ACK를 확인하는 시간이 들어간다. 이후의 EA 재무장 전송은 다음 구간이다.

실기의 FINAL_ACK 무진행 polling 루프 누적 590,477,039클록을 완료 표시 수로 나누면 9.93ms다. 이 세션 카운터는 ARM이 기다린 측정치이고, 그동안 65816은 DMA·VBlank 대기·표시를 진행할 수 있다. 출력 시간에 별도로 더하거나 전부 절감 가능한 CPU 시간으로 세지 않았다. 실기 로그에는 65816의 명령별 시각이 없다. [실기 기록](nes-hardware530-results.ko.md)

두 시작 클록 3,000,000 / 3,178,684에서 링크된 ARM 호출의 진입·반환, 65816 업로드 목록의 각 명령, 실제 PPU DMA 시작·마지막 쓰기, VBlank 대기 진입·복귀를 같은 타임라인에 기록했다. 905–957의 53화면을 모두 실행했고 첫 두 화면 뒤 907–957의 51화면 및 밀집 951–955를 집계했다. 두 위상의 세대별 map 데이터·순서와 OBJ·BG tile 내용·개수가 일치한다. 각 위상의 패킷 도착, CPU 소비 이벤트, OBJ ROM 응답 시각, RGB는 저장된 MMC529 기준과 일치한다. SPI·IRQ·ROM 경쟁을 포함한 모델이며 아래 수치를 실기 플레이의 개별 프레임에 대입하지 않는다.

## 출력 호출 1회당 비용

아래 행은 서로 겹치지 않는다. ‘명령 제어’는 목록 순회, DMA 설정·서비스·정리 등에서 실제 DMA 구간과 VBlank 대기를 제외한 시간이다. DMA 자체는 MDMAEN 쓰기부터 마지막 PPU 데이터 쓰기까지다. 표시 전 선행 DMA는 발생한 시점에 귀속하며 SEAL 목록의 DMA에 다시 더하지 않았다.

51화면 중 새 최종 VBlank를 기다린 경우는 27/25화면이었다. 나머지는 기존 전송 예산으로 바로 표시(각 18회)하거나 빔 확인 후 같은 blank를 재사용(6/8회)했다. 밀집 951–955에서는 양 위상 모두 5화면 중 4화면이 추가 blank를 기다렸다. 밀집 평균의 최종 대기는 **11.955/11.968ms**, raw의 DMA·제어 합은 약 **0.53ms**, tile은 약 **0.51ms**였다.

필요 클록은 실제 빔 래치에서 247번 **시작 전**까지의 차이다. 528에서 기록한 ‘247번 시작 이후 경과 클록’보다 1 크다. 마지막 blank 이전 작업을 제거해도 중간의 VBlank 대기에 흡수될 수 있어, 명령 시간을 계산할 때는 직전 업로드 대기에서 복귀한 뒤의 구간만 셌다. 952·954 모두 raw 여섯 DMA의 실제 쓰기는 약 3,324–3,368클록이어서 이 쓰기만 없애도 두 위상 모두 검사선에는 못 미친다.

## 같은 작업량에서 64B의 효과를 검증한 대조 시험

945 직전 화면까지 원본으로 재생한 뒤 945 한 화면의 **선행 map 허용선만 254→232번 행**으로 좁혔다. 재생 중 WRAM의 비교 상수 한 바이트만 바꿨고 최종 246번 검사선·STOP·독립 map 검사·표시 루틴은 원본을 사용했다. 각 위상에서 패킷·payload·도착 시각을 원본대로 유지하고 944까지의 전체 이벤트, 945까지 모든 RGB와 소비 ACK의 순서·상태를 대조했다. 이 시험은 패킷 도착을 고정한 소비기 단독 대조다. 앞선 53화면 비교에는 원본 ARM 피드백이 포함된다.

| 위상 | 945의 선행 map | SEAL의 큰 map DMA | 최종 선택 | 표시 ACK 변화 |
|---|---|---|---|---:|
| 1 | 오프셋 2,240의 64B → 0B | 1,280 → 1,344B | 같은 blank → 다음 blank | +15.223ms |
| 2 | 0B → 0B | 1,344 → 1,344B | 두 경우 모두 다음 blank | −0.009ms |

첫 위상의 SEAL load 차이는 386클록(0.018ms)이고 최종 ACK 차이는 326,940클록이었다. raw 여섯 건과 tile 전송량은 그대로였다. 검사선 바로 앞에서는 수락된 map 한 행을 어느 blank에서 처리하느냐가 실제 표시 간격을 바꿨다.

## 먼저 시험할 변경

1. **목표는 마지막 blank에서 952는 6,107클록, 954는 7,899클록 이상을 회수하는 것이다.** 검사선과 STOP을 유지한다. 945의 대조처럼 성공 여부는 전송량 외에 같은 blank를 재사용했는지와 실제 최종 ACK로 판정한다.
2. **952에서는 먼저 수락된 작은 tile 명령의 선택·병합을 시험한다.** 아직 SEAL에 남았던 앞쪽 16·48·32·32·32B 명령은 양 위상 모두 데이터 수락 이후 이전 blank에서 큐가 빈 구간이 관측됐다. 마지막 blank에서 이 다섯 명령이 차지한 구간의 합은 약 8,158클록이다. 같은 빈 구간을 여러 명령이 공유할 수 있으므로 전부 이동 가능한 비용으로 확정하지 않는다. 열린 tail과 bank·token 소유권, ready head 우선, 기존 map DMA와의 교체 비용을 함께 검증한다.
3. **954는 tile 선택만 바꿔서는 예산이 부족하다.** 앞쪽 16·144·16B를 모두 옮긴다는 가정에서도 5,462/5,438클록이고, 뒤의 384B OBJ tile에는 현 일정에서 비어 있는 선행 시작 구간이 없었다. 1,536B map의 수락 뒤 시작 가능 구간도 704/0클록이었다. 954에서는 해당 map 범위나 뒤의 OBJ 공급을 이전 blank 전에 수락시키는 변경을 함께 시험한다. 952에 남은 768B map도 현재 일정에서는 첫 행 수락 뒤 선행 시작 구간이 두 위상 모두 0이었다.
4. raw 여섯 행은 **각 64B가 모두 수락된 시점부터 SEAL 발행 전까지**, 기존 idle DMA를 보존하고 새 패킷이 대기하지 않는 VBlank 구간이 952·954 양 위상 모두 0이었다. raw 전체는 SEAL load 2.64–3.35ms 전에 준비됐지만 그 시간대가 중요하다. raw를 선행하려면 데이터와 독립 검사에 필요한 문맥을 더 먼저 보내거나 이전에 표시를 확정한 뱅크 이력을 검증해서 재사용해야 한다. 이번 우선순위는 기존 map·tile 수락 경로를 활용하는 쪽이다.

선행 구간은 실제 ACK와 다음 패킷의 PUSH 사이를 빔 허용 구간과 교차시킨 뒤, 이미 실행한 idle grant부터 마지막 PPU 쓰기까지 제외해 구했다. map은 254번, tile은 232번까지의 **시작 가능 시간**이고, raw는 낙관적으로 VBlank 전체를 허용했다. 검사·설정 비용과 열린 명령 제약을 차감하기 전이며 명령별 구간을 합산해 여유를 부풀리지 않는다. 새 설치본이나 실기 fps 측정은 없다.
