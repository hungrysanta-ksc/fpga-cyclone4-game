# MMC903 데모 후반의 두 지연을 분리한 결과

실기 기준은 MMC897의 SRAM D0 송신과 MMC903의 계측 결과다. MMC903은 오프닝 18.21 FPS, 데모 17.17 FPS로 60초를 실행하고 메뉴로 복귀했다. 904에서는 원본 게임과 두 시작 위상의 재생으로 지연 구간을 좁혔다. 새 실기 FPS 측정은 없다. [MMC903 실기 분석](nes-hardware903-results.ko.md)

## 세대 1065에서 입력 완료까지 약 228ms

무입력 원본의 3,600장 이미지 중 3347–3368은 픽셀이 전부 검다. 독립 실행으로 3300–3500의 PPU 패턴 읽기를 세었다. 3348은 192선 dot 91에서 게임이 배경과 스프라이트를 끄고, 3349–3361은 13장 연속 읽기 0회다. 3362에서는 20,244회로 회복한다. 실제 MMC903 보드의 수집·송신 RTL에 dot 0부터 공급하면 3347은 통과하고 3348과 무읽기 대표 프레임 3350은 패킷을 발행하지 않고 소유권을 반환한다. 3362는 다시 통과한다. 해당 전환을 재생한 SNES 출력도 공백 직전과 복귀 시점 모두 검다.

| 직전 공개부터 경과 | 실기 1065 | 재생 3362 위상 1 | 위상 2 |
|---|---:|---:|---:|
| 첫 입력 블록 준비 | 미계측 | 216.328ms | 216.310ms |
| 첫 유효 D0 응답 종료 | 미계측 | 216.457ms | 216.421ms |
| 첫 D1 수신 종료 | 미계측 | 216.645ms | 216.609ms |
| 마지막 데이터 D2 확인 | 228.23–228.38ms 구간 | 225.973ms | 225.937ms |
| 마지막 OBJ 128B 준비 | 253.477ms | 250.444ms | 250.426ms |
| 화면 공개 | 266.301ms · 16 VBlank | 267.152ms · 16 VBlank | 282.526ms · 17 VBlank |

재생에서는 최초 유효 D0부터 16개 데이터 블록의 마지막 반환 확인까지 두 위상 모두 9.52ms다. 약 216ms가 먼저 경과한 시점에야 받을 입력이 생겼다. 실기와 재생은 변경 map 33과 마지막 OBJ 128B가 일치한다. 단, 실기 세대 차이는 14이고 재생 원본 3347→3362의 차이는 15다. 재생의 공급 공백은 관측한 원본 읽기로 설정했으며 실기 세대에 대응하는 원본 프레임 번호는 미계측이다. 이 구간을 개선 대상으로 삼으면 원래 검은 화면을 여러 번 공개하는 것만으로 FPS가 오를 수 있다.

## 세대 1086에서 입력 완료 후 마지막 OBJ까지 약 118ms

실기에서는 직전과 연속된 세대에서 변경 map 0, 마지막 OBJ 32B, 타일 token 증가 8, 공개 간격 8 VBlank가 관측됐다. 입력 완료 후 마지막 OBJ가 FPGA에 준비되기까지 118.02–118.17ms가 걸렸다. 원본 3408–3436에서 여덟 장을 골라 두 장을 준비 구간으로 두고 같은 ARM·65816 실행 파일로 여섯 표시 간격을 비교했다. 아래 시간은 입력 완료 확인부터 마지막 타일 준비까지이며 각 칸은 위상 1 / 위상 2다.

| 원본과 비교 조건 | 실측 캐시 적중을 재생 | PSRAM 허가 대기만 제거 | OBJ 캡처 적중을 모두 제거 |
|---|---:|---:|---:|
| 3424 · 변경 map 0, 새 OBJ 33개 | 23.25 / 23.32ms | 23.28 / 23.31ms | 88.91 / 88.84ms |
| 3428 · 기준 PSRAM 읽기 28회 | 22.87 / 15.70ms | 11.78 / 11.78ms | 16.23 / 16.35ms |
| 3436 · 변경 map 0, 타일 token 8개 | 17.92 / 17.88ms | 18.25 / 17.86ms | 49.32 / 49.42ms |
| 여섯 표시 간격 합 | 15 / 15 VBlank | 14 / 14 VBlank | 21 / 21 VBlank |

3424는 첫 plan 묶음 발행까지 약 9.5ms가 들고 기준 재생에서 PSRAM 읽기는 0회다. 같은 타일을 전부 캡처 실패로 처리하면 328회 읽기가 추가되고, 그중 허가를 기다린 시간은 75.41 / 75.37ms다. 마지막 OBJ는 3424에서 352B, 3436에서 128B라서 어느 쪽도 실기 1086과 정확히 일치하지 않는다. 3428의 캐시 적중 제거 조건에서 위상 1이 오히려 빨라지는 건 앞선 화면부터 연속 실행해 ROM 허가 구간과의 정렬도 바뀌기 때문이다. 여섯 간격 전체에서 평가해야 한다.

3424의 두 뱅크에서 token 14·15가 먼저 준비된다. 65816이 14를 반환한 뒤 16이 준비되기까지 0.002ms 이내였고, token 17–22의 반환 직후에도 각각 두 번호 뒤의 타일이 0.002ms 이내에 준비됐다. ROM 읽기 0회인 화면에서도 연속 타일의 공급 시각은 앞선 소비자의 뱅크 반환을 따라간다. 두 위상에서 마지막 token 25의 준비→반환은 3.32ms였다. 이 값은 실기 1086의 개별 token 반환 기록을 대신하지 않는다.

PSRAM 허가 대기를 제거한 대조군에서 마지막 ACK는 위상 1에서 17,491,318→15,707,316, 위상 2에서 17,852,534→16,064,780 SNES 마스터클록이었다. 절대 ACK 차이에는 앞의 준비 두 장이 포함된다. 이 대조군은 읽기 횟수와 응답 자체의 비용을 보존한다. ROM 허가 시각은 부팅 코어 재생에서 관측한 여덟 구간을 반복 사용한다. 실기 1086의 ROM 중재와 ARM 명령별 실행 시간은 미계측이다.

## 다음 작업

1. 55–60초의 긴 OBJ 세대에서 첫 E9 발행, 묶음별 ROM 요청·허가 대기 누계, 두 staging 뱅크의 점유·반환을 같은 세대와 token으로 연결한다. 우선 기존 SPI 응답과 RAM 기록을 사용하고 계측 전후 ARM 일정 편차를 대조한다.
2. 인접 두 화면의 변경 map 수, BG·OBJ 작업량, token 개수와 마지막 OBJ 크기까지 맞춘다. 실제로 처음 밀린 경계가 확인되면 그 경계만 변경하고 무입력 두 시작 위상의 표시 간격 합과 마지막 ACK를 함께 비교한다.
3. 실기 보고는 기존 1–30초·30–60초 FPS를 유지하고 원본 렌더링 중단 구간을 별도로 표시한다. 이번 단계에서 제품 ARM·65816·FPGA와 STOP·독립 검사·메뉴 복귀 경로는 수정하지 않았다.

## 재현

기존 820 원본 PNG 보관본, 903 보드 소스, 897 ARM 링크, 890/903 소비 ROM, 509 ROM 달력과 로컬 게임 파일을 사용한다. `tools/replay_nes_gap904.py <단계> <작업 임시 루트> <로컬 NES 경로>`로 새 904 출력 디렉터리에 `capture`, `count`, `index`, `geometry`, `board` 순으로 실행한다. `board`는 기존 Questa FLOAT 래퍼 안에서 실행한다. 이어서 `replay`를 `--group gap`과 `--group obj` 각각 `--phase 1`, `--phase 2`로 실행한다. OBJ는 각 위상에서 `--ideal-grant`와 `--cold-obj`도 따로 실행한다. 마지막에 `python tools/analyze_nes_gap904.py <작업 임시 루트> <결과.json>`으로 원본, 보드, 화면별 비교를 검증한다. [화면별 시각·작업량과 파일 해시](../analysis/gap904-results.json)
