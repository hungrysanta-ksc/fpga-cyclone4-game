# NES175: 느린 소비 후 회복 검증, 관측 후보는 배포 보류

NES174 화면 정지는 아직 해결하지 못했다. 이번에는 배포된 수집기·fill·전송기·두 클록 mailbox를 함께 연결해 느린 소비 후 회복을 확인했다. 실기에서 누락된 생산 상태를 읽기 위한 두 후보는 FPGA 타이밍을 통과하지 못해 채택하지 않았다. **새 ZIP은 없으며, 같은174 실기 시험을 반복할 필요는 없다.**

## 확인한 연결 조건

기존 시험은 저장된 장면을 전송하거나 실제 게임의 초기26프레임을 즉시 해제했다. 이번 시험은 현재174 RTL의 수집부터 COMMIT 후 해제까지 연결한다. 입력은 합성한224행 PPU 이벤트이며, NES CPU·게임 ROM·물리 SPI·SNES 출력은 포함하지 않는다.

- 명목 NES 화면 간격357,366클록에서 생산을 계속하며 호스트의 COMMIT 소비 후170ms, 이후40ms 동안 다음 레코드 소비를 멈췄다. PREPARED에도1ms 지연을 넣었다. 실기 MCU의 정확한 실행 재현은 아니다.
- BEGIN/END/COMMIT 각5회, 해제8회, 표시 마스크가 지원 범위를 벗어난 후보3회 거부 후 정상 후보로 회복했다. 총31화면 구간 중23개는 이전 후보가 보유된 채 지나갔다.
- 세대1·2·3의 전달 후 세대4·5·6을 거부하고 세대7·8을 전달했다. 세대·CHR528바이트의 순서/내용·END 카운터·mailbox의 정지 중 데이터 보존을 검사했다.
- 수집기 해제를 일부러 차단하면 첫COMMIT 뒤 `owned=1 / generation=1 / DRAIN=11`에서 멈추는 것을 검출했다.

따라서 **이 조건의 해제·재수집 경로는 정상**이다. 실제 게임에서 수집 허용 조건을 반복 위반하는 경우나 물리 전송 문제를 배제한 결과는 아니다. 약0.502초 모델의5회 완료를 실기 FPS로 환산하지 않는다.

초기 시험01은 테스트벤치 변수 선언 순서 때문에 컴파일에 실패했다. 시험02의 정상 경로는 통과했지만 오류 주입이 호스트 COMMIT 수신 시점에 의존해 두 번째 해제부터 차단했다. 최종03은 생산자 해제를 직접 차단하며, 예상한 첫COMMIT 이후 정지를 검출한다. 실패 원본은 보존했고 장치 결함이나 라이선스 문제로 분류하지 않는다.

## 미채택 관측 후보

| 후보 | 변경 | 실제 최악 setup | hold 최솟값 | 자원 | 결정 |
|---|---|---:|---:|---|---|
| A4 이벤트 이력 | 기존16×96 RAM에 화면 경계·새 보유·해제 시점 저장 | -0.178ns | +0.130ns | 15,060LE / 961LAB / 36M9K | 미채택 |
| A5 종료 직전 상태 | 기존 매 클록 기록을 유지하고 입력96비트만 생산 상태로 교체 | -1.114ns | +0.154ns | 15,083LE / 963LAB / 36M9K | 미채택 |

A4는 희소 기록·20회 기록 후 마지막16개 유지·STOP 보존·첫 fault 포함의38검사 및 매 클록 기록으로 바꾼 오류 주입을 통과했다. 그러나 타이밍 실패로 배포할 수 없다.

A5는 수집기의 현재 오류와 전송기 상태를 출력하는 wire만 추가한다. 수집/전송의 상태 갱신·해제·ACK·PPU 진행·이력 RAM·기록 주기·SPI 명령은 유지한다. 이 조건은 생성된 소스와174 원본의 정확한 변환 비교로 확인했다. A4의 이벤트 RAM 검증을 A5의 새 실기 검증으로 간주하지 않는다.

두 MCU도 전체 링크를 확인했다. static26,564 + foreground37,312 + IRQ508바이트, 남은 여유1,040바이트다. A4 보고서는 최대3927/4096바이트, A5는3923/4096바이트다. 런타임·영상 변환·패킷 전송·사운드·입력은174 그대로다. A4는 이력 wire version2/A4, A5는 기존 version1/A5로 서로 다르며 혼용할 수 없다. 둘 다 설치용 파일로 제공하지 않는다.

## 타이밍 실패에서 확인한 것

A4 최악 경로는 loader `fault → reject_state[2]`다. A5는 loader `release_reset[1] → active_reset → load_ready → control.snapshot[40]`이며, 배선 지연이 전체 데이터 지연의 약75%다. reset 레지스터 출력에서 첫 조합 노드까지2.679ns, `active_reset` 조합 출력 fanout40, 이후 SPI snapshot으로 이어진다.

이 A5 경로는 **reset 동기화기가 서로 합쳐졌다는 증거가 아니다.** loader의 `load_ready`가 SPI 응답에 실제로 사용되는 경로다. 기존165 호스트 mailbox reset 분리 처방을 그대로 반복하지 않는다. 새 후보의 NES 관측 로직이 메모리 클록에서 실행된다는 뜻도 아니다. 관측 변경에 따른 전체 배치 변화로 기존 메모리 제어 경로의 여유가 달라졌다.

174의 검증된 setup+0.246ns·hold+0.156ns와 배포 ZIP은 유지한다. SDC·클록·false path·multicycle·seed를 바꾸지 않았다. 두 후보가 실제 클록 단계에서 실패했으므로 새 외부 IO/CDC 검사나 ZIP 생성은 진행하지 않았다.

## 다음 작업의 순서

1. **174의 통과한 배치를 보존할 수 있는 관측 변경 방법을 먼저 확인한다.** Quartus가 지원하는 보존 범위와 현재 산출물의 적용 가능성을 확인한 뒤 진행한다. 지원 여부나 적용 효과를 아직 검증한 것은 아니다. 불가능하면 현재 두 경로의 공유 READY/reset/오류 응답 구조를 근거로 한 변경 하나를 설계하고 명령 수락·응답 시점 계약을 먼저 검토한다.
2. 같은 관측 신호를 바꾸거나 seed·속성만 바꿔 전체FIT을 반복하지 않는다. A4/A5 소스도 통과 후보처럼 사용하지 않는다. 실제 원인을 읽을 정보 없이 같은174를 다시 실기에 보내지 않는다.
3. 최소 상태 읽기가 타이밍을 통과하면 필요한 변경 경계·IO·MCU 쌍을 확인하고 **실제 SMB3로 바로 확인**한다. ROM 초기 부팅·색상 A/B·044 복원 시험을 다시 나열하지 않는다.
4. 정지 해결과 함께174의 평균167.5ms 변환/전송·표시 비용을 줄여야 한다. 기존 SNES delta DMA를 재구현하지 않는다. 전체 테이블 생략은 비활성 WRAM의 기준 세대 상속 없이 적용하지 않는다.

연속 영상·사운드 → 장기 플레이/오류·본체 리셋 로그 → 입력 유지 순서를 유지한다. 카트리지 세이브 SRAM·GBC·164 복원 경로를 보존하며 RUN 중 SD 쓰기와 두 번째 MCU 전체 화면 버퍼를 추가하지 않는다.
