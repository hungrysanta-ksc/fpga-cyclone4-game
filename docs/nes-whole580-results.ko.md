# 580: MMC577 전체 비용표와 R1 남은 계측

PR150 병합 `588fa177ed1a82056a5cc86813506c3f2024cc70`과 head 포함·tree 일치를 확인하고 `codex/nes-whole-budget-580`에서 [579 계획](nes-retrospective579-plan.json)의 R1을 진행했다. 제품 기준은 **MMC577 그대로**다. 이번에는 기존 자료를 재분석하고 시험 도구의 로그 변수 오류만 수정했다. 새 펌웨어·RTL·SDC·합성·전체 시뮬레이션·ZIP은 없다.

## 확인한 결론

다음 개선의 우선순위는 **반복 입력/출력 본문과 계획·공급 비용을 함께 줄이는 구조**다. SEAL 뒤 DMA만 더 줄여서는 현재 전체 예산을 설명할 수 없다. 다만 입력·계획 구간은 계산만의 시간이 아니며 SPI·ROM·credit 대기를 포함하므로 아래 숫자를 ARM 순수 계산 시간으로 해석하지 않는다.

- 실기 수신19.891ms + 계획·공급14.830ms + 출력·최종ACK36.366ms. 표시 평균71.695ms와 차이0.609ms는 미귀속/계측 경계 차이로 남겼다.
- 기존 공동 실행의 초기 두 화면 이후 평균 ACK 간격은 두 위상70.477/71.125ms. SEAL 뒤 실제 CPU DMA는0.993/0.996ms, 출력 진입→SEAL 수락은21.632/21.669ms다.
- 같은 기록의 밀집951–955 표시 간격은83.157/83.121ms. 이 구간 ROM request→grant 합집합은15.941/16.113ms지만 다른 작업과 겹친 **자원 점유/대기 기록**이다. 종단 비용에 더하거나 그대로 절감 가능 시간으로 빼지 않는다.
- 조회D0/E0/E8을 제외한 실기 관측 전송량은5963.90B/표시, wire18.176ms. 잠정12ms 예산3937.5B보다2026.40B(약34%) 많고 필수 조회·gap도 별도 필요하다. 이는 현재 관측 작업량 투영이며 모든 게임/장면의 불가능성 증명은 아니다.

## 중복 없는 시간표

두 뱅크 초기화 후907–957의51간격 평균, 단위ms다. 906까지 포함한52간격×2위상의 각 행에서 아래8항 합계가 실제 ACK 간격과1e-9ms 이내로 일치한다. 이전 표시와 최종ACK의 간격도 별도로 저장한다.

| 서로 겹치지 않는 구간 | 위상1 | 위상2 |
|---|---:|---:|
| 이전 ACK→다음 source 시작 | 0.553 | 0.554 |
| source→planner 진입 | 22.126 | 22.079 |
| planner→출력 진입 | 14.992 | 14.996 |
| 출력 진입→SEAL 수락 | 21.632 | 21.669 |
| SEAL 뒤 검사 | 2.354 | 2.354 |
| SEAL 뒤 VBlank service 대기 | 6.614 | 7.270 |
| SEAL 뒤 DMA | 0.993 | 0.996 |
| SEAL 뒤 기타 setup/control | 1.213 | 1.207 |
| **ACK 간격 합계** | **70.477** | **71.125** |

여기의 DMA는 **SEAL 뒤**다. 앞서 실행된 tile/map DMA는 앞 구간에 포함되므로 전체 DMA가1ms라는 뜻이 아니다. VBlank service 대기 역시 업로드 가능 구간을 기다린 시간까지 포함하며 최종 표시 직전 대기만 뜻하지 않는다.

952·957의 최종 표시 대기는 두 위상 모두0회다. 전체51개에서는 위상2의931에1회가 남으며 이를 숨기지 않았다. 마지막957 ACK는87545284/88254606 master clocks로 기존과 동일하고 전체 VRAM DMA는각114352B다. 이번 재분석을 성능 향상으로 집계하지 않는다.

51화면 조회 제외 전송량은6597.35/6597.98B이며 밀집5화면은7082.60/7085.80B다. 실기5963.90B와 작업량이 다르므로 이 모델을 실기36.366ms의 직접 분해로 합성하지 않는다. wire 합계는 관측 명령별 합계와 일치하며 두 위상에서 프레임별 D1/E1/E9 작업 바이트는 동일하다. 조회 횟수는 위상에 따라 달라질 수 있다.

## 발견·수정한 시험 로그 오류

`test_nes_raw506_joint.py`의 마지막 D2 처리에서 SPI 시작을 담던 `start`가 다음 캡처 시작으로 덮어써졌다. 기존 각 위상에53건씩 시작>종료가 기록돼 있었다. 모두 해당 generation의 마지막 D2이며, 잘못 기록된 값은 원래 코드의 다음 캡처 시작 공식과 정확히 일치했다. SPI 종료 시각은 전체 기록에서 단조 증가한다.

변수를 `capture_start`로 분리했다. 실제 hook 본문을 실행하는 [회귀 검사](../tools/check_nes_clock580.py)는 마지막/중간 D2×캡처 위상2개×RPC overshoot2개, 총8조건에서 **로그의 start 외 실행 시계·다음 capture 시각·index·register/memory write·RPC 호출이 동일**함을 확인했다. 경계는 mock이며 전체 시뮬레이션을 다시 통과했다고 주장하지 않는다.

기존 raw trace는 수정하지 않았다. 누락된 SPI 시작을 역산해 채우지 않고 전체 SPI span은 `null`, 올바른 항목의 합집합만 subset으로 저장한다. wire 바이트와 외부8구간 합계는 이 잘못된 start를 사용하지 않는다. 미래 실행의 로그만 수정되며 제품 timing/STOP/ACK에는 변경이 없다.

## 자원·보호 조건

선택576/577의15260LE(여유148),14191comb,8407FF,51M9K(여유5),ARM Flash 여유84B/BSS18592B를 유지한다. 새 FIT·STA 또는 빌드를 실행하지 않았으므로 새 자원 절감은0이다. 외부 IO 전체 sign-off·지속60Hz는 미완료다.

독립 검사·STOP·부분전송 무효화·최종ACK 뒤 이력 공개/EA·VBlank·메뉴/base 복귀·GBC/save 경로는 제품 변경 없이 기존 근거를 유지한다. 이번 로그 검사8건을 새 STOP/메뉴 실기 시험으로 대체 집계하지 않는다.

## 다음 한 단계와 중단선

R1의 기존 자료 분석은 완료했다. **R1 전체는 누락 계측 전으로 유지하며 R2 구현 선택은 아직 승인하지 않는다.** 남은 것은 반복 본문을 없앨 수 있는 양과 그 비용을 같은 장면에 연결하는 단 한 차례의 제한 조사다.

1. 기존 선택 fixture를 복구해 cold/정적 warm/이동/밀집의 canonical·압축 section 바이트, base 대비 실제 변경량, 입력·출력 순서를 기록한다. 기존 counter/버퍼 재사용을 우선하고 필요할 때만 별도 진단 빌드로 한정한다.
2. 같은 generation에 capture 시각/거부 원인·ARM 준비·SEAL/ACK·게임 진행을 연결할 수 있는지 확인한다. 게임 진행/입력 지연이나 물리 ROM grant가 관측 불가하면 결측으로 남긴다. 영상·838표시를 무손실 capture 증거로 사용하지 않는다.
3. 물리 출력/ROM 분해가 구조 판정을 바꿀 때만 필요한 phase mark를 추가한다. 계측 overhead와 진단판/제품판 자원을 분리한다. Flash84B에 상시 logger를 얹을 수 있다고 가정하지 않는다.
4. 이 한 차례 뒤에도 물리 cycle/ROM/capture 연결이 부족하면 그 한계를 보고하고 R2는 조건부 예산 비교만 한다. 무근거 CPI/대기값을 채우거나 같은 전체 시험을 반복하지 않는다.

R2 비교표에는 입력 본문 제거와 출력 이력 재사용의 wire·비중첩 계산·포트/이력/STOP 복구·**실제 삭제할 코드**를 함께 넣는다. ROM/선행DMA는 결합 일정으로 포함한다. 같은 바이트 재검사·개별FSM/seed·양수 timer 반복은 재개하지 않는다.
