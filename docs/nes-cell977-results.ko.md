# 911 셀 주소 계산을 줄인 뒤의 캡처·표시 일정

## 목표

976 슬롯 후보를 기준으로 911 BG 처리 비용을 분해하고, 주소 계산과 descriptor 준비 중 큰 쪽을 줄였다. 합격 조건은 스크롤 선행, 908 공개, 독립 검사와 STOP을 유지하면서 두 시작 위상 모두 910→911 표시 간격을 2→1 VBlank로 줄이고 912 최종 ACK도 앞당기는 것이다.

## 작업내용

976에서 보고한 잔여 2.367ms는 **슬롯 후보 적용 전 973 대조군**의 값이다. 이번에는 976 슬롯 후보 자체를 실행했다. zero BG 서비스부터 스크롤 테이블 루프 입구까지 ARM의 실행 주소와 다음 주소까지 경과한 마스터 클록을 쌍으로 기록했다. 실제 링크에 대응하는 GCC 목록의 소스 행으로 분류하고, 타일 검사·슬롯 함수·map 쓰기 함수에 들어간 시간은 각각 분리했다. 두 위상 모두 계측을 켜고 끈 SPI·65816·타일 이벤트와 진단 BIN이 바이트 단위로 같았다.

| 976 슬롯 후보에서 다시 잰 비용 | 위상 1 (ms) | 위상 2 (ms) |
|---|---:|---:|
| BG 전체, 스크롤 테이블 생성 직전까지 | 3.783 | 3.781 |
| 세 함수 비용을 뺀 잔여 | 2.222 | 2.220 |
| └ 셀 주소 계산과 해당 주소 접근 | 0.514 | 0.514 |
| └ descriptor 준비와 그 내부 초기화 | 0.171 | 0.171 |
| └ 재사용할 행 탐색과 66B 비교 | 0.775 | 0.775 |
| └ 나머지 반복 제어·슬롯 힌트 확인·워드 조립 등 | 0.762 | 0.760 |

주소 항목에는 소스 행·열·VRAM 페이지 오프셋 산술과 같은 소스 행에서 수행한 셀 읽기·검사가 들어간다. 최적화된 ARM 명령에는 여러 C 연산이 합쳐질 수 있다. 계산식 자체의 단독 하드웨어 지연으로 해석하면 안 된다.

1. **행 주소**는 입력 행 포인터와 시작 열·두 번째 페이지 시작점을 행마다 한 번 정했다. 33셀 안에서 현재 오프셋을 2씩 더하고 경계에서 반대쪽 페이지로 옮긴다.
2. **16비트 워드**는 여기에 16비트 셀 읽기·비교를 연결했다. 값이 바뀐 워드만 쓰고 해당 dirty 비트를 세운다. Cortex-M4의 little-endian 표현을 사용하며 바이트 배열에는 고정 길이 memcpy로 접근한다.
3. **행 검색 포함**은 각 행 중앙 셀의 하위 3비트로 가능한 이전 행을 골라 원래 순서로 비교한다. 같은 입력에는 같은 분류 값이 나오며, 재사용은 기존 예외 검사와 66B 전체 일치 뒤에만 허용한다. 첫·중앙·마지막 셀을 모두 쓰는 변형은 Flash 한도를 12B 초과해 실행에서 제외했다.

## 성과

단위는 ms이며 각 칸은 위상 1 / 위상 2다. ARM 링크·65816·기존 FPGA 포트 모델을 같은 두 시작 조건에서 905부터 912까지 연속 실행했다. 양수 ACK 변화는 지연이다.

| 후보 | planner→E9 발행 | planner→SEAL 수락 | 911 표시 간격 | 밀집 여섯 간격 | 912 ACK 변화 | Flash |
|---|---:|---:|---:|---:|---:|---:|
| 976 슬롯 | 7.280 / 7.329 | 15.186 / 15.247 | 2 / 2 | 13 / 13 | 기준 | 212,936B |
| 행 주소 | 7.113 / 7.113 | 14.985 / 14.974 | 2 / 2 | 14 / 13 | +17.017 / −0.024 | 212,952B |
| 16비트 워드 | 6.659 / 6.610 | 14.569 / 14.490 | 2 / 2 | 14 / 14 | +17.023 / +17.007 | 212,964B |
| 행 검색 포함 | 6.107 / 6.058 | 13.997 / 14.020 | 2 / 2 | 14 / 14 | +17.017 / +0.350 | 212,992B |

가장 빠른 후보에서 911 planner 진입을 기준으로 E9는 1.173 / 1.271ms, SEAL은 1.189 / 1.226ms 앞당겨졌다. 하지만 910 입력의 마지막 두 D2 사이 간격은 1.965 / 1.838ms에서 3.547 / 3.370ms로 늘었다. 그 사이 이전 표시의 최종 ACK를 기다리는 E0가 8 / 7회에서 20 / 19회로 늘었고 EA·E8·D3·D0·D1·마지막 D2가 이어졌다.

행 검색 후보의 마지막 D2는 마스터 클록 14,658,287 / 14,655,973에 끝났다. 직전 캡처 시작선 14,652,088을 각각 **0.289 / 0.181ms** 넘겨 911 캡처가 다음 허가 구간으로 갔다. 위상 2에서는 908과 910 자체가 기준보다 한 VBlank 먼저 공개된 것까지 포함해 비교했다. 두 위상 모두 908은 245선, 911은 244선에 공개됐고 910→911은 여전히 2회였다. E0 반복의 원인과 줄일 수 있는 양은 따로 확인해야 한다.

모든 실행 후보에서 스크롤·패딩 수락이 첫 타일보다 앞섰다. 각 위상에서 905–912 RGB 8장, map 패킷 52개의 세대·범위·데이터와 전체 E9 레코드가 기준과 일치했다. 각 후보에 911 STOP 및 잘못된 SEAL을 각각 주입했을 때 910 RGB를 유지한 채 0xE4 / 0xE0로 끝났다. 새 실기판은 만들지 않았고 실기 FPS·메뉴 복귀는 이번에 재측정하지 않았다. [두 위상 명령별 시각과 오류 재생 결과](../analysis/cell977-results.json)

## 후속작업

976 슬롯을 계산 대조군으로 유지한다. 911 planner 비용을 가장 많이 줄인 행 검색 후보에서는 909 공개·65816 최종 ACK·첫 유효 E0·EA와 910의 마지막 입력 반환을 같은 시각축에서 비교한다. 이전 최종 ACK와 EA 뒤 COMMIT 순서를 유지하며 910 마지막 D2가 직전 캡처 시작선 안에 드는지 먼저 확인한 뒤, 911의 잔여 DMA와 SEAL 마감을 재검증한다.

재현에는 976 슬롯 링크와 같은 TEMP를 사용한다. `nes_cell977.py profile TEMP --phase N`으로 기준 명령을 계측한다. `prepare TEMP`에 옵션 없음·`--word`·`--bucket`·`--mid`를 각각 적용하고 `build_nes_trial577.ps1`로 전체 링크한다. Flash 한도 내 세 후보는 `run TEMP --phase N`으로 실행한다. `check_nes_cell977.py TEMP TEMP/nes-MODE-FAULT --mode MODE --guard FAULT`로 stop_decode와 bad_seal을 재생한 뒤 같은 스크립트에 TEMP와 결과 JSON 경로를 주어 집계한다.
