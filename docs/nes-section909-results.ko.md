# MMC907 section 5 발행 순서와 선행 DMA 검증

실기 기준은 MMC907을 유지한다. 기존 묶음을 마지막 OBJ 준비 전에 65816까지 전달할 수 있었다. 그만큼 팔레트·OAM 수락이 밀리면서 여섯 표시 간격 합과 마지막 ACK를 함께 줄인 조건은 없었다.

## 바꾼 순서

MMC907의 906 보드와 65816 표시 ROM을 사용해 ARM 발행 순서 두 가지를 비교했다. 원본과 두 후보 모두 플래시에 최종 링크한 코드를 실행했다. 원본 SHA-256은 `dba9d47853d5c470a85b7041019d396bd0abf70939c14ff7751ccf2e3cbcfe74`다.

- **909A**는 scroll·패딩 전송이 끝났고 확정된 patch가 있으며 이 화면의 map 업로드와 팔레트·OAM 재사용이 없고 타일 생산이 진행 중일 때, section 5를 팔레트와 OAM 앞에 발행한다.
- **909B**는 팔레트를 원래 자리에서 발행하고, 같은 조건에서 OBJ를 하나 이상 발행한 경우 section 5를 OAM 앞에 둔다.

두 경우 모두 계획이 끝나면 확정된 CHR 마지막 192B, HDMA 테이블 243B, 길이 필드 6B를 기존 작업 버퍼에 모은다. 201B와 240B를 같은 offset에 같은 순서로 enqueue한다. 각 패킷은 기존 타일·큐 credit 검사를 거치며 SEAL은 모든 타일 완료와 독립 검사를 기다린다. 별도 이력이나 staging 슬롯은 추가하지 않았다.

## 비교 방법

모험도 4 후반 캡처 8장(3408–3436)을 같은 SPI 비용·ROM 허가 일정으로 재생했다. 위상 1과 2는 시작 시각만 다르며 각 위상 내에서 MMC907과 후보의 시작 시각은 같다. 각 조건에서 여덟 RGB 화면과 모든 출력 패킷의 내용·개수·section 5 순서를 대조했다. 패킷 비교는 발행 순서에 따라 부여되는 시퀀스만 제외한다. 별도로 각 세대의 실제 65816 최종 ACK와 유효 E0 identity·CRC, section 5 WRAM 복원·쓰기 범위를 확인했다.

선행 DMA는 실제 65816 DMA 시작과 마지막 쓰기를 짝지어 map offset 또는 tile VRAM 목적지별로 비교했다. 기존 범위의 바이트가 SEAL 전에 이전과 같거나 이른 VBlank에 전달됐는지 판정했다. 초기 화면 905의 마지막 쓰기 훅은 첫 공개 이후에 켜지므로 이 대조는 906–912에 적용한다. 여섯 표시 간격 합은 화면 906 공개부터 912 공개까지다. 마지막 ACK와 SEAL은 공통 시작 기준이며 실기에서 별도로 측정한 시각은 이전 908 기록에 있다.

## 두 시작 위상의 결과

아래 시간은 마지막 재생 화면 912(게임 캡처 3436)의 MMC907 대비 차이다. 양수는 늦어진 시간이다. 각 칸은 위상 1 / 위상 2 순서다.

| 발행 순서 | OBJ 캐시 | 여섯 표시 간격 합 (VBlank) | SEAL 수락 차이 (ms) | 65816 마지막 ACK 차이 (ms) |
|---|---|---:|---:|---:|
| MMC907 | 기존 / 빈 캐시 각각 | 15 / 15, 20 / 20 | 기준 | 기준 |
| 909A · section 5 먼저 | 기존 | 15 / 15 | +0.951 / +0.822 | −0.003 / −0.047 |
| 909A · section 5 먼저 | 빈 캐시 | 20 / 20 | +0.142 / +0.090 | 0 / 0 |
| 909B · 팔레트 먼저 | 기존 | 15 / 15 | +0.990 / +0.896 | +0.004 / 0 |
| 909B · 팔레트 먼저 | 빈 캐시 | 20 / 20 | +0.041 / −0.016 | +0.011 / −0.018 |

- **언제 수락됐나.** 기존 캐시의 MMC907은 마지막 OBJ 준비 뒤 3.696 / 3.652ms에 첫 묶음 발행을 시작했다. 909A는 OBJ 준비 전 6.725 / 6.451ms에 시작해 두 번째 패킷까지 65816이 4.528 / 4.274ms 전에 수락했다. 그러나 마지막 팔레트 수락이 3.356 / 3.301ms, 마지막 OAM 수락이 2.217 / 2.164ms 늦어졌다. OBJ 반환 뒤 SEAL까지도 2.936 / 3.012ms에서 3.513 / 3.510ms로 늘었다.
- **빈 캐시.** MMC907 자체가 OBJ 준비 약 29.5ms 전에 첫 묶음을 발행했다. 909A가 이를 약 37ms 전까지 앞당겨도 마지막 표시는 두 위상에서 각각 VBlank 54 / 55였다. 기존 캐시에서도 세 링크 모두 49 / 50에 마지막 화면을 공개했다.
- **선행 DMA.** 비교한 전 세대에서 기존 선행 DMA 범위의 누락은 0B였다. 909A 위상 2의 화면 906에서는 두 캐시 상태 모두 map 1,344B가 VBlank 33에서 34로 밀렸다. 909B는 네 조건 모두 MMC907의 기존 선행 DMA 바이트를 같거나 이른 VBlank에 완료했다. 마지막 화면의 빈 캐시 선행 DMA 496B 역시 유지됐다.
- **보호 조건.** 두 최종 링크의 Flash는 909A 212,908B, 909B 212,904B로 한도 212,992B 안에 들었다. SRAM D0 송신 네 곳, 입력 CRC 오류 거부, 정상 최종 ACK, 시간 제한 STOP·base 복구·메뉴 반환 경로를 확인했다. 실제 ARM·65816 명령과 큐·SPI·ROM 경쟁 모형을 함께 실행한 결과다. 실기 FPS 기준은 기존 MMC907이다.

MMC907 기존 캐시에서 마지막 OBJ 반환을 0으로 놓으면 마지막 OAM 수락은 +0.082 / +0.083ms, 첫 201B 발행은 +0.621 / +0.658ms, 두 번째 240B 수락은 +2.292 / +2.294ms, SEAL 수락은 +2.936 / +3.012ms였다. 909A에서는 마지막 OAM이 +1.925 / +1.923ms까지 밀렸다. 다음 후보는 MMC907의 OAM 발행 자리를 유지하는 쪽이다. 첫 패킷을 미리 조립해 OAM 수락 뒤 발행까지의 0.54–0.58ms를 줄일 수 있는지, 마지막 240B 수락 뒤 SEAL까지의 0.64–0.72ms 중 얼마가 필수 검사·credit 대기인지 따로 판정한다.

## 재현

1. `python tools/nes_section909.py patch`로 MMC907 원본 링크에서 두 패치를 생성한다. 각 패치와 `probes/nes-trial907/link`를 `tools/build_nes_mmc479_arm.ps1`에 전달해 해당 후보 폴더의 `link`로 전체 빌드한다.
2. `python tools/nes_section909.py guards "<모험도 4 ROM>"`을 각 후보에 실행한다. B는 `--after-palette`를 추가한다.
3. `python tools/nes_section909.py replay <MMC907 재생 작업 경로> <1|2>`를 두 시작 위상에서 실행한다. 빈 OBJ 캐시는 `--cold`, B는 `--after-palette`다.
4. `python tools/analyze_nes_section909.py <재생 작업 경로> analysis/section909-results.json`으로 MMC907 네 기준 실행과 후보 여덟 실행을 비교한다. [세대별 결과와 선행 DMA 범위](../analysis/section909-results.json)
