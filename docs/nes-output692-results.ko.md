## 확인한 병목

MMC690 ARM은 기존688과 799개 함수의 주소·크기·명령 바이트가 같다. 선택689D 보드와685 CPU의 기존 두 시작 위상 기록을 해시로 고정하고, 같은 map·OBJ 작업량의 104개 warm 출력 비용을 다시 합산했다. 새 성능 후보·새 실기·새 RTL/FIT 결과가 아니다. 실기 평균25.561ms를 아래 비율로 나눠 추정하지 않는다.

다음 우선순위는 **발행 구간과 실제 수락 마감을 함께 앞당기는 것**이다. 마지막 표시 대기 제거는 이미 끝났고, DMA 엔진 자체의 속도만 높여서는 남은 발행 비용을 설명하지 못한다. 기존과 같은 고정 polling 횟수·DMA 크기·위상별 상수 탐색은 재개하지 않는다.

## 장시간판에서 실제로 바꿔야 할 것

다음 실기 전달부터 **60초 비교판과 시간 제한 없는 장시간판을 별도 파일명·로그명으로 함께 제공**한다. RESTORE는 계속 제외한다. 이번692에는 새 설치본을 만들지 않았다.

현재 링크된 MMC690 ARM으로 일곱 경계 조건을 실행했다. 59.99초는 진행,60초/60초 이후는DEADLINE, tick wrap 전후의 짧은 경과는 정상이다. 시간을 크게 늘려도 누적4,194,304번째 step에서LIMIT가 발생한다. limit0을 직접 주입하면 즉시DEADLINE이며, 정상begin API도0을 거부한다. 즉 숫자 하나 변경은 장시간판 구현이 아니다. 한 시간 경과 값 주입은 **실제 한 시간 실행이 아니다**.

1. 60초 비교판은 현재 종료·5–40초/40–55초 완료 집계를 유지한다. 장시간판은 정상 플레이 시간 제한을 없애되, 부팅5초·SPI·credit·ROM·STOP의 고장 감시는 유지한다.
2. 세션 누적 step cap을 진행 기반의 정지 감시로 교체한다. 진행 없이 반복할 때는 계속 차단하고, 정상 진행 횟수만으로 끝나지 않게 한다. tick/세대/credit wrap과 장시간 통계 overflow를 별도 검사한다.
3. 사용자의 종료 요청은 실제 입력→SNES/FPGA 공개→ARM 확인→STOP→base/menu의 경로로 연결한다. 아직 종료 버튼 조합은 확정하지 않았다. 물리 RESET은 현재세션을FAILED로 래치하므로 정상 메뉴 종료로 안내하지 않는다. STOP 뒤 미완료 입력·이력 무효화와 stale ACK 차단을 유지한다.
4. 현재55초 이후 frame-start 통계는 모두bin11로 합쳐진다. 비교판 서식은 보존하고 장시간판에는 실제 경과시간·종료 이유·표시 수·최대 간격·오류 및 복구 수를 유한 메모리로 남긴다. 누적 bin11을55–60초 FPS로 오독하지 않게 표기한다. RUN 중 SD 기록은 별도 비용·안전 검증 없이 추가하지 않는다. 로그 저장은 검증된 STOP 뒤에 수행한다.
5. 두 버전은 같은 성능 구현을 사용한다. 장시간판만의 종료/계측 비용을 별도로 측정하고, 고유 marker·ZIP·로그 파일명과 패키지 해시를 검증한다. 실제 장시간 안정성은 사용자의 후속 실기에서 확인한다.

## 자원·통과 조건과 다음 순서

현재Flash212984/212992B(8B여유), data10040B/BSS19544B, CPU body여유0B/packed13B, FPGA15295LE·963/963LAB·56/56M9K다. 기존 제어를 대체하고 전체 링크에서 비용을 확인해야 한다. 변경 없는 보드의 FIT/STA는 재실행하지 않았다. 외부IO sign-off 미완료 범위도 그대로다.

다음 단계는 **장시간판의 종료·정지 감시·로그 경계를 먼저 구현하고 실제 링크 비용 및 STOP/menu를 검증**한다. 이어951 패킷별 tail의 필요한 수락 마감을 확정하고 최소 후보를 두 위상 동일 작업량으로 검증한다. 두 위상의 밀집 표시 간격·957 마지막 ACK 동시 개선,911 마감·951 공개선·952 표시3회·957 최종대기0회·7블록 선행 수신·큰 tile 묶음·독립 검사·cold/빈 캡처 회복을 요구한다. 전체 비용과 변경 경계의 회귀 검증을 통과한 뒤60초/장시간판을 함께 전달한다. 부팅 stage0 희귀 실패는 별도 추적하며 근거 없이 timeout을 늘리거나 자동 재시도를 넣지 않는다.

## 재현과 한계

`tools/check_nes_longrun692.py --arm <MMC690-src> --out <new-guards.json>`은 링크된 Cortex-M4 코드를 실행하되 tick과 SPI 응답을 주입한다. 처음guard01은 test harness의 DWT 영역/receiver 초기 상태 누락으로 실패했다. 원시 실패 로그를 보존했고, 해당 테스트 환경만 고친guard02가 통과했다. 제품 수정으로 세지 않는다.

`tools/analyze_nes_output692.py --arm <MMC690-src> --old-arm <688-src> --traces <trace-root> --guards <new-guards.json> --out <new-analysis.json>`은 `nes-status689-arm1/2` 및 `nes-front638-both1h/2h`를 읽는다. 신규하드웨어 시간 측정이나 새종단CPU 실행은 아니다. 원본trace/ELF/사용자ROM은Git에 없으며 [689 보관 목록](../analysis/status689-archive.json)과 [692 보관 목록](../analysis/output692-archive.json)에서 로컬 의존성과 해시를 확인한다. 이 공개 분석만으로 clean-clone 전체 보드 재빌드가 된다고 주장하지 않는다.
