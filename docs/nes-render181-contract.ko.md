후속 진행: 후보 수집기와 실제 PPU 정렬 검증까지 완료했다. [현재 범위와 다음 작업](nes-collect181-contract.ko.md)을 먼저 읽는다. 아래는 독립 경로 완료 시점의 기록이다.

# NES181 — 영향을 받은 행만 최종 픽셀로 보존하는 출력 구현

180 실기에서 확인한 raster08·compact82·185/224행 거부를 해결하기 위해, **일반 행은 기존 타일/스프라이트 경로를 유지하고 표현하기 어려운 소수의 행은 실제 PPU의 합성 완료 픽셀로 표시하는 방식**을 구현·검증했다. 추가 관측기나 게임별 예외 처리가 아니다.

현재 완료 범위는 독립 행 보존 RTL과 SNES 변환·표시 시험이다. 기존 게임 수집기, 전송 규격, MCU, 배포용 SNES 클라이언트에 아직 연결하지 않았다. **화면 정지 수정 완료·배치 통과·새 실기 시험판·60fps 달성을 뜻하지 않는다.** 배포180은 그대로 유지한다.

## 이 방식을 택한 이유

한 행의 시작 상태만 저장하는 기존 raster 구조는 행 도중 렌더링 중단·재개를 표현하지 못한다. 타일 fetch가 누락되면 compact의 기대 행/열도 어긋난다. 오류 검사만 해제하거나 빈 타일을 넣으면 화면의 일부가 오래된 데이터로 채워질 수 있다.

렌더링 비활성 구간의 색은 항상 검정이 아니다. PPU 주소가 팔레트 영역을 가리키는 경우 해당 색이 나올 수 있다. 최종 픽셀을 보존하면 이 색과 이미 합성된 BG/OBJ 우선순위를 별도로 추측할 필요가 없다. [NES PPU rendering](https://www.nesdev.org/wiki/PPU_rendering)

SNES는 화면 중간에 배경 모드를 바꿀 수 있다. 특수 행에서는 mode3의8bpp BG1만 사용하고, 나머지 행에서는 기존 mode0 BG1+OBJ로 돌아오는 방식을 사용한다. 이번 시험에서는 실제65816 코드의 DMA/HDMA와 SNES PPU 모델로 행 경계까지 확인했다. [SNES backgrounds](https://snes.nesdev.org/wiki/Backgrounds), [HDMA](https://snes.nesdev.org/wiki/DMA_registers)

## 구현된 행 보존 RTL

`src/nes/video/nes_patch_rows181.sv`는 정렬된6비트 최종 색과 행/열 번호를 받는다. 입력은 아직 실제 PPU 출력에 연결하지 않은 인터페이스다.

- 7개 보존 행과1개 임시 행, 총2,048×6비트=12,288비트 RAM이다. M9K 속성을 지정했지만 실제 합성·배치 자원 수는 아직 측정하지 않았다.
- 매 행 전체를 임시 슬롯에 기록한다. 오류/표현 불가 판정이 행 끝에 도착해도 앞쪽 픽셀을 보존할 수 있다. 판정된 행만 슬롯을 확정하고 나머지 행은 같은 임시 슬롯을 재사용한다.
- 상위 수집기는 `row_commit / row_patched / row_slot`을 자기 행 설명에 기록해야 한다. 이 모듈은 중복 행 목록을 보관하지 않는다.
- 행0..223, 픽셀0..255의 순서와 완결성을 검사한다. 8번째 특수 행은 용량 오류로 전체 후보를 거부한다. RAM을 순환하여 앞의 행을 덮어쓰지 않는다.
- 세대와 소유권이 일치하는 완성 후보만 읽을 수 있다. STOP/release, 수집 중 오류, 봉인 뒤 늦은 source fault도 공개를 차단한다. payload RAM을 reset하지 않으며 다음 세대가 이전 픽셀을 읽지 못한다.
- 6비트는 강조색 정보를 포함하지 않는다. 기존에 지원하지 않는 강조색 조건을 이번 경로로 무조건 허용하면 안 된다. 실제 PPU의 정렬과 출력 범위도 통합 시 별도로 확인해야 한다.

## SNES 표시 방식과 공간

특수 행의 실제 NES 색0..63을 CGRAM64..127로 옮긴다. 이 영역은 현재 일반 배경0..31, OBJ128..255와 겹치지 않는다. 모든 색 인덱스가0보다 크므로 NES 색0도 투명색으로 잘못 처리하지 않는다. 특수 행에서는 OBJ를 끄므로 이미 합성된 픽셀 위에 스프라이트를 다시 그리지 않는다.

| VRAM 바이트 주소 | 버퍼A | 버퍼B | 크기 |
| --- | --- | --- | --- |
| 기존 BG | 0000 | c000 | 최대4000 |
| 기존 OBJ | 4000 | 8000 | 최대1000 |
| 특수 행 CHR | 5000 | 9000 | 0800 |
| 기존 map | 6000 | a000 | 1000 |
| 특수 행 map | 7000 | b000 | 0800 |

7개 행을32개8bpp 타일의 서로 다른 fineY에 넣어 CHR2,048바이트로 표시한다. 별도32×32 map은2,048바이트다. B버퍼의8bpp 문자 주소 wrap도 실제 SNES 모델에서 검증했다. 주소는 VRAM 바이트 단위이며 카트리지 세이브 SRAM은 사용하지 않는다.

HDMA3개 채널로 BGMODE/MOSAIC/BG1SC/BG2SC, TM/TS/TMW/TSW, BG1 H/V scroll을 행별로 설정한다. 특수 행에서는 윈도우도 비활성화한다. 원래 왼쪽 클리핑은 보존된 실제 픽셀에 이미 들어 있어야 한다. 기존 배포 클라이언트의 채널 배치와 입력/STOP 서비스 연결은 아직 수행하지 않았다.

## 완료한 검증

| 검증 | 결과 | 범위 |
| --- | --- | --- |
| Questa 행 RAM | 9경우,2,560픽셀 정확 비교 | 늦은 판정, clock 간격,0/7행, 용량 초과, 픽셀 누락, 세대 오류, release, 시작 동시/수집 중/봉인 후 source fault |
| RTL 덤프→SNES | 두 화면114,688 표시 픽셀 전체 일치 | RTL의7행 출력을 실제65816 DMA/HDMA/SNES PPU 모델에 연결; 양쪽 VRAM 버퍼, 최상단/최하단/연속 행/타일 경계 |
| 색·우선순위 | 기대 이미지와 일치 | 특수 행의64색, 비검정 색, 인접 일반 행의 OBJ, 특수 행에 기존 OBJ가 다시 덮이지 않음 |
| 잘못된 입력 | 6경우 거부 | 행 범위, 길이, 색 범위, 순서, 중복, 용량 |

입력은 합성 색이며 실제 SMB3 프레임이 아니다. 두 번째 SNES 화면은 RTL 색에 고정 색 이동을 적용하여 버퍼 전환을 구분했다. 기대 이미지 계산은 읽어 온 RTL 값이 아닌 독립 산식으로 작성했다. 실제 게임의 캡처 정렬·compact 재동기화·전송·실기 PPU는 아직 검증하지 않았다. 첫7경우 RTL/독립 SNES 시험은 보존하되 최종 결과는 시작 동시 fault도 추가한9경우 RTL이다. 출력 덤프 해시가 앞선8경우와 같아 동일 입력의 SNES 결합 시험을 재사용했으며 새로 실행했다고 계산하지 않는다.

## 다음 통합 순서 — 새 진단이나 긴 부팅 반복 없이

1. **실제 PPU 픽셀 정렬과 행별 판정.** 기존 비교 벤치는 cycle2..257을256픽셀로 관측한다. 생산 경로는 해당 clock-enable 후 색/좌표 시점에 맞춰야 한다. 현재 `tap_ce`를 그대로 연결해서 한 픽셀 밀림을 만들지 않는다. 렌더링 변화와 compact 누락을 행 단위로 모으고, 영향받은 다음 행의 prefetch도 포함한다.193행 고정이나 ROM/매퍼별 예외는 금지한다.
2. **compact 행 복구.** 완전하게 보존된 특수 행만 기존 타일 완결성 조건을 대체할 수 있다. 다음 정상 행은 절대 행 번호와 column0으로 재동기화한다. 이전 행의 오류를 모든 이후 행에 전파하지 않는다. 특수 행이 없는 행·불완전 픽셀·ROM fault·용량 초과는 계속 거부한다. 기존 palette/group/object 한도를 조용히 풀지 않는다.
3. **전송과 MCU 수명 분리.** 새 규격으로 행 슬롯과 픽셀을 보내고 구버전은 거부하게 한다. MCU `required[2048]`는 CHR 수신 때 필요하지만 모든 CHR이 끝나고 missing0/lane0/기하학 섹션 완결성이 검증된 이후에는 필요하지 않다. 이 경계 뒤 일방향 상태로 전환해 같은 공간을7×256=1,792바이트 픽셀 및 작은 메타데이터/설정 HDMA용으로 쓰는 안을 우선 구현한다. 그 뒤 CHR 입력을 금지하고 END/COMMIT·세대·순서·길이 검사를 유지한다. **이는 아직 구현되지 않은 메모리 수명 설계다.** 새 영구1,792바이트 배열을 추가하지 않는다.
4. **배포 SNES 클라이언트.** 위 VRAM 공백과 CGRAM64..127 및 추가 HDMA 설정을 기존 staging/최종ACK/양쪽 버퍼와 연결한다. 특수 CHR/map staging, 최대7행에서의 설정 HDMA 크기, WRAM 영역 겹침,4096바이트 부트ROM 한도, vblank 예산과 STOP을 검증한다. 예시 시험 ROM은 기존 패킷·클라이언트가 아니다.
5. **한 번의 통합 승인 뒤 실기.** 결합 경계 시험·ARM 링크/stack·정당화된 FPGA 배치/조건부 IO 뒤 SMB3 숫자1→A로 간다. 전체 FPGA는 이미962/963 LAB으로 여유가 적으므로 단독 RAM 크기를 전체 적합성으로 계산하지 않는다. 아직 FIT/ASM/새ZIP을 만들지 않았다. 같은180·044 재시험도 필요 없다.

전체 프레임 버퍼나60fps 달성으로 해석하지 않는다. 특수 행 최대1,792색 바이트와 CHR2,048바이트·map/팔레트/HDMA의 전송 비용을 전체 경로에 포함해야 한다. 정지 해결과 별도로 차분/base-generation/최종ACK의 갱신 지연을 계속 줄인다. AV 약60fps→장시간 플레이·오류/리셋 로그→입력 유지 순서는 유지한다.
