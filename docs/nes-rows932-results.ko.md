# MMC932 · 태그 3081의 확정 시점과 세대 912의 선행 DMA

**3081 행 0은 두 위상 모두 6265 행 0–2와 같은 ROM 허가 구간에 공급할 수 있었다.** 행 0만 읽으면 약 10.9ms의 대기는 같은 타일의 행 1로 옮겨간다. 연속 슬롯 전체를 읽으면 두 위상 모두 밀집 여섯 간격 합이 16→15 VBlank로 줄지만, 기존 496B의 DMA는 SEAL 뒤에 실행된다. 실기 기준은 MMC925를 유지한다.

## ARM이 확정한 바이트와 ROM 허가

세대 912의 두 번째 E9에는 7개 레코드가 있다. 두 번째가 태그 6265의 마스크 `07`, **세 번째가 `81 90 03 6e 00 09 0c ff`**다. 후자는 OBJ 슬롯 110, 태그 3081, 행 0–7 전부를 명시한다. 이전 E9의 마지막 슬롯은 109다. 실제 ARM 전송의 CRC16·CRC8·끝 표식이 유효한 뒤에만 이 정보를 사용했다. 공급 후보는 세대·태그 번호를 조건으로 쓰지 않고 E9 사이에 이어지는 슬롯 번호로 범위를 찾는다. 931의 행 공급이 먼저 ROM 허가를 쓰고 남은 포트에서만 읽었다.

| 빈 캐시, NTSC 마스터클록 | 위상 1 | 위상 2 |
|---|---:|---:|
| 두 번째 E9 수락 (반올림) | 17,023,027 | 17,380,230 |
| 6265 행 2 선행 읽기 허가 | 17,138,424 | 17,495,784 |
| 3081 행 0 선행 읽기 허가 → 응답 | 17,138,508 → 17,138,513 | 17,495,868 → 17,495,873 |
| 931의 3081 행 0 일반 요청 → 허가 | 17,255,747 → 17,489,748 | 17,612,879 → 17,847,108 |

두 행의 허가 차이는 84클록이다. 같은 ROM 구간인지는 원시 허가 기록의 반복 주기와 NES 프레임 번호를 함께 대조했다. 각 후보는 보조 판독에 CDC 8클록과 레코드당 20클록을 부과했다. 일반 요청과 선행 요청에 중복 배정된 허가는 없었다.

## 여섯 표시 간격과 마지막 ACK

위상 1 / 2 순서다. ‘보존’은 MMC925의 여섯 목적지 범위가 SEAL 전에 실제로 받은 공통 바이트 수다. 같은 크기의 다른 타일로 대체한 경우를 제외했다.

| 빈 캐시 공급 정책 | 선행 DMA 총량 (B) | 기존 496B 중 보존 (B) | 여섯 간격 합 (VBlank) | MMC925 대비 912 ACK 단축 (ms) |
|---|---:|---:|---:|---:|
| 931 최근 두 번째 레코드 | 528 / 528 | 496 / 496 | 16 / 16 | 0.060 / 0.031 |
| 3081 행 0 추가 | 528 / 528 | 496 / 496 | 16 / 16 | 0.060 / 0.031 |
| 3081의 확정 마스크 전체 | 528 / 496 | 496 / 496 | 16 / 16 | 0.048 / 0.000 |
| 뒤따르는 연속 슬롯의 확정 마스크까지 | 0 / 0 | 0 / 0 | **15 / 15** | **16.261 / 16.252** |

행 0만 추가하면 다음 일반 읽기인 3081 행 1에서 10.895 / 10.905ms를 기다렸다. 마스크 전체를 앞당기면 다음 태그 6264 행 0이 9.648 / 9.658ms를 기다렸다. 연속 슬롯까지 공급하면 마지막 128B OBJ(token 38)의 일반 ROM 요청이 사라지고, 마지막 표시 간격만 3→2 VBlank가 됐다. 912 공개 시각은 VBlank 49 / 50의 248선이다.

## 496B가 앞선 VBlank에 들어가지 못한 이유

연속 슬롯 후보에서 65816이 SEAL을 수락한 시각은 17,369,860 / 17,727,028클록이다. 496B에 해당하는 여섯 DMA는 그 **다음** VBlank에서 정상 실행됐다. 그보다 한 VBlank 앞의 종료 시각을 추적된 주사선의 가장 늦은 가능한 경계로 잡아도 17,153,588 / 17,511,202클록이다.

양쪽 모두 이 경계까지 FPGA에서 준비된 원래 범위는 최대 112B였고, 65816에서 복사·반환까지 끝낸 범위는 첫 BG **16B**였다. 나머지 480B 중 첫 32B OBJ(token 32)의 반환은 경계보다 0.82 / 0.79ms 늦었다. 288B OBJ(token 35)는 **생산 완료 자체가 2.040 / 2.019ms 늦었다.** 다음 비교는 이 둘의 준비·수락·반환과 이전 VBlank의 실제 DMA 기회부터 추적한다.

## 보호 조건과 재현

* 후보 세 가지, 기존·빈 캐시, 두 위상의 12개 재생에서 동일한 ARM·65816 링크로 여덟 화면의 RGB·타일·map·팔레트·section 5를 대조했다. token 37·38 외의 다른 타일 37묶음의 준비 시각은 MMC925보다 늦어진 경우가 없었다.
* 기존 캐시는 모두 밀집 13회와 MMC925 최종 ACK 시각을 유지했다. 910의 D2 여유도 120 / 499클록을 유지했다. 빈 캐시에서는 931과 같은 캡처선을 탔고 D2는 그 선보다 50,086 / 51,062클록 뒤였다.
* 연속 슬롯 후보에서 6265·3081·6264의 허가 전·응답 중·응답 뒤 STOP을 위상당 152조건으로 검사했다. 65816 손상 descriptor·중복·잘못된 SEAL 거부, 복사·표시·OBJ 마지막 바이트 STOP을 다시 실행했다. SRAM D0 송신과 타이머·base·메뉴 복귀는 동일한 펌웨어 해시의 기존 검증 결과와 대조했다.
* 공유 ROM 포트는 기록된 보드 허가 일정 모델을 사용했다. 보드 RTL·FIT·STA와 실기 FPS는 새로 측정하지 않았다.

재현은 `tools/nes_rows932.py MODE TEMP PHASE [--cold]`에서 `row`, `mask`, `run`을 실행한다. `nes_return920.guards`와 `nes_obj923.obj_stops`에 `first`, `tag='932run'`을 전달해 `probes/nes-rows932/guards.json`, `stops.json`을 저장한다. `tools/analyze_nes_rows932.py TEMP analysis/rows932-results.json`으로 MMC925와 931 대조군을 함께 비교한다.
