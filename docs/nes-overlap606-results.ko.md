# 606 · 954의 PPU 캡처와 이전 표시 대기 중 입력 예산

**954가 요구하는 CHR 272 B는 모두 현재 PPU 캡처에서 확보할 수 있다. 반면 953의 SEAL 이후 대기만으로는 954의 입력 확인·계획·출력을 60 Hz 마감에 넣을 수 없었다.** 보드 기준은 MMC577이며 이번 단계는 이 두 조건을 분리해 같은 시간축에 놓은 진단이다.

## CHR 데이터가 생기는 시각

geometry230의 954·955 PPU strobe에 601에서 검증한 물리 주소·plane·값을 한 건씩 대응시켰다. 954의 실제 BG·OBJ 소비 주소와 값 272개가 모두 서로 다르다. 같은 인덱스가 다른 tag로 덮이면 이전 lane을 즉시 무효화했다. 모든 수치는 해당 프레임에서 비어 있는 캐시로 시작하며, strobe 다음 dot부터 쓴 값을 사용할 수 있게 했다.

| BG·OBJ 각각의 직접 매핑 라인 | 데이터 RAM | 954 캡처 종료 때 남은 필수 바이트 |
|---:|---:|---:|
| 16 | 512 B | 44 / 272 |
| 32 | 1,024 B | 112 / 272 |
| 64 | 2,048 B | 208 / 272 |
| 128 | 4,096 B | 272 / 272 |

검사한 네 크기 중 128라인씩 둔 경우에만 목표 264 B를 넘었다. 이 구성은 캡처 시작 후 **13.030 ms**에 264 B, **13.284 ms**에 272 B를 확보하고 캡처 종료까지 유지했다. 561의 capture gate에 동일한 4 master clock/dot로 놓으면 264 B가 확보되는 시각은 기존 954 입력 시작보다 두 위상 각각 **36.658 / 36.621 ms 앞**이다. 서로 다른 장비에서 나온 입력을 이 일정에 정렬한 값이다.

955 쓰기를 같은 캐시에 계속 적용하면서 954의 기존 실제 요청 순서와 대조하면 두 위상 모두 272 B가 적중한다. 단, 601 RTL은 capture와 query의 동시 소유를 금지한다. **각 위상에서 1회는 다음 capture가 열려 있어 원래 요청 시각에 읽을 수 없었다.** 이 한 건을 미루거나 ROM으로 보내는 비용과 955 캡처 손실 방지는 통합 경로의 검증 항목이다. 기존 601 단독 Lite MAP은 166 LE·38,400 bit이고 MMC577 보드 여유는 148 LE·M9K 5개다. 4,096 B에는 디렉터리가 별도로 필요하다. 606에서는 보드 FIT·STA를 다시 돌리지 않았다.

## 953의 최종 ACK를 지키며 옮길 수 있는 입력

954에서 604의 전체 ARM ELF를 그대로 실행해 D0/D1/D2/D3를 실제 FPGA RTL 핀에 연결했다. 605와 같은 D1 복원·성공 반환·첫 E9, 여섯 geometry 배열·raw 바이트를 확인했다. 출력은 같은 모델 소비자로 SEAL·최종 표시 ACK·EA까지 실행했다. **이전 화면의 실제 ACK·공유 SPI 시각은 561의 953 연결 추적**에서 가져왔다. 아래 중첩은 두 기록을 합친 재생 결과다.

- 기존 ACK 조회 주기는 두 위상 모두 약 0.279 ms다. 조회 사이 최대 SPI 여유는 0.172 / 0.170 ms이고 첫 D1 한 건은 0.829 ms다. 기존 조회 시각을 전부 지키면 첫 D1조차 끊지 않고 보낼 수 없다.
- 605의 첫 BG tag를 포함하는 **첫 여섯 블록**으로 범위를 고정했다. 이전 ACK가 아직 없다는 응답을 확인한 뒤 한 블록씩 수신·검사·POP하고 다음 조회 시각에 복귀했다. 한 ARM에서 순차 실행하고 여섯 번 모두 기존 조회 한 주기의 비용을 지불했다. 두 위상에서 완료 전 상태가 동일한 E0 응답 37회를 건너뛰었고, 마지막 선행 블록은 기존 EA보다 1.166 / 1.445 ms 전에 끝났다. 원래의 첫 양성 E0·최종 ACK·EA 시각을 지킨 것은 이 두 기록에서 확인한 결과다. ACK 재조회 간격은 최대 2.235 ms로 늘어 실제 IRQ·STOP 응답 시간에 대한 보장은 별도다.
- 이 경우 입력·복원 9.059 ms를 앞으로 옮겨도 EA 뒤 **입력 COMMIT 8.697 ms → 첫 E9 16.852 ms**다. 60 Hz 표시 기한은 각각 EA 뒤 **15.910 / 15.941 ms**다. 첫 E9만으로 이미 0.942 / 0.910 ms 늦고 뒤의 DMA와 표시가 남는다.
- 더 낙관적으로 953 SEAL 뒤 전 구간을 954 입력에 할당해도 8블록, map 843/957개까지다. 행·OBJ·raster는 아직 0개다. 이 구간에서 기존 전체 계획기를 미리 실행할 수 없다.

이전 SEAL은 뱅크 이력을 확정하는 사건이 아니다. 지금 런타임은 최종 ACK에서 이전 receiver의 generation을 대조하고 EA 뒤에야 `nes_native165_consumed`를 호출한다. 같은 receiver를 먼저 덮으면 이전 세대 확인·해제 경로가 새 입력에 닿는다. 별도 receiver 한 개의 실제 크기는 **9,880 B**다. 한 개를 공유하려면 이전 identity·실패 상태를 분리하고 이전 EA가 새 receiver를 해제할 수 없게 해야 한다. 여섯 번 POP한 뒤 실제 ARM 파서에 ABORT를 주는 시험에서는 늦은 COMMIT이 거부되고 cold 전체 재수신이 성공했다. 두 세대의 소유권 전환과 STOP 뒤 메뉴 복귀를 새 보드에서 시험한 단계는 아니다.

## ROM 대기를 모두 없애도 남는 출력 비용

현재 ARM에서 COMMIT 확인부터 첫 E9 완료까지 **8.155 ms**다. 이 중 SPI·드라이버는 0.509 ms, 전송 밖의 ARM 실행은 **7.646 ms**다. 여섯 블록만 옮기는 재생에서 ROM과 후속 계산·조회를 전부 무료로 두더라도 현재 필수 E1/E9 wire 4,133 B를 보내 SEAL을 마치는 시각은 EA 뒤 **29.448 ms**다.

아래는 입력 14블록을 전부 이전 EA 전에 끝낼 수 있다고 둔 별도 민감도다. EA 이후의 첫 E9 의존성은 유지했다. 최종 VBlank·ACK 시간은 포함하지 않는다.

| 조건 | EA 이후 SEAL까지 |
|---|---:|
| 첫 E9 이후 현 모델의 필수 출력 wire만 부과 | 20.751 ms |
| 561에서 확인한 tile 묶음 전송량 적용 | 19.419 ms |
| 여기에 582의 8 B map 형식 전송량까지 적용 | 14.768 ms |
| 마지막 경우의 필수 E1 26회·E9 2회에 드라이버 평균만 추가 | **16.162 ms** |

604 모델과 561의 E1 내역 차이 **437 B**는 모두 7번 bulk 명령에서 발생했다. BG 184 B, OBJ 253 B로 23 B 명령 19개에 해당한다. 561은 첫 E9 전에 83 B map을 먼저 보내지만 표에서는 604 발행 순서를 고정하고 bulk 묶음 절감만 옮겼다. 582 map은 독립 검사에 필요한 선언을 포함한 622 B로, 양쪽의 기존 map 2,148 B를 대체한다고 가정했다. 이 마지막 조합도 위상별로 0.252 / 0.220 ms 늦다. 이후 계산·credit·독립 검사·DMA·VBlank를 추가해야 하고, 599의 상속 검사 비용도 그대로 남을 수 있다. 14.768 ms를 60 Hz 달성으로 집계하지 않는다.
