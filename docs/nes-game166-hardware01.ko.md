# NES166 실기 결과 — 화면 완성 전 CHR 수집 취소 확인

사용자는165와 증상이 같다고 보고했다. 무영상은 해결되지 않았지만, 이번 최소 수신 기록으로 실패 구간을 좁혔다. **게임 실행 전체 실패나 SNES 출력 완료 후 화면 손상으로 판단하지 않는다. 완성된 프레임이 표시 경로까지 도달하지 않았다.**

|항목|로그 결과|
|---|---|
|영상 시작 / 취소|BEGIN383 / ABORT383|
|영상 끝 / 승인 / 표시 완료|END0 / COMMIT0 / native_frames0|
|첫·마지막 취소 이유|export reason4: fill 실패 요약|
|첫 취소까지 수신|총1508개 데이터 레코드 = 영상 구성1472개 + CHR36바이트|
|ROM 적재·비교|393216바이트, verify_error0 / run_rom_error0|
|종료·복구|시간 만료1, STOP 성공, 기본 코어 복구, MENU_PREPARED|
|사운드 초기화|SPC A9, unmute1|

진행 기록0~99는 연속이다. DISPLAY_NEXT231450ms→DISPLAY_STOPPED291460ms로 RUN 구간은 **60010ms**다. MENU_PREPARED294570ms이며 펌웨어 tick 기준이다. 첫 BEGIN과 첫 ABORT의 MCU 수신 시각 차이는130ms다. 이 값에는 영상 구성 레코드 전달 시간 등이 포함되어 있으므로 CHR fill 단독 실행 시간이나 실제 PSRAM 지연으로 해석하지 않는다.

## 확정한 것과 아직 모르는 것

첫 프레임은 CHR36바이트까지 수신한 뒤 취소되었다. 수신 시작 자체와 초기 그래픽 읽기는 진행됐으나, END/COMMIT까지 간 프레임은 없다. 따라서 **SNES 전송 전 버퍼 비우기·PPU 초기화 누락보다 앞단의 fill 실패를 먼저 수정한다.** 첫 완성 화면까지 forced blank를 유지하는 표시 절차와도 부합한다. 기존166 준비 과정의 잔존 데이터가 있는 WRAM 첫 화면 시험은 모델 검증이며, SNES 실기 경로의 모든 문제를 배제하는 증거는 아니다.

중간381회의 취소 이유는 저장하지 않았다. 첫·마지막의 export 오류4는 fill 실패를 묶은 코드이고, fill 내부의 오류4(대기 상한 초과)와 같은 의미가 아니다. 세부 fill 오류·실패 상태를 현재 로그만으로 확정할 수 없다. 수신/변환/표시 오류0 역시 실행하지 못한 뒤쪽 경로의 정상 완료를 의미하지 않는다.

약6.1ms인 WAIT_CYCLES131072는 사용권을 기다리는 REQUEST와 MCU 소비를 기다리는 STREAM에도 적용된다. 실제 사용권은 scanline242..259 중 코어가 안전한 조건에 한정된다. 다음 수직 공백까지의 정상 대기가 이 제한보다 길 수 있으므로 **대기 정책이 유력한 조사 대상**이다. 다만 lease, 전체 상한, lookup, 메모리 응답 주소·세대·오류도 세부 코드 확인 전에는 배제하지 않는다.

screen_error169는 SPC 초기화 A9 값이다. 마지막 run_flags1은 STOP 후 held 상태다. 버튼 기록9개는 완료된8비트 읽기 값의 변화이며 실제 버튼 클릭 수나 입력 유지 품질을 뜻하지 않는다.

## 다음 작업

선택된 fill/arbiter 설정에서 수직 공백 경계와 실제 소비 지연을 재현해 사용권 획득 전 대기, 획득 후 응답 watchdog, 전송 대기를 분리한다. 짧은 메모리 응답 watchdog까지 일괄 늘리지 않는다. CPU/PPU 우선순위, 전체 유한 상한, 취소 후 응답 drain은 보존한다. 필요한 세부 fill 오류는 기존 ABORT 기록 경로에 전달하고 원인을 수정한 SMB3 시험판으로 돌아간다. 같은166 재시험·영상·044 복원 시험은 추가로 필요하지 않다.

이번 변경은 결과와 다음 계획의 기록이다. 새 펌웨어·FPGA·시험 ZIP은 만들지 않았다. [원본 로그 해시·파싱·소스 근거](../analysis/game166-hardware01-verification.json). 실기 SD 파일을 PC에서 읽어 설치 바이트까지 검증한 것은 아니다.
