# NES182 실기 — 표시 완료 약26% 증가, 끊김은 남음

사용자의 “조금 나아졌지만 여전히 끊긴다”는 관찰과 로그가 일치한다. **DMA 변경 뒤 표시 처리량은 증가했지만60fps 목표에는 크게 못 미친다.** 이번에는 두TXT만 받았다. 영상 분석이나 음성·육안 메뉴 복귀 확인을 새로 수행했다고 기록하지 않는다.

## 181과 비교

|항목|181|182|
|---|---:|---:|
|실행 구간|60.06초|60.07초|
|최종 표시ACK 완료|136회|171회|
|평균 표시 완료율|2.264회/초|2.847회/초|
|전체 시간/완료 수|441.6ms|351.3ms|
|수신·후보 대기 누적|28.38초|28.52초|
|변환·CHR 전송 누적|7.74초|9.25초|
|나머지 전송·표시ACK 누적|23.71초|21.81초|

완료율은 약25.7% 늘었다. 이는 전체 시험의 표시ACK 평균이며 NES 실행FPS·TV주사율·순간FPS가 아니다. 같은 입력 시퀀스와 장면을 재생한 통제 시험도 아니므로 DMA 자체가 정확히25.7% 빨라졌다고 해석하지 않는다. 사용자 체감과 함께 개선 근거로 사용한다.

완료 한 건당 누적시간은 수신208.7→166.8ms, 변환/CHR56.9→54.1ms, 나머지전송/ACK174.3→127.5ms다. 변환 누적시간이 늘어난 것은 처리한 화면 수도 늘었기 때문이며, 이 수치만으로 변환이 느려졌다고 볼 수 없다. 각 구간에는 대기·SPI·SNES 처리가 섞여 있고10ms단위 누적이다. 실제 프레임별 지연분포는 없다.

전체평균351ms는60fps의16.7ms보다 약21배 길다. 게임을 의도적으로 이 속도로 제한한 것은 아니며, 단순히 전송 드라이버만 바꾸는 것으로는 부족하다.

## 통신량이 함께 증가

transaction은137,469→280,177회, clocked bytes는4,811,300→7,351,325B로 늘었다. 후자는2.625MHz에서 순수 wire시간 하한22.404초다. 완료 한 건당 약43.0KB지만 **필수 화면payload가 아니다.** 양방향 경로의 요청·status·ACK polling이 포함되고 service observer의 직접SPI는 별도다. TX/RX를 두 배로 계산하지 않는다.

DMA가 빈 상태조회나 ACK대기도 빠르게 반복하게 했을 가능성이 있다. 다만 이번 로그에는 종류별 전송량이 없으며 장면도 달라, 증가분을 전부 불필요한poll로 단정할 수 없다. 실제 유효payload와 대기확인 비용을 구분하고 줄여야 한다. 기존 합성raw7 egress하한22.154ms는 별도 범위로, 이번60초 실기의 누적 wire시간22.404초와 혼동하지 않는다.

## 종료와 오류 해석

- ROM393,216B 적재·비교 완료. verify/RUN/ROM/최초/STOP 오류0, sink/video 오류0, 전송ABORT0.
- BEGIN172, END/COMMIT/최종표시ACK171. 마지막표시236세대/59.97초. 다음237세대 수신 중 종료됐다.
- DISPLAY232900→292970ms, 총60070ms. `native_result=1`은 기한 종료이며 처음 발생한 원인이 보존된다.
- `native_receiver_error=24`는 D2 POP 전송 또는 응답status 확인 실패다. 실제 실행소스에서guard가 기한을 먼저 기록한 뒤 이 경로가 실패할 수 있으므로 이번24는 종료 중 부차 결과로 판단한다. POP 원시응답은 없어서 전송실패와status불일치를 직접 구분할 수 없으며, CRC손상·DMA고장의 증거로 삼지 않는다.
- STOP·기본FPGA복원·메뉴준비296230ms 완료. 이것은 로그상 복귀 준비 완료이며 사용자의 육안 확인을 대신하지 않는다.
- SPC A9/유효1/unmute1. `screen_error=169`는 사운드 초기화 결과이며 영상 오류가 아니다. 이번 실제 음질에 대한 추가 확인은 없다.

최근16episode는8거부/8회복, 모두224행이며 raster/compact오류0이다. fetch오류04×3,01×2,07×1,20×1,오류0·mask00×1이다. 07은01|02|04의 조합,20은프레임 종료 시 미완료 low/high pair다. 01은새low앞기존pair잔류,02는low주소조건,04는high짝조건이다. 시각·오류위치·전체빈도가 없으므로 특정 버튼·장면의 원인으로 연결하지 않는다. patch오류도 기존25bit observer 범위 밖이므로오류0거부가 가능하다. 보호조건을 없애는 해결책은 사용하지 않는다.

## 작업 의미와 다음 순서

이번 결과는 전송 방식 개선이 처리량에 도움이 됐다는 근거다. **60fps 미달의 주원인을 DMA나 FPGA배선 하나로 확정한 결과는 아니다.** 기존182를 후속 비교 기준으로 보존한다.

1. 실제 호출 경로에서 유효payload/status/ACK polling의 양과 비용을 구분해, 작은 패킷 집계 및 불필요한 반복조회 절감 후보를 고른다. 더 빠르게 polling만 반복하거나 SPI클록을 무작정 올리지 않는다.
2. 이미 구현한1813/1815압축을 반복하지 않고, 목적VRAM bank의 기준세대가 확인되는 section/CHR 차등전송을 검토한다.
3. FPGA export COMMIT의capture해제와 MCU 최종displayACK의workspace해제는 다르다. 버퍼 수명을 지키면서 수집·전송·표시를 겹칠 수 있는지16.7ms 예산으로 평가한다. 세이브SRAM을 작업공간으로 사용하지 않는다.
4. fetch재동기화도 남은 항목으로 유지하되 새 범용진단을 늘리는 대신 필요한 경계만 확인하고 실제SMB3로 검증한다.

같은182·044 재시험, 무변경FIT, 새펌웨어/ZIP은 이번 결과 정리에 필요하지 않다. AV60fps→장기플레이와 오류/리셋로그→입력유지 순서를 유지한다. GBC164·기존 세이브·이전 완료자료 보존.
