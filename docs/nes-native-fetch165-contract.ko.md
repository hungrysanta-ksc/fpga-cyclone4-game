# NES165 실제 패턴 읽기와 필요한 물리 타일

실제 PPU의 배경·스프라이트 패턴 적재 시점과 같은 클록의 매핑된 CHR 주소를 연결했다. 화면 중 같은 논리 슬롯의 물리 뱅크가 달라져도 두 타일을 모두 필요한 집합에 남긴다. **SNES 갱신 명령 생성·부족한 CHR 보충·실기 속도 개선은 아직 미완료**다. 설치 후보는164를 유지한다.

[검증 요약](../analysis/native-fetch165-verification.json) · [이전 공통 소유권](nes-native-scene165-contract.ko.md) · [그래픽 설계](nes-native-video-feasibility.ko.md).

## 실제 연결

- 기존 BgPainter의 패턴 적재 조건과 SpriteAddressGen의 `load_pix1/load_pix2`를 사용한다. 스프라이트 속성/X는 SpriteSet에 들어가는 실제 임시 OAM 바이트를 같은 단계에서 관측하며, 실제 `dummy_sprite`를 구분한다. 새 관측 레지스터는 코어 동작을 제어하지 않는다.
- 논리 주소는 현재 `native_chr_logical`, 물리 주소는 현재 `ppumem_addr`다. 지연된 디버그 주소나 예측 주소를 사용하지 않는다. 매퍼 레지스터의 별도 복사본도 만들지 않는다. 기존 MMC3·CIRAM 미러링이 선택한 결과를 따라간다.
- 물리 CHR 범위는 SMB3의 `0x200000..0x21ffff`다. 각 저/고 비트플레인이 유효한 읽기인지 확인하고, 두 주소가 정확히8바이트 차이인지 검사한다. 논리 슬롯/행/속성/표시 위치도 같아야 한다. 두 읽기 사이에 뱅크가 바뀐 패턴을 한 타일로 대체하지 않는다.
- 모든 제어·조회·이벤트는 NES 클록에 속한다. host 신호를 직접 연결하지 않는다. ROM 요청·CPU 정지·게임 데이터 변경은 추가하지 않았다.

## 표시 위치와 수집 경계

표시 crop은 NES8~231행이다. **7행 dot257부터** 수집을 시작해야8행의 스프라이트와 배경 미리읽기를 포함한다. 종료는232행 dot1이다.

배경 미리읽기 dot326/328은 다음 행의 열0, dot334/336은 다음 행의 열1이다. 표시 중 dot6/8부터 열2가 이어지며 dot246/248은 열32다. 열33은 화면 밖으로 제외한다. 열 번호는 fine X 적용 전이므로 픽셀 X는 `열×8 - 표시 행의 fine_x`다. 이전 행에서 미리읽을 때의 fine X를 빼지 않는다. 원래 BgPainter의 파이프라인과 fine X0~7, 각256픽셀을 대조했다.

스프라이트는 실제 평가된 순서0~7, 실제 X/속성, **다음 표시 행**, 실제 매핑된 타일의 행을 기록한다. 8×16 타일의 어느 절반을 사용하는지와 수직 반전은 SpriteAddressGen이 만든 실제 주소에 이미 반영된다. 수평 반전/우선순위/팔레트는 원래 속성을 보존한다. NES의 원래 픽셀 합성·스프라이트0 판정·IRQ는 그대로이며, 새 SNES 소비자의 동등성을 증명한 것은 아니다. 추가 스프라이트 경로는 명시적으로 거부한다.

## 이벤트와 필요 집합

유효한 고 비트플레인 적재 다음 NES 클록 구간에 `event_valid`와64비트 `event_data`를 출력한다. 이 스트림은 **아직 저장·압축·소비하지 않는다**. 전송 완료나 화면 준비로 해석하지 않는다.

초기화·release 후8192NES클록 동안 명시적으로 지우고 다음7행 경계부터 시작한다. RAM 전체 비동기 reset은 없다. 기록을 마친 후에만`owned`를 올리고, 소유 중에는 새 이벤트를 무시한다. `query_tile`을 넣고 query를 올리면 다음 클록에 response와2비트 필요 여부를 받는다. invalid 집합은0을 반환하며 release/reset은 진행 중 조회·반쪽 패턴을 취소한다. 16비트 generation은 순환하고, 재사용 때마다 scrub하므로 순환이 이전 비트를 되살리지 않는다. 실제 M9K 사용량은 아직 합성·배치하지 않았다.

## 기존 화면 묶음과 결합

고정된 기존 소스는 수정하지 않고 생성본`nes_native_scene_fetch165`에 시작 허용 입력만 추가했다. 필요 집합의7행 시작이 먼저 없으면 기존8행 상태/CIRAM/OAM 수집도 시작하지 않는다. 정상 게시에는 양쪽 소유권이 모두 필요하다.8행 이전에 오류가 나면 PPU CE가 멈춰도 필요 집합의 오류로 공통 소유권을 반환하며, 나머지 조회는 차단한다. 공통 generation은7행에서 시작한 필요 집합의 번호다. release는 양쪽을 함께 해제한다.

`native_snapshot_valid`도 여전히 전체 frame-ready가 아니다. 기존 논리 슬롯 CHR캐시는 같은 프레임의 여러 물리 뱅크나 일부만 읽은 타일을 모두 보관하지 못할 수 있다. 이번 물리 필요 목록은 그 사실을 숨기지 않고 후속 보충/할당 단계에 필요한 주소를 제공한다. 스크롤/팔레트 수집기의 기존 거부 조건도 유지한다.

## 검증 결과와 한계

선택 test02에서26755검사·54개 패턴 쌍·2048배경 픽셀·6개 거부 시나리오를 통과했다. 실제 MMC3에 뱅크 쓰기와 반전을 적용하고, 전8192타일을 두 번 조회하여 동결을 확인했으며 release 후 모두0임을 확인했다. 서로 다른 물리 뱅크, BG/OBJ 겸용, crop/dummy 제외, 플레인 중간 뱅크 변경, 유효하지 않은 응답, 미완성 쌍, CE가 멈춘 오류, release 취소, 시드한 세대 순환을 확인했다. 실제 SpriteAddressGen의8×8/8×16·수평/수직 반전·주소·속성/X도 검사했다.

생성된 부모 연결부에서 **두 인스턴스의 배선을 그대로 추출**한 시험은13검사를 통과했다. 미리읽기를 놓친8행 시작 차단,8행 이전 오류·복사 도중 오류의 CE 정지 복귀, 정상 상태/메모리 봉인과 조회, 공통 release를 검사했다. 메모리 입력0/합성 행 일정이며 전체 보드나 게임 실행은 아니다. 실제 부모와 코어는 생성·컴파일했다. 컴파일 오류/경고0, 시뮬레이션 오류0; 경계 시험의 미연결 포트 경고44개와27개는 원시 로그에 남겼다. test01도 통과했고 연결 시험을 추가한02를 선택했다.

기존 캐시·CIRAM/OAM·raster·실제 SMB3 부팅20프레임 검증은 해시가 같은 소스를 재사용한다. 전체 부팅/적재/044복원/변경 없는 기능을 다시 검사하지 않았다. 새 ROM 실행, host CDC, 타일 보충, SNES 표시, FPGA 자원·타이밍, ARM 빌드, SD 패키지 및 실기 FPS는 이번 완료 범위가 아니다.

## 다음 구현

1. **이벤트를 SNES가 쓸 수 있는 제한된 타일맵/OBJ/행 명령으로 줄이는 소비자**를 연결한다. 우선 SMB3 첫 레벨에서 실제 필요한 표현과 working set을 확인한다. 최대33BG+8OBJ를224행 모두64비트로 저장하면73472바이트이므로 원시 이벤트 전체 버퍼·전송은 채택하지 않는다.
2. 같은 논리 슬롯의 여러 물리 타일을 보존할 물리 태그 할당과 누락 바이트 보충을 연결한다. 현재 캐시 hit만으로 준비 완료라 하지 않는다. PSRAM 읽기는 기존 CPU/PPU 기한을 보존하는 유한 예산 아래에서만 수행하고, 한도 초과는 명시적으로 보류한다.
3. host CDC/SNES 출력과 기존38M9K 픽셀 버퍼 교체를 함께 구현한다. 최소한의 변경 경계·자원/타이밍 검사를 통과하면 실제 SMB3로 화면·소리·조작을 확인한다. 현재56/56M9K 설계에 단순 추가하지 않는다. 그 다음60초 제한·오류/리셋 로그·장시간 입력 유지로 간다.
