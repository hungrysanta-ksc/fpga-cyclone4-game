# NES222 실기: 시작·60초 플레이 통과, 첫 레벨 스크롤 개선

PR121 `codex/nes-planner-index-221`. 이 결과가 이전222 시험판 준비/실기 미수집 기록보다 우선한다. 새 펌웨어·FPGA·시험 패키지를 만드는 작업은 아니다.

## 작업 의미

221의 슬롯 검색 인덱스와222의 시작 절차 보강을 함께 사용한 실기에서 게임 시작, 첫 레벨의 긴 스크롤, 약60초 후 메뉴 복귀를 확인했다. 사용자도 눈에 띄는 개선을 보고했다. **실기 성능 개선의 근거가 생겼지만,60fps와 정상 플레이 품질은 아직 미달**이다.221 실패 원인을 특정 물리 신호로 확정하거나 장기 안정성을 보장하는 결과는 아니다.

## 실행과 종료

- ROM393216B 전체 load/compare 통과, RUN/ROM/STOP 오류0. DISPLAY_NEXT234800ms→DISPLAY_STOPPED294890ms,60.09초. 메뉴 준비298200ms, 영상65초부터 실제 카트리지 메뉴가 보인다.
- 화면 완료365회, 마지막59.97초/gen575. 다음gen576은 BEGIN만 기록되고60초 deadline1로 종료. BEGIN366/END365/COMMIT365/ABORT0, sink11082송신=11082회수, plan/sink/video/window 오류0, 물리 전송 실패0.
- `native_receiver_error=23`은 D1의 **전송 callback 실패 또는 CRC 불일치**를 합친 코드다. 실제 소스는 deadline을 먼저 기록하고 보존한다. 이번 값은 다음 프레임 수신 중 종료한 상황과 일치하며, 독립적인 CRC 고장 증거가 아니다. 원시 응답을 따로 확보한 것은 아니므로 CRC가 측정됐다고도 주장하지 않는다.
- `screen_frames=0`은 untrusted 구필드다. `screen_error=169/A9`는 SPC 초기화 결과이며 화면 오류가 아니다. SPC unmute 확인1. 소리는 이번 분석에서 별도 청음하지 않았으므로 청음 확인으로 기록하지 않는다.
- 입력 로그는 변경된8bit 읽기109회/마지막16개를 보존하며 B·RIGHT·A 조합을 포함한다. 영상의 이동/점프와 모순되지 않지만 입력 지연·유지 품질 전체의 정량 검증은 아니다.

## 시작 보강이 실제 사용된 경로

pre reason6/all00 → RESET 해제 뒤 post reason1/빈F7·CRC 정상 → READY431poll/5tick(약50ms). signals=`00060707`, boot first=`01000000`, last=`0104a903`.

즉 리셋 중 무응답을 즉시 오류 처리하지 않고 한 번 해제 후 확인하는 경로가 실제로 필요했던 실행이다. pre-only arm01을 채택했다면 이 로그의 응답을 거부했을 것이다. **/WR-low를 실측한 것은 아니다.** 기록 신호는 RESET/DONE/RDY 표본이며 파형이 아니다. 큰 작업 공간의 READY 이후 확보와 pre/post 확인을 함께 바꿨으므로221 실패의 유일한 원인이나 개별 수정의 기여도는 분리되지 않았다. 추가 동일 시작 시험이나 FIT 반복보다 성능 작업으로 돌아간다.

## 남은60fps 병목과 다음 구현

12bin의7481069SPI clock bytes 합계가 전체 로그와 일치한다. ingress3385340(45.25%),E8 802520(10.73%),E9 28388(0.38%),E0 1657100(22.15%),E1 1605166(21.46%),other2555B. source reads/SNES VBlank 횟수는 여전히 미측정이다.

새 D1 encoded payload2851105B는 실제2.625MHz에서 완료당 평균23.81ms, ingress 전체는28.27ms에 해당한다. D1에는 내부 record header와 마지막 미완료 작업이 포함되며 압축 가능한 현재 표현이다. NES의 불변 대역폭 하한이라는 뜻은 아니다. **현재 표현을 그대로 매프레임 보내면서60fps를 달성할 수 있다고 보기는 어렵다.** D0 status396496B를 전부 없애도 순수 전송시간 약1.21초/session이므로 조회만 줄이는 작업으로 목표에 도달하지 못한다.

수신21.89초/계획19.41초/SEAL18.39초로 병목이 여러 구간에 걸쳐 있다. 슬롯 검색 최적화는 유지하고 다음 우선순위는 다음과 같다.

1. 스크롤 시 반복되는 geometry의 D1 표현을 작게 만들고, 가능한 범위의 변경분 전달을 검토한다. 전체 화면을 다시 만드는 양 자체를 줄인다. 기존220/222 실기 스크롤 분포를 비용 기준으로 쓰고, 확보하지 않은 전체 geometry 덤프를 있다고 가정하지 않는다.
2. 원본 좌표와 스크롤을 반영한 map 갱신을 수신·계획과 함께 설계한다. 패턴 재사용이 되어도 맵을 매번 크게 전송하면 병목이 남는다. `mapdirty=6030`은 직전 표시 대비64B block 수이고 실제 inactive-bank 누적 union 전송량은 아니다.
3. 공유SPI와SNES 소비를 합한16.67ms 예산을 먼저 확인하고 최소 경계 검증 후 실제 첫 레벨로 간다. polling-only/cache 증설/시작 진단/FIT 반복으로 회귀하지 않는다.

physical CHR key/row-alt/mask/epoch/활성bank 보호/최종 displayACK를 유지한다. ARM 여유1912B,FPGA252LE/6LAB/9M9K는 다른 자원이다. 저장SRAM은 사용하지 않으며 GBC164·기존 패키지는 유지한다. MMC4/5의 fetch-time 상태와 향후 저장/로드 기능을 훼손하는 무조건 delta 재사용은 금지한다. 같은222/044 재시험이나 추가 영상은 현재 결과 정리에 필요하지 않다.

## 재현과 한계

`tools/analyze_nes_game222.py --archive <probes/nes-game222-hardware01>`는 원본 해시, 필드·단계·bin/전체합·실제 종료 소스를 대조한다. 봉인 후 덮어쓰기를 거부한다. [분석 JSON](../analysis/game222-hardware01-verification.json)에 원시 필드·표본별 수치·소스 해시를 보존했다.

receive bin2193tick과 profile2189tick의40ms 차이는 별도 tick 호출 위치에서 발생 가능한10ms 양자화 누적 차이다. 값을 강제로 일치시키지 않는다. 다른 plan/seal합계는 일치한다. wire에는 별도 서비스/오디오와 parallel aperture DMA가 포함되지 않는다. byte 비율을 실행 시간 비율로 바꾸지 않는다. 정확 영상/host 동기화, 모든 프레임의 실기 출력 속도, 전체 mapper/장기 안정성은 이 결과로 입증되지 않았다.
