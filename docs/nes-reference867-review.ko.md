# sd2snes+ v2.19와 MMC866의 NES 표시 경로 회고

**판정.** 60 FPS를 위해 우선 바꿀 부분은 같은 배경을 기술하고 운반하는 방법이다. sd2snes+는 NES에서 발생한 쓰기를 FPGA가 모아 SNES에 직접 제공한다. MMC866은 원본을 ARM으로 받아 대상 뱅크에 표시할 결과를 계산하고, 그 결과의 범위와 데이터를 다시 발행한다. 이 설계는 raster 예외와 불완전한 전송을 처리하기에 유리하지만, 이전 화면과 거의 같은 장면에도 거래와 수락 비용이 든다. 두 기기의 정확한 체감 속도 차이 중 몇 %가 각 원인인지는 아직 측정되지 않았다.

## 배포본과 소스

첨부 ZIP의 SHA256은 `bb86ee8782181a2daecfc79f79a937fc0e8b9664f4628577f5e7bedf40bdf895`다. 658 조사 때의 릴리스와 ZIP 자체 및 STM32·SNES 렌더러·FPGA 4종이 모두 일치한다. 669가 고정한 소스 파일 다섯 개도 다시 해시 대조했다. 모험도 4 시험 ROM은 mapper 4, PRG 256KiB·CHR-ROM 128KiB다. 공개 소스의 동작 설명은 고정 태그를 기준으로 했다. 배포 비트스트림을 소스에서 다시 합성한 결과나 이 ROM의 sd2snes+ 실기 측정치는 이번 비교에 없다. [태그 소스](https://github.com/ludufre/sd2snes/tree/6867510aba14693543577a87fa161595e1422b42) · [검산 결과](../analysis/reference867-review.json)

| 비교 항목 | sd2snes+ | MMC866 |
|---|---|---|
| 데이터 생산 | FPGA가 nametable 연속 쓰기, OAM·팔레트·CHR 창 상태를 명령화한다. 두 8KiB mailbox를 사용한다. | FPGA 입력을 ARM이 D1으로 수신한다. ARM이 slot·팔레트·목적 뱅크까지 반영한 표시 계획을 만들고 E1으로 발행한다. |
| 준비와 소비 | SNES가 활성 표시 중 mailbox를 최대 512B씩 WRAM으로 DMA한다. main에서 변환하고 NMI에서 준비된 결과를 반영한다. | 수신·준비·선행 DMA도 겹친다. tile 준비 조회, 큐 반환, SEAL 검사와 공개가 세대별로 연결된다. |
| mapper 4의 BG | 8개 1KiB CHR 창과 주사선별 구성을 추적한다. 구성과 사용 평면·상주 상태가 그대로이고 미완료 로드도 없으면 재계산을 생략하는 경로가 있다. | slot 계획은 더 다양한 행·tile 조합을 표현한다. 선택한 BG의 로딩 시 사전 변환과 PSRAM 2B 공급은 이미 반영됐다. |
| 소비가 밀릴 때 | 남은 두 버퍼 안에서 순서대로 소비하고, 복사 중 두 세대 이상 앞서 재사용된 버퍼는 폐기한다. 건너뛴 변경은 FPGA가 모아 다시 보낸다. 파싱한 세대의 ACK와 NMI의 실제 공개는 별도다. | 수신 credit과 최종 표시 ACK를 구분한다. 독립 검사와 DMA 뒤에 표시 이력을 확정한다. |

sd2snes+도 NMI 진입이 늦으면 OAM까지 쓰다가 표시 구간을 침범하지 않도록 이전 화면을 유지한다. 다만 mapper 4에서 화면에 필요한 구성이 둘보다 많으면 주사선 점유가 큰 두 구성을 우선하고 일부 구간은 현재 구성으로 대체할 수 있다. 같은 seq가 두 번 파싱에 실패하면 진행용 ACK를 허용하는 분기도 있다. 이는 정확도와 진행성을 절충한 구체적 사례다. 사용자가 본 깨진 타일의 원인은 해당 장면의 CHR 주소와 실제 출력이 있어야 특정할 수 있다. ## 현재 비용을 실기와 동일 입력에서 각각 확인한 결과

- **실기.** MMC866의 데모 30초는 507장·16.90 FPS이며 MMC855는 504장·16.80 FPS였다. MMC866의 데모 평균 표시 간격은 59.17ms이고 60 FPS 예산은 16.67ms다. 60초 전체의 유효 EA 거래 1,043회로 정규화하면 E8은 96.06회·10.50ms, E0는 32.41회·3.54ms, D1은 5.48ms, E1은 4.22ms였다. 전체 SPI 거래 안에서 잰 시간은 EA당 28.70ms였다. IRQ와 guard·대기를 포함하며 phase 시간과 중첩된다. E8+E0의 14.04ms를 통째로 없애도 그만큼 공개가 앞당겨진다는 뜻은 아니다. 타일이 준비되지 않았거나 VBlank를 기다리는 동안에도 조회한다. [구간과 명령별 계산](../analysis/reference867-review.json)
- **동일 입력 재생.** 35–40초 부근의 2120–2364 원본을 4장 간격으로 뽑아 첫 두 장으로 뱅크를 준비하고 60장을 대조했다. 각 화면을 직전 목표 뱅크와 비교하면 NES nametable 끝 상태에서 달라진 바이트는 총 563개였다. ARM이 최종 생성한 4,096B SNES map에서 달라진 16비트 단어는 총 1,415개였다. 두 위상 모두 map E1만 351거래·69,213B였다. 43장은 변경이 있었고 한 장 최대 47단어였다. 17장은 완성 map이 같았고 map 패킷도 없었다. NT 끝 상태의 차이로 중간 raster나 CHR 변경을 생략할 수는 없다. 네 장 간격의 재생 표본과 실기의 모든 표시 세대는 서로 다른 모집단이다.
- **전송 표현의 상한 시험.** 변경 단어에 `offset16 + value16`, 변경이 있는 화면에 8B 메타데이터와 19B E1 외피를 가정했다. 이 표본에서는 모두 한 패킷에 들어가고, 이전 뱅크에 적용한 60장의 map이 두 위상 모두 원래 4,096B와 일치했다. 예상 map 전송은 43거래·6,821B다. 90.1%는 이 표본의 **map E1 바이트** 절감 가능량이다. 이전 뱅크의 유효 이력과 독립 expected가 있어야 하며, MCU 비교·65816 검사·실제 DMA·cold·STOP·부분 갱신의 비용은 아직 포함하지 않았다. sd2snes+ 전송량이나 새 제품 FPS의 측정치가 아니다.

## 어떻게 방향을 바꿀 것인가

1. **실기 대조의 분모를 먼저 맞춘다.** 같은 보드·모험도 4 ROM·무입력에서 오프닝 [1,30)초와 데모 [30,60)초를 맞춘다. 두 시스템 모두 NES 원본 세대, 실제로 적용한 서로 다른 세대, 반복한 VBlank, 건너뛴 세대와 잘못 그린 장면을 구별한다. 우선 같은 동선의 60Hz 캡처로 스크롤·스프라이트 위치가 갱신된 빈도를 비교할 수 있다. 정지 장면과 깨짐 때문에 영상 차이만으로 원본 세대 수를 단정할 수 없다. upstream에는 decode·skip·늦은 apply를 나눠 세는 선택적 NES_PERF 빌드가 있고 첨부 ZIP에는 별도 perf ROM이 없다. [상류 계측 정의](https://github.com/ludufre/sd2snes/blob/6867510aba14693543577a87fa161595e1422b42/snes/nes/nes_perf.a65#L1-L25) · [빌드 선택](https://github.com/ludufre/sd2snes/blob/6867510aba14693543577a87fa161595e1422b42/snes/nes/Makefile#L29-L36)
2. **무엇을 생략할 수 있는지 검사하는 비용부터 잰다.** ARM이 이미 확정한 SNES 단어만 기록하고 목표 뱅크가 확인된 경우 기존 E1과 큐를 쓰는 후보를 먼저 비용 비교한다. 모든 2,048단어를 매번 재비교하는 비용과 행을 완성할 때 변경을 모으는 비용, receiver가 건너뛴 바이트의 WRAM 손상을 검출하는 비용을 함께 센다. 기존 853의 같은 열 23행 명령과 함께 같은 링크에서 비교한다. 단어 수가 많거나 이력이 무효면 기존 전체 행을 보내고, 부분 수신·STOP 이후에는 공개 이력에서 복구한다. 동일 픽셀·세대·최종 ACK와 두 위상 소요 시간이 모두 검증될 때만 채택한다.
3. **남은 큰 차이는 생산자와 소비자 사이의 왕복이다.** 실제 거래에서 producer가 준비된 시각과 ARM이 처음 관측한 시각을 맞추고, 이미 검증된 표시 명령을 SNES가 직접 읽는 경우 없앨 D1/E1/E8 거래와 새 포트·CDC·소유권 비용을 함께 비교한다. 저장 credit을 먼저 반환하더라도 표시 이력은 최종 ACK에서 확정한다. 671에서 원본 nametable 변환과 소프트웨어 CRC를 65816에 넘긴 실험은 954 한 장에서 행 복원·검사만 88.99ms였다. 그 방식을 반복할 이유는 없다. MMC855 보드는 M9K 56/56, LAB 962/963이고 MMC866 ARM은 Flash가 4B 남는다. 16KiB mailbox를 더하는 안은 기존 저장과 제어 중 무엇을 삭제할지부터 입증해야 한다. [이전 실패 비용](nes-supply671-results.ko.md) · [669의 구조 비교](nes-reference669-plan.ko.md)

이번 회고에서 펌웨어·RTL은 수정하지 않았다. PR169의 master 병합점은 `6e7b13b`이고 실제 MMC866 전달본까지의 로컬 커밋은 `8185096`이다. 새 실기판을 준비할 때는 로컬 전달본의 후속 네 커밋을 master와 먼저 일치시킨다. 검산에는 `audit_nes_reference867.py`에 첨부 ZIP, 보존한 658 소스 디렉터리, 861·866 재생의 temp 디렉터리, 실기 로그 디렉터리, 검증된 MMC866 ZIP, 결과 JSON의 경로를 각각 지정한다.
