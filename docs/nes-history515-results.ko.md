# MMC509 대상 뱅크의 최종 ACK 행 이력 재사용

실기 기준은 MMC509(12.82fps)다. 515는 65816이 생략 바이트의 CRC를 다시 계산하지 않고 이전 표시에서 확정한 행을 재사용하는 후보로, PCB용 ARM·65816 코드와 전체 보드 빌드에 연결했다. 아래 시간은 SMB3 캡처에 대해 실제 바이너리를 실행한 결과다. ARM CPI, SPI·IRQ 도착과 ROM 중재에는 기존 모델을 사용했다. [실기 기준](nes-hardware510-results.ko.md) · [측정 결과](../analysis/history515-verification.json)

## 재사용 조건

65816은 VBlank 최종 ACK를 쓴 직후, 해당 뱅크에서 **이번에 실제 수신한 64행의 비트맵**과 표시 serial 하위 16비트를 보관한다. ARM도 일치하는 최종 표시 ACK만 받아 같은 비트맵을 공개한다. 다음 번 그 뱅크를 쓸 때 행이 비트맵에 있고 ARM의 8B 변경 마스크에서 해당 끝부분이 깨끗하며 기대값이 모두 0이면 전송을 생략한다. 나머지는 기존 전체 행 literal 또는 반복 워드 패킷으로 전송한다. BEGIN은 기존의 32비트 표시 base·serial, epoch, generation과 대상 뱅크를 검사한다.

새 명령 op11에는 부분 DMA 범위와 직전 대상 뱅크 serial을 싣는다. 65816은 자기 행 비트맵과 반전 사본의 해당 비트, 뱅크 공개 상태, serial, 범위·정렬·중복 수신을 검사한다. ACK 뒤 WRAM이 손상될 수 있으므로 생략 구간은 8B당 네 개의 16비트 워드를 읽어 0인지 확인한다. 이력만으로 새 WRAM 손상을 찾아낼 수는 없다. 이전 op10은 거절한다. VRAM map은 각 최종 표시에서 독립 이미지와 대조했으며 실행 중 손상 검사는 재사용하는 WRAM 구간에 적용된다. [ARM·65816 생성기](../tools/nes_history515.py)

905~916의 원래 패킷 경계에서 변경되지 않은 끝부분은 4,800B였다. 바깥쪽부터 연속된 0 그룹은 3,008B, 직전 대상 표시의 행 수신 이력까지 만족하는 부분은 1,856B(37개 패킷)였다. cold 두 화면은 전체 64행을 요구한다. [기존 CRC 후보](nes-trim514-results.ko.md) · [독립 재구성](../tools/analyze_nes_history515.py)

## 동일 일정 비교

시작 3,000,000 master clocks, ARM CPI 2, ROM stride 48·phase 0, 일반 큐 4개와 bulk 슬롯 2개를 고정했다. 후반 간격은 906의 최종 ACK부터 916까지 열 구간이다.

|---|---:|---:|---:|
| 첫 표시까지 (ms) | 225.499 | 208.859 | 208.862 |
| 두 번째 표시 간격 (ms) | 232.962 | 232.256 | 232.256 |
| 후반 10개 간격 합 (ms) | 931.101492 | 915.149093 | 915.145927 |
| 후반 평균 (ms) | 93.110149 | 91.514909 | 91.514593 |
| 후반 최소~최대 (ms) | 67.715~99.848 | 67.701~99.857 | 67.735~100.397 |
| E1 전송 / VRAM DMA (B) | 41,376 / 36,144 | 41,376 / 36,144 | 39,520 / 34,288 |
| E0 조회 횟수 / 전체 SPI (B) | 1,939 / 141,259 | 1,997 / 142,763 | 2,027 / 141,567 |
| ARM 명령 / SysTick | 32,325,082 / 140 | 30,578,482 / 136 | 30,658,753 / 136 |

515와 공통 코드 대조군은 마지막 916을 정확히 같은 clock에 표시했다. 515의 906은 68클록 늦었고 915는 12,398클록(0.577ms) 늦었다. 10구간 평균의 0.317µs 감소는 집계 시작점이 늦어진 결과다.

두 번째 비교에서는 세 구성의 시작을 모두 178,684 master clocks(약 8.32ms) 늦추고 같은 ROM 허용 캘린더를 유지했다. 세 구성에서 12개 최종 ACK와 두 뱅크의 map·RGB를 다시 확인했다.

| 시작 master clock | MMC509 후반 평균 | 공통 코드 후반 평균 | 515 후반 평균 |
|---:|---:|---:|---:|
| 3,000,000 | 93.110149ms | 91.514909ms | 91.514593ms |
| 3,178,684 | 93.108771ms | 93.179171ms | 93.178836ms |

두 번째 시작에서 515의 후반 간격은 원본보다 0.070065ms 길었다. 공통 코드와 비교하면 906의 ACK는 264클록, 916은 336클록 일찍 도착했다. 따라서 10구간 동안 단축된 시간은 총 72클록, 평균 0.335µs다. 두 시작 모두 공통 코드에서 515로 바꿔 추가로 확보한 표시 프레임은 없었다. 실기에 전달할 개선으로 채택하지 않는다.

## 이력과 검사 비용

- **ARM 생성**. 실제 링크한 commit 함수를 같은 12화면의 행 사용 패턴으로 실행했다. 원본 903명령/commit에 비해 515는 1,415~1,529명령으로 평균 559명령 더 사용했다. 이 비용과 zero-run 검사, IRQ·polling은 위 공동 일정에서 모두 실행했다. [ARM 검사](../tools/check_nes_history515_arm.py)
- **65816 공개와 소비**. 두 뱅크의 행 비트맵 16B, 반전 사본 16B, serial 4B를 추가했다. 기존 부분 DMA의 상태·임시 8B를 포함해 MMC509 대비 WRAM 44B다. 최종 ACK 쓰기에서 공개 완료까지 12회 각각 1,104 master clocks(51.40µs)가 걸렸다. 별도 패킷 재생에서 같은 37개 map의 수신 가능→ACK 시간 합은 원본 26.598ms, 514의 CRC 89.746ms, 515는 36.683ms였다. 1,856B를 생략한 SPI 선로 시간은 2.625Mbps에서 5.656ms다. 소비 시간과 선로 시간은 겹치므로 둘을 더해 전체 표시 시간을 추정하지 않는다. [공개·소비 계측](../tools/measure_nes_history515.py)
- **STOP과 손상 검출**. 검사 중·최종 표시 직전 STOP 모두 두 뱅크 공개 플래그를 40 master clocks(1.86µs)에 무효화했다. 실제 STOP 레지스터 읽기부터 취소 ACK까지 각각 1,530 / 1,868클록이었다. stale serial, 이전 명령, 누락된 행, 손상된 이력 비트·반전 사본·WRAM 끝 바이트를 거절하고 이전 표시를 유지했다. 중단 당시 양쪽 WRAM·VRAM과 남은 이력 메모리로 새 실행을 시작해 두 cold map이 각각 64행 모두 복구되는지 확인했다. [65816 거절·복구 시험](../tools/test_nes_history515_guards.py)
- **Flash·RAM·회로**. 원본 / 공통 코드 / 515의 ARM Flash 잔여는 36 / 252 / 64B, 관측 스택 여유는 2,488 / 2,488 / 2,304B다. 세 빌드 모두 data 10,040B, BSS 18,576B다. 515의 65816 본체는 4,785/4,960B로 원본보다 474B 증가했고, 관측 스택 사용은 11→14B였다. Quartus Lite 25.1의 EP4CE15F17C8 전체 배치는 원본과 같은 15,164 LE, 조합 함수 14,172, FF 8,394, RAM 264,816bit, M9K 51개였다. 같은 SDC에서 관련 setup +0.078ns, hold +0.139ns였다.

기본 일정의 396개 패킷을 복원해 원본과 대조했다. 12개 화면의 WRAM·VRAM map 4,096B, RGB와 VBlank 최종 ACK·EA가 일치했다. 같은 보드의 E1 RTL에 일반 패킷 364개를 SPI로 보내 read·ACK까지 대조하고 CRC 오류와 reset을 검사했다. 515 ARM ELF에서 정상 base 복구는 메뉴 반환을 허용했고 program·DONE·busy·token 오류는 안전 반환을 차단했다. 새 실물 메뉴 시험은 수행하지 않았다.

## 재현

[빌드 입력](../cores/nes/REPRODUCING.ko.md)의 MMC509 ARM03, 513 capture04, 512 원본·514 공통 코드 대조군을 사용한다. `nes_history515.py`로 ARM patch와 65816 client를 만든 뒤 `build_nes_mmc479_arm.ps1`로 ARM을 링크한다. 507 보드에 `prepare_nes_transfer512_board.py --variant map`으로 같은 client를 넣고 Quartus Lite 전체 compile과 기존 timing506.tcl을 실행한다. `test_nes_trim514_schedule.py`의 기본 시각과 `--start-clock 3178684`에서 비교한다. 별도 E1 시험에는 `--partial-opcode 11`을 사용한다. 전체 행 복구, STOP, ARM 이력, base-only 복구 시험과 공개 시간 계측 뒤 [분석기](../tools/analyze_nes_history515.py)를 실행한다.

검증 원자료는 작업 공간의 `probes/nes-history515`에 있으며 ARM02와 design03이 최종 쌍이다. 기본 공동 일정은 `nes-history515-joint02`, 추가 일정은 `nes-history515-phase-{original,control,history}01`, 보드는 `nes-history515-fit03`이다. 원본·대조군을 포함한 선택 자료 42개를 `probes/nes-history515/selected-evidence.zip`에 보관하고 각 항목을 다시 읽어 확인했다. SHA-256은 `7dee93a15a3e31fd68912bd458c9c2f6b75b4c32c9ae26bf9aabd545799cb91d`다.

다음은 [511 측정](nes-output511-results.ko.md)에서 후반 평균 11.32ms였던 section 5(HDMA·raw)의 일반 소비와 SEAL 준비 시각을 같은 VBlank 일정에 놓는 일이다. 실제 남은 VBlank 안에 DMA·표시를 끝낼 수 있는 구간을 먼저 식별한다.
