# 960 · 959의 두 번째 DMA 검사를 정적 ROM에서 실행

## 목표

959에서 24B 초과였던 65816 프로그램을 5,120B ROM에 넣고 처음부터 부팅한다. 빈 캐시 두 위상에서 906의 남은 VBlank에 1,920B map을 보내면서 911 공개 전 912 입력 17블록, 912의 496B 선행 DMA와 최종 ACK를 확인한다. 실기 기준은 MMC955다. [959의 동일 SEAL 대조](nes-blank959-results.ko.md)

## 작업내용

부팅 스트림에서 거리 1–16의 2바이트 역참조를 한 바이트로 표현했다. 같은 6,836B 본문의 압축 크기는 4,871→4,802B, 복원·재검사 로더는 209→230B다. 벡터 64B를 합쳐 **5,096/5,120B**로 들어간다. 실행 중 사용하는 WRAM 본문은 959의 기존 소량 DMA 경로와 두 번째 검사를 보존한 후보와 바이트 단위로 같다. 모험도 4의 입력·출력 패킷, ARM SRAM 송신, DMA 서비스에는 이 압축 형식을 사용하지 않는다.

65816 리셋 벡터에서 시작해 복원한 6,836B를 원본과 대조했다. 실제 검증 루프에서 WRAM을 한 바이트 변경하면 상태 0xE1로 진입을 차단했다. 별도 부팅 시험에서 WRAM 본문 진입 시각이 MMC955보다 13.231ms 빨랐다. 아래 연속 일정은 최종 ROM으로 다시 실행한 결과다. 부팅 시험의 절감 시간을 표시 간격이나 ACK에서 추가로 빼지 않았다.

같은 MMC955 ARM과 952 보드의 ROM 허가 일정을 사용했다. 빈 캐시는 각 위상에서 세대 905의 행 캐시를 906으로 넘겼고, RTL이 내놓은 E8 상태를 ARM에 되먹여 E9 송신과 후속 65816 일정을 다시 실행했다. 기존 캐시는 양쪽 ROM을 같은 공급 모델로 처음부터 재생했다.

## 성과

| 지표 | 위상 1 | 위상 2 |
|---|---:|---:|
| 빈 캐시 906 공개 VBlank · MMC955 경로 → 960 | 35 → 34 | 36 → 35 |
| 960의 906 map DMA 첫 쓰기 → 마지막 쓰기 | 227 → 239선 | 240 → 252선 |
| 911 공개 전 912 입력 D2 반환 · 대조군 → 960 | 17 → 17 | 0 → 17 |
| 960의 912 SEAL 전 직전 VBlank DMA | 496B | 496B |
| 빈 캐시 906→912 표시 간격 합 | 14 → 14 | 15 → 14 |
| 빈 캐시 912 최종 ACK 변화 | −16.644ms | −33.644ms |
| 기존 캐시 906→912 표시 간격 합 | 13 → 13 | 13 → 13 |
| 기존 캐시 912 최종 ACK 변화 | +0.0048ms | 0ms |

빈 캐시 대조군은 958에서 906의 RTL 응답을 반영한 MMC955 경로다. 905 공개부터 912 공개까지는 21→20회·22→20회였다. 906 자체가 한 VBlank 먼저 공개되므로 906을 시작점으로 세는 여섯 간격과 차이가 난다. 두 위상 모두 여덟 화면의 RGB·22,512B의 VRAM DMA를 대조했고 906은 255선에서 공개했다. 906의 E8과 일곱 번째 E9의 75B 본문 수락을 RTL로 확인했다. 905의 일부 E8 응답과 다른 세대의 공급 일정에는 모델 차이가 남는다. [위상별 원시각과 검증 결과](../analysis/blank960-results.json)

STOP을 906의 1,920B DMA 선택 직전과 마지막 바이트에 각각 주입했다. 선택 직전에는 전송 0B, 마지막 바이트에서는 진행 중인 1,920B만 완료했다. 두 경우 모두 새 공개·최종 ACK 없이 이전 화면을 보존했다. 잘못된 SEAL 세대도 거절했다. 같은 ARM의 메뉴 종료와 base FPGA 복구는 재생에서 통과했다.

ROM 초기값을 교체해 Quartus Lite 전체 MAP·FIT·ASM·STA를 다시 실행했다. 952와 960 모두 **15,247 LE, 961 LAB, 56 M9K, RAM 320,616비트**다. 전체 최저 여유는 setup +0.579ns, hold +0.162ns, recovery +1.298ns, removal +0.364ns, 최소 펄스폭 +2.632ns로 같았다.

## 후속작업

빈 캐시에서 907은 두 위상 모두 먼저 공개되지만 908 공개는 여전히 VBlank 39·40이다. 65816이 908의 마지막 OBJ 패킷을 읽기 시작하는 시각은 255·256선이고 SEAL 수락은 두 위상 모두 다음 화면 주사의 28선이다. 이때 tile·팔레트·OAM 등 6개 DMA에 1,792B가 남는다. 다음 검증은 마지막 OBJ의 ROM 준비, 첫 유효 E8, 65816 패킷 읽기 사이의 시간을 나란히 비교해 **907→908의 세 간격 중 한 VBlank를 줄일 수 있는지** 확인한다. 기존 캐시 13회와 911 공개 전 입력 17블록을 함께 대조한다. 이번 측정은 60초 실기 FPS에 대한 추정값을 제공하지 않는다.

재현에는 기존 958/959 재생 자료를 사용한다. `tools/nes_blank960.py prepare TEMP` 후 두 위상의 `static`, `credit`, `closed`를 차례대로 실행한다. 각 단계에서 기존 FLOAT 래퍼로 `tools/check_nes_ready958.ps1`을 실행하고 `NES_959_RTL`에는 각각 `960static`, `960credit`, `960closed`, `NES_958_RTL`에는 `closed`, `credit`, `closed`를 지정한다. 기존 캐시는 `control`과 `static`에 `--cache warm`을 준다. `fit`은 952 보드 소스와 새 ROM으로 전체 Quartus를 실행한다. 오류 주입은 `tools/check_nes_blank960.py TEMP --phase N --guard before|after|identity`, 집계는 같은 스크립트에 `TEMP`만 주어 실행한다. 부팅·ARM 메뉴·복구 대조는 각각 `check_nes_longrun694_boot.py`, `check_nes_menu533.py`, `check_nes_transfer512_recovery.py`를 사용한다.
