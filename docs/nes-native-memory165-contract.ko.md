# NES165 CHR 보충의 기존 ROM 읽기 경로 연결

PR107의 [공통 장면·보충 인터페이스](nes-native-frame165-contract.ko.md)에 실제 메모리 공유 연결을 추가했다. 이전 문서의 ‘PSRAM arbiter 미연결’ 상태는 이 구현으로 갱신한다. **실제 코어와 물리 읽기 RTL을 연결한 시뮬레이션까지 완료했으며, 기판 검증·호스트 전송·SNES 표시·165 설치 파일은 아직 없다.** 설치 후보는 사운드와 메뉴 복귀를 확인한164다.

## 구현과 수락 조건

`nes_native_memory165.py`가 기존164 기반 코어와 `nes_native_frame165`를 복사한 뒤 `nes_native_arbiter165`를 삽입한다. 기존 `nes_rom_physical`의 바이트·주소·READ16 동작은 그대로 사용한다. ROM 서비스의 기존 캐시·요청 논리는 바꾸지 않고 관측 출력 `native_core_safe`만 추가한다. CPU/PPU CE를 늘이거나 다른 PSRAM 소유자를 만들지 않는다.

단순히 요청이 없는 클록에는 보충하지 않는다. 다음 조건이 모두 참일 때만 한 바이트를 수락한다.

- 고정 NTSC/MMC3 결선에서 CPU 분주 위치3, PPU 행242 이상260 미만이다. 가시 행과 다음 프레임 준비 구간은 제외한다.
- CPU는 이미 캐시에 있는 상위 ROM을 읽으며, reset·코어 일시정지·DMA·DMC 요청이 없다.
- 기존 ROM 서비스는 진행 중 요청, CPU/PPU 미충족 요청, 선읽기 요청과 오류가 없다.
- 실제 reader가 준비됐고 새 core 요청도 없다. 같은 클록의 core 요청이 항상 우선한다.

CPU 데이터의 실제 사용 위치는 분주11/12다. 보충 응답은 변경하지 않은168MHz/READ16 reader를 전제로7 NES 클록 이내라는 조건을 둔다. 70ns 메모리 모델의 이번 실제 코어와8개 클록 위상 시험에서는 최대5클록이었다. **이 수치는 배치 후 타이밍·아날로그 CDC·모든 매퍼나 클록 모드의 최악 지연 증명이 아니다.** 조건을 변경하면 해당 경계를 다시 검증한다.

## 응답·취소·장면 수명

보충 수락 시 주소와16비트 generation, 소유권을 보관한다. 보충 응답은 게임 ROM 서비스에 전달하지 않는다. 취소되면 읽기를 강제로 끊거나 공유 reader를 reset하지 않고, 응답을 끝까지 기다려 폐기한다. 지연·주소 불일치·backend 오류는 sticky fault로 추가 보충을 막는다. 지연만으로 소유권을 풀지는 않는다. 공통 reset을 사용할 때에는 adapter와 실제 reader를 함께 reset해야 한다.

`fill_idle`은 보충 소유권이 없고 reader가 준비된 상태다. 한 요청만 허용하고 수락된 요청을 끝까지 배출하므로, 이전 보충의 미래 응답이 없다는 의미를 갖는다. 별도 큐가 있는 다른 backend에 그대로 적용하면 안 된다. core 요청과 보충 요청은 각각 ready 계약을 지켜야 한다.

보충 중에는 공통 장면 조회 포트를 보충기가 소유한다. 호스트 조회는 보충 시작/진행 중 차단한다. 보충에는 최대512타일/8192바이트·총262144 NES 클록의 기존 상한을 유지하고, 안전한 수직 공백을 기다릴 수 있도록 이 결선의 단계 대기를65536클록으로 설정했다. 기본 보충 모듈의1024클록 정책은 수정하지 않았다. 이 예산은 속도 보증이 아니다.

바이트는 `generation / tile / lane / kind / data`로 전달한다. 성공 전 데이터는 임시이며 실패 시 폐기한다. 성공 뒤에도 장면 소유권과 generation이 유효해야 한다. **보충 성공은 업로드 ACK나 SNES 게시 성공이 아니다.** 실제 호스트가 받아 둘 저장 공간·역압력·게시/폐기 프로토콜이 다음 구현 대상이다.

## 검증 결과와 한계

선택 실행은 `memory01 / arbiter01 / verify01`이다. [검증 요약](../analysis/native-memory165-verification.json)에 실행 소스·원시 결과의 해시를 기록했다.

| 확인 | 결과 |
| --- | --- |
| 실제 SMB3 CPU/PPU/MMC3 + 기존70ns reader |20프레임의 CPU/PPU 바이트·기한 검사 통과, 기존20개 출력 파일과 동일 |
| 실제 공유 reader에서 받은 CHR |프레임12/14/16/18/20, 각15타일240바이트, 총1200바이트 정확 |
| 받은 CHR + 공통 위치/행/팔레트로 재구성 |5장면286720픽셀이 실제 PPU 출력과 동일 |
| 요청~응답 |실제 코어 최대5 NES 클록, 장면 보충34509~34521클록 |
|8개 클록 위상 경계 시험 |총1352검사; core 우선·금지 구간·보충 응답 분리·취소·공통 reset·메모리 클록 정지/회복·주소/오류 통과 |
| 생성된 부모 `nes_live_joint` |컴파일 통과. 부모 전체 실행·SPI/MCU/SNES 통합 시험은 아님 |

이번 실제 코어 시험은 보충 완료 뒤8192개 필요 비트를 포함한 전체 조회를 다시 덤프한다. 이 진단 조회로 장면 소유 시간이 다음 프레임까지 이어져12 이후 짝수 프레임만 받는다. generation12~16과 실제 frame12/14/16/18/20을 구분했다. **이 시험의 건너뛰기는 제품 FPS 측정이 아니며, 그렇다고60fps 가능성을 증명한 것도 아니다.** 모델의 부팅 표본에는 버튼·첫 레벨 부하가 없다. 기존20프레임 재실행은 메모리 소유권 변경이 CPU/PPU에 영향을 주는지 확인하기 위해 한 번 수행했다.

재현 도구는 `test_nes_native_memory165.py`(실제 코어), `test_nes_native_arbiter165.py`(경계 및 부모 컴파일), `verify_nes_native_memory165.py`(실제 받은 바이트와 이전 픽셀 비교)다. 비공개164 입력·사용자 ROM·승인된 FLOAT 래퍼를 사용한다. ROM·덤프·프레임·라이선스는 공개하지 않는다.

## 다음 구현

1. 같은 generation의 위치정보·행 상태·보충 바이트를 호스트로 전달하고, 완성된 장면만 ACK/게시하도록 연결한다. 시험용 전체8192 재조회는 제품 경로에 넣지 않는다. 보충 실패·역압력·호스트 취소는 이전 화면 유지로 처리한다.
2. 기존 SNES 소비자와 명령 생성에 연결하면서38M9K 픽셀 버퍼를 제거한다. 현재56/56M9K 구성에 추가만 하지 않는다. PC 참조의 전체 이벤트/VRAM 그래프를 FPGA에 복사하지 않는다.
3. 변경 경로의 최소 검사와 실제 자원·타이밍 확인 후 SMB3 첫 레벨 실기로 간다. 같은 부팅·플레인·합성 A/B·044 시험은 변경 없이 반복하지 않는다. 실기에서 화면·사운드가 쓸 만해진 뒤60초 제한과 오류/본체 리셋 로그, 입력 유지 품질을 개선한다.
