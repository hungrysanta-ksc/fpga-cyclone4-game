# NES 1060 실기판

디버그판 또는 배포판 ZIP 하나를 SD 루트에 풀고 같은 드래곤퀘스트 IV 한글판을 선택한다. 기존 SRAM과 강제 저장 슬롯을 유지한 상태에서 L+R+START → SLOT 1 → LOAD STATE로 성 안의 위치가 돌아오는지 확인한다. 같은 슬롯을 한 번 더 불러온 다음 EXIT TO MENU를 실행한다.

1059 디버그 실기 로그는 두 번째 ROM 검사에서 256번째 섹터를 채우고 895,744 / 1,048,576 B에 끝났다. 1060은 128 KiB에 최근 256개 진행 레코드를 보존한다. 여러 차례 LOAD한 로그는 각 섹터의 seq 순으로 읽는다. 디버그 파일은 nes-progress-debug1060.txt, nes-game-last-debug1060.txt, nes-frame-debug1060.bin, nes-stop-debug1060.bin이다. 배포판은 시간 제한 없이 플레이할 수 있으며 1059에서 실기 확인한 파일을 사용한다.

## 1059 실기 계측

| 게임 | 1–30초 표시 FPS (1058 → 1059) | 30–60초 표시 FPS | 55–60초 입력 완료→ACK 중앙값 |
|---|---:|---:|---:|
| 와이와이월드 2 | 25.14 → 26.10 | 21.53 → 19.43 | 46.57 → 51.23 ms |
| 배틀토드 | 15.10 → 14.48 | 9.00 → 8.43 | 79.70 → 96.33 ms |

계측 길이는 29초와 30초다. 각 빌드와 게임당 1회이며 수동 플레이와 퀵로드로 장면 차이가 있다. 배틀토드의 1059 마지막 5초에서는 타일맵 변경 행이 0인 화면이 39개 중 35개였다. 타일 공급과 최종 공개를 같은 저장 지점에서 비교해야 한다.


## 드래곤퀘스트 IV와 배틀토드의 스프라이트 대조

드래곤퀘스트 IV의 첨부 슬롯을 보드와 같은 CPU·PPU·매퍼 RTL에 복원했다. 정지 중에 스프라이트 메모리 256바이트를 독립 포트로 모두 읽고 파일과 대조했다. 아래 방향 입력을 준 뒤에는 각 화면에서 원본 OAM으로 예상한 스프라이트 행과 실제 PPU 패턴 요청, FPGA가 ARM으로 보낼 압축 레코드를 대조했다. 세 화면 각각 288개 행의 위치·우선순위·타일 번호·속성·패턴 행이 모두 일치했다. 이 시험의 끝은 FPGA 출력 레코드다. SNES VRAM에 쓰인 픽셀과 실제 표시 시점은 후속 비교 대상으로 남는다.

배틀토드 원본을 같은 진행 입력으로 실행해 첫 스테이지 두 구간(게임 프레임 2100–2159, 6000–6059)의 OAM을 매 화면 읽었다. 두 구간 모두 한 줄의 최대 스프라이트 수는 8개였고 초과한 화면은 0/60이었다. 실기에서 깨진 순간은 기록에 특정되지 않았다. 1059 실기 후반 표본 39개에서 첫 입력 수신부터 입력 완료까지 중앙값은 13.24 ms, 입력 완료부터 유효 ACK까지는 96.33 ms였다. 두 값은 각각의 중앙값이다.

준비·확인 순서는 prepare_cart_debug1060.py, 디버그 ARM 링크, check_cart_debug1060.py, 단일 FLOAT 좌석에서 test_dq4_castle1060.ps1, check_dq4_objects1060.py, probe_battletoads_oam1060.py, package_cart_debug1060.py다. 1059 링크에서는 256번 기록에서 재현했고 1060 링크에서는 520개 기록과 첨부 배터리·슬롯의 읽기를 검사했다.
