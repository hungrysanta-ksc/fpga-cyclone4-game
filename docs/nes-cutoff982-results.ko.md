# 911의 SEAL 검사와 246선 공개 예산

## 목표

978 returned에서 911의 SEAL 검사를 미리 수행하거나 잔여 DMA를 이전 VBlank에 보내는 것만으로 911을 한 번의 표시 간격에 공개할 수 있는지 확인한다. 981의 두 슬롯 선행 발행에서 909 선행 DMA가 위상 1에서 624→592B로 줄어든 원인도 분리한다.

## 작업내용

같은 65816 ROM과 같은 905–911 패킷으로 두 위상을 부팅부터 Mesen에서 재생했다. 명령 실행 콜백으로 SEAL 검사 함수들의 진입 클록·수직선·수평 클록을 기록했다. 978과 981 두 슬롯 후보는 원래 SEAL·업로드·공개·ACK 클록 및 일곱 화면의 RGB와 대조했다. 별도로 981의 909 token 22 전송만 1,800 마스터 클록 늦추고, 뒤따르는 E1과 E0가 앞 거래와 겹치지 않는 첫 시각으로 이동하는 조건을 재생했다. 65816에는 변경된 E1 도착 시각을 공급한다. E0 응답을 실제 ARM에 되먹이는 연속 실행은 이 대조군의 범위 밖이다.

## 성과

### 911에서 수락 시점으로 옮길 수 있는 작업

| 978에서 실제 실행한 구간 | 위상 1 | 위상 2 | 선행 조건 |
|---|---:|---:|---|
| SEAL 진입 → 의미 검사 시작 | 0.178ms | 0.179ms | 최종 패킷의 세대·뱅크·길이를 확인 |
| 스크롤 검사 시작 → 테이블 검사 시작 | 0.111ms | 0.111ms | 스크롤은 앞의 21B에서 확정. 누적 224줄 및 최종 표시 문맥을 결합해야 함 |
| 테이블 검사 시작 → coverage 검사 시작 | 0.545ms | 0.545ms | 행 수·종료·HDMA 설정·길이를 WRAM에서 독립 검사. 마지막 240B까지 복원돼야 전체 검사가 가능 |
| coverage 시작 → 업로드 준비 | 0.473ms | 0.473ms | 수신 중 만든 뱅크별 기록을 SEAL이 지정한 타일·map 범위와 대조한 후 업로드 허용 |

마지막 240B 패킷을 반환한 뒤 SEAL 패킷을 로드하기까지 CPU에 남은 시간은 **0.187 / 0.035ms**였다. 테이블 검사 전체를 그 사이에 넣으면 SEAL 로드 또는 마지막 패킷의 credit 반환이 밀린다. 앞부분을 수신할 때 검사하려면 어떤 뱅크·범위에 대한 결과인지 보존하고, 뒤에 쓰기가 생기거나 STOP이 발생하면 무효화해야 한다. 최종 필수 범위는 SEAL payload에 들어 있으므로 coverage 검사를 단순 생략할 수 없다.

### DMA까지 포함한 마감

마감을 넉넉하게 잡아 246번 선 끝까지 모두 쓸 수 있다고 계산했다. SEAL 진입은 **240선 h720 / 241선 h500**, 남은 시간은 **0.411 / 0.358ms**였다.

| SEAL 뒤 남긴 DMA | 잔여량 | 위상 1 마감 여유 | 위상 2 마감 여유 |
|---|---:|---:|---:|
| 978 전량. 바이트당 8클록만 계산 | 1,680B | −0.215ms | −0.268ms |
| BG·OBJ 432B를 미리 보낸 경우. 바이트당 8클록 | 1,248B | −0.054ms | −0.107ms |
| raw 192B까지 미리 보낸 경우. 바이트당 8클록 | 1,056B | +0.018ms | −0.036ms |
| 같은 1,056B. 실제 팔레트 DMA 시작 → 공개 시간 적용 | 1,056B | **−0.154ms** | **−0.208ms** |

처음 세 줄은 CPU 검사·DMA 선택·채널 설정·화면 공개 비용을 모두 0으로 놓은 전송 하한이다. 마지막 줄은 실제 다음 VBlank에 측정한 팔레트 512B·OAM 544B의 첫 DMA 시작부터 공개까지 0.565 / 0.565ms를 적용했다. 따라서 624B를 선행 DMA하고 검사를 전부 숨겨도 같은 공개 경로라면 **978의 SEAL 자체를 양쪽에서 추가로 앞당겨야 한다.** 검사 비용까지 그대로 남긴 경우 필요한 선행 시간은 약 1.460 / 1.515ms다. 팔레트 이전의 DMA 설정 비용까지 고려하면 더 필요하다. 981 두 슬롯 후보로도 전량 검사 은폐·624B 선행을 가정한 같은 계산에서 0.005 / 0.047ms 부족했다.

### 909에서 빠진 32B의 원인

위상 1에서 981 후보의 token 22가 마스터 클록 14,278,720에 큐에 도착했다. 65816은 14,279,614에 이 새 패킷을 선택했고, 이미 수락했던 마지막 32B OBJ가 다음 VBlank로 밀렸다. 같은 바이너리와 같은 타일로 token 22만 1,800클록(83.8µs) 늦춰 보니, 65816이 14,279,690(251선)에 32B를 DMA하고 이후 새 패킷을 수락했다. 뒤 E1·E0의 SPI 점유도 각각 1,486·1,265클록 밀어 계산했고 다음 유휴 구간에서 원래 일정에 합류했다. 새 패킷 우선권은 유지했다.

| 909 측정 | 978 기준 | 981 두 슬롯 | token 22 지연 대조군 |
|---|---:|---:|---:|
| 선행 DMA, 위상 1 / 2 | 624 / 624B | 592 / 624B | **624 / 624B** |
| 909 최종 ACK, 위상 1 / 2 (마스터 클록) | 14,630,972 / 14,630,972 | 14,632,132 / 14,630,972 | **14,630,972 / 14,630,972** |
| 911 표시 간격, 위상 1 / 2 | 2 / 2 | 2 / 2 | 2 / 2 |

새 OBJ의 공급 부족이 아니라 새 패킷 도착과 빈 큐 DMA 선택의 순서 때문에 32B를 놓쳤음을 확인했다. 83.8µs는 검증한 지연량으로만 사용한다. ARM에 고정 대기를 추가하지 않았다. 정상 재생의 일곱 화면은 원본 RGB와 일치했고, 지연 대조군에 STOP·불량 SEAL을 각각 주입했을 때 0xE4·0xE0로 종료하며 직전 910 화면이 보존됐다. 이 시험은 911까지의 65816 소비자 재생이므로 912 최종 ACK나 실기 FPS 개선을 주장할 근거가 없다.

## 후속작업

911에서는 마지막 201B·240B section 5 패킷이 ARM에서 확정되는 때와 E1 발행 사이를 계측한다. 첫 201B가 담은 raw 192B를 비활성 VRAM에 미리 보낼 수 있는지와 테이블의 나머지 240B를 더 일찍 수락할 수 있는지를 분리한다. 기존 979의 발행 순서 변경만으로 얻은 결과와 대조하고, 위 마감을 넘길 수 있는 경우만 908 공개·909 선행 624B·910 캡처·912 최종 ACK까지 실제 ARM 연속 일정으로 검증한다. 이 단계의 실기 기준은 MMC966, 개발 기준은 978 returned다.

재현은 `nes_cutoff982.py TEMP PHASE MODE`에서 위상 1·2와 모드 `ref`, `pair`, `defer`를 사용한다. 위상 1의 `defer`에 `--fault bad_seal`과 `--fault stop_decode`를 각각 실행한 뒤 `check_nes_cutoff982.py TEMP analysis/cutoff982-results.json`로 집계한다. [실행 클록·큐 도착·DMA 기록](../analysis/cutoff982-results.json)
