# NES221 실기: 화면 프로그램 READY 대기 실패

사용자는 로딩 중 메뉴로 바로 돌아왔다고 보고했다. 세 TXT 원본을 `probes/nes-game221-hardware01/raw`에 복사하고 해시를 검증했다. [재현 가능한 분석](../analysis/game221-hardware01-verification.json). **실기 시작 실패이며,221 성능 개선 효과는 아직 측정하지 못했다.**

## 확인된 사실

| 단계 | 결과 |
|---|---|
| 게임 ROM 적재·전체 비교 | 393216B 일치, verified=1, verify_error=0 |
| FPGA NES 시작 | START 전송, observer2398→14227968, ROM 오류0 |
| SNES 화면 프로그램 시작 | boot_reason=5(TIMEOUT),44820회 조회,500tick=5초 |
| 준비 상태 | 처음과 끝01000000: 유효 응답이지만 stage/error/flags 모두0 |
| 시작·종료 시 핀 표본 | 0606: RESET 비활성,FPGA DONE/MCU_RDY 활성 |
| 화면 파이프라인 | runtime begin 이전 종료, BEGIN/plan/표시/전송 모두0 |
| 성능 bin | 12×21값 모두0. 처리량·FPS 수치로 해석 불가 |
| 종료·복구 | STOP/base/menu 준비 성공, 사용자 실제 메뉴 복귀 확인 |

DISPLAY_NEXT231440ms→DISPLAY_STOPPED236460ms는5.02초다. 게임60초 제한이 아니라 **SNES 준비 응답을 기다리는5초 분기**로 종료했다. 과거213에서는 서비스/SPI 실패와 시간 초과를 구분할 수 없었지만 이번에는214에서 추가한 boot_reason으로 구분된다. runtime의native_result=2와run_first_error=6은 이 시작 실패의 전파 결과다.

NES 코어 관찰 카운터는 진행했지만 SNES 화면 프로그램의 첫 단계1도 관측되지 않았다. 화면 프로그램 준비 완료3에 도달하지 못했으므로 게임 실행 전체가 정상이라고 할 수 없다. 프로그램 읽기 감지 flags0은 관찰 조건을 만족한 읽기가 없었다는 뜻이며, CPU가 전혀 버스 접근을 하지 않았다는 확정 증거는 아니다. flags7을 필수조건으로 새로 도입하지 않는다(220 정상 시작은flags4).

## 220과 대조한 범위

- 패키지의FPGA SHA256은220/221 모두 `31908516ec18ea04760328245590eb72c969783e84d82619cf1f5b8be6f592e2`. SNES212 프로그램을 포함한 전체 이미지가 같다. 실기에 설치된 전체 이미지 해시는 로그에 없으며 boardID74만으로 이를 증명하지 않는다.
- 실제 선택 ARM의run136, runtime board, boot214, CF86 reset/ownership, ROM START/transfer, menu-return8파일은220과 바이트 동일하다. 소스 동일성은 물리적 리셋 타이밍 동일성의 증명이 아니다.
- linked ARM에서도`native_boot172` 호출보다 앞에 인덱스 초기화·검색 호출이 없다. 실패 시`nes_runtime165_begin`에 들어가지 않는다. 따라서 인덱스 충돌이나 스크롤 계산 부하를 이번 직접 실패 원인으로 볼 근거가 없다.
- 다만 증가한 RUN 스택은 준비 대기 전부터 예약된다. 기존 전체 ARM/IRQ 정적검사의 여유1992B는 통과했지만 실기 high-water 측정이 아니다. 메모리 배치 영향까지 완전히 배제했다는 주장은 하지 않는다.
- 220은431poll/4tick 후0104a903(READY3/SPCA9/flags4),221은44820poll/500tick 후에도01000000이다.213과stage0/flags0 증상이 같지만 동일 원인 여부는 미확정이다.

## 작업 의미와 다음 순서

이번 변경은 **실패를 성능 퇴행으로 오진하지 않도록 시작 경계와 미측정 범위를 확정하는 결과 기록**이다. 신규 펌웨어나 수정 완료 주장은 없다.221 인덱스 및 수신·스크롤 맵을 함께 줄여16.67ms를 확보하는 성능 계획은 유지하되, 먼저 시작을 복구해야 한다.

1. 실제 리셋 해제→host bridge admission→compact ROM/reset-vector 응답→SNES 단계 기록을 하나의 경계로 점검한다. SPI 종료/idle 및SNES write 상태와 시작 허용의 상대 시점도 포함한다.
2.213/214에서 이미 통과한 독립 ROM 부팅·고정 버스 재생을 그대로 반복하지 않는다. 실제 ARM 리셋·START 순서와 연결되지 않은 부분, 증가한 스택의 수명, 물리 이미지 식별 공백을 구분한다. 현재 로그만으로 리셋·버스·상태 감지 중 하나를 원인으로 확정하지 않는다.
3. 재현된 조건에 맞춰 수정하고 첫 레벨 스크롤 실기로 돌아간다. 재현이 안 되면 다음 변경은 이 경계를 구분하는 데 필요한 최소 정보와 함께 설계한다. 대기 시간 확대·무조건 재시도·인덱스 철회·새FIT 반복으로 대신하지 않는다.

같은221/044 재시험이나 추가 영상은 지금 요청하지 않는다. 기존221 배포 archive는 봉인 상태 그대로 두며 시험 안내에는 실패 결과 링크만 추가한다. 저장SRAM/GBC164/기존 패키지 보존. PR121에서 결과를 관리한다.
