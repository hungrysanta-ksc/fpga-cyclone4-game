# 538. MMC533의 951 표시와 952 OBJ 공급

## MMC533에서 기다린 구간

동일한 입력 905–957을 시작 클록 3,000,000과 3,178,684에서 비교했다. 951의 SEAL 수락은 65816이 head를 읽은 시점이다. 952의 시각은 직전 951의 실제 표시(`reveal`)를 0ms로 잡았다. ARM 명령·SysTick·공유 SPI·두 tile bank·65816 DMA를 연결하고 부트 코어 시험에서 기록한 8프레임 ROM 허용표를 반복했다.

| MMC533 관측값 | 위상 1 | 위상 2 |
|---|---:|---:|
| 951 SEAL 수락 → 첫 PPU DMA | 11.216ms | 11.333ms |
| 첫 DMA → 최종 빔 latch | 1.457ms | 1.457ms |
| latch 행 / 수평 master clock | 249 / 88 | 248 / 1,340 |
| 246행 허용 끝을 넘긴 시간 | 약 0.131ms | 약 0.126ms |
| latch 당시 VBlank 잔여 시간 | 약 0.822ms | 약 0.827ms |
| 952 END 함수 진입 | 43.763ms | 43.754ms |
| 마지막 OBJ 계획·END 동시 수락 | 85.996ms | 85.708ms |
| 마지막 OBJ ROM 응답 | 100.635ms | 100.639ms |
| 마지막 OBJ 패킷의 65816 ACK | 102.782ms | 102.789ms |
| SEAL head 읽기 | 104.542ms | 104.486ms |

951의 첫 업로드 VBlank에서는 map 1,088B(3회), tile 400B(2회), compact raw 384B(6회)를 전송했다. map은 수신 주소와 뱅크를 기준으로 분류했다. DMA 시작부터 마지막 바이트까지 합하면 약 0.73ms이고 나머지에는 명령별 설정·서비스·다음 전송 준비가 들어간다. 마지막 DMA 뒤 byte credit은 1,264였지만 팔레트 512B·OAM 544B·표시 갱신을 허용하는 246행 검사를 통과하지 못했다. 다음 VBlank까지 기다려 SEAL 수락부터 표시까지 두 VBlank가 지났다. 잔여 시간은 실제 latch의 행·수평 클록으로 계산한 근사값이다.

952는 첫 BG 계획을 발행한 뒤 OBJ 13개와 3개를 두 E9로 나눠 보냈다. 마지막 3개는 END와 같은 전송에 있었다. END 함수 진입부터 마지막 E9 전송 시작까지 42.077 / 41.798ms가 걸렸다. E8이 새 계획도 받지 않고 소비할 bulk도 제시하지 않은 응답이 각각 91회였다. bulk 응답은 18 / 17회, 새 E9를 받을 수 있다는 응답은 각각 1회였다. 마지막 OBJ를 읽은 뒤에도 65816의 bulk 소비와 SEAL 패킷 발행·수락 시간이 남았다.

## 교체한 동작

- **65816만 변경**한 후보는 SEAL의 독립 검사를 통과한 명령 목록에서 한 VBlank에 넣을 범위를 기다리기 전에 계산한다. 기존과 같은 4,192 예산, 명령당 96의 설정비, raw의 상태별 비용을 적용한다. 묶음의 끝은 기존 길이 임시 변수에 저장한다. 새 blank에서 일반 전송의 채널 모드와 소스 뱅크를 한 번 설정한다. 팔레트·OAM descriptor도 미리 쓰고 실제 PPU 갱신은 기존 빔·STOP 검사 뒤에 실행한다.
- **ARM만 변경**한 후보는 compact OBJ 이외의 레코드를 포함한 버퍼가 8개에 도달한 뒤 compact OBJ가 들어올 때 기존 E8·credit 절차로 발행한다. 첫 BG 즉시 발행과 OBJ만 있는 15개 묶음을 유지한다. 정확히 8개 뒤에 END가 오면 기존 묶음을 닫는다. 실제 ELF에서 혼합·OBJ 단독·BG→OBJ·END·full 형식 경계와 STOP·E8 CRC 오류를 시험했다.
- **결합**은 위의 두 실행 파일을 함께 사용한다. 65816 본체는 4,941→4,949B(여유 11B), 전체 프로그램은 같은 5,120B다. ARM Flash는 212,420→212,440B(여유 552B), BSS는 18,592B다. ARM 단독은 MMC533의 65816을 사용한다.

## 두 시작 위상의 연속 결과

밀집 구간은 951–955의 다섯 표시 간격이다. 마지막 ACK는 화면 957의 절대 시각을 같은 시작 시각의 MMC533과 비교했다. 음수는 단축이다.

| 정책 | 평균 표시 간격(ms), 위상 1 / 2 | 밀집 VBlank 합 | 마지막 ACK 차이(ms) |
|---|---:|---:|---:|
| MMC533 | 103.109 / 103.115 | 31 / 31 | 기준 |
| 65816 예산·descriptor 선행 준비 | 103.127 / 99.789 | 31 / 30 | −33.271 / −66.534 |
| ARM 혼합 묶음 조기 발행 | 106.504 / 109.563 | 32 / 33 | +16.650 / +49.941 |
| 65816·ARM 결합 | 106.531 / 106.530 | 32 / 32 | −16.644 / −16.634 |
| MMC533 ARM · 65816 선행 준비와 raw 서비스 직접 호출 | 99.789 / 99.813 | 30 / 30 | −66.554 / −49.918 |

ARM 변경은 952의 OBJ 묶음을 13+3에서 6+10으로 바꿨다. END 수락은 68.173 / 68.145ms로 빨라졌지만 마지막 OBJ ROM 응답은 117.411 / 117.420ms로 늦어졌다. 같은 160회 읽기에서 마지막 응답을 약 한 프레임 늦게 받아 SEAL head도 120.719 / 120.897ms가 됐다. ARM 변경은 제외한다.

65816만 바꾼 첫 후보는 951에서 위상 2의 마지막 검사를 246행으로 앞당겼다. 위상 1에서는 선행 DMA 후 남은 map이 원본보다 128B 많았고 최종 latch가 247행의 276번째 master clock에 걸렸다. 246행 끝에서 약 0.013ms 차이다. 결합 후보는 두 위상 모두 247행에서 한 번 더 기다렸고, 위상 1의 913에서는 첫 BG도 직전 표시 기준으로 ROM 허용 구간을 한 번 늦게 받았다.

마지막 비교에서는 MMC533 ARM과 246행 검사를 그대로 두고, compact raw DMA 준비 시 서비스 함수를 중간 래퍼 없이 호출했다. 각 저위·상위 plane DMA 전의 STOP 확인과 취소 시 VRAM 증가 모드 복원을 보존한다.

**밀집 구간과 마지막 ACK는 두 위상 모두 단축됐다.** MMC533 ARM에 마지막 65816 후보를 붙인 결과 951은 SEAL 이후 두 VBlank에서 한 VBlank로 줄었다. 남은 map 1,216B·tile 400B·raw 384B를 처리하고 두 위상 모두 246행에서 최종 검사를 통과했다. 이때 246행 끝까지 약 0.012 / 0.024ms가 남았다. 952와 954의 최종 대기는 모두 0회였다. 네 새 정책의 여덟 연속 실행에서 53장 RGB, map과 tile 내용, ROM 읽기 5,616회, VRAM DMA 125,488B, 최종 ACK와 독립 재생을 확인했다.

**실기 전달은 보류한다.** 첫 BG를 요청하는 30개 화면 중 위상 1은 전부 기존 ROM 구간을 지켰다. 위상 2의 913에서는 직전 표시부터 입력 시작까지 0.610→0.778ms, 입력에서 첫 BG 요청까지 32.657→32.871ms가 됐다. 첫 E9 앞의 E1은 두 실행 모두 BEGIN 31B 한 건이었다. 후보 요청은 앞 구간의 마지막 grant보다 0.126ms 늦어 15.716ms를 기다렸다. 직전 912 표시가 이미 약 한 VBlank 당겨져 공통 시작 기준의 실제 grant는 오히려 0.555ms 빨랐지만, 직전 표시 기준으로는 두 번째에서 세 번째 ROM 구간으로 밀렸다. 밀집 구간 952–955는 기존 첫 BG 구간을 지켰다. 951에는 BG 읽기 계획이 없었다.

MMC533 ARM과 raw 서비스 중복 호출을 없앤 538 소비기를 비교 기준으로 보존한다. 위상 2의 913에서 첫 BG 요청이 직전 ROM grant를 0.126ms 놓쳤다. 입력 시작과 BEGIN 후 첫 E9 준비를 앞당긴 뒤 30개 첫 BG 구간, 951의 1-VBlank 표시, 밀집 평균과 957 ACK를 같은 두 위상에서 다시 비교한다. 실기 기준은 MMC533이다.

## 재현과 검사 범위

[65816 생성기](../tools/nes_seal538.py)에 `--early-final`을 준다. 마지막 raw 서비스 비교에는 `--inline-raw-service`를 함께 준다. [ARM 패치·wire 순서 생성기](../tools/prepare_nes_obj538.py)에 MMC533 ELF와 원래 489 plans를 주고 기존 479 빌더로 링크한다. [532 공동 실행기](../tools/test_nes_tile532.py)에서 `--trace-credit --trace-rom`을 켜고 두 시작 시각을 대입한다. 각 실행을 별도 PUSH 재생과 비교하고 [분석기](../tools/analyze_nes_seal538.py)로 집계한다. [측정값과 파일 해시](../analysis/seal538-verification.json)

새 경계에서 [실제 ARM 발행·오류 주입](../tools/check_nes_obj538.py), 기존 ARM 15건, 65816 STOP·새 head·cold·중복·누락 검사 22건을 실행했다. 추가로 두 뱅크의 예산 순회와 최종 표시 직전에 [STOP을 주입](../tools/test_nes_seal538_stop.py)해 STOP 수신 뒤 추가 DMA가 없고, 이전 화면과 identity가 유지되며 새 최종 ACK가 나오지 않는지 검사했다. raw 서비스 변경에는 같은 22건을 반복하고 저위·상위 plane 경계를 포함한 STOP 7건도 실행했다.

최초 65816 빌드는 고정 fill 바이트와 본체 끝이 겹쳐 생성기의 검사가 중단했다. 독립 검사에서 허용하는 단일 명령의 최대 크기 4,096과 설정비 96이 한 묶음의 예산 안에 들어온다는 조건을 사용해 중복 분기를 제거했고, 최종 이미지가 fill 바이트 검사를 통과했다. 초기 실행 중 기준 ARM이 532인 네 건은 중단해 제외했다. 기준 및 65816 단독 결과에는 실기 MMC533의 ARM 해시를 요구한다.
