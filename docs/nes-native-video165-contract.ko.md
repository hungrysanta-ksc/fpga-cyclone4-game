# NES165 유한 C 표시 변환기

[SPI 수신기](nes-native-spi165-contract.ko.md)의 COMMITTED 장면을 SNES용 타일·맵·OAM·CGRAM·HDMA로 바꾸는 C 코드를 추가했다. 기존 PC 참조의 큰 픽셀/VRAM 복사 구조를 그대로 이식하지 않는다. **표시 변환은 C로 구현했지만 MCU 게임 루프, 실기 임시 저장 버스, SNES 소비자 및 FPGA 프레임버퍼 교체는 아직 미연결이다.** 설치 후보164와 사운드·입력·STOP 경로는 그대로다.

## 데이터와 메모리

입력은 기존 `nes_native165`와 NES→SNES 색상 변환표64개다. 실제 수신기의 COMMITTED 상태만 허용한다. BG 셀·행·플레인 예외·raster·물리 CHR를 함께 사용하고, 새 PPU 관측이나 별도 mapper shadow를 만들지 않는다.

출력 후보 `nes_native_video165`는 **15,888바이트**다. BG 패턴은 물리 타일13비트와 저/고 플레인의 각 행 선택48비트를 합친 정확한61비트 키로 식별한다. 해시 충돌에 의존하지 않는다. OBJ는 물리 타일과 행 마스크 키를 사용한다. 키는 한 후보의 슬롯 할당 동안만 사용하며 장면 간 캐시는 아니다.

패턴 데이터는 `stage(ctx, kind, slot, bytes, size)` callback으로16/32바이트씩 전달한다. 이후 후보에는 맵4096바이트, OAM544바이트, CGRAM512바이트, 최대1121바이트 HDMA 표와 최초 행 스크롤 값 등이 남는다. callback은 **표시 중인 VRAM이 아닌 임시 저장소에만** 써야 한다. 일부 패턴을 넘긴 뒤 오류가 나면 해당 후보 전체를 폐기한다. `valid`는 변환 성공이지 SNES 표시 완료가 아니다. callback은 유한 시간 안에 반환해야 하며 실패한 쓰기를 자동 재시도하지 않는다.

초기 구현02는 패턴 전체를 보관해27,662바이트였다. 기존164의 `.data 1048 + .ahbram 8992 + .bss 16324 = 26364`바이트와 수신기18,064바이트를 더하면72,090바이트로64KB SRAM을 초과한다. 그래서03에서 패턴을 외부로 내보내고 키만 보관하도록 변경했다.

현재 단순 합산은 **60,316바이트**, 기존 링커 RAM영역65,424바이트와의 차이는5,108바이트다. 이는 기존 동적 할당·스택·새 저장 버스 코드·정렬을 반영한 링크 결과나 안전 여유가 아니다. ARM 변환 함수 자체의 직접 스택은704바이트, 하위함수·callback·인터럽트 스택은 별도다. **두 출력 후보나 전체 VRAM shadow를 MCU에 동시에 추가하면 안 된다.** SNES WRAM 등의 외부 임시 저장소와 한 후보의 소유권을 연결하고 실제 링크/스택을 검사해야 한다.

## SNES 표현

- BG는 팔레트/실제 셀 내용/column0 fineY 변화에 맞춰 최대32행 묶음으로 다시 구성한다. 저·고 플레인 fineY 예외를 별도로 반영한다. 슬롯0은 투명 패턴, 나머지 BG 패턴 상한은1023개다.
- OBJ는 compact 자료에 보존된 NES 평가 rank 순으로 정렬한다. 같은 rank가 같은 가시행을 점유하면 거부한다. 팔레트 경계를 지나는 fragment는 행 마스크를 나누고 최대128개, 한 SNES 행의 평가 대상은 투명 행까지 포함해32개로 제한한다. OBJ 패턴 상한은128개다. clipping/flip/배경 뒤 우선순위와 실제 평가된 행 마스크를 반영한다.
- 2bpp BG,4bpp OBJ,64×32 타일맵,2팔레트 epoch,mode3 HDMA의 가로/세로 스크롤을 생성한다. mask1e·동일 backdrop 등 기존 표현 범위 밖 장면은 거부한다.
- BG 키/패턴의 슬롯은 후보마다 재할당한다. 이전 장면과 안정적인 슬롯 재사용이나 차분 명령 생성은 이번 C 코드에 포함되지 않는다.

## 실행 검증

선택03은 기존 frame03에서 수집한 **서로 다른 SMB3 frame12와15**를 재사용했다. 기존 공개 자료와 입력 해시를 대조했으며 게임 부팅·RTL 시뮬레이션을 반복하지 않았다.

1. 조회 자료와 이미 확보한 물리 CHR로 내부 레코드를 만들고 기존 C 수신기를 거쳐 COMMITTED 장면을 만들었다. 이 시험의 PREPARED ACK는 harness가 대신하며 SPI 왕복은 이전 검증을 재사용한다.
2. 실제 새 C 코드가 생성한 패턴/맵/OAM/CGRAM/HDMA를 수집했다. harness의 전체 패턴 배열은 PC의 외부 임시 저장소 모델이며 MCU 전역변수가 아니다.
3. PC 시험 도구가 초기 업로드와 장면 간 차분 명령을 조립하고 실제 SNES CPU/DMA/PPU 에뮬레이터로 실행했다. **차분 업로더는 아직 PC 코드**다.
4.114,688개의 가시 픽셀이 기존 NES 코어의 원본 픽셀과 모두 일치했다. 초기5493바이트/6명령, 다음18바이트/2명령이며 두 번째 commit은scanline226의vblank 안이다. 작은 부팅 장면 차이이므로 첫 레벨 부하나 실기 FPS의 근거가 아니다.

각 장면에서 미승인 상태·mask 오류·누락 CHR·중복 예외·중복 평가 rank·callback 실패6종을 거부했고 오류 뒤 다시 정상 변환했다. callback 실패는 추가 호출 없이 반환했다. Cortex-M4/Thumb/Os 오브젝트2216바이트를 컴파일했다. 전체 펌웨어 링크/보드 실행은 하지 않았다.

01은 컴파일러의 오해 가능한 들여쓰기 경고로 중단했고 보존했다.02는 C/SNES 픽셀 일치에 성공했지만 SRAM 합산 초과로 채택하지 않았다.03은 저장 구조 변경 후 C·ARM·SNES 검증을 다시 통과했다. 기존 archive/public pin은 수정하지 않았다.

재현: `tools/test_nes_native_video165.py --scenes <frame03> --out <새 경로> --gcc <host GCC> --arm-bin <ARM bin> --mesen <Mesen>`.

## 다음 연결

1. 실제 MCU RUN 루프의 기존50ms 대기를 단순히 유지하면 직렬 수신 기한을 지킬 수 없다. 수신/표시 작업을 나눠 호출하는 스케줄, CF86·ROM 오류·STOP 정리를 함께 연결한다. 기존60초 카운터를 CPU 연산시간이 늘어난 상태에서 실제60초로 간주하지 않는다.
2. 위 callback의 실기 임시 저장 경로와 SNES 명령/vblank 완료 ACK를 구현한다. 수신 COMMIT, 변환 valid, 업로드 완료, 표시 완료를 구분하고, 실패 후보는 현재 표시를 변경하지 않는다. 단일 후보/외부 staging으로 SRAM을 지킨다.
3. 기존38M9K 프레임버퍼를 제거·교체하고 실제 전체 SRAM 링크·FPGA 자원/타이밍·전송 예산을 확인한다. 현재56/56M9K에 추가만 하지 않는다. 기존 SPI 표본의39.59ms 병목도 여전히 남는다.
4. 변경 경로의 최소 검사 뒤 SMB3 첫 레벨 실기로 간다. 이번 작은 장면18바이트 결과를 일반 게임 화면의 차분 효율로 확대하지 않는다. 같은 부팅/A-B/044 시험을 반복하지 않는다. 사용 가능한 영상·사운드 뒤 장시간 플레이/오류·본체 리셋 로그/DOWN 유지 품질을 진행한다.
