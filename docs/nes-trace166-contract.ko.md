# NES166 — 영상 수신 단계 기록과 초기화 절차 확인

165 실기에서는 사운드·메뉴 복귀가 성공했으나 첫 영상이 완성되지 않았다. 166은 같은 FPGA를 유지하면서 수신 단계와 첫 취소 원인을 남긴다. **영상 수정 완료나 실기 통과가 아니다.**

## 초기화 절차 점검

사용자는 SNES 출력 전 버퍼 정리·초기화 누락 가능성을 제기했다. MCU는 RUN 시작에 수신·변환·출력 상태를 초기화한다. SNES 클라이언트는 화면을 끈 채 메타데이터·이전 표시 여부를 지우고, 첫 프레임은 차이 비교 없이 필요한 모든 영역을 DMA로 보낸다. 완료한 뒤 화면을 켜고 표시 ACK를 보낸다. 그래서 첫 프레임이 오지 않으면 화면은 계속 꺼져 있다.

작업 RAM128KB(두 bank7F 영상 후보·메타데이터·scratch 포함)를 비영 값으로 채운 뒤 실제65816 수신·DMA 코드를 실행했다. 첫 화면61184픽셀이 기존 기준 이미지와 일치했고45개 실제 SNES ACK, COMMIT1회를 확인했다. 무조건 RAM을0으로 지워야만 첫 화면이 나오는 것은 아니다. 이 시험은 WRAM 잔존 데이터 조건이며, 실기 VRAM·전기적 리셋·CDC 전체를 검증한 것은 아니다. 새 증거 없이 대용량 버퍼 전체 clear를 추가하지 않는다.

## 대기 제한 재현

설치165와 같은 fill WAIT131072/total2097152, export total4194304를 사용했다. 유한한140000클록 메모리 grant 대기와 소비 대기에서 fill 오류4가 재현됐다.100클록 간격으로 수신하면 export COMMIT1회,10000클록 간격이면 영상 정보420개 레코드까지 진행 후 취소1이 발생했다. 이는 정상적인 느린 진행도 현재 상한을 넘을 수 있다는 모델 증거다. 실기에서 이 지연이 발생했다는 증거는 아니므로 FPGA 상한을 임의로 바꾸지 않았다.

## 166 변경과 검증

- CRC를 통과하고 의미 검증을 통과한 각 레코드 뒤에 BEGIN/END/ABORT/COMMIT와 첫 취소 이유·당시 정보량을 기록한다. 레코드 수신은 패킷 POP 완료 또는 SNES 표시 완료와 구분한다.
- 48바이트 독립 상태는 다음 BEGIN의 수신 버퍼 초기화와 RUN 작업 공간 해제 후에도 유지된다. 새 실행 시작에는 초기화한다. 토큰·세대 wrap, 한 패킷의 ABORT→BEGIN, 첫 이유 유지, 잘못된 토큰/세대 제외와 기존 runtime10조건을 통과했다. 정상 실제 SNES 연결에서는 BEGIN/END/COMMIT 각1, ABORT0을 확인했다.
- 기존 SPI/CRC 검증·60초 시간 제한·ROM/CF86 검사·STOP·사운드·메뉴 복귀 경로는 유지했다. RUN 중 SD 쓰기, 세이브 SRAM 사용, 새 FPGA 합성·배치는 없다.
- ARM 전체 링크196748바이트. 정적RAM26520, RUN 밖 여유38904, RUN 호출 경로37320+IRQ508 이후 계산상1076바이트가 남는다. 수신 작업 공간33952바이트 수명은 그대로다. 새13개 라이브러리/플랫폼 몸체는 주소 재배치 외에 이전과 동일함을 대조하고 호출 그래프를 다시 검사했다. 실측 스택 최고 사용량은 아니다.
- 실제165 보고서 숫자를 uint32 최댓값으로 넓히고 새17필드를 더한 로그는3649/4096바이트다. 향후 포맷 변경까지 보장하는 것은 아니다.

## 다음 판정

`trace_begins=0`이면 프레임 수집·geometry 허용·리셋/활성화와 첫 전송 경로를 우선 확인한다. BEGIN은 있으나 ABORT가 반복되면 첫 이유와 수신 정보량을 기준으로 경로를 좁힌다. 이유1은 lease/enable/전체 상한의 공통 오류이므로 시간 초과라고 단정하지 않는다. 이유4도 fill 실패 요약이며 세부 fill 오류가 아니다. END 이후 COMMIT이 없으면 PREPARED/승인 절차, COMMIT 이후 native_frames0이면 변환·SNES 전송/표시 ACK를 조사한다. `trace_state`는 마지막으로 정상 수신한 레코드 직후 상태이며 최종 오류 상태와 다를 수 있다. tick은100Hz 부팅 기준이고 전송 경계의 표본이다.

이번 목표는 원인을 실제 SMB3 로그 한 번으로 구분하는 것이다. 화면이 검정이면 촬영·버튼 입력은 필요 없다. 같은165나044 반복 시험은 요청하지 않는다. 이후 확인된 원인만 수정하고 실제 게임 화면·사운드 검증으로 돌아간다.
