# 912의 연속 OBJ 헤더와 첫 plan 공급 예산

## 목표

978에서 912의 연속 OBJ 두 개를 한 패킷에 넣어도 각 뱅크를 독립적으로 검사·반환하면서 VBlank 46 시작 전에 업로드 그룹을 준비할 수 있는지 판단한다. 공개 마감은 같은 VBlank의 246선이다.

## 작업내용

966에 사용한 964 보드의 `nes_direct206` 연결, `nes_plan_spi200`의 E8 스냅샷, `nes_bulk_aperture188`의 반환 로직을 978 ARM의 20B E8 검사와 대조했다. E8은 현재 읽기 뱅크의 descriptor 하나를 전달한다. 일치하는 token의 consume만 읽기 뱅크를 전환한다. 912의 연속 OBJ 경계 여섯 곳 모두 다음 token을 처음 확인한 E8이 이전 token 반환 뒤에 있었다. 첫 패킷 발행을 보류하고 기존 E8 두 번으로 묶음을 만들면 첫 뱅크를 반환할 소비 명령까지 보류된다.

가상의 두 뱅크 스냅샷으로 이 제약을 푼 경우를 계산했다. 한 E8에 두 번째 offset·span·token 8B를 추가하고 두 E1의 46B를 31B로 합친다. 두 token의 본문 읽기·범위 검사·consume은 각각 수행하고 두 번째 consume 뒤에만 패킷 credit을 돌려준다. 첫 token 반환은 두 번째 본문 소비를 기다리지 않는다. 32–38번 OBJ 일곱 개에서 겹치지 않는 인접 쌍을 고르는 전체 21가지 조합을 두 위상에서 평가했다.

- 낙관적 일정은 첫 E9 수락에 모든 타일이 준비되고 E0·E8과 공유 버스 경쟁이 무료라고 가정한다. 1005의 두 슬롯 탐색으로 section별 순서를 유지하는 모든 인터리빙을 비교했다. 두 번째 공통 헤더와 첫 개별 ACK의 관측 구간을 통째로 빼고 새 분기 비용도 0으로 두었다. 계산 끝점은 SEAL 검사 뒤 업로드 진입이다.
- 비용을 포함한 일정은 1004 대조군 발행 순서, 다른 SPI 거래의 점유, E0로 확인한 credit, E8, section 5의 540B와 타일 뱅크 반환을 적용했다. 타일은 관측한 ROM 준비 시각 및 두 token 전의 반환과 후속 생산 시간 중 늦은 시각에 공급한다. 처리 시간은 해당 token의 65816 실측값이며 새 명령의 분기·ARM 조립 비용은 0으로 놓았다. 대조군의 그룹 준비를 실제 재생보다 0.518 / 0.465ms 일찍 예측하므로 후보 간 차이는 일정 추정치다.

## 성과

아래는 VB46 시작에 부족한 시간이다. 각 행은 위상 1과 2에서 같은 조합을 사용했다.

| 일정과 끝점 | 위상 1 | 위상 2 |
|---|---:|---:|
| 기존 헤더, 낙관적 업로드 진입 | 1.223ms | 1.209ms |
| 32+33·35+36·37+38, 가장 이른 낙관적 업로드 진입 | 0.699ms | 0.680ms |
| 기존 헤더, 비용을 포함한 그룹 준비 | 6.008ms | 5.997ms |
| 33+34·37+38, 비용을 포함해 가장 이른 그룹 준비 | 5.796ms | 5.782ms |

최대 세 쌍은 E1 45B와 E8 36B를 절약한다. 비용을 포함한 최선은 두 쌍이다. E0는 49회에서 41회로 줄고 마지막 쌍에서 뒤 token 준비를 약 0.31ms 기다린다. 21가지 모두 업로드 진입부터 VB46 시작을 넘겼다. 978 재생에서 912는 두 위상 모두 VB47 242선에 공개되고 244선에서 최종 ACK됐다. 새 펌웨어나 공개·최종 ACK 개선 실측값은 없다.

1004 원시 기록을 다시 검사했다. 두 위상에서 908은 VB38 245선에 공개되고 909는 624B를 선행 DMA했으며 910 마지막 D2는 기준과 일치했다. 두 위상 여섯 정책의 정상 재생과 잘못된 SEAL·디코드 중 STOP 주입 12건의 결과가 기존 기록과 일치했다. 실제 보드·메뉴 경로는 이번 예산 비교에서 변경하지 않았다.

## 후속작업

978을 유지한다. 세 쌍을 묶는 낙관적 일정에서도 section 5 후반 두 패킷의 payload 전송 시간을 전부 제거했을 때 업로드 진입 시각은 같았다. 두 패킷의 수신 CPU 비용까지 0으로 두어도 4,451 / 4,055클록 부족했다.

다음 계측 대상은 912의 첫 123B E9다. planner 진입부터 발행까지 공유 SPI가 비어 있던 시간은 106,237 / 106,282클록(각각 약 4.95ms)이었다. 이 시간에 ARM이 실제로 어느 BG·OBJ descriptor까지 확정했는지 확인한다. 세 쌍을 가정해 모든 타일의 공급 가능 시각을 15,012 / 14,616클록 앞당겨야 낙관적 업로드 진입이 VB46 시작 전에 온다. 기존 헤더 그대로라면 48,000클록을 앞당겨도 3,331 / 3,043클록 부족했다. 따라서 첫 plan 발행과 함께 수신·SEAL 실행량도 줄일 수 있는지 비교하고, 실제 65816과 STOP 회귀를 통과한 후보만 실기판으로 검토한다.
