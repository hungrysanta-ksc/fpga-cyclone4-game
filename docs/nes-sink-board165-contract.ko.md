# NES165 실제 보드 연결과 자원 한도

PR108의 [패킷 접속부](nes-sink-bridge165-contract.ko.md)를 실제164 보드 최상위 회로에 연결했다. 기존38M9K 프레임버퍼와 구형 SNES 버스 소유자는 제거했다. **기능 시험과 전체 합성은 통과했으나, 실제 Fitter는 논리 용량 초과로 실패했다.** 실기 설치 후보는164이며 새SD 패키지는 없다. [검증 기록](../analysis/sink-board165-verification.json).

## 실제로 연결된 부분

- CPU/PPU/MMC3/APU, ROM 적재·읽기, native 장면 수집·전송, 새 패킷 접속부가 같은 물리 최상위에 들어간다. 최상위 이름 `fxpak_nes_screen137_top`은 기존 이름을 유지한다.
- SPI의 core boot/native, observer, status, sink 네 선택 그룹은 서로 배타적으로 MISO를 구동한다. 예상하지 못한 중복 선택은 핀을 해제한다. 그룹 내부의 기존 boot/native 중재도 유지한다.
- RUN reset/active, SNES 패킷·ACK·버튼, ROM 오류의2단 동기화와 native SPI 오류→STOP을 연결했다. sink 자체 오류는 기존 E0 상태와6001 레지스터에서 관측한다. MCU의 실제 오류 처리·로그 루프 연결은 아직 남았다.
- 기존 패드·DAC·관측 모듈은164 원본 바이트를 보존했다. CPU/PPU CE 속도나 읽기 타이밍을 바꾸지 않았다. SNES 상태 쓰기7000/7001도 유지한다.
- **status73은 E6/version2, observer70은 기존 E5, sinkE0은 F6다.** 옛 주석의 D4를 현재 observer 응답으로 오인하면 안 된다. 구형 E5/version1 화면 클라이언트로 새 버스를 실행하면 안 된다. 새 MCU 펌웨어의 엄격한 식별 검사·RUN 연결은 다음 단계다.
- 실제122핀 배치와 SDC는164와 같다. 카트리지 SRAM은 주소0/OE1/WE1/DATA high-Z 그대로다. 세이브·자동 저장·복구 영역을 영상 메모리로 쓰지 않는다. SNES 내부 WRAM7F와 구분한다.

## RAM 합성 수정

첫 전체 합성에서는 배열13개가 RAM으로 추론되지 않아 레지스터 한도를 넘었다. 그중 큰 저장 배열8개에 대해 읽기 레지스터와 출력 선택을 분리했다. compact의 map/row/object/exception, raster의 row/color, required tile, SPI buffer가 대상이다. required tile의 수집/조회는 소유권에 따라 단일 읽기 주소를 공유하며 기존 연속 쓰기 전달 처리를 유지한다. SPI는 바이트 인덱스 변경 후 동기 읽기가 준비된 값을 다음 전송에 사용한다.

선택본 board03에서8개 모두 `altsyncram`으로 추론된다.6개는 M9K 지정, raster2개는 AUTO다. 이는 합성 결과이며 실제 RAM 배치 승인은 아니다. 기존 공개 RTL을 덮어쓰지 않고 `nes_sink_board165.py`와 `nes_native_ram_board165.py`가 검증된164 입력의 사본을 만든다. 재현하려면 materializer에 `--evidence <164 evidence> --client <sink01> --out <새 ASCII 경로>`를 준다. 준비 결과에 모든 합성 입력 해시를 저장한다.

## 변경 경로 검증

선택 test04/board03:

- 실제 장면 소유권 RTL:9장면,1740검사,7거부 경로 통과.
- 기존 실제 SMB3 기록3개(frame12/mode0, frame15/mode0, frame12/mode2)를 변경된 RAM 회로에 재생했다. 출력 데이터·사건·이전 값이 기존 결과와 바이트 단위로 일치했다.
- SPI 기록1717개를 위상0/3.5ns에서 재생했다. 각47블록/191요청의 전송 기록이 기존 spi04와 같다. SPI 시험 속도2.625MHz이며 외부 IO 타이밍 승인은 아니다.
- 실제 보드 최상위와 주변 회로에서 SPI 식별/중재, 패킷 게시→SNES 읽기→12바이트 ACK, 패드 CDC, ROM/native 오류 STOP, 중복 선택 시 MISO 해제, RUN 종료·재시작, SRAM 비구동을 확인했다.13개 누적 검사와 DAC 클록5593에지 관측. DAC 소리 품질이나 메뉴 복귀 실기 시험은 아니다.
- 마지막 시험의 CPU/적재 생명주기만 stub이다. 실제 전체 CPU/PPU 코어는 별도의 전체 합성·배치 시도에 들어갔다. 이 구분 없이 새게임 부팅 성공으로 쓰면 안 된다.

test01의 생성 stub 빈 포트, test02의 선언 순서, test03의 구형 D4 기대값 오류는 보존했다. 마지막 수정은 실제164 응답 E5와 observer의250kHz 계약을 사용했다. board01 합성 실패, board02 RAM 추론 개선, board03 최종 동일 합성 수치·Fitter 실패도 보존했다. 보고서 검사기의 초기 AUTO RAM 분류 오류도 기능 실패와 구분한다.

## 전체 배치 결과와 다음 순서

| 항목 | board03 결과 |
| --- | ---: |
| 합성 추정 LE | 21,442 |
| 조합 논리 | 16,441 |
| 레지스터 | 8,294 |
| 논리 메모리 비트 | 197,104 |
| 실제/가상 핀 | 122/0 |
| PLL | 1 |
| EP4CE15 LE 한도 | 15,408 |

Fitter170011/171000은 조합 노드16,441개가15,408개보다 많아 배치할 수 없다고 보고했다. 합성 추정LE와 최종 배치LE는 같지 않다. 실제164도 추정16,362→배치14,711이었으므로 이번에는 추정치만 보고 결론 내리지 않고 Fitter를 실행했다. 아직 배선·STA·새 CDC/IO·MTBF 통과, 전체 MCU 링크·중첩 스택, 설치 패키지,60fps는 어느 것도 주장하지 않는다.

지역 조합 논리 비용은 OAMEval5664, compact1359, raster637, SPI exporter494, sink endpoint489다. OAMEval은164에서도5662였으므로 이번 관측 포트가 새로5664개를 만든 것은 아니다. 기존 코어에 남은 여유가 작은 상태에서 새 화면 경로가 추가된 결과다. 단순히1033개만 줄이면 최종 배치가 보장되는 것도 아니다.

1. 가장 큰 OAM의 기존 비동기 읽기·행 복사·쓰기 선택 구조와 compact/raster의 레지스터 비용을 검토한다. 외부 세이브 SRAM, 사운드·입력 삭제, 근거 없는 타이밍 완화로 해결하지 않는다. 실제 비용을 줄이는 변경을 먼저 선택한다.
2. 변경한 OAM/장면 경계와 실제 SMB3 자료만 비교한 뒤 같은 전체 최상위를 다시 합성·배치한다. 무변경 재배치나 전체 부팅 재시험을 반복하지 않는다.
3. 자원이 들어가면 MCU의 실제 수신→변환→SNES ACK에 RUN guard/경과시간/STOP/오디오·입력 서비스를 연결한다. 전체 링크·스택·클라이언트 공간 및 바뀐 타이밍 최소 확인 뒤 SMB3 첫 레벨 실기로 간다.

최소 안정성 확보 후 실기 데이터를 우선한다. 같은 A/B·044 복원·부팅 시험 반복이나 추가 일반 진단 도구 제작을 다음 목표로 삼지 않는다. 화면·사운드가 사용 가능해진 뒤 장시간 플레이/오류·본체 리셋 로그/방향키 유지 순서를 이어간다.
