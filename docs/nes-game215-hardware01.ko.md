# NES215 실기 2회: 동일한 FPGA 오류 응답

사용자는 두 시도 모두 스테이지 선택 진입 시 실패했으며, 성공할 때도 있다는 앞선 추측을 철회했다. **동일 시험판의 간헐적60초 성공을 전제로 삼지 않는다.** 원본6TXT와2MOV는 `probes/nes-game215-hardware01/run1,run2/raw`에 SHA256과 함께 보존했다. [기계 분석](../analysis/game215-hardware01-verification.json).

## 로그 대조

| 항목 | 테스트1 | 테스트2 |
|---|---:|---:|
| 부팅 READY | 약50ms/429poll | 약50ms/429poll |
| DISPLAY 시작→중단 | 10.12초 | 15.66초 |
| 완료 표시 수 | 60회 | 97회 |
| 마지막 표시 generation | 78 | 115 |
| 실패 generation | 79 | 116 |
| phase / reason | 1 FLUSH / 4 FLAGS | 동일 |
| FPGA accepted / ARM expected | 1 / 1 | 1 / 1 |
| 로컬 보류 계획 | 9개/76B | 15개/111B |
| video error | 0 | 13 |
| ROM / receiver / sink / window / STOP 오류 | 모두0 | 모두0 |
| window sent=retired | 1055 | 1687 |

테스트1의60은 **표시 완료 횟수**이며60초를 뜻하지 않는다. 두 경우 모두60초 제한보다 일찍 DISPLAY 오류5/run_first_error4로 끝났다. 매번 geometry COMMIT은 표시 수보다1 많고, 그 다음 프레임은 plan_end=0으로 완료하지 못했다.

두 실행의 최초 실패 응답은20바이트가 완전히 같다.

```text
00 d7 04 80 00 01 00 00 00 00 00 00 00 00 00 00 00 00 00 7f
```

헤더D7/버전4/CRC8=7F가 정상이다. 상태80은 **FPGA fault bit만1**이며 END/retiring/credit은0이다. accepted=1은 ARM 예상과 일치하고 descriptor 없음 영역도0이다. 즉 이번에는 잘못된 E8 응답·CRC·수락 수 불일치가 아니라 FPGA가 보고한 내부 오류를 ARM이 정상적으로 감지했다. 다만 정상 E8 CRC가 **이전에 보낸 E9 요청의 payload/framing까지 무결했다는 증거는 아니다.** accepted는 E9 프레이밍 수락 수이며 타일 실행 완료 수가 아니다.

테스트1은 planner가 끝난 뒤 finish의 flush에서 발견됐다. 테스트2는 OBJ 계획을 내보내다가15개 배치의 자동 flush에서 같은 fault를 발견했다. `nes_resident211_slot`은 하위 emit 실패 시에도 UINT16_MAX를 반환하고 상위 OBJ 경로가 video error13을 붙인다. 따라서13만 보고128개 OBJ 슬롯 부족이 원인이라고 해석하면 안 된다.

## 영상 확인

FFmpeg로 각 영상을 초당2장 추출해 전체 구간을 확인했다. 다음은 영상 자체의 대략적인 시각이며 MCU tick과 정확히 동기화한 값이 아니다.

| 영상 | 관찰 |
|---|---|
| IMG_3704.MOV,15.20초 | 오프닝→약3.5초 플레이어 선택→약7초 월드맵/시작 안내. 안내가 일부 바뀐 뒤 마지막 화면 유지. 약13초 카트리지 메뉴 복귀 |
| IMG_3705.MOV,21.93초 | 로딩 말미→오프닝→약12초 플레이어 선택→약14.5초 월드맵/시작 안내. 해당 화면 유지 후 약20.5초 카트리지 메뉴 복귀 |

**월드맵의 첫 화면은 두 번 모두 실제로 표시됐다.** 이후의 갱신 경로가 중단된 장면이며, 실제 첫 레벨 플레이는 보이지 않는다. 메뉴 복귀는 두 영상 모두 확인했다. 두 번째는 오프닝을 더 오래 지나온 후 같은 장면에서 실패했으므로, 단순히 같은 실행 시간이 지나서 종료됐다는 설명과 맞지 않는다. 버튼을 누른 정확한 시점이나 MCU 오류 발생 프레임은 영상 샘플만으로 확정하지 않는다. CRT 촬영 색 변화는 결함으로 평가하지 않았고 오디오는 이번 분석에서 판정하지 않았다.

## 원인 범위와 다음 작업

정상 부팅 후 FPGA 쪽 계획 처리에 fault가 발생했다는 것까지 확인됐다. SPI endpoint/batch decoder/CHR 읽기·arbiter/lease/bulk/consume 오류가 host fault로 합쳐지므로 **최초 내부 모듈은 아직 알 수 없다.** 두 로그가 같은 fault 계열을 보여도 모든 실행에서 반드시 같은 세부 원인이라고 증명한 것은 아니다.

우선 확인할 가설은 **출력 버퍼가 비거나 ROM 읽기 차례가 오기를 정상적으로 기다리는 시간을 타일 전체 실행 제한에 포함하는지**다. 선택된 `nes_source_tile192`는 tile205에 MAX_CYCLES=1048576을 전달한다. tile205 단독 기본값4096으로 계산하면 틀린다. busy 타이머는 EMIT 대기 등에도 진행하며, 실제 core 우선권·SNES 소비 지연은 기존215 결합 시험에서 모델로 단순화됐다. 이 가설은 현재 소스로 설명 가능한 검증 대상이며 실기 원인 확정은 아니다.

다음에는 선택207의 실제 C/SPI/lease/READ16/bulk 연결에 실물과 같은 ROM 허용 구간·SNES 소비 지연을 주고 **처음 발생한 내부 fault를 잡는다.** 정상적인 대기와 잘못된 요청·실제 읽기 실패를 구분한 뒤 수정해야 한다. 제품 timeout 확대/오류 검사 제거/캐시 비활성화로 우회하지 않는다. 새215 반복 시험은 필요하지 않다.

## 작업 의미

이번 작업은60fps용 변경 타일 출력의 실기 실패를 **E8 응답 검사 여러 후보에서 FPGA 내부 fault로 좁힌 것**이다. 통신 응답 CRC 문제로 접근하거나60초 성공이 섞였다고 가정하지 않는다. 실기 원인을 수정한 뒤 실제 첫 레벨 스크롤 성능 측정으로 돌아간다. 이번 커밋은 결과·영상 관찰·인계이며 새 firmware/FIT/ZIP은 없다. 기존215 archive/저장SRAM/GBC164/배포 파일은 보존한다.
