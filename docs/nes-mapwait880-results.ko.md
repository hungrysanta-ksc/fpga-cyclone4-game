# 880 · 마지막 map credit과 실제 DMA 완료를 구분한 발행 시험

MMC872를 실기 기준으로 두고 무입력 데모의 950에서 65816의 마지막 map 반환, PPU에 쓴 마지막 바이트, 진행 통지, ARM의 첫 유효 E0, 첫 scroll 발행·수락과 화면 공개를 같은 시계로 측정했다.

## ARM에서 식별할 수 있는 시점

기존 MMC872 보드에는 DMA 시작 시각을 알려 주는 플래그가 없다. 65816이 마지막 바이트를 전송한 뒤 `$601D`에 쓰고, FPGA는 유효한 반환 문맥에 큐가 비어 있을 때 E0에 진행 비트 `0x08`을 공개한다. 새 패킷이 수락되거나 ACK·STOP이 발생하면 이 문맥은 사라진다. ARM은 응답 CRC와 발행·반환 카운터, 마지막 패킷 identity를 검증한다. 이 비트는 바이트 수를 담지 않으므로 실제 범위는 DMA 기록으로 확인해야 한다.

878의 성공 일정에서 마지막 1,088B의 DMA 시작은 50729436 / 51085664클록, 마지막 바이트는 50738448 / 51094680클록이었다. 진행 통지는 그보다 576 / 580클록 뒤였다. 이미 첫 scroll이 발행돼 ARM은 해당 map에 대한 진행 비트를 한 번도 받지 못했다. 앞선 192B 두 건은 이전 VBlank에 끝나 있었다.

879 전체 링크에서는 마지막 map이 89 / 93선에 반환됐고 앞선 384B도 아직 남아 있었다. 같은 65816 바이너리에 같은 패킷·후속 간격을 넣어 첫 scroll부터 179,789 / 174,286클록만 늦춘 소비기 대조에서는 1,472B가 두 위상 모두 직전 VBlank 227선에 DMA됐다. 950 공개는 144→143 / 145→144로 한 번씩 빨라졌다. 이 시험에서 정해 준 scroll 시각에는 ARM의 E0 조회 비용이 들어 있지 않다.

## 실제 ARM 후보와 비교 방법

기존 두 페이지 map 발행 조건에서 마지막 map 반환을 확인한 다음, 동일한 전체 E0 응답에서 진행이 보이면 첫 scroll을 발행한다. 진행이 없으면 최대 96회의 drain 호출 후 발행한다. 각 drain은 미반환 패킷이 있으면 기존 제한 안에서 여러 번 상태를 읽을 수 있다. CRC·identity·STOP 오류는 기존처럼 즉시 실패한다. 96회는 진행 비트가 오지 않아도 계속 표시하기 위한 상한이다.

같은 ARM 바이너리의 대조군은 새 호출에 전달된 상한만 1로 바꾸고 첫 전체 반환 검사를 그대로 실행했다. 팔레트 발행에 사용하던 별도의 120회 제한도 그대로 실행했다. 추가 후보에서는 실제 ARM이 다음 입력의 END를 확인했고 현재 화면의 SEAL 반환을 기다리고 있을 때만 기존 128µs 대기를 96µs로 줄였다.

| 950 · 진행 확인 후보의 마스터 클록 | 위상 1 | 위상 2 |
|---|---:|---:|
| 65816 마지막 map 반환 | 50,160,506 | 50,873,874 |
| ARM의 첫 유효 map credit 응답 완료 | 50,164,210 | 50,878,821 |
| 1,472B DMA 시작 | 50,340,286 | 51,055,376 |
| PPU에 쓴 마지막 바이트 | 50,352,448 | 51,067,544 |
| 65816 진행 통지 | 50,353,026 | 51,068,124 |
| 진행 비트가 있는 E0 응답 완료 | 50,357,705 | 51,072,316 |
| 첫 scroll E1 발행 | 50,358,312 | 51,072,923 |

실제 진행 통지는 두 위상에서 마지막 바이트보다 578 / 580클록 뒤였다. 첫 유효 map credit부터 scroll까지는 두 위상 모두 194,102클록(9.04ms)이 걸렸다. 이 사이 E0 조회는 71회, SPI 전송은 1,420B였다. 951 입력이 준비된 시각은 scroll 발행보다 568 / 693클록 뒤여서 이 9ms 동안 951 D1을 받을 수 없었다.

실제 패킷을 같은 65816으로 다시 재생해 WRAM 원본 주소·VRAM 목적 주소·PPU 쓰기 포트·데이터를 바이트별로 기록했다. 두 위상 모두 기존 192+192+1,088B와 새 1,472B가 정확히 일치했다. 새 일정에서는 같은 VBlank에 이어서 64B도 전송했다. 이 검사는 공동 재생의 PPU 버스 관측이며 실기에서 ARM이 보는 값은 E0의 진행 비트다.

## 950에서 얻은 한 VBlank가 끝까지 남는가

| 밀집 데모 · 위상 1 / 2 | MMC872 | 880 같은 링크, credit만 | 880 진행 확인 |
|---|---:|---:|---:|
| 950 표시 간격 | 4 / 4 | 4 / 4 | **3 / 3** |
| 952 표시 간격 | 2 / 2 | 2 / 2 | **2 / 2** |
| 60개 표시 간격 합 | 141 / 141 | 139 / 140 | **139 / 139** |
| 마지막 65816 ACK (클록) | 65,017,306 / 65,380,210 | 64,302,558 / 65,016,962 | **64,302,242 / 64,659,938** |

MMC872 대비 마지막 ACK는 33.294 / 33.536ms 빨라졌다. 이 중 **진행 조회 자체**의 효과는 같은 바이너리 대조에서 구분된다. 위상 1은 950에서 얻은 한 VBlank가 959에서 상쇄되고 960–963에서 다시 변동해 최종적으로 316클록만 빨랐다. 위상 2는 950에서 얻은 이득이 끝까지 유지돼 357,024클록(16.623ms) 빨랐다.

## 부팅부터 실행한 결과와 실기 진입 판정

| 실제 ARM 링크 · 위상 1 / 2 | MMC872 | 진행 확인 | 진행 확인 + END 뒤 96µs |
|---|---:|---:|---:|
| 오프닝 703 공개 VBlank | 59 / 59 | 60 / 60 | 60 / 60 |
| 오프닝 759 공개 VBlank | 176 / 176 | 173 / 174 | 175 / 174 |
| 전환 48개 간격 합 | 119 / 119 | 121 / 122 | 121 / 121 |
| 950 표시 간격 | 4 / 4 | 3 / 3 | 3 / 3 |
| 952 공개 VBlank | 148 / 149 | 146 / 148 | 146 / 147 |
| 밀집 데모 60개 간격 합 | 141 / 141 | 139 / 139 | **139 / 138** |
| 마지막 65816 ACK (클록) | 65,017,306 / 65,380,210 | 64,302,242 / 64,659,938 | **64,302,558 / 64,303,112** |

96µs 결합 후보의 마지막 ACK는 MMC872보다 **33.279 / 50.151ms** 일찍 도착했다. 진행 확인 단독과 비교하면 위상 1은 316클록 늦었고 위상 2는 356,826클록 빨랐다. 두 후보 모두 952를 241선에 공개하고 이전 최종 ACK → EA → 재무장 → 새 COMMIT의 순서를 지켰다.

단순 반복 구현은 Flash 한도를 48B 초과했다. 기존 팔레트 대기와 체크된 drain 함수를 공유하고 raster 복원 함수를 인라인화한 뒤에는 진행 확인 단독이 212,936B, END 결합이 212,960B로 212,992B 한도에 들어갔다. 보드 RTL과 65816 이미지는 MMC872 것을 사용했다. 보드 RTL의 진행 통지·E0 스냅숏·경합·STOP·잘못된 ACK 시험은 Questa의 두 버스 시작 위상에서 각각 22개 상태 조회를 통과했다.

오프닝 703과 전환 마감 때문에 실기 비교 기준은 MMC872를 유지한다. 진행 대기를 켜고 끈 같은 링크에서 오프닝 전체의 SPI 거래 8,366 / 8,422건과 모든 공개 시각(프레임·선)은 일치했다. 오프닝은 두 위상에서 각각 내부 세대 906과 909의 SEAL 수락이 처음 늦어진 경로부터 점검한다.

전환은 두 위상 모두 941에서 SPI 일정이 처음 갈라졌다. 같은 바이너리에서 credit만 확인하면 SEAL은 VBlank 117의 151선에 수락되고 118에 공개됐다. 진행 대기를 켜면 첫 credit 뒤 추가 E0 95회가 전부 진행 비트 없이 끝나고 SEAL은 VBlank 118의 83 / 82선, 공개는 119가 됐다. 전환 전체에서 진행 대기의 순비용은 양쪽 모두 1 VBlank였다.

941은 마지막 credit 전에 이미 1,472B를 선행 전송했지만 950은 그때까지 선행 전송이 0B였다. ARM이 이 시점까지 받은 진행 비트는 두 세대 모두 0회였다. 발행한 패킷에는 차이가 있다. 941의 map은 연속된 두 페이지의 일반 패킷 16개였고, 950에는 추가 64B 범위와 고정값 압축 패킷 두 개가 있었다. 다음 후보는 이처럼 ARM이 이미 아는 map 범위와 남은 출력량으로 기다릴 대상을 좁히고, 941·950과 나머지 전체 구간에서 효과를 구분한다.

## 재현

1. 879 전체 ARM 소스에 `prepare_nes_mapwait880.py BASE/src PATCH`를 적용하고 기존 `build_nes_mmc479_arm.ps1`로 링크한다. END 대기 결합 후보에는 `--post-end`를 추가한다. 각 작업 디렉터리의 `client02`에는 원래 65816 바이너리를 둔다.
2. `replay_nes_mapwait880.py TEMP PHASE WORK CLIP`로 오프닝·전환·밀집을 각각 부팅하고 두 시작 위상을 재생한다. 같은 바이너리 대조는 밀집에서 `--credit-only`, END 결합은 `replay_nes_table877.py TEMP PHASE WORK 880-end CLIP`을 사용한다.
3. `test_nes_mapwait880.py TEMP PHASE`와 `--held`로 879의 소비기 단독 대조를 실행한다. `--audit 878-once`와 `--audit 880-progress`는 950에서 빈 큐일 때 발생한 PPU DMA의 주소·쓰기 포트·데이터를 바이트 단위로 기록한다.
4. 기존 Starter FLOAT 래퍼에서 `check_nes_progress680_rtl.py`에 MMC872 보드 소스를 지정한다. 실험의 10개 ARM scroll 응답 조건은 `guard_nes_scroll874.py SRC OUT --progress-reads 96`으로 확인한다. 입력·FINISH·메뉴·65816 복구 검사는 879와 같은 도구를 각 최종 링크와 실제 생성한 패킷에 적용한다. `check_nes_mapwait880.py TEMP analysis/mapwait880-results.json`으로 집계한다.
