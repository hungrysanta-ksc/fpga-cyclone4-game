# MMC690 실기 두 실행: 소폭 개선과 첫 표시 전 시간 초과

1차는 실행 실패·메뉴 복귀 성공, 2차는 실행·메뉴 복귀 성공이다. 사용자는 프레임 차이를 거의 느끼지 못했다. 성공 실행의 5–55초 완료 표시는 MMC666의977→990회, 평균19.54→19.80fps(+1.33%)다. 초반의 작은 증가와 후반의 거의 동일한 결과는 이 체감과 부합한다. 실패 실행은 성능 집계에서 제외했다.

## 성공 실행의 구간 비교

| 완료 표시 구간 | MMC666 | MMC690 | 차이 |
|---|---:|---:|---:|
| 5–40초 | 687회 / 19.63fps | 699회 / 19.97fps | +12회 / +1.75% |
| 40–55초 | 290회 / 19.33fps | 291회 / 19.40fps | +1회 / +0.34% |
| 5–55초 | 977회 / 19.54fps | 990회 / 19.80fps | +13회 / +1.33% |
| 전체 실행 | 1221회 / 60.32초 / 20.24fps | 1250회 / 60.35초 / 20.71fps | 시작·마지막5초 포함, 주 비교에서 제외 |

5–40초·40–55초는 ARM이 최종 표시 완료를 확인한 카운터다. 작업량은 별도의 프레임 시작 기준 bin이므로 구간 경계가 같다는 이유로 개별 표시와 일대일 대응시키지 않는다.

| DWT 단계 평균(ms/완료 표시) | MMC666 | MMC690 | 차이 |
|---|---:|---:|---:|
| 수신 | 10.44 | 10.64 | +0.21 |
| 계획·공급 | 11.34 | 11.25 | −0.09 |
| 출력·최종 ACK | 26.84 | 25.56 | −1.28 |

출력·최종 ACK가 여전히 가장 크다. 같은 출력 단계의 시작 bin 평균은 초반28.98→27.68ms, 후반30.62→30.65ms로 후반 개선이 거의 없다. 위상에는 IRQ·조회·대기가 포함되고 중첩 SPI 카운터를 다시 더하지 않는다. 로그만으로 실제 DMA와 마지막 VBlank를 나눌 수 없다.

화면당 map 변경량은 초반−24.30%·후반−7.31%, OBJ 처리량은 +10.56%·+46.51%다. BG는 +0.13%·−1.20%이고 E1 전송량은 −12.37%·−3.71%다. 작업량이 달라 1.33% 전부를 구현의 가속으로 설명하거나 후반 OBJ 증가만으로 더 큰 가속률을 추정하지 않는다. 동일 입력/장면으로 동기화한 실기가 아니며 반복 표본도 부족하다.

## 1차 실패의 경계

| 항목 | 1차 실패 | 2차 성공 |
|---|---|---|
| 적재·readback | 393216B, 검증 성공 | 동일 |
| START·reset 해제 후 빈 큐 | 정상 F7 응답 | 동일 |
| 첫 준비 응답 | 01400500 | 01400500 |
| 마지막 준비 응답 | 01580500, stage0 | 01fca903, stage3 |
| 준비 대기 | 44241회, 5000ms timeout | 3010회, 340ms |
| native 전송·표시 | 모두0 | 1250표시 |
| STOP·base·메뉴 | 정상, 종료 후3280ms에 MENU_PREPARED | 정상, 사용자 복귀 확인 |

MMC551과 MMC639의 실패도 적재 뒤 stage0에서5초 준비 timeout이었다. 이전 마지막 응답은01580000이고 이번은01580500이므로 바이트까지 같은 실패는 아니다. 이번05는 `spc_init_status_valid=0`이다. 선택 펌웨어는 A9 또는 E1–E5만 유효한 SPC 결과로 인정하므로05를 오디오 초기화 오류 코드로 해석하지 않는다.

현재 근거는 첫 표시 전 부팅 준비 경계로 범위를 좁힌다. SNES의 첫 fetch·WRAM 복원·준비 상태 공개 중 어느 지점인지, E0/queue 변경이나 좁은 setup 여유가 원인인지는 확정할 수 없다. 이번 두 번에서 한 번 실패한 것을 장기 실패율50%로 추정하지 않는다. 실패 DWT는 `cost_sampled=0`으로 무효화되어 이전 실행 비용이 섞이지 않았다. 근거 없는 재시도/지연/STA 제약 완화는 적용하지 않았다.

## 정상 실행의 종료와 회복

입력 COMMIT1251회, 최종 표시·EA1250회이며 마지막 표시는59.96초다. 마지막 generation1288의 SEAL 한 개는 미반환이므로 표시 수에 넣지 않았다. runtime 최초 결과1은60초 DEADLINE이다. window_error2는 guard 거부, receiver_error21은 D0 전송 거부 또는 상태 검사 실패 경로에 해당한다. 마지막 PC/응답이 없어21의 정확한 분기를 단정하지 않으며 중간 CRC 고장으로 분류하지 않는다. 기록된 CRC 오류·전송 중단·ROM 오류·plan 오류는0이다.

capture 이력에는 REJECT→RECOVERY 두 쌍과 마지막 REJECT가 있다. 기록된 collector 오류는 모두0이며 마지막 REJECT의 벽시계 시각과 뒤의 회복은 이 로그에서 확인되지 않는다. 따라서 전체 캡처 무손실이나 모든 회복 완료를 주장하지 않는다. STOP·base 복구·메뉴 준비와 사용자 메뉴 복귀는 두 실행 모두 확인됐다.

## 다음 판단

MMC690은 실행 가능한 새 측정 표본이며, MMC666을 대조군으로 보존한다. 추가 구현 전 출력·최종 ACK25.56ms 중 마지막 확정 데이터의 발행·65816 수락·DMA·VBlank를 같은 map/OBJ 작업량과 두 시작 위상으로 나눈다. 후반 FPS는 사실상 그대로이므로 초반 평균만으로 후보를 채택하지 않는다.

부팅 실패는 별도 안정성 항목으로 유지한다. 551/639/690의 첫 fetch·WRAM 복원·준비 상태 쓰기 경계를 선택 소스와 대조하되, 특정 결함이나 재현이 확인되기 전 대기 연장·자동 재시도로 덮지 않는다. 자연 재발 로그는 계속 보존한다. 이번에는 제품 코드·RTL·설치본을 변경하거나 변경 없는 FIT/시뮬레이션을 반복하지 않았다.
