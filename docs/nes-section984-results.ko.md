# 911의 raw·HDMA 441B 묶음 실측

## 목표

983에서 구성한 75B 표현을 978의 전체 링크에 연결해, 911 표시를 직전 VBlank로 옮길 수 있는지 확인했다. 실기 기준은 MMC966이다.

## 작업내용

ARM은 section 5의 1121 위치에서 raw 세 평면의 64B 반복, 테이블 세 개의 길이 21B, 각 테이블의 60B 패딩을 확인한다. 모두 맞으면 길이·대표 단어·테이블 본문을 한 E1에 담고, 어긋나면 원래의 201B·240B를 보낸다. 호스트에서 같은 C 판정 함수에 raw 바이트 192개, 패딩 바이트 180개, 길이 필드 3개를 각각 다르게 넣어 375번 모두 원본 경로 선택을 확인했다.

65816은 수신 길이·목적지·세 테이블 길이를 검증한 뒤 기존 범위 검사에 원래 길이 441B를 등록한다. 각 구간에 값을 쓰고 실제 WRAM을 다시 읽어 송신 측 값과 대조하며 최대 64B마다 STOP을 확인한다. 기존 SEAL에서 전체 의미 검사와 공개를 처리한다.

905–912를 두 시작 위상에서 전체 링크한 ARM과 Mesen 65816으로 부팅부터 재생했다. 원래 978, 새 수신 ROM에 978 ARM이 원본 두 패킷을 보내는 대조군, 새 수신 ROM에 압축 ARM을 연결한 후보를 비교했다. 수신 ROM은 보드 한도를 넘어서 시뮬레이터의 저장 공간을 확장했다. SPI·ROM 경합은 기존 공동 재생 모델을 사용했다.

위상 1과 2 순이다. SPI에서 약 1.223ms를 절약했지만 같은 수신 ROM에서 복원·검사·반환이 약 3.576ms 더 걸렸다. SPI와 CPU는 겹쳐 실행되므로 두 값의 차를 전체 표시 시간으로 환산할 수 없다. 두 위상 모두 905–912 전체에서 압축 조건이 성립했다. 위상 1은 906 공개부터 한 VBlank 늦었다. 위상 2는 첫 공개부터 한 VBlank, 906 공개부터 두 VBlank 늦었다. 이후 여섯 간격 합만 보면 이 누적 차이가 드러나지 않는다.

두 위상의 RGB 여덟 장, map 데이터와 plan 레코드가 각각 978과 일치했다. 위상 1에서는 패킷 반환 때 905–911의 WRAM 441B를 세대별 원본과 직접 대조했다. 911 첫 64B 후 STOP은 0xE4, 첫 평면의 WRAM 손상은 해당 압축 명령에서 0xE0, 잘못된 SEAL도 0xE0로 종료했다. 세 경우 모두 910 화면을 보존했다. 링크한 ARM 메뉴 복귀의 정상 분기와 실패 분기도 대조했다. 처음 사용한 관측기는 905 첫 공개 전부터 표시 뱅크가 다르다고 가정해 중단됐다. 첫 공개 이후에 이 조건을 적용한 뒤 전체 검사를 다시 통과했다.

ARM Flash는 213,164 / 212,992B, 수신 ROM은 로더 포함 5,288 / 5,056B다. 현 보드 한도를 각각 172B·232B 초과해 실기 전달 후보에서 제외했다. [두 위상 계측·오류 주입·전체 링크 결과](../analysis/section984-results.json)

## 후속작업

978의 빠른 리터럴 복사 경로를 유지한다. 다음 후보에서는 마지막 section 5 반환 이전에 실제로 확정된 타일을 어느 VBlank에 DMA할 수 있는지, 그때 팔레트·OAM과 SEAL에 몇 클록이 남는지 고정 도착 시각으로 먼저 재생한다. 982에서 624B를 미리 보내도 전체 검사를 유지하면 1.460 / 1.515ms가 더 필요했다. 이 예산과 909의 624B를 두 위상에서 만족할 가능성이 보일 때 ARM 발행 순서를 바꾼다.

재현은 `nes_section984.py prepare TEMP`, 생성된 link의 `build_nes_trial577.ps1` 전체 링크, `nes_section984.py run TEMP --phase 1|2` 순이다. 대조군은 같은 실행에 `--control`을 붙인다. `check_nes_section984.py TEMP 1 normal|partial|damage|seal`과 `analyze_nes_section984.py TEMP analysis/section984-results.json`으로 최종 결과를 확인한다.
