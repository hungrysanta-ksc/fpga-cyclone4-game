# NES173 실기 — 초기 갱신 비용과 이후 정지 확인

173은172와 같은 증상이라는 사용자 보고다. 로그는 **RUN 시작 후5.79초까지16회 표시 ACK를 완료하고, 남은 약54.21초 동안 추가 완료 없이 정상60초 한도로 종료**했음을 보여준다. 화면 정지와 초기 갱신 지연은 모두 남아 있다. 이번 시간 측정 목적은 달성했으며 새 펌웨어·FPGA·시험 패키지는 만들지 않았다.

## 결과와172 비교

| 항목 | 172 | 173 |
| --- | --- | --- |
| BEGIN / END / COMMIT / 표시 ACK | 각14 | 각16 |
| 마지막 generation | 27 | 30 |
| 수신 ABORT | 0 | 0 |
| ROM·sink·video 오류 | 0 | 0 |
| 종료 사유 | DEADLINE 1 | DEADLINE 1 |
| 표시 구간 | 60050ms | 60060ms |

ROM393216바이트 적재·비교 일치, 준비 단계3, SPC A9/unmute1이다. STOP·기본 FPGA 복구·메뉴 준비가 정상이며 마지막 진행 기록은295750ms의 MENU_PREPARED다. 새 영상은 없고 실제 화면·소리는 사용자 “172와 동일” 보고에 따른다. 종료 로그의 `run_passed=1`을 정상 게임 플레이나 연속 화면 성공으로 해석하지 않는다.

16회로 늘었다는 사실은 속도 개선의 증거가 아니다. 173은 시간 측정만 바꾸었고172에는 같은 시간값이 없다. 또한 정지를 정확히generation27에 고정된 사건으로 취급하지 않는다. 이번 마지막 값은30이며 모델의frame24와도 직접 대응하지 않는다.

## 시간 측정

| 측정 단계 |16회 누적 | 완료1회당 평균 |
| --- | --- | --- |
| 변환·패턴 staging 전송·BEGIN/guard |910ms | 약56.9ms |
| 테이블/SEAL 전송·SNES 처리·표시 ACK/guard |2340ms | 약146.3ms |
| 위 두 단계 합 |3250ms | 약203.1ms |

두 직렬 단계만 회당 약203ms다. 수신·생산 대기를 제외해도60fps의 약16.7ms 예산과 큰 차이가 있다. **프레임 거부로 인한 정지만 고쳐서는 정상 속도가 되지 않는다.** 수치는10ms 시계의 누적값과 실제 완료 횟수로 산출했으며 모든 갱신의 지연이 같다는 뜻은 아니다.

RUN 시작→마지막 ACK5.79초 동안16회이므로 구간 평균은 약2.76회 ACK/초다. 첫 표시 전 대기와 같은 그림 재표시 가능성이 포함되므로 TV의 실제 FPS나 게임 내부 실행 속도로 명명하지 않는다. 개별 완료 간격도 이 로그에는 없다.

`profile_receive_ticks=5417`은54.17초다. 정지 이후 상태 폴링·후보 대기가 포함된 전체 실행 누적값으로,16장 그래픽을 받는 데54초 걸렸다는 뜻이 아니다. 단계 합은57.42초이며60초와의 차이2.58초는 단계 밖 guard/루프·계측 경계·미완료 호출 등이 포함될 수 있다. 그 차이를 특정 전송 단계나 SNES 시간으로 임의 배정하지 않는다. 정지 전 수신시간을 전체 수신값에서54.21초 빼서 산출할 수도 없다.

## 어디를 줄일 것인가

배포한 `nes_native_sink165.c`의 seal은 매 후보마다 map4096+CGRAM512+OAM544=**5152바이트**에 HDMA를 더해240바이트 단위로 전송하고 각 패킷의 ACK를 기다린다. HDMA와 마지막 SEAL까지 최소26패킷이며 패턴 전송은 별도다. 이 소스상의 동작은 로그의2.34초에 포함된다.

따라서2.34초를 순수 SNES PPU DMA 또는 vblank 대기만의 비용이라고 단정하지 않는다. 이미 SNES 측 비교·차이 DMA가 있으므로 같은 최적화를 다시 추가하기보다 **MCU→SNES 전체 테이블 반복 전송과 패킷별 왕복**, 변환 단계의 패턴별 전송부터 줄일 필요가 있다. 제한된 변경분 전달·묶음 전송의 구현 가능성을 검토하되 MCU에 두 프레임 전체를 추가 저장하거나 세이브 SRAM을 쓰지 않는다. 안전 확인·STOP/입력/사운드 서비스와 ACK 소유권도 유지한다.

## 정지 원인과 다음 작업

BEGIN/END/COMMIT 모두16이며 이후 새 BEGIN 수신이 없다. 받은 ABORT도0이다. 전송 전 허용 조건 탈락이나 release/DRAIN/fill 진행 정지는 여전히 구분되지 않는다. 이전 모델에서 확인한 서로 다른 타일의 low/high plane 읽기는 구체적인 원인 후보지만 이번 실기 로그가 그 오류를 직접 기록하지는 않는다. `receiver_error=21`은 deadline으로 전송을 거절한 뒤 남은 후속 값이며 새 SPI 손상 증거가 아니다.

1. 재현된 타일 간 plane/행 조합을 보존하는 제한된 표현을 구현한다. high 주소만 사용하거나 거부 조건만 완화하지 않는다. 필요한 변경 경계만 검증한 뒤 SMB3로 확인한다.
2. 동시에 비용이 큰 seal 경로의 전체 테이블 반복 전송·패킷 ACK 왕복과 패턴별 전송 구조를 검토한다. 이번 측정만으로 병목을 순수 DMA·SPI·C 변환 중 하나로 확정하지 않는다.
3. 동일173·044·부팅/A-B·무변경 FIT나 범용 관측 확장을 반복하지 않는다. 다음 실기는 표현/전송을 실제로 바꾼 후보로 진행한다. 약60fps 연속 AV→장기 플레이/오류·본체 리셋 로그→입력 유지 순서와 GBC·164·세이브 보호를 유지한다.
