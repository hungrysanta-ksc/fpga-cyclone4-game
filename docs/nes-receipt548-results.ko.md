# NES 548 · 반복 패킷 수신 증명과 뱅크별 행 재사용

547은 957의 마지막 대기를 두 위상에서 없앴지만, warm 화면의 384B 이력 비교에 평균 1.93ms를 사용했다. 548은 수신 시 확인한 값과 목적지 범위를 보존해 SEAL에서 원본 행을 다시 읽는 작업을 없앴다. 실기 기준은 MMC540이며 시간 비교에는 동일한 [5,40)·[40,55) 집계 ARM을 사용한다. [547 측정](nes-history547-results.ko.md)

## 확정 위치와 비용

일반값 후보는 두 원본 바이트가 같은 section 5의 op4·op5를 기존 고정 source DMA로 복원한다. 마지막 조각과 STOP 검사를 통과한 **한 패킷**의 시작과 끝이 행 전체를 포함할 때만 해당 행을 기록한다. 행 끝을 E라 하면 조건은 `패킷 시작 + 64 ≤ E ≤ 패킷 끝(배타)`이다. 부분 범위를 이어 붙이지 않는다. 수신기의 기존 길이·연속 오프셋·독립 범위 검사와 패킷 수락 ACK 순서를 거친다.

BEGIN은 현재 프레임의 여섯 기록을 지운다. 일반값 버전은 16비트 기록 0을 ‘증명 없음’, 1..256을 ‘바이트 값 + 1’로 사용한다. 임시 12B와 뱅크당 12B로 SNES WRAM 36B가 든다. 비교용 소형 버전은 짧은 반복의 00·FF 및 긴 00을 두 비트맵에 기록하며 총 6B를 사용한다. 두 버전 모두 547의 768B 그림자 메모리를 제거했다.

SEAL의 독립 검사 뒤, 대상 뱅크의 직전 최종 ACK에서 유효해진 기록과 이번 기록이 모두 있고 값이 같은 행만 생략한다. 뱅크 유효 태그를 먼저 지운 채 후보 기록을 저장하고, 실제 표시 확정·최종 ACK 경로에서 태그를 공개한다. 오류 경로는 오류 코드와 상태를 보존하면서 오류 ACK 전에 양 뱅크 태그를 지운다. cold·형식 변경·무효 태그는 원본 행 모두를 복원한다. 행별 STOP 서비스와 source 포인터 진행, 246행 마감은 기존 경로를 쓴다. [65816 생성기](../tools/nes_receipt548.py)

## 검증

- 임의 값 후보에서 긴 0x37 반복과 00·FF가 이전 ACK와 같은 경우 여섯 행을 모두 생략했다. 행 경계를 걸치는 64B 반복은 두 행 어디에도 증명을 만들지 않았다. 값 변경, 서로 다른 두 바이트의 반복, 부분 literal이 포함된 경우에는 원본을 전송했다. 1·2행 전환과 기존 3행 형식에서 돌려본 8개 RGB도 546과 일치했다. [입력·형식 경계 시험](../tools/test_nes_receipt548_counts.py)
- 이전에 표시했던 두 뱅크 각각에서 반복 수신 도중, raw 쓰기 전, 첫 실제 raw DMA 뒤에 STOP을 걸었다. 오류 ACK 0xE4와 양 뱅크 무효 태그, 이전 화면 보존을 확인했다. 중단 당시의 뱅크 기록과 실제 VRAM 2,048B를 이식해 재실행하면 모두 여섯 행을 썼고 정상 최종 ACK를 보냈다. 이 시험은 부분 상태에서의 복구를 모델로 확인한다. [취소·전체 복원](../tools/test_nes_receipt548_recovery.py)
- 64B fill STOP 8건, 최종 표시 STOP 7건, 새 head·누락·중복 등 22건과 같은 ARM의 메뉴 복귀 경로를 검사했다. 실물 메뉴 복귀의 기준 기록은 MMC540이다.

독립 재생은 실제 패킷 수락 ACK에서 증명을 별도로 구성한다. 매 최종 표시 ACK의 물리 VRAM 바이트를 보존해 다음 같은 뱅크에서 생략하는 모든 행과 대조한다. 실제 skip mask·전송 분기·VRAM·RGB·표시 시각까지 확인한다. [독립 재생](../tools/replay_nes_receipt548.py) · [전체 비용 대조](../tools/analyze_nes_receipt548.py)

## 재현

`nes_receipt548.py --any-value`로 일반값 버전을 빌드한다. 기본값도 일반값 버전이다. `--bitmap`을 주면 소형 비트맵 버전이다. hardware541/ARM02, dense519/fixture01, order520/oracle-compact01, service509-rom03, 3,000,000/3,178,684 master clocks에서 `test_nes_tile532.py --trace-credit --trace-rom`을 실행한 뒤 `replay_nes_receipt548.py`로 독립 재생한다. `test_nes_dma542_fixed.py`의 고정 도착 대조에는 546의 해당 위상 패킷을 사용한다. 이 일정은 53개의 고정 캡처와 반복되는 8프레임 부트 ROM 허용표를 사용한다.

## 두 시작 위상

| 546 → 548 일반값 | 위상 1 | 위상 2 |
|---|---:|---:|
| 957의 실제 빔 판독 | 248행 h=98 → 246행 h=624 | 248행 h=98 → 246행 h=624 |
| 957의 최종 대기 | 1 → 0회 | 1 → 0회 |
| 밀집 951–955 평균 표시 간격 | 99.867600 → 99.870207ms | 99.870281 → 99.871324ms |
| 밀집 VBlank 합계 | 30 → 30 | 30 → 30 |
| 53번째 표시 ACK 차이 | −65.169077ms | −65.169077ms |

957의 마지막 확정 bank 0은 955였다. 마스크 0x1D로 0·2·3·4번 행을 생략해 SEAL 이후 raw DMA는 384→128B, map과 tile은 각각 1,536B·336B였다. 53화면에서는 174행을 생략해 VRAM DMA가 125,488→114,352B였다. 547의 768B 이력 읽기·쓰기에 접근하면 실패하도록 한 독립 재생에서도 53개 RGB와 표시·ACK가 일치했다. 이벤트 수는 9,911/9,912개다. ROM 읽기 5,616회, 두 bulk 슬롯, 952/954 최종 대기 0회와 첫 BG 상대 ROM 허용 구간을 보존했다. [기계 판독 결과](../analysis/receipt548-verification.json)

일반값 버전의 warm 수신 기록 계산은 평균 0.170ms, SEAL에서 두 기록을 결합하는 시간은 0.105ms다. 두 계측 구간의 합은 약 0.275ms다. 547은 SEAL의 원본 비교만 약 1.933ms였다. 첫 두 화면 이후 51개 표시 간격은 일반값 버전에서 79.295/78.969ms였다. 집계 변경만 적용한 대조군과 비교한 마지막 ACK는 148.379/165.007ms 빨랐고, 원본 MMC540 대비로는 131.729/148.380ms 빨랐다. 이들은 같은 캡처 일정에서 계산한 값이다.

6B 비트맵 대조군은 수신 기록 0.182ms·SEAL 결합 0.031–0.032ms였다. 957 대기 0회와 같은 174행 생략을 유지하며 546 대비 마지막 ACK가 98.425/81.791ms 빨랐다. 이 경우에도 밀집 VBlank 합계는 30/30이었다. 일반값 후보는 본문 4,956B(+4B 대 546), 비트맵 후보는 4,952B이며 모두 5,120B에 매핑된다.

**판정.** 384B 재비교 제거, 957의 대기 0회, 546 대비 전체 마지막 ACK 단축은 두 위상에서 확인했다. 밀집 구간 개선까지 요구하는 실기 승격 조건은 통과하지 못했다. 실기 기준은 MMC540이며 이번 후보의 FIT/STA 및 실기 FPS는 미측정이다. 밀집 다섯 화면에서 SEAL head를 읽고 표시까지는 각각 1 VBlank씩이었다. 표시 간격이 가장 긴 952는 직전 표시부터 SEAL head까지 6 VBlank, 그 뒤 1 VBlank로 두 위상이 같다. 다음 비교는 548의 수신 증명과 957 대기 0회를 대조군으로 두고 952의 SEAL 전 공급 일정을 줄이는 데 둔다.

초기 4,984B 빌드는 용량 검사에서 거부됐다. 제한값 정상 공동 실행은 client02, 최종 일반값 공동 실행·취소·복구는 client04다. 중간 client03의 공동 실행은 중단했고 53화면 결과로 쓰지 않았다. 오류 ACK 직전에 태그를 지우는 변경은 같은 12B 오류 처리 블록에 들어갔다. 제한값 수정판 client05도 client02 도착 기록에서 전체 소비 이벤트·클록·RGB를 그대로 재현했고 부분 상태 복원 6건을 통과했다. 기본 옵션으로 다시 만든 일반값 ROM은 client04와 SHA256이 같다.

원시 실행·빌드·중단 기록·복구 이미지는 로컬 `probes/nes-receipt548/archive01/evidence.zip`의 8,331개 파일을 다시 풀어 해시를 확인했다. ZIP SHA256은 `bd1f1151cb90a0570182ab46e0bc0c7d2fe13ce5445190ebeb0a2689e87f81f6`이다.
