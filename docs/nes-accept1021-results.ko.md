# 23행 화면의 SEAL 수락 비용과 패킷 선검사

MMC1012를 실기 기준으로 유지한다. 모험도 4 원본 3462(재생 세대 908)의 section 5 마지막 240B를 수락할 때 스크롤·HDMA 테이블을 검사하고 compact raw DMA의 시작 주소를 준비했다. 두 위상 모두 목표 map 192B를 선행 DMA했지만 직전 VBlank 38의 246선 마감은 회복하지 못했다.

## 무엇을 앞당겼는가

65816이 한 행의 compact 패킷을 전부 WRAM에 기록하고 section 5 커서가 1,562B에 도달하면 기존 의미 검사를 실행한다. 길이 21인 세 HDMA 테이블과 스크롤의 유효 범위를 보관한다. SEAL은 세대·순서·뱅크·구간 길이와 타일·map 수신 범위를 다시 확인한다. 준비해 둔 DMA 주소는 행 수·표시 mask·길이가 일치할 때 사용한다. 활성 바이트가 바뀌었으면 SEAL을 거부한다. 다른 레이아웃은 기존 검사를 사용한다. 뱅크 이력의 무효화와 PPU 쓰기는 원래 단계에서 실행한다.

## 두 시작 위상의 실제 ARM·65816 공동 실행

| 세대 908의 SEAL 경로 (ms) | 기준 위상 1 | 후보 위상 1 | 기준 위상 2 | 후보 위상 2 |
|---|---:|---:|---:|---:|
| 수락·헤더 및 manifest | 0.245 | 0.247 | 0.247 | 0.247 |
| compact DMA 레이아웃 | 0.064 | 0.050 | 0.064 | 0.050 |
| 스크롤·HDMA 의미 검사 및 후보의 WRAM 재확인 | 0.681 | 0.327 | 0.679 | 0.327 |
| 타일 수신 범위 | 0.401 | 0.401 | 0.402 | 0.401 |
| map 수신 범위·업로드 진입 | 0.079 | 0.079 | 0.077 | 0.079 |
| **수락부터 업로드 진입까지** | **1.470** | **1.104** | **1.469** | **1.103** |

기존 1.466ms를 측정한 MMC1020의 DMA 시작 동기 조건에서도 서비스 시간이 1.108/1.109ms로 줄었다. 이 조건은 송신기가 실제 DMA 시작을 즉시 아는 분리 재생이다. 위 표는 MMC1012 ARM의 SPI·credit 처리까지 되먹인 별도 실행이다.

공동 실행의 240B 수락→큐 반환은 0.383→1.411ms 및 0.382→1.443ms로 늘었다. 뒤따르는 OAM 재사용 패킷과 SEAL이 기다리면서 SEAL 수락 자체는 1.373/1.495ms 늦어졌다. 세대 908은 두 위상 모두 VBlank 38의 253선에 192B DMA를 시작하고 VBlank 39의 240선에 잔여 DMA를 끝냈다. 공개는 242선, ACK는 244선으로 기준과 같았다(ACK 차이 +8/+0 master clocks). 여덟 화면의 마지막 세대 912 ACK도 기준 대비 +0/+112클록이었다.

원래 MMC1012조차 세대 908의 SEAL을 직전 246선 마감보다 8.410/8.329ms 뒤에 수락했다. 다음 실험의 기준은 마지막 OBJ와 일반 패킷의 준비 시각부터 그 8ms를 어떻게 당길 수 있는지다. 수락 때 큐를 점유해 독립 검사를 통째로 앞당기는 방식은 이번 화면의 우선순위에서 제외한다.

## 검증과 적용 범위

세대 905–912의 작업량·패킷 내용·RGB·WRAM map을 대조했고, 고정 캐시 입력과 ROM 읽기 할당 3,136회를 양쪽에서 유지했다. 동일한 MMC1012 ARM 메뉴 복구 코드에서 메뉴 준비와 reset 해제를 확인했다. 세대 오류, 수신하지 않은 타일을 요구하는 SEAL, 선검사 뒤 HDMA 바이트 손상, SEAL 처리 중 STOP은 모두 직전 화면을 보존하고 준비 상태를 무효화했다. 부팅 위상을 고정한 패킷 도착 시각 재생에서는 위상 1의 192B가 선행되지 않았다. 이 결과도 공동 실행 결과와 함께 남겼다.

후보는 WRAM 90B를 추가 사용하고 65816 ROM이 5,389B로 보드 할당 5,120B보다 269B 크다. 실행 결과는 확장 진단 ROM의 에뮬레이션이다. 새 실기 설치본은 만들지 않았다.
