# 950 마지막 테이블과 951 END 수신 일정

실기 기준은 MMC872다. 876에서 950의 map 1,088B 선행 DMA와 표시 3회를 두 시작 위상에서 유지한 ARM 재시도 후보를 출발점으로 삼았다. 그 링크에서는 951 첫 D1이 일찍 끝났지만 두 번째 D1이 874보다 89 / 26µs 늦었다. 950 공개 시점에 951 END를 담은 블록의 D2 반환도 아직 7,708 / 7,849클록 남아 있었다.

## 비교한 ARM 발행 순서

| 후보 | 변경한 경로 |
|---|---|
| 테이블 연속 발행 | 앞의 201B 패킷이 plan을 확인했으면 뒤의 240B는 기존 큐 credit으로 발행한다. 이전 bulk의 반환을 확인할 수 있는 범위를 넘기기 전에는 일반 발행 경로로 돌아간다. SEAL은 기존 END·bulk 반환 검사를 수행한다. |
| 테이블 먼저 발행 | 양쪽 뱅크의 최종 ACK 이력과 현재 출력이 일치해 팔레트·OAM 재사용이 가능할 때, 두 테이블 패킷을 먼저 보내고 재사용 명령을 보낸다. 실제 대상 뱅크 검사는 65816이 수행한다. |
| 두 패킷 사이에 재사용 | 같은 이력 조건에서 201B, 재사용 명령, 240B, SEAL 순서로 발행한다. 240B와 SEAL이 큐에서 이어질 수 있다. 패치 테이블이 없는 화면에서는 이전 위치에서 재사용을 발행한다. |
| 테이블 우선·큐 공유 | 테이블 뒤의 재사용 명령과 184B raw 패치 SEAL이 기존 두 슬롯에 함께 머물 수 있게 한다. SEAL은 선행 명령의 성공 후 소비된다. |

비교 대조군에는 876의 발행 순서를 사용했다. 네 후보와 대조군 모두 D2·D3의 8바이트 명령 생성을 기존 로더와 공유한다. CRC8의 입력·초깃값·다항식은 같다. 로더의 24비트 주소, D2·D3의 16비트 토큰, 인수 및 양쪽 경계 바이트를 포함한 120개 벡터를 링크된 ARM에서 검사한다. 처음 링크한 연속·테이블 우선 후보는 각각 Flash를 40B·36B 넘겨 크기 비교용으로 보관했다.

## 시각을 읽는 기준

- 950 공개는 65816의 화면 전환 명령에서 기록한 `reveal`이다. 951 END 완료는 D1·데이터 검사·D2 반환·후속 D0 상태 확인을 마치고 ARM의 `nes_native165_poll`이 성공과 COMPLETE 상태로 복귀한 시각이다. D2의 SPI 거래만 끝난 시각과 구분해 기록한다.
- 951 마지막 D2는 950 최종 ACK와 EA 뒤에 승인된 별도의 COMMIT 레코드 반환이다. 위상 1의 51,103,624클록, 위상 2의 51,460,992클록이 874의 직전 캡처 시작선이다. 952는 같은 절대 VBlank 번호에서 비교한다. 직전 화면의 공개가 밀렸을 때 표시 간격만 짧아지는 경우를 걸러낸다.
- 950의 map DMA, 952의 공개·잔여 DMA, 마지막 65816 ACK와 ARM의 첫 유효 E0를 각각 기록한다. 같은 dot 0 입력과 SPI·ROM 조건에서 map·유효 화면 픽셀, 밀집 작업량, section 5의 전체 바이트열과 각 세대의 SEAL 바이트를 대조한다.

## 두 번째 D1의 이득이 END까지 이어지는가

테이블 우선 후보에서 876 재시도 링크와 같은 화면을 비교했다. 마지막 240B 테이블 발행 시작이 위상 1에서 36,226클록(1.687ms), 위상 2에서 40,603클록(1.891ms) 빨라졌다. 951의 두 번째 D1 수신 완료도 17,028 / 21,404클록(0.793 / 0.997ms) 앞당겼다. 그러나 950의 재사용 명령과 SEAL도 같은 SPI를 써야 했다. 세 번째 D1 완료에 남은 이득은 109 / 4,485클록(0.005 / 0.209ms)이었다.

951 END 직전의 120B D1 거래에는 페이로드 117B가 들어 있다. 여기에는 연속 raster 184줄과 39줄, 일반 raster 한 줄, 팔레트, META_END가 함께 담긴다. 테이블 우선 링크에서 이 D1의 종료부터 D2 전송 **시작**까지 두 위상 모두 약 0.943ms가 걸렸다. 이 구간에는 데이터 CRC, ARM 복원, META_END의 전체 개수·타일 요구 검사가 포함된다. 블록에서 각 함수가 쓴 시간은 따로 계측하지 않았다. 875에서 단일 raster 루프 단축을 이미 시험했으므로, 재시도한다면 두 번째 D1만 볼 것이 아니라 세 번째 D1과 이 블록의 반환까지 절감이 이어지는지 비교해야 한다.

## 두 시작 위상의 결과

표 안은 위상 1 / 위상 2 순서다. D2 지연은 874의 직전 캡처선을 넘긴 시간이고, 952의 목표 공개 번호는 147 / 148이다. 마지막 ACK 차이는 MMC872를 기준으로 한 65816의 ACK 공개 시각이다. 별도로 기록한 ARM의 유효 E0와 단위가 같은 클록이다.

테이블 우선은 950의 선행 DMA와 오프닝 759의 VBlank 마감(176 / 176)을 지켰다. 951 END 완료는 950 공개보다 0.460 / 0.245ms 늦었다. 밀집 구간의 65816 마지막 ACK는 위상 1에서 MMC872와 같은 클록, 위상 2에서 0.264ms 빨랐다. 전환은 MMC872의 119 / 119보다 길어졌다.

큐를 공유한 위상 1에서는 END가 950 공개보다 **839클록(39µs) 먼저 완료**됐다. 그러나 공개 후 65816 ACK까지 2,936클록, ARM의 유효 E0까지 누적 9,818클록, EA까지 15,159클록, D3까지 19,653클록, 마지막 D2까지 25,598클록이 걸렸다. 공개부터 캡처선까지 이용할 수 있는 21,578클록보다 4,020클록 길었다. 위상 2는 950의 1,088B가 선행되지 않아 표시가 4회로 늘었다. END만 더 일찍 처리해도 두 위상의 캡처가 회복된다는 가정은 이 결과로 기각한다.

재사용을 두 테이블 사이에 넣은 위상 1은 47개 화면을 공개한 뒤 952의 192B 비활성 map DMA 진입 검사에서 중단됐다. 같은 패킷과 클록으로 65816만 다시 실행해 951 공개·952 SEAL 수락·업로드 진입이 원 실행과 정확히 일치하는지 확인했다. 빔 래치 값은 VBlank 147의 253선 수평 클록 2, 설정 경로 진입은 254선이었다. 허용하는 래치의 마지막 선은 252다. 검사를 유지해 이 후보를 제외했다.

네 후보 모두 실제 발행한 패킷에서 65816 독립 검사·STOP·부분 전송·cold 재시작 등 12개 경로와 ARM의 메뉴 복귀 경로를 점검했다. 큐 공유 후보에서는 세대 907의 재사용 serial을 손상시키고 정상 SEAL도 큐에 함께 넣었다. 기존 두 화면만 공개하고 오류 0xE0으로 거부했다. FPGA와 65816 바이너리를 교체하지 않았다. MMC872 링크와 후보에 동일한 dot 0 보정 입력을 넣어 얻은 연속 재생 결과다. 신규 실기 FPS는 측정하지 않았다.

실기 기준은 MMC872를 유지한다. 다음 후보의 첫 판정은 950의 정상 공개 시각을 고정하고 공개 직후 E0·EA와 951 COMMIT(D3·D1·D2)의 실제 거래 중 어느 대기를 4,020클록 넘게 줄일 수 있는지다. prior ACK의 CRC·identity 및 EA 이후 COMMIT 승인 순서는 유지한다. 위상 2의 950 선행 DMA도 함께 회복할 때만 전체 세 장면을 비교한다.

## 재현

1. `prepare_nes_table877.py BASE PATCH POLICY --shared`를 실행한다. BASE는 876 재시도 링크의 `src`, POLICY는 `pair`, `table`, `interleave`, `fifo`, `control`이다. `build_nes_mmc479_arm.ps1`로 전체 링크하고 874의 `client02`를 사용한다.
2. `replay_nes_table877.py TEMP PHASE WORK TAG CLIP`으로 두 위상에서 오프닝·전환·밀집 장면을 재생한다. 대조군은 밀집 두 위상을 사용한다. 태그는 `877-s` 뒤에 정책 이름을 붙인다. END 관측 훅은 ARM 코드·클록·레지스터를 변경하지 않는다.
3. 각 후보에서 `check_nes_table877.py commands`, `guard_nes_scroll874.py`, `guard_nes_capture871.py`, `guard_nes_progress870.py`, `check_nes_menu533.py --trial 872`를 실행한다. `check_nes_strip869.py guards`로 후보가 실제로 발행한 패킷에서 65816 손상 검출·부분 쓰기·STOP·cold 재시작을 검사한다. `check_nes_table877.py report TEMP OUT pair table interleave fifo`가 링크 해시·검사 결과·클록·채택 조건을 대조한다. [클록별 기록](../analysis/table877-results.json)

4. `check_nes_table877.py beam TEMP OUT`은 원래 DMA 검사를 유지한 채 실패한 빔 값을 출력한다. `check_nes_table877.py reuse TEMP OUT`은 재사용 명령의 serial을 손상시키고 후속 SEAL을 같은 큐에 넣는다. 두 진단 JSON을 해당 후보 작업 폴더에 생성한 뒤 report를 실행한다.
