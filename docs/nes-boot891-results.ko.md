# MMC890의 RESET 벡터와 첫 stage 쓰기

MMC890 일반 1회차와 NES BOOT는 384KiB 검증과 START를 통과한 뒤 stage 0에서 5초 동안 대기했다. NES BOOT에서는 ARM이 상태를 44,507회 읽었다. 두 실행 모두 STOP 뒤 메뉴로 복귀했다. 일반 2회차는 `DISPLAY_NEXT`가 마지막 기록이며, 전원을 다시 켠 뒤 메뉴로 복귀했다. 이 실행에서 START 또는 5초 타임아웃에 도달했는지는 알 수 없다. [실기 로그 대조](../analysis/hardware890-startup.json)

## 실행 코드와 버스에서 각각 확인한 내용

MMC872와 MMC890의 배치 후 ROM은 RESET 벡터가 모두 `00 80`이고 첫 stage 쓰기 명령까지 39B가 일치한다. Mesen에서 두 정적 ROM을 각각 처음부터 실행하면 `$00:8000` 진입은 186, `$00:8024`의 쓰기 명령 실행은 608, `$00:7000=1`은 640 마스터클록이다. stage 3은 각각 5,257,022와 5,273,588클록이다. 이 차이는 첫 기록 **뒤**에 생긴다. 이 시험은 카트리지의 전기적 RESET 해제를 측정하지 않는다.

실제 보드 최상위 RTL에 SNES 읽기·쓰기와 ARM SPI 파형을 넣었다. 보드 외부에서 결정되는 세션 시작·리셋과 호스트 클록은 시험에서 직접 제어했다. 각 시작 위상에서 주소·양방향 데이터·출력 허가와 SPI73 응답을 대조했다. 기존 `05`는 첫 벡터 주소가 첫 E0 뒤, 두 번째 E0 전에 동기화된 세션이 비활성일 때 관측됐음을 뜻한다. 당시 출력된 값과 어느 벡터 바이트였는지는 이 코드에 없다. 두 벡터 읽기가 모두 무구동이거나 낮은 바이트만 무구동이어도 `05`가 나온다. 먼저 비활성 읽기가 한 번 있고 뒤이어 유효한 벡터를 읽어 stage 1까지 가는 경우도 첫 관측 자체는 같다.

## stage 0 진단 해석

새 상태는 첫 E0 이후 stage 0 동안 관측한 사건을 누적한다. 실제 오류 코드가 설정되면 그 값을 우선한다. stage 1 이후에는 원래 stage와 오류 형식을 사용한다.

| 비트 | 관측한 사건 |
|---|---|
| 0, 1 | 안정된 주소의 `$00:FFFC`, `$00:FFFD` 읽기 |
| 2, 3 | 각 읽기에서 보드가 출력했고 값이 각각 `00`, `80` |
| 4 | 보드가 출력한 벡터 바이트에서 예상값과 다른 값을 샘플 |
| 5 | `$00:8000`에서 출력한 첫 명령 바이트 `78`을 샘플 |
| 6 | `$00:7000`의 쓰기 스트로브 종료를 관측 |

| 핀에 인가한 조건 | 새 상태 | SPI73 stage |
|---|---:|---:|
| 정상 벡터·첫 쓰기 | 내부 `6F` | 1 |
| 두 벡터 모두 무구동 | `03` | 0 |
| 낮은 바이트 무구동, 높은 바이트 정상 | `0B` | 0 |
| 비활성 읽기 후 두 바이트와 첫 쓰기 정상 | 내부 `6F` | 1 |
| 정상 벡터·첫 명령, 쓰기 생략 | `2F` | 0 |
| 정상 벡터·첫 명령, 세션이 내려간 뒤 쓰기 | `6F` | 0 |
| 높은 벡터 바이트에 `81` 주입 | `17` | 0 |

네 가지 호스트 클록 위상에서 같은 조건을 적용했다. SPI 상태 읽기 도중에 stage를 바꾼 경우와 읽기를 중단한 뒤 다시 시작한 경우에도 이전 응답과 새 응답을 구분한다. 이 값은 FPGA의 관측 이력이다. SNES가 어느 클록에 어떤 값을 래치했는지, 서로 다른 읽기가 한 번의 RESET에 속하는지까지 알려 주지는 않는다.

## 보드 선택과 전달본

| 회로 | Quartus Lite 전체 보드 결과 |
|---|---|
| A · 원래 응답 선택기 | 965 LAB 필요, 기기 한도 963 |
| B · 직렬 응답 | 배치 성공. NES reset 해제로부터 호스트 진단 비트까지 setup −9.794ns |
| C · 출력 허가와 데이터 동기화 | 965 LAB 필요 |
| D · 직전 주소의 비교 결과를 보관 | setup +0.267ns. 미제약 입력 경로 664→718 |
| E · 읽기·선택·주소를 같은 호스트 샘플에서 판정 | 15,334 LE, 963/963 LAB, 56/56 M9K. setup +0.410ns, hold +0.149ns, recovery +1.575ns, removal +0.489ns |

MMC891 전달본에는 E를 사용했다. 전체 STA의 기존 미제약 입력 포트 54개와 출력 포트 수는 동일하다. 미제약 입력 경로는 setup·hold 각각 664→557개다. 배치 후 외부 입력별 도달점을 대조하면 클록 핀을 제외한 새 연결은 `SNES_ROMSEL_IN → select_sync[0]` 한 곳이다. 기존 클록·핀 제약을 그대로 사용했다. 지정 경로 6개 그룹도 각각 통과했다.

최종 ARM 이미지는 212,956B로 Flash 36B가 남는다. MMC890과 헤더를 제외한 바이트를 대조해 판번호 문자열 변경만 확인했다. 최종 ARM의 BOOT 파일 선택값 386, 원본 ROM 수락·손상 ROM 거부, STOP 뒤 base 복구와 메뉴 해제 경로를 시험했다. 압축 이미지의 프로그래머 전송 바이트와 ZIP 내용도 확인했다. MMC891 실기 결과는 다음 NES BOOT 로그에서 확인한다. [검증 수치](../analysis/boot891-results.json) · [설치본 검증](../analysis/trial891-package.json) · [실기 순서](nes-mmc891-trial.ko.md)

## 재현

1. MMC872·MMC890의 보드·클라이언트는 각 전달본의 재현 절차로 준비한다. `check_nes_boot891_cpu.py TEMP 새출력경로`로 두 65816 실행 기록을 만든다.
2. `nes_boot891_witness.py TEMP --variant 891D`로 MMC890 보드에서 SPI73 진단 RTL만 교체하고 Quartus Lite MAP·FIT·ASM·STA와 지정 경로 검사를 실행한다. 최초 회로는 `891`, 직렬 응답은 `891B`, 동기화된 데이터·출력 허가를 함께 사용하는 회로는 `891C`이다. `891D`는 C에서 쓰던 직전 24비트 주소를 주소 일치·stage 쓰기·error 쓰기 세 비트로 교체한다.
3. 기존 Questa Starter FLOAT 래퍼에서 `check_nes_boot891.py TEMP 새출력경로 --variant 891D`를 실행한다. ROM 바이트 검증, 보드별 28조건, SPI 도중 상태 변경과 중단을 확인한다. D에서는 매 호스트 클록마다 세 비트를 원래 24비트 주소 레지스터와 대조한다.
4. 같은 절차로 `--variant 891E`를 실행한다. `report_nes_boot891.py TEMP CPU결과 A결과 B결과 C결과 D결과 E결과`로 실행·배치 기록을 요약한다. 보드당 조건은 동일한 7종 × 4위상이다.
5. MMC890과 891E 양쪽 배치 디렉터리에 `nes_boot891_io.tcl`을 `boot891-inputs.tcl`로 복사해 `quartus_sta -t boot891-inputs.tcl`을 실행한다. `package_nes_boot891.py prepare` 후 기존 `build_nes_mmc479_arm.ps1`로 MMC890의 link-credit을 바탕으로 nes-trial891/patch를 적용해 nes-trial891/link-credit에 최종 링크한다. `loader ROM`, `check_nes_menu533.py`, `check_nes_transfer512_recovery.py --fault none`를 판번호 891로 실행해 WORK의 loader.json, menu.json, base/result.json을 만든다. 마지막으로 `package_nes_boot891.py image TEMP`, `pack TEMP --cases E결과`를 실행한다.
