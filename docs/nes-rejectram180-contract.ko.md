# NES180 — 기존 기록 RAM을 이용한 오류 비교

최종 결과: 기능 시험은 통과했지만 실제 클록 setup −0.227ns로 미채택이다. 별도로 시험한 오류 문맥 저장 공간 공유 후보도 967/963 LAB으로 배치에 실패했다. 두 후보와 다음 관측 범위 축소 결정은 [저장 공간 재사용 결과](nes-rejectstorage180-contract.ko.md)에 정리한다. 새 실기 패키지는 없다.

이 후보는 기존180의 `previous_signature` 25비트 레지스터를 제거하고 history RAM에 이미 저장된 직전 사건의 오류 벡터를 읽어 비교한다. 첫 오류 위치용26비트는 그대로 유지한다. 별도 프레임버퍼·세이브 SRAM·RAM 블록을 추가하지 않는다. 게임의 수집·허용·해제·전송 경로와 MCU는 변경하지 않는다.

## 동작과 지연

- 실행 중 RAM 읽기 주소는 `next_slot - 1`, 즉 마지막 기록이다. 종료 후에는 기존 SPI 페이지 주소로 전환한다.
- 기존96비트 RAM 출력 중 `[85:61]`을 오류 비교에 사용한다. 별도25비트 복사 레지스터는 없다.
- 새 사건을 쓴 클록에서는 RAM 출력에 이전 주소의 값이 남을 수 있다. `feedback_pending180` 한 비트로 그 값을 무효화한다. 다음 읽기 클록 이후 새 오류 벡터를 사용할 수 있다.
- RAM이 비었거나 피드백이 무효이면 같은 오류라도 보수적으로 기록한다. 오래된 값 때문에 새로운 오류를 생략하지 않는다. 아주 짧은 사건 간격에서는 중복 사건이 추가될 수 있으며, 이를 모든 프레임의 완전한 기록이나 FPS로 해석하지 않는다.
- `active`와 `stopped`는 기존 의미를 유지한다. 샘플이 없는 기간을 STOP으로 해석하지 않는다. STOP·fault가 확정된 후에는 기록 RAM이 바뀌지 않는다.

기록기와 witness는 모두 `SNES_SYSCLK`에서 동작한다. 이 피드백은 기록 여부 결정에만 연결되며 게임 실행으로 돌아가지 않는다. RAM 읽기 지연을 게임의 추정 프레임 간격으로 덮지 않는다. 연속 클록의 쓰기까지 시험하고, 무효 피드백에서는 기록을 생략하지 않는 규칙을 적용한다.

## 유지되는 규격

명령77/A0–BF, descriptor 버전2, `LAST16_REJECT180_V2`, 최근16×96비트, 오류 위치와 확정 때 개수의 의미는 [기존180 규격](nes-reject180-contract.ko.md)을 따른다. 첫 유효 geometry 이후부터 거부 오류 종류의 변화와 정상 회복을 기록한다. 최초 관측 클록은 원래 CPU 쓰기 시각과 다르며, 조기 실패 프레임의 확정 오류가 모든 후속 오류를 포함하지는 않는다.

MCU는 기존 `nes-reject180/arm02`의198,012바이트 펌웨어를 그대로 재사용한다. 전체 소스·실행 파일·기존 ARM/판독/formatter 결과를 해시로 확인한다. 여유1,040바이트·최대 TXT3,920/4,096바이트 결과를 재사용하며 새로운 시험으로 중복 계산하지 않는다. 수집기 해제14위치/42검사도 해당 RTL이 동일하므로 기존 결과를 재사용한다.

## 새로 실행한 검증

전체 후보 SV를 컴파일하고 실제 observer SPI로 거부·회복·반복 생략·취소·순환·STOP·fault·초기화를 검증했다. 피드백을 명시적으로 무효화한 상태에서도 동일 오류 사건이 남는지 추가 확인했다. 별도의 RAM 시험에서는 연속20쓰기, 출력 갱신 시점, 실행 중32개 SPI 주소 선택, STOP 뒤 주소 복귀와 fault 동시 기록을 확인했다. 첫 시험도 통과했으며, 두 번째 시험은 무효 피드백 주입을 추가한 최종 검증이다.

이 작업은 실기의 미확인 fetch/compact/raster 거부 사유를 얻기 위한 최소 관측 후보다. 렌더링 중단·재개 지원이나 약60fps 개선 자체를 구현한 것은 아니다. 실제 타이밍·조건부 IO·패키지 승인 여부는 `analysis/rejectram180-verification.json`과 최신 인계 문서를 기준으로 판단한다.
