# NES167 — 정상 대기 분리 수정, 타이밍 미달로 배포 보류

166의 BEGIN383/ABORT383/END0/COMMIT0 결과에 따라 화면 완성 전 CHR 수집을 수정했다. **기능 검증은 통과했으나 실제 클록 타이밍은 미달이다.167 실기 ZIP은 만들지 않았고 기존 승인 FPGA를 교체하지 않았다.**

## 수정 내용

- 메모리 사용권 획득 전 REQUEST와 소비자가 데이터를 가져가길 기다리는 STREAM을 짧은 대기 오류에서 제외한다. 조회 응답과 이미 요청한 메모리 응답의 짧은 제한은 유지한다. 중재기의7 NES 클록 응답 감시·CPU/PPU 우선순위·사용권 취소 drain은 원본 그대로다.
- 기존 fill 전체2097152클록·export 전체4194304클록만 유지하면 유한한 정상 대기에서도 전체 제한에 걸렸다. 전체 상한을 각각16777216/33554432클록(약0.78/1.56초)으로 구분해 설정했다. 무한 대기를 허용하지 않으며60초 RUN 제한도 그대로다. 이는 시험용 처리 예산으로, 모든512타일/8192바이트 프레임의 WCET나60fps 보장이 아니다.
- 대기 카운터를 상한을 표현할 수 있는 폭으로 줄인다. 제한에서 제외한 상태에서는 wrap을 허용하되 그 상태를 벗어나는 handshake에서0으로 초기화한다. 조회·응답 대기는 wrap 전에 실패한다. 정상 모드의 출력·요청 시점은 등가성 시험으로 확인했다.
- ABORT의 기존 하위4비트 사유를 유지하고 상위4비트에 fill 세부 오류를 고정한다. release/clear 뒤에도 취소 패킷을 보낼 때까지 값이 유지된다. SPI 식별자74·레코드 폭·수신 검증은 유지하며 기존 MCU 수신기도 이 바이트를 보존할 수 있다.
-167 MCU는166에서 후보명·파일 경로·진행 로그 이름만 바뀐다. 48바이트 trace, RUN 메모리 수명·사운드·입력·STOP·메뉴 복귀는 그대로다. 카트리지 세이브 SRAM을 사용하지 않는다.

## 검증 결과와 한계

실제 fill+arbiter+export를 연결하고 scanline242..259의 사용권 조건과 주기적인 코어 우선 요청, 느린 소비를 모델링했다.1472개 구성 레코드는166의 첫 수신 수와 같게 만든 시험 입력이며, 그 화면의 실제 타일 배치를 재현한 것은 아니다. PSRAM 응답·조회·호스트는 모델이다.

|시험|결과|
|---|---|
|기존 정책,1900클록마다 소비|14바이트 뒤 export4/fill4 취소|
|짧은 대기만 제외, 기존 전체 상한|56바이트 뒤 export 전체 상한 취소|
|수정 예산, 서로 다른3개 시작 위상|각240바이트 완성·COMMIT|

전체 ARM 링크196748바이트, 정적RAM26520바이트, RUN/IRQ 계산 후 여유1076바이트다.1405개 MCU 입력은166과 동일하며3개 파일의 이름·경로 문자열만 변경했다. 기존166의 실제 SNES 코드45ACK/61184픽셀·runtime10조건은 이 바이트 일치를 근거로 재사용했다. 새 실기 영상·FPS·버튼 유지 통과를 뜻하지 않는다.

Standard Fit은 자동 모드보다 결과가 좋다는 보장이 없으며 어려운 설계에서는 두 모드가 같은 최대 노력을 사용한다. [Quartus 공식 문서](https://docs.altera.com/r/docs/683283/18.1/design-compilation-user-guide-quartus-prime-standard-edition/fitter-effort-setting?contentId=eFqycz5UTR94IZsNCdSVvg). 이번에도 탐색 배수를 더 늘린 결과는 악화되어 기각했다.

## 다음 작업과 재현

실기 ZIP은 보류한다. 기능 수정은 유지하고 map04(Standard Fit, placement multiplier1.0)의 실제168MHz ROM CHECK 경로 check_response_address[8]→check_next[13] 경로(-0.003ns)를 직접 분석한다. 기존 compare165의 기각된 비교식/설정과 map01~05를 반복하지 않는다. 해당 제어 영역의 배치 보존·국소 제어/팬아웃 개선을 먼저 검토하고 필요한 경계만 검증한다. 클록/false-path 완화·seed 순회 금지. 실제 클록 setup/hold와 새 배치의 조건부 IO/reset이 통과하면 기존167 MCU·미변경 SNES 결과를 재사용해 ASM/ZIP 후 SMB3 실기로 간다. 같은166·044·무변경 부팅은 요청하지 않는다.

`nes_pacing167.py --baseline <boundary165/map02> --out <새 ASCII 경로> --standard-fit`가 다음 분석 기준map04를 재현한다.61개 입력 바이트 일치를 확인했으며 재현을 위한 FIT 반복은 하지 않았다. `--placement-effort`는 기각된map05 실험용이며 채택 설정이 아니다. 현재 체크/패키지 도구와167 사용 안내는 배포 준비용이다. 최종 IO 체크·ASM·ZIP 생성은 아직 실행하지 않았다.

긴 test02가 끝나기 전에 작업 트리의 도구를 변경해 원래 결과 JSON의 두 도구 해시가 종료 시점 버전을 가리킨 문제가 있었다. 원문은 보존하고 **시험 시작에 복사한 도구·RTL 해시**를 source-pin-addendum에 별도로 고정했다. 최종 모델 driver는 실행 복사본을 해시하도록 고쳤다. 최종 카운터 등가성은 실행된 참조 RTL과 직접 대조했다. test01의90초 호스트 제한 종료와 equiv01의 벤치 선언 순서 오류도 보존했으며 DUT/라이선스 실패로 해석하지 않는다.
