# NES186 실기 결과 — 정적인 화면 개선, 스크롤 병목 유지

사용자는 **사운드·조작 정상, 움직임이 적은 화면은 확실히 덜 끊기지만 스크롤하면 심하게 끊김**을 보고했다. 국소적인 개선은 확인했지만 60fps 목표는 미달이다. 원본 두 TXT를 private `probes/nes-game186-hardware01/raw`에 그대로 보관했다. [분석 JSON](../analysis/game186-hardware01-verification.json)에 해시·100개 단계·전체 상태·비교 계산·기존 배포 소스 연결을 기록했다.

## 표시와 비용

| 항목 | NES185 | NES186 |
|---|---:|---:|
| DISPLAY 구간 | 60.06s | 60.06s |
| 확인된 표시 완료 | 180 | 182 |
| 전체 평균 표시 완료율 | 2.997/s | 3.030/s |
| 수신 누적 | 28.19s | 27.71s |
| 변환·CHR 전송 누적 | 7.76s | 7.90s |
| 나머지 전송·표시 대기 누적 | 23.53s | 23.95s |
| SPI 거래 | 269,524 | 263,091 |
| SPI clocked bytes | 7,514,384 | 7,574,556 |
| 표시 큐 전송 패킷 | 14,333 | 8,147 |

큐 패킷은 **43.16% 감소**했지만 전체 거래는2.39% 감소, clocked bytes는0.80% 증가했다. 전체 표시 완료는1.11% 증가에 그쳐 평균330ms/완료로 목표16.7ms와 여전히 차이가 크다. 서로 다른 입력·장면의 시험이므로 이 비율을 통제된 개선율로 취급하지 않는다. 평균은 특정 스크롤 장면의 FPS나 CRT 주사율이 아니며, 사용자가 느낀 정적 장면 개선과 양립한다. 로그에는 장면·COPY 횟수·map/CHR별 바이트가 없어 원인별 기여율을 계산할 수 없다.

receive는 수신 대기·읽기·prepare, build는 변환·CHR 전송, seal은 나머지 전송·최종 표시 완료 대기다. 합59.56초와 DISPLAY60.06초 차이에는 마지막 미완료 작업·guard·10ms 해상도·측정 경계가 포함된다. wire는 헤더·폴링도 포함해 순수 그래픽 payload가 아니다.

## 종료와 오류 해석

BEGIN/END/COMMIT183, ABORT0, 확인된 표시 ACK182. 마지막 표시 generation256은59.74초다. 그 다음 generation257/serial183/sequence39의 **SEAL(op3)** 을 기다리다가 종료됐다. 큐 sent8147/retired8146으로 한 개가 남았고 최종ACK는 확인되지 않았다. 이 마지막 화면이 물리적으로 적용됐는지는 로그만으로 알 수 없으므로 확인된 표시 수에 더하지 않는다.

`native_result=1`과 DISPLAY60.06초는 제한 시간 종료다. `native_sink_error=2`, `sink_window_error=3`을 별도 통신 고장으로 단정하지 않는다. 배포 코드에서 window3은 transfer callback 실패이며, callback은 실제 SPI 전후에도 deadline guard를 검사한다. 첫 runtime 결과가 유지되는 구조라 이번 primary deadline 뒤 sink/window 오류가 붙는 경로와 일치한다. window3 자체를 guard2 또는 CRC4라고 잘못 해석하지 않는다. 전부0인 ACK는 invalid placeholder이고, flags3은 마지막 상태 표본의 queued+ACK-present이지 이번 최종 표시 성공이 아니다.

ROM/검증/receiver/video/STOP 오류0, STOP·기본 코어 복원·298490ms MENU_PREPARED까지 확인했다. 실제 파일 메뉴 표시는 이번 사용자 메시지에 명시되지 않아 로그 이상의 승인을 하지 않는다. SPC A9/unmute1과 사용자 청취가 일치하고, 조작 정상이라는 관측도 기록했다. 입력 기록은 마지막16개 변경값이며 A/B/RIGHT 동시 입력·해제 등이 보인다. 모든 버튼 유지시간을 검증한 자료는 아니다.

마지막16개 PPU 사건은 reject8/recovery8, 모든224행·29그룹, compact/raster 오류0이다. reject의 fetch 오류는01 네 번,04 세 번,06 한 번이다. 이는 회복 가능한 수집 거부도 남아 있음을 뜻한다. 시각·장면 연결과 거부 지속시간이 없고 generation은mod256이므로 스크롤과의 인과관계나 손실 프레임 수를 계산하지 않는다. 다른 비용과 함께 확인해야 하며 전송만이 유일한 원인이라고 단정하지 않는다.

## 코드에서 확인한 제약과 다음 작업

186은 같은 목적지 오프셋의 map을 비교하고, 같으면 이전 WRAM의 **같은 오프셋**을256바이트씩 복사한다. 화면이 옆으로 이동했을 때 이전 화면의 다른 위치에 있는 동일 타일을 찾아 재사용하는 방식은 아니다. 따라서 스크롤 시 복사 적중률이 낮아질 가능성이 있다. 현재 로그로 실제 적중률을 측정한 것은 아니다.

배포 converter는 매 화면 BG/OBJ 슬롯을 초기화하고 등장 순서로 배정하며, 그 화면에서 할당한 패턴을 다시 stage한다. 스크롤로 등장 순서가 변하면 같은 그림의 슬롯 번호도 바뀔 수 있어 map 차등과 CHR 전송 모두에 불리하다. SNES의 기존 로컬 VRAM 차등 업로드는 상류 FPGA→MCU 및 MCU→SNES 전송 자체를 없애주지는 않는다. fine X와 행별 vertical offset은 이미 HDMA로 처리하므로 단순히 스크롤 레지스터를 추가하는 작업을 반복하지 않는다.

다음은 보관된 실제 SMB3의 연속 스크롤 장면을 현재 converter에 통과시켜 map 변화·슬롯 재배정·CHR 전송량과 수집 거부/수신 대기를 구분한다. 전체60fps 경로를 기준으로 **화면 간 패턴 식별 안정화와 정확한 CHR 재사용, 이동한 map 재사용**의 비용·메모리 수명을 비교하고 가장 큰 실제 비용부터 줄인다. 먼저 COPY 크기만 다시 늘리거나 ACK 검증을 제거하지 않는다.

슬롯 재사용은 mapper bank 전환·CHR RAM 쓰기·행별 패턴/팔레트 변화·raw 전환·세대/비활성 bank/최종ACK를 함께 다뤄야 한다. 주소가 같다는 이유만으로 그림이 같다고 간주하지 않는다. bg_keys 공간은 OBJ scratch와 raw patch에 재사용 중이므로 기존 키를 그냥 보존할 수 없다. ARM 잔여1204바이트·SNES body3776/3776·세이브 SRAM 미사용 조건 아래 설계하고 필요한 최소 결합 검증 후 실기 첫 레벨로 간다.

이번 턴은 결과·계획 기록이며 새 FW/FPGA/ZIP은 없다. 같은186/044·별도 입력·불변 FIT 시험을 요청하지 않는다. GBC164·기존 증거를 유지하고, AV60fps→장기플레이/오류·reset로그→입력품질 순서 및 MMC4/5/state/mute/frameskip 요구를 보존한다.
