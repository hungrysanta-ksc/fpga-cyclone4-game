# NES187 화면 출력 구조 회고와 수정된 구현 계획

2026-10-15~16. 사용자 요청에 따른 164→186 회고. PR116 같은 branch. **187은 구조 검토 번호이며 새 실기판이 아니다.** 기준 배포는186 그대로다. [검증 요약](../analysis/video-arch187-verification.json), [재현 도구](../tools/nes_video_arch187.py), [186 실기](nes-game186-hardware01.ko.md).

## 판단

SNES의 타일·스크롤·스프라이트 기능으로 전송량을 줄이려던 방향은 유지한다. 그러나 현재의 **한 화면 수집→SPI 수신→MCU 변환→같은 SPI로 재전송→SNES 표시 완료**를 최종60fps 구조로 간주하는 계획은 수정한다. 화면 간 안정된 패턴 재사용, 수집과 전송의 겹침, 필요하면 카트리지 병렬 읽기 경로를 함께 설계한다. COPY 크기나 polling만 계속 조정하지 않는다.

자원 부족만으로 출력 방식을 바꾼 것은 아니다. 164도 TV 출력은 SNES PPU였다. 지금도 NES CPU·PPU·APU·매퍼의 실행과 게임상 타이밍은 FPGA가 맡는다. SNES가 NES PPU 에뮬레이션 전체를 대신하는 구조가 아니다.

| 경로 | FPGA에서 SNES까지 | 장점 / 한계 |
|---|---|---|
| 164 완성 픽셀 | FPGA 최종6비트 색 캡처 → 카트리지 bank40 읽기/DMA → SNES Mode3 8bpp | MCU 대량 데이터 왕복 없음. 하지만 화면마다57,344B를 업로드 |
| 186 그래픽 정보 | FPGA compact/raw 수집 → SPI → MCU 타일 변환 → SPI 큐 → SNES WRAM/VRAM → 표시 ACK | 원본 패턴·스크롤 재사용 가능. 현재는 매 화면 슬롯 재배정·재전송과 직렬 작업 비용이 큼 |
| 다음 후보 | 안정된 패턴 식별·소스 변경 추적 + 작은 불변 snapshot/부분 streaming + 병렬 bulk 읽기 후보 | 수집/전송/표시 처리량을 함께 개선. 아직 생산 구현·자원·실기 승인은 없음 |

FPGA에서 TV로 직접 RGB/HDMI를 출력하는 원본 FPGA 보드의 방식은 현재 카트리지 출력 배선과 같지 않다. 이것은 펌웨어의 경로 선택만으로 얻는 대안이 아니다.

## 과거보다 느린가

사용자가 예전이 더 빨랐다고 느낀 것을 부정할 근거는 없다. 예전에는 MCU 왕복이 없었고, 지금은 그 비용이 추가됐다. 다만 동일 장면의 신뢰할 수 있는 표시 시각 기록이 없어 양쪽의 실제 FPS 우열을 확정할 수 없다.

164는57,344B를5,632×10+1,024, 총11 VBlank에 나눴다. 60Hz 기준 새 완성 화면의 이론상 상한은 약5.45회/초이며 수집·준비 대기는 제외한 값이다. 당시 사용자 결과도 검정 구간 제거·사운드는 성공했으나 심한 끊김으로 정상 플레이는 실패했다. `screen_frames=281`은 신뢰 플래그0이어서 FPS로 환산할 수 없다. 163의 강제 블랭크 방식도 무점멸60fps 기준이 아니었다.

186은60.06초에 표시 완료182회(전체 평균3.03회/초), 수신27.71초·변환/CHR7.90초·나머지전송/표시23.95초다. 큐 요청은185 대비43.16% 줄었지만 완료 수는180→182였다. 다른 장면과 입력의 단회 결과이므로 인과적 개선율은 아니다. 정지 장면에서 절약한 바이트가 스크롤 처리량을 증명하지 못한다는 결과다.

## 현재의 절약된 FPGA 자원

숫자는 실제 FIT 보고서에서 추출했다.186은184의 배치·배선을 재사용한다.

| 자원 | 164 | 현재186 | 현재 잔여 |
|---|---:|---:|---:|
| LE | 14,711 / 15,408 | 13,466 / 15,408 | 1,942 |
| LAB | 960 / 963 | 939 / 963 | 24 |
| M9K | 56 / 56 | 42 / 56 | 14 |

14 M9K의 물리 비트 합은16,128B지만 포트 폭·깊이·배치 때문에 모두 임의의 바이트 저장소로 쓸 수 있다는 뜻은 아니다. LE는 약87%지만 LAB는 약98% 사용 중이다. 큰 조합 논리나 매퍼를13%만큼 더 넣을 수 있다는 보장도 없다.

예전 framebuffer는38 M9K, 소비기는2 M9K였다. 현재의 서로 겹치지 않는 native_frame15 + fill1 + native_spi1 + sink5를 통째로 뺀 뒤 예전 두 블록을 넣는 단순 회계는 `42−22+38+2=60 M9K`다. **이것은 합성한 복귀 후보가 아니다.** 관측 RAM 재배치·공유·ROM 대체로 달라질 수 있지만, 현재 절약량만으로 예전 경로를 그대로 붙일 수 있다는 가정은 성립하지 않는다. OAM 최적화는 어느 후보에서도 재사용할 가치가 있다.

256×224×6bit 화면 한 장은 저장 비트만으로 최소38 M9K다. 색강조 등을 픽셀당9bit로 보존한다면 최소56개다. 현재 native_frame15개를 단순 복제해도42+15=57개다. 따라서 여유 자원은 전체 프레임 이중 버퍼보다 **패턴 내용/세대 메타데이터와 작은 snapshot·streaming 버퍼**부터 수명·포트 표를 만들어 배분한다. 세이브 SRAM은 사용하지 않는다.

## 메모리를 늘려도 남는 전송 한계

SNES DMA는 바이트당8 master cycle과 추가 시작 비용이 든다. VRAM은 VBlank/강제 블랭크 동안 갱신해야 하며, 카트리지→WRAM DMA를 활성 화면 중 수행할 수 있어도 SCPU는 정지한다. [Anomie의 SNES timing 문서](https://github.com/gilligan/snesdev/blob/master/docs/timing.txt).

- 8bpp 전체57,344B의 순수 DMA 시간만 약21.36ms다. 16.67ms보다 길고 실제 VRAM 허용 시간은 더 짧다.
- NTSC224줄의 VBlank 전체를 환산한 약6,308B도 시작·HDMA·CPU 작업 전의 거친 상한이다. 안전한 업로드 예산으로 그대로 채택하지 않는다.
- 같은2.625MHz SPI를 쓰는 양방향 합계는16.67ms에 이론상5,469B다. 상태 조회·헤더·간격·MCU 계산은 아직 빼지 않은 수치다.

기존 실제 C→65816 합성7화면의259 request/ACK를 다시 읽었다. 초기 normal의30요청/5,357B는 필수 E1/CRC만 더해도 전송 하한16.60ms다. 다른6화면의 하한은4.10~16.60ms다. **이것은 egress만의 낙관적 하한이며 실제 SMB3 스크롤이나 FPGA→MCU ingress를 포함하지 않는다.** 여기에 서로 다른 장면의 ingress를 더해 실측이라고 부르지 않는다.

같은5,357B가 이미 준비된 카트리지 읽기창에 있다면 WRAM DMA 하한은 약2.00ms다. 병렬 경로를 검토할 이유는 충분하지만, 이 수치로8배 실제 향상을 약속할 수 없다. 데이터 생성/변환·읽기 타이밍·SCPU decode·VRAM 업로드가 남는다. MCU가 그 창을 채우느라 같은 SPI 바이트를 그대로 쓴다면 병목을 옮긴 것뿐이다. **소스에서 데이터가 어디서 만들어지고 어디에 보관되는지까지 포함해야** 대안이 된다.

## 원래 계획과 현재 구현 사이의 차이

[165 최초 조사](nes-video-transfer-research.ko.md)는 원본 CHR 패턴의 안정된 재사용을 핵심으로 잡았다. [PocketNES 실제 소스](https://github.com/Dwedit/PocketNES/blob/main/src/ppu.s)도 CHR-RAM 쓰기로 dirty 타일/행을 표시하고 캐시에 저장한다. 이 원리는 최종 화면 좌표별 픽셀 차분과 다르다. 기기의 버스·PPU가 달라 속도 수치를 이식할 수는 없다.

현재 생산 C는 매 화면 BG 키와 슬롯을 다시 만들고 할당한 패턴을 다시 준비한다. 185/186 COPY는 같은 map 오프셋의 재사용이지 안정된 CHR 캐시가 아니다. 화면이 스크롤하면 동일한 패턴도 슬롯/배치 변화로 재전송될 여지가 있다. PC 참조의 영구 슬롯 기능이 생산 경로까지 완료됐다고 보면 안 된다. `bg_keys`는 OBJ scratch/raw patch와 메모리 수명을 공유하므로 단순히 초기화를 없애서 캐시로 만들 수도 없다.

[181 cadence 계약](nes-cadence181-contract.ko.md)에 이미 남긴 수집 병목도 여전히 중요하다. 현재 수집은 line7/dot257 시작, line232/dot1 종료이며 다음 시작까지60Hz 참조 모델상 약2.401ms다. exporter COMMIT이 transport에 받아들여질 때 수집 버퍼를 해제하고8,192클록 scrub을 수행한다. 이것은 **SNES 표시 ACK와 다른 사건**이다. MCU는 별도로 conversion→seal→표시 ACK까지 단일 workspace를 점유한다. 그러므로 전송 바이트만 줄여도 매 원본 프레임 수집/표시가 된다고 볼 수 없다.

부팅·ROM 응답·화면 중단 복구·음성·입력 유지·원자적 화면 공개를 고친 작업은 유지할 기반이다. 반면 핵심 재사용/수집 겹침을 미룬 채 지역적 절약률로60fps에 접근한다고 판단한 것은 비효율이었다. 앞으로는 바이트 절약률보다 **대표 스크롤 장면의 소스 수집률·전송 서비스 시간·표시 완료 간격**을 함께 채택 기준으로 삼는다. 파이프라인 지연과 처리량도 구분한다: 몇 프레임 지연이 있어도60Hz 처리는 가능하지만, 공유 자원 점유와 버퍼 재사용이 다음 프레임을 막아서는 안 된다.

## 여러 매퍼로의 확장

현재 제품 연결은 `mapper_flags=4`, `MMC5=0`이며 CHR 수집 lookup도8,192태그/물리주소[16:4], 즉 현재 SMB3의128KiB CHR 범위를 전제로 한다. 일반 매퍼/더 큰 CHR/CHR-RAM을 이미 지원한다고 볼 수 없다. `cart_nrom.sv`라는 파일명도 실제 지원 범위를 설명하지 않는다.

[상위 NES_MiSTer cart 구현](https://github.com/MiSTer-devel/NES_MiSTer/blob/master/rtl/cart.sv)은 MMC4와 MMC5를 별도 연결하고 MMC5에 CHR 반환 데이터·확장 속성·쓰기·오디오·상태 포트를 둔다. 단순 주소 변환만 추가하는 것으로 끝나지 않는다.

다음 구조는 실제 PPU fetch 시점의 해석된 데이터/매핑을 보존해야 한다. MMC4 latch, MMC5 ExRAM/확장 속성·분할·IRQ·확장 음성과 CHR-RAM 내용 변경을 나중에 최종 레지스터 값으로 재구성하면 안 된다. 캐시 식별은 물리 패턴 주소만 아니라 내용 세대·행 구성/매핑 변화까지 포함한다. 해시 일치만으로 내용 동일을 단정하지 않는다.

SNES가 표현할 수 있는 행/팔레트/OBJ 한계를 넘는 경우의 raw fallback도 남긴다. 현재7행 raw·팔레트/그룹/OBJ 제한을 범용 NES 지원이라고 홍보하지 않는다. 모든 매퍼를 한 bitstream에 동시에 넣기보다 **게임 로드 시 매퍼 계열별 FPGA 구성 선택**을 우선 후보로 삼아 자원을 공유한다. 아직 구현/FIT되지 않았으며 MMC5에 충분한 여유가 확보됐다는 주장은 하지 않는다. 상태 저장·로드에서는 캐시/화면 base를 무효화하고 정합성 있게 재시작해야 한다. mute/frameskip을 위해 게임 실행·음성·화면 소비의 소유권을 분리한다.

## 수정된 다음 작업과 중단 기준

1. **대표 데이터로 선택:** 이미 보관한 SMB3 연속 스크롤의 실제 fetch/CHR/map/표시 자료를 같은 세대로 묶는다. 초기/정지/스크롤/장면 전환 각각 ingress+egress, CHR 재사용, 수집 누락, 대상 VRAM 변경량을 계산한다. 없는 정보는 미측정으로 남기고 전체 게임 긴 시뮬레이션부터 반복하지 않는다.
2. **설계 후보를 작게 비교:** 안정된 패턴 슬롯·CHR 내용 세대 추적과 작은 snapshot/부분 streaming을 묶는다. 현재 SPI 유지 후보와 FPGA 준비 데이터의 카트리지 병렬 bulk 읽기 후보를 동일 데이터로 비교한다. MCU왕복을 실제로 줄이는지, 버퍼 포트/수명·14M9K/24LAB 및 매퍼 여유가 성립하는지 먼저 표로 확인한다. 첫 후보는 prepared read aperture의 주소/데이터/세대 소유권까지 작게 구현해 기존 SNES 읽기 경로와 연결하는 것이다. 전체 새 출력 엔진을 한 번에 만들지 않는다.
3. **소수의 의미 있는 검증:** 스크롤 중 기존 패턴 재사용, CHR-RAM/뱅크 변화, raw 진입/복귀, backpressure/STOP/reset, 쓰는 중 snapshot을 읽지 않음을 실제 경계에서 검증한다. 현재 소리·입력 서비스와 최종 표시 ACK를 유지한다. 실패하면 보호 검사를 없애지 말고 해당 설계를 수정한다.
4. **실기 채택:** 전체 서비스 예산이16.67ms 처리량과 양립하고 실제 메모리·배치/타이밍이 맞는 후보만 짝패키지로 만들어 SMB3 숫자1+A/연속 달리기로 시험한다. 초기 keyframe/장면 전환 비용과 지속 스크롤을 구분해 기록한다. 같은186/044, 별도 입력 시험, 변경 없는 FIT는 반복하지 않는다.

최대 변화 장면이 예산을 넘으면60fps 범용 지원을 선언하지 않는다. 화면 생성은 계속하며 오래된 대기 화면을 버리는 명시적 frameskip 정책을 별도로 정의할 수 있지만, 부분 화면/서로 다른 세대를 섞거나 낮은 표시율을60fps로 부르지 않는다. AV 개선→장기 플레이/오류·실기 reset 로그→입력 품질 순서를 유지한다.
