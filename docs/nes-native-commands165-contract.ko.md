# NES165 타일·스프라이트 갱신 명령

fetch165 이벤트를 실제 SNES VRAM/OAM/CGRAM/HDMA 바이트로 바꾸는 **개발 PC용 참조 소비자**를 구현했다. 합성 장면을 SNES CPU/DMA/PPU 모델에서 실행하여 원본 이벤트로 그린 픽셀과 대조했다. FPGA/MCU에서 이 소비자가 실행되는 것은 아니며, 설치 후보와 실기 속도는164 상태다.

[검증](../analysis/native-commands165-verification.json) · [이벤트 입력 계약](nes-native-fetch165-contract.ko.md) · [소비자](../tools/nes_native_commands165.py) · [실행 시험](../tools/test_nes_native_commands165.py).

## 입력과 표현

- 입력은 앞서 정의한64비트 fetch 이벤트,224행의 fine X/표시 마스크/유효 팔레트32색, 물리 태그별 완성된 CHR16바이트다. 이번 시험은 합성 이벤트와 PC가 제공한 완성 타일을 사용한다. 실제 FPGA 스트림/행 상태의 직렬화·전송·누락 타일 읽기는 연결하지 않았다.
- 배경은33열의 물리 타일/팔레트가 같고 fine Y가 이어지는 행을 묶는다. 최대32개 타일맵 행으로 표현하고, 표시 행별 스크롤 차이는 HDMA로 적용한다. fine X를 픽셀로 다시 그리지 않는다.
- 스프라이트는 실제 평가 결과의 X/물리 타일/위쪽 행/속성/팔레트가 같은8×8 조각으로 합친다. 실제 평가되지 않은 행은 패턴 바이트를0으로 만들어 가린다.8×16 결과는 물리 타일 두 조각으로 표현한다. 이전 평가 순서가 유지되는 OAM 순서를 만들 수 없으면 거부한다.
- 물리 태그에 SNES 패턴 슬롯을 할당한다. 다음 장면에도 필요한 태그는 슬롯을 유지하고, 빠진 태그의 슬롯만 재사용한다. OBJ는 평가된 행 마스크도 키에 포함한다. 같은 논리 슬롯의 다른 물리 타일을 같은 패턴으로 오인하지 않는다.
- 팔레트는 기존164의 RGB555 변환을 재사용한다. 최대2개 팔레트 묶음을 CGRAM에 동시에 배치하고 타일/OBJ의 팔레트 번호로 선택한다. 이는 PC 기준의 디지털 색 대조이며 CRT의 아날로그 색 재현 승인은 아니다.

## 메모리와 게시

| SNES 공간 | 사용 |
| --- | --- |
| VRAM 바이트0000–3fff | BG2bpp 최대1023패턴과 투명 슬롯0 |
| VRAM 바이트4000–7fff | OBJ4bpp 최대512패턴; 상위 플레인은0 |
| VRAM 바이트8000–8fff | 64×32 BG타일맵1개,4KiB |
| OAM | 최대128개8×8 조각,544바이트 |
| CGRAM | BG8팔레트/OBJ8팔레트와 공통 배경색,512바이트 |
| WRAM7E:9000 | 직접 mode3 HDMA 표, 최대224×5+1바이트 |

VRAM 주소는 표에서 바이트 기준이다. SNES 레지스터에는 워드 주소로 설정한다. SNES의 숨겨진 첫 스캔라인을 반영하여 VOFS를1줄 보정한다. [Mesen SNES PPU 구현](https://github.com/SourMesen/Mesen2/blob/master/Core/SNES/SnesPpu.cpp), [SNES PPU와 NES의 차이](https://snes.nesdev.org/wiki/SNES_PPU_for_NES_developers)를 참고했다. 두 장면 전체 픽셀 대조가 실제 레지스터 설정·우선순위·반전·스크롤 결과를 확인한다.

앞선40KiB/타일맵 이중화 제안에서 이번 참조 구현은 **36KiB/타일맵1개**로 좁혔다. 초기 화면은 forced blank 중 적재하고, 이후에는 한 vblank 안에 끝나는 갱신만 승인하는 계약이다. 여러 vblank에 나누어 같은 맵/패턴을 덮으면서 원자적 전환이라고 하지 않는다.

변경된 VRAM 워드를 찾고32바이트 이하의 간격을 합쳐 DMA 수를 줄인다. CGRAM/OAM/HDMA는 내용이 바뀌면 각 묶음을 전송한다. 후속 화면은 `payload + 96×명령 수 ≤ 5000`, 명령32개 이하일 때만 준비한다. **5000/96은 보수적인 개발 정책이며 보드의 최악 실행시간을 증명한 값이 아니다.** 실제 MCU/SNES 전송기와 입력/음성/종료 처리를 연결한 뒤 실행 예산을 확정해야 한다.

`prepare`는 게시 상태를 바꾸지 않는다. 지원 범위·완성 타일·용량·전송 예산을 하나라도 만족하지 못하면 예외로 거부하며 이전 상태를 유지한다. `commit`은 승인한 묶음에만 적용하고, 이미 적용한 세대는 다시 적용할 수 없다. 실기에서는 실제 전송 ACK 후에만 이 상태를 전진시켜야 한다. 현재 세대는 PC 정수이며 보드의 고정폭 세대/CDC를 대신하지 않는다.

## 지원 범위와 거부

현재 참조 소비자는 마스크`1e`(BG/OBJ와 왼쪽8픽셀 표시, 강조/흑백 없음),224행 모두33BG이벤트, 최대2팔레트/공통 배경색,32BG행,128OBJ조각을 요구한다. NES 행당8개 평가 규칙 외에 SNES 행당32개 객체 제한도 확인한다. 투명하게 가린 OBJ도 SNES 평가 개수에 포함한다. 모든 객체가8픽셀 폭이므로34개 슬리버 제한도 넘지 않는다.

표시 비활성/왼쪽 클리핑/강조, 배경색의 행 중 변경,3개 이상 팔레트, 더 복잡한 래스터/객체 순서는 지원했다고 하지 않는다. 실제 SMB3 첫 레벨이 이 범위를 만족하는지는 아직 측정하지 않았다. 범위 밖 장면을 조용히 틀리게 그리거나 화면이 최신이라고 표시하면 안 된다. 실기 연결 전 실제 게임 이벤트에서 필요한 조건을 확인하고 해당 조건만 추가한다.

## 선택 시험02

| 항목 | 결과 |
| --- | --- |
| 입력 | 장면당7469개 합성 이벤트,30BG묶음,12OBJ조각 |
| 첫 적재 | 5755바이트/6명령, forced blank 중 적재 |
| 스크롤·타일·OBJ 위치 변경 | 573바이트/4명령, 계산 예산957 |
| 갱신 완료 | SNES 모델 스캔라인230; 모든 표시 후 VRAM/OAM/CGRAM 쓰기는 vblank 내부 |
| 픽셀 대조 | 두256×224장면, 총114688픽셀 완전 일치 |
| 변화 없는 장면 | 전송 명령0개 |
| 거부 | 예산·누락/중복BG·누락타일·예약비트·팔레트/마스크·BG행 용량·중복commit·OBJ순서/중복rank/OAM용량/행당평가 용량,13가지 |

실제 SNES 코드가 VRAM/OAM/CGRAM DMA와 행별 HDMA를 실행한다. 독립 기준 영상은 원본 NES 이벤트/플레인/팔레트에서 직접 계산하며 컴파일된 SNES 타일맵/슬롯/OAM을 사용하지 않는다. 겹치는 객체 우선순위, 양축 반전, 상하·오른쪽 crop, 평가 행 누락, 팔레트 경계, 수평/수직 스크롤 변경을 포함한다. 화면 공개 뒤 추가 forced blank는 없다. 시험 ROM801바이트 코드는 고정된 두 묶음을 펼쳐 실행하는 공급기이며, 최종2KiB SNES 프로그램/명령 파서는 아니다.

시험01도 통과했다. 시험02는 실제 스크롤 변화와 추가 용량 거부를 포함한다. 출력·원시 로그를 둘 다 보관했으며02를 선택했다. 변경 없는 Questa/전체 NES 부팅/FPGA 배치/ARM/044복원을 반복하지 않았다. 두 모델 장면의 작은 전송량을 실제 SMB3 프레임률이나60fps 증명으로 확대하지 않는다.

## 다음 작업

1. 실제 fetch/raster 스트림에서 이 표현을 온라인으로 생성하는 제한된 생산자와 물리 태그별 누락 CHR 보충을 연결한다. PC의 전체 이벤트 목록/64KiB shadow VRAM/정렬 자료구조를 그대로 FPGA에 옮기지 않는다. 원시73472바이트 프레임 버퍼도 만들지 않는다.
2. 게임 실행 한 번에서 수집·변환을 함께 확인하여 SMB3의 표시 마스크/팔레트/조각 용량·전송량을 측정한다. 초기 부팅만 따로 재검사하거나 합성 장면 종류만 계속 늘리지 않는다. 범위 밖이면 필요한 표현부터 수정한다.
3. host CDC, 전송 ACK, 유한 vblank 소비자와38M9K 기존 픽셀 버퍼 교체를 묶어 구현한다. 실제 자원/타이밍과 최소 변경 검사를 거쳐 SMB3 첫 레벨 실기로 간다.164 사운드·STOP/메뉴를 유지하고, 그 뒤60초 제한·오류/리셋 로그·장시간 입력 유지를 진행한다.
