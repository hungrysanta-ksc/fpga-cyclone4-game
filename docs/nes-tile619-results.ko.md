# 619 · 954의 tile 수락 마감과 독립 검사 비용

**독립 검사만 단축한 후보를 다음 비교에 보존한다.** 53화면 마지막 ACK가 두 위상 모두 한 VBlank 빨라졌다. 954의 표시 간격은 모든 경우 5 VBlank였다. 늦은 tile 허용을 함께 적용하면 위상 1에서 오히려 마지막 ACK가 33.236 ms 늦어져 결합 후보는 제외한다. 보드 준비 기준은 616B, 실기 기준은 MMC613이다.

| 65816 구성 | 951–955 표시 합계(VBlank) | 평균 표시 간격(ms) | 마지막 ACK 차이(ms, 618 대비) | 954의 다음 VBlank로 넘어간 tile |
|---|---:|---:|---:|---:|
| 618 | 22 / 22 | 73.115 / 73.138 | 0 / 0 | 544 / 544 B |
| 늦은 tile만 | 22 / 22 | 73.117 / 73.133 | −0.042 / −0.048 | 544 / 544 B |
| 독립 검사 단축만 | 22 / 21 | 73.064 / 69.842 | −16.700 / −16.676 | 544 / 0 B |
| 둘 다 | 22 / 21 | 73.063 / 69.837 | +33.236 / −16.676 | 0 / 0 B |

각 셀은 시작 클록 3,000,000 / 3,178,684 순이다. 검사 단독 후보에서 위상 1의 표시 간격 이득은 922에서 발생했다. 위상 2에서는 922의 1회 증가와 923의 1회 감소가 상쇄되고 955가 5→4 VBlank가 됐다. 네 구성 모두 952 표시 간격 4회, 955 첫 map 192B와 후반 384B 선행, 957 최종 대기 0회를 유지했다. 905–957의 RGB·map·일반/압축 payload·tile 작업, VRAM DMA 총 114,352B가 기준과 일치했다.

954에서 독립 검사 진입부터 업로드 진입까지는 618의 1.325 / 1.325 ms에서 검사 단독 후보의 0.624 / 0.625 ms로 줄었다. 결합 후보는 **SEAL 검사 후 같은 VBlank**에 map 192B와 tile 544B를 모두 보냈다. 그 뒤 raw 처리로 넘어갈 때 이미 249 / 251번 라인이어서 최종 표시의 246번 검사선을 지났다. raw 192B, 팔레트 512B, OAM 544B와 실제 표시는 다음 VBlank에서 실행됐다. 두 위상 모두 954를 한 VBlank 당기려면 검사 후 DMA 외의 작업도 앞당겨야 한다.

## 618에서 남은 544B

954의 마지막 선행 DMA 기회에서 65816은 map 1,152B와 384B를 전송했다. 다음 세 tile은 그때 아직 수락되지 않았다. 아래의 마감은 252번 라인이 끝나는 시점이다. 마지막 master clock은 두 위상에서 모두 79,322,976이다.

| tile과 비활성 뱅크 내 offset | 마감 이후 65816 수락, 위상 1 | 위상 2 |
|---|---:|---:|
| BG 144B · 1968 | 1.475 ms | 1.473 ms |
| BG 16B · 1952 | 2.667 ms | 2.666 ms |
| OBJ 384B · 1888 | 4.513 ms | 4.425 ms |

두 번째 plan 묶음(15개)을 받은 직후의 BG 주소 98,752 읽기가 ROM 허가까지 **14.837 / 14.872 ms**를 기다렸다. 허가는 선행 DMA 마감 0.415 ms 전이었다. 144B BG 생산이 끝났을 때 남은 시간은 0.112 ms였다. 그 뒤 ARM의 상태 조회·E1 발행과 65816 수락이 이어졌다. 실제 패킷 도착을 고정한 618 재생에서 selector와 53화면 추적을 원래 실행과 대조했다.

이 144B를 완성하려면 두 번째 plan 묶음부터 ROM 읽기 96회가 더 필요했다. 첫 plan 슬롯 해제 이후 직전 ROM 허용 구간에는 259회분의 허가가 남아 있었다. 끝에서 96번째 허가는 클록 78,968,544였다. 같은 주소·캐시 적중을 가정하면 다음 묶음의 첫 요청을 적어도 **1.251 / 1.216 ms** 앞당겨야 이 구간에서 96번을 모두 읽을 수 있다. ARM 준비·SPI·주소 사이 간격까지 충족하는지는 후속 실행으로 확인해야 한다.

## 실제 65816에서 바꾼 두 부분

- 늦은 tile 후보는 233–252번 라인에서도 선택된 tile이 384B 이하이고 우선할 map tail이 없으면 DMA를 허용한다. 수락된 비활성 뱅크의 작업만 사용한다. DMA 직전 STOP·새 head의 우선권과 동기 DMA 뒤 retirement를 유지한다.
- 독립 검사 후보는 SEAL의 144B tile 요구 비트맵과 대상 뱅크의 유효 비트맵을 16B씩 순회한다. 각 16비트 워드에서 요구된 비트가 누락되면 같은 오류 경로로 간다. 두 뱅크의 행 검사, cold 검사, 246번 최종 빔 검사와 ACK 발행 조건은 기존 코드를 사용한다.
- 618 ARM03과 FPGA·ROM 달력을 고정하고 기존 618, tile만, 검사만, 둘 다의 네 경우를 비교했다. ARM Flash는 212,992B다. 65816 본체는 각각 5,068 / 5,080 / 5,157 / 5,169B다. 모두 6KiB 진단 배치에서 실행했다.

## 경계 시험

결합 후보에서 252번 라인 후반에 시작을 허용한 384B tile의 첫 쓰기와 마지막 쓰기는 254·256번 라인이었다. 400B는 0B, 새 head를 제시한 128B와 STOP·새 head가 겹친 384B도 0B였다. 실제 1,152B map의 경계와 두 뱅크의 누락·중복, SEAL의 예산 계산 및 최종 표시 진입 시 STOP도 확인했다. 두 뱅크 각각 비트맵의 0·15·16·143번째 바이트에서 요구 비트를 세우고 유효 비트를 지운 8건 모두 오류 ACK와 직전 화면을 확인했다. 최초 경계 fixture에서 합성 tile payload가 후속 정상 패킷의 범위와 겹쳤다. 정상 표시까지 진행하는 새 head 시험에는 원래 128B payload를 사용하고, 384·400B fixture는 STOP 경로에 한정해 다시 검증했다.

## 재현

1. `tools/nes_tile619.py <출력> --mode tile|coverage|both`로 65816을 각각 생성한다.
2. [618 실행 조건](nes-oam618-results.ko.md)의 arm03을 사용해 `tools/test_nes_board611.py`를 시작 클록 3,000,000과 3,178,684에 실행한다. ARM 명령·SPI/IRQ·두 슬롯·65816/PPU는 연결 일정으로, ROM 중재는 기존 8개 부트 프레임의 실측 허가 달력을 반복해 평가한다.
3. `tools/replay_nes_quiet608.py --generation 954`로 두 위상의 618을 재생한다. 결합 후보에서 `tools/test_nes_tile619_edges.py`, `tools/test_nes_map616_edges.py`, `tools/test_nes_seal538_stop.py`를 실행한다. `tools/analyze_nes_tile619.py`로 프로그램·입출력·시각·RGB·map 해시를 대조한다. [기계 판독 결과](../analysis/tile619-verification.json)
4. 검사 단독 후보에서도 같은 세 경계 시험을 실행한다. 보드 FIT·STA·실기 메뉴 복귀·FPS는 새 전달본 단계에서 확인한다.
