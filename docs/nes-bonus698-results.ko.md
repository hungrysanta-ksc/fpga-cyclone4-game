# 698: 월드 1 스페이드 진입과 MMC696 오류 재현

**실제 ROM에서 치트 해제 후 보너스 게임에 진입했고, 선택된 MMC696 RTL의 경계 재생에서 실기와 동일한 ROM·PPU 오류 문맥을 재현했다.** 원인은 주소 계산 오류보다 **CHR 뱅크 전환 직전 옛 주소 읽기가 먼저 수락되어 새 주소 읽기의 마감을 소모하는 경로**다. 생산 코드 수정·새 설치본은 아직 없다.

## 실제 ROM의 단축 진입

대상은 사용자의 SMB3(J), mapper4, SHA256 `dbb1cb5e18b091ca9101b1c2f5a5d6bdbeaa4a30ae1a504251310f6765cabb49`다. 다른 지역판의 주소라고 가정하지 않았다. [Southbird 공개 역어셈블리](https://github.com/captainsouthbird/smb3/blob/master/smb3.asm)의 맵 좌표 설명을 참고하고 실제 ROM의 RAM·화면으로 확인했다.

| 시점 | 조작·확인 |
|---|---|
| 월드 1 맵 대기 | CPU RAM `$0075=40`, `$0079=20` 확인 |
| frame350, 한 번만 | `$0075:40→60`, `$0079:20→80`; Y/X 좌표 두 바이트만 변경 |
| 이후 | RAM 치트 쓰기 없음. 레벨 데이터·CHR·ROM·사용자 저장 파일은 수정하지 않음 |
| frame360–365 A | 스페이드의 정상 안내 화면 진입 |
| frame550–555 A | 회전 그림 게임 시작; frame650·680 화면 확인 |

초기 START는 frame30–33,90–95다. 선택한 재생은 `reference06`, 680프레임이며 frame355의 진입 직전 화면과 관리형 Mesen의 진입 직전 상태도 비공개 근거에 보존했다. 이 단축은 1·2레벨 완료 이력을 재현하지 않는다. 원래의 보너스 진입 코드를 실행하는 최소 위치 개입이며, 14분 플레이 이력을 통째로 복원한 것은 아니다.

GUI 없는 reference 시험에는 NES 패드 설정이 필요했다. 패드 없는 첫 시도들은 제목 화면에 남았으므로 장면 통과로 사용하지 않는다. 최종 시험은 위치 변경 전 원래 좌표가 `40/20`인지도 검사한다. 전체 CPU 부팅 RTL은 6프레임까지 실행 후 비용이 커 중단했다. 그 종료 뒤의 EOF/라이선스 프로세스 메시지는 강제 종료 결과이며 새 라이선스 장애가 아니다. 이후 시험은 동일 1좌석 FLOAT로 순차 실행했다.

## 실제 게임이 만드는 위험 구간

회전 게임에서 192번 주사선에 CHR register5를 `$7E`로 바꾸는 쓰기를 93회 관측했다. 시점은 dot250,252,253,255,256,258,259,261이며, frame588은 **dot261**이었다. 그 순간 PPU는 8×16 sprite 모드이고 secondary OAM 첫 네 바이트는 `F8 FF FF FF`였다.

이 OAM 값을 선택 PPU의 SpriteAddressGen에 공급하면 논리주소 `$1FE7`이 나온다. MMC3 bank5가 `$23→$7E`로 바뀌면 물리주소는 `$208FE7→$21FBE7`이 된다. 후자는 실기 오류의 pending/demand 주소와 같다. 실기와 참조 에뮬레이터의 주사선 번호가 비슷하다는 이유만으로 동일하다고 하지 않고, 실제 선택 RTL에서 두 문맥 값을 비교했다.

## 분리 재생 결과

선택694 보드의 PPU·MMC3·early ROM service·168MHz physical reader를 바이트 그대로 사용했다. ROM 데이터는 실제 파일, PSRAM 모델은 70ns, READ_CYCLES는 실제 보드의16이다. PPU clock enable·CPU 출력 버스 위상과 secondary OAM 입력을 시험벤치가 공급한다. 실제 CPU 명령 전체·collector/export/tile 실행은 포함하지 않는다.

| 조건 | 3개 메모리 위상 결과 |
|---|---|
| bank `$7E`가 이미 확정 | 통과, CHR 소비 바이트 독립 대조 일치 |
| bank 변경을 충분히 일찍 확정 | 통과 |
| dot261의 네 master-clock 위치에서 `$23→$7E` 변경 | **12/12 동일 오류2** |
| 먼저 수락된 CPU 읽기 뒤 bank 변경 | 이 배치에서는 통과: 옛 CHR 요청이 시작되는 것을 지연시킴 |
| bank 유지 + 같은 CPU 읽기 | 통과 |

위상은0/3.5/5.5ns이며 총24개 조건이다. 오류12개 모두 아래 값이 실기와 **64비트 전체 일치**했다.

```text
ROM context: e200c3f7ce21fbe7
PPU state:   604198007f9f9f9c
error:       2 / line192 / dot262 / pending=demand=21fbe7 / age1
```

대표 실패의 NES master-clock 일정은 다음과 같다.

| step | 사건 |
|---:|---|
|48 (dot261 시작)|논리주소 `$1FE7` 확정, 기존 bank `$23`의 `$208FE7` 읽기 수락|
|49–52|실제 bank `$7E` 반영; 옛 읽기는 취소되지 않고 진행|
|53|옛 응답 도착, 새 주소 `$21FBE7` 읽기 수락|
|55 (dot262 소비)|새 읽기 age1·응답 없음 → 독립 마감 검사 오류2|
|58|새 데이터 응답; 필요한 시점보다3 master clocks 늦음|

master clock 주기46.560846ns 기준 새 요청에 남은 시간은 약93.12ns이고, 이 재생의 응답은5클록 뒤였다. 늦어진3클록은 약139.68ns다. 프레임 전체 지연이나 실측 보드 IO 시간으로 확대 해석하지 않는다.

주소 생성 자체는 올바르다. 현재 mapper의 raw-write preview는 별도 hint 포트에 있지만 PPU hint가 sprite fetch를 제외한다. 정상 CHR 포트는 commit된 bank를 사용하므로, 같은 경계에서 옛 주소 요청이 먼저 허가된다. **외부 tile 트래픽 없이도 실기 서명이 재현되므로 tile 경쟁은 이 실패의 필수 조건이 아니다.** 반대로 모든 경쟁을 줄이면 안전해진다는 결론도 틀린다. 위 CPU 대조군처럼 옛 요청의 시작을 막아 우연히 통과할 수 있다. 실기 직전의 전체 중재 이력은 로그에 없으므로 이 단일 경로가 유일한 발생 경로라고 단정하지 않는다.

## 보호 조건과 다음 수정 경계

24조건 모두 종료 시 공통 STOP/reset으로 미완료 읽기·응답·valid·PSRAM OE가 차단됨을 검사했다. 다음 조건의 reset 해제 뒤 정상 읽기도 재실행했다. 독립 실제 sample 마감과 ROM 바이트 대조는 유지했다. 오류를 무시하거나 timeout·NES clock을 바꾸지 않았다.

ARM·65816·최종 ACK·STOP/base/menu 생산 코드는 바꾸지 않았다. 메뉴 복귀의 새 실기 시험은 아니며, 기존696의 실제 복귀 성공과694 검증을 유지한다. 실패한 프레임에 최종 ACK를 강제로 만드는 변경은 없다. 생산 변경이 없어 Flash·회로 비용의 새 절감이나 FIT 결과도 주장하지 않는다.

다음은 **sprite 주소 확정·mapper preview·옛 요청 수락을 한 경계로 묶는 최소 수정**이다. 이미 진행 중인 옛 읽기를 무조건 덮어쓰거나 정상 mapper 시점을 앞당기지 않는다. 유효 sprite·dummy sprite, 같은/다른 bank, 실제 CPU/plan 경쟁, STOP 전후에서 물리 tag와 독립 소비 검사를 유지해야 한다. `F8 FF FF FF`가 dummy fetch라는 이유만으로 전체 PPU 검사를 끄는 방안은 채택하지 않는다. 위24조건을 재사용하고 실제 CPU 쓰기 안정 구간을 추가 연결한 뒤 전체 보드 비용·두 위상 표시 일정·메뉴 경로를 검사한다. 안정성 수정 전 출력 미세 최적화는 보류한다.
