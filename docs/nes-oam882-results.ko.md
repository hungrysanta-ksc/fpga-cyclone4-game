# 882 · map 전송이 없는 화면의 OAM 재사용 순서

전환 952는 map 업로드 없이 BG 16B 하나를 갱신한다. 881은 BG 뒤에 section 5의 201B·240B 패킷을 먼저 보내고 OAM 재사용 명령을 SEAL 바로 앞에 보냈다. 882는 기존 두 뱅크의 최종 ACK 이력과 팔레트·OAM 일치 검사를 통과하면 OAM을 앞에 보낸다. 세대 번호는 ARM의 발행 조건에 쓰지 않는다.

## 952의 같은 바이너리 대조

map 업로드가 없는 화면 전체에 적용한 첫 링크에서 **전환 952 한 장**의 발행 순서만 되돌렸다. 두 실행은 951 공개 클록까지 같고, SPI가 처음 달라진 세대는 952다. 큐 순번을 제외한 모든 패킷의 내용·개수와 952의 최종 RGB가 일치했다.

| 전환 952 | 위상 1 | 위상 2 |
|---|---:|---:|
| SEAL 수락을 앞당긴 시간 | 36,188클록 (1.685ms) | 24,664클록 (1.148ms) |
| 이전 순서에서 마지막 DMA | VBlank 141, 231선 | VBlank 141, 231선 |
| OAM 우선일 때 마지막 DMA | VBlank 140, 232선 | VBlank 140, 232선 |
| OAM 우선일 때 공개 | VBlank 140, 235선 | VBlank 140, 235선 |

이전 순서에서는 BG 16B까지 VBlank 140에 들어갔다. OAM을 먼저 보내면 같은 VBlank에 raw CHR 64B 세 번, 팔레트 2B, OAM 112B까지 들어가서 951→952 간격이 2회에서 1회로 줄었다.

|---|---:|---|---:|---:|---:|
| MMC872 | — | 59·231 / 59·231 | 119 / 119 | 141 / 141 | 65,017,306 / 65,380,210 |
| 881 | 212,964B | 60·228 / 60·231 | 120 / 120 | 139 / 138 | 64,302,558 / 64,303,112 |

| 타일 한 개 + SEAL 직접 작성 | 212,988B | 59·250 / 60·231 | 119 / 119 | 138 / 140 | 63,945,512 / 65,017,724 |

두 번째 후보는 212,992B 한도를 8B 초과했다. 세 번째는 6개 길이를 최종 SEAL 버퍼에 직접 써 12B를 줄였다. 세 장면의 모든 세대에서 881과 SEAL의 세대·길이·데이터가 일치했다. 두 위상의 전환 941 공개는 118, 952 공개는 140이다. 밀집 950은 1,472+64B 선행 DMA와 표시 3회를, 밀집 952는 표시 2회를 유지했다. 위상 2에서 950과 952의 공개는 881보다 한 VBlank씩 늦었다. 오프닝 759의 공개는 174 / 174로 기준 176 이내였다.

최종 후보의 밀집 마지막 ACK는 MMC872보다 49.904 / 16.878ms 빨랐다. 881과 비교하면 위상 1은 16.624ms 빨라졌고 위상 2는 33.273ms 늦어졌다. 실기 기준은 MMC872로 유지한다.

## 밀집 위상 2에서 처음 잃은 간격

910의 표시가 2→3 VBlank가 됐다. 입력 909의 마지막 D2가 끝나야 910을 캡처할 수 있다. 881은 D2를 16,437,996클록에 끝내 16,438,928클록 시작선을 932클록 앞섰다. SEAL 직접 작성 후보는 16,442,574클록에 끝나 **3,646클록 늦었다**.

직전 표시 908의 65816 ACK는 142클록 늦었지만 ARM의 첫 유효 E0는 4,578클록 늦었다. E0부터 마지막 D2까지는 두 링크 모두 13,022클록이었다. 다음은 908의 최종 ACK를 확인하는 ARM 조회 시점에서 약 0.170ms를 회수하고 909의 D2가 시작선 전에 끝나는지 검증한다. 다른 밀집 화면에서도 증가·감소가 있으므로 910 회복 뒤 두 위상의 60간격 합과 마지막 ACK를 다시 비교해야 한다.

## 오프닝 BG 공급

위상 1에서 MMC872와 881을 같은 입력으로 부팅해 내부 세대 906의 BG 캐시 미스 1,920개를 주소 순서대로 대조했다. 계측 실행의 SPI 기록은 각각의 전체 실행과 일치했다. 마지막 32회 읽기에서 주소 111,744의 요청은 16,788,074 / 16,792,238클록에 발생했다. 중간 캐시 적중·타일 해석 비용을 포함한 요청 간격은 두 실행에서 같았다.

같은 ROM 허가표에서 이 32회가 직전 구간에 전부 들어가는 마지막 시작 시각은 **16,789,812클록**이다. 881에서 첫 요청을 2,426클록(0.113ms) 당기면 마지막 응답이 16,792,145클록에 끝난다. 한 클록 늦게 시작하면 마지막 응답은 17,132,513클록이다. 이는 읽기 구간만 옮긴 계산이다. 이 마감을 맞추도록 실제 ARM·생산자 일정을 변경한 후에는 전체 재생으로 오프닝 공개까지 확인해야 한다. 최초 요청은 128B E9 전송이 끝나기 전에 이미 발생했다.

각 후보에서 두 위상 총 348장의 활성 RGB·map, 이전 ACK → EA → 재무장 → COMMIT 순서, ARM credit·입력·메뉴 복귀와 65816의 cold·부분 수신·STOP·재시작을 검사했다. 비교에는 MMC872의 동일한 보드·65816과 기록 기반 ROM 허가표를 사용했다. 이번 결과의 시간 단위는 결합 재생의 마스터 클록이며 실기 FPS는 미측정이다.

## 재현

1. 881 전체 링크의 `src`에 `prepare_nes_oam882.py`를 적용한다. 기본 옵션은 전체 무map 후보, `--single-tile`은 resident planner의 쓰기가 한 타일인 후보, `--single-tile --direct-seal`은 같은 조건에서 SEAL 길이를 최종 패킷에 직접 기록하는 후보다. 각각 기존 전체 빌드와 MMC872의 `client02`를 사용한다.
2. `replay_nes_table877.py TEMP PHASE WORK TAG CLIP`으로 세 후보의 오프닝·전환·밀집을 두 위상에서 재생한다. 태그는 `882-oam`, `882-single`, `882-direct`다. 같은 링크 대조군은 `replay_nes_oam882_control.py TEMP PHASE WORK`로 실행한다.
3. `trace_nes_bg882.py TEMP 1 WORK TAG`로 `872-final`·`881-range`의 오프닝 두 세대만 계측한다. 다음 입력 선행 수신을 보존하기 위해 원래의 전체 입력 목록을 사용한다.
4. 881의 ARM credit·입력·최종 ACK·메뉴 및 65816 STOP·cold 가드를 각 링크에 적용한다. 두 위상에서 `test_nes_mapwait880.py TEMP PHASE --audit TAG`를 실행해 950의 PPU 포트·주소·데이터를 기록한 다음 `check_nes_oam882.py TEMP PROBES analysis/oam882-results.json`으로 비교한다. [장면별 패킷·DMA·ACK와 합격 조건](../analysis/oam882-results.json)
