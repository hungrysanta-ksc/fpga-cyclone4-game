# 911의 마지막 384B OBJ가 E8에서 E1까지 기다린 시간

## 목표

972에서 첫 팔레트를 앞당긴 뒤 길어진 OBJ 발행 대기를 직전 뱅크 반환, ARM 조회, 팔레트 SPI 점유로 분리했다. 채택 조건은 두 시작 위상에서 911 공개 간격과 912 최종 ACK가 함께 줄어드는 것이다.

## 작업내용

MMC966 동일 조건 대조군과 972의 첫 팔레트 32B 선행 후보를 같은 빈 캐시 일정에서 다시 실행했다. 911의 E8 응답을 실제 ARM 바이너리에 반환하면서 세대·토큰·CRC·크기·목적지를 확인했고, 같은 토큰의 E1과 연결했다. 기록 전후 대조군의 SPI·65816 이벤트·타일 생산 기록·BIN은 바이트 단위로 같았다.

두 후보에서는 972의 첫 32B를 보낸 뒤 32B OBJ의 반환 확인이 남았을 때 기존 plan 진행 함수를 한 번 호출했다. 비교한 위치는 96B 팔레트 앞과 232B 팔레트 앞이다. 두 후보 모두 기존 뱅크 반환과 큐 credit·STOP 검사를 거친다. 비교에는 기존 FPGA 공급 모델과 실제 MMC966 65816 코드를 사용했다.

## 성과

단위는 ms이며 각 칸은 위상 1 / 2다. 시작은 포트 모델이 token 30을 공개한 시각, 반환은 65816에서 token 29의 뱅크를 반환한 시각이다. 조회는 token 30이 들어 있는 첫 E8이다.

| 발행 조건 | 공개→직전 뱅크 반환 | 반환→조회 시작 | E8 거래 | 유효 응답→E1 시작 | 공개→E1 전체 |
|---|---:|---:|---:|---:|---:|
| MMC966 | 0.813 / 0.810 | 0.338 / 0.341 | 0.109 / 0.109 | 0.024 / 0.024 | 1.284 / 1.284 |
| 972 첫 팔레트 선행 | 0.867 / 0.772 | 1.039 / 1.025 | 0.109 / 0.109 | 0.024 / 0.024 | 2.039 / 1.930 |
| 96B 전 OBJ 서비스 | 0.867 / 0.771 | 1.040 / 1.026 | 0.109 / 0.109 | 0.024 / 0.024 | 2.039 / 1.930 |
| 232B 전 OBJ 서비스 | 0.867 / 0.771 | 0.418 / 0.404 | 0.109 / 0.109 | 0.024 / 0.024 | 1.417 / 1.308 |

972에서 직전 뱅크 반환과 조회 사이에 겹친 팔레트 SPI 거래는 0.640 / 0.626ms였다. 232B 앞에서 OBJ를 서비스하자 이 두 거래가 조회 뒤로 이동했다. 직전 뱅크 반환 시각과 유효 응답 이후 발행 비용은 거의 같았다.

이 후보의 908 공개와 910→911 간격은 원래 VBlank에 머물렀다. 911은 2 / 2 VBlank이고 912 최종 ACK는 MMC966보다 9.87 / 5.96µs 빨랐다. 마지막 OBJ ACK부터 SEAL 수락까지 4.246 / 4.162ms 중 OAM 세 패킷의 65816 수락→ACK가 합계 2.000 / 1.997ms를 차지했다. 그중 반복 OAM 명령(op8)이 1.180 / 1.180ms다. 나머지는 팔레트·section 5 패킷 처리와 패킷 사이 간격이다. 같은 검사·업로드 비용을 적용했을 때 직전 VBlank 종료까지의 부족분은 2.386 / 2.297ms였다.

별도 65816 재생에서는 마지막 OBJ까지 도착 시각을 고정하고 이후 일반 패킷 전체가 즉시 준비돼 있다고 가정했다. 실제 패킷 순서·거래 길이·큐 제한과 65816 검사를 적용하고 다른 SPI 사용자의 점유는 제외했다. SEAL 수락이 0.356 / 0.273ms 빨라져 직전 261선에 도달했지만 두 위상 모두 검사를 마친 뒤 다음 VBlank에 공개했다. 이는 해당 도착 조건·패킷 순서의 재생 결과다.

모든 조건에서 두 위상의 905–912 RGB 화면 여덟 장이 대조군과 일치했다. 위상 1에서 새 ARM 두 후보 모두 STOP(0xE4)·잘못된 SEAL 세대(0xE0) 주입 뒤 910 화면을 유지했다. Flash는 96B 후보 212,860B, 232B 후보 212,856B로 한도 212,992B 이내였다. 이번 결과에는 새 실기 FPS·메뉴 복귀 측정이 없다. [거래별 클록·부하·오류 시험 결과](../analysis/token973-results.json)

## 후속작업

MMC966을 유지한다. 다음에는 911 OAM의 65816 수락→ACK 약 2ms를 WRAM 쓰기와 필수 검사로 분리하고, 앞선 스크롤 패딩 복원이 첫 OBJ 뱅크 반환을 늦추는지도 함께 본다. 기존 화면의 독립 검사를 유지하고 908·911 공개와 912 최종 ACK가 함께 개선될 때 실기 후보로 올린다.

재현 시 972 대조군과 동일한 TEMP를 사용한다. `nes_token973.py prepare`로 before96·before232의 소스를 생성하고 해당 link를 `build_nes_trial577.ps1`로 빌드한다. `run MODE TEMP --phase N`으로 네 모드를 두 위상에서 실행한다. `check_nes_token973.py TEMP OUT --mode MODE --guard FAULT`로 두 후보의 bad_seal·stop_decode를, `--tail-phase N`으로 후반 연속 발행을 재생한다. 출력 폴더는 각각 TEMP 아래 nes-973-MODE-FAULT와 nes-973-tail-pN이다. 마지막에 같은 스크립트에 TEMP와 결과 JSON 경로를 주어 집계한다.
