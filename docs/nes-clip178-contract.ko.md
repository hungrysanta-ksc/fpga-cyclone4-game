# NES178 — START 뒤 화면 거부 재현과 왼쪽 클리핑 지원 후보

## 배포 검증 완료 — 178 실기 결과 대기

기존 아래 기능 검증에 이어20바이트 SEAL의 잘못된 길이/표시 설정7경우 거부, 실제177 기반의 MCU 전체 링크와 RUN/IRQ 여유1,040바이트, 로그 최대3,925/4,096바이트를 확인했다. 단일 FIT에서15,093LE·962LAB·36M9K, 실제 클록 setup+0.201ns/hold+0.147ns를 통과했다. 더 엄격한 배치 목표-0.017ns와 기존 reset24경로는 남아 있으며 전체 IO/CDC 승인으로 확대하지 않는다. 기존 조건의 외부 타이밍·테스트한 SNES4096바이트의 MIF 일치·압축 왕복을 확인해 실기 ZIP을 만들었다.

공통 PPU 기능이라 같은 설정을 쓰는 다른 게임도 영향을 받을 수 있다. 하지만 현재1e/18 외의 표시 방식은 여전히 미지원이며 게임·매퍼 전체 호환성을 보장하지 않는다. [지원 범위와 대응 순서](nes-video-compatibility178.ko.md)를 따른다.

[178 실기 안내](nes-game178-ready.ko.md) · [배포 검증 기록](../analysis/clip178-pair-verification.json). 실기 정지 해결·60fps는 아직 미완료다. 아래는 후보 기능 검증 당시의 기록으로, 당시 미완료였던 배포 검증은 이 절이 갱신한다.

**목표 일본판 SMB3에서 START 이후 표시 설정이 바뀌면 기존 수집기가 정상 화면까지 계속 거부하는 문제를 재현했다.** 이를 지원하는 FPGA·MCU·SNES 변경 후보와 기능 검증을 완료했다. 아직 전체 ARM 링크·FPGA 타이밍·실기 검증 전이므로 배포본은177을 유지하고 새 ZIP은 제공하지 않는다. 초기 끊김과60fps 목표도 미완료다.

## 재현한 문제

실제 CPU/PPU/MMC3와 배포177의 패드 직렬 모듈·수집기를 사용했다. ROM 내용·CPU RAM은 수정하지 않았다. ROM 읽기만 이상적인 메모리 모델이며 물리 PSRAM·전송기·SPI·SNES 경로는 이 재현에 포함하지 않았다.

| 모델 구간 | 결과 |
| --- | --- |
| 입력 전 | 첫26개 수집 상태와24·25프레임 픽셀이 기존174 기준과 일치 |
| START 입력 | 30·55프레임에서 누름,34·59에서 해제; 실제 직렬 읽기08/00 확인 |
| 12~65프레임 | mask1e, 정상 후보54개 |
| 66프레임 | 전환 중 mask00, 불완전 화면 거부 |
| 67~100프레임 | mask18,34개 모두 오류0400000; raster의 표시 설정 오류6번 비트만 설정 |
| 느린 소비 | 정상 후보를10프레임 보유;72~100프레임29개도 같은 이유로 거부 |

전환 후에도224행·30묶음·2객체·2~3예외·팔레트1개가 수집됐고 fetch/compact 오류는0이다. 영상 코어의79·95프레임 픽셀은 실제 플레이어 선택 화면이다. **게임이 화면을 만들지 못한 것이 아니라 수집기의 허용 조건이 그 화면을 막는다.** 기존 exporter는 BEGIN 이전 거부를 release하고 ABORT 패킷을 내보내지 않으므로 실기의 ‘추가 BEGIN 없음·ABORT0·오디오/입력 계속’과 일치하는 설명이다. 실기의 정확한 최초 실패 순간을 직접 기록한 증거는 아니므로 보드 원인의 최종 확인은 수정판으로 한다.

게임 초기 대기 때문에 두 START 모두 도입부 건너뛰기 전에 전달됐다. 따라서 이번 재현은 **플레이어 선택까지**이며 월드맵·첫 레벨 검증으로 확대하지 않는다.80프레임 A 입력도 기록했지만 레벨 진입 증거가 아니다. 실행 속도나100프레임 수집 개수는 TV FPS가 아니다.

외부 역분석 소스도 도입부의1e에서 건너뛰기 후18로 바뀌는 흐름을 보여준다. 일본판에 같은 코드 주소가 있다고 가정하지 않고 위 실제 ROM 실행으로 대조했다. [SMB3 도입부 코드](https://github.com/captainsouthbird/smb3/blob/master/PRG/prg024.asm)

## 변경 후보

`nes_clip178.py`가 배포 소스를 변환한다. 기존 수집 용량·타임아웃·코어 우선권은 유지한다.

- FPGA raster: 한 프레임 전체가1e 또는18인 경우만 허용한다. 프레임 도중 mask 변경, 강제 비표시, emphasis·grayscale 등 다른 모드는 계속 거부한다. 부분 전환 화면을 억지로 확정하지 않는다.
- MCU 변환기:224행의 mask가 같은지 확인하고 계획에 보존한다. 기존 정렬 패딩1바이트를 사용해 호스트 계획 크기15,888바이트를 유지한다. ARM 전체 스택·링크 여유는 별도 확인해야 한다.
- 패킷: SEAL을18→20바이트로 명시적으로 확장하고 끝의16비트 필드에001e/0018을 전달한다. 일반 데이터·ACK 토큰 형식은 유지한다. 구형 클라이언트와 혼합 배포하지 않는다.
- SNES: window1을x0~7에 설정하고 최종 vblank에서만 BG1/OBJ 윈도 적용을 켜거나 끈다.0018이면 왼쪽8픽셀을 backdrop으로,001e이면 기존 화면으로 표시한다. 비활성 VRAM 복사 중에는 이전 화면의 윈도 상태를 유지한다. 전체 화면을 끄는 방식이나 추가 세이브 SRAM은 사용하지 않는다.

SNES 윈도 레지스터와 BG/OBJ 마스킹 의미는 에뮬레이터 구현을 참고하고 실제 SNES CPU/PPU 모델의 픽셀로 확인했다. [bsnes 레지스터 처리](https://github.com/bsnes-emu/bsnes/blob/master/bsnes/sfc/ppu/io.cpp), [윈도 처리](https://github.com/bsnes-emu/bsnes/blob/master/bsnes/sfc/ppu/window.cpp)

변경된 실제 게임 수집기 전체를 다시100프레임 실행한 결과는 아니다. 수집기 거부 원인은 배포본의 실제 게임 실행으로 확인했고 변경 조건은 별도의 경계 시험으로 검증했다. SNES 시험은 기존 게임 장면을 사용한 파일 mailbox이며 실제 SPI나 보드 전송 속도 증거가 아니다.

첫 재현의 컴파일 오류(선언 위치), 두 번째 재현 완료 뒤 검증기의 상대 경로 오류, sandbox GCC 실행 오류와 MCU 시험의 trace 의존성 누락을 보존했다. 재현은100프레임을 정상 종료했으며 상대 경로만 수정한 검증기로 완료 로그를 재검사했다. 같은30분 시뮬레이션을 반복하지 않았다. MCU 최종 검사는 배포174 형식과 trace 소스를 사용했다.

## 다음 작업 순서

1. 새 SEAL 길이·잘못된 mask·구형 패킷 거부를 확인하고, 실제177 MCU 준비본에 이 후보를 적용해 전체 ARM 링크/RUN·IRQ 여유를 확인한다. 호스트 구조체 크기를 ARM 여유 승인으로 대체하지 않는다.
2. 177 기준에서 raster 변경과 새 SNES 이미지의 짝을 만들고 필요한 단일 FIT·기존 조건의 외부 타이밍·ROM 이미지 일치를 검증한다. 실패하면 원인을 보고하며 미검증 바이너리를 배포하지 않는다.
3. 통과하면 SMB3 실기 ZIP을 제공한다. START 선택 화면→월드맵→첫 레벨에서 영상이 계속 갱신되는지와 사운드·메뉴 복귀를 확인한다. 같은177/044 재시험이나 긴 무입력 도입부 반복은 생략한다.
4. 화면 정지 해소와 별도로177 계약의 앞단 테이블 변경분 전송·기준세대/ACK 확정을 진행한다.60fps에 미달하는 초기 끊김을 이번 클리핑 지원으로 해결했다고 기록하지 않는다. 연속 AV→장기 실행/오류·리셋 로그→입력 유지 순서를 유지한다.
