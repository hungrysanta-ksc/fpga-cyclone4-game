# 마지막 OBJ와 SEAL 사이에 놓친 VBlank

## 목표

모험도 4의 MMC966 빈 캐시 재생에서 907의 일반 출력 발행을 앞당기면 직전 VBlank에 표시할 수 있는지 시험했다. 같은 기준으로 마지막 타일 준비 여유가 더 큰 911도 확인했다. 실기 대조군은 MMC955다.

## 작업내용

두 시작 위상의 ARM SPI 기록을 세대·순번·명령·타일 토큰으로 65816의 패킷 로드·반환에 연결했다. 실제 MMC966 수신 ROM을 처음부터 Mesen에서 실행했다. 대조군은 원본 도착 시각으로 SEAL·업로드·공개·ACK 클록까지 재현했다. 각 시험에서 목표 세대까지 모든 화면의 RGB와 직전 공개 시각을 원본과 대조했다.

발행 순서를 바꾼 시험은 원래 전송한 바이트와 타일 payload, 패킷별 실측 SPI 거래 길이, 큐의 네 슬롯, 65816 독립 검사·DMA를 유지했다. 이동한 패킷은 새 순번을 받는다. 타일 명령은 원본 ARM이 유효한 타일을 처음 확인한 뒤에만 출발한다. 출력 여유를 측정하는 시험이므로 일반 패킷을 미리 만들 수 있다고 가정했다. 911의 마지막 조건에서는 **기존 E1 이외의 모든 SPI 거래**를 원래 시각에 예약하고, E1 한 건이 통째로 들어가는 구간에서만 발행했다. 바뀐 ARM 코드·FPGA의 폐루프 실행은 후속 검증 대상이다.

## 성과

907에서 마지막 OBJ가 준비된 뒤 SEAL 로드까지 걸린 시간을 겹치지 않게 나눴다. 한 패킷을 처리하는 동안 도착한 다음 패킷의 전송 시간은 다시 더하지 않았다.

| 907의 65816 경로 | 위상 1 | 위상 2 |
|---|---:|---:|
| 이전 패킷 반환 뒤 다음 패킷이 큐에 들어오기까지 | 0.954ms | 0.859ms |
| 이전 패킷이 반환되고 다음 패킷도 도착한 뒤 실제 로드까지 | 0.507ms | 0.613ms |
| 로드된 패킷 처리·반환 | 6.901ms | 6.686ms |
| 합계 | 8.362ms | 8.158ms |

마지막 OBJ가 준비됐을 때 직전 VBlank 끝까지 남은 시간은 0.665 / 0.664ms였다. 같은 비용의 SEAL 로드→업로드 진입과 마지막 팔레트 DMA 시작→화면 공개만 넣어도 1.368 / 1.371ms가 부족했다. 다른 DMA와 거래 대기를 모두 빼 준 계산이다. 실제 수신 재생에서도 907의 표시 간격은 모든 조건에서 **2 VBlank**였다.

| 907 조건 | SEAL 수락이 빨라진 시간, 위상 1 / 2 | 최종 ACK 변화, 위상 1 / 2 |
|---|---:|---:|
| 마지막 OBJ 도착 뒤의 패킷만 연속 발행 | 0.253 / 0.252ms | 0.006 / 0.011ms 늦음 |
| BEGIN 뒤 원래 순서로 연속 발행 | 1.507 / 1.176ms | 0.252 / 0.111ms 빠름 |
| 마지막 OBJ 앞에 나머지 일반 패킷 발행 | 2.543 / 2.315ms | 0.335 / 0.510ms 늦음 |

마지막 조건에서는 대조군의 map 선행 DMA 768 / 1,152B가 모두 사라졌다. SEAL만 앞당기는 순서 변경은 다음 실기 후보에서 제외한다.

911에서는 마지막 OBJ 준비부터 직전 VBlank 끝까지 6.218 / 6.274ms가 남았다. 대조군은 두 위상에서 모두 2 VBlank였다.

| 911 조건 | 표시 간격, 위상 1 / 2 | 최종 ACK 단축, 위상 1 / 2 |
|---|---:|---:|
| 마지막 OBJ만 일반 출력 뒤로 이동 | 2 / 2 | 0.008 / 0.011ms |
| 세 타일 명령 모두 일반 출력 뒤로 이동 | 1 / 1 | 16.636 / 16.639ms |
| 세 타일 명령 뒤로 이동, 기존 공유 SPI 거래 시각까지 보존 | **1 / 1** | **16.559 / 16.658ms** |

공유 SPI 보존 조건에서 911은 245 / 244선에 공개됐다. 토큰 28·29·30의 실제 65816 뱅크 반환은 위상 1에서 각각 1,090·14,226·26,900클록 빨라졌다. 위상 2의 토큰 28은 92클록 늦고 29·30은 9,264·21,908클록 빨랐다. 두 위상 모두 일반 출력의 첫 팔레트를 원래 ARM 발행보다 약 9ms 앞서 제공한 결과다. 별도 오류 시험에서 SEAL 검사 중 STOP은 상태 0xE4, 잘못된 SEAL 세대는 0xE0으로 끝났고 양쪽 모두 910 화면을 유지했다.

같은 MMC966 ARM 바이너리를 끝까지 실행해 각 선행 발행 시각의 송신 원본 버퍼를 최종 payload와 대조했다. 두 위상에서 0–5 마스터클록 이내에 읽은 결과가 같았다. 첫 팔레트 32B 중 **24B**, 첫 OAM 176B 중 **172B**, section 5의 조립 버퍼 두 조각은 각각 **100/201B**, **25/240B**가 최종값과 달랐다. 기존 ARM이 실제 발행한 시각에는 네 버퍼가 모두 일치했고, 관측 전후 SPI·65816 이벤트와 실기 형식 BIN도 동일했다. 따라서 큐 순서만 바꾸면 이전 데이터가 나간다. 원본 입력에서 이 데이터가 언제 계산 가능한지는 별도로 측정해야 한다.

## 후속작업

이후 실행한 [971 ARM 실제 생성·선행 발행 비교](nes-palette971-results.ko.md)에서 팔레트·테이블의 준비 시각과 타일 공급에 미친 영향을 확인했다.

911의 목표는 실제 ARM에서 첫 타일 전 일반 출력 준비를 끝내고 E9·유효 E8과 두 타일 뱅크의 공급을 유지하는 것이다. 특히 위상 2의 토큰 28 반환과 후속 384B 생산을 다시 결합해야 한다. 911의 공개와 다음 912 최종 ACK까지 같은 연속 일정에서 개선된 뒤 실기판을 결정한다. 이번 재생 결과는 1–30초·30–60초 실기 FPS에 반영하지 않는다. [클록별 발행·수락·DMA·공개 기록](../analysis/output970-results.json)

재현에는 MMC966 빈 캐시의 두 위상 원본과 기존 Mesen 실행 파일이 필요하다. `tools/check_nes_output970.py`에 TEMP, 새 출력 폴더, 위상, 조건을 주고 911에는 `--generation 911`을 지정한다. 907은 control/tail/frame/ordinary, 911은 control/ordinary/prelude/reserved를 실행한다. 911 위상 1의 prelude에서 `--fault stop_decode`, `--fault bad_seal`도 각각 실행한다. `tools/check_nes_payload970.py`로 원본 링크의 버퍼를 확인하고 `tools/analyze_nes_output970.py`로 두 위상 결과를 집계한다.
