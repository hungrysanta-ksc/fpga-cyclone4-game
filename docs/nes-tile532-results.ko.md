# 532. 작은 tile 선행 처리와 반환 credit으로 map 수락 앞당기기

작은 tile 우선 처리와 최대 128B map DMA를 결합한 소비기를 다음 보드 시험 후보로 선택했다. 952·954 모두 두 시작 위상에서 246번 검사선까지 표시 준비를 마쳐 마지막 VBlank 대기 한 번이 사라졌다. 같은 시작부터 53번째 화면인 957의 최종 ACK까지 걸린 시간은 199.669/183.048ms 줄었다. 실기 기준은 MMC529다.

## 구현

MMC529의 SNES 소비기는 보통 닫힌 tile보다 마지막 map 명령을 먼저 선택하고, 단독 tile tail은 열어 두었다. 532에서는 수락된 목록의 첫 명령이 160B 이하 tile이면 먼저 선택한다. 그 명령만 남았으면 동기 DMA 완료 후 양쪽 커서를 함께 초기화한다. 232번 주사선을 넘으면 tile을 보류하고, 사용 가능한 map tail은 기존대로 254번까지 64B씩 옮긴다. MDMAEN 직전의 새 head·STOP 확인과 최종 표시의 246번 검사선은 유지했다. 246번은 표시 여부를 결정하는 시점이며, 이어지는 표시 쓰기와 ACK는 같은 blank 안에서 더 늦게 끝날 수 있다.

두 번째 소비기는 같은 map 명령에 연속 두 행이 수락돼 있으면 128B, 한 행만 남으면 64B를 보낸다. 세 번째 소비기는 실제 blank를 확인한 뒤 앞쪽의 살아 있는 명령 최대 8개에서 작은 tile을 찾는다. 안쪽 tile의 DMA가 끝나면 맨 앞 명령 8B를 완료된 자리로 옮겨 목록에 빈 칸이 생기지 않게 한다. 늦어진 요청이나 STOP에는 목록을 바꾸지 않는다.

새 tile을 등록할 때 tail이 map이라면 바로 앞의 **아직 소비하지 않은 명령 하나**를 추가로 검사한다. 기존 명령의 WRAM·VRAM 끝 주소가 모두 새 명령의 시작 주소와 일치하고 합친 길이가 기존 한도 안일 때만 길이를 늘린다. 독립 수신·유효성 비트맵은 원래 단위로 갱신한다. [65816 생성기](../tools/nes_tile532.py)

ARM은 END가 막혔고 현재 E8에 ready bulk와 E9 credit이 없을 때만 다음 map을 시도한다. 캐시된 점유가 3 이상이어도 한 번 E0를 읽어 실제로 반환된 credit을 확인한다. 큐가 비었으면 마지막 ACK identity·서명까지 비교하고, 실제 점유가 2 이하일 때만 원래 DATA/RLE 패킷을 하나 보낸다. 초기 후보는 906에서 이전 bulk 완료 표적과 sent가 9건 벌어져 기존 4건 검사에 걸렸다. 최종 후보는 bulk 표적 뒤 3건 이상을 발행한 경우 다음 map 전 기존 `complete485` 검사를 거쳐 표적을 정리한다. [ARM 준비기](../tools/prepare_nes_tile532.py)

## 비교 조건

동일한 905–957 입력에서 ① MMC529, ② 532 ARM + 529 소비기, ③ 작은 tile 우선 + 64B map, ④ 같은 방식 + 최대 128B map, ⑤ 목록 안쪽 tile 선택 + 최대 128B map을 3,000,000 / 3,178,684 클록에서 비교했다. 각 실행의 53화면 RGB, 실제 패킷 내용·개수와 map 발행 순서, 444개 tile 내용, ROM read 배정 및 VRAM DMA 바이트를 대조했다. 표의 map·OBJ 수락은 해당 세대의 입력 시작부터 65816이 실제 데이터를 소비하고 ACK를 발행할 때까지다. map 대상은 MMC529의 954에서 마지막 blank까지 남았던 연속 1,536B 전부다. 최종 ACK 비교는 공통 시작 시각부터 957까지의 연속 결과다.

목록 안쪽을 선택하면 952의 기존 잔여 tile 중 160/128B를 미리 옮겼다. 둘째 위상에서는 선행 map이 832B에 그쳤고 246번 검사선에 4,325클록 늦어 다시 한 번 기다렸다. 이 후보의 957 ACK는 183.035/66.568ms 빨라졌다. 두 위상과 두 목표 화면을 모두 통과한 후보는 목록 앞의 작은 tile과 최대 두 행의 map을 선택하는 방식이었다.

907–957 전체에서 선택 후보의 표시 간격이 한 VBlank 늘어난 화면은 첫 위상 910·926, 둘째 위상 910·913·926이었다. 반대로 두 목표 화면은 네 비교 모두에서 실제 표시 간격도 한 VBlank 줄었다. 평균과 마지막 ACK만으로 모든 화면의 개선을 가정하지 않았다.

952에서는 MMC529의 마지막 업로드까지 남았던 tile 576B 중 첫 BG tile 16B를 두 위상 모두 먼저 보냈다. 나머지 560B의 목적지는 서로 떨어져 있었다. 53화면에서 map을 사이에 둔 tile의 추가 병합은 선택 후보에 한 번도 일어나지 않았다. 이득의 차이는 남은 map에서 보인다. 같은 ARM에서 map grant를 64B에서 최대 128B로 바꾸자 952의 선행 map이 832/1,280B에서 1,920/1,920B가 됐다. 64B 후보는 두 위상 모두 마지막 blank를 기다렸다.

954의 기존 잔여 map 1,536B는 ARM만 바꿔도 약 61ms에 전부 수락됐지만 두 위상 모두 최종 대기가 남았다. 선택 후보는 SEAL에 남은 map을 기준 1,536B에서 192/0B로 줄였다. 마지막 OBJ 수락은 첫 위상에서 86.462→68.615ms, 둘째 위상에서 86.392→84.452ms였다. 선택 후보의 952/954 최종 검사 시점은 첫 위상 243/243번, 둘째 위상 243/240번이었다.

## 검사와 비용

- 새 ARM의 credit 랩 시험에서 0xfffc부터 8개 map을 보내 sent가 4가 되는 동안 이전 bulk ACK를 확인했다. 큐 점유 3이 유지되면 map을 발행하지 않았고 잘못된 E0 CRC·ACK identity는 END 전에 차단했다. 기존 첫 map 경계 9건과 E8 응답 회귀 40건도 통과했다.
- 실제 65816의 단독 tile은 양 뱅크에서 128B·16B로 시험했다. 별도 순서 고정 시험에서 16B와 64B 사이에 map을 두었을 때 하나의 80B DMA가 발생했다. 새 head, STOP, 동시 도착, 최초 PPU 쓰기 뒤 head·STOP, cold 복구, 중복 map 및 manifest 누락 거부까지 소비기별로 22건을 확인했다. 안쪽 tile 선택에는 별도로 6건의 경합 시험을 적용했다. 254번 map은 실제 PPU에서 각각 64/128/128B DMA를 허용했고 255·256번 map과 233번 tile은 거부했다. [경합 시험](../tools/test_nes_tile532_priority.py) grant 전에 도착한 head·STOP은 DMA를 막았다. 최초 쓰기 뒤 도착한 경우에는 이미 시작한 동기 DMA가 끝난 후 head 처리 또는 STOP으로 전환했다.
- 실제 연속 실행에서는 각 선행 tile이 수락된 bulk payload와 일치하는지 마지막 PPU 쓰기 뒤 VRAM에서 확인했다. 각 위상의 기록된 도착 시각으로 별도 재생해 전체 소비 이벤트·클록, tile grant·병합 기록과 RGB를 대조했다.
- 모든 연속 실행은 1,689개 패킷, 444개 tile, ROM 읽기 배정 5,616회와 VRAM DMA 125,488B로 같았다. 원래 529 소비기와 532 소비기 3종도 다시 생성해 각각 실행에 쓴 ROM과 SHA-256이 같은지 확인했다.
- ARM Flash는 212,248→212,420B로 572B가 남고 BSS는 18,592B다. 65816 본문은 기준 4,825B에서 후보 순서대로 4,913/4,941/4,958B가 됐다. 이 시험은 링크된 ARM·SysTick·공유 SPI·두 bulk 슬롯·ROM 허용 일정과 Mesen의 65816을 연결한 시뮬레이션이다. 새 FPGA 보드 합성·실기 측정은 수행하지 않았다.

## 재현

첫 위상 ARM 단독 대조와 안쪽 선택은 942에서 Mesen의 1초 Lua 콜백 제한에 걸린 실행을 별도로 보존했다. 동일 해시 실행 파일의 별도 portable 설정에서 `Debug.ScriptWindow.ScriptTimeout`을 90초로 두고 처음부터 다시 실행했다. 실제 2.2초 콜백 종료를 확인했고 942 전까지 ARM 대조 5,681개와 안쪽 선택 5,475개의 소비 이벤트·클록은 중단된 기록과 일치했다. 설정은 호스트 대기 제한에만 적용했다.

[529 기준](nes-flash529-results.ko.md)의 ARM에 준비기를 적용해 기존 STM32 빌더로 링크하고 `nes_tile532.py --out`으로 64B 소비기를 만든다. 같은 명령에 각각 `--paired-map` 또는 `--interior`를 주어 두 128B 소비기를 만든다. 529의 동일 fixture·calendar·driver를 사용해 ARM만 바꾼 대조군은 [531 계측기](../tools/trace_nes_output531.py), 결합 후보는 [532 계측기](../tools/test_nes_tile532.py)로 두 시작 클록을 실행한다. 결합 결과를 `--trace`로 독립 재생한 뒤 credit·경합 시험과 [분석기](../tools/analyze_nes_tile532.py)를 실행한다.
