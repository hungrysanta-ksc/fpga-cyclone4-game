# NES172 실기 — 초기 표시 통과, 이후 화면 갱신 정지

172는 표시 준비와 14회 표시 완료 응답을 통과했지만, 이후 화면이 멈췄다. 버튼과 스테이지 음악은 계속 동작했다는 사용자 관찰과 달리 화면은 초기 장면에 남았다. 약 60초 뒤 종료는 오류 탈출이 아닌 정상 실행 한도이며 메뉴 복귀도 확인됐다. **연속 화면·정상 플레이 목표는 미달성이다.**

## 확인 결과

| 항목 | 결과 |
| --- | --- |
| ROM | 393216바이트 적재·비교 일치, ROM 오류 0 |
| 시작 | `screen_stage=3`, 표시 준비 통과, SPC A9 / unmute 1 |
| 받은 영상 후보 | BEGIN 14 / END 14 / COMMIT 14 / ABORT 0 |
| 표시 완료 | `native_frames=14`, 마지막 generation 27 |
| 종료 | `native_result=1` — 정상 DEADLINE, sink/video 오류 0 |
| 표시 시도 구간 | 231740→291790ms, 차이 60050ms |
| 메뉴 복귀 | STOP·base_restored·safe_to_reload 1, MENU_PREPARED 294950ms, 영상 말미 메뉴 확인 |
| 입력 | 변경된 8비트 입력 읽기 300회, 마지막 16기록에 A/B/LEFT·해제 포함 |

입력 300회는 물리 버튼을 300번 눌렀다는 뜻이 아니다. 해제·동시 입력을 포함한 값 변경 횟수이며 입력 유지 품질을 증명하지 않는다. 구형 `screen_frames=0`은 신뢰하지 않는 보조 필드다. 실제 완료 수는 SNES의 일치하는 SEAL/display ACK를 확인한 뒤 증가하는 `native_frames`로 판단한다. 이 14회도 초당 프레임 수나 서로 다른 그림 14장의 증명은 아니다.

첨부 MOV는 66.20초다. 10초 간격으로 추출한 초반·중반·후반 표본에서 같은 마리오/루이지 초기 자세가 유지되고 마지막 표본은 파일 메뉴다. 초기 몇 프레임 움직임과 음악·버튼 반응은 사용자 보고를 함께 기록한다. 음성을 별도로 판독하지 않았으며 SPC 초기화 성공을 실제 음질 검증으로 대신하지 않는다. CRT 촬영에 따른 대각선·밝기·색 변화는 결함 근거에서 제외한다.

## 170과 같은 점, 다른 점

| 항목 | 170 | 172 |
| --- | --- | --- |
| 보이는 증상 | 몇 프레임 뒤 정지, 소리·입력 반응 | 동일 |
| 표시 완료 응답 | 13회, generation 27 | 14회, generation 27 |
| BEGIN / COMMIT / ABORT | 21 / 13 / 8 | 14 / 14 / 0 |
| 수집 중단 근거 | 최초·마지막 0x34, CHR 전체 시간 예산 초과 | 받은 ABORT 없음 |
| 종료 | 정상 실행 한도 | 정상 실행 한도 |

따라서 이번 현상을 그대로 “170의 CHR 시간 초과 재발”로 분류하지 않는다. 이번에는 수신한 14개 후보 모두 표시 응답까지 완료됐으며, 이후 새로운 BEGIN이 기록되지 않았다. 171 FIFO가 모든 장면에서 시간 초과를 해결했다고 단정할 수도 없다. 전송을 시작하지 못한 장면에는 FIFO 효과를 평가할 근거가 없다. 169/171의 첫 BEGIN 응답 실패는 이번에 재현되지 않았고 172의 준비 확인은 통과했지만, 이전 부팅 실패의 근본 원인까지 확정된 것은 아니다.

## 현재 로그로 좁힐 수 있는 범위

배포 소스의 exporter는 IDLE에서 geometry가 유효하지 않거나 행·그룹·오브젝트·예외·팔레트 수가 허용 범위를 벗어나면 프레임을 해제하고 DRAIN으로 간다. 이 경로는 BEGIN이나 ABORT를 보내지 않는다. 따라서 **ABORT 0은 모든 프레임이 허용됐다는 뜻이 아니다.** fetch/compact/raster 결합이 완료되지 않거나, COMMIT 뒤 공통 해제·`fill_busy`·DRAIN 대기가 풀리지 않아도 다음 BEGIN은 수신되지 않을 수 있다. 생성됐지만 아직 전달되지 않은 경우도 현재 기록만으로 배제하지 않는다.

`trace_state=4`, `trace_kind=7`, `trace_index=3`은 마지막으로 검증한 COMMIT 레코드 시점의 수신 상태다. 실시간 FPGA 상태가 아니다. 표시 완료 후 `nes_native165_consumed()`가 별도로 수신기를 IDLE로 되돌리므로 이 필드로 “COMMITTED에 고착됐다”고 판단하지 않는다.

`native_receiver_error=21`도 이번 종료의 최초 원인이 아니다. 실행 guard가 먼저 DEADLINE을 설정해 전송을 거절하면 수신기가 후속 21을 남길 수 있다. 최초 결과는 1로 보존된다. 실제 SPI 손상이 확인됐다는 뜻으로 읽지 않는다. `screen_error=169`는 0xA9 SPC 결과이며 영상 오류 코드가 아니다.

표시 시도 60050ms는 준비 대기·마무리를 포함한 펌웨어 구간이다. 6000tick 게임 제한은 준비 완료 뒤 시작하므로 별도 정확한 부팅 시간이나 TV 표시 시간을 산출하지 않는다.

## 다음 작업

1. 마지막 표시 generation 27 뒤 **fetch/compact/raster 프레임 결합과 전송 전 허용 조건**, 공통 release와 exporter DRAIN/`fill_busy` 연결을 우선 확인한다. “허용 조건에서 계속 탈락”과 “해제 후 다음 수집 미진행”을 구분한다.
2. 소스와 최소 재현으로 구분되지 않으면 해당 경계의 거부 사유·진행 상태만 기존 종료 로그에 보존한다. 실행 중 SD 쓰기나 범용 진단 확장, 근거 없는 시간 제한 증가는 하지 않는다.
3. 해당 경계를 수정하고 필요한 검증 후 실제 SMB3로 복귀한다. 기존 부팅·A/B·044·무변경 FIT·같은172 시험은 반복하지 않는다. 연속 AV→장기 실행/오류·본체 리셋 로그→입력 유지 순서, 세이브 SRAM/GBC/164 보호를 유지한다.

이번 커밋은 결과와 다음 계획만 기록한다. 새 펌웨어·FPGA·ZIP은 없다. [원본 해시·필드·배포 소스 대조](../analysis/game172-hardware01-verification.json). TXT·영상 원본은 비공개 보관하고 기존 빌드·검증 기록은 변경하지 않는다.
