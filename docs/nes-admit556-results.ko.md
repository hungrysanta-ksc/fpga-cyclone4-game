# 556. 192B map 수락과 최종 표시

557에서 실제 보드의 E9 쓰기 권한이 이 기록의 연속 모델보다 먼저 열린다는 것을 확인했다. 아래 수치는 기존 모델의 비교값으로 보존한다. 보드 동작을 반영한 954 표시 간격과 다음 작업 기준은 [557 E8/E9 대조](nes-end557-results.ko.md)를 따른다.

555의 512B map 후보를 기준으로 954의 오프셋 2,432 패킷을 추적했다. 두 위상 모두 ARM은 packet 함수 진입→enqueue에 166 master clock, enqueue→E1 SPI 시작에 6,783클록, 211B 전송에 14,880클록을 썼다. SPI 도착→65816 head는 848 / 172클록이었다. 수락 ACK가 늦어진 두 번째 위상에서 큐 대기는 약 0.008ms였다.

## 수락 경로에서 줄인 일

555의 65816에서 head→수락 ACK는 15,164 / 15,764클록이었다. 두 위상 모두 단위 좌표 계산과 첫 비트 위치 결정에 2,480클록, 그 뒤 세 행의 비트 검사·기록과 descriptor 주소 계산까지 4,382클록을 썼다. 실제 192B WRAM DMA 시작→accepted 진입은 1,756클록이었다. 각 수치는 실제로 실행한 PC와 DMA 레지스터 쓰기에서 얻었다.

- **65816 변경**. 검증한 section으로 BG·OBJ·map의 단위 크기(16·32·64B)를 선택해 바이트 오프셋과 길이를 각각 한 번 변환한다. 첫 비트 마스크를 계산한 뒤 순차 이동하고, 한 바이트를 소진할 때만 두 bitmap 인덱스를 증가시킨다. 이미 수락한 단위가 겹치면 기존 오류 경로로 들어간다. 범위 검사, 실제 payload 복사, bank별 유효 이력, descriptor 병합, STOP과 최종 ACK는 그대로 실행한다. [65816 생성기](../tools/nes_admit556.py)
- **ARM 변경**. E1의 command 바이트부터 마지막 payload 바이트까지 CRC16을 계산할 때 이미 링크된 CCITT 테이블 함수에 같은 초기값 `0xffff`를 넘긴다. E1 형식과 수신 측 CRC 검사는 동일하다. 가능한 E1 CRC 입력 길이 17–257B와 실제 954 패킷으로 링크된 M4와 독립 CRC를 대조했다. [ARM overlay](../tools/prepare_nes_admit556.py) · [CRC 시험](../tools/check_nes_admit556_crc.py)

## 두 시작 위상의 전체 일정

각 셀은 시작 클록 3,000,000 / 3,178,684 순서다. 밀집 구간은 951–955의 표시 간격 다섯 개다. 마지막 ACK 차이는 같은 시작 위상의 555에 대한 53번째 화면의 차이다.

| 경로 | 192B 수락 ACK 행 | 954 표시 간격 (VB) | 밀집 합계 (VB) | 밀집 평균 (ms) | 마지막 ACK 단축 (ms) |
|---|---:|---:|---:|---:|---:|
| 555 기준 | 252 / 256 | 5 / 6 | 27 / 28 | 89.968 / 93.174 | 기준 |
| 65816 검사만 | 252 / 253 | 6 / 5 | 28 / 27 | 93.184 / 89.860 | 16.904 / 66.306 |
| ARM CRC만 | 234 / 233 | 5 / 6 | 27 / 28 | 89.847 / 93.175 | 183.412 / 182.647 |
| 둘 다 | 229 / 225 | 6 / 6 | 28 / 28 | 93.175 / 93.172 | 216.452 / 216.297 |

ARM 변경은 enqueue→E1 시작을 6,783→906클록으로 줄였다. 결합 후보에서 65816의 범위 검사 진입→append는 4,132 / 4,156클록, head→수락 ACK는 12,304 / 12,512클록이었다. E1은 여전히 211B다. 555 PUSH 시각을 고정하고 새 65816만 재생하면 수락 ACK는 250 / 254행, 954 표시는 5 / 5 VB였다.

연속 실행에서는 192B를 더 일찍 수락해도 마지막 OBJ가 늦으면 표시를 앞당길 수 없었다. 결합 후보는 SEAL 뒤 최종 대기가 양쪽 모두 0회였지만, 마지막 OBJ 응답이 555의 67.449 / 67.360ms에서 83.356 / 83.222ms로 밀렸다. 그 결과 SEAL 전에 VBlank가 4→5회 경과했다. 마지막 18개 ROM 읽기 가운데 18 / 8개가 원래 허용 구간 밖으로 넘어갔다. 953은 모든 경우 5 VB, 952와 957의 최종 대기는 0회였다. 957에서는 ARM 변경 시 마지막 tile ACK 전 map 발행이 2개에서 3개로 늘었다. 첫 BG ROM 허용 구간의 상대 순번이 늦어진 프레임은 없었다.

**다음 비교는 최종 E8 확인→E9 END 발행에 집중한다.** 관측한 읽기 사이 간격을 그대로 두고 ROM 달력에서 역산하면, 결합 후보의 첫 OBJ 요청을 위상별로 최소 1,652 / 511 master clock(약 77 / 24µs) 앞당겨야 같은 구간에 18개를 끝낼 수 있다. 이 값은 해당 달력과 간격에 대한 조건부 예산이다. E8에서 credit이 실제로 열린 시각, 직전 poll, 3,877클록 걸린 최종 E9의 시작·완료를 함께 추적한다. 허용 전 발행을 막고 STOP·오류·최종 ACK를 유지한 채 두 위상에서 밀집 구간을 다시 비교한다. 이번에는 실기 전달본을 선정하지 않았다.

## 전체 비용과 검증

65816 본문은 4,950→4,931B, ARM Flash는 212,940→212,908B(여유 52→84B), BSS는 18,592B였다. 각 실행에서 53개 RGB, map·tile, ROM 읽기 5,616회, VRAM DMA 114,352B와 최종 ACK를 대조했다. 매 실행의 BG·OBJ·map 수락 642건에 대해 비트맵과 양쪽 뱅크 이력을 독립적으로 확인했다. head·STOP 우선, 누락·중복 등 22건과 954 팔레트·OAM·HDMA 수락 뒤 STOP 3건을 확인했다. 세 STOP 모두 직전 953 화면 보존과 오류 ACK 0xe4를 확인했다. 링크된 ARM의 credit·END·CRC 오류, 5–40초·40–55초 집계와 메뉴 복귀 분기를 통과했다.

Quartus Lite로 기존 555와 새 556 client를 각각 넣어 전체 보드를 FIT·STA했다. MMC551의 73개 입력 중 65816 프로그램 ROM만 바뀌었다. 두 보드 모두 15,164 LE, 조합 논리 14,172개, FF 8,394개, RAM 264,816bit, M9K 51개로 MMC551과 같았다. 관련 setup/hold 최소 여유는 +0.078 / +0.139ns, 전체 setup/recovery 최악값은 −7.081 / −8.480ns로 같았다. 전체 STA 요약과 미제약 개수도 같았다. 556의 implementation·nominal 상세 목록은 각각 두 행이 달랐지만 각 뷰 54개 코너·클록·검사 그룹의 최악 slack은 모두 일치했다. ## 재현

555의 554 ARM03/src와 555 client01을 기준으로 한다. ARM overlay를 479 빌더로 링크하고 `nes_admit556.py`로 65816을 생성한다. `test_nes_prelude554.py --keep-run`에 555와 같은 489 plans·capture, 231 raw·geometry, 503 SPI 모델, 509 ROM 달력과 555 tile fixture를 주고 시작 클록 3,000,000 / 3,178,684로 실행한다. 65816만, ARM만, 둘 다 바꾼 세 쌍과 555 두 위상을 독립 재생한다. 시각은 Cortex-M4 명령 CPI=2, 실제 65816, 공유 SPI·IRQ·두 bulk bank, 반복한 부팅 ROM 허용 구간의 모델로 얻었다. [명령별 계측과 bitmap 검증](../tools/replay_nes_admit556.py) · [전체 비교](../tools/analyze_nes_admit556.py)

독립 재생은 각 BG·OBJ·map 수락 직전의 dirty 152B와 두 뱅크의 유효 이력 304B로 다음 상태를 계산하고 append 직전에 모두 대조한다. 원본과 후보의 실제 `mark212` 기계어를 직접 실행한 시험은 각각 108건이다. 두 뱅크와 세 section, 마스크가 바이트 경계를 넘는 경우, 마지막 단위, 4KiB 구간, 첫·마지막 단위에서 중복과 반대쪽 뱅크 보존을 포함한다. [직접 수락 시험](../tools/test_nes_admit556_ranges.py)

로컬 검증 보관본 `probes/nes-admit556/archive01/evidence.zip`의 4,944개 파일을 원본과 대조했다. SHA256은 `5efdaa9e2dbceffe4bf185b0701f6e51777bea60b4fa229ca018257904a7dc4a`다.
