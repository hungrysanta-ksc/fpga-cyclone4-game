# 563 · 클록 정지 시 메모리 차단과 RUN 주소 캡처

실기는 MMC558, 기능 대조군은 562다. 563은 메모리 시작 허가를 메모리 클록의 두 플립플롭으로 전달한다. lock 상실·외부 reset·고장 래치는 비동기로 두 플립플롭을 지운다. 이로써 참조 클록의 정상 시작 신호가 메모리 reset을 비동기로 해제하던 경로를 제거했다. 참조 클록이 내리는 고장 신호는 메모리 클록이 멈춰도 차단할 수 있다. [562의 측정과 기존 문제](nes-owner562-results.ko.md)

## 한쪽 클록을 정지시킨 시험

Questa 한 좌석에서 562와 563의 실제 clock guard, 시작 대기 회로, 로컬 reset 체인과 ROM reader를 연결했다. 두 시작 위상에서 각 클록을 (1) 양쪽 heartbeat의 초기 허가 전, (2) 33,603클록 시작 대기 중, (3) PSRAM OE가 이미 활성인 읽기 중에 멈췄다.

- 563은 메모리 클록 정지 후 2.962–3.041µs, 참조 클록 정지 후 3.812–4.003µs에 고장을 래치하고 PSRAM CE·OE를 비활성으로 돌렸다. 수치는 시험한 정지 시점에서 관측한 시간이다.
- 정지 중인 읽기의 응답은 나오지 않았다. 클록을 복원하고 700 메모리 에지를 더 진행해도 고장 상태가 유지됐다. 공통 reset 뒤 다시 초기 허가·대기를 거쳐 새 주소의 올바른 데이터를 읽었다.
- 두 클록이 함께 멈춘 경우에는 별도로 lock 상실을 인가해 비동기 차단을 확인했다. 한 클록으로 다른 클록의 정지를 감시하는 방식은 양쪽 모두 정지했을 때 자체 시간 기준이 없다.
- 각 위상에서 562와 563의 시작 허가, 주소 캡처, 읽기 응답 및 고장 관측 기록 21개가 같은 시각에 발생했다. 정상 시작은 release 후 arm 1에지와 기존 대기 33,603에지를 지켰다.

## 22비트 주소가 캡처되기까지의 여유

reader는 NES 쪽에서 주소와 요청 토글을 함께 래치한다. 메모리 쪽에서 토글이 동기화 첫 단에 들어간 뒤 두 번째 단을 거치고, 그 다음 IDLE 에지에서 주소를 캡처한다. RTL 시험에서 실제 캡처마다 첫 샘플과의 간격은 메모리 2주기였고 그동안 주소는 유지됐다.

TimeQuest에서 배치된 주소 출발 레지스터마다 메모리 도메인의 최악 setup 경로를 조회했다. 22개 논리 비트 중 20번은 두 보드 모두 19번 출발 레지스터에 병합됐으며, 이 별칭은 MAP 보고서로 확인했다. 따라서 독립 출발점은 21개다. 주소의 최후 필요 시각은 **원래 보드 제약**의 setup 결과에서 구한다.

토글의 최초 샘플 시각을 계산할 때만 두 번째 분석용 timing netlist에서 `request_toggle → request_sync[0]`의 기존 false-path 한 줄을 제외하고 hold 경로를 조회했다. 주소의 원래·분석용 결과가 전 비트에서 일치하는지도 검사했다. FIT와 보드 통과 판정은 원래 SDC로 진행했다.

같은 이상적 출발 에지를 기준으로, 주소가 setup을 충족하는 데 필요한 간격은 `latch − launch − setup_slack`, 첫 단에서 토글을 잡을 수 있는 가장 이른 에지는 `latch − launch + hold_slack`으로 계산했다. 가장 이른 에지에 2 × 5.952ns를 더한 뒤 주소의 최후 필요 시각을 뺐다. 위치와 에지에 따른 clock 경로·setup·hold 보정이 있는 분석이므로 순수 배선 지연을 사용한 값과 다르다.

| 563 코너 | 첫 단 최초 에지 | 주소 최후 필요 시각 | 두 주기 뒤 여유 |
|---|---:|---:|---:|
| Slow 85°C | 3.958ns | 4.372ns | 11.490ns |
| Slow 0°C | 3.464ns | 3.922ns | 11.446ns |
| Fast 0°C | 1.748ns | 2.135ns | 11.517ns |

가장 이른 토글과 가장 늦은 주소를 **서로 다른 코너에서** 취한 결과는 562에서 9.256ns, 563에서 9.280ns다. 이는 해당 배치와 요청 프로토콜의 캡처 예산이다. 보드 전체 STA나 동기화기 MTBF 판정에는 별도 기준을 적용한다.

## 전체 보드와 표시 결과

| 같은 Quartus Lite·device·seed·SDC | MMC558 | 562 | 563 |
|---|---:|---:|---:|
| LE / 15,408 | 15,164 | 15,213 | 15,252 |
| 조합 논리 / FF | 14,172 / 8,394 | 14,188 / 8,398 | 14,223 / 8,398 |
| M9K | 51 | 51 | 51 |
| 대상 setup / hold | +0.078 / +0.139ns | +0.386 / +0.140ns | **−0.333 / +0.139ns** |
| MMC558보다 악화된 기존 음수 STA 항목 | 기준 | 7 | 3 |

563의 정상 시작 허가는 `ref_qualified → release_pipe[0]`의 첫 동기화 단계로 옮겨갔다. Slow 85°C에서 그 입력의 setup은 −4.332ns이고, 두 release 플립플롭 사이의 setup/hold는 +4.993/+0.505ns다. 고장 래치에 의한 비동기 차단 경로는 남아 있다. 전체 FIT는 성공했으나 메모리 클록의 SPI 명령 수신 `byte_count[2] → arg[7]` setup이 구현·nominal 양쪽에서 −0.333ns다. MMC558 대비 남은 세 음수 항목은 84MHz recovery의 slow 85°C 0.005ns·fast 0°C 0.032ns 차이와 NES setup의 slow 0°C 0.083ns 차이다. 원래 SDC의 미제약 항목 수는 그대로다.

두 시작 위상의 562 ARM·SPI·IRQ·ROM 도착 기록을 사용해 65816 소비를 다시 실행했다. 각 위상의 53개 RGB와 표시 ACK가 일치했고 각각 9,464개와 9,462개 이벤트를 대조했다. 952는 5 VBlank, 밀집 5화면은 합계 25 VBlank(평균 83.157 / 83.121ms), 957 최종 검사 뒤 추가 대기는 0회다. 이 비교는 563의 정상 허가 시각을 RTL로 검증하고 기존 연속 일정을 재생한 결과다. 실제 보드에서 새 FPS를 측정한 단계는 아니다.

**MMC558을 실기 기준으로 유지한다.** 다음은 SPI 명령의 바이트 위치 4에서 인자를 받을 때 `byte_count`에서 쓰기 허가를 만드는 경로를 검증한다. 현재 바이트 위치를 앞선 비트에서 확정할 수 있는지, SS 해제·중단·잘못된 패킷에서 이전 쓰기 허가가 남지 않는지를 우선 비교한다. 같은 전체 보드에서 대상 setup과 나머지 세 음수 항목을 함께 평가한다. [검증 데이터·경로 양 끝](../analysis/guard563-verification.json)

## 재현

1. `prepare_nes_guard563.py --base <MMC558 보드> --out <새 보드>`를 실행하고 Quartus Lite의 `quartus_sh --flow compile board`, 기존 `timing506.tcl`과 `report_nes_owner562.tcl`을 실행한다.
2. `report_nes_capture563.tcl`을 562·563 두 보드 디렉터리에 복사해 각각 `quartus_sta -t capture563.tcl`로 실행한다. 원본 SDC는 변경하지 않는다.
3. 기존 FLOAT wrapper에서 `check_nes_guard563.py`로 두 보드를 순차 검사한다. 선택한 시뮬레이션은 rtl02다. 첫 벤치에서 net 선언 문법을 고쳤다. 562 두 일정에 `replay_nes_close561.py`를 적용한 후 `analyze_nes_guard563.py`로 53화면·양쪽 FIT·STA·클록 결함 시험을 결합한다.
