# 912 타일 슬롯과 SEAL credit 검증

## 목표

978의 세대 912를 VBlank 46 시작 전에 그룹 준비하고 같은 VBlank 246선까지 공개할 수 있는지 확인한다. 후속 타일용 슬롯 확보와 SEAL용 credit 확보를 분리하고 두 시작 위상의 최종 ACK를 비교한다.

## 작업내용

978의 같은 부팅 시점에서 905–912의 65816을 재생했다. 912 BEGIN까지의 패킷은 원본 그대로다. 이후 두 슬롯 비교에서는 준비된 일반 패킷을 우선하는 동일 대조군에 예약 조건만 바꿨다. ARM의 바이트 확정 시각, 두 타일 뱅크의 실제 65816 반환, ROM 생산 시각, 각 패킷 길이와 공유 SPI 점유를 사용했다. 큐 반환은 E0를 발행해 결과가 돌아와야 송신 측에 보인다. 진행 없는 E0를 포함해 매번 2,347마스터클록을 청구했다. E8은 준비된 타일마다 한 번 청구한다. 발행 정책은 재생 모델이고 실행한 수신 코드는 978이다.

- 타일 예약은 token 33 발행 직후부터 마지막 token 38까지 일반 패킷이 마지막 빈 슬롯을 쓰지 못하게 했다. 추가 대조군에서는 34의 공급에 필요한 token 33도 보호하도록 예약을 한 타일 일찍 시작했다.
- SEAL 예약은 마지막 데이터 패킷을 보낼 때 두 슬롯의 credit을 먼저 확인해 하나를 남겼다. SEAL 자체는 앞의 19개 패킷이 모두 발행된 뒤에만 같은 큐에 들어간다.
- 별도로 978 링크 ARM 원본의 E0 응답 CRC와 수락·반환 카운터를 확인했다. 실제 네 패킷 창에서 필요한 마지막 E0 수신 직후, ARM의 후처리·발행 시간이 0인 경우까지 같은 65816에서 재생했다.

## 성과

숫자는 시작 위상 1 / 2 순서다. 그룹 지연은 VBlank 46 시작 기준이고, 마지막 열은 원본 978 대비 65816 최종 성공 ACK 지연이다.

| 발행 조건 | 그룹 지연(ms) | 912 공개 | 최종 ACK 지연(클록) |
|---|---:|---|---:|
| 978 원본 | 9.446 / 9.444 | VB47 242 / 242선 | 0 / 0 |
| 두 슬롯 대조군 | 6.527 / 6.462 | VB47 246 / 247선 | 6,148 / 6,680 |
| 후속 다섯 타일에 슬롯 예약 | 6.527 / 6.462 | VB47 246 / 247선 | 6,148 / 6,680 |
| 선행 token 33부터 슬롯 예약 | 8.221 / 8.212 | VB47 247 / 247선 | 7,446 / 7,398 |
| SEAL credit 예약 | 6.776 / 6.710 | VB47 247 / 246선 | 6,500 / 6,468 |
| 다섯 타일 예약 + SEAL credit 예약 | 6.776 / 6.710 | VB47 247 / 246선 | 6,500 / 6,468 |
| 978 원래 순서에서 마지막 E0 직후 SEAL 발행 | 9.446 / 9.444 | VB47 242 / 242선 | 0 / 0 |

후속 다섯 타일 예약을 시작할 때는 일반 패킷이 이미 모두 발행돼 대조군과 같은 거래가 실행됐다. 한 타일 먼저 예약하면 token 34–37 네 개가 VB46 전에 반환됐다. 마지막 token 38 반환도 대조군보다 3.260 / 3.200ms 빨라졌다. 그러나 section 5의 마지막 240B 패킷 도착이 VB46 시작 후 5.644 / 5.635ms까지 밀렸고, E0 횟수도 41 / 40회에서 63 / 63회로 늘었다.

SEAL 예약은 마지막 타일 E1 종료와 SEAL E1 시작 사이를 4 / 14클록으로 줄였다. 그 대신 마지막 타일을 보내기 전 빈 슬롯 둘을 확보하느라 E0가 두 번씩 늘었고, 그룹 준비가 대조군보다 0.250 / 0.248ms 늦어졌다. 978 원본에서도 마지막 240B 전의 E0는 수락 193·반환 190으로 네 자리 중 하나만 남았다. 240B를 보내면 확인된 credit이 소진된다. 다음 E0(수락 194·반환 192)는 필수였고, 그 뒤 남은 1,082클록의 ARM 발행 대기를 없애도 수신기가 직전 패킷을 처리하는 동안이어서 SEAL 수락·공개·최종 ACK 시각은 같았다.

908 공개, 909 선행 DMA 624B, 910 마지막 D2 및 905–911의 전체 수신 이벤트가 원본과 같았다. 정상 실행 12건에서 905–912 RGB와 최종 성공 ACK를 검증했다. 두 위상에서 타일 예약 두 방식과 SEAL 예약에 각각 잘못된 세대의 SEAL 및 디코드 도중 STOP을 주입한 12건은 모두 911 화면을 유지했고 912 성공 ACK를 차단했다. [위상별 발행·수락·반환·공개 시각](../analysis/credit1004-results.json)

## 후속작업

978을 유지한다. 발행 순서만 바꾼 세 경우 모두 VB46 마감을 놓쳤다. 다음 후보를 고를 때는 후속 타일과 section 5를 함께 수락하는 데 필요한 65816 실행량부터 비교한다. 1002에서 같은 section 순서의 수신 비용만으로도 SPI·credit을 무료로 가정한 예산을 1.153 / 1.139ms 초과했다. 타일 또는 일반 패킷 한쪽의 대기만 줄인 결과로는 VB46 공개를 예측하기 어렵다.

재현은 978·1002 원본 TEMP에서 위상 1·2별로 `tools/nes_credit1004.py TEMP PHASE POLICY`를 실행한다. POLICY는 fixed·control·tile·feed·seal·both다. tile·feed·seal은 각각 `--fault bad_seal`과 `--fault stop_decode`도 실행한다. 마지막에 `tools/check_nes_credit1004.py TEMP analysis/credit1004-results.json`이 두 슬롯·SPI 비중복·E0 소비와 화면·거부 결과를 대조한다.
