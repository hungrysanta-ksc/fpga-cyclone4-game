# NES165 분할 경계의 저·고 플레인 보존

## 결과와 원인

SMB3 부팅의 12~20번째 표시 프레임 중 7개에서 빠지던 BG 셀을 복구했다. 실제 CPU/PPU/MMC3와 70ns PSRAM 모델을 다시 실행해 두 패턴 읽기 순간의 주소·설명자와 BgPainter의 입력 및 로드된 시프트 레지스터를 대조했다. 66,528개 BG 쌍의 실제 플레인 로드가 일치했다. 기존 수집기가 거부한 7개는 모두 **같은 타일에서 저·고 플레인의 fine Y만 달라진 경우**였다.

| 프레임 | NES 행/고 플레인 dot | 표시 행/열 | 저 → 고 물리 주소 | 저 → 고 fine Y |
| --- | --- | --- | --- | --- |
| 12, 14, 16, 18, 20 | 193 / 216 | 185 / 28 | 21efc1 → 21efc8 | 1 → 0 |
| 15, 19 | 193 / 232 | 185 / 30 | 21e150 → 21e159 | 0 → 1 |

원본 PPU는 두 시점의 바이트를 각각 정상적으로 로드한다. 주소의 행이 바뀌었다는 사실만으로 ROM 응답 오류나 잘못된 실행으로 볼 수 없다. 기존 `fetch165`는 같은 행을 강제해 오류04로 이 셀을 누락했다. 이번에 확인한 직접 원인은 **수집 형식의 과도한 동일 행 조건**이다. 특정 CPU 쓰기 명령의 원인까지 새 추적으로 확정한 것은 아니다.

## 변경 계약

- 기존 공개 `nes_native_fetch165.sv`와 `nes_native_compact165.sv`는 보존했다. 새 `nes_native_planes165.sv`와 `nes_native_compact_planes165.sv`를 검증했다. 보드에 채택된 RTL을 몰래 바꾸지 않는다.
- BG의 같은 물리 타일·논리 타일·속성·위치·평가 종류인 경우에만 두 fine Y를 따로 보존한다. 유효 응답, 저/고 플레인 선택, 정상적인 쌍 순서는 계속 요구한다. 다른 타일/은행, 다른 속성, 잘못된 주소·응답, 혼합 OBJ는 허용하지 않는다.
- 이벤트의 기존 bit15:13은 고 플레인 fine Y다. bit56은 혼합 표시, bit55:53은 저 플레인 fine Y이며 나머지 확장 비트는0이다. 혼합이 없으면 확장 비트는 전부0이다. 이 확장을 이해하지 못하는 기존 소비자에 직접 전달하면 안 된다.
- 압축 예외는 `{표시행8, 열6, 고fine3, 저fine3}`의20비트다. 최대128개이며 첫 열도 지원한다. 일반적인 셀별 fine Y 차이도 이 표를 공유한다. 최대치 초과 시 게시하지 않는다.
- 고정 데이터 RAM 논리량은28,384비트로, 이전보다384비트 늘었다. 예외의 직렬화는 여전히3바이트다. 현재 행/평가 순위 레지스터와 실제 M9K 패킹·LAB·타이밍은 별도다.
- 두 플레인이 같은 물리 타일을 쓰므로 기존 필요한 타일 집합을 그대로 유지할 수 있다. 전체8192태그 조회를 각 정상 재생에서 대조했다. 저 플레인의 다른 타일을 누락하는 식으로 조건을 완화하지 않는다.
- PC `PlaneConsumer`는 저·고 행을 따로 복사한 파생 패턴을 만든다. 상태는 실제 업로드 ACK 뒤에만 commit해야 한다. 가상 패턴 번호를 물리 PSRAM 주소로 쓰면 안 된다. 완성 CHR는 아직 PC의 비공개 ROM에서 공급한다.

## 검증

새 수집기 → 새 압축기는 재생 시험에서 **직접 연결**했다. 실제 게임에서 저장한 같은 에지의 관측값과 원래 NES 클록 간격을 사용했다. 실제 코어를 동시에 인스턴스화한 새 결선 실행은 아니며, 원본 코어의20프레임 실행은 관측 자료를 얻는 용도다.

- 표시9프레임 모두 7,401이벤트를 완전 수집했다. 기존 수집기를 나란히 실행하면 예전7개 오류04가 재현되며, 원래 정상 이벤트는 그대로다. 바뀐 것은 빠졌던 혼합 셀 하나의 추가뿐이다.
- 압축 결과는30 BG행 묶음,2 OBJ조각,2 fine Y예외로 프레임당2,226바이트의 위치/태그 정보다. CHR·팔레트·행 상태·전송 헤더를 포함한 총 전송량이 아니다.
- 압축 복원 → 독립적인 플레인별 픽셀 참조는 **원본 NES PPU의516,096픽셀과 완전 일치**했다. 두 주소의 실제 ROM 바이트와 BgPainter 로드도 별도로 확인했다.
- 실제 거부 지점에서 응답 무효·물리 타일 변경·논리 타일 변경·속성 변경·잘못된 플레인 선택·ROM 오류를 각각 넣은6사례는 게시를 거부했다. 실패 세대/범위 밖 조회/release 이후 조회도 확인했다.
- 새 예외 형식의 첫 열,128개 경계,129개 초과,표시 없는 확장,혼합 OBJ,예약 비트의6사례를 확인했다. 용량 초과·잘못된 형식은 거부했다.
- 서로 다른 혼합 조건의12·15번째 화면을 실제 SNES CPU/DMA/PPU 모델에 전달해 **114,688픽셀 완전 일치**를 확인했다. 첫 적재5,493바이트/6명령, 다음22바이트/2명령이고 갱신 완료는vblank226행이다. 공개 뒤 추가 forced blank나 활성 화면 중 VRAM/OAM/CGRAM 쓰기는 없었다.

두 부팅 화면 사이22바이트는 이 표본의 값이다. 스크롤하는 첫 레벨, 매 프레임 최악 전송량, 지속60fps, 물리 보드 타이밍을 입증하지 않는다. 기존5000바이트+명령 비용의 정책 한도는 WCET가 아니다.

재현 도구는 `test_nes_native_pair165.py`(실제 관측), `test_nes_native_planes165.py`(수집/압축 재생), `test_nes_native_plane_limits165.py`(변경 경계), `test_nes_native_planes_snes165.py`(SNES)다. 비공개 ROM과 고정된164 입력, 승인된 FLOAT 래퍼를 사용한다. 원시 입력·로그·실행 소스는 비공개 보관하며 [공개 검증 요약](../analysis/native-planes165-verification.json)에 해시를 남긴다. 관측 스크립트의 긴 문자열만 가독성을 위해 펼쳤고 Python AST 동일성을 확인했다. 실행 후 수정한 RTL 기능은 없다.

## 남은 작업과 다음 순서

이번 혼합 셀 누락은 해결했다. **165 설치 패키지와 실기 속도 개선은 아직 완료되지 않았다.** 기존164 사운드·STOP·메뉴 복귀 경로를 유지한다.

1. 수정 수집기·압축기·행별 상태를 같은 세대의 게시 경로에 연결한다. 기존 raster 오류10은 접근 자체를 거부하므로, 실제 셀 정보와 행 상태가 표현하는 범위에 맞춰 조건을 연결한다. 해당 비트를 모든 경우에 무시하지 않는다. 이번 PC 참조도 다른 raster 오류는 제외한12~20프레임만 다뤘다.
2. 필요한 물리 CHR의 유한 보충과 host CDC·완료 ACK·실제 SNES 소비자를 연결한다. 타일이 누락되거나 업로드가 끝나지 않으면 이전 게시 상태를 유지한다. 전체 이벤트 버퍼·무제한 PSRAM 읽기는 추가하지 않는다.
3. 기존38M9K 픽셀 버퍼를 교체하고 최소한의 자원·타이밍·변경 경로 검사를 통과한 후보로 실제 SMB3 첫 레벨을 시험한다. 현재56/56M9K에 새 경로를 단순 추가할 수 없다.

같은 부팅 관측이나 합성 A/B·044 복원을 변경 없이 반복하지 않는다. 이후 영상/사운드 품질이 확보되면60초 제한·오류/본체 리셋 로그·장시간 입력 유지를 다룬다. PR107에 이어서 기록하고 사용자가 머지한다.
