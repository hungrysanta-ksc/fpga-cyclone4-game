# 1000 · 912의 마지막 타일과 raw DMA

## 목표

978의 908 공개·909 선행 624B·910 캡처를 유지하고, 912의 타일 수락과 DMA 순서를 대조해 VBlank 46의 246선 종료 전에 화면을 공개할 수 있는지 확인한다.

## 작업내용

978의 실제 ARM 발행 기록과, 999에서 일반 패킷을 먼저 허용한 두 슬롯 재생을 구분했다. 후자에서는 911까지 동일한 실행을 재생한 뒤 912의 마지막 32B·128B OBJ와 raw 192B의 순서를 바꿨다. 순서만 시험할 때는 이미 검사를 통과한 descriptor를 비용 없이 재배열했다. 별도 후보는 65816 코드로 미소비 OBJ의 원본·목적지 연속성, 중간 두 쓰기와의 비중첩, 2,048B 한도를 검사한 뒤 288B와 128B를 416B로 병합한다. 후보 코드는 912 SEAL 수신 시 WRAM에 설치해 원래의 부팅·발행 시각을 보존했다.

## 성과

978의 원래 일정에서 마지막 두 OBJ의 수락·반환은 VBlank 46의 246선 마감에 맞지 않았다. 실제 발행 기록을 고정한 재생에서는 288B가 이미 DMA돼 SEAL 뒤에 남은 descriptor가 타일 32B·128B와 raw뿐이었다. 병합은 발동하지 않았고 912 공개는 VBlank 47, ACK는 978보다 212 / 272클록 늦었다. 일반 패킷을 먼저 보낸 999 대조군에서는 두 OBJ의 반환이 202·213선까지 앞당겨져 모든 타일이 VBlank 46의 시작 전에 준비됐다. 그 상태에서도 SEAL 수락은 213선, 독립 검사 뒤 업로드 진입은 236선이었다.

| 999 발행 일정에서의 65816 시험 | VBlank 46 DMA | 912 공개 위상 1 / 2 | 대조군 대비 최종 ACK 위상 1 / 2 |
|---|---:|---|---:|
| 원래 순서 | 496B | 47회 242 / 242선 | 기준 |
| 마지막 32B·128B OBJ 먼저 | 624B | 47회 241 / 241선 | 80.9 / 75.3µs 단축 |
| raw 192B 먼저, 이어서 두 OBJ | 0B | 47회 248 / 248선 | 368.2 / 367.3µs 지연 |
| 288B+128B 실제 병합 | 176B | 47회 244 / 244선 | 136.8 / 142.4µs 지연 |

병합한 두 범위의 WRAM 주소는 52,384·52,672이고 VRAM 바이트 주소는 36,000·36,288이다. 416B가 실제 한 번 전송됐지만 기존 늦은 VBlank의 단일 descriptor 제한 384B를 넘어 전체가 다음 VBlank로 밀렸다. raw 세 전송은 각각 64B이며 전용 VRAM 증가 모드를 쓴다. 실제 목록에서 raw에 부과하는 예산은 384B다. raw를 맨 앞으로 옮긴 재생에서는 현재 VBlank에서 첫 전송도 시작하지 못했다. 65816 코드 172B를 같은 방식으로 압축하면 기존 이미지보다 114B 늘어 물리 ROM 한도를 90B 초과한다.

**시간 예산.** 236선 업로드 진입 시점에 남은 시간은 14,026 / 14,042 마스터 클록이었다. 타일 656B·raw 192B·팔레트 512B·OAM 544B의 순수 DMA만 15,232클록이므로 설정·공개 비용을 모두 빼도 1,206 / 1,190클록이 부족하다. 912 마지막 D2 직후에 준비된 BEGIN을 바로 발행할 수 있다고 가정하고 실제 BEGIN 전송 비용을 포함하면 업로드 진입은 두 위상 모두 231선으로 당겨졌지만 공개는 여전히 VBlank 47이었다.

추가로 기존의 STOP 검사와 실제 그룹 DMA를 그대로 실행하되 VBlank 시작부터 전 구간을 쓸 수 있게 **다음 새 VBlank에서** 측정했다. 원래 순서의 공개는 두 위상 모두 248선으로 246선 종료보다 1,866클록(86.9µs) 늦었다. 병합한 그룹도 247선으로 1,012클록(47.1µs) 늦었다. 이 수치는 준비가 완전히 끝난 그룹의 실행 비용이다. 이를 직전 VBlank에서 쓰려면 그 VBlank 시작 전에 독립 검사·그룹 준비까지 끝내야 한다.

부팅부터 911까지 65816 이벤트를 978과 대조했고 양쪽 908 공개·909 선행 624B·910의 입력 일정은 보존했다. 정상 재생마다 905–912의 RGB를 대조했다. 손상된 SEAL과 전송 도중 STOP은 912 공개·최종 ACK를 차단하고 911 화면을 보존했다. 416B 직후 STOP을 요청하면 기존 그룹 루프가 32B 두 건을 비활성 VRAM에 더 보낸 뒤 중단했다. descriptor 경계에서 기존 STOP 서비스를 호출하자 두 위상 모두 416B가 마지막 DMA였고, 상태 0xE4로 911 화면을 보존했다. 정상 경로에서는 병합만 적용한 경우보다 ACK가 추가로 76.9 / 72.6µs 늦었다. 이 결과는 에뮬레이터 측정이다. 실기 기준과 설치본은 기존 판을 사용한다. ## 후속작업

912에서는 descriptor 순서만 바꾸는 작업을 종료한다. 다음 검증은 65816이 각 패킷을 수락하면서 최종 그룹 준비를 어디까지 마칠 수 있는지, VBlank 전에 끝낼 수 있는 검사와 SEAL 뒤에만 가능한 identity·coverage 검사가 각각 몇 클록인지 측정한다. 동시에 새 VBlank에서의 1,866클록을 DMA 설정·STOP 서비스·최종 PPU 공개로 나눠 실제로 삭제할 중복이 있는지 확인한다. 978의 실제 ARM 발행에서도 두 조건을 함께 충족할 근거가 생길 때만 전체 일정에 연결한다.

재현에는 978의 `978returned` 및 999의 `nes-ready999-bank-0-p1/p2` 원본이 필요하다. `tools/nes_dma1000.py TEMP PHASE MODE`에서 control·priority·rawfirst·join·fresh·freshjoin·guardjoin을 각각 실행한다. control에는 `--earliest-begin`, join에는 `--recorded` 및 `--fault bad_seal|stop_raw|stop_join`을 각각 별도로 실행하며 guardjoin에는 추가로 `--fault stop_join`을 사용한다. `tools/check_nes_dma1000.py TEMP OUT`이 양쪽 결과와 ROM 용량을 검증한다.
