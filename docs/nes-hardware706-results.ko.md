# MMC704·705 실기: 스페이드 통과, 서로 다른 부팅 실패와 반복 화면 깨짐

첨부12로그를 네 실행으로 분리했다. **스페이드 보너스 게임을 끝까지 통과한 실기 사례가 확보됐지만 전체 안정성 승인은 아니다.** 첫 실행 실패 두 건은 원인이 다르고, 여러 장면에서 반복된 타일 깨짐은 낮은 FPS만으로 설명할 수 없다. 이번 작업은 분석·근거 보존이며 생산 코드·보드·설치본을 변경하지 않았다.

## 네 실행의 판정

| 실행 | 표시 실행 구간 | 완료 표시 | 종료 원인 | STOP/base/menu |
|---|---:|---:|---|---|
| MMC704 1차 | 5.01초 | 0 | 첫 준비 stage0에서5초 timeout | 정상 |
| MMC704 2차 | 60.35초 | 1,189 | 정상60초 제한 | 정상 |
| MMC705 1차 | 0.22초 | 0 | 배경 CHR 읽기 마감 오류2 | 정상 |
| MMC705 2차 | 298.56초 | 5,957 | 사용자 종료 경로8 | 정상 |

위 시간은 `DISPLAY_NEXT→DISPLAY_STOPPED`이며 ROM 적재 시간은 제외한다. 네 번 모두384KiB 적재·readback과 START는 성공했다. 표본 두 번 중 한 번 실패한 것을 장기 실패율50%로 일반화하지 않는다.

MMC705 2차는 사용자 관찰상 스페이드 안내·회전 게임·클리어에 성공했다. 로그에는 ROM·CRC·plan 오류가 없고 마지막 `screen_stage=0x7e`, `native_result=8`이다. 선택 ARM의 `nes_runtime_board165.inc`에서 이 조합은 사용자 종료로 연결된다. 마지막 SEAL 한 개는 취소됐고 최종 ACK로 집계하지 않았다. 약4분59초 동안 진행한 결과이며 이전14분11초보다 긴 장시간 검증은 아니다.

## 첫 실행 실패는 분리해서 추적한다

**MMC704 1차:** 준비 응답 `01400500→01580500`, stage0,44,213회 조회,500tick=5초 대기다. native 전송·표시·ROM 오류는0이다. MMC690 실패와 마지막 응답까지 같은 계열이며 MMC551/639의 stage0 timeout 이력과 연결한다. `screen_error=05`는 `spc_init_status_valid=0`이라 오디오 초기화 오류 코드로 확정하지 않는다. 첫 SNES fetch·WRAM 복원·준비 공개 중 실제로 멈춘 위치는 로그에 없다.

**MMC705 1차:** 기존 스페이드 CPU 오류와 다른 **배경 패턴 읽기**다.

| 최초 고장 정보 | 값 |
|---|---|
| ROM 오류 / CPU observer 최초 오류 | 2 / 1 |
| 문맥 / PPU 상태 | `e30143c2c221e161` / `60b9880005858586` |
| PPU 위치 | 193선 / 230dot, sprite_fetch=0 |
| 실제 요구·진행 중 주소 | 모두 `0x21e161` |
| age / busy / response | 2 / 1 / 0 |
| PPU sample / valid | 1 / 0 |
| CPU valid / hint | 1 / 1 |

필요한 주소의 읽기는 진행 중이지만 소비 마감까지 응답이 오지 않았다. 주소 불일치나 CRC 오류를 기록한 경우가 아니다. 701의CPU `0x03fb34`/192:265,696의sprite CHR/192:262와 구분한다. 앞선 CPU 요청·mapper 변경·hint 수락·PSRAM 점유 이력이 없으므로 지연의 선행 원인은 미확정이다.

703B의 sprite 조건은 이 고장 시점에는 비활성이다. 그렇다고 그 이전 캐시/요청 일정의 영향을 배제하거나 기존 오류라고 단정할 수 없다. 699/703B를 같은 실제 CPU·ROM 조건에서 재생해 최초 차이를 찾아야 한다. 기존36조건 통과는 이 배경 경계의 증명이 아니다. 실패 두 건의 DWT는 `cost_sampled=0`이며 성능 계산에 넣지 않았다.

## 성공 실행의 FPS

최종 표시 완료 카운터를 사용하고 시작·마지막5초를 제외했다. 서로 다른 실행과 장면을 합쳐 하나의 FPS로 만들지 않았다.

| 구간 | MMC700 이전60초 | MMC704 2차 | 변화 | MMC705 2차 첫 구간 |
|---|---:|---:|---:|---:|
| 5–40초 | 20.89 | 18.69 | −10.53% | 19.29 |
| 40–55초 | 21.87 | 19.87 | −9.15% | 23.53 |
| 5–55초 | 21.18 | 19.04 | −10.10% | 20.56 |

이번 MMC704 측정값은 이전보다 낮다. 다만 화면당 map 변경량은 초반+18.53%/후반+11.33%,OBJ는+3.66%/+48.03%,E1 전송량은+7.81%/+3.91%로 작업량도 늘었다. **보드 수정 때문에10.10% 느려졌다고 인과적으로 단정할 수는 없다.** ARM·65816의 실행 코드는 이름 외 동일하며 703은 안정성 수정으로 전달됐다. 같은 작업량의 비교가 필요하다.

MMC705의 이전701 대비 첫5–40초는−4.66%,40–55초는+18.46%지만 동일 플레이가 아니다. 장시간판은 첫 두 완료 카운터만 계속 보존하고 작업량 bin은 약60초마다 재사용한다. 이번에는240.13초 이후 작업량만 남으므로 초반55초와 맞춰 가속률을 계산하지 않는다.

## 끊김과 타일 깨짐

| 전체 성공 실행의 DWT 평균(ms/완료 표시) | MMC704 | MMC705 |
|---|---:|---:|
| 수신 | 8.85 | 9.61 |
| 계획·공급 | 11.65 | 11.34 |
| 출력·최종 ACK | 29.48 | 28.60 |

출력·최종 ACK가 가장 크다. 이 값은 IRQ·조회·대기를 포함하며 중첩된 SPI 비용을 다시 더하지 않는다. 현재 로그만으로 DMA와 마지막 VBlank를 나눌 수 없다.

MMC705의 마지막 epoch에서 완료 표시 사이 **260ms,430ms,300ms** 공백이 기록됐다. 최대430ms는 시작 시각255.13–260.13초 bin에 귀속된다. 개별 화면·스페이드 시각은 기록하지 않아 그 구간을 보너스 게임으로 명명하지 않는다. 마지막 bin은 부분 구간이며 bin은 프레임 시작 소유권 기준이다. 430ms를 지속 FPS로 환산하지 않는다.

캡처 이력의 마지막16항목은 REJECT→RECOVERY8쌍이다. 모두 기록된 collector 오류0이며 거부 시 후보 display mask는0,회복 시24다. 0개 또는 소수 BG 그룹과 회복까지11–21세대 차이가 보이지만 절대 시각이 없어430ms 공백과 직접 연결하지 않는다. 전환 중 표현 가능한 화면을 기다린 정황은 있으나 전체 캡처가 무손실이라는 뜻은 아니다.

사용자는 **여러 장면에서 타일 밀림·깨짐이 반복됐다**고 확인했다. 정상적인 완성 프레임 교체라면 출력이 늦어져도 이전 완성 화면이 유지돼야 한다. 깨짐을 단순 성능 부족으로 처리하지 않고, 캡처의 scroll/CHR bank 일관성 → ARM의 map/tile 이력 → 실제 비활성 VRAM DMA·표시 bank 전환을 검사할 별도 정확성 문제로 등록한다. 전송 CRC·최종 ACK는 입력 화면의 의미와 픽셀까지 보증하지 않는다. 오류 시각의 캡처·VRAM·영상이 없으므로 어느 단계인지 아직 확정하지 않았다.

MMC704 종료 시 `native_video_error=7`도 구분한다. 선택 planner에서는7이 BG 슬롯 부족뿐 아니라 map 발행 callback 실패에도 사용된다. 최초 runtime 결과는60초 deadline1이고 window3은 transfer callback 거부다. 실패 SPI·CRC는0이며 정확한 호출 위치가 없으므로 이7을 플레이 중 슬롯 부족이나 타일 깨짐의 증거로 사용하지 않는다. MMC705의 window2 역시 정상 사용자 종료 guard 거부와 일치한다.

## 다음 순서

1. **배경 CHR 마감 재현:** MMC705 1차의193:230/0x21e161을 실제 CPU·mapper·PSRAM 요청/응답 시간축에서699와703B로 비교한다. 기존 스페이드 CPU·CHR 두 plane·다음 sprite와 STOP 검사를 함께 유지한다. 오류 무시나 timeout 연장으로 통과시키지 않는다.
2. **반복 화면 깨짐:** 재현 가능한 게임 진행에서 NES 캡처/CHR·scroll과 ARM 결과·실제 SNES VRAM/표시 bank를 대조한다. 처리 지연 중 완성 화면 유지와 부분 전송·최종 ACK 이력의 일관성을 먼저 확인한다. 새 로그가 필요하면 현재 회로·Flash 예산 안에서 원인 경계에 필요한 최소 정보만 정한다.
3. **별도 부팅 timeout:** MMC704/690의 같은 stage0 응답에서 첫 SNES fetch·압축 해제/WRAM·ready 공개 경계를 추적한다. 배경 마감 오류와 같은 오류로 묶거나 무조건 재시도를 넣지 않는다.
4. 위 안정성 경계를 확인한 뒤 동일 map·OBJ 작업량으로 출력·최종 ACK 병목을 재개한다. 기존703 두 위상 일정·독립 검사·STOP·메뉴 복귀는 보호한다.

분석 도구는 `tools/analyze_nes_hardware706.py`, 선택 근거는 `WORKSPACE/probes/nes-hardware706/analysis02`다. 원본12로그·선택 ARM/RTL·분석 결과를 SHA256으로 보존했다. analysis01도 남겼으며 analysis02는 사용자의 여러 장면 반복 관찰을 반영했다. 새 구현·FIT·STA·실기 설치본은 없다.
