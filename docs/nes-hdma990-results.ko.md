# 990 · 911의 HDMA 행 선행 발행

## 목표

978과 같은 두 부팅 위상에서 911의 마지막 큐 반환을 앞당겨 VBlank 44의 246선 끝까지 공개할 수 있는지 확인한다. 908 공개, 909의 선행 DMA 624B, 910 캡처, 독립 검사, STOP, 912 최종 ACK를 함께 비교한다.

## 작업내용

- ARM Unicorn에서 raw 원본의 실제 192바이트, 3개 HDMA 스트림의 유효 바이트와 길이, SPI용 raw 복사본의 마지막 쓰기를 따로 기록했다. 65816에서는 실제 수락·반환과 PPU DMA 포트의 마지막 바이트를 같은 실행에서 기록했다. 905부터 912까지 각 세대의 최종 RGB, map, tile plan과 section 5 복원 내용을 대조했다.
- 원래 발행 위치에서 HDMA 240+9B를 raw보다 먼저 보내는 대조군과, planner가 세 행을 먼저 만든 뒤 검사가 끝난 sink 진입 시점에 먼저 보내는 후보를 나눴다. 후자는 각 21B인 세 스트림을 담은 183B를 보내고, 수신기가 60B 패딩과 길이 6B를 복원한다. raw는 대상 뱅크의 빈 192B 범위에만 쓸 수 있다. 미완료 범위가 있으면 SEAL을 거부한다.
- 송신 큐를 그대로 진행시키는 경우, OAM보다 raw를 앞세우는 경우, OAM 반환을 기다려 타일 DMA 기회를 만드는 경우를 분리했다. 911 raw의 세 64B 구간은 각각 같은 16비트 단어 32개였다. 이 조건을 ARM이 검사하고 6B를 전송해 65816이 실제 192B를 복원하는 비용도 별도로 측정했다.
- planner 내부에서 즉시 발행한 두 후보는 양 위상 모두 909에서 sink 오류 5로 중단됐다. 아래 완주 수치는 sink 진입 검사를 거치는 후보 또는 원래 발행 위치의 대조군에서 얻었다. FPGA ROM 중재를 포함하는 기존 재생 모델을 사용했다. 실기 FPS와 새 Quartus 결과는 측정 범위 밖이다.

## 성과

978에서는 raw 픽셀보다 HDMA 유효 행·길이가 0.076ms 늦게 확정됐다. 길이가 확정된 뒤 첫 201B 패킷 발행까지는 4.186 / 4.310ms가 더 걸렸다. 후보에서는 세 행·길이가 raw보다 0.098ms 일찍 확정됐다. 아래 값은 위상 1 / 2 순서이며, 큐 반환은 SEAL 바로 앞 마지막 데이터 패킷의 65816 ACK다. 양수 차이는 978보다 늦음을 뜻한다.

| 발행 방식 | 마지막 큐 반환 차이 ms | 909 선행 DMA B | 911 직전 246선까지 DMA B | 911 표시 간격 | 912 ACK 차이 ms |
|---|---:|---:|---:|---:|---:|
| 978 | 0 / 0 | 624 / 624 | 0 / 0 | 2 / 2 | 0 / 0 |
| 원래 위치에서 HDMA→raw | +0.498 / +0.229 | 624 / 624 | 0 / 0 | 2 / 2 | +0.010 / +0.018 |
| HDMA 183B 먼저, raw 192B는 OAM 뒤 | +0.356 / +0.152 | 464 / 464 | 0 / 0 | 2 / 2 | +0.336 / +0.344 |
| HDMA 먼저, OAM 반환 대기 후 raw | +1.270 / +1.322 | 464 / 464 | 432 / 432 | 2 / 2 | +0.352 / +0.349 |
| HDMA 먼저, raw를 6B로 보내 192B 복원 | +0.852 / +0.685 | 464 / 464 | 0 / 0 | 2 / 2 | +0.330 / +0.339 |
| 6B raw와 OAM 반환 대기 결합 | +1.148 / +1.123 | 464 / 464 | 16 / 432 | 2 / 2 | +0.341 / +0.339 |

OAM 반환 뒤 raw 192B를 그대로 보낸 경우 HDMA 첫 발행은 978의 첫 raw·테이블 패킷보다 3.521 / 3.722ms 빨랐다. 양 위상 모두 908은 VBlank 38의 245선에 공개됐고, 910 캡처 여유는 0.011 / 0.072ms였다. 그러나 마지막 OAM과 raw의 서비스가 뒤에 남았다. 911의 타일 16+32+384B는 VBlank 44의 243선에 끝났다. 잔여 raw 192B·팔레트 512B·OAM 544B의 마지막 쓰기는 VBlank 45의 238선, 공개는 240선이었다. 밀집 여섯 간격은 978과 같은 13 VBlank였다.

243선에서 타일을 끝냈을 때 246선 끝까지 5,192 / 5,212 master clocks가 남았다. 잔여 1,248B의 순수 DMA만 9,984클록이므로 설정과 검사 비용을 모두 없애도 0.223 / 0.222ms가 모자란다. 실제 첫 raw DMA 시작부터 공개까지는 18,876 / 18,916클록이 걸렸다. 이 경로를 유지한다면 첫 raw DMA 시작 마감은 두 위상 모두 약 233선이다.

978의 ARM Flash는 212,992B, 저장형 65816 ROM은 5,096B다. 432B를 양쪽 모두 옮긴 후보는 각각 213,308B와 5,312B로 두 한도(212,992B, 5,120B)를 넘었다. 전체 후보별 코드 크기·해시·DMA 시작 및 종료·오류 주입 결과은 [측정 결과](../analysis/hdma990-results.json)에 보관한다.

오류 주입 8건에서는 모두 직전 910 화면을 보존했다. raw 누락·부분 수신과 WRAM 행 손상은 0xE0, 독립 검사 도중 STOP 및 HDMA 수락 뒤 raw가 아직 비어 있을 때의 STOP은 0xE4로 종료했다. 후자의 두 위상에서 STOP을 실제로 읽은 것을 확인하고, 그 응답에서 송신을 끊었다. raw가 오기 전의 테이블 249B와 SEAL 전 전체 441B도 978 원본과 대조했다.

재현에 사용한 도구는 `tools/build_nes_hdma990.py`(후보 ARM 소스·65816 ROM 생성), `tools/build_nes_trial577.ps1`(ARM 링크), `tools/nes_hdma990.py`(두 위상 전체 재생), `tools/test_nes_hdma990.py`(고정 도착 시각 오류 주입), `tools/check_nes_hdma990.py`(교차 대조)다. JSON의 `ref`는 978 재실행, `safegap`은 183B HDMA와 OAM 반환 대기, `rlegap`은 같은 순서에서 raw를 6B로 보낸 후보를 가리킨다.

## 후속작업

978을 유지한다. 다음 비교에서는 910 표시 대기 중에 911의 확정 raw를 비활성 VRAM에 쓸 수 있는 최초 시각과 911 첫 타일의 실제 수락 시각을 먼저 대조한다. 화면에 영향을 주는 팔레트·OAM은 공개 VBlank 안에 두고, 909 선행 624B를 유지한 조건에서 마지막 타일과 raw가 끝난 뒤 남는 시간을 측정한다. 후보 선택에는 911의 246선 공개와 두 위상의 912 최종 ACK를 함께 사용한다.
