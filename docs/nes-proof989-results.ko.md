# 911 수락 시점의 독립 검사와 타일 DMA

## 목표

978을 기준으로 908 공개, 909 선행 전송 624B, 910 캡처 및 911 타일 432B 선행 DMA를 보존하면서 911을 VBlank 44의 246선 끝까지 공개하고 912 최종 ACK를 줄일 수 있는지 시험했다.

## 작업내용

첫 후보는 65816이 스크롤 21B를 수락한 직후 WRAM에서 네 구간의 길이·224선 합·종결자를 검사하고 원본 21B를 보관한다. 겹치는 쓰기와 BEGIN은 쓰기 전 헤더 경로에서 검사 결과를 지운다. 분리된 타일·팔레트·OAM 및 겹치지 않는 section 5 이어쓰기는 기존 범위 검사를 통과해야 한다. SEAL에서는 독립적으로 검사한 바이트와 실제 WRAM을 다시 대조하고 기존 테이블 의미 검사와 최종 coverage 검사를 실행한다.

두 번째 후보는 한 행의 마지막 테이블 리터럴이 수락되면 기존 의미 검사기를 실행한다. 임시로 설정한 메타데이터 네 단어는 호출 직후 복구한다. 21B 형식의 네 HDMA 스트림, 각 스트림 바로 뒤 패딩 한 바이트 및 길이 세 단어를 보관한다. SEAL에서 도착한 메타데이터와 바이트를 다시 대조한다. 다른 길이·레이아웃은 기존 검사기를 사용한다. 후보 모두 검사 결과는 한 번의 SEAL에만 쓸 수 있다. 데이터 쓰기나 상태 변경이 가능한 새 명령과 STOP에서 해당 결과의 유효성을 관리한다.

같은 입력에서 실제 ARM 링크와 Mesen 65816을 905부터 912까지 두 위상으로 실행했다. 978 원본 및 동일 ARM·원본 65816의 985 두 대조군과 비교했다. 별도 재생에서는 910까지 같은 부팅 ROM·ARM 일정을 사용하고 911 BEGIN에서 수신 코드만 바꿨다. 905–912 RGB, map 바이트, 타일 plan, 출력 패킷과 911의 DMA 종류·순서를 대조했다.

## 성과

스크롤 검사와 선행 DMA를 함께 유지한 전체 부팅 결과다. 최종 ACK 변화는 978 대비다.

| 항목 | 위상 1 | 위상 2 |
|---|---:|---:|
| 908 공개 | VBlank 38·245선 | VBlank 38·245선 |
| 909 선행 DMA / 910 캡처 여유 | 624B / 0.086ms | 624B / 0.152ms |
| 검사 결과 기록부터 첫 타일 DMA까지 | 10.234ms | 10.237ms |
| 911 타일 432B 마지막 바이트 | VBlank 44·248선 | VBlank 44·248선 |
| 911 공개 / 밀집 여섯 간격 | VBlank 45·240선 / 13회 | VBlank 45·240선 / 13회 |
| 912 최종 ACK | 0.008ms 빠름 | 0.018ms 늦음 |

스크롤 검사·보관에 0.102ms, SEAL 재대조에 0.067ms가 걸렸다. 타일의 마지막 바이트가 이미 246선 끝보다 0.105 / 0.102ms 늦었다. 같은 ARM의 985 대조군에 비해 SEAL 진입→업로드는 0.010 / 0.007ms 줄었다. 910까지 부팅을 일치시킨 스크롤 대조 실험도 432B는 선행했지만 911 공개는 VBlank 45였다.

테이블까지 먼저 검사하면 SEAL 진입→업로드는 978의 1.306 / 1.308ms에서 1.032 / 1.031ms로 줄었다. 다만 마지막 249B 테이블 중 240B가 마지막 패킷에 들어 있다. 해당 패킷 수락 경로의 검사·보관에 0.939 / 0.937ms가 걸렸다. 마지막 큐 반환 뒤에 DMA 기회를 주면 직전 VBlank의 타일 전송은 0B가 됐다. 두 테이블 패킷 사이를 비우면 432B를 옮겼으나 타일 DMA가 시작된 뒤에야 검사 결과가 기록됐고 위상 2의 908 공개도 한 번 밀렸다. 스크롤 후보에서 이 발행 방식을 쓰면 910 캡처를 0.127 / 0.061ms 놓쳤다.

두 위상에 각각 아홉 건의 고장을 주입했다. 검사 후 스크롤·테이블·길이 바이트 직접 변경, 새 패킷에 의한 추가·중첩 쓰기, 잘못된 SEAL 세대는 0xE0로 거부했다. 살아 있는 검사 결과를 확인한 뒤 SEAL부터 유지한 STOP은 0xE4가 반환됐다. 모두 911 최종 ACK 없이 910 화면이 보존됐고 검사 결과가 비워졌다. 직접 WRAM 변경 검출 시점은 SEAL 재대조이며, 명령을 통한 무효화 시점과 구분했다. 최초 STOP 주입기의 펄스는 수신기가 읽기 전에 사라져 정상 커밋됐다. 최종 시험은 STOP을 수신기가 읽을 때까지 유지했다. 초기 분기 반전 오류가 있던 진단 ROM의 수치는 제외했다.

두 ARM 대조 링크는 각각 213,040B로 Flash 한도를 48B 초과했다. 65816 로더·압축 본문·벡터는 테이블 후보 5,364B와 스크롤 후보 5,423B로 각각 244B와 303B 초과했다. 추가 WRAM은 각각 96B와 23B다. 메뉴는 같은 ARM 소스의 정상 해제·실패 차단 경로를 검사했다. 이번 결과는 실기 FPS가 아니다. [시각·코드 해시·고장별 결과](../analysis/proof989-results.json)

## 후속작업

978을 유지한다. 다음 후보는 201B 패킷 앞 192B의 raw와 마지막 240B의 테이블이 각각 언제 확정되는지부터 대조한다. 유효한 HDMA 행을 먼저 보내고 패딩과 raw를 나중에 보내는 순서가 가능한지, 그러면서 최종 큐 반환과 빈 큐 DMA가 앞당겨지는지 검사한다. 432B만 246선에 맞춰도 잔여 raw 192B·팔레트 512B·OAM 544B의 순수 DMA에 최소 0.465ms가 더 필요하다. 이 비용과 설정·공개까지 포함해 두 위상의 911 공개와 912 ACK가 함께 빨라질 때 채택한다.
