# NES171 — 제한된 메모리 읽기와 MCU 소비 대기를 FIFO로 분리

## 문제와 변경 범위

170 실기는13회 표시 후 후보가8회 중단됐고 최초·마지막 사유0x34는 fill 전체 제한 초과였다. 기존 fill은1바이트를 읽은 뒤 MCU 소비가 끝나야 다음 읽기를 요청했다. vblank 구간에만 허용되는 메모리 승인이 host 전송 대기와 직렬로 묶인다. 실제 지연의 비율은170 로그에 없으므로 단일 원인 확정이나 물리 처리량 측정으로 표현하지 않는다.

171은 fill 내부에256×27비트 FIFO를 넣는다. 데이터8비트와 물리 타일13비트·lane4비트·종류2비트를 한 항목으로 저장한다.256은 실제 CHR 데이터 바이트 수이며 총 저장량은6912비트, M9K1개다. FIFO 공간이 있으면 기존 arbiter가 승인한 읽기를 진행하고, 소비자는 별도로 순서대로 받는다. 카트리지 세이브 SRAM은 사용하지 않는다.

- 기존 단일 메모리 요청·CPU/PPU 우선·vblank 자격·7에지 응답 감시를 그대로 사용한다. FIFO가 가득 차면 새 요청을 중단한다.
- 주소·세대·오류 검증에 성공한 응답만 저장한다. FIFO에 세대가 다른 데이터가 섞이지 않도록 clear/reset/재시작 시 포인터·개수·출력 유효를 초기화한다. 미완료 물리 요청은 기존 quarantine/flush 절차로 회수한다.
- 동기식 RAM 읽기가 끝나야 출력 유효를 올린다. 마지막 항목의 pop과 새 write가 겹칠 때 read-during-write 결과는 유효로 내보내지 않고 다음 읽기를 기다린다. 미초기화 RAM의 내용은 화면에 노출하지 않는다.
- 필요한 타일을 모두 읽고 FIFO까지 비워야 fill 완료다. COMMIT/SEAL/표시 ACK 계약은 바뀌지 않는다. 실패한 후보는 여전히 폐기한다.
- fill 전체16777216, export 전체33554432, 짧은 제한131072클록은 유지한다. cooperative 짧은 제한에서 REQUEST와 마지막 FIFO DRAIN 대기를 제외하지만, 모든 대기는 전체 제한에 포함한다. 기존 REQUEST/STREAM 정책에 대응하며 무한 대기를 허용하지 않는다.
- MCU 변경은171 파일명·식별자뿐이다.170 transport·로그·사운드·입력·60초 종료·RUN 중 SD 쓰기 금지와 SNES169 VRAM 분할 표시는 그대로다.

## 검증 근거와 한계

같은 실제 fill/arbiter/export RTL을 연결하고 query·메모리 데이터·메모리 승인 가능 구간·소비자 속도를 모델링했다. 기존 경로는128타일 조건에서654바이트 뒤 전체 제한0x34로 중단됐다. FIFO 경로는 같은 조건에서2048바이트를 완료했다. 최대512타일8192바이트도 두 가지 슬롯 시작 위상에서 기존 제한 안에 완료했다. 이는 원래 병목 구조의 재현·비교이며 실제170의1892바이트 실패 지점을 그대로 재생한 것은 아니다. 호스트/SPI의 물리 대기 패턴이나 게임 fps 측정도 아니다.

주소·세대·백엔드 오류·지연 응답·clear/reset·한도·lease 취소의16개 기존 검사와, FIFO가 가득 찬 뒤 clear/세대 취소/reset 검사로 변경 경계를 검증한다.512타일 비교는 여러 번의 FIFO 포인터 순환과 모든8192바이트의 순서·내용을 검사한다. 변경하지 않은 게임 부팅·매퍼·입력·오디오 시험을 다시 쌓지 않는다.

새 전체 MAP/FIT와3코너 타이밍을 확인한다. 실제 클록 기준과 더 엄격한 분석 예산 보고서를 구분한다. 외부 IO는 기존70ns PSRAM·PCB 여유 가정으로 조건부 계산하며 전기적 실측·전체 CDC/MTBF 승인을 주장하지 않는다. 기존 SNES 프로그램을 다시 합성하므로 프로그램 원본 바이트와 패키지 경로도 대조한다.

ARM은 실제 full-link/RUN·IRQ 그래프와 변경 없는 라이브러리 본문을 확인한다. RUN37320+IRQ508 후 RAM 여유1024바이트, 최대 TXT4020/4096바이트다. 새 영구 MCU 영상 버퍼는 없다.
