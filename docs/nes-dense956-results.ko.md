# MMC955 후반 OBJ 지연과 MMC956 실기 진단판

## 목표

PR175가 master에 병합된 커밋 `03ebcee`에서 시작했다. 실기 속도 기준은 MMC955, 모험도 4 무입력 오프닝 23.28 FPS와 데모 23.90 FPS다. 55–60초 중 마지막 OBJ 준비에 약 60ms가 걸린 두 화면을 대상으로 첫 ROM 요청·허가와 같은 뱅크의 직전 반환 시각을 비교한다.

## 작업내용

MMC955 BIN의 세대·token·뱅크 검사를 거친 120개 요약을 다시 읽었다. 두 화면 모두 상세 페이지가 저장되지 않아, MMC956에서 기존 320개 기록 공간을 두 슬롯으로 나눴다. 슬롯당 타일 128개와 묶음 32개까지 보관한다. 16B 헤더와 각 32B 응답에서 세대·token을 검증하고 마지막 페이지까지 통과한 슬롯만 공개한다. 952 FPGA·65816·메뉴 이미지와 8,044B BIN 크기는 MMC955와 같다.

## 성과

| MMC955 실기 | 56.44초 / 세대 1396 | 56.68초 / 세대 1400 |
|---|---:|---:|
| BG / OBJ / 변경 map 행 | 529 / 51 / 0 | 528 / 55 / 0 |
| 타일 / 묶음 수 | 19 / 5 | 33 / 8 |
| 마지막 OBJ 바이트 / staging 오프셋 | 32 / 1,184 | 32 / 1,216 |
| 입력 완료 → 첫 E9 범위 | 6.376–7.948ms | 7.015–8.588ms |
| 첫 E9 → 마지막 OBJ 준비 | 60.855ms | 60.075ms |
| 마지막 OBJ 준비 → 첫 유효 최종 ACK 추정 | 11.282–12.854ms | 11.672–13.245ms |
| 입력 완료 → 첫 유효 최종 ACK | 80.085ms | 80.335ms |

마지막 OBJ 준비 이후의 범위는 마지막 행에서 앞의 두 구간을 차감한 값이다. MMC955 관측 정밀도(약 0.390ms)와 첫 E9의 경계를 적용했다. 지연 대부분은 첫 E9 발행 이후 타일 공급 구간에 있었다. 세대 1393에서 관측한 ROM 허가 0회는 이 두 세대에 적용할 수 없다.

최종 MMC956 ARM에 MMC955의 실제 120개 행과 통제한 상세 페이지 응답을 입력했다. 정상 재생에서는 요약 35·39번째에서 세대 1396·1400만 선택했고 상세 페이지 조회는 13+21=34회였다. 두 번째 상세 복사 중 token을 바꾸면 첫 슬롯만 공개됐다. Flash는 212,952/212,992B다. 최종 링크에서 SRAM D0 네 곳, 잘못된 CRC와 오래된 세대·token 거부, ROM 로더, 60초 타이머, STOP·base/메뉴 복귀 경로를 시험했다. [최종 링크·ZIP 검증](../analysis/trial956-package.json)

## 후속작업

MMC956의 60초 무입력 실기 로그 한 세트를 받으면 `tools/analyze_nes_dense956.py BIN`으로 두 화면의 묶음을 시간순으로 읽는다. 각 타일의 최초 요청→허가, 첫→마지막 허가, 같은 뱅크의 직전 반환→다음 최초 요청을 구분한다. 캐시 적중 시 요청 시각이 없으므로 뱅크 대기를 역산할 수 없는 구간은 미측정으로 남긴다. 이번 보드에서 관측되는 표시 간격은 ARM의 연속 최종 ACK 간격이며 정확한 공개 VBlank 번호는 별도 관측이 필요하다. [설치 및 회수할 파일](nes-mmc956-trial.ko.md)

재현 시 `prepare_nes_dense956.py`, `build_nes_trial577.ps1 -SourceRoot ../probes/nes-trial956/link` 순으로 실행한다. 최종 링크의 공통 검사는 `check_nes_supply905_arm.run`에 MMC956, 짧은 헤더, `nes_order938.empty_next_offer`, marker 값 (4,8,16,24)를 전달한다. `package_nes_dense956.py MMC955_BIN`은 두 슬롯 검증과 SHA 검사를 통과한 파일만 패키징한다.
