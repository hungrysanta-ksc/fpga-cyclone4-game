# 570 · 메모리 시작 허가와 고장 중 E9 수락

**다음 검토 기준은 로컬 해제 후보(board05), 실기 기준은 MMC558이다.** 이 후보는 기존 비교 기준인 코너·클록별 최악 음수 slack(WNS) 회귀를 8개에서 0개로 줄였다. 미제약 출력 집계가 늘어 실기 ZIP은 보류한다.

기준은 568 A loader와 569 직접 캡처를 함께 사용한 보드다. 다섯 후보는 모두 동일한 loader·plan ABI·제약·seed를 사용한다. **메모리 대조군**은 참조 클록의 시작 허가만 168MHz에서 두 플립플롭으로 받은 후 메모리 쪽 허가와 결합한다. **슬롯 차단 후보**는 여기에 NES 생산자 고장과 sticky fault를 받아 비동기로 닫히는 host 차단 신호를 plan transport의 STOP으로 연결한다. **SPI 차단 후보**는 이 신호를 SPI endpoint의 `source_fault`에도 연결한다. **뱅크 공유 후보**는 같은 신호를 타일 뱅크의 STOP에도 연결해 고장 시 RAM 소유권을 함께 취소한다. **로컬 해제 후보**는 동일한 즉시 차단을 유지하며 plan과 타일 뱅크가 공통 reset을 별도로 한 번 더 받던 배선을 제거한다. 두 하위 회로 모두 공통 reset이 들어오면 host 차단 체인을 통해 비동기로 닫히고 host 에지에서만 풀린다. 기존 NES·host 고장 래치와 상대 도메인의 보고 경로는 유지한다.

## 마지막 E9의 수락 시점

실제 954 E9 패킷을 보드의 SPI endpoint에 전송했다. payload·CRC·trailer가 들어왔지만 SS가 아직 낮을 때, 두 클록을 멈추고 NES 고장을 인가했다. SS를 올린 뒤 **NES를 정지한 채 host만 12에지** 실행했다. 이 사례는 전체 보드 watchdog이 개입하기 전에 SPI 수락과 RAM 소유권이 어긋날 수 있는지를 보기 위해 direct 경로를 분리한 시험이다.

| 정지 중에 확인한 항목 | 569 기준 | 슬롯만 차단 | SPI 수락까지 차단 |
|---|---:|---:|---:|
| NES fault 래치 전 writable이 계속 1인 경우 (lease·core·실제 tile 고장) | 3/3 | 0/3 | 0/3 |
| 마지막 SS 뒤 E9 수락 횟수 증가 | 1 | 1 | 0 |

두 위상에서 각각 두 슬롯을 봉인한 뒤 host를 먼저 멈추고 NES 고장을 래치하는 경우도 확인했다. `nf`가 이미 올라오면 기준과 후보 모두 host 에지 없이 plan 노출과 retire를 차단했다. 차이는 **생산자 고장이 올라온 마지막 NES 에지와 `nf`가 이를 샘플하는 다음 에지 사이**에 있었다. 새 후보는 이 구간에서도 실제 쓰기 허가와 E9 수락을 함께 차단한다. SPI가 이미 전송한 상태 바이트는 해당 스냅샷을 뜬 시각의 값이다. 실기에서 잘못된 반환을 관측한 사례와는 구분한다.

다음 E8을 실제 SPI로 읽어 CRC8까지 확인했다. 기준과 슬롯만 차단한 후보는 고장 플래그 `80`에 수락 1을 반환했다. SPI까지 차단한 후보는 같은 플래그에 수락 0을 반환했다. 두 클록이 멈춘 가운데 공통 reset을 짧게 걸고 재개한 뒤에는 정상 플래그 `01`·수락 0으로 돌아왔다. 시뮬레이션에서 차단이 먼저 일어나도 host와 NES의 sticky *보고* 플래그는 각 도메인이 클록을 받은 뒤에 올라올 수 있다.

## 클록 정지와 복구 조건

참조·메모리 클록 중 하나만 남은 경우에는 초기 자격 확인 전, 33,603클록 시작 대기 중, PSRAM OE가 활성인 읽기 중에 다른 클록을 멈췄다. 살아 있는 쪽 watchdog의 고장 래치가 올라간 뒤에는 멈춘 도메인의 다음 에지 없이 메모리 핀이 비활성이 되고 미완료 응답이 폐기됐다. 메모리 클록 정지를 참조 쪽에서 검출하는 데 2.962–3.041µs, 참조 클록 정지를 메모리 쪽에서 검출하는 데 3.812–4.003µs가 걸렸다. 정상 시작 시 마지막 자격 확인 뒤 메모리 release까지는 두 위상에서 11.904ns였다. 시험한 시작 순서에서는 참조 허가의 추가 동기화가 시작 시간을 늦추지 않았다. 클록만 재개해서는 다시 시작하지 않았다.

**두 클록을 동시에 멈추고 lock 입력을 유지하면** 두 watchdog도 멈춘다. 진행 중이던 PSRAM 읽기는 5µs 뒤에도 OE가 활성인 상태였다. 이때 외부 lock 상실을 인가하면 클록 에지 없이 핀이 닫혔다. 여기서 즉시 차단은 고장·reset이 실제로 인가된 뒤에 추가 클록이 필요 없다는 RTL 관측이다. 보드 전파 지연이나 실제 PLL의 lock 감지 시간까지 측정한 값은 아니다.

## 타일 뱅크의 STOP 경계

토큰 1의 16B 뱅크에서 토큰 하위 두 바이트를 먼저 쓴 뒤 실제 SNES aperture를 읽고 있는 상태로 두 클록을 정지시켰다. NES 고장이 올라오자 SPI 차단 후보와 뱅크 공유 후보 모두 SNES 데이터 버스를 해제했다. 이 시점에 전자는 내부 `chunk_ready`가 여전히 1이었고, 뱅크에 차단을 공유한 경우는 0이었다. 공통 reset 뒤 새 토큰 1에 다른 16B를 발행했다. 상위 두 바이트와 commit만 보내면 이전 하위 두 바이트를 이어 쓸 수 없어 소비 펄스는 0회였다. 새 16B 전체를 읽고 네 토큰 바이트를 모두 쓴 경우에만 소비 펄스가 1회였다. 이 벤치의 ROM 응답은 패턴이고, 타일 생산기·두 뱅크·SNES 버스 제어는 보드 RTL이다. 최종 표시 ACK 시각은 별도의 65816 재생에서 확인했다.

## 표시 일정

실제 plan SPI·두 슬롯 RAM·NES decoder에서 위상별 16개 STOP 지점/클록 조합, 잘못된 CRC·길이·lease, 슬롯 재사용과 최종 retire를 검사했다. 954는 기존 ARM의 E8 8회·E9 3회에 ROM 경합에 따른 타일 완료 시각을 공급해 23개 plan과 END를 확인했다. SPI 종료 시각은 두 방식으로 대조했다. 고장 주입은 ROM 공급을 막아 디코더가 실제로 머무는 READY를 기준으로 했다. 초기 벤치는 RUN을 기다려 타임아웃이 났고, 이를 바로잡아 시험했다. 53개 화면은 같은 두 도착 기록으로 실제 65816에서 따로 재생했다. 위상별 9,464 / 9,462개 이벤트와 RGB 전체가 569와 일치했다. 952·957은 모두 표시 간격 5 VBlank, 최종 준비 뒤 대기 0회였고 마지막 ACK는 87,545,284 / 88,254,606 master clocks였다. 실제 ARM 프레임 루프를 새로 실행하거나 실기 FPS를 계측한 결과는 아니다.

## 실기 인계에 남은 항목

원래 배치 제약의 미제약 출력 경로 수(setup / hold)는 MMC558 **3,015 / 3,018**, 569 **3,008 / 3,011**, 로컬 해제 후보 **3,018 / 3,021**이다. 569에서 늘어난 10개는 기존 SNES 데이터 8핀과 OE·DIR에 하나씩 추가된 경로다. 후보 netlist에서 출발점 이름은 `transport.hrelease.release_reset[1]`이었다.

원래 SDC를 그대로 둔 채 별도 가상 IO 뷰에서 register→pin 데이터 지연도 조회했다. 85°C host 최악 지연은 MMC558의 OE / DIR / DATA 최대 18.113 / 16.911 / 23.477ns에서 후보의 18.344 / 18.194 / 27.148ns로 변했다. 추가로 보이는 release 레지스터 자체에서 출발한 지연은 16.648 / 16.431 / 최대 23.668ns였다. 이 값은 외부 보드의 허용 시간이나 RESET 입력부터 핀의 고임피던스까지의 실측값이 아니다. 별도 조회 결과를 원래 STA 예외로 적용하지 않았다.

다음은 이 열 핀에서 **활성 읽기의 소유권과 데이터 버스 해제 선택**을 확인하는 일이다. aperture와 제어 레지스터의 해제 경로를 같은 배치에서 대조하고, 추가 미제약 경로와 recovery TNS를 줄인 뒤 WNS·PSRAM·두 위상 표시가 유지되는지 검사한다. 실기판과 5–55초 FPS 기준은 MMC558에 둔다.

## 재현

`prepare_nes_gate570.py`에 MMC558 보드를 지정한다. `--memory-only`는 메모리 대조군, 기본값은 슬롯 차단 후보, `--mask-ingress`는 SPI 차단 후보, `--shared-bulk`는 뱅크 공유 후보, `--local-release`는 두 하위 회로의 중복 reset 입력을 없앤 후보다. 각 후보에서 Quartus Lite 전체 compile과 기존 `timing506.tcl`, arg564·pins565·owner562 경로 보고서를 실행한다. `report_nes_gate570.tcl`로 569와 다섯 후보의 실제 레지스터와 setup/recovery 끝점을 대조한다. MMC558·569·로컬 해제 보드의 별도 핀 지연 조회에는 `report_nes_snes570.tcl`을 사용한다. `check_nes_gate570.py`와 `observe_nes_gate570.py`는 기존 Starter FLOAT 한 좌석에서 순서대로 실행한다. 562의 두 도착 일정으로 `replay_nes_close561.py --all-banks`를 실행하고 `analyze_nes_gate570.py`로 판정을 묶는다.
