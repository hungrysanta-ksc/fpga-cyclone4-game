# 951의 OAM·HDMA 묶음 수락과 마지막 VBlank

**621을 유지한다.** 기존 map literal 경로에서 OAM 세 명령을 하나로, HDMA 앞부분 두 명령을 하나로 묶었다. 후반 head가 24→21개가 되고 951의 E1 전송량은 59B 줄었다. 같은 바이너리의 즉시 공급 대조군에서 SEAL 수락은 1.297 / 1.301ms 빨라졌다. 두 위상 모두 951은 여전히 4 VBlank였다. [측정값·원자료 해시](../analysis/tail631-verification.json)

## 같은 작업량의 수신 비용

905–950의 패킷과 951의 마지막 OBJ까지 원래 625 시간을 고정했다. 기본 즉시 공급 시험은 OBJ 뒤 모든 명령이 준비됐다고 가정하되 네 칸의 큐와 실제 head 소비·ACK를 지킨다. 기준과 후보 모두 같은 631 수신기에서 실행해 디스패치 변경 비용을 분리했다. 표의 시각은 세 번째 VBlank의 246번 선 끝을 기준으로 하며 음수는 마감 전이다.

| OBJ 뒤 즉시 공급 | 후반 head 수 | OAM 전체 소비 (ms) | HDMA 1,121B 소비 (ms) | SEAL 수락 (ms) | upload 함수 진입 (ms) |
|---|---:|---:|---:|---:|---:|
| 원래 패킷 | 24 | 2.175 / 2.173 | 1.774 / 1.770 | +1.289 / +1.527 | +2.921 / +3.157 |
| OAM만 묶음 | 22 | 1.228 / 1.229 | 1.788 / 1.775 | +0.289 / +0.513 | +1.905 / +2.136 |
| HDMA만 묶음 | 23 | 2.175 / 2.173 | 1.507 / 1.508 | +0.966 / +1.227 | +2.602 / +2.859 |
| 둘 다 묶음 | 21 | 1.228 / 1.229 | 1.513 / 1.518 | −0.008 / +0.226 | +1.598 / +1.839 |

* OAM은 112B literal, 4B 패턴으로 복원하는 400B, 32B 고정값으로 총 544B를 쓴다. 65816이 후보 뱅크에 4B 패턴을 직접 쓰며 64B 이내마다 STOP을 확인한다. OAM 묶음의 절감은 SPI 39B다.
* HDMA는 21B literal과 1,100B 고정값을 하나의 연속 범위로 검사하고 복원한다. 고정 source DMA는 최대 64B씩 실시한다. 1,121 이후의 raw HDMA와 독립 receipt·최종 검사는 기존 경로로 진행한다. SPI 20B가 줄었다.
* 두 형식 모두 실제 길이·섹션·시작·확장 크기가 일치해야 하고, 기존 frame identity·순번·범위 검사 뒤에만 쓴다. 한 명령의 마지막 STOP 확인과 실제 쓰기 완료 뒤에만 credit을 반환한다. 951 이외의 일반화된 발행기는 이번 시험 범위 밖이다. 65816 본체는 5,323→5,777B, 전용 임시는 WRAM 4B다. 같은 바이너리를 재생성해 이미지 해시를 대조했다.
* 원래 **625 PUSH 시각**을 썼을 때는 묶음의 마지막 구성 패킷까지 기다린 뒤 새 head를 제공했다. 결합 후보의 SEAL 수락은 +6.497 / +7.291ms, 첫 SEAL DMA는 +15.288 / +15.283ms였다. 951 ACK 차이는 625 대비 +0.006 / −0.517ms다. 공급을 실제로 앞당기기 전에는 즉시 공급 결과를 연속 일정의 이득으로 사용할 수 없다.

## BG 확정 후 빈 SPI 시간의 한계

2.871ms 동안 원래 SPI 거래가 없음을 두 위상에서 확인했다. map 한 패킷을 앞당길 때마다 반환 상태 E0 20B, tile 우선 확인 E8 20B, map E1 211B의 실제 거래 시간을 반영했다. 세 패킷이면 2.733ms가 들어 ARM의 추가 작업에는 약 0.138ms만 남는다. 이는 ARM이 planner와 SPI를 병렬 수행했다는 측정이 아니다. 이전 628 ARM의 동기 전송에서는 한 패킷만 먼저 발행했다. 나머지 명령은 마지막 OBJ 뒤 즉시 제공한 상한 시험이다. [628의 실제 ARM 비교](nes-map628-results.ko.md)

| 결합 후보의 선행 map | SEAL 수락 (ms) | upload 함수 진입 (ms) | SEAL 뒤 첫 DMA (ms) | 목표 VBlank에서 착수한 SEAL DMA 바이트 | 950→951 |
|---|---:|---:|---:|---:|---:|
| 0개 | −0.008 / +0.226 | +1.598 / +1.839 | +15.293 / +15.304 | 0 / 0B | 4 / 4 |
| 2개 | −1.118 / −0.909 | +0.461 / +0.670 | +15.288 / +15.299 | 0 / 0B | 4 / 4 |
| 3개 | −1.748 / −1.577 | −0.157 / +0.007 | +0.171 / +0.335 | 400 / 384B | 4 / 4 |

세 패킷을 앞당긴 재생에서 선행 조회 시점의 큐 점유는 0→1→1이었다. 951의 첫 SEAL DMA는 목표 VBlank의 249 / 252번 선에서 시작했다. 위상 1은 384B와 16B, 위상 2는 384B를 전송했고 남은 DMA는 다음 VBlank까지 기다렸다. 951 최종 ACK는 기준보다 0.300 / 0.243ms 빨랐다. 이 수치는 957이나 실기의 마지막 ACK가 아니다.

## 보호 시험과 다음 작업

각 후보·위상에서 905–951의 47개 RGB와 독립 map 검사를 통과했다. 묶음 소비 ACK에서는 실제 비활성 WRAM 544B·1,121B 전체를 와이어 입력에서 독립 복원한 값과 대조했다. 잘못된 OAM 길이·주소·확장량, scroll 길이·확장량, 이전 serial과 잘못된 cold head를 거부했다. OAM과 scroll에서 각각 부분 쓰기 뒤 STOP을 넣어 이전 950 화면과 취소 ACK를 확인했다. scroll 중단 당시의 map WRAM·VRAM 16KiB와 양쪽 뱅크의 OAM·HDMA WRAM 3,778B를 재주입해 cold 905·906의 OAM·map·HDMA·RGB와 최종 ACK를 확인했다.

다음은 625의 실제 발행 일정을 기준으로 **SEAL 수락 후 수행하는 HDMA 형식 검사와 tile·map coverage 확인 중, 해당 입력의 마지막 소비 ACK 때부터 확정되는 부분**을 분리하는 일이다. 두 검사의 총시간과 그 사이에 겹칠 수 있는 시간부터 계산한다. 마지막 identity·미수신·중복·STOP·최종 표시 검사는 유지한다. 951에서 실제 DMA가 246번 선 전에 얼마나 끝나는지와 두 위상 모두 목표 VBlank에 표시되는지를 먼저 본다. 고정 도착 시험에서 그 조건을 충족해야 ARM·IRQ·ROM 연속 일정, 957 최종 대기 0회, 전체 Flash·Quartus Lite와 실기 전달 단계로 넘어간다. 이번에는 새 FPGA·ARM 배포본을 만들지 않았다.

## 재현

* 625 위상별 trace, 624 base-client와 같은 Mesen을 사용한다. `tools/nes_tail631.py`로 진단 client를 생성한다. op9는 이 이미지 전용이다.
* `tools/replay_nes_tail631.py --which neither|oam|scroll|both --ready`를 두 위상에서 실행한다. 기본 625 제공 일정은 neither·both에서 `--ready`를 생략한다. 선행 공급은 `--which both --ready --early 2|3`이다. 공통 인자는 `--trace --base-client --client --mesen --out`이다. 출력 폴더는 `nes-tail631-{mode}-{ready|paced}-{phase}a`, 선행 시험은 마지막 a 대신 early2 / early3이다.
* `tools/check_nes_tail631.py`로 위상 1의 손상·STOP·재시작을 `nes-tail631-guards02`에 저장한다. `tools/analyze_nes_tail631.py --traces $env:TEMP --out analysis/tail631-verification.json`이 원래 PUSH와 실제 head·ACK 클록, DMA, RGB, 보호 시험을 검증한다. 유휴 DMA가 다음 index로 먼저 기록될 수 있어 패킷 종류는 실제 load 이벤트와 와이어 양쪽에서 대조한다.
