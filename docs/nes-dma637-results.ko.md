# 637 — 952의 선행 DMA와 다음 화면의 입력 수신

비교 기준은 636의 수정 ARM과 5 KiB 보드 ROM이다. 905~957을 연속 실행해 ARM 발행·SPI·IRQ·ROM 중재·두 슬롯, 65816의 수락·DMA·표시와 마지막 ACK를 같은 시작 시각끼리 비교했다. 시뮬레이션은 실제 ARM 바이너리와 65816 프로그램을 사용한다. ARM 시간은 CPI 2, SPI와 ROM은 636의 측정 기반 비용과 중재 일정을 사용한다. 실기 기준은 MMC613이다. [636 기준](nes-export636-results.ko.md)

**952의 5→4 VBlank는 네 조건 모두 재현했다. 951은 3 VBlank·246번 선, 957은 최종 추가 대기 0회였다. 953이 3→4 VBlank로 늘어 밀집 다섯 간격의 합은 19회였다.** 두 블록 후보 F와 한 블록 후보 G는 957에서 네 조건별 최종 ACK 시각까지 서로 일치했다. 전체 일정 개선을 채택 조건으로 삼아 개발 기준 636과 실기 기준 MMC613을 유지한다.

| 조건 | 951 공개선, 636 → F | 952 간격 (VBlank) | F의 SEAL 전 map / tile (B) | 밀집 평균, 636 → F (ms) | 957 ACK 차이 (ms) |
|---|---:|---:|---:|---:|---:|
| 부팅 중 1 | 246 → 246 | 5 → 4 | 1152 / 64 | 63.215 → 63.143 | +16.553 |
| 부팅 중 2 | 249 → 246 | 5 → 4 | 1344 / 96 | 63.168 → 63.217 | -16.868 |
| 부팅 후 1 | 246 → 246 | 5 → 4 | 1344 / 96 | 63.171 → 63.163 | -0.141 |
| 부팅 후 2 | 246 → 246 | 5 → 4 | 1344 / 96 | 63.232 → 63.160 | +16.558 |

ACK 차이가 음수면 F가 빠르다. 표의 DMA는 952에서 실제로 먼저 전송한 합계다. F는 원래 남아 있던 map·tile의 일부를 앞당겨 한 VBlank를 회수했다. SEAL 뒤 잔량은 map 576~768 B·tile 480~512 B였다. 905~951의 47개 실제 ACK 시각은 같은 ARM 루프의 1·2·3블록 후보끼리 일치했다. 전체 비교는 7후보 × 4조건 × 53화면이다.

## 얼마를 미리 옮길 수 있었나

952의 작업량은 map 1,920 B·tile 576 B다. 636에서는 두 부팅 조건과 두 시작 위상 중 세 경우에 map 192 B·tile 16 B를 SEAL 전에 전송해 1,728 B·560 B가 남았다. 부팅 중 시작 위상 2에서는 이미 map 384 B를 전송해 1,536 B·560 B가 남았다. 후보마다 같은 바이트·목적지와 53개 화면의 RGB, map, CGRAM, OAM을 대조했다.

ARM은 이전 bank가 표시됐고 대상 map의 오른쪽 19행 이상이 연속이며 OBJ 512 B 이상을 발행한 경우에만 시험 정책을 사용했다. 65816이 이미 수락한 inactive-bank descriptor만 DMA하며, 매 grant 직전에 STOP·새 패킷과 실제 빔 위치를 확인한다.

| 후보 | 변경 | ARM Flash (한도 212,992 B) |
|---|---|---:|
| A | 스크롤 수락 확인 뒤 30회 상태를 확인하며 후속 HDMA 발행을 늦춤 | 212,948 B |
| B | 기존 map credit 반환 직후 같은 방식으로 40회 상태 확인 | 212,892 B |
| C | B에 65816의 선두 map 우선 처리를 결합. 뒤에 있던 tile이 목록 앞쪽으로 나옴 | 212,892 B |
| D | C의 대기 구간을 최대 3회의 다음 입력 조회·수신으로 교체 | 212,964 B |
| E | C의 대기 중 처음 37회는 상태 확인, 마지막 3회는 실제 입력 조회·수신 | 212,960 B |
| F / G | E와 같은 40회 중 마지막 2회 / 1회만 수신 | 각각 212,960 B |

D~G는 SEAL 전에 받은 블록을 636의 일곱 번 예산에 포함한다. 이전 최종 ACK·EA 뒤에만 다음 D3를 보낸다. 수신 오류가 발생하면 해당 세대의 새 SEAL·이력 공개를 중단한다. 여섯 ARM 링크의 BSS는 모두 19,544 B다. C~G는 635 본체에서 map을 선택하는 분기의 목적지만 1바이트 바꿨다. 압축한 65816은 기존 5,120 B 보드 ROM에 들어가며 예약 영역 밖에 32 B가 남았다. 새 ROM의 실제 부트에서 5,760 B 전체 일치와 손상 시 실행 차단을 확인했다. WRAM 진입은 636과 같은 6,274,666 master clocks다. 같은 ROM을 636과 같은 Cyclone IV 입력·제약으로 Quartus Lite에서 전체 FIT·STA했다. 15,351/15,408 LE, 8,474 FF, M9K 56/56, 전체 setup +0.565 ns·hold +0.153 ns·recovery +1.682 ns·removal +0.481 ns, ROM_OE setup +0.895 ns로 636과 같았다.

## 발행을 미루면 다음 화면에서 무슨 일이 생겼나

A·B는 네 조건 모두 952의 SEAL 전 map을 1,152 B까지 올려 표시를 5→4 VBlank로 당겼다. tile은 16 B만 전송됐다. C는 세 조건에서 tile도 64~96 B까지 전송했다. 줄어든 표시 대기만큼 다음 화면을 항상 빨리 준비할 수 있는 것은 아니었다. 부팅 후 위상 1에서 B는 953의 이전 표시 ACK 전 입력 반환이 7→4블록, 953 표시 간격이 3→4 VBlank가 됐다. A의 같은 위상에서는 953이 세 번을 지켰지만 954가 4→5회가 됐다.

D에서 952의 마지막 map·tile 수락과 953 캡처 완료 사이에는 3.81~4.50 ms가 남아 있었다. 즉시 실행한 세 번의 조회는 네 조건 모두 빈 상태였고, SEAL 전 반환은 0블록이었다. 이후 수신 예산도 네 번만 남아 밀집 구간은 636의 19회에서 20회로 늘었다. 이 때문에 E에서는 같은 세 번의 수신을 캡처 대기 구간 끝에서 실행했다.

E는 네 조건 모두 953의 세 블록을 SEAL 전에, 일곱 블록을 952 최종 ACK 전에 반환했다. 953은 3 VBlank로 되돌아왔지만 952는 5회였다. 같은 65816을 쓴 C에서는 952 SEAL 수락이 123~136번 선, 검사 후 업로드 진입이 148~162번 선이었다. E에서는 수락이 199~207번 선, 업로드 진입이 다음 VBlank의 225~233번 선으로 밀렸다. 이 경계에서 선행 수신을 2회·1회로 줄인 F·G를 각각 전체 링크했다. 세 후보의 실행 섹션 차이는 F 1바이트, G 2바이트로 해당 ARM 루프에 한정된다.

F·G는 모두 952를 4회로 회복하지만, SEAL 전 1·2블록과 관계없이 952 최종 ACK 전까지 반환한 953 입력은 총 4블록이었다. 636의 분포 [3, 5, 3, 4, 4]가 [3, 4, 4, 4, 4]가 됐다. 952 표시를 기준으로 F의 953 첫 BG ROM 요청은 636보다 3.32~3.90 ms, 실제 중재 응답은 15.34~15.71 ms 늦었다. 반면 마지막 OBJ ROM 응답은 0.54~1.00 ms 빨랐다. 다음은 953의 D1 복원 완료·D3·첫 BG plan이 직전 ROM 허용 구간을 놓치는 지점과, 마지막 OBJ 뒤 SEAL이 늦어지는 발행·수락 시간을 나눠 검증한다. 952의 대기 횟수만 바꾸는 반복 시험은 종료한다.

## 안전성 확인

전체 실행은 각 양의 최종 ACK 때 VRAM·표시 결과를 대조하고, 선행 DMA 시점에 원본 바이트의 수락 여부·목적지·전송 길이를 검사한다. 여섯 ARM ELF에서 정상·base 실패·menu 실패·오류 latch·checkpoint 실패에 따른 메뉴 복귀 경로도 확인했다. ARM 단위 시험은 작업량 경계, credit 실패, 대기 중 서비스 중단, 최종 ACK 거절에서 이력 보존과 후속 발행을 검사한다. D~G의 실제 수신 함수에서는 세 블록을 SEAL 전에 받더라도 이후 합계가 일곱 블록 이내인지와 IO·CRC·deadline·중단 뒤 D3 차단을 검사했다.

기존 65816의 STOP·새 head·손상 검사는 9건을 재실행했다. 선두 map 우선 수신기는 252번 선에서 1,152 B를 전송한 뒤 STOP, 새 head와 STOP의 우선 처리, 253번 선 거절, 두 bank의 누락·중복 검출을 별도로 확인했다. 기존 시험기가 항상 목록 끝 map을 기대해 새 수신기에서 실패했고, 수정한 시험기는 실제 선두 주소·VRAM·길이와 두 목록 포인터를 비교한다. 선두 우선판에서 252번 선의 수평 clock 1,000 이후 latch를 요구한 추가 시험은 해당 위상에 도달하지 못했다. 이 끝점은 미검증이다.

## 재현 방법

1. 636의 `arm02`, `client02`, 두 부팅 조건의 `nes-export636-run{1,2}{d,h}` 추적을 준비한다. A~G의 COMMIT 반환·시작 조건은 같은 이름의 636 대조군과 같다. 시작 master clock은 부팅 중 3,000,000 / 3,178,684, 부팅 뒤 7,288,416 / 7,467,100이다.
2. `tools/prepare_nes_dma637.py <636 arm02> <out>`으로 여섯 ARM 프로젝트를 생성한다. 출력 폴더 `arm01/02/03/04`의 옵션은 각각 기본, `--after-map`, `--receive`, `--late-receive`다. `arm05/06`은 `--late-receive --late-blocks 2/1`이다. 각각 `tools/build_nes_trial577.ps1`로 링크한다. `tools/nes_head637.py <635 client04> <637 client01>`로 선두 map 수신기를 만든다.
3. [636의 연속 일정 실행 명령](nes-export636-results.ko.md)에서 ARM과 client를 위 표대로 연결하고 A~G를 각각 `nes-dma637-run`, `-map`, `-head`, `-rx`, `-late`, `-two`, `-one` 접두어와 `1d/2d/1h/2h` 접미어로 저장한다. `h`는 `--commit-pop-bound`로 COMMIT의 D2 반환까지 포함한다.
4. ARM마다 `check_nes_dma637.py`, `check_nes_reuse635_arm.py`, `check_nes_overlap634_arm.py --in-place`를 실행한다. D~G 수신 검사에는 `--before-seal`을 추가한다. 기존 client는 `test_nes_map616_edges.py`, 새 client는 `check_nes_head637.py`로 경계를 검사한다. `tools/analyze_nes_dma637.py --traces <raw> --build <637> --out analysis/dma637-verification.json`이 수락 바이트·DMA·위상·ACK를 대조한다.
