# NES165 첫 실기 결과 — 사운드·메뉴 복귀 통과, 영상 미출력

사용자 관찰: 게임 실행 뒤 화면은 나오지 않았고 소리만 났다. 약60초 후 메뉴로 정상 복귀했다. 이번 결과는 **영상 실패**이며 전체 게임 구동 통과로 처리하지 않는다.

|항목|결과|
|---|---|
|ROM 적재·검증|393216바이트 모두 비교, verify_error=0|
|코어 ROM 오류|run_rom_error=0, 실행 관측 카운터 증가|
|사운드|사용자 청취 확인, SPC A9/unmute=1|
|새 경로 표시 완료|native_frames=0, screen_frames=0|
|종료 원인|native_result=1: 시간 만료|
|종료·메뉴 복귀|stop_ok=1, run_stop_error=0, base_restored=1, 사용자 확인|

진행 로그는0~99번이 연속이며 DISPLAY_NEXT=232650ms, DISPLAY_STOPPED=292670ms다. 두 시점 차이는 **60020ms**이고 MENU_PREPARED는295790ms다. 펌웨어 tick 기준으로 적재·검증 등에 약3분52.65초, 실행/표시 구간에 약60.02초가 걸렸다. 별도 벽시계 실측값으로 오인하지 않는다.

## 오류 번호 해석

`run_first_error=5`는 새 어댑터의 표시 완료 프레임0 조건이다. `native_receiver_error=21`은 STATUS의 ID/CRC 실패뿐 아니라 transport callback의 false에도 설정된다. callback은 거래 전후의 시간 guard가 만료돼도 false를 반환한다. runtime은 첫 종료 원인을 보존하므로, 이번 `native_result=1`과 오류21의 조합을 근거로 **SPI가 고장나서 60초 동안 실패했다고 단정하면 안 된다.**

마지막 `run_flags=1`은 STOP 후 다시 읽은 held 상태다. RUN 내내 코어가 정지했다는 뜻이 아니다. 버튼 변화 표본도 남았지만 화면 없이 조작 품질·입력 유지를 검증했다고 볼 수는 없다.

## 원인 범위와 다음 가설

소스상 COMMITTED 영상은 즉시 변환·SNES 전송으로 넘어간다. 변환/표시 실패는 그 자리에서 종료하며, 이번 종료는 수신 poll에서 발생했다. 표시 완료 수0과 함께 보면 **정상 게임 실행 중 새 영상 데이터가 완성·승인되는 앞단**을 먼저 조사해야 한다. 기존의 소리 출력과 메뉴 복귀는 이 판단을 뒷받침한다. TV의 색상·타일 설정만 바꾸거나 같은 시험을 더 오래 기다리는 것은 우선순위가 아니다.

331746회 거래와4188112 wire bytes는 전송 활동이 있었다는 증거다. 성공한 프레임 수나 순수 픽셀 데이터량은 아니다. 현재 로그에는 BEGIN/END/ABORT/COMMIT 횟수와 FPGA의 취소 이유가 없고, 수신기는 ABORT를 만나면 이유를 보존하지 않은 채 IDLE로 돌아간다. 따라서 반복 취소의 직접 증거는 아직 부족하다.

우선 검토할 구체적인 가설은 **정상적인 그래픽 읽기·전송 대기를 시간 초과로 취급해 프레임을 계속 취소하는 경우**다. 선택 FPGA의 fill은 WAIT_CYCLES=131072로, 소스의 NTSC master clock 기준 약6.1ms다. 이 카운터는 REQUEST에서 메모리 사용권을 기다릴 때와 STREAM에서 MCU 소비를 기다릴 때도 증가한다. 사용권은 scanline242..259의 제한된 수직 공백 구간에만 허용하므로, 다음 허용 구간까지의 정상 대기가 상한보다 길 수 있다. export4194304/fill2097152의 전체 상한에도 host backpressure 시간이 포함된다. 어느 조건이 이번 실패를 일으켰는지는 **미확정**이다.

다음 작업은 기존 fill/export 경계에서 긴 합법적 대기와 MCU 소비 지연을 재현하고, BEGIN/END/ABORT/COMMIT 횟수·첫 취소 이유·마지막 수신 단계를 최소한으로 남기는 것이다. 근거 없이 상한만 늘리거나 CPU/PPU 우선순위를 해제하지 않는다. 사용자에게 같은165 재실행이나044 복원 시험을 요청하지 않는다. 다음 시험도 SMB3 실제 ROM을 사용한다.

[원본 로그 해시·파싱 결과](../analysis/game165-hardware01-verification.json). 원본 TXT는 private 증거 폴더에 그대로 보관했다. 설치 파일을 PC에서 다시 읽은 것은 아니므로 패키지 SHA가 실기 파일 readback으로 확인됐다고 주장하지 않는다. 이번에는 펌웨어·FPGA·시험 ZIP을 변경하지 않았다.
