# sd2snesHST 두 저장소 운영 계획

## 이름과 역할

제품 이름은 **sd2snesHST**, HST는 사용자가 20년 넘게 사용해 온 프리랜서 프로그래머 팀명 **HungrySanTa**의 약자입니다.

| 항목 | 개발 저장소 | 사용자 배포 저장소 |
| --- | --- | --- |
| 저장소 | hungrysanta-ksc/fpga-cyclone4-game | hungrysanta-ksc/sd2snesHST — 생성 완료, 0.9.0 초안 |
| 독자 | 개발자·코어 기여자 | 설치·업데이트하는 사용자 |
| 내용 | 구현, 빌드, 테스트, 설계, 출처, 실패/실험 기록 | README, 설치·사용법, 호환성, 변경 기록, Releases, 문제 보고 |
| 구현 수정 | 이곳에서만 수행 | 확정 소스 스냅샷을 릴리스에 첨부 |
| 문제 접수 | 재현 조사·수정 PR·upstream 추적 | 사용자 증상과 설치 문의 |
| 완료 기록 | 코어 후보·커밋·검증 증거 | 제품 버전·지원 범위·설치 자산 |

사용자 이슈를 개발 이슈로 연결할 때 관련 링크를 양방향으로 남기고, 사용자에게는 해당 제품 버전의 해결 여부를 안내합니다. 같은 코드를 양쪽에서 따로 고치지 않습니다.

## 제품 버전과 개발 후보

첫 공개 매핑은 **sd2snesHST 0.9.0 → GBC C44**입니다.

- 제품 릴리스 태그: `v0.9.0`.
- 제품 PATCH 예: 0.9.1 — 수정·호환성·문서/패키지 보완. 한번 공개한 0.9.0 파일을 몰래 교체하지 않습니다.
- 제품 MINOR 예: 0.10.0 — 새 코어나 주요 기능을 검증해 추가할 때. 숫자 증가가 특정 코어의 구현을 보장하지 않습니다.
- 1.0.0 — 지원 범위, 설치/업데이트/복구, 저장 형식, 문서와 배포 절차의 안정화 기준을 정한 후 별도로 판단합니다.
- 개발 후보: 기존 `gbc/C44`를 보존하고 새 코어는 `nes/N01`, `pce/P01`처럼 코어별 식별자를 사용합니다. 이 이름은 제안 규칙이며 아직 새 후보를 빌드한 것은 아닙니다.
- `0.x` 중에도 SRAM·RTC·강제 저장 형식의 변경 여부를 릴리스마다 명시합니다. 형식이 바뀌면 백업·이전 방법을 먼저 제공합니다.

제품 버전은 배포 묶음의 버전입니다. sd2snes 원본 기반 버전, GBC 후보 번호, FPGA 이미지 버전과 동일한 숫자로 맞추지 않습니다.

## 배포 추적성

릴리스 manifest는 다음을 연결합니다.

1. 제품 이름·버전과 사용자 저장소 태그.
2. 개발 저장소의 정확한 소스 커밋 및 소스 ZIP 해시.
3. 포함 코어·후보, 대상 보드·펌웨어 기반.
4. 설치 파일별 SHA256과 전체 업데이트 ZIP 해시.
5. 배터리 저장·RTC·강제 저장 형식 및 이전 버전 호환성.
6. 같은 후보의 빌드·검증 결과, 라이선스·출처 고지.

0.9.0의 검증된 구현 커밋은 `35ef4aef14fc6abef6495a980b7f00f257e5174f`입니다. 이후 문서 정리 커밋과 이 실행 기준선을 구분합니다. 첫 릴리스의 소스는 이 구현 커밋의 재현 가능한 전체 묶음을 첨부하고, 현재 계획 문서는 사용자 저장소 문서 커밋으로 관리할 수 있습니다.

고정 upstream 커밋·overlay·생성기·빌드 지침을 포함한 소스 자산을 함께 보관합니다. 이동 가능한 브랜치 링크만으로 소스 제공을 대신하지 않습니다. 파일별 라이선스 조건과 필요한 대응 소스 범위는 발행 전에 검토합니다.

## 배포 저장소 구조 제안

```text
sd2snesHST/
  README.md
  CHANGELOG.md
  docs/
    USER-GUIDE.ko.md
    COMPATIBILITY.ko.md
  manifests/
    0.9.0.json
  .github/ISSUE_TEMPLATE/
    bug-report.yml
    installation.yml
```

큰 실행 파일은 Git 이력에 반복 추가하지 않고 GitHub Releases에 둡니다. 각 릴리스에는 업데이트 ZIP, 대응 소스 ZIP, SHA256SUMS, manifest, 필요한 고지를 제공합니다. 처음부터 프로젝트 전체를 임의의 단일 라이선스로 덮지 않습니다.

## 개발 저장소 운영

코어별 `cores/<id>/`는 구현 위치·상태·검증·다음 작업을 안내합니다. 공통 코드와 코어 전용 코드는 경계를 문서화하고, 두 번째 사용처가 검증되기 전에는 추측으로 추상화하지 않습니다. 기존 소스 파일 이동은 빌드·해시 기준선을 바꾸므로 별도 리팩터링으로 수행합니다.

배포판과 실험판은 구분합니다. 실험판은 최종 Release의 latest로 올리지 않으며, 사용자 테스트용 후보 ID·복구 방법을 함께 제공합니다.
