# NES181 선택 회로 자원 검토

출발점은 board181/map03이다. 실제 보드와 MCU 연결은 완료됐지만 FPGA는965 LAB가 필요해963 LAB 한도를 초과했다. 이번 작업은 오류 검사나 수용 가능한 장면을 줄이지 않고 조합 선택 회로를 변경한다. 보드의68개 입력 해시를 검사해 새 디렉터리에 복사하고 변경 대상만 변환한다. 기존 공개 수집기·완료 archive·180 설치본은 수정하지 않는다.

## 오브젝트 키 비교 후보

기존 compact는8개 슬롯 중38비트 키를 선택한 뒤 현재 오브젝트와 비교한다. `tools/nes_rank181.py`는 각 슬롯에서 키를 비교한 다음8개의1비트 결과 중 하나를 선택한다. rank_valid 검사, 메모리 쓰기, 입력 수용 클록, 오류 우선순위는 유지한다.

`rank181/test01`은 기준 map03과 모든 출력 포트를109,533클록 비교했다.8장면, 같은 키4,824회·새 키14,796회, 유효 RAM 조회384회가 포함된다. 뒤쪽100,000클록은 결정적 제어/잘못된 이벤트 입력이다. 전체 입력에 대한 형식 증명은 아니다. `collect01`은 원본181 compact와3,287,929클록 일치하고14경우·raw3,328픽셀·정상180 대비9,624단어·복구43,923셀을 통과했다. `join01`은 실제 보드 인스턴스/중재 코드로512픽셀·CHR960바이트·fill8,192조회·대기5,753클록·1 COMMIT/해제를 통과했다.

그러나 실제 배치 준비에서15,038 LE·38 M9K·**967 LAB**가 필요했다. 기존14,972 LE·965 LAB보다 나쁘므로 **채택하지 않는다**. 기능 동등성과 자원 효율은 별개다. 비교기 분산만으로 넓은 선택 회로보다 저렴하다고 가정하지 않는다.

## 팔레트 색 선택 후보

`tools/nes_palette181.py`는 다시 board181/map03에서 시작한다. 위 오브젝트 키 변경을 포함하지 않는다. 기존 `held_palette[copy_offset*6+:6]` 대신 고정 배선으로32색×6비트를6개의32비트 레인으로 옮겨 해석하고 각 레인에서5비트 색 인덱스로1비트를 선택한다. 저장 비트와 순서는 동일하며 배선만 전치된다. 곱셈을 포함하는 가변 시작 위치 선택을6개의 고정32:1 선택으로 표현한다.

복사32클록, palette RAM 주소/값, held/line palette 비교, 첫 팔레트·두 번째 팔레트·초과 오류, backdrop 검사, 행 종료·source_fault·해제 우선순위는 바꾸지 않는다. 새 레지스터나 RAM 읽기 지연은 없다. `tools/test_nes_palette181.py`는 준비된 실제 수집기에서 원본 raster의 모든 출력과 복사 중 색 값을 클록마다 비교한다. 실제 보드 결합도 별도로 확인한다. PPU 입력·메모리·호스트는 모델이며 전체 게임 또는 물리 보드 통과는 아니다.

선택 후보의 raster 조합 함수는587→503으로 감소했다. 원본과3,287,929클록·384회 복사값 비교,14경우 수집기 및 실제 보드 부분 결합 검사가 통과했다. 별도 `palette181_tb.sv`는192비트를 각각 켠 패턴과 전체0/1, 두 팔레트 뱅크 및 세 번째 팔레트 거부를 실제 순차 복사 경로로 검사했다.194패턴·18,624개 저장값 확인이 통과했다. 이 시험은 조합 선택의 임의192비트 입력 전체에 대한 형식 증명은 아니다.

## 유지할 범위

MCU와 SNES 소스/이미지는 바뀌지 않는다. board181의 전체 ARM199,604바이트·RUN/IRQ 여유1,032바이트 검사와 client181의4KB 이미지 근거를 해시로 재사용한다. 같은 전체 ARM 빌드를 반복하지 않는다. 세이브 SRAM·GBC·164 복구판·180 배포본을 보존한다.

전체 FIT, 실제 클록 setup/hold, 조건부 IO/리셋 검증이 통과하기 전에는 새로운 설치 패키지를 만들지 않는다. raw 전송 약53ms 모델과 최대7vblank+final 표시 단계는 이번 선택 회로 변경으로 해결되지 않는다. 정지 해소 후에도 실제 SMB3의 생산·전송·표시완료 간격을 측정해야 하며60fps·장기 플레이·입력 유지 품질은 아직 미완료다.

## 최종 FIT 판정

**팔레트 후보는 초기 placement에 성공했지만, routing과 도구 내부 자동 재시도 후 최종 FIT가 실패했다.** 진행 중의 placement 성공을 전체 배치·배선 성공으로 해석하면 안 된다. 최종 실패 보고의 값은14,961 LE·965/963 LAB·38 M9K다. 이는 실패한 구현의 부분 수치이며 정상 배선 구현의 자원 수치가 아니다. STA·조건부 IO·ASM·새 ZIP은 실행/승인하지 않았다. 오브젝트 키 후보와 팔레트 후보를 합치지도 않았다.

| 근거 | 실제 결과 |
| --- | --- |
| 팔레트 합성 조합 함수 |587→503; 전체 합성 추정 LE19,649→19,562 |
| 최초 placement | 성공 |
| 최종 routing/FIT | 실패; 필요965 LAB / 한도963 |
| 배선하지 못한 신호 |79개, 이 중 OAM67개 |
| 둘 이상의 신호가 요구한 배선 자원 |75개 |
| hold 보정을 위해 추가된 지연 합 |605.4ns; 여러 신호의 합계이며 slack이 아님 |

hold 지연 합은 PLL clk1→nes398.9ns, PLL clk0→nes151.3ns, 복수 출발 클록 그룹→nes37.8ns, 복수 도착 그룹17.4ns다. 상세 목록에는 native_prepared의 held→received, 첫 동기화 FF, ROM 응답, pad/audio 및 reset 교차가 있다. Fitter는 hold 보정을 위한 배선 요구가 과도하며 수렴을 위해 일부 지연을 줄인다고 보고했다. **이 결과는 혼잡과 CDC 제약을 함께 점검할 근거이지, 특정 회로 하나가 유일한 원인이라는 증명은 아니다.**

## 다음 작업: 클록 관계와 CDC 계약부터 확인

실제 소스는 CLKIN을 PLL에 넣고 SNES_SYSCLK를 NES 클록으로 사용한다. 현재 SDC는 두 root clock과 PLL 파생 클록을 선언하며 비동기 관계·최소 지연 예외는 없다. Standard Edition Timing Analyzer는 별도 선언이 없으면 클록들을 관련된 것으로 취급하며, 위상이 정해지지 않은 전송이라도 데이터 지연 상·하한이 필요하면 두 한도를 함께 명시하도록 설명한다. 이는 제약 검토 근거이며 현재 설계의 안전성을 대신 증명하지 않는다. [Intel Standard Edition Timing Analyzer, 2.3.7.2–3](https://www.intel.com/programmable/technical-pdfs/683068.pdf)

1. 두 외부 root 및 같은 PLL의 두 출력 관계를 구분하고 모든 교차 신호를 목록화한다. native_records/prepared뿐 아니라 ROM request/reply, pad, audio, clock guard, reset을 포함한다.
2. 첫 동기화 FF와 다비트 held payload를 구분한다. 실제 request/ACK, 데이터 유지 기간, 지연된 수신 capture, backpressure, STOP/cancel, common reset/클록 정지 계약으로 안전성을 확인한다. 기존165 경계 시험과 소스 핀이 맞으면 재사용한다.
3. 설치된 **Standard25.1**에서 지원되는 명령과 예외 우선순위를 확인한다. 필요 경로에만 검증된 최소/최대 데이터 지연을 지정하고 적용 대상 수·누락·동기화 체인 내부 타이밍을 검사한다. Pro Edition 문법을 그대로 옮기지 않는다. 클록 전체를 통째로 제외하거나 hold 최적화를 끄는 것으로 통과시키지 않는다.
4. 필요하면 OAM에 집중된 저장/조회 배선을 구조적으로 줄인다. OAM67/79는 혼잡 위치의 단서이며 기능 결함을 뜻하지 않는다. 이전165 OAM 구조와 시험 결과를 먼저 확인해 이미 폐기한 후보를 반복하지 않는다.
5. 변경된 경계의 최소 기능 검사 후 정당화된 전체 FIT를 한 번 실행한다. 실제 클록·조건부 IO/리셋까지 통과하면 현재 paired ARM/client로 SMB3 숫자1 타일→A 실기를 준비한다.

동일 seed 재시도·작은 비트 반복 FIT·클록 완화·기능/용량 검사 삭제는 하지 않는다. 이번 후보는 분석용으로 보존하며 아직 채택하지 않는다. Standard 설계 권고도 올바른 클록 도메인 제약과 동기화 체인 타이밍을 요구한다. [Intel Standard Edition Design Recommendations](https://www.intel.com/programmable/technical-pdfs/683323.pdf)

원시 근거1,068파일과 완료 기록은 `probes/nes-rank181`에 동결했다. 기존39개 소스 핀·13,054개 원시 근거·180 MCU1,413파일/FPGA62입력/ZIP·GBC 설정 보존도 확인했다. [검증 데이터](../analysis/rank181-verification.json), [현재 인계](../cores/nes/HANDOFF.ko.md)를 다음 작업의 출발점으로 사용한다.
