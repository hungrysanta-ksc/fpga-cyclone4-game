# 707 · 배경 CHR 마감 수정과 속도 작업 재개

**707D는 MMC705 첫 실행의 배경 CHR 오류와 같은 문맥을 재현한 두 경계를 수정했다.** 실제 T65·PSRAM 경계 시험, 기존 sprite·STOP 회귀, 전체 Quartus Lite FIT·기존 제약 STA를 통과했다. 두 시작 위상의 표시 일정은 기존과 동일하다. 새 실기 확인이나 FPS 향상 주장은 아니다.

PR156 병합 `4ee65ac300c3b5eca73848bd0b408c1bc63b6800`에서 새 브랜치 `codex/nes-bg-deadline-707`를 만들었다. 사용자 확인에 따라 스페이드 진입은 해결로 인정하고, 반복 화면 깨짐·기존 stage0 부팅 timeout은 관찰 항목으로 보존한다. 이번 속도 작업을 그 두 조사 때문에 보류하지 않는다.

## 원인 경계와 수정

실기 오류는 193선/230dot, 배경 CHR `21E161`, error2/age2였다. ROM 문맥 `e30143c2c221e161`과 PPU 상태 `60b9880005858586`를 모두 일치시키는 재현을 얻었다.

1. **렌더링 시작 직후:** 첫 BG 읽기의 주소가 확정되기 전에 CPU 요청이 reader를 점유했다. 원본 ROM의 `$F869`부터 실제 T65로 실행한 `LDA #$18; STA $2001`과 후속 읽기를 사용했다. 이전 렌더링 파이프라인 단계에서 안전하게 예측할 수 있는 첫 주소를 기존 hint 경로로 공급한다. 다음 ALE가 있는 경우 전체 주소, 없는 경우 기존 외부 low latch를 사용한다.
2. **`$2007` 읽기 종료:** 자연 부팅 추적에서 원본 `$A83C: LDA $2007` 뒤 fine-Y가 증가하고 다음 BG 요청이 늦어지는 경계를 찾았다. 실제 T65·PPUDATA 파이프라인·스크롤 증가를 실행하면 기존 보드에서 동일 오류가 났다. 마지막 read 단계에서 실제 주소 생성기의 다음 fine-Y를 사용해 BG 요청을 앞당긴다. 실제 증가·mask 계산을 공유하며 별도의 주소 복원기를 만들지 않았다.

두 번째 재현의 대표 case7은 기존 BG 요청이 step36에 수락되고 step39에 마감을 놓쳤다. 수정본은 step28에 요청하고 step33에 응답을 확보했다. CPU `$A840` 읽기는 뒤이어 처리되어 step38에 응답했고 CPU·다음 CHR도 독립 바이트 검사를 통과했다.

변경 파일은 **`rtl/ppu.sv` 하나**다. CPU/PPU 클록, mapper commit, 요청 우선순위, PSRAM 지연, 실제 소비 주소의 tag 검사, 오류 마감, STOP·ACK 회로는 바꾸지 않았다. 실기 로그에 직전 CPU 이력 전체가 없으므로 두 유효한 재현 중 어느 하나가 물리 실행의 유일한 원인이었다고 단정하지 않는다.

| 실제 T65 `$2007` | 3개 메모리 위상 36조건 통과; 기존은 6조건 실패 |

| fine-Y·copy/mask·wrap | 3,072조건에서 원본 주소 생성기의 실제 다음 레지스터와 일치, rendering일 때 preview도 실제 다음 fine-Y와 일치 |
| SPI·두 슬롯·최종 ACK·ROM bus | 해당 회로의 기존703 검증 소스 핀과 D의 바이트 동일성 확인 |
| ARM·65816 일정 | 두 위상 각각 53화면, 표시·최종 ACK 클록 단위 동일 |

위 기능 조건은 총 367개이며 fine-Y 3,072조건은 별도다. 실제 CPU 시험은 native arbiter fill 경쟁과 원본 PRG/CHR 바이트 대조를 포함한다. PPU 위치·초기 name/scroll은 통제한 경계 fixture이며 게임 전체 플레이 증명은 아니다. 자연 부팅20화면은 **기존703B**에서 원인 추적용으로 실행했으며 수정본의 전체 게임 통과로 계산하지 않는다.

| 전체 보드 | LE | LAB | setup / hold / recovery / removal(ns) | 판정 |
|---|---:|---:|---|---|
| 기존703B | 15,348 | 963 | +0.137 / +0.157 / +1.412 / +0.482 | 기준 |
| A · 별도 early hint | 15,296 | 962 | −0.171 / +0.139 / +1.410 / +0.325 | setup 실패 |
| B · restart decode 공유 | 15,272 | 964 요구 | FIT 실패 | 미선택 |
| C · 기존 full-address 경로 재사용 | 15,367 | 963 | +0.185 / +0.133 / +1.820 / +0.489 | `$2007` 경계 미해결 |
| **D · fine-Y 계산 공유 포함** | **15,322** | **962** | **+0.362 / +0.145 / +1.594 / +0.483** | **선택** |

D는 기존보다 LE26·LAB1 감소, FF8,377·RAM305,264bit·M9K56개는 동일하다. 남은 자원은 LE86/LAB1/M9K0이다. 배치 결과를 순수 논리 삭제량으로 해석하지 않는다. 제약·pin·seed는 그대로이며 PSRAM word 반환·reader/MISO·ROM OE/CE 개별 보고서도 양수다. 외부 IO 전체 sign-off는 여전히 미완료다. ARM Flash/RAM·65816 ROM 증가는0이다.

밀집 표시 간격은 **49.879668 / 49.866743ms**, 957 마지막 ACK는 **67,513,300 / 67,870,990 master clocks**로 기존703과 같다. 951 공개는245/236선, 952 표시3 VBlank, 957 최종 대기0회를 유지했다. 이 일정은 실제 링크 ARM·65816과 기존 SPI/IRQ/ROM 달력 재생이다. 수정된 NES/PSRAM RTL 경계 시험과 별개이며 전체 FPGA와 동시에 실행한 종단 증명은 아니다. 메뉴/base 생산 경로와 바이너리도 유지했으며 새 실기 메뉴 시험은 하지 않았다.

## 이어갈 속도 작업

동일한 map·OBJ 작업량의 951을 다시 분해했다. 실기 평균28.60ms를 모델 비율로 나눈 값이 아니다.

| 951 출력 비용(ms) | 위상1 | 위상2 |
|---|---:|---:|
| 출력 진입→첫 E1 | 0.359 | 0.359 |
| 첫 E1→SEAL 발행 | 14.955 | 15.557 |
| SEAL 큐 대기 | 0.039 | 0.006 |
| 검사 | 1.631 | 1.632 |
| 업로드 VBlank 대기 | 8.700 | 8.091 |
| 남은 DMA | 0.786 | 0.276 |
| 나머지 CPU | 0.986 | 0.873 |
| 마지막 표시 VBlank 대기 | 0 | 0 |
| ACK→ARM 반환 | 0.322 | 0.428 |

마지막 tile ACK 뒤 **17패킷·2,351B**, SEAL 수락까지 **11.873 / 12.451ms**가 남는다. 이 안에는 map 192B 패킷7개와 OAM·section5·SEAL이 있다. map은 마지막 tile ACK보다 약7.2ms 앞서 확정되고 나머지 데이터도 약4.3ms 앞서 확정된다. 951의 BG ROM 거래는0이며 마지막 OBJ ROM 응답도 마지막 tile ACK보다 앞선다. 따라서 여기서는 ROM reader를 다시 바꾸기보다 **이미 확정된 후반 패킷의 준비·발행·credit 대기를 줄이는 것**을 먼저 비교한다. 데이터 확정과 serializer 진입은 다른 시각으로 기록했다.

다음 순서와 통과 기준:

1. 707D와 기존 ARM·65816을 고정 대조군으로 둔다. 마지막 tile 전에 확정된 패킷을 보낼 실제 SPI 빈 구간과 credit 반환을 대조한다. bulk 소비·다음 입력7블록·새 패킷·STOP 우선권을 빼앗은 시간을 모두 비용에 넣는다.
2. 기존 ABI에서 후반 발행 순서를 바꾸는 최소 후보를 먼저 실행한다. 준비됐다는 이유만으로 버스가 비었다고 가정하거나 위상별 고정 sleep을 추가하지 않는다. Flash 여유는 정상판8B/장시간판52B이므로 기존 코드를 교체하는 범위에서 예산을 잡는다.
3. 두 위상 전체 905–957의 작업·독립 바이트/coverage·최종 ACK를 맞춘다. 911 마감,951 공개≤246선,952 표시3회,957 최종 대기0회와7블록 선행 수신을 보존하고 밀집 간격·마지막 ACK가 함께 줄어야 채택한다.
4. 646의 OAM 단독 선행과647의 패딩 이력 단독 후보는 이미 다른 화면·공개선 회귀로 실패했다. 새 일정 근거 없이 반복하지 않는다. 위 표의 VBlank 대기를 삭제 가능한 고정 비용으로 계산하지 않는다.

반복 화면 깨짐과 stage0 timeout은 사용자 요청대로 별도 관찰로 남긴다. 향후 전달은 새 이름의60초/장시간판이며 RESTORE·게임 ROM·세이브를 제외한다. 이번에는 설치본을 만들지 않았다.

## 재현·보존

703B의 `inputs703.json`과82개 핀 파일을 준비한 뒤 `tools/prepare_nes_bg707.py --base <703B> --out <new> --reuse --readtail`로 D를 생성한다. `probe_nes_bg707_boundary.py`, `probe_nes_bg707_cpu.py`, `probe_nes_bg707_read_cpu.py`, `probe_nes_bg707_replay.py`, `probe_nes_bg707_fine.py`가 각 경계 fixture를 만든다. `probe_nes_bonus703.py`의 sprite/STOP 대조도 D에 결합한다. 라이선스1좌석 wrapper에서 `probe_nes_bonus698.py run`을 순차 실행한다.

분석기는 로그의 완료 문자열뿐 아니라 **각 CASE의 failed/error·독립 검사·원본 파일 해시를 검증**한다. `tools/analyze_nes_bg707.py --temp <build-root> --probe <probe-root> --out <new-analysis>`는 전체 FIT/STA와 두 위상 결과를 묶는다. 보고서·생산 patch·소스·실패 중간본·원시 로그는 private evidence ZIP에 보존했다. ROM/추출 PRG·CHR·화면 dump·라이선스/서버 로그는 제외했다. analysis01은 개별 STA 보고서 생성 전 분석 실패이며 analysis02가 최종이다.
