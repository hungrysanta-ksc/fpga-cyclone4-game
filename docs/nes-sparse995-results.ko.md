# 995 · 911의 테이블·SEAL 압축 검증

## 목표

978의 908 공개, 909의 624B 선행 DMA, 910 캡처를 유지하며 911을 VBlank 44의 246선 안에 공개하고 912 최종 ACK를 앞당긴다. 911의 두 패킷만 바꾸는 실험과 같은 형식을 매 세대에 적용한 ARM·65816 공동 실행을 비교했다.

## 작업내용

- 240B 테이블의 215B와 168B SEAL의 132B가 0이었다. 8B당 점유 마스크 1B와 0이 아닌 리터럴을 보낸다. 실제 ARM 송신기는 원래 길이보다 짧을 때 이 형식을 선택하고 물리 길이와 CRC16을 다시 계산한다. 테이블·SEAL의 식별자와 논리 범위는 고정했다.
- 첫 대조는 동일한 978 바이너리로 부팅해 910 ACK까지 클록이 같은지 확인했다. 911에서 선택한 E1의 직렬 전송 시간만 바꿨다. 드라이버 고정 비용, ARM 발행, 큐 credit, 65816의 논리 데이터 소비와 독립 검사는 유지했다. 두 코덱 비용을 0으로 둔 이 대조에서 E1 헤더와 CRC의 전송 시간도 유지했다.
- 두 번째 실험에서 전체 링크한 Cortex-M4가 실제 짧은 E1과 CRC를 생성했다. Mesen의 65816은 물리 패킷에서 마스크와 리터럴을 읽어 WRAM으로 복원했다. 읽기 한계와 리터럴 수를 확인하고 8B마다 STOP을 조회했다. 두 위상 각각 16개 압축 패킷이 기존 소비기로 넘어갔다.
- 두 번째 실험의 큐와 주소 전환은 시험기에서 연결했다. 시험기는 압축 CRC를 확인하고, 65816이 복원한 헤더·본문을 독립 참조와 대조한 뒤 같은 바이트를 기존 수신 창으로 노출한다. 기존 검사·DMA·공개·최종 ACK는 원래 65816이 실행한다. 이 연결에는 FPGA의 실제 주소 선택 비용이 포함되지 않았다. 65816 진단 루틴은 234B이며 WRAM에 주입했다.

ARM은 212,992→213,184B로 Flash 한도를 192B 초과했다. 두 위상에서 여덟 화면의 RGB가 978과 일치했다. 별도 재생에서 64B 복원 뒤 STOP은 0xE4, 마지막 리터럴 누락과 올바르게 압축한 잘못된 SEAL 버전은 각각 0xE0로 끝났다. 여섯 오류 주입 모두 910 화면과 최종 표시 이력을 보존했다. 실기 메뉴 복귀와 새 보드 FIT·STA는 이번 실험에서 측정하지 않았다. ## 후속작업

978을 유지한다. 다음 실험은 909와 911이 번갈아 사용하는 대상 뱅크의 OAM을 다룬다. 최종 ACK가 난 909와 911의 논리 OAM을 재구성하면 176–211의 36B는 전부 바뀌고, 212–511의 300B와 512–543의 32B는 모두 같다. 911에서 마지막 32B OAM의 반환만으로도 낙관적 SEAL 마감보다 0.314 / 0.568ms 늦다. 909 ACK 뒤 실제 WRAM 쓰기를 추적해 이 332B의 보존 여부를 확인한다. 보존이 확인되면 새 36B의 처리와 332B의 재사용을 묶어 큐 반환 횟수까지 줄이는 비용을 먼저 재생한다. 독립 검사, 손상 검출, 부분 쓰기·STOP 무효화, cold 전체 복원의 비용을 포함해 양쪽 위상에서 911 공개와 912 ACK가 개선될 때 채택한다.

재현 도구는 `tools/nes_sparse995.py`(선로 비용 분리), `tools/build_nes_sparse995.py`와 기존 `build_nes_trial577.ps1`(전체 ARM 링크), `tools/nes_receiver995.py`(공동 실행), `tools/test_nes_sparse995.py`(오류 주입), `tools/check_nes_sparse995.py`(대조·집계)다. 초기 선로 대조가 드라이버 비용을 계측 초기화 전에 저장해 905부터 달라진 것을 발견했다. 위 표는 보정 후 905–910의 최종 ACK가 978과 클록 단위로 일치한 대조만 사용했다.
