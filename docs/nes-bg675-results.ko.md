# 675: 첫 zero 소비와 BG 계획 허가의 결합

기준은 MMC666 ARM·665 보드·65816이다. 674의 반복 작은 묶음은 기각한 상태로 보존한다. 이번 변경은 첫 zero 타일의 소비를 먼저 요청하고 첫 compact BG 쌍에만 검증된 plan bank 허가를 사용한다. 이후의 큰 BG·OBJ 묶음, 독립 검사와 실제 소비 완료·최종 표시 ACK의 구분을 유지한다.

**기능은 통과했지만 종단 시간은 실패해 MMC666을 유지한다.** [검증 JSON](../analysis/bg675-verification.json). 초기 허가와 후속 큰 묶음의 양립은 확인했으나, 빨라진 타일 공급이 기존 map 뒤 대기 조건과 맞물려 952 표시를 늦췄다. 새 전달본은 만들지 않았다.

## 두 시작 위상의 전체 결과

106화면의 map·OBJ·ordinary 바이트, 독립 복원·CRC와 VRAM 출력, 실제 최종 ACK를 대조했다. map·tile 전체 전송량은 동일하다. 밀집 구간은 기존과 같은 951–955이며 실제 5–55초 실기 집계와 혼동하지 않는다.

| 항목 | 위상1 MMC666→675 | 위상2 MMC666→675 |
|---|---:|---:|
| 밀집 총 VBlank | 15→17 | 15→16 |
| 밀집 평균 표시 간격 | 49.920847→56.622592ms | 49.916880→53.227393ms |
| 957 마지막 ACK 차이 | +33.763227ms | +16.925706ms |
| 952 표시 간격 | 3→5회 | 3→4회 |
| 954·955·957 표시 간격 | 각각3→3회 | 각각3→3회 |
| 911 SEAL 수락/검사 후 진입선 | 188/214 | 185/211 |
| 951 공개선 | 239 | 239 |
| 957 최종 대기 | 0회 | 0회 |

표시 간격이 VBlank 단위로 회귀한 화면은 952뿐이며 새 최종 대기는 없다. E8 조회는 2,040/1,860B 감소했지만 E0가 3,220/1,720B, E9가168B 증가했다. D0 증가까지 포함한 전체 SPI 차이는 +1,356/+68B다. 거래 하나의 감소를 전체 시간 개선으로 취급하지 않는다.

## 952: 타일은 빨라졌지만 map 뒤 기존 대기가 새로 걸린다

다음 시각은 모두 해당 화면의 직전 표시부터 잰 값이다.

| 사건 | 위상1 원본→후보 | 위상2 원본→후보 |
|---|---:|---:|
| 마지막 tile ACK | 43.313→32.966ms | 43.263→33.219ms |
| 마지막 map ACK | 33.125→36.384ms | 33.405→36.684ms |
| map drain 복귀→첫 ordinary 요청 | 0.093667→6.561557ms | 0.093667→6.561366ms |
| SEAL 수락 | 46.373→49.767ms | 46.095→50.032ms |
| SEAL 검사 뒤 업로드 진입 | 48.013→51.386ms | 47.736→51.628ms |
| 선행 map DMA | 1,536→192B | 1,536→768B |
| 업로드 VBlank 대기 | 0.613→29.111ms | 0.874→13.480ms |

zero 소비와 BG 허가는 효과가 있었다. 마지막 tile ACK를 약10.0–10.3ms 앞당겼고, 674에서 보인14–15ms의 plan emit 정지도 사라졌다. 952의 E9는 `2/15/4 → 2/2/4/13`이다. 그러나 tile 우선 공급과 map 발행의 교차 순서가 바뀌어 전체 map 소비는 약3.26–3.28ms 늦어졌다.

변경하지 않은 `nes_sink212_seal`은 긴 map tail을 drain한 뒤, 이전 표시 이력이 있고 `obj_next>=16`이면 40회 wait를 실행한다. 앞38회는 일반 대기, 뒤2회는 다음 입력의 수신을 허용한다. 원본은 map drain 때 OBJ 제출이 아직 시작되지 않았지만 후보는 이미 마지막 tile ACK까지 끝났다. 실제 호출·SPI 기록에서 후보의 drain 뒤 첫 ordinary 요청까지6.561ms가 걸리며 뒤쪽에는 다음 입력의 D0/D1/D2 두 거래가 있다. 동일 링크 ARM의 별도 경계 시험도 obj_next 15/16에서 wait 0/40회와 STOP 중단을 확인했다. 전체 재생에 wait 호출 횟수 자체를 새로 계측한 것은 아니므로 원시 함수·SPI 시각과 이 독립 조건 시험을 구분한다.

이 대기는 원래 빈 큐의 map 선행 DMA 기회를 주기 위한 것이다. 타일 공급만 빨라진 새 일정에서는 기존 조건이 추가 지연을 유발한다. 후보의 SEAL 검사는 이미 VBlank를 지나 0/4선에 진입하고, 남은 map DMA가 커져 다음 업로드까지 기다린다. **최종 대기0회만 유지하는 것으로 종단 개선을 판정할 수 없다.** 대기를 모두 삭제한 경우의 시간은 이번에 실행하지 않았으며6.56ms를 그대로 개선 실적으로 빼지 않는다.

## 954·957: 큰 묶음은 유지하지만 ROM 마감은 아직 부족하다

954는 `2/8/14 → 2/2/7/13`, 957은 `2/12 → 2/2/10` E9 record 묶음이다. 954의 마지막 BG 발행 수락은 직전 표시 기준25.020/24.779→21.460/21.532ms로 빨라졌지만 마지막 BG 준비가 이전 ROM 창보다 여전히1.941/2.283ms 늦다. 해당 창으로 모든 BG를 옮기지 못해 표시3회는 그대로다.

957의 마지막 BG 호출 내부 대기는674의 약1.306ms에서 약0.334ms로 줄었다. BG 쌍 E9 수락은MMC666의23.771/24.001→17.457/17.278ms다. 다만 각 실행의 실제 ROM 달력으로 계산하면 위상1은 이전 창 종료보다0.775µs 늦고, 위상2는4.137µs 앞설 뿐이다. 후속 decode·RAM/ROM 처리까지 포함한 마지막 BG 응답은 모두 다음 창이며, 표시3회와최종대기0회가 유지될 뿐 추가 이득은 없다. 원본의 ‘직전 표시 대비 창 종료’ 시각을 바뀐 연속 일정에 그대로 적용하지 않았다.

## 구현과 소유권

`prepare_nes_bg675.py`는 원본 firmware hash를 확인한 별도 빌드에서 `nes_plan_service200.c`만 변경한다. 첫 BG의 기존 발행은 그대로이며, 두 번째 BG를 저장할 때 아직 bulk descriptor가 없으면 E8을 한 번 확인해 zero 타일의 E1 소비 요청을 먼저 제출한다. BG가 하나뿐인 화면에는 이 추가 거래가 없다.

첫 묶음 발행 뒤 `sent=1`, 검증된 두 뱅크 이력, 두 compact BG record·14B·비END 조건을 모두 만족할 때만 초기 쌍을 발행한다. CRC와 수락 count를 통과한 E8이 plan bank 쓰기 허가와 미소비 tile descriptor를 함께 보고하면 쓰기 허가를 유지한다. 기존 descriptor의 generation·token·전체 내용 검사, 이전 bulk receipt 확인과 전송 직전 STOP 검사는 그대로다. 타일 소비 완료로 간주하거나 최종 ACK를 생성하지 않는다.

후속 큰 묶음의 기존 BG/OBJ 경계는 초기 쌍 다음에도 적용한다. 실제 링크 ARM의 BG10개·OBJ12개 시험에서 E9 record 수는 `2(제로+첫BG) → 2 → 7 → 13(OBJ+END)`이다. 674처럼 BG 두 개마다 반복 발행하지 않는다. 프레임 번호·ROM 위상·주사선별 상수 분기는 없다.

## 실제 경계 검사

- 기존 보드665의 합성 입력과 일치하는 RTL 15파일을 사용했다. SOF는 `49cf57dec08a0c3d5548ddde497d92d241e8539a46a34827a3f066a8c6165343`이다. 단일 Starter FLOAT 좌석에서 두 host 시작 위상을 순차 실행했다.
- zero 타일을 읽지 않고 BG 두 개를 수락해도 최초 token·descriptor가 보존된다. 반복 E8은 소비를 진전시키지 않는다. 네 tile의 실제 read와 receipt를 순서대로 확인하고, END 뒤에도 표시 lease가 임의로 해제되지 않음을 확인했다. 미소비 계획이 있는 상태의 STOP/reset과 cold 재시작도 통과했다. ROM 응답은 0 데이터 모형이며 실제 PSRAM 일정·PPU 표시를 이 시험으로 증명하지 않는다.
- 실제 링크 ARM 12조건에서 cold/한 뱅크/두 뱅크 이력, bank busy, 잘못된 CRC/count/generation, 동일 token의 descriptor 변경, zero 제출 뒤 STOP, pair query/발행 직전 STOP, 불명확한 E1 전송 실패를 확인했다. 소비 완료를 지연시킨 상태에서도 BG grant가 사용되며, 오류 뒤 새 E9·EA는 나오지 않는다. 최종 표시 ACK 없는 retire는 거부된다.
- 기존 END 단독 허가 9조건, routing/STOP 12조건, SEAL/credit/최종 ACK 5조건, 메뉴 준비·해제 5조건과 파일 marker 4조건을 통과했다. 메뉴 시험은 외부 IO를 모형화한 실제 ARM 경계 검사이며 새 실기 성공을 뜻하지 않는다. cold/부분 복원·캡처 회복·65816 STOP/DMA 구현은 변경하지 않았다.

## 자원과 검증 범위

전체 ARM 링크 파일은 212,624B로 원본보다 128B 증가하며 Flash 여유는 368B다. data 10,040B·BSS 19,544B는 동일하다. 컴파일러의 함수별 stack 보고에서 emit은 16→24B, poll 56B·drive 32B·flush 24B는 동일하고 새 predicate는 0B다. 이를 전체 호출 경로의 최대 stack 측정으로 부르지 않는다.

FPGA·65816 바이트는 변경하지 않았다. 보드 비용은 기존 15,324LE·962LAB·56M9K, setup +0.511/hold +0.149/recovery +1.828/removal +0.393ns이며 같은 전체 합성을 반복하지 않았다. 외부 IO 전체 sign-off와 지속 60fps는 여전히 미완료다.

전체 일정은 실제 링크 ARM과65816을 실행하고 CPI2·shared SPI·IRQ 모형 및 측정된 반복 ROM 허용 달력을 사용한다. 두 시작 시각은 7,288,416/7,467,100 master clock이며 각 905–957의 53화면이다. 변경 없는673 대조군은 MMC666의 모든 ACK와 출력 바이트가 동일한 것으로 고정돼 있다. 실기 평균26.84ms를 재생 비율로 나누거나 이 결과를 실기 FPS로 환산하지 않는다.

## 재현

`prepare_nes_bg675.py ../probes/nes-trial666/arm01 <새 빌드>` 뒤 `build_nes_trial577.ps1 -SourceRoot <새 빌드>`로 전체 링크한다. `check_nes_bg675_arm.py --arm <새 빌드>/src --out <새 JSON>`으로 ARM 경계를 확인한다. `check_nes_bg675_rtl.py --board <665 보드> --bin <Questa win64> --out <새 폴더>`는 승인된 FLOAT wrapper의 절대경로 job에서 실행한다. 한 좌석으로 순차 실행하며 새 라이선스 smoke는 하지 않는다.

전체 재생은 기존 `test_nes_ready673.py`를 그대로 사용한다. 실제 인자는 로컬 `../probes/nes-bg675/replay.ps1`, 결과는 ASCII Temp의 `nes-bg675-grant1/grant2`다. 기준은 `nes-ready673-b1/b2`이며 `analyze_nes_bg675.py`에 `--traces/--arm/--base-arm/--guards/--out`으로 연결한다. 새 도구와 검증 JSON에 원본·산출물 hash를 고정한다. 로컬 상용 ROM·측정 fixture·도구 의존성을 임의 데이터로 대체하지 않는다.

## 다음 순서

1. 제품은MMC666을 유지한다. 675는기능이 확인된 연구 후보이며 첫 pair 크기·고정위상을 바꾸는 반복 시험은 하지 않는다.
2. 952의 map drain→ordinary 사이 대기를 **실제 map DMA 진행·큐 유휴 기회·다음 입력 수신**으로 나눈다. obj_next의 도착 순서에 따라40회 대기가 새로 붙는 조건을 대체할 경계부터 정한다. 675의 실제 tile 이득을 보존하면서 선행 map DMA1,536B와SEAL 마감을 회복할 수 있는지 확인한다. 대기 횟수만 줄이거나 STOP/독립 검사/다음 입력 비용을 생략하지 않는다.
3. 해당 후보 하나를 동일 두 위상으로 검증한다. 911≤189/214선,951≤246선,952≤3회,954/955 회귀 없음,957 최종대기0회 및 밀집 평균·마지막ACK 동시 개선을 모두 요구한다. 조건 실패 시MMC666을 유지한다. 954의 별도 준비 지연과957 ROM 처리 여유는 이 게이트 뒤 순서로 두고, 미세한 고정 위상 조정을 성과로 만들지 않는다.

원시 재생·전체 ARM ELF/firmware·RTL 입력과 결과·guard·공개 도구는 `archive_nes_bg675.py`로 별도 보관한다. [보관 manifest 요약](../analysis/bg675-archive.json). 라이선스 wrapper 출력·서버 로그는 포함하지 않는다. README의 실기 성능과 기존 설치 ZIP은 변경하지 않는다.
