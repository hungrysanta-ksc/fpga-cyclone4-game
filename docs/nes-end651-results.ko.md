# NES 651 · 마지막 타일과 END 발행

905–957 연속 실행에서 651 grant가 양 시작 위상의 954·955를 각각 3 VBlank에 표시했다. 실기 기준은 MMC643이다.

## 650 packed에서 위상 2가 늦어진 이유

955의 ARM END 함수 진입을 각 위상의 0 ms로 맞췄다. 두 실행은 같은 ROM 달력과 같은 map·OBJ 작업을 쓴다. 144회의 BG ROM 허가 시각은 절대 master clock 기준으로 전부 일치했다. 첫 허가는 66,806,268, 마지막 BG 응답은 66,815,429였다. OBJ 쪽 144회 읽기는 모두 기존 캡처에서 공급했다. END 함수가 위상 2에서 약 0.277 ms 먼저 진입해 같은 BG 준비가 END 기준으로는 뒤에 보였다.

| 955의 사건 · END 진입 후 ms | 위상 1 | 위상 2 |
|---|---:|---:|
| END E9를 쓸 plan bank에 credit 발생 | 6.413 | 6.690 |
| 144 B BG 타일 묶음 준비 | 6.508 | 6.785 |
| 상태를 가른 E8 샘플 | 6.598 · plan과 BG 모두 준비 | 6.598 · 둘 다 대기 |
| BG descriptor를 실제 본 첫 E8 | 6.598 | 7.624 |
| BG 타일 E1 발행 완료 | 6.873 | 7.899 |
| 65816의 해당 타일 ACK | 7.882 | 8.973 |
| ARM이 해당 큐 credit을 확인 | 8.142 | 9.447 |
| 마지막 OBJ 캡처 읽기 응답 | 8.975 | 10.312 |
| END E9 발행 완료 | 10.713 | 12.019 |
| ARM 출력 함수 진입 | 10.717 | 12.023 |

위상 2는 6.598 ms의 E8 뒤 211 B map 거래를 하나 더 보냈다. 이 구간 안에서 map E1은 8→9회, E8은 13→15회였다. 출력 큐 상태 E0는 양쪽 모두 6회였다. END→출력 **+1.306 ms**를 중복 없이 나누면 **map 전송 +0.693 ms, E8 두 번 +0.218 ms, SPI 밖 ARM 실행·guard·대기 +0.395 ms**다. 타일 ACK와 큐 credit이 늦어진 시각은 이 같은 시간을 다른 경계에서 본 것이다. 전체 map 바이트가 늘어난 것으로 계산하지 않는다.

## 채택한 ARM 일정과 실기 진입 조건

grant는 plan bank와 미소비 타일을 함께 보고한 E8을 사용한다. 타일의 generation·token·descriptor를 독립 확인하고 먼저 제출한다. 이미 CRC까지 완성된 END 단독 E9에 한해 같은 응답의 bank credit을 사용하고, 전송 직전에 STOP을 다시 확인한다. FINISH와 최종 ACK에서는 실제 소비 완료를 기다린다.

| 판정 · 651 grant | 위상 1 | 위상 2 |
|---|---:|---:|
| 648의 954 SEAL 마감 여유 · 953 표시 기준 | 0.146424 ms | 0.011340 ms |
| 648의 954 SEAL 마감 여유 · 공통 시작 기준 | 49.857207 ms | 33.312962 ms |
| 951 공개선 / 957 최종 추가 대기 | 239 / 0 | 239 / 0 |
| 951–955 표시 간격 (VBlank) | 3·4·3·3·3 | 3·4·3·3·3 |
| 957 ACK 절대 master clock | 69,312,386 | 69,669,640 |
| 954 ACK 전 검증·반환한 955 geometry 블록 | 5 / 7 | 5 / 7 |

MMC643의 951–955 평균은 59.834 / 59.870 ms였고, 651 grant는 53.286 / 53.283 ms였다. 650 packed와 따로 비교하면 957 ACK는 0.063 / 0.366 ms 늦었다. 위상 2에서 906은 8→9회, 914는 4→3회, 938은 3→4회, 955는 4→3회였다. 955에서 되찾은 한 VBlank는 연속 실행 앞부분에서 밀린 한 VBlank를 상쇄했다.

두 번째 warm bank의 BG를 여덟 개까지 묶는 첫 구현은 혼합 묶음도 일찍 닫아 953의 독립 plan 순서 검사에서 탈락했다. 7개 모두 BG인 경우로 제한한 bg8을 재실행했다. handoff의 짧은 END 함수 시간은 실제 E9 발행 시각과 구분해 표기했다.

grant의 전체 Flash는 213,316 B로 650 packed보다 44 B 늘었고 보드 한도 212,992 B를 324 B 초과했다. 실기 전달 전 최소 324 B를 절감하고, 압축 송신기를 실제 FPGA에 연결해 생성 지연과 RAM 포트 경쟁을 포함한 두 일정 및 Quartus Lite 전체 FIT·STA를 다시 검증한다. 위상 2의 상대 SEAL 여유가 11.34 µs라서 동일 시작 시각에서 다시 측정해야 한다.

## 변경과 검증 범위

네 후보는 각각 650 packed에서 독립적으로 빌드했다. geometry 블록 경계와 495 B 압축, 65816 ROM, 압축 입력의 독립 검사, 공통 SPI·ROM 달력과 시작 시각은 같다.

- **bg8**는 두 번째 warm plan 묶음에서 7번째 BG가 확정된 뒤 바로 다음 BG까지 같은 E9에 넣는다. OBJ가 먼저 오면 기존 BG를 발행하고 OBJ를 새 묶음에 넣는다.
- **short**는 END 단독 bank가 기다리는 동안의 선행 map 한 번을 최대 3행에서 1행으로 제한한다. 이후 같은 cursor부터 남은 행을 보낸다.
- **handoff**는 END 단독 헤더와 CRC를 만든 뒤 첫 출력 서비스에 실제 E9 발행을 넘긴다. END 함수가 일찍 반환하는 효과와 실제 E9·SEAL·표시 시각을 따로 집계한다.
- **grant**는 검증한 E8이 새 타일과 쓰기 가능한 plan bank를 동시에 보고하면 타일을 먼저 제출한 뒤 그 응답으로 준비된 END 단독 E9를 보낸다. 같은 token의 반복 응답은 descriptor 전체가 일치할 때만 허용한다. FINISH·최종 ACK와 EA는 기존 소비 확인을 거친다.

각 후보의 두 시작 위상에서 905–957을 연속 실행했다. 53화면마다 map WRAM·VRAM, 화면 RGB·CGRAM·OAM·HDMA·최종 ACK를 대조했다. map을 나눠 보낸 경우에는 원래 **모든 대상 주소와 바이트가 중복 없이** 한 번씩 쓰였는지 확인했다. 실제 tile 바이트와 BG 적중 48회·OBJ 캡처 1,200회, 두 슬롯 한도, 앞 화면 ACK→EA→다음 입력 COMMIT 순서도 검사했다.

MMC643 보드의 실제 plan SPI·bank·타일 RTL을 Questa에서 실행했다. 미소비 타일과 plan credit이 동시에 보이는 E8 뒤 END를 발행해 앞 token이 보존되고 두 타일을 순서대로 읽어 반환하며, STOP으로 소유권이 초기화되는 것을 확인했다. 네 ELF에서도 새 descriptor, 반복 token, bank 대기, 손상 CRC·다른 세대·변조된 descriptor·타일 제출 직후 STOP·모호한 E1 실패를 주입했다. geometry 독립 검사, 잘못된 최종 ACK, 메뉴 준비·해제와 base 정상 복귀·네 실패 차단은 별도 ARM 시험이다. 실기 메뉴와 FPS를 새로 측정하지 않았다.

### 재현

1. `prepare_nes_end651.py <650 packed 빌드> <새 폴더> bg|short|handoff|grant`로 각 후보를 만들고 `build_nes_trial577.ps1`로 전체 링크한다.
2. [650의 실행 조건](nes-geometry650-results.ko.md)에서 `test_nes_geometry650.py --geometry650 --commit-pop-bound --keep-run`을 사용한다. 시작 시각 7,288,416·7,467,100, 637 client01과 압축 송신 참조를 공통으로 사용한다. bg 모드의 빌드·trace 디렉터리 이름은 bg8이다. 후보 trace 이름은 `nes-end651-{모드}{위상}`이다.
3. 각 ELF에 `check_nes_end651_arm.py`, `check_nes_geometry650.py`, `check_nes_tail648_arm.py`, `check_nes_menu533.py --trial 643`, `check_nes_dma637.py --late-receive --late-blocks 2`, `check_nes_transfer512_recovery.py --trial 643`의 다섯 케이스를 실행한다. 기존 한 좌석 FLOAT wrapper 안에서 `check_nes_end651_rtl.py`를 실행한다.
4. `analyze_nes_end651.py --traces … --build … --rtl … --data … --out …`로 보관된 650 packed 두 기준 trace와 여덟 후보 trace를 대조한다. ARM CPI 2, SPI 드라이버 비용과 ROM 공급 창은 기존 모델이며, 실제 보드의 압축 송신기 생성 비용·FIT·STA는 후속 검증 사항이다.
