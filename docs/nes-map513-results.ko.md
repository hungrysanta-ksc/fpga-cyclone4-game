# MMC509 대상 뱅크 map 전송 조사 (513)

**64B 행 이력을 저장해 재전송을 생략하는 후보는 보류한다.** 같은 MMC509 ARM이 생산한 71화면에서 초기 두 화면 이후 전송한 1,763개 행은 모두 대상 뱅크와 적어도 한 바이트가 달랐다. 반면 한 행 안의 16비트 워드는 95.38%가 같았다. 다음 실험 후보는 **8B 단위 변경 기록으로 기존 패킷의 앞뒤만 잘라내고, 가운데는 기존 literal DMA 한 번으로 보내는 방식**이다. [측정 JSON](../analysis/map513-verification.json)

## 비교 기준

- MMC509 배포 ELF의 실제 수신기·planner·map 생산기를 실행해 generation 905~975의 패킷과 매 단계의 4,096B 목표 map을 수집했다. 905~916에서는 bank와 map 패킷의 주소·복원 바이트를 512의 원본 ARM·65816 공동 실행과 전부 대조했다. 나머지 59화면의 sink ACK는 모델이다. 이 결과로 실기에서 특정 레벨의 FPS를 계산할 수 없다. [ARM 수집기](../tools/measure_nes_map513.py) · [512 공동 실행](nes-transfer512-results.ko.md)
- 첫 사용 시 두 뱅크의 내용은 미확정으로 놓았다. 독립적으로 패킷을 적용한 전체 뱅크 이미지가 planner 이미지와 일치하는지 확인한 뒤, 해당 serial·generation·bank의 최종 ACK에서만 이력을 공개했다. STOP 뒤에는 두 뱅크 이력을 모두 무효화했다. 실제 MMC509 resident 코드에서도 미표시·잘못된 serial/generation/bank, STOP, 늦은 commit, reset 뒤 cold를 검사했다. [분석기](../tools/analyze_nes_map513.py)

| 구간 | 예정 map 패킷 | 전송 대상 행 | 완전히 같은 행 | 같은 16비트 워드 |
|---|---:|---:|---:|---:|
| 초기 2화면 | 44 | 128 | 비교할 유효 이력 없음 | — |
| 기존 공동 실행과 대조한 후반 10화면 | 88 | 239 | 0 | 7,328 / 7,648 |
| 후반 69화면 전체 | 644 | 1,763 | 0 | 53,809 / 56,416 |

행 전체의 바이트를 독립적으로 보관하면 두 뱅크 8,192B와 유효 비트 16B가 든다. 원본 공동 실행에서 관측한 ARM 작업 공간 끝과 최저 SP의 간격은 2,488B다. 실제 배포 ELF의 `memcmp`·`memcpy`로 후반 대상 행을 비교·복사하면 153,947 + 84,624개 명령을 실행한다. 평균 3,458개/화면이고 84MHz·CPI 2 가정으로 0.082ms다. 호출·관리·IRQ 비용은 별도다. 이 표본에서 행 단위로 회수한 전송량은 **0B**다.

## 한 패킷에서 연속 범위만 남기기

예를 들어 907의 map offset 320~383은 한 바이트라도 달라 64B 전체 생략이 불가능하다. 16B 단위로 실제 쓰기를 확인하면 352~367만 보내도 된다. 앞뒤 48B를 잘라내고 같은 패킷으로 16B를 한 번 보낸다.

기록은 최종 이미지 차이만 보고 역산하지 않았다. 실제 `map_word185` 진입 때 기존 값과 쓸 값을 비교했고, WRAM 쓰기 관측도 따로 했다. 중간에 바뀌었다 복귀한 워드 역시 변경으로 남긴다. 이력 없는 cold에서는 모두 변경으로 표시하고, 변경 비트를 양쪽 뱅크에 누적하며 해당 뱅크가 표시된 뒤에만 지운다. 기존 한 패킷에서 첫 변경 그룹부터 마지막 그룹까지만 남긴 뒤 각 프레임의 최종 map 4,096B를 다시 비교했다. 기존 RLE 또는 원래 패킷이 더 작거나 같으면 원래 표현을 선택했다.

| 변경 그룹 | 후반 69화면 평균 절감량 | 2.625MHz 전송 시간 환산 | 추가 ARM 마스크 | ARM 커널 .text | 마스크 작업 시간 환산¹ |
|---|---:|---:|---:|---:|---:|
| 8B | 502.38B/화면 | 1.531ms | 192B | 148B | 0.030ms/화면 |
| 16B | 429.22B/화면 | 1.308ms | 96B | 148B | 0.019ms/화면 |
| 32B | 281.97B/화면 | 0.859ms | 48B | 144B | 0.013ms/화면 |

¹ Cortex-M4용으로 빌드한 커널을 실제 planner 쓰기 순서로 실행했다. 변경 비트 설정·두 뱅크 병합·패킷 범위 탐색·ACK 뒤 지우기의 실행 명령 수를 84MHz·CPI 2로 환산했다. 컴파일된 코드 크기는 독립 커널 기준이고, 호출부·Flash 버스·SPI·IRQ·65816 검사는 포함되지 않는다. [측정 커널](../tools/nes_map513_mask.c) · [실행기](../tools/check_nes_map513_mask.py)

후반 69화면의 원래 map 전송은 헤더·CRC 포함 125,068B다. 8B 방식은 패킷 수를 유지하면서 이 중 34,664B를 덜 보낸다. 512와 대조한 후반 10화면만 보면 표시당 480B, 전송 환산 1.463ms다. 기존 SPI 조회나 VBlank 대기를 절감분에 포함하지 않았다. 추가 RAM은 현재 쓰기용 마스크 하나와 뱅크 마스크 둘을 합한 값이다.

## 구현 판단과 다음 관문

- **8B를 우선 시험한다.** 16B와 커널 크기가 같고 추가 RAM 96B로 평균 73.16B를 더 줄인다. MMC509의 Flash 잔여는 36B라서, 148B 커널을 그대로 추가하면 호출부 이전부터 112B 초과다. 기존 범위 계산과 직렬화 코드를 대체해 실제 링크 크기를 확인하는 것이 첫 조건이다.
- 65816의 기존 `mark212`는 64B 정렬을 검사한다. 부분 literal을 사용할 때는 출력 패킷의 실제 쓰기 범위와 독립 검사에서 인정할 논리 행 범위를 구분해야 한다. 같은 epoch·bank·마지막 표시 identity 및 유효한 기존 행에서만 생략을 허용하고, cold·STOP·불일치 때는 완전한 행을 요구한다. 생략한 바이트까지 포함한 기대 행을 소비기가 독립적으로 확인할 방법과 그 비용도 필요하다. 예를 들어 짧아진 644개 패킷마다 검사값 2B를 새로 싣는 경우 후반 절감량은 34,664B에서 33,376B로 줄고, 65816 검사 시간은 별도로 든다. 이번 측정에는 새 검증과 DMA descriptor 비용이 들어 있지 않다.
- 독립 검사·중간 STOP·최종 ACK·VBlank를 유지한 ARM·65816 구현을 같은 905~916 일정에서 원본과 대조한다. 최종 ACK 간격과 기능이 함께 개선될 때 보드 전체 Quartus Lite 비용을 확인한다. 이번 단계는 바이트와 ARM 비용 측정이며 새로운 보드 산출물이나 실기 표시율은 없다. 실기 기준은 MMC509 12.82fps다.

재현할 때 `measure_nes_map513.py`에 배포 ARM03/src와 delta231/test07을 전달한다. `check_nes_map513_mask.py`에 같은 ARM과 수집 결과를, `analyze_nes_map513.py`에 수집 결과·커널 결과와 원본 joint 경로를 전달한다. 선택 자료는 작업공간의 `probes/nes-map513/capture04`, `kernel05`, `analysis06.json`이다. 79개 선택 자료의 보관본은 같은 폴더의 `selected-evidence.zip`이며 SHA-256은 `146c7642142af6c0af6bdc8660612be58a31cfd1e0b8f1ae46401e94555e304d`이다. 이전 캡처의 프레임별 쓰기 목록 참조가 공유된 문제는 독립 커널 대조에서 발견해 수정하고 다시 수집했다.
