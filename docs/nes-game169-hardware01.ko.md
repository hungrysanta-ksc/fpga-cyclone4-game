# NES169 실기 — 첫 표시 요청의 무응답으로 화면 출력 실패

> 시간 정정: 사용자가 재확인해 종료까지 약13~14초, 총 실행 약4분이라고 정정했다. 아래 최초 관찰의 약60초보다 이 정정을 우선하며, 펌웨어13490ms와 부합한다. [다음170 시험판](nes-game170-ready.ko.md).

사용자는 로딩 화면이 그대로 유지되다가, 예상 로드 완료 시점부터 약60초 뒤 메뉴로 돌아왔다고 보고했다. **169의 연속 화면 개선 목표는 달성하지 못했다.** 168은7장 표시 뒤 E3로 종료됐지만,169는 첫 표시 요청부터 유효한 ACK를 받지 못했다. 같은 외관의 오류로 묶지 않는다.

## 확인된 범위와 미확인 원인

요청은 `01000000010000000c00000000000000`이다. `sink_trace_ack_valid=0`이므로 뒤의0으로 채워진 ACK는 실제 수신 응답이 아니다. 불일치 비트0도 성공을 뜻하지 않는다. 큰 화면 갱신의 SEAL이나 E2/E3 분할 처리까지 도달하지 않았으며, 이전 E3가 재발했다고 해석하지 않는다.

MCU가 ROM을 검증하고 FPGA의 첫 영상 후보를 받아 COMMIT까지 진행한 것은 확인된다. 반면 SNES가 첫 BEGIN에 응답하지 않아 표시 완료는0회다. 따라서 게임 파일 자체를 전혀 읽지 못한 실패보다 **SNES 표시 프로그램 기동 또는 첫 패킷 통신 경계의 실패**를 우선 조사한다. 이것만으로 전체 게임 실행 정상, SNES CPU 정지, 리셋 해제 실패, 사운드 고장을 확정할 수는 없다.

하위 exchange는 초기 F6 상태/CRC·busy 검사, 패킷 전송, 응답 상태 검사, 최대65536회 대기로 구성된다. 로그에는 어느 검사에서 실패했는지와 마지막 F6 원문이 없다.67709회 통신·1076731바이트는 응답 대기 소진과 부합할 가능성이 있지만, 그것만으로65536회 소진을 확정하지 않는다. guard/IO 오류는 먼저 기록되면 DISPLAY로 덮지 않는 구현이므로, native_result5는 정상60초 종료 코드와 다르다. 현재 오류 코드가 구분하지 못하는 하위 사유는 다음 최소 보강의 후보다.

진행 기록0~99는 연속이고 시각도 단조 증가한다. DISPLAY_NEXT231680ms→DISPLAY_STOPPED245170ms는13490ms이며 MENU_PREPARED248340ms다. 이는 준비·정지를 포함한 펌웨어 tick 구간으로 검증된 실측 시간이 아니다. 사용자 약60초 관찰도 그대로 보존한다. 양자의 차이를 곧바로 시계 고장으로 단정하거나 정상60초 종료로 분류하지 않는다.

## 이번에 대조한 구현·산출물

- 168 대비 MCU의 RUN·리셋 세션·sink transport·실패 기록 등6개 핵심 파일은 바이트가 같다.
- 169 compact ROM4096바이트와 Quartus 갱신 MIF가 일치한다. 실제 bus의 주소 선택 규칙으로 복원한 전체32768바이트가 Mesen 검사에 사용한 SFC와 일치하며, 리셋 벡터는008000이다.
- 첫256바이트의 부트 코드 변경은 WRAM 복사 길이2651→3154에 해당하는2바이트뿐이다. 코드가 저장 영역을 넘는 단순 길이 문제는 이 대조에서 발견하지 못했다.
- CDB가 해당 MIF를 처리했고 ASM/CPF가 성공한 기존 로그를 확인했다. 패키징된 FPGA 파일을 풀면 생성 RBF와 같다. **RBF 내부 ROM 비트 추출이나 실기 ROM readback을 수행한 것은 아니므로 실제 실행 바이트까지 증명한 것은 아니다.**

기존169의 실제65816/C 파일 mailbox 검증은 분할 전송 알고리즘의 근거로 남는다. 물리 카트리지 기동·SPI·전체 게임 검증을 대신하지 못하며 이번 실기 실패를 통과로 처리하지 않는다.

## 다음 작업

1. SNES 리셋 해제→벡터/부트 ROM 읽기→WRAM 복사→초기화→첫 BEGIN ACK의 실제 연결을 확인한다. stage0/flags0은 우선순위 근거이며 `screen_telemetry_trusted=0`과 관측 한계를 함께 유지한다.
2. 169 ROM 갱신·실제 실행 이미지 경계를 먼저 검증한다. 공통 board ID74와 MCU의169 표시는 실기 SNES ROM의 내용 해시가 아니므로 특정 비트스트림 실행을 단독 증명하지 못한다. 기존 자료로 통신 실패를 나눌 수 없을 때만 최초 exchange 실패 위치와 마지막 F6 상태를 기존 종료 TXT에 최소 추가한다. 무조건 대기/전송 상한 증가, 오류 검사 제거, 임의 성공 ACK는 하지 않는다.
3. 확인된 차이에 대한 최소 검증 후 수정 시험판으로 SMB3 실기에 복귀한다. 분할 갱신의 실제 효과·연속 AV는 여전히 미완료다. 다음은 장기 플레이/오류·본체 리셋 로그, 이후 입력 유지 순서다.

이번에는 분석·기록만 변경했다. 새 펌웨어·FPGA·ZIP은 만들지 않았다. 같은169 재시험·추가 영상·044 복원·무변경 FIT는 요청하지 않는다. 세이브 SRAM·GBC·164와 이전 완료 검증 파일을 보존한다. 원본 TXT는 비공개 보관하며 [전체 필드·시간·해시·산출물 대조](../analysis/game169-hardware01-verification.json)를 함께 남긴다.
