# 911의 E9 선행 발행과 첫 팔레트 32B

## 목표

971에서 팔레트 선행 발행으로 잃은 E9 공급 시각을 회복하고, 실제 ARM 팔레트 생성과 타일 공급을 겹쳐 911 공개와 912 최종 ACK를 앞당길 수 있는지 확인했다.

## 작업내용

MMC966 ARM의 OBJ 계산 완료 시점에 plan 레코드 14개와 END가 한 E9에 들어간다. 기존 코드는 14개부터 이 발행을 미뤘다. 972에서는 원래의 바이트 한도·CRC·큐 수락·STOP 검사를 유지하고 END를 15번째 레코드로 붙였다. 두 번째 후보는 첫 E9 발행 완료 뒤, map 전송이 없고 raw 행이 하나인 경우에만 확정된 팔레트 앞 32B를 같은 SPI로 보낸다. 65816이 받는 팔레트 범위는 원래와 동일하다.

기존 MMC966 ARM과 두 후보를 빈 캐시에서 같은 ROM 허가 일정·부팅 위상으로 각각 905–912까지 실행했다. ARM의 팔레트 쓰기를 추가 관측한 실행에서는 송신 원본 32B를 재구성하고, 계측 전후 SPI·타일 생산·65816 이벤트와 실기 형식 BIN이 일치하는지 확인했다.

## 성과

각 쌍은 위상 1 / 2 순서다. E9와 첫 팔레트는 911 BEGIN부터 발행 시작까지이며, ACK 변화는 같은 위상의 MMC966 대조군 기준이다.

| 조건 | E9 발행 | 첫 팔레트 발행 | 910→911 간격 | 912 최종 ACK |
|---|---:|---:|---:|---:|
| MMC966 대조군 | 8.999 / 9.048ms | 10.589 / 10.638ms | 2 / 2 VBlank | 기준 |
| E9만 선행 | 8.792 / 8.841ms | 10.589 / 10.638ms | 2 / 2 VBlank | 동일 / 6.0µs 빠름 |
| E9 선행 + 첫 32B 발행 | 8.794 / 8.843ms | 9.497 / 9.546ms | 2 / 2 VBlank | 9.9µs 빠름 / 8.8µs 늦음 |

두 후보 모두 908을 기존 VBlank의 245선에 표시했다. 결합 후보에서 첫 32B에 대한 마지막 ARM 쓰기는 E9 전송 종료 후 275.34 / 275.32µs였다. 이 시점에는 16B BG와 32B OBJ가 이미 준비됐고, 마지막 384B OBJ는 E9 종료 후 802 / 818µs에 준비됐다. 빈 캐시로 출발한 이 연속 실행에서도 911 자체의 새 CHR 수요 ROM 허가는 두 위상 모두 0회였다. 이 구간에서 겹친 것은 팔레트 계산과 타일 생산이다.

결합 후보의 마지막 OBJ가 포트 모델에 보인 뒤 ARM이 해당 E1을 시작하기까지는 대조군 1.284 / 1.284ms에서 2.039 / 1.930ms로 늘었다. 사이에 앞선 OBJ의 E1과 팔레트의 후속 세 거래가 있었다. SEAL 수락부터 독립 검사·업로드·공개에 드는 비용을 그대로 적용하면 직전 VBlank 종료까지 부족한 시간은 2.956 / 2.948ms였다. 이는 당시 DMA 일정으로 계산한 근삿값이다.

두 후보 모두 두 위상에서 8개 RGB 화면이 대조군과 일치했다. 위상 1에서 각 후보에 911 검사 중 STOP과 잘못된 SEAL 세대를 넣었고 각각 0xE4와 0xE0으로 끝나며 910 화면이 보존됐다. Flash는 대조군과 E9 단독이 212,460B, 결합 후보가 212,808B로 한도 212,992B 이내였다. 이 실험은 ARM·65816 실행과 FPGA 공급 모델의 결과다. 실기 FPS·메뉴 복귀나 새 RTL FIT·STA는 측정하지 않았다.

## 후속작업

MMC966을 비교 기준으로 유지한다. 다음에는 마지막 384B OBJ가 보인 뒤 ARM이 동일 token을 처음 확인한 E8과 해당 E1 발행을 대조해, 기다린 시간 중 후속 팔레트 전송과 앞선 뱅크 반환이 차지한 몫을 가른다. 그 구간만 줄여도 2.95ms를 전부 확보할 수 없으므로 OAM·section 5의 마지막 발행과 SEAL 수락을 함께 비교한다. [두 위상 클록·패킷·독립 검사 결과](../analysis/palette972-results.json)

재현에는 971의 동일 조건 대조군과 MMC966 link가 필요하다. `nes_plan_palette972.py prepare TEMP`와 `--prefix`로 각 작업 폴더를 만든 뒤 `build_nes_trial577.ps1`로 해당 link를 빌드한다. 각 후보에서 `run TEMP --phase 1/2`를 실행한다. `check_nes_palette972.py observe TEMP`로 같은 위상과 후보의 쓰기를 계측한다. `bad_seal`·`stop_decode`는 위상 1에서 후보별로 실행하고 마지막에 `report TEMP --out analysis/palette972-results.json`으로 집계한다.
