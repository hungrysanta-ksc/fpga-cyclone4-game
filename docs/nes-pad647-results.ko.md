# 647 · 955의 1,100 B 패딩 복원과 표시 경계

실기 기준은 MMC643이다. 65816이 같은 뱅크에 이미 복원한 패딩을 재사용하면 개별 명령의 시간이 약 75% 줄었다. 955의 상대 표시 간격은 두 위상 모두 4 VBlank였고, 954 대조와 951 공개선에서 각각 한 번씩 회귀했다. 후보는 실기 전달 대상에서 제외한다. [정량 결과와 추적 해시](../analysis/pad647-verification.json)

## 어디에 1.50 ms를 썼나

MMC643 ARM이 보낸 section 5의 op5는 offset 21부터 1,100 B를 0으로 채운다. payload는 2 B다. Mesen에서 실제 65816 명령 주소와 DMA 레지스터 쓰기, ACK doorbell을 관측했다. 수락 시각은 큐 head를 읽기 시작한 load다. 아래 구간은 겹치지 않으며 반올림 전 합계가 load→ACK와 일치한다.

| 955의 기준 소비 시간(ms) | 위상 1 | 위상 2 |
|---|---:|---:|
| 헤더·섹션·범위 검사와 주소 설정 | 0.228 | 0.223 |
| 복원 진입·종료 | 0.026 | 0.030 |
| STOP·입력 서비스 19회 | 0.370 | 0.373 |
| DMA 길이·잔량 등 청크 제어 | 0.302 | 0.310 |
| DMA 기동부터 다음 반복 진입까지 | 0.501 | 0.487 |
| coverage 기록·ACK 발행 | 0.073 | 0.073 |
| **합계** | **1.499** | **1.497** |

DMA는 64 B 17회와 12 B 1회였다. DMA 행에는 기동 뒤 CPU가 다음 반복으로 돌아오는 시간도 포함한다. 후보의 따뜻한 뱅크에서는 DMA 0회, STOP 서비스 1회, 정상 receipt·ACK까지 **0.368 / 0.368 ms**였다. cold 두 화면은 양쪽 뱅크에 1,100 B를 각각 썼다. 이어지는 51화면 모두 해당 뱅크의 이력을 사용했다.

## 실행 조건과 복구

65816은 순차 offset, 값·길이와 범위 검사에 성공한 section 5의 영(0) 패딩 중 끝이 1121인 구간만 기록한다. BEGIN에서 이번 기록을 비운다. 최종 표시 ACK가 성공하면 대상 뱅크의 시작 offset+1과 그 보수를 보관한다. 다음 재사용에는 비활성 뱅크, 유효한 표시 serial, 보수 일치, 기존 범위가 새 범위를 포함한다는 조건이 필요하다. 같은 section의 앞선 순차 쓰기는 이번 시작 offset에서 끝나며 이후 쓰기는 1121부터 가능하다. 실제 receiver가 이력과 범위를 판단하며 ARM 패킷 형식은 동일하다. 독립 oracle은 생략한 바이트도 매번 전부 읽어 확인한다. 이력은 해당 WRAM 영역을 소비자가 단독 소유한다는 전제가 있다.

실제 65816에서 양쪽 뱅크의 재사용 직전 STOP, 손상된 이력 때문에 전체 쓰기로 돌아간 뒤 64 B 시점의 STOP, 이력 한 비트 손상 뒤 18회 전체 복원을 시험했다. 취소된 화면은 발행되지 않았고 직전 화면 RGB가 일치했다. STOP 시 남긴 부분 기록·양쪽 뱅크 데이터를 다시 넣고 cold 시작한 시험에서 DMA 36회로 두 패딩 전부를 복원하고 map·HDMA·표시를 확인했다. 보드의 빈 캡처 회복(32→33, 97→98) 및 ARM 메뉴·base 복귀는 기존 시험의 RTL·펌웨어 해시를 대조했다. 새 실기 측정은 없다.

## 같은 시작 시각에서 본 전체 일정

각각 905–957의 53화면을 두 시작 시각(7,288,416 / 7,467,100 master clocks)에서 실행했다. 65816 부팅 뒤 첫 poll은 6,553,302→6,991,264 clocks로 늦어졌지만 두 시작 시각보다 앞선다. 실제 ARM ELF(CPI 2)·SysTick과 65816을 연결했고 SPI·두 슬롯·ROM 공급은 같은 모델과 위상을 사용했다. 패킷은 동적으로 발행한다. token·목적지·실제 바이트·전송 개수는 같고 credit에 따라 독립 명령의 순서는 달라졌다. 네 실행 모두 53회 최종 ACK와 RGB·map·CGRAM·OAM·HDMA 검사를 통과했다.

| 지표 | 위상 1 MMC643 → 647 | 위상 2 MMC643 → 647 |
|---|---:|---:|
| 직전 표시→955 패딩 수락(ms) | 42.034 → 43.163 | 42.246 → 41.999 |
| 패딩 개별 ACK→SEAL 수락(ms) | 4.534 → 5.010 | 4.536 → 5.005 |
| 직전 표시→955 SEAL 수락(ms) | 48.067 → 48.541 | 48.279 → 47.372 |
| 954 상대 표시 간격(VBlank) | 4 → 5 | 4 → 4 |
| 955 상대 표시 간격(VBlank) | 4 → 4 | 4 → 4 |
| 955 절대 표시 프레임 | 192 → 192 | 193 → 192 |
| 951–955 간격 합(VBlank) | 18 → 19 | 18 → 18 |
| 951–955 평균 간격(ms) | 59.834 → 63.079 | 59.870 → 59.829 |
| 957 마지막 ACK 차이(ms) | −0.167 | −16.436 |

위상 1의 954는 업로드 뒤 최종 표시를 추가로 한 VBlank 기다렸다. 위상 2의 955는 시작 이후 누적 표시가 한 프레임 앞섰지만 직전 화면과의 간격은 4회였다. 952 간격 4회·957 최종 추가 대기 0회는 양쪽에서 유지했다. 951 공개선은 위상 1에서 246→242, 위상 2에서 245→247로 이동했다.

955에서 패딩 ACK 뒤 후속 head가 아직 발행되지 않아 기다린 합이 1.562→1.981 / 1.534→1.950 ms로 늘었다. 후보에서 offset 1505의 240 B 테이블 패킷과 168 B SEAL payload 발행을 기다린 시간만 각각 0.908·0.991 / 0.897·0.982 ms다. 나머지 head 소비는 2.731 / 2.735 ms였다. 업로드 루틴의 첫 VBlank 대기 진입과 직전 225번 선 사이에 여전히 약 1.70 / 1.98 ms가 남았다. 이는 빔 정렬 차이이며 그대로 회수할 수 있는 시간으로 계산하지 않는다.

## 다음 작업과 재현

다음 대조에서는 패딩 단독 튜닝을 멈추고, 240 B 테이블과 SEAL의 ARM 준비 완료·발행 가능 credit·실제 SPI 시작/완료를 먼저 분리한다. 독립 검사에 필요한 데이터가 확정되는 시점을 사용해 후반 발행 대기를 줄일 수 있는지 본다. 상대 955와 957 마지막 ACK, 954 추가 대기와 951 공개선이 동시에 통과해야 한다.

ARM Flash는 기존 212,932 B다. 후보의 65816 실행 코드는 5,760→5,893 B, 이력 데이터는 +10 B다. 기존 5,120 B 물리 ROM에 재압축한 여유는 32→25 B였다. 새 FPGA FIT·STA나 보드 설치본은 만들지 않았다.

1. 635 client04를 입력으로 `tools/nes_pad647.py`를 실행한다. 637 변경을 적용한 중간 본문의 SHA-256을 MMC643과 대조한 뒤 ROM과 실행 주소표를 만든다.
2. [646 재현 조건](nes-tail646-results.ko.md)에서 `tools/test_nes_pad647.py --commit-pop-bound`를 MMC643과 후보 65816에 각각 사용한다. 두 모드 모두 reject643 arm01이다. 시작 시각을 위 표의 조건으로 고정하고 관측 결과를 `nes-pad647-{base,reuse}{1,2}`에 기록한다.
3. `tools/check_nes_pad647.py`에 후보 client, 기준 패킷 trace, Mesen 경로와 새 출력 폴더를 전달해 취소와 재시작을 검사한다. `tools/analyze_nes_pad647.py`로 네 일정, 동일 RTL의 빈 캡처 회복 증거, 동일 ELF의 메뉴·base 시험 및 새 guard 결과를 대조한다.
