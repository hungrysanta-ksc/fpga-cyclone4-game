# MMC930 · 마지막 두 OBJ의 준비와 뱅크 반환

실기 성능 기준은 MMC925를 유지한다. 세대 912에서 token 37(32B)의 반환을 앞당기는 실험과, 그보다 앞선 큰 OBJ를 OAM보다 먼저 처리하는 실험을 분리했다. 기준 ARM·65816 링크의 SPI 이벤트와 결과를 그대로 재현한 뒤 변경했다.

## 기존 캐시에서 128B 준비를 막은 뱅크

두 위상 모두 뱅크 두 개가 차서 생산자가 token 36의 반환을 기다렸다. 반환 **698 마스터클록(32.5µs)** 뒤에 마지막 128B OBJ(token 38)가 준비됐다. token 37은 그때도 소비 중이었다. 따라서 token 37 반환은 다음 E8 수락을 앞당길 수 있지만, 이미 준비된 token 38의 생산 시각은 앞당길 수 없다. 세대 912의 기존 캐시에서 실제 공급 모델의 일반·선행 PSRAM 허가는 모두 0회였다.

| MMC925 · token 37(32B) | 위상 1 | 위상 2 |
|---|---:|---:|
| FPGA 준비 → ARM 첫 유효 E8 응답 | 3.004ms | 2.991ms |
| E8 응답 → E1 발행 종료 | 0.144ms | 0.144ms |
| E1 종료 → 65816 헤더 수락 | 0.968ms | 0.977ms |
| 수락 → staging 첫 바이트 읽기 | 0.428ms | 0.427ms |
| 첫 바이트 → 마지막 바이트 읽기 | 0.013ms | 0.013ms |
| 마지막 바이트 → 뱅크 반환 | 0.035ms | 0.035ms |

## 발행 순서 세 가지의 비용

아래는 기존 캐시의 여섯 표시 간격 합과 912 최종 ACK다. ACK 차이에서 양수는 지연이다. 모든 후보는 타일을 읽거나 뱅크를 반환할 때 원래의 CRC·descriptor·identity 검사를 사용했다.

| ARM 후보 | 위상 1 / 2 표시 간격 합 | 위상 1 / 2 최종 ACK 차이 | Flash |
|---|---:|---:|---:|
| MMC925 | 13 / 13 VBlank | 기준 | 212,940B |
| OAM 채우기 전 기존 12회 대기 뒤, DMA 진행 표시가 없으면 타일 서비스 | 14 / 14 | +16.662 / +16.633ms | 212,964B |
| 같은 위치에서 1회 대기 뒤 타일 서비스 | 14 / 14 | +16.656 / +16.589ms | 212,964B |
| 큰 OBJ가 미반환이면 첫 OAM 데이터 앞에서 타일 서비스, 채우기 전 기존 대기 유지 | 13 / 13 | −0.049 / −0.099ms | 213,040B |

1회 대기는 직전 공개를 기준으로 token 37 반환을 2.508 / 2.307ms 앞당겼다. 그러나 910 입력의 마지막 D2가 캡처선을 7,153 / 8,856클록 넘겨 두 위상 모두 910→911 표시 간격이 2→3회가 됐다. 큰 OBJ를 먼저 처리한 후보는 두 위상 모두 910 캡처 마감을 지켰고 912 선행 DMA가 원본 112 / 48B에서 176 / 176B로 늘었다. 표시 간격 합은 그대로이고 Flash 한도는 48B 넘었다.

## 빈 캐시에서 처음 늦어진 ROM 읽기

빈 캐시에서는 세 후보 모두 두 위상에서 선행 DMA 496B와 표시 간격 합 16 VBlank를 유지했다. 최종 ACK 변화는 전체 여섯 비교에서 −0.019~+0.023ms였다.

token 37은 CHR 태그 6265의 행 0·1·2를 쓴다. 두 위상에서 이 태그의 행 3–7에는 이미 선행 ROM 허가가 있었고, 행 0–2는 소비자가 요청해야 했다. 첫 행 주소 `0x18790`의 **요청→허가만 12.414 / 12.349ms**였다. 뒤이은 두 요청은 각각 0.009ms 안에 허가됐다. token 38의 첫 일반 요청 대기는 두 위상 모두 56클록이었다. 같은 태그를 조회해도 필요한 행이 준비돼 있는지가 달랐다.

다음 검증은 태그 6265가 처음 수락된 시점에 행 0–2의 필요성을 이미 알 수 있었는지부터 확인한다. 이미 수락된 plan으로 알 수 있는 경우와, 태그의 나머지 행을 추측해 읽는 경우를 구분한다. 세 행을 앞당길 때 소비하는 공유 ROM 허가, 밀린 다른 타일, 910 캡처, 빈 캐시의 496B 선행 DMA, 두 위상의 912 공개·최종 ACK를 함께 비교한다.

## 검증과 재현

동일한 55–60초 클립에 MMC925의 실제 ARM·65816 명령과 공유 SPI·ROM·IRQ 모델을 사용했다. 실기 세대 1225의 물리 ROM 버스 시각을 직접 기록한 값은 없다. ROM 허가는 모델에서 실행한 거래이며, 별도 공급 추적의 전체 65816 이벤트와 일반 허가 목록을 계측 전 대조군과 비교했다.

1. `tools/nes_return930.py prepare MODE`로 `handoff`, `short`, `prefix`를 생성하고 기존 `build_nes_trial577.ps1`로 각 ARM 전체 링크를 빌드한다.
2. 각 후보와 대조군 `base`, 공급 추적 `supply`에 대해 `replay MODE TEMP PHASE [--cold]`를 실행한다. 수락·첫/마지막 읽기·반환·ACK를 같은 token에 연결한다.
3. 각 후보에 기존 `check_nes_supply905_arm.run(...,925,short_header=True)`, 후보 태그로 `nes_return920.guards`와 `nes_obj923.obj_stops`를 적용한다. SRAM D0 네 곳, 손상 CRC·descriptor·중복·잘못된 SEAL 거부, 복사/표시 중 STOP, OBJ의 마지막 바이트 STOP, base·메뉴 복귀 경로를 확인한다.
4. `tools/analyze_nes_return930.py TEMP analysis/return930-results.json`으로 여덟 화면의 RGB·타일·map·팔레트·section 5와 세 후보의 전체 일정을 대조한다.
