# 937 · OAM 준비 비용과 910 캡처 마감

936 batchfast의 전체 ARM 링크와 935 bounded 65816을 출발점으로 삼았다. ARM의 반복 구간 탐색만 교체한 `runs`에서 기존 캐시 두 위상 모두 밀집 여섯 간격 합 13 VBlank, 빈 캐시 두 위상 모두 15 VBlank와 SEAL 전 496B를 확인했다. 타일별 생산 무회귀 조건이 남아 있어 실기 기준은 MMC925를 유지한다.

## 같은 입력과 시작 위상에서의 결과

시간 차이는 21,477,272Hz master clock 기준이다. 음수는 912 최종 ACK가 앞당겨졌다는 뜻이다. 910 여유는 마지막 COMMIT의 D2와 목표 캡처선 사이의 시간이다.

| 캐시·위상 | 여섯 간격 936 → 937 runs | 909 공개 직전 VBlank의 선행 DMA | 910 캡처 여유 | 912 ACK 차이 대 936 | 912 ACK 차이 대 MMC925 |
|---|---:|---:|---:|---:|---:|
| 기존 1 | 13 → 13 | 624 → 592B | 90.65µs | −0.037ms | −0.221ms |
| 기존 2 | 14 → 13 | 48 → 624B | 38.18µs | −16.620ms | −0.257ms |
| 빈 1 | 15 → 15 | 528 → 528B | 14.306ms | −0.005ms | −16.639ms |
| 빈 2 | 15 → 15 | 528 → 528B | 14.078ms | −0.005ms | −16.620ms |

기존 캐시 위상 2에서 936은 235선에 OAM을 수락했다. 937 runs는 수락된 32B·384B OBJ를 238·243선에 먼저 DMA하고 254선에 OAM을 수락했다. 910의 첫 D1은 936보다 0.569ms 빨랐다. 위상 1에서는 오히려 0.204ms 늦었으나 마지막 COMMIT D2는 0.049ms 빨라 캡처선을 지켰다. 912의 빈 캐시 496B는 두 위상 모두 기존 여섯 VRAM 목적지에 기록됐다.

## 대기 연장과 준비 비용의 차이

- 긴 plan의 OAM 대기를 12회에서 24회로 늘린 대조군은 909의 후속 OBJ DMA를 회복했지만, 910 캡처를 0.737 / 1.437ms 놓쳤다. 기존 캐시가 14 / 14회로 끝났다.
- 64B 반복 word를 찾는 ARM `span_piece`는 기존에 후보 시작 바이트마다 같은 데이터를 다시 비교했다. 단순 순방향 탐색은 기존 캐시 13 / 13을 달성했지만 빈 캐시 위상 2에서 마지막 32B가 밀려 선행 DMA가 464B에 그쳤다. 불일치 위치로 건너뛰는 `skip`은 496B를 회복했으나 935 대비 다른 타일의 최대 지연이 0.553ms였다.
- `runs`는 64B 미만을 즉시 반환하고, 시작점의 2B 반복 길이를 한 번 계산한다. 긴 반복이면 그 길이를 반환하고, 아니면 처음 불일치한 쌍부터 두 칸 전 바이트와 연속해서 일치하는지를 센다. 홀수 시작과 239번째 바이트의 반복도 찾는다. 전체 링크는 **212,960 / 212,992B**다.
- 두 구현에서 추출한 C 함수를 126,192개 입력에 대조했다. 네 재생 각각에서 일반 전송 명령 132개의 세대·section별 순서, 오프셋, 길이와 내용이 동일했다. 타일을 포함한 최종 출력은 별도로 화면·섹션·VRAM 기준에 대조했다.

## 남은 회귀와 다음 작업

935 대비 37개 비대상 타일 묶음 중 늦게 준비된 수는 기존 캐시 13 / 8, 빈 캐시 8 / 8이다. 기존 캐시에서 가장 늦어진 것은 두 위상 모두 909 token 24의 352B OBJ로 8,878 / 4,726클록(0.413 / 0.220ms)이다. 빈 캐시 위상 1의 912 최종 ACK도 935보다 28클록(1.30µs) 늦고 위상 2는 같았다.

기존 캐시 위상 2에서 직전 token 23(32B)은 생산 14,602,579, 첫 유효 E8 14,686,773, 반환 14,701,870클록이었다. token 24(352B)는 생산 14,679,434, E8 14,711,671, 반환 14,733,366클록이었다. 두 위상 모두 token 23 준비부터 token 24 준비까지 OBJ용 신규 ROM 요청·허가는 0건이었다. 352B가 준비되는 시각은 935·936·937 여섯 재생 모두 앞선 token 22(64B)의 실제 뱅크 반환 뒤 정확히 2,418클록이었다. 위상 1에서 token 22의 ARM 발행은 935보다 9,014클록 빨랐지만 65816 수락은 8,882클록 늦었다. 발행→수락 구간이 415→18,311클록으로 늘었고, 그사이 65816이 반복 OAM 패킷(op 8, section 4)을 반환했다. 수락 뒤 복사·반환 비용은 10,940→10,936클록이었다. 다음에는 이 OAM과 이미 발행 가능한 64B OBJ의 큐 진입 순서를 조정해 본다. 위상 2에서는 token 22의 생산 자체도 3,416클록 늦어 두 원인을 분리해야 한다. 기존 캐시 위상 2에서 확보한 캡처 여유 38.18µs와 빈 캐시 496B를 함께 확인한다.

## 재현과 검증 범위

1. 936 batchfast와 935 bounded를 준비한 뒤 `tools/nes_oam937.py prepare MODE TEMP`와 `tools/build_nes_trial577.ps1 ../probes/nes-oam937/MODE/link`로 ARM 전체 링크를 만든다. MODE는 double, linear, skip, runs다.
2. `tools/nes_oam937.py replay MODE TEMP PHASE CACHE`로 위상 1·2와 warm·cold를 각각 재생한다. `tools/check_nes_span937.py MODE`로 탐색을 바꾼 세 후보의 패킷 경계를 원본과 대조한다.
3. `tools/nes_oam937.py proof runs TEMP`와 `guards runs TEMP`로 정상 부팅, SRAM D0 네 경로, CRC 거부, STOP·base·메뉴 복구와 65816 독립 검사를 확인한다. 후속 32B가 선택되는 순간의 STOP과 새 패킷 우선은 두 빈 캐시 위상에서 따로 검사한다.
4. `tools/analyze_nes_oam937.py TEMP analysis/oam937-results.json double linear skip runs`로 링크 해시·패킷 일치·클록·주입 결과를 집계한다. 실제 ARM 바이너리와 65816 ROM을 재생했고, 공유 ROM·SPI와 보드 I/O에는 모델을 사용했다. 실기 FPS는 이번 측정 범위 밖이다.
