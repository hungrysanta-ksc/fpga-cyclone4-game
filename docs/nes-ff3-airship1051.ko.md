# FF3 비공정 이동과 CHR RAM 갱신

FF3 1050 실기에서 사용자가 전투·전환 점선 수정과 X/Y 연사를 확인했다. 첨부한 비공정 슬롯은 순번 13이다. 이 슬롯을 원본 한글판으로 복원한 뒤 23프레임 동안 기다리고 24~88프레임에는 오른쪽을 눌러 이동했다. 같은 세이브에서 정지·비행 구간을 분리했다.

## 측정 결과

비행 중 화면에 쓰인 배경 타일 64개 중 47개가 CHR RAM의 첫 1KiB 페이지에 있었다. 게임이 프레임마다 타일 두 개에 한 바이트씩 써서, 1050은 이 페이지의 이전 타일을 양쪽 VRAM 뱅크에서 모두 무효화했다. 실제 쓰기는 같은 128B 범위에 모였고 여기에 속하는 배경 타일은 5개였다. 다음 표는 같은 PPU 입력과 실제 ARM 링크를 재생한 결과다. 처음 두 화면은 두 뱅크를 처음 채우므로 따로 제외했다.

| 장면 | 비교 화면 수 | 1050 타일 DMA | 1051 타일 DMA |
|---|---:|---:|---:|
| 비공정 정지 | 4 | 3,136B | 640B |
| 비공정 비행 | 6 | 4,864B | 832B |
| 마을 보행 | 4 | 3,136B | 768B |
| 필드 보행 | 4 | 3,648B | 576B |

비행 6장에서 타일 명령이 296→44개, E9 명령 데이터가 2,056→292B로 줄었다. 실제 SPI 조회·패킷 헤더는 별도다. 연속 비행 28장의 모든 CHR 쓰기를 합산해 네 장마다 표시하면 두 뱅크 준비 뒤 5개 화면의 DMA는 3,840→480B였다. 다섯 장마다 표시하면 4개 화면에서 3,328→640B였다. 이전 ARM과 1051의 페이지 모드 및 범위 모드 사이에서 map·OAM·CGRAM·HDMA와 표시 슬롯의 타일 정의를 대조했다.

## 구현과 다음 측정

FPGA가 캡처 사이의 물리 CHR RAM 쓰기 주소를 추적한다. 모든 쓰기가 하나의 128B 범위에 속할 때만 기존 길이의 헤더에 범위 번호를 싣는다. 둘 이상에 흩어지면 기존 페이지 마스크를 보낸다. 부팅·STOP·캡처 취소 때는 페이지 기준으로 복구한다. ARM은 양쪽 출력 뱅크에 같은 규칙을 적용한다. 65816 프로그램과 강제 저장 파일 형식은 1050과 같다.

비행 6장의 계획 함수는 868,560→865,032명령이었다. 타일 전송을 줄여도 화면 전체에 대한 ARM 계획 비용이 남는다. 마지막 비행 화면에서 계획 함수 본체에 93,130명령이 걸렸다. 다음에는 같은 슬롯·동선에서 입력 완료→첫 타일 발행, 마지막 타일 반환→SEAL, SEAL→표시·최종 ACK를 분리해 어느 구간이 VBlank를 놓치는지 비교한다. 모험도처럼 CHR ROM을 쓰는 게임에는 공통 ARM 계획·출력 경로의 개선을 별도로 대조한다.

## 실기 비교

Quartus Lite 전체 FIT에서 15,273/15,408 LE, 963/963 LAB, 56/56 M9K를 사용했다. 클록 허가 동기화 레지스터를 기존에 통과한 위치에 두고, ROM 로더의 타이머 허가를 감소·재적재 데이터와 분리했다. 내부 STA 57개 검사의 최소 슬랙은 +0.166ns, 기존 외부 PSRAM 접근 예산의 최소 여유는 3.407ns였다. SRAM 핀 지연은 세 코너에서 별도로 추출했다. 실제 로더 RTL의 512KiB 적재·START·STOP, 링크된 ARM의 네 저장 슬롯과 base 복귀가 통과했다. ARM Flash는 212,964/212,992B다.

검증을 통과해 제공한 ZIP의 `sd2snes` 폴더를 SD 루트에 병합한다. 기존 FF3를 선택하고 비공정 슬롯을 불러온다. 같은 위치에서 잠시 멈췄다가 같은 방향으로 비행하고 퀵메뉴의 EXIT TO MENU로 종료한다. 로그는 `nes-game-last-ff31051.txt`, `nes-progress-ff31051.txt`, `nes-frame-ff31051.bin`이다. 화면 속도와 지도·기체·움직이는 지형의 갱신을 함께 확인한다. 위 표는 실기 FPS를 측정한 값이 아니다.
