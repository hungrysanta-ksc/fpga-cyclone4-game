# NES 939 · 909의 32B OBJ 반환과 후속 뱅크 공급

## 처음 늦어진 구간

935 bounded와 938 fit의 동일한 token 20을 대조했다. 단위는 SNES master clock(21,477,272Hz)이다. E8과 E1은 ARM SPI 거래 종료, 65816 수락은 해당 큐 head를 읽은 시각, 뱅크 반환은 마지막 실제 읽기 뒤 consume strobe다. 공개와 최종 ACK는 별도로 검사했다.

| 기존 캐시 | FPGA 준비→첫 유효 E8 | E8→E1 | E1→65816 수락 | 수락→뱅크 반환 |
|---|---:|---:|---:|---:|
| 위상 1 · 935 → 938 | 51,536 → 56,685 | 3,082 → 3,086 | 553 → 880 | 10,210 → 10,214 |
| 위상 2 · 935 → 938 | 52,390 → 56,545 | 3,082 → 3,085 | 1,657 → 1,049 | 10,208 → 10,214 |

위상 1은 token 20 생산 자체가 이미 1,398클록 늦었다. 그 이후에는 첫 유효 E8까지의 대기가 5,149클록 늘었다. 위상 2는 생산 시각이 같고 이 대기만 4,155클록 늘었다. 직전 token 19의 65816 head ACK부터 token 20의 첫 유효 E8까지는 938에서 12,782/12,648클록이었다. 위상 1에서 935는 이 구간에 212B OAM prefix의 E1을 겹쳤고 938은 token 20 제출 뒤에 이를 보냈다. 준비→발견 동안 938은 두 위상 모두 E0를 여덟 번 사용했다. 반복 OAM fill은 이 prefix와 별개의 명령이다.

## 발행 실험

기존 ARM 링크에 두 변경을 따로 적용하고 결합했다. 첫째는 짝수 길이 패킷에서 2B 주기 반복을 찾을 때 `memcmp(data, data+2, n-2)`로 같은 범위만 검사하는 변경이다. 둘째는 직전 OBJ의 응답을 기다릴 때 고정 128µs 휴지기를 줄이는 변경이다. CRC, token, 실제 큐 반환, STOP guard를 매 거래에서 계속 확인한다. 팔레트와 OAM 데이터 및 패킷 경계는 네 재생 모두 938과 대조했다.

- `credit`은 팔레트 서비스 사이에 허용하는 일반 패킷을 줄였지만 기존 캐시가 14/14회가 되었고 910 캡처선을 놓쳤다.
- `words`만으로는 기존 캐시 14/14회였다. 32B 직후의 휴지기까지 줄인 `joint`는 기존 13/13회, 빈 496B·15/15회였으나 Flash가 8B 초과했다. 같은 처리와 압축한 메뉴 마커를 쓴 `marker`는 212,972B에 들어갔지만 빈 위상 1의 912 ACK가 935보다 28클록 늦었다.
- `tile`은 실제로 큐에 발행한 마지막 section이 OBJ일 때 휴지기를 줄인다. E0 조회 수와 각 뱅크의 반환 시각을 따로 기록했다. `tail`은 section 5까지 이를 확대했지만 빈 위상 2에서 선행 DMA가 464B로 줄었다.

- 935의 212B OAM prefix 겹침을 복구하려고 prefix에 네 번째 큐 credit까지 허용한 대조군도 재생했다. token 20의 첫 유효 E8은 당겨졌지만 기존 14/14회, 빈 위상 2의 선행 DMA는 464B였고 Flash도 12B 초과했다.

## 전체 링크 결과

938의 간격과 935의 최종 ACK 조건을 함께 충족한 후보는 `tile`이다. ARM 212,984/212,992B이며 정적 65816 ROM은 935와 같다. 최종 링크에서 SRAM D0 네 곳, CRC 거부, 잘못된 descriptor·중복·SEAL 거부, 복사·표시 중 STOP, 32/352B 마지막 바이트 STOP, 부팅·base·메뉴 복귀가 통과했다. 빈 캐시의 두 위상 모두 32B 후속 DMA 직전 STOP과 새 head 우선도 통과했다. 아래 단축량은 token 20 반환과 64B·352B 준비는 938 대비, ACK 및 다른 타일 공급은 935 대비다. 네 조건 모두 token 20 반환 단축량이 다음 64B 준비 단축량과 정확히 일치했다.

| 캐시·위상 | token 20 반환 단축 | 64B / 352B 준비 단축 | 910 캡처 여유 | 여섯 간격 합 | 912 SEAL 전 DMA | 912 ACK 단축 | 935보다 늦은 묶음 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 기존 1 | 140.89µs | 140.89 / 200.40µs | 38.55µs | 13 | 112B | 16.682ms | 10/37 |
| 기존 2 | 340.82µs | 340.82 / 359.17µs | 140.57µs | 13 | 48B | 16.624ms | 7/37 |
| 빈 1 | 104.02µs | 104.02 / 604.73µs | 15.60ms | 15 | 496B | 4.19µs | 8/37 |
| 빈 2 | 241.19µs | 241.19 / 736.78µs | 15.49ms | 15 | 496B | 18.53µs | 4/37 |

기존 캐시에서 준비→첫 유효 E8은 938의 56,685/56,545클록에서 50,772/49,691클록으로 줄었다. 이 구간의 E0는 8/8회에서 10/10회로 늘었다. 같은 구간에서 65816 수락→반환은 약 10,200클록이다. 반환 확인을 더 자주 하여 E8을 앞당겼고, 938 대비 여섯 표시 간격 합은 네 조건 모두 같았다. 912 최종 ACK의 938 대비 변화(음수는 단축)는 기존 위상 1·2에서 −16/+496클록, 빈 위상 1·2에서 0/−160클록이었다. 기존 위상 2는 23.09µs 늦었다.

개별 공급 조건은 미달이다. 기존 위상 1의 최대 지연은 909 token 22의 3,856클록(180µs), 빈 위상 2는 911 token 28의 3,205클록(149µs)이다. 기존 위상 1에서는 909 첫 BG(token 14)가 이미 3,085클록 늦었다. 935·938·939 세 실행에서 이 BG와 빈 위상 2의 911 첫 BG는 각각 첫 E9 종료 후 정확히 106클록에 준비됐다. 기존 위상 1의 909는 입력 시작부터 935보다 3,081클록 늦었다. 빈 위상 2의 911은 입력 시작이 4,018클록 빨랐지만 planner 진입 때 3,205클록 늦었다. 다음 대상으로 908 공개→909 입력 시작과 911 입력 시작→planner 진입(7,223클록 증가)을 구분한다. 비교 집합은 앞선 단계와 동일하게 912의 대상 token 32·35를 제외한 37개다.

`retired`는 기존 위상 2에서 37개 모두 935 이내였지만 빈 위상 1의 최종 ACK가 134클록 늦었다. 이 결과와 `tile`의 결과는 각각 별도의 전체 링크에서 얻었다. 실기 기준은 MMC925를 유지한다.

## 재현

938 fit ARM과 935 bounded 65816 산출물을 사용한다. `tools/nes_head939.py prepare MODE TEMP`로 소스를 만들고 `tools/build_nes_trial577.ps1 ../probes/nes-head939/MODE/link`로 전체 링크를 생성한다. `replay MODE TEMP PHASE CACHE`는 실제 ARM과 65816을 시작부터 재생하고 905–912의 화면·VRAM·수신 및 공개 순서를 대조한다. ROM 포트·SPI·보드 I/O는 모델이다.

선정 후보의 `proof`와 `guards`는 부팅·SRAM D0 네 경로·손상 CRC·STOP·base/메뉴 복귀 및 32/352B의 마지막 바이트 취소를 검사한다. 빈 캐시 두 위상에서 후속 32B DMA를 선택하는 경계의 STOP과 새 패킷 우선도 검사한다. 메뉴 마커를 바꾼 후보에는 `dispatch`를 추가로 사용한다. `tools/analyze_nes_head939.py TEMP analysis/head939-results.json MODES...`는 각 최종 링크 해시, token별 실제 수락·반환, 두 기준과의 차이를 집계한다.
