# NES226 실기 결과: 스크롤 개선 확인, 전송 비용이 다음 과제

사용자는 첫 레벨 스크롤의 확실한 개선, 정상 사운드와 메뉴 복귀를 보고했다. 영상의 첫 레벨 이동과 로그의 60초 실행·표시 완료 증가도 이에 부합한다. **226의 계산 최적화는 유효한 진전으로 기록하되, 60fps나 정상 플레이 수준의 스크롤 성능을 달성한 것으로 판정하지 않는다.** 이번 결과만 PR124에 추가하며 새 펌웨어는 만들지 않는다.

## 작업 의미

일반 배경 셀의 반복 계산을 생략한226이 실제 게임 실행 중에도 계획 계산 비용을 줄였다는 근거다. 이제 수신·타일 완료·SNES 전송 비용이 상대적으로 더 크게 남는다. 디버그 항목을 확장하거나 계산 최적화만 반복하기보다, 실제 스크롤의 전체16.67ms 예산을 맞추는 다음 구현을 선택하는 자료로 사용한다.

## 실행과 종료

- ROM393216B 적재·대조 일치, verified/end_accepted=1. ROM/RUN/STOP 오류0, fault_context_valid=0.
- DISPLAY_NEXT231230ms → DISPLAY_STOPPED291290ms: **60060ms**. MENU_PREPARED294490ms이며 사용자의 메뉴 복귀 보고와 영상63초 부근의 메뉴로 확인된다.
- native_frames=452, 마지막 displayACK는59850ms/gen745. geometry BEGIN/END/COMMIT은 각각453, ABORT0이다. geometry COMMIT은 화면 표시 완료와 다르다.
- 종료 원인은 native_result=1, 즉60초 deadline이다. 이번에는 마지막 SEAL 완료 대기 중 guard가 중지시켜 sink/window_error=2가 남았다. 선택 소스의 window io()에서2는 **다음 I/O 전 guard 거부**, CRC/ACK 불일치 코드가 아니다.
- 마지막 요청은 SEAL/op3, sequence35, serial453, generation747, payload168B. sent13035/retired13034로 종료 스냅샷에서1건이 미완료다. ack_valid=0의0-filled ACK는 수신한 잘못된 ACK라는 증거가 아니다. gen747이 이후 표시됐는지는 이 로그로 확인할 수 없다.
- receiver/video/plan 오류0, failed_transfers=0. 첫 deadline을 유지하는 runtime과 마지막 요청·카운터가 일치하므로 이번 sink2를 별도의 중간 게임 다운으로 분류하지 않는다. 모든 패킷이 완료됐다고 기록하지도 않는다.
- screen_error=169/A9는 SPC 초기화 결과이고 unmute_confirmed=1이다. screen_frames=0은 신뢰하지 않는 기존 계측이다. 소리는 사용자 확인을 근거로 정상 기록한다. 이번 영상 소리를 별도로 청취한 것은 아니다.
- 입력 로그는 완료된8비트 읽기 값이 바뀐127회이며, 실제 버튼 클릭127회를 뜻하지 않는다. 이번 사용자가 입력 유지 품질을 별도로 판정한 것은 아니다.

## 225와 비교

| 항목 | 225 | 226 |
|---|---:|---:|
| 실행 구간 | 60.07초 | 60.06초 |
| displayACK 완료 | 401회 | 452회 |
| 전체 완료 평균 | 6.68회/초 | 7.53회/초 |
| 완료 간 최대 기록 간격 | 400ms | 370ms |
| 수신 누적 | 19.68초 | 22.40초 |
| 계획 단계 전체 | 21.46초 | 16.00초 |
| 계획 계산, callback 포함 | 12.80초 | 7.17초 |
| SEAL·표시 ACK 단계 | 18.29초 | 21.11초 |

완료1회로 나눈 계획 계산은31.92→15.86ms, 전체 계획 단계는53.52→35.40ms다. 반면 수신은49.08→49.56ms, SEAL은45.61→46.70ms로 거의 그대로다. 표시 완료가 늘면서 수신·SEAL의 총합이 커진 것만으로 이 단계의 회귀를 주장할 수 없다.

완료 횟수는12.72% 증가했지만 **서로 다른 플레이 경로·장면·죽음 횟수를 가진 전체 실행 비교**다. 정확한 스크롤 FPS 증가율이나 같은 장면의 인과 효과로 해석하지 않는다. 전체7.53회/초는 로그의 표시 완료 평균이며 NES 게임 실행 속도나 TV 주사율이 아니다. 계산 최적화 효과의 방향은 실기 결과와 부합하지만 순수 CPU 사이클 개선율을 측정한 것도 아니다.

## 새 단계 계측으로 좁혀진 다음 대상

226의12개 bin 각각에서 BEGIN + planner + finish = 전체 plan이 일치한다.

- BEGIN0.88초: 프레임 준비와 sink 시작.
- planner7.17초: 계획 계산과 내부 callback0.64초 포함. 단순 차6.53초도 정확한 CPU 계측은 아니다.
- finish7.95초: END 처리, 타일 생성 완료 및 bulk service/drain 등을 포함한다. 순수 FPGA 연산 시간으로 부르면 안 된다.

BEGIN만 줄여서는 효과가 작다. 수신22.40초와 SEAL21.11초, finish7.95초를 함께 줄여야 한다. 기록된 D1 payload만 현재2.625MHz SPI에서 완료1회당18.00ms, 전체 계수된 SPI는53.66ms에 해당한다. 이미16.67ms를 넘으므로 현 직렬 경로에서 ACK 조회 몇 개나 계산만 줄이는 것으로60fps를 보장할 수 없다. 이는 현재 형식·트래픽의 환산값이며 NES 자체의 불가능성 증명이나 다른 전송 구조의 하한은 아니다.

다음 구현 우선순위는 다음과 같다.

1. 실제 스크롤에서 수신하는 geometry/metadata와 SNES로 보내는 metadata/SEAL 경로의 반복 전송·직렬 대기를 줄일 대상을 선택한다. 기존 원시 입력/동일 스크롤 fixture로 전후 전송량·총비용을 비교한다.
2. finish의 source 생성/bulk drain과 위 경로의 겹쳐 처리 가능성을 함께 검토한다. E8 횟수를 메모리 miss나 대기 시간으로 대체하지 않는다.
3. source epoch, row/alt/mask, 두bank의 유효성, 마지막 실제 displayACK, 공통 STOP, 오디오·입력을 보존한다. 느린 소비자에게 사용 중인 버퍼를 덮어쓰는 식으로 확인 절차를 제거하지 않는다.
4. 최소 경계 검증 후 첫 레벨 스크롤 실기로 판정한다. 이번과 같은226/044 재시험이나 새 계측만을 위한 별도 시험·FIT 반복은 하지 않는다.

ARM 여유1792B와 미래 mapper 확장 여지를 고려한다. 저장SRAM·GBC164·기존 봉인 자료는 유지한다. 새로운 큰 캐시 또는 FPGA 변경이 필요하다고 이번 로그만으로 단정하지 않는다.

## 영상과 측정 한계

63.97초 영상에서2fps로128개 샘플을 추출했고,1초 간격64개 장면을4개 contact sheet로 검토했다. 영상0–2초 오프닝,3–4초 선택,5–9초 월드맵,10–11초 진입,12–42초 첫 레벨,43초 사망/이탈,44–46초 월드맵,47–48초 재진입,49–60초 첫 레벨,61–62초 종료 중 마지막 화면 유지,63초 메뉴다. 스크롤은14–17/21–29/34–39/53–57초에서 확인된다.

이는 **장면 분류**이며 영상의 고유 표시 프레임 수 측정이 아니다. CRT 촬영 띠·색상은 결함 판정에서 제외했다. 호스트 로그와 영상의 정확한 시작 offset이 없어5초 bin을 특정 장면에 정확히 대응시키지 않았다.

10ms 계측에서 receive bin합2241과 profile2240은 별도로 tick을 읽는다.453회의 성공 build에는 마지막 미완료SEAL의 build가 포함되므로452display로 나눈 값은 전체 비용을 나눈 평균이다. 실패한 최종 SEAL은 성공 시 누적하는 SEAL 시간에 전부 들어가지 않는다. 단계 합계를 완전한 wall-time 분할로 해석하지 않는다. 병렬 aperture DMA와 별도 오디오/service 트래픽은 wire 집계 밖이며 source miss·SNES VBlank는 아직 직접 계측하지 않는다.
