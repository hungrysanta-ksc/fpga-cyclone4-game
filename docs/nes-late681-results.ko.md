# 681: 늦은 tile 허용과 map 발행·DMA 우선권

실기 선택본은 **MMC666**이다. 이번 작업은680의 실제 E0 진행 알림·고정 인접 map과678 입력 credit 수정을 기준으로, 956의 남은512B와957 마지막384B를 생산·수락·DMA 시각으로 분리한다. 같은 시작7288416/7467100, 같은 ROM 달력, 실제 전체 링크 ARM·65816에서 비교한다. 한 화면의 최소 시간을 다른 구성의 최종 ACK와 합치지 않는다.

## 원인과 구현 경계

956에서 늦게 수락된 작은 tile도 기존 큰 tile과 같이232선 제한을 받았다. map은252선까지 허용하므로, 새 패킷이 없는 구간에서도 그 tile이 명령 목록 앞에 남았다. 기존160B 이하 분류만 실제 늦은 VBlank에 허용한다. map 최대1,152B·252선, 새 패킷/STOP 우선권, 실제 DMA 뒤 주소·길이 갱신은 유지했다. VBlank 자체나 크기 상수를 늘리지 않았다.

957은 BG48B가 준비돼 있어도 warm map 연속 발행의 `complete485` 우선 분기 때문에 E8 확인이 뒤로 갔다. 680의 실제 BG 수락은245/250선, 소비 ACK는255/259선이라 그 ACK 뒤의 빈 큐만으로 마지막384B를 선행 전송할 수 없다. ARM의 기존 bulk kind·offset으로 BG→OBJ 인계 경계를 확인하도록 변경했다. 새 문맥·타이머·고정 대기는 추가하지 않았다.

그러나 BG를 먼저 보낸다고 map DMA가 자동으로 빨라지지는 않았다. 넓은 BG 조회 후보는957 BG를118/116선에 수락했지만 마지막 map 수락이256/257선으로 늦어졌다. E1 데이터량은 같고957 E8 총량은 오히려260→220B이므로, 단순히 조회 바이트 증가만으로 설명할 수 없다. bulk 소비·credit과 후속 map의 발행 순서가 함께 바뀐 결과다.

이에 첫 zero BG의 인계만 먼저 처리하고, 이후의 비zero BG/OBJ는 기존 map 연속 발행으로 복귀하는 후보를 분리했다. 이어 늦은 VBlank에서 작은 tile이 이미 수락된 map을 밀어내는 문제를 확인해, **기존 map 선택을 먼저 유지하고 적격 map이 없을 때만 작은 tile을 실행**하는 결합 후보를 만들었다. frame 번호·위상별 지연이나 탐색 길이 변경은 사용하지 않는다.

## 안전·비용

- 작은 tile160B를252선 후반에 판단한 실제65816 경계 시험에서 마지막 write는255선이었다. map 우선 결합도252선 h1154 latch→254선 h714 DMA→255선 h700 마지막 write로 VBlank 안에 끝났다. 시험용 caller 대기 후 **원래 프로그램 전체 바이트를 복구·확인**하고 실제 beam/MDMA를 실행했다.
- STOP·새 패킷이 먼저 도착하면 DMA0B다. 진행 중 STOP은 현재 atomic DMA 뒤 멈추고 이전 표시를 보존한다. 원본128/16B tile의12개 경합·cold 복구,176B의 늦은 차단과128B의253선 차단,14개 map 경합/누락 검사와2개 최종 ACK 취소를 새 ROM별로 확인했다. 최대160B는 실제 수신 payload/descriptor를 함께 늘린 directed STOP 시험이며 그 수정 화면을 정상 게임 픽셀로 주장하지 않는다.
- 새 ARM 인계5조건과 기존 진행/identity/CRC/STOP28조건, 입력 credit9조건, 메뉴/base5조건·marker4조건을 실제 링크 코드에서 확인했다. 물리 메뉴 복귀 재시험은 아니다.
- ARM 넓은 BG 후보212844B/free148, 첫 zero 경계 후보212848B/free144다. data10040B/BSS19544B로680과 같고, `poll`64B·`progress`32B stack을 유지한다.
- 작은 tile 우선 ROM은 body5964B/physical spare2B, map 우선은 body5967B/physical spare0B다. 모두 같은5,120B 이미지이며 복원 바이트를 원본 body와 비교한다. persistent WRAM 추가0,680의DMA stack3B를 그대로 사용한다.
- FPGA 실행 RTL은680과 동일하다. 681 ROM이 들어간 보드 입력 manifest를 별도로 준비하고 전체 입력 hash를 대조한다. 기존680의 전체 MAP+35comb/+3FF/0RAM을 새 FIT 절감으로 쓰지 않는다. 실제 배치84LE·1LAB 여유는 새 ROM을 포함한 전체 FIT/STA 전에는 확정하지 않는다.

## 다음 순서

**채택하지 않고 MMC666을 유지한다.** 마지막 후보는957의 마지막384B를 위상1에서 실제로 선행 전송했지만, 총 선행 map은680과 같은1,664B다. 기존 offset1024의384B를 대신 남겼으므로 순절감으로 계산하지 않는다. 위상2는1,280B여서680보다384B 적고 마지막384B도 남는다. 956 선행 map은512/512→128/128B로 감소한다.

최종 후보에서956의 geometry는 직전 표시 ACK 전에7/6→5/5블록만 들어왔다. 일곱 번째 복원 완료는 직전 ACK보다1.722642/1.834977ms 뒤다. 첫 zero 수락이238/244→259/258선으로 늦고, 다음 BG48B 생산 완료는65887282→66095290 / 66253380→66452650 masterclock으로 늦었다. END 함수 자체의0.655823ms는 같다. 즉, 수신·공급 위상이 ROM 허용 창을 놓친 문제를 늦은 DMA 허용만으로 해결하지 못했다.

1. 680의 검증된 입력 credit 수정·진행 알림·고정 인접 map을 비교 근거로 유지하고,681 후보는 실기 선택하지 않는다. 첫 zero/BG 우선 적용 범위만 다시 넓히지 않는다.
2. 955 마지막 tile/ordinary 발행과 실제 D1/D2/D0 반환에서956 geometry7블록을 얼마나 앞당겨야 하는지 먼저 확정한다. 입력 완료·최종 표시 ACK identity를 분리한 기존 소유권을 유지한다. 첫 BG가 한 ROM 창을 놓쳐 생기는 지연 증폭을 분리한다.
3. 957은 offset1024의384B와 마지막3200의384B가 함께 남지 않는지 검사한다. 하나의 범위를 앞당기는 성과로 총 선행량 감소를 가리지 않는다. 새 패킷/STOP 우선권과 독립 검사를 유지한다.
4. Flash144B·body17B·packed ROM0B이므로 추가 관측/제어를 그냥 더하지 않는다. 기존 동작의 삭제·순비용과 두 위상 마감을 입증한 후에만 전체 Lite FIT/STA로 진행한다. 이번에는 보드 입력만 검증했고 새 합성·설치본·실기 FPS 측정은 없다.
