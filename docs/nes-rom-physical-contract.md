# NES052 physical ROM read / CDC contract

Candidate `NES-R1-ROM-PHYSICAL-052`. Hardware baseline remains044.

## Implemented path

Original `nes_rom_physical.sv` replaces the single-clock test backend with a read-only PSRAM pin controller in an independent memory clock domain. The source interface preserves051's ready-qualified grant, one outstanding request, physical response tag and byte data. Requests may be accepted on the same source edge as the previous response. The caller must only assert a grant when ready and keep ROM immutable until common reset.

Source address_hold and request toggle remain stable until completion. Two memory-clock synchronizer stages carry the toggle; the pin controller captures the bundled address only after observing stage2. Three memory clocks later it samples the selected byte and updates data_hold and ack_toggle. Two source-clock stages carry ack; response is consumed on a later source edge while data_hold stays stable. No independent data-bit synchronization or additional speculative address source is used. The next accepted request authorizes reuse of the holding registers. A clocked read-release interval precedes any subsequent pin access.

Common asynchronous reset cancels both directions and deasserts chip selects/OE immediately. Each clock domain releases through two local flops. Independent domain resets are unsupported. The caller must reset051 caches with this backend; there is no loader epoch, mutable-ROM invalidation, save retention or board recovery controller. A stopped memory clock leaves a request pending;051 retains its timeout/deadline response policy.

The diagnostic physical byte address is22bits: PRG0x000000–0x00FFFF, CHR0x200000–0x207FFF. Byte bit1 selects chip; pin address is byte[21:2] zero-extended to22bits; byte bit0 selects physical15:8 when zero,7:0 when one. This matches the byte layout observed in protected GBC rom_bus_bridge_save/psram_rw3_save references, which were not modified. Both byte enables are low for reads; WE is permanently high and this module never drives memory data. A future loader/ownership mux is required for writes.
