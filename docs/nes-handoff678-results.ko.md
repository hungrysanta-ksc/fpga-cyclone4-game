# 678: map→tile 전환과 다음 입력의 수신 예산

**957 위상1의 선행 map을512→1664B로 회복하고 마지막ACK 지연을+0.484→+0.01043ms로 줄였다. 그러나956의 선행DMA는 회복하지 못했고 두 위상 동시 개선 조건도 미달했다. 실기 기준은MMC666을 유지한다.**

677의 warm map 구간 우선권, 초기 zero/BG 허가와 후속 큰 plan 묶음을 유지했다. 956·957의 map 수락→후속 tile→빈 큐 DMA를 같은 작업량과 두 전체 시작 시각에서 비교했다. [최종 근거](../analysis/handoff678-verification.json) · [FINISH 전환 단독](../analysis/handoff678-input-verification.json) · [복수 tile 제한 대조군](../analysis/handoff678-multi-verification.json)

## 원인과 교체한 경계

677에서는956의 map 수락이 앞당겨졌어도 선행 map DMA가 원본640/512B에서128/128B로 감소했다. 957 위상1 역시 map512B를 선행한 뒤, 이미 수락된 offset2048의1536B를 남긴 채 후속 tile을 수락했다. STOP·새 패킷 우선 정책에 따라 빈 큐 DMA 기회가 끝났고, 뒤의 최종 업로드가 길어졌다. 956에서 넘긴0.347530ms와957 자체ACK의 약0.136423ms가 합쳐졌다. 추가 VBlank 횟수만으로는 이 차이를 설명할 수 없다.

새 경계는 새 tile descriptor를 실제로 E8에서 확인한 때다. 기존 bulk 토큰의 완료와 map 큐의 CRC·count·identity를 먼저 확인하고, descriptor를 기존 함수 stack에 유지한 채 다음 입력의 STATUS와 가능한 한 블록 READ/복원/POP을 실행한다. 이후 같은 descriptor를 E1로 발행한다. 실제 SNES가 DMA 선택·완료를 맡으며 map 수신 ACK를 DMA 완료나 최종 표시 ACK로 바꾸지 않는다. 새 타이머·고정 침묵 시간·세대별 조건·추가 버퍼는 없다.

처음 `input`은 FINISH에서만 이 전환을 적용했다. `multi`는 단일 BG16B/OBJ32B를 즉시 발행하도록 제한한 대조군이다. 이 둘은 의도한 수신 중첩보다 앞선 예산 관리 문제를 드러냈다.

**빈 D0도 한 블록으로 세는 오류를 수정했다.** 676에서 추가한 reason4가 `prefetch_left`를 poll 전에 차감했다. 678의 이른 조회에서는 다음 캡처가 준비되지 않아 D0만 반환했는데도7→6이 됐다. FINISH 단독 후보의911은 이전910 최종ACK 전에7블록 대신6블록만 받았고, 일곱 번째 D2는 ACK 뒤1.124/1.159ms로 밀렸다. 911 자체에서는 callback이 실행되지 않았는데도 검사 후 진입이221/222선으로 늦어져 VBlank를 하나 더 기다렸다. MMC666 실기에서 새로 발견한 오류라는 뜻은 아니며, 이번 선행 경로에서 드러난 문제다.

최종 `credit`은 READ 데이터 CRC·복원·D2 반환 확인까지 성공해 `next_token`이 바뀐 경우에만 예산을 차감한다. 빈 D0는 한번만 실행하고 반환하며 미래 캡처를 기다리지 않는다. 초기7블록 상한과 최종ACK→EA→새COMMIT 순서는 그대로다. 956의 후속 tile은 FINISH 이전의 마지막 E9 처리에서 나타났으므로, 조건을 END 발행 문맥(`ending`)으로 연결했다. 초기 BG plan 공급은 이 조건에 포함하지 않는다.

956 위상1은map 수락 시각이677과 정확히 같고, 후속tile을 약0.666ms 늦췄지만 빈 큐 DMA는 여전히128B뿐이다. SEAL은38.895→39.406ms로 늦어지고 업로드 VBlank 대기는7.838→7.349ms로 줄었으나, 실제DMA/나머지CPU 비용은 거의 그대로여서 표시가677보다0.02160ms 늦다. **956의0.348ms를 줄였다고 판정하지 않는다.**

957 위상1은232선tile16B,235선map384B 뒤241선map1152B를 추가로 보냈다. 그1152B가 최종 업로드에서 빠져 자체 표시 간격이0.358705ms 줄었다. 그러나956에서 물려받은0.369134ms가 남아 마지막ACK는 원본보다224 master clocks(0.010430ms) 늦다. 위상2는이전표시 지연0.179259ms보다 자체개선0.361964ms가커 마지막ACK가0.182705ms 빠르다. 전체ACK는67517582/67875496이다.

952는3회는 유지하지만 선행 map은677의1536/1152B에서1152/384B로 줄고, 같은VBlank 내부 표시 간격은677보다약0.258/0.239ms 길다. 큰묶음 유지와모든화면의서브프레임개선은같은주장이아니다.

**실제 다음 입력 복원 중첩은 아직0블록이다.** 최종 후보의새callback34/35회는모두미준비D0만반환했다. 각약0.105ms이며957 위상1에서한DMA가시작됐다. 이결과를수신복원과DMA를겹친성과로설명하지않는다. 다음수신예산을보존하고조회/발행시각을바꾼효과다. 53화면전체SPI는341819/342447B로MMC666대비1356/1300B적고677보다는260/240B많다. D1/D2/E1 payload량은같다.

두 전체 시작 시각은7288416/7467100 master clock이다. 같은 시작 시각이어도 앞선 화면의 처리 차이가 뒤의 ROM/VBlank 위상을 바꾸므로, 구간 자체 지연과 이전 표시에서 넘겨받는 지연을 나눴다. 밀집951–955 평균과957 마지막ACK를 별도 필수 조건으로 비교한다. 실제5–55초 실기 FPS나 출력26.84ms를 모델의 개선 비율로 환산하지 않는다.

## 검사·메모리·보드 비용

- 각 바이너리에서 map 구간13조건, 마지막 큰 묶음7조건, 초기 grant12조건, END9조건, 입력8+map-tail5조건, routing12조건과 메뉴5조건/marker4조건을 검사했다.
- 새 전환은 cold·직전tile·반복token·descriptor 세대·E8/E0 CRC·credit·identity·입력 실패·STOP·counter wrap·단일/복수 BG·OBJ를 검사했다. 최종 후보는 마지막 E9/FLUSH의 정상·직전tile·STOP도 포함해18조건이다. 입력 callback을 대신한 경계 검사와 실제 runtime callback 검사를 구분했다.
- 실제 callback9조건은 빈 D0 두 번 뒤 실제 READ,65535→0 token 순환, 완료된 입력, READ 전/후STOP,CRC·POP반환·IO 실패를 포함한다. 실패 때 새 tile·D3·EA를 발행하지 않는다. 완료된 표시 이력 없이 최종ACK를 만들지 않는다.
- Flash는 `input`212776B/free216B, `multi`212804B/free188B, `credit`212800B/free192B다. 677 대비 최종후보+76B다. data10040/BSS19544B와 추가static RAM0B는 같다. `poll` 함수 stack56→64B, `progress`32B·`wait634`24B는 같으며 전체 호출 stack 상한을 새로 입증한 값은 아니다.
- FPGA·65816 바이트는665/MMC666과 같다. 전체15324LE·962LAB·56M9K, setup+0.511/hold+0.149/recovery+1.828/removal+0.393ns의 기존 전체 FIT/STA를 재사용했다. 새 회로 절감·새 합성·실기 메뉴 복귀를 시행했다는 뜻은 아니다. 메뉴/STOP 검사는 실제 ARM의 기존 준비·해제 경로를 대상으로 했다.

실행은 actual linked Cortex-M4·65816에CPI2, 실제 SysTick 코드의 경계 dispatch, 공유SPI 드라이버 비용과 반복 ROM 허가 달력을 적용했다. 전체 live NES/PSRAM·물리 IRQ 지연·외부IO 전체 sign-off·60fps 증명은 아니다. 게임ROM·save·RESTORE·MMC666 설치본은 변경하지 않았다.

## 재현과 다음 단계

`prepare_nes_handoff678.py <677 run01> <새 폴더>`는 base firmware hash를 확인한다. 기본 `input`, `--multi`, `--credit`을 각각 새 폴더에 생성하고 `build_nes_trial577.ps1`로 전체 링크한다. `check_nes_handoff678.py`에 대응 옵션을 주고 최종 후보는 `check_nes_credit678.py`를 추가한다. 실제 재생 인자는 private `probes/nes-handoff678/replay.ps1`, `multi-replay.ps1`, `credit-replay.ps1`에 보존했다. ASCII Temp의 `nes-handoff678-{input,multi,credit}{1,2}`가 원시 결과다.

`analyze_nes_handoff678.py --tag input|multi|credit`는 같은 작업량·보호선·수락 범위 안의 실제 DMA·다음 입력 예산·최종ACK·바이너리·자원을 대조한다. [보관 요약](../analysis/handoff678-archive.json)은 실패 로그를 포함한 소스·ELF·펌웨어·원시 재생의 byte hash와 압축 해제 후 검증을 연결한다. 저장소에는 재현 도구와 분석만 넣고 게임 데이터·도구·private 실행 산출물은 넣지 않는다.

다음은 **956의실제DMA완료를ARM이알수있는최소경계와삭제예산을먼저확정**한다. 678의수신예산수정은유지할근거가있지만,모든선행조회/발행변경을제품에채택하지않는다. 677/678의같은시작·같은범위로956의마지막map수락약27.73ms→다음VBlank약32–34ms→후속tile소비를고정대기가아닌실제완료이벤트로연결할수있는지판정한다. 단독D0삽입·묶음크기·위상별상수의추가탐색은보류한다.

기존665의bus는빈큐에서ACK write/publish를허용하지않고,endpoint는ACK를검사한뒤queue를retire한다. 따라서기존ACK를DMA완료알림으로재사용하면안된다. 새로운진행표시는기존packet ACK·최종display ACK와분리하고,현재표시serial/generation·bank·범위에묶어STOP/부분전송/cold에서무효화해야한다. 오래된완료나동기화지연이새tile을허가해서는안된다.

사전예산상한은선택본기준84LE·1LAB·0M9K·ARM496B·압축SNES ROM11B이며,678을합치면ARM192B뿐이다. 기존E0거래에얹을경우추가wire0B는**설계목표**일뿐검증된절감이아니다. SNES의DMA후공개명령·FPGA latch/identity/CRC snapshot·ARM검사및응답왕복을모두계상하고,대체할기존제어를찾지못하면새RTL/FIT반복을시작하지않는다. 이문서에서는진행인터페이스구현이나회로적합을주장하지않는다. 두위상의911/951/952/957조건과밀집간격·마지막ACK동시개선전에는새ZIP을전달하지않는다.
