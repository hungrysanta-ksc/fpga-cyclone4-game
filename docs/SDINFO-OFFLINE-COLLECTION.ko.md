# SD 파일 직접 수집 — 074 실기 실패 이후

## 현재 판단

사용자는074 실행에서 `HW005000.TXT`0바이트·화면 없음과 카트리지 LED가 외부에서 보이지 않음을 확인했다. 본체의 붉은 전원 램프는074의 Ready/Read/Write 진단 출력이 아니다. 외부 가시성을 확인하지 않고 전달한 LED 진단은 이 사용 환경에서 사용할 수 없다. **074 재시험·LED 영상 요청·기판 분해를 중단한다.** 과거074 안내와 패키지는 당시 구현 기록이며 현재 권장 절차가 아니다.

현재 수집 함수는 SD의 고정 파일4개를 읽어 파일 크기/CRC/압축 복원 정보/메뉴 헤더와 reset byte를 추출한다. 이 정보는 파일 사본에서 동일하게 구할 수 있다. 따라서 이 단계에서 실기 실행이나 새 펌웨어는 필요하지 않다. SD 파일 정보 확보와 STM32의 실제 SD 쓰기 오류 해결을 분리한다.

## 전달할 파일

전원을 끈 뒤 SD를 평소 파일을 복사하는 환경에서 열고, `sd2snes` 폴더의 아래 파일을 **PC의 별도 폴더로 복사하여 ZIP으로 묶어** 전달한다. 카트리지 자체를 PC에 연결하는 요청이 아니다. SD 파일을 이동·수정하거나 전체 게임/세이브를 포함할 필요가 없다.

| 파일 | 분석 목적 |
| --- | --- |
| `firmware.before-sdinfo072.stm` | 진단 펌웨어를 넣기 전 원본 펌웨어 사본 |
| `firmware.stm` | 현재 SD에서 실행 중인 펌웨어 식별 및 원본과 구분 |
| `fpga_base.bi3` | 실제 기본 FPGA 파일의 RLE 복원 정보 |
| `m3nu.bin` | 실제 메뉴의 크기·후보 헤더·reset 경로 |

파일 이름은 `menu.bin`이 아니라 **`m3nu.bin`**이다. 없는 파일은 새로 만들거나 이름을 바꿔 대체하지 말고, 없다고 알려준다. 특히 원본 사본이 없으면 현재074 `firmware.stm`을 원본 사본으로 복사하지 않는다. 다른 위치에 보관한 진단 이전 원본이 있다면 그 출처를 설명하고 별도 이름으로 포함할 수 있다. 개인정보나 게임·세이브 파일은 요청하지 않는다.

현재 진단 펌웨어를 교체하기 전에 위 사본을 확보하면 실행 이미지 확인에도 도움이 된다. 이후 전원이 꺼진 상태에서 기존 독립 백업의 **확인된 원본 firmware**를 복원한다.074를 다시 실행할 이유는 없다. 원본을 찾을 수 없으면 임의의 다른 펌웨어로 복원하지 않는다.

## 분석과 다음 완료 조건

수신한 파일마다 크기와 SHA256/CRC를 기록하고 원본/현재 진단 이미지를 구분한다. 기존 수집기의 고정4경로·크기한도·압축 복원·메뉴6헤더/reset 추출을 파일 사본에 적용하고 actual menu 분류 코드와 대조한다. 파일 수집만으로 원본 복원·메뉴/GBC 재실행·CF68 설치·실기 SD 드라이버 성공을 승인하지 않는다.

074 저장 오류의 정확한 원인은 여전히 미확정이다. 파일 내용 분석은 그 원인 증명이 아니다. 실제 SD 쓰기 경로가 필요해질 때에는 성공했던 HWINFO002의 하위 쓰기와 현재 bounded 경로를 차등 분석하고 actual command/data/CRC/busy를 모델링해 인과 대조를 만든다. 공유 오류 뒤 SD/SPI 재접근·불확실 쓰기 재시도·무제한 legacy fallback으로 보호를 우회하지 않는다. 새 실기 테스트는 사용자가 실제로 관측할 수 있는 결과와 로컬 검증이 갖춰진 뒤에만 제안한다.
